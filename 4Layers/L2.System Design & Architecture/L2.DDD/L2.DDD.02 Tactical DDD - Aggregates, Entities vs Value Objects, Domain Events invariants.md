**TL;DR**:
*   **Value Objects** — это ваша главная защита от "Primitive Obsession". Используйте их везде, где нет жизненного цикла.
*   **Entities** — нужны только там, где важна история изменений и идентичность.
*   **Aggregates** — это **границы транзакций**, а не просто графы объектов. Главное правило практика: делайте агрегаты максимально маленькими.
*   **Domain Events** — способ разорвать жесткую связность между агрегатами (Eventual Consistency).

На уровне Practitioner вы перестаете думать таблицами базы данных (`UserTable`, `OrderTable`) и начинаете думать поведением и инвариантами.

## 1. Value Objects (Объекты-значения): Семантическое ядро системы

Для Staff Architect Value Object — это не просто паттерн проектирования, это способ создания **системы типов предметной области**.

Если Entities (Сущности) отвечают за **"Кто?"** (Идентичность, Жизненный цикл), то Value Objects отвечают за **"Какой?"** и **"Сколько?"** (Характеристики, Меры, Описания).

### 1.1. Фундаментальные характеристики (Deep Dive)

Чтобы объект считался истинным VO, он должен удовлетворять трем строгим критериям. Если нарушен хотя бы один — вы создаете бомбу замедленного действия.

#### A. Структурное равенство (Structural Equality)
Два объекта равны не потому, что занимают одну ячейку памяти (identity equality), а потому, что их **значения** совпадают.
*   **Термин:** *Conceptual Whole* (Концептуальное целое).
*   **Пояснение:** $5 долларов в моем кошельке и $5 долларов в вашем — это одни и те же "пять долларов" с точки зрения их ценности. Нам не важно, разные ли это купюры, нам важен номинал.
*   **В коде:** Вы обязаны переопределить `equals()` и `hashCode()`, опираясь на все поля объекта.

#### B. Неизменяемость (Immutability)
Это критическое требование для многопоточных и распределенных систем.
*   **Правило:** После вызова конструктора состояние VO не может быть изменено. Сеттеров (`setSomething`) не существует.
*   **Зачем это Архитектору:**
    1.  **Thread Safety:** VO можно безопасно передавать между потоками без синхронизации.
    2.  **Caching/Hashing:** VO можно безопасно использовать как ключи в `HashMap` или в кэшах (Redis).
    3.  **Отсутствие побочных эффектов:** Передавая VO в чужой метод, вы гарантируете, что метод не изменит данные "под капотом".

#### C. Самовалидация (Self-Encapsulated Validation)
VO — это барьер для некорректных данных.
*   **Концепция "Always Valid":** Невозможно создать экземпляр VO, который нарушает бизнес-правила. Валидация происходит **только** в момент создания (в конструкторе или фабричном методе).
*   **Разница с валидацией DTO:** DTO проверяет формат ("строка не пустая"). VO проверяет смысл ("дата окончания не может быть раньше даты начала").

### 1.2. Поведение: Value Objects как "Притягатели логики"

Самая большая ошибка — делать VO "тупыми" контейнерами данных. VO должны содержать **чистые функции (Pure Functions)** и **комбинаторы**.

**Термин:** *Side-Effect Free Function* — функция, которая не меняет состояние объекта и не взаимодействует с внешним миром (БД, сеть), а возвращает **новый** экземпляр VO или примитив.

#### Пример: `TimeRange` (Временной интервал)
Представьте, что вам нужно проверить, пересекаются ли две встречи.

**Плохой подход (Primitive Obsession + Anemic):**
```java
// Логика размазана по сервису
if (meetingA.start < meetingB.end && meetingA.end > meetingB.start) {
    // пересечение...
}
```

**Подход Practitioner (Rich Value Object):**
```java
public final class TimeRange {
    private final LocalDateTime start;
    private final LocalDateTime end;

    public TimeRange(LocalDateTime start, LocalDateTime end) {
        if (end.isBefore(start)) throw new IllegalArgumentException("End cannot be before Start");
        this.start = start;
        this.end = end;
    }

    // Чистая функция: возвращает boolean, ничего не меняет
    public boolean overlaps(TimeRange other) {
        return this.start.isBefore(other.end) && this.end.isAfter(other.start);
    }

    // Комбинатор: возвращает НОВЫЙ Value Object
    public TimeRange intersection(TimeRange other) {
         if (!overlaps(other)) throw new DomainException("No intersection");
         return new TimeRange(
             max(this.start, other.start),
             min(this.end, other.end)
         );
    }
}
```
**Результат:** Вся сложная математика времени инкапсулирована и протестирована один раз внутри `TimeRange`. Сервисный слой просто вызывает `rangeA.overlaps(rangeB)`.

### 1.3. Архитектурная борьба с "Одержимостью примитивами" (Primitive Obsession)

Primitive Obsession — это использование стандартных типов языка (`int`, `string`, `double`) для моделирования понятий предметной области.

**Почему это плохо для Senior Architect:**
1.  **Ложная совместимость:** Если `UserId` — это `UUID`, и `OrderId` — это `UUID`, компилятор позволит вам передать ID заказа в метод, ожидающий ID пользователя. Это баг, который сложно отловить.
2.  **Дублирование инвариантов:** Если "Телефон" — это `String`, вам придется писать `RegEx` проверку в каждом месте, где этот телефон используется (в контроллере, в сервисе, в сущности).

**Решение:**
Оборачивайте примитивы. Даже если класс содержит всего одно поле.
*   `class PhoneNumber` (внутри string + regex validation)
*   `class Temperature` (внутри double + unit validation)
*   `class ZipCode` (внутри string)

**Цена:** Небольшой оверхед на создание объектов (в современных JVM/Runtime он ничтожен благодаря Escape Analysis).
**Выигрыш:** Компилятор проверяет бизнес-логику за вас. Вы не можете сложить `Temperature` и `ZipCode`.

### 1.4. Value Objects и Персистентность (Mapping)

Как хранить VO в базе данных?

1.  **Flattening (Embedding):**
    Самый частый паттерн. Поля VO "раскладываются" в колонки родительской таблицы сущности.
    *   В Java JPA: `@Embeddable` / `@Embedded`.
    *   *Пример:* В таблице `users` будут колонки `address_city`, `address_street`, `address_zip`. В коде это один объект `Address`.
2.  **Serialization (JSON/Blob):**
    Если VO сложный (например, список характеристик товара), его можно сохранить как JSON в одной колонке (`jsonb` в Postgres).
    *   *Плюс:* Гибкость.
    *   *Минус:* Сложно искать по внутренним полям (если БД не умеет индексировать JSON).
3.  **Separate Table (Антипаттерн для VO):**
    Если вы сохраняете `Address` в отдельную таблицу `addresses` с ID, и делаете `One-To-One` связь — вы технически превратили VO в Entity. Делайте это только если вам *действительно* нужно ссылаться на этот адрес из других мест или отслеживать его изменения отдельно.

### Резюме раздела
Value Object — это **неизменяемый** контейнер данных и логики, который определяется своим **значением**, а не идентификатором. Использование VO переносит сложность валидации и вычислений из "жирных" сервисов в компактные, легко тестируемые классы, делая архитектуру устойчивой к ошибкам.

## 2. Entities (Сущности): Идентичность и Жизненный цикл

Если Value Object отвечает на вопрос **«Какой?»** (описание характеристик), то Entity отвечает на вопрос **«Кто?»** (уникальность и история).

Сущность — это не просто контейнер данных. Это модель процесса или актора, имеющая **Identity (Идентичность)**, которая переживает изменения всех остальных атрибутов.

### 2.1. Фундаментальный принцип: Идентичность (Identity)

Идентичность — это стержень сущности.

1.  **Отделение ID от атрибутов:**
    Если у пользователя изменилось имя, адрес и даже пол — это всё тот же пользователь. В отличие от Value Object (где изменение поля означает новый объект), Сущность обязана сохранять ссылочную целостность.
2.  **Контракт `equals()`:**
    Две сущности равны **тогда и только тогда**, когда равны их ID (и они принадлежат одному типу). Состояние остальных полей игнорируется при сравнении.
    *   *Пример:* `User(id=1, name="Alice")` **равен** `User(id=1, name="Bob")`. Это один и тот же человек, данные которого рассинхронизировались (или это разные версии объекта во времени).

#### Стратегии генерации ID (Architecture Decision)
Архитектор должен выбрать стратегию создания ID *до* написания кода, так как это влияет на производительность и распределенность.

*   **Surrogate Identity (Суррогатный ключ):**
    *   *UUID/GUID:* Генерируется приложением. **Рекомендация DDD.** Позволяет создать валидную сущность и ее ID *до* сохранения в базу. Идеально для распределенных систем и шардинга.
    *   *DB Sequence (Auto Increment):* Генерируется базой данных. **Антипаттерн в DDD.** Вы не знаете ID сущности, пока не сохраните её. Это нарушает инварианты (сущность без ID невалидна) и заставляет писать лишний код для получения ID.
*   **Natural Identity (Естественный ключ):**
    *   Использование email, SSN (номер соцстрахования), ISBN в качестве ID.
    *   **Риск:** Естественные ключи *меняются*. Люди меняют фамилии, компании меняют налоговые номера. Изменение Primary Key в БД — это боль. Используйте суррогатные ID для связей, а естественные — как уникальные атрибуты.

---

### 2.2. Изменчивость (Mutability) и Управление состоянием

В отличие от неизменяемых (Immutable) Value Objects, Сущности **изменяемы (Mutable)**. Но эта изменчивость должна быть строго контролируемой.

#### Понятие "Конечный автомат" (State Machine)
Рассматривайте каждую сущность как конечный автомат. У неё есть текущее состояние (State) и разрешенные переходы.

**Антипаттерн (Anemic Setter):**
```java
order.setStatus("SHIPPED"); // Никакой проверки. Можно отправить отмененный заказ?
order.setShippedDate(null); // Нарушение целостности.
```

**Practitioner Approach (Rich Behavior):**
Сущность предоставляет **методы-действия**, которые инкапсулируют бизнес-правила перехода.
```java
public class Order {
    private OrderId id;
    private OrderStatus status;
    private List<OrderItem> items;

    // Метод выражает Ubiquitous Language ("Ship", а не "SetStatus")
    public void ship(TrackingNumber tracking) {
        if (this.status != OrderStatus.PAID) {
            throw new DomainException("Cannot ship unpaid order.");
        }
        if (this.items.isEmpty()) {
            throw new DomainException("Cannot ship empty order.");
        }
        
        this.status = OrderStatus.SHIPPED;
        // Публикация доменного события
        this.addDomainEvent(new OrderShippedEvent(this.id, tracking));
    }
}
```

### 2.3. Локальные сущности vs Корни агрегата

Не все сущности равны. Важно различать **Aggregate Root** (Корень) и **Local Entity** (Локальная сущность).

*   **Aggregate Root (Global Identity):** Имеет глобально уникальный ID. К нему можно обратиться напрямую через Репозиторий (`repo.findById()`). Пример: `Order`.
*   **Local Entity (Local Identity):** Имеет ID, но он уникален *только внутри* родителя. Не имеет смысла без родителя.
    *   *Пример:* `OrderItem` (Позиция заказа).
    *   У `OrderItem` может быть ID (для БД), но вы никогда не делаете запрос `OrderItemRepository.findById()`. Вы делаете `Order.getItems()`.
    *   Жизненный цикл локальной сущности полностью управляется корнем. Если удаляется `Order`, каскадно удаляются все `OrderItem`.

---

### 2.4. Валидация Сущностей

В отличие от Value Objects, которые валидны по определению ("всегда"), Сущность может находиться в процессе изменения.
Однако, **транзакционная целостность** требует, чтобы в конце транзакции (при сохранении) сущность была в валидном состоянии.

1.  **Инварианты:** Правила, которые должны быть истинны всегда. (Например, "В активном заказе должен быть минимум один товар").
2.  **Контекстная валидация:** Правила, зависящие от фазы. (Например, "При создании черновика адрес не обязателен, но при переводе в статус `CONFIRMED` адрес обязан быть заполнен").

### 2.5. Пример: Разница мышления

**Задача:** Спроектировать систему управления задачами (Task Tracker).

**Подход Data-Driven (Неверный):**
*   Таблица `Tasks`.
*   Класс `Task` с полями `Id`, `Title`, `AssigneeId`, `DueDate`.
*   Сервис `TaskService`, который меняет поля через сеттеры.

**Подход DDD Entity (Верный):**
*   Сущность `Task` с четким жизненным циклом.
*   Поля:
    *   `TaskId` (Strongly typed ID - Value Object).
    *   `Title` (непустая строка).
    *   `TaskStatus` (Todo -> InProgress -> Done).
*   Поведение:
    *   `assignTo(User user)` — проверяет, не заблокирована ли задача.
    *   `complete()` — проверяет, есть ли исполнитель. Если исполнителя нет, задачу нельзя закрыть.
    *   `postpone(DueDate newDate)` — метод переноса срока (бизнес-действие), а не просто `setDueDate`.

### Резюме раздела
**Entity** — это модель актора с **непрерывной историей**.
Главная ответственность архитектора при проектировании Сущностей:
1.  Выбрать стратегию **Identity** (предпочтительно UUID на клиенте/в коде).
2.  Запретить прямые сеттеры (`setX`) и заменить их на **методы-действия** (`doX`), защищающие инварианты.
3.  Четко разделить сущности на **Глобальные (Roots)** и **Локальные**, чтобы не создавать лишних Репозиториев.

## 3. Aggregates (Агрегаты): Граница транзакции и Конкурентности

Агрегат — это кластер (группа) связанных объектов (Сущностей и Value Objects), которые мы рассматриваем как **единое целое** с точки зрения изменения данных.

Если Сущность — это модель *чего-то* (User, Order), то Агрегат — это техническая граница, определяющая, *как* мы это сохраняем и защищаем.

### 3.1. Анатомия Агрегата: Корень и Граница

Агрегат состоит из двух концептуальных частей:
1.  **Aggregate Root (Корень агрегата):** Это единственная Сущность внутри кластера, которая имеет **глобальный идентификатор**.
    *   *Правило:* Внешний мир (Сервисы, Контроллеры, другие Агрегаты) может ссылаться **только** на Корень. Доступ к внутренним объектам (например, `OrderItem`) возможен только через методы Корня (`Order`).
    *   *Аналогия:* Корень — это API-шлюз для внутренних данных агрегата.
2.  **Boundary (Граница):** Воображаемая линия, очерчивающая, что входит в транзакцию. Всё, что внутри границы, загружается из БД целиком и сохраняется целиком.

### 3.2. Главное правило: Агрегат = Граница транзакции

Это правило, которое нарушают чаще всего.
**Правило:** Одна транзакция базы данных должна менять **только один** экземпляр агрегата.

*   **Почему это важно:**
    *   Если вы меняете 10 агрегатов в одной транзакции, вы держите блокировки (Row Locks) на 10 таблицах/строках. Это убивает пропускную способность (Throughput) и ведет к Deadlocks.
    *   В микросервисной архитектуре или NoSQL (MongoDB, Cassandra) транзакции часто ограничены одним документом (агрегатом). DDD готовит вас к шардингу.

*   **Что если нужно изменить два агрегата?**
    *   Используйте **Eventual Consistency** (Согласованность в конечном счете).
    *   Агрегат А меняется $\to$ Публикует событие $\to$ Агрегат Б слушает событие и меняется.

### 3.3. Эвристика проектирования: Размер имеет значение

Архитектор постоянно балансирует между двумя силами: **Удобство** vs **Конкурентность**.

#### Антипаттерн: Гигантские Агрегаты (God Aggregates)
Желание объединить всё, что логически связано.
*   *Пример:* Агрегат `Product` содержит список `List<Review>` (тысячи отзывов).
*   **Проблема производительности:** Чтобы изменить цену товара (`Product`), ORM/DB загрузит в память все 5000 отзывов.
*   **Проблема конкурентности (Lock Contention):** Если Пользователь 1 добавляет отзыв, а Менеджер меняет описание товара — они не смогут сделать это одновременно, так как оба блокируют одну строку `Product` (через Version/Lock).
*   **Решение:** Вынести `Review` в отдельный агрегат. Связать по `productId`.

#### Правило Staff Engineer:
> "Проектируйте агрегаты настолько маленькими, насколько это возможно, сохраняя истинные инварианты."

### 3.4. Инварианты: Истинные vs Бизнес-правила

Как понять, нужно ли объединять объекты в один агрегат? Проверьте тип инварианта.

1.  **Истинный инвариант (Транзакционный):** Правило должно быть соблюдено в ту же секунду.
    *   *Пример:* "Позиция заказа не может существовать без Заказа".
    *   *Решение:* `OrderItem` — часть агрегата `Order`.
2.  **Бизнес-правило (Эвентуальное):** Правило может быть проверено с задержкой в миллисекунды.
    *   *Пример:* "Количество заказов одного клиента не может превышать 10".
    *   *Ошибка:* Делать агрегат `Customer` со списком `Orders`.
    *   *Решение:* Два агрегата (`Customer`, `Order`). Проверка лимита через запрос в БД (`count(*)`) или асинхронный валидатор (Saga). Риск того, что пользователь успеет сделать 11-й заказ в ту же миллисекунду, принимается бизнесом ради производительности.

### 3.5. Ссылки между агрегатами: ID Only

Это самый контринтуитивный момент для тех, кто привык к JPA/Hibernate `@OneToMany`.

**Правило:** Агрегаты ссылаются друг на друга **только по ID**, никогда по объектной ссылке.

*   **Плохо (JPA Style):**
    ```java
    class Order {
        @ManyToOne
        private Customer customer; // Жесткая связь
    }
    ```
    *Риск:* Случайный вызов `order.getCustomer().changeAddress(...)` внутри транзакции заказа приведет к изменению Клиента. Это неявный побочный эффект.

*   **Хорошо (DDD Style):**
    ```java
    class Order {
        private CustomerId customerId; // Ссылка по ID
    }
    ```
    *Плюс:*
    1.  Границы транзакции очевидны. Вы не можете случайно изменить Клиента.
    2.  Позволяет разнести `Order` и `Customer` в разные микросервисы или разные БД в будущем без переписывания кода.
    3.  Меньше потребление памяти (нет Lazy Loading графа на полбазы).

### 3.6. Управление конкурентным доступом (Concurrency Control)

Агрегат не будет работать без механизма блокировок.

*   **Optimistic Locking (Оптимистичная блокировка):**
    Стандарт де-факто. В корне агрегата есть поле `version`.
    1.  Читаем Агрегат (version=1).
    2.  Меняем в памяти.
    3.  Сохраняем: `UPDATE ... SET version=2 WHERE id=... AND version=1`.
    4.  Если записей обновлено 0 (кто-то успел изменить версию на 2) — бросаем исключение и просим пользователя повторить.
*   Это гарантирует, что бизнес-инварианты, проверенные в памяти, не протухли на момент записи в БД.

### Резюме раздела
**Агрегат** — это механизм защиты данных в конкурентной среде.
1.  **Корень** управляет доступом.
2.  **Граница** определяет размер транзакции.
3.  **Ссылки по ID** предотвращают создание монолитного "клубка" объектов.
4.  **Маленький размер** агрегата — залог высокой масштабируемости системы.

## 4. Invariants (Инварианты)

Инвариант — это бизнес-условие, которое должно оставаться истинным **всегда** после завершения транзакции.
В отличие от валидации (которая проверяет *формат* данных), инвариант проверяет *состояние* и *бизнес-смысл*.

### 4.1. Валидация vs Инварианты
Важно различать эти понятия, так как они живут в разных слоях приложения.

1.  **Валидация (Stateless / Context-Free):**
    *   Проверяет правильность формата атрибутов.
    *   *Пример:* "Email должен содержать @", "Цена не может быть отрицательной".
    *   *Где живет:* В конструкторах **Value Objects** или на уровне DTO.
    *   *Характеристика:* Не зависит от текущего состояния системы (БД). $5 всегда $5.
2.  **Инвариант (Stateful / Context-Dependent):**
    *   Проверяет возможность изменения, основываясь на *текущем* состоянии агрегата.
    *   *Пример:* "Нельзя отменить заказ, который уже доставлен", "Нельзя снять со счета больше, чем там есть".
    *   *Где живет:* В методах сущностей (Entities) и корня Агрегата.
    *   *Характеристика:* Зависит от истории (State).

---

### 4.2. Типология Инвариантов: Проектирование Границ

Тип инварианта определяет размер вашего Агрегата. Это **лакмусовая бумажка** при проектировании.

#### А. Транзакционные Инварианты (Strong Consistency)
Это правила, нарушение которых делает систему **некорректной** даже на долю секунды.

*   **Требование:** Данные, участвующие в правиле, должны находиться внутри **одного** Агрегата и сохраняться атомарно.
*   **Пример:** "Минимальная сумма заказа для бесплатной доставки — $50".
    *   *Анализ:* Чтобы это проверить, мы должны знать сумму всех позиций (`OrderItems`).
    *   *Вывод:* Мы не можем добавлять `OrderItem` в БД отдельно от `Order`. `OrderItem` обязан быть частью агрегата `Order`, чтобы пересчет суммы и проверка условия произошли под одним локом базы данных.

#### Б. Эвентуальные Инварианты (Eventual Consistency)
Это правила, которые бизнес *хотел бы* видеть строгими, но техническая цена (блокировки, производительность) слишком высока. Мы допускаем временную несогласованность.

*   **Требование:** Данные могут быть в разных Агрегатах. Согласованность достигается через задержку (секунды/минуты).
*   **Пример:** "В инвентаре не может быть продано товара больше, чем есть на складе".
    *   *Наивный подход (Транзакционный):* В одной транзакции обновлять `Order` и декрементировать `InventoryItem`.
    *   *Проблема:* `InventoryItem` ("iPhone 15") становится "горячей точкой". Все покупатели блокируют одну строку склада. Очередь, тайм-ауты, провал продаж в "Черную пятницу".
    *   *Решение (Эвентуальное):*
        1.  Агрегат `Order` создается свободно (Optimistic success).
        2.  Асинхронно отправляется событие `OrderCreated`.
        3.  Агрегат `Inventory` получает событие и пытается списать товар.
        4.  Если товара нет — срабатывает **Компенсирующее действие**.

---

### 4.3. Компенсирующие действия (Compensating Actions)

Если вы выбираете Эвентуальные Инварианты, вы **обязаны** спроектировать путь отката. Система не может просто "зависнуть" в невалидном состоянии.

**Сценарий:** Заказ создан, но на складе пусто (рассинхрон).
1.  **Бизнес-решение:** Отменить заказ и отправить email с извинениями? Или поставить заказ в статус `Backlog` (ждет поставки)?
2.  **Реализация:**
    *   Сервис Склада публикует событие `StockReservationFailed`.
    *   Сервис Заказов слушает его и выполняет команду `Order.cancel("Out of stock")`.
    *   Это называется паттерном **Saga**.

---

### 4.4. Инварианты Уникальности (Set Validation)

Специфический тип инварианта: "Email пользователя должен быть уникальным".

*   **Ловушка:** Многие пытаются проверить это внутри агрегата `User`. Но агрегат `User` видит только *себя*. Он не видит других пользователей.
*   **Неверное решение:** Создать мега-агрегат `AllUsersList` (блокировка всей системы при каждой регистрации).
*   **Верное решение 1 (Техническое):** Уникальный индекс в базе данных (`UNIQUE CONSTRAINT`). Пусть БД выбросит исключение, а приложение его обработает.
*   **Верное решение 2 (Выделенный сервис):** Отдельный микро-сервис (или таблица) `EmailRegistry`, который занят только резервированием email-адресов (Lookup table).

### 4.5. Пример: Игра в Покер

Представьте агрегат `PokerTable`.

1.  **Транзакционный инвариант:** "Сумма фишек у всех игроков + Банк на столе = Константа (сколько было на начало раздачи)".
    *   *Решение:* Игроки и Банк должны быть частью одного агрегата `Table` во время раздачи. Нельзя снять фишки у игрока и не положить их в банк атомарно.
2.  **Эвентуальный инвариант:** "Игрок не может играть за двумя столами одновременно".
    *   *Решение:* Сделать это транзакционным сложно (нужно блокировать все столы мира). Проще проверить это асинхронно и "кикнуть" игрока с одного из столов, если обнаружено нарушение.

### Резюме раздела
**Инвариант** — это закон вашего Домена.
*   Если закон должен соблюдаться мгновенно — это диктует границы **одного Агрегата**.
*   Если закон может быть соблюден с задержкой — это диктует использование **Eventual Consistency** и **Sagas**.
*   Задача архитектора — убедить бизнес, что большинство "строгих" правил на самом деле могут быть эвентуальными ради масштабируемости.

## 5. Domain Events (Доменные события): Клей системы

Доменное событие — это запись о том, что **что-то важное уже произошло** в предметной области.
Ключевые слова:
1.  **Неизменяемость (Immutable):** Прошлое изменить нельзя.
2.  **Прошедшее время (Past Tense):** Имя события всегда отражает свершившийся факт. Не `CreateOrder`, а `OrderCreated`.
3.  **Бизнес-значимость:** Не каждое изменение поля — событие. `AddressCorrected` — это событие, а исправление опечатки в логе — нет.

### 5.1. Внутренние vs Интеграционные события (Internal vs Integration)

Это архитектурное различие критически важно для предотвращения **Leakage of Encapsulation** (Утечки инкапсуляции).

#### А. Внутренние события (Domain Events)
*   **Область действия:** Внутри одного Bounded Context (часто внутри одного процесса/монолита).
*   **Цель:** Запустить побочные эффекты в *других* агрегатах того же контекста (Eventual Consistency).
*   **Состав:** Могут содержать полные Доменные Сущности (поскольку получатель находится в том же контексте и знает модель).
*   **Транспорт:** In-Memory шина (Spring ApplicationEvents, Guava EventBus, MediatR).

#### Б. Интеграционные события (Integration Events)
*   **Область действия:** Между разными Bounded Contexts (Микросервисами).
*   **Цель:** Уведомить внешний мир.
*   **Состав:** **Никогда** не должны содержать внутренние сущности. Это должен быть чистый, стабильный DTO (Published Language). Если вы измените поле в БД, вы не должны сломать внешних потребителей.
*   **Транспорт:** Message Broker (Kafka, RabbitMQ, SNS/SQS).

**Пример архитектора:**
1.  Агрегат `Order` публикует внутреннее событие `OrderPlaced` (с объектами `User` и `Items`).
2.  Обработчик внутри того же сервиса перехватывает его, конвертирует в плоский JSON-контракт `PublicOrderPlaced` и кладет в Kafka для сервиса Доставки.

---

### 5.2. Паттерны наполнения (Event Enrichment)

Сколько данных класть в событие?

1.  **Thin Event (Тонкое событие / Notification):**
    *   *Payload:* `{ "orderId": "123", "eventType": "OrderPlaced" }`
    *   *Плюс:* Максимальная развязанность. Событие никогда не устаревает.
    *   *Минус (Thundering Herd):* Потребитель (Доставка) должен прийти по API обратно к Источнику (Заказам), чтобы узнать адрес. Если событий 10,000 в секунду, вы положите свой же API (Self-DoS).
2.  **Fat Event (Толстое событие / Event-Carried State Transfer):**
    *   *Payload:* Полная копия состояния заказа на момент создания.
    *   *Плюс:* Потребитель автономен. Ему не нужно вызывать API источника.
    *   *Минус:* Риск рассинхронизации данных (данные в событии могут устареть к моменту обработки). Жесткая привязка к схеме данных.

**Рекомендация:** Для High-Load систем используйте **Fat Events** для обеспечения автономности сервисов, но версионируйте схему (Schema Registry).

### 5.3. Проблема Dual Write и Transactional Outbox

Это классический вопрос на собеседовании на уровень Staff.
**Сценарий:** Вы сохраняете `Order` в БД и отправляете сообщение в `Kafka`.
*   Если упала БД после отправки в Kafka $\to$ В брокере "призрак" несуществующего заказа.
*   Если упала Kafka после коммита в БД $\to$ Заказ есть, но никто о нем не знает (потеря данных).

Распределенные транзакции (2PC/XA) — это медленно и ненадежно в микросервисах.

#### Решение: Transactional Outbox Pattern
Атомарность гарантируется локальной транзакцией БД.

1.  **Транзакция:**
    ```sql
    BEGIN;
    INSERT INTO orders (id, ...) VALUES (...);
    INSERT INTO outbox (id, payload, created_at) VALUES (uuid(), '{json}', now());
    COMMIT;
    ```
    Обе записи появляются или исчезают одновременно.

2.  **Реле (The Relay):**
    Отдельный фоновый процесс (или CDC - Change Data Capture инструмент, например, **Debezium**) читает таблицу `outbox` и перекладывает сообщения в Kafka.
    *   Если Реле упадет, оно просто перечитает таблицу после рестарта.

---

### 5.4. Идемпотентность (Idempotency) на стороне потребителя

В распределенных системах гарантия доставки — **At-Least-Once** (Хотя бы раз). Это значит, что подписчик может получить событие `OrderPaid` дважды (например, из-за ретраев сети или сбоя брокера).

Архитектор обязан требовать идемпотентности от обработчиков.

1.  **Техническая идемпотентность (Deduplication):**
    *   Таблица `processed_events (event_id)`.
    *   Если `insert` падает с ошибкой уникальности — игнорируем сообщение.
2.  **Бизнес-идемпотентность:**
    *   Операция `setStatus(PAID)` идемпотентна (повторный вызов ничего не меняет).
    *   Операция `balance += 10` **не идемпотентна**. Она требует проверки `transaction_id`.

### 5.5. Policy objects (Политики)

Иногда событие должно запустить сложную логику, затрагивающую несколько агрегатов. Не пишите это в контроллере.
Используйте **Policy** (или Process Manager).

*   *Сценарий:* `OrderCreated`. Нужно: списать товар, отправить SMS, начислить бонусы.
*   *Реализация:* Слушатель события `OrderCreatedEventHandler` выступает как оркестратор, отправляя команды в соответствующие агрегаты.

### Резюме раздела
**Доменные события** — это не просто логирование.
1.  Они **убирают прямую зависимость** между подсистемами.
2.  Требуют защиты через **Outbox Pattern** для надежности.
3.  Разделяются на **Внутренние** (богатые) и **Внешние** (стабильные контракты).
4.  Перекладывают ответственность за дубликаты на **Потребителя** (Идемпотентность).

## 6. Чек-лист уровня Practitioner

1.  **Reference by ID:** Ссылаются ли ваши агрегаты друг на друга по ID (`CustomerId`), или по объекту (`Customer`)?
    *   *Правильно:* По ID. Это позволяет лениво загружать данные, разбивать монолит на микросервисы и уменьшает размер транзакции.
2.  **Anemic Domain Model:** Где лежит ваша бизнес-логика?
    *   Если в `Service` слое (`OrderService`), а сущности — это просто геттеры/сеттеры — у вас **Анемичная модель** (процедурный код в ООП обертке).
    *   Переносите логику ("отменить заказ", "добавить позицию") внутрь сущности `Order`.
3.  **VO Validation:** Можно ли в вашем коде создать `new EmailAddress("invalid-string")`?
    *   Если да, вы нарушаете принцип VO. Валидация должна быть в конструкторе.
4.  **Optimistic Locking:** Используете ли вы версионирование (`@Version` в JPA/Hibernate) для защиты агрегатов от конкурентной записи?
    *   Агрегат — это граница целостности, он обязан защищать себя от состояния гонки.

### Заключение
**Tactical DDD** требует дисциплины. Легче написать анемичный сервис и "Transaction Script", чем проектировать богатую модель.
Но именно богатая модель (Aggregates + VO) позволяет системе жить 5-10 лет, не превращаясь в запутанный комок грязи, где изменение в одном месте ломает всё в другом.
**Агрегат гарантирует инварианты. События гарантируют развитие процесса.**

**TL;DR**:
*   **Data Contracts**: Это API-контракты для данных. Способ перенести ответственность за качество с Потребителя (который страдает) на Производителя (который ломает).
*   **Data Quality Testing**: Детерминированные проверки (Null check, Regex), которые блокируют деплой или загрузку.
*   **Data Observability & Anomaly Detection**: Вероятностный мониторинг (ML-based) для обнаружения "неизвестных неизвестных" (Drift, Volume Drop) в потоках.

## 1. Data Contracts: Сдвиг ответственности влево (Shift Left)

**Проблема**: В классической архитектуре Data Engineering работает в режиме "Пожарной команды".
1.  Бэкенд-разработчик команды `Orders` делает рефакторинг: меняет тип поля `price` с `DECIMAL` на `STRING` (потому что добавили валюту "100 USD").
2.  Это изменение — **Internal Implementation Detail** сервиса. Разработчик прав, он владеет своим кодом.
3.  Но дата-инженеры настроили CDC (Change Data Capture) прямо на эту таблицу `orders`.
4.  **Итог**: Ночью ETL-пайплайн падает с ошибкой `Type Mismatch`. Отчетность CEO сломана. Дата-команда чинит это 2 дня, ругаясь на бэкенд.

**Data Contract** — это решение этой проблемы через введение явного **Интерфейса**. Это API для данных.

### 1.1. Философия: Data Products vs. Data Exhaust

Чтобы внедрить контракты, нужно изменить ментальность (Mindset shift):
*   **Data Exhaust (Выхлоп данных)**: Данные — это побочный продукт работы сервиса (логи, дампы БД). Никто не гарантирует их качество. Это статус-кво.
*   **Data Product (Продукт данных)**: Сервис-источник осознанно публикует данные как продукт для внешних потребителей. У продукта есть спецификация, версия и гарантии.

**Shift Left (Сдвиг влево)** означает, что качество данных проверяется не "Справа" (в DWH, когда уже поздно), а "Слева" (в CI/CD пайплайне источника, *до* деплоя изменений).

### 1.2. Техническая реализация Контракта (The Spec)

Контракт — это файл (обычно YAML/JSON), лежащий в git-репозитории сервиса-источника. Он описывает **Публичный Интерфейс** данных, который *не обязан* совпадать с внутренней схемой БД.

**Пример реального контракта (ODCS - Open Data Contract Standard style):**

```yaml
dataContract:
  id: "urn:datacontract:checkout:orders:v2"
  owner: "team-checkout"
  status: "active"
  
  # 1. SCHEMA (Структура)
  model:
    - name: "completed_orders"
      type: "table"
      description: "Только успешно завершенные и оплаченные заказы."
      columns:
        - name: "order_id"
          type: "string(uuid)"
          nullable: false
          description: "Unique identifier"
        - name: "total_amount"
          type: "decimal(18,2)" # Контракт гарантирует Decimal, даже если внутри String
          nullable: false
        - name: "customer_email"
          type: "string"
          tags: ["pii", "gdpr"] # Метаданные для Governance

  # 2. SLA (Гарантии сервиса)
  serviceLevelAgreement:
    freshness: "15 minutes"   # Данные появятся в стриме не позднее чем через 15 мин
    availability: "99.9%"
    
  # 3. QUALITY (Встроенные тесты)
  qualityAttributes:
    - rule: "total_amount > 0"
      severity: "critical"    # Если нарушено - блокируем пайплайн
```

### 1.3. Архитектурные паттерны развязки (Decoupling Patterns)

Как технически обеспечить выполнение контракта, если внутренняя схема БД меняется?
Паттерн **Explicit Output Port** (Явный выходной порт).

Мы запрещаем DWH читать сырые таблицы (`SELECT * FROM raw_orders`). Вместо этого Producer обязан предоставить стабильный интерфейс:

**Вариант А: Public Views (Для батчевой обработки)**
*   В БД микросервиса создается схема `analytics_public`.
*   В ней создается View: `CREATE VIEW v_completed_orders AS SELECT id as order_id, CAST(price as DECIMAL) ... FROM internal_schema.orders WHERE status = 'DONE'`.
*   Контракт проверяет схему именно этой View.
*   Если разработчик меняет внутреннюю таблицу, View ломается -> CI падает -> Разработчик чинит View (адаптер) -> DWH ничего не замечает.

**Вариант Б: Stream Publication (Transactional Outbox)**
*   Сервис пишет события в Kafka топик `public.orders.v2`.
*   Схема топика (Protobuf/Avro) жестко зафиксирована в Schema Registry.
*   Сериализатор (Serializer) в коде сервиса упадет, если попытаться записать строку в поле Decimal.

### 1.4. Жизненный цикл изменений (Contract Evolution)

Контракты должны версионироваться. Нельзя просто изменить контракт и сломать потребителей.

1.  **Breaking Change Detection**:
    *   CI/CD инструмент (например, Data Contract CLI) сравнивает новый YAML со старым.
    *   Если удалена колонка или изменен тип (`int` -> `string`) — это **Major Change**.
    *   Билд блокируется: "Вы нарушаете контракт v2. Либо откатите изменения, либо выпустите контракт v3".
2.  **Эволюция схемы**:
    *   **Forward Compatible**: Можно добавлять новые nullable колонки. Старые потребители их игнорируют.
    *   **Backward Compatible**: Нельзя удалять обязательные поля.

### 1.5. Почему это работает (The Incentive Model)

Главный вопрос Практика: *"Зачем бэкендерам писать эти контракты? Им это не нужно".*

Ответ архитектора: **Freedom of Refactoring**.
*   *Без контракта*: Дата-инженеры приходят к бэкендерам и кричат: "Ничего не трогайте! Вы сломаете нам отчетность!". Бэкенд парализован.
*   *С контрактом*: Бэкендеры могут переписать БД хоть на NoSQL, хоть переименовать все таблицы. Главное — чтобы **Public View** или **Kafka Topic** выдавали данные согласно контракту.
*   Контракт — это не "оковы", это граница, внутри которой команда Producer-а полностью автономна.

### Резюме раздела 1

**Data Contract** — это механизм инкапсуляции для данных.
1.  Это **API**, а не схема базы.
2.  Оно проверяется **автоматически в CI** сервиса-источника.
3.  Оно гарантирует **стабильность** для потребителя и **свободу рефакторинга** для производителя.
4.  Без Data Contracts любая микросервисная архитектура со временем превращается в распределенный монолит из-за жесткой связности по данным.

## 2. Data Quality Testing: Детерминированные проверки

**Определение**: DQ Testing — это применение **детерминированных** проверок (Assertions) к физическим данным в пайплайне.
*   *Детерминированные* означает, что результат всегда бинарный: `PASS` или `FAIL`.
*   Если проверка вероятностная ("Кажется, продаж слишком мало"), это не Тестирование, это *Anomaly Detection* (см. след. раздел).

### 2.1. Пирамида тестирования в Data Engineering

Как и в разработке ПО, у нас есть уровни тестирования. Архитектор должен внедрить оба:

1.  **Data Unit Tests (Тестирование Логики)**:
    *   *Что тестируем*: Ваш SQL/Python код трансформации.
    *   *Метод*: Мы подаем на вход **Mock Data** (фиксированный CSV из 5 строк) и ожидаем фиксированный выход.
    *   *Инструмент*: `dbt unit tests` (появились в dbt 1.8+), `pytest`.
    *   *Цель*: Гарантировать, что формула расчета `Gross Margin` верна, даже если реальных данных еще нет.

2.  **Data Quality Tests (Тестирование Состояния)**:
    *   *Что тестируем*: Реальные данные, пришедшие из источника.
    *   *Метод*: SQL-запросы к продакшн-таблицам (Assertions).
    *   *Инструмент*: `dbt tests`, `Great Expectations`, `Soda`.
    *   *Цель*: Гарантировать, что источник не прислал мусор (Nulls, Duplicates, Invalid FK).

---

### 2.2. Шесть измерений DQ: От теории к SQL

На уровне Practitioner вы не пишете в отчетах "Проблема с Точностью". Вы пишете конкретный SQL-тест.

| Измерение (Dimension) | Суть проблемы | Пример реализации теста (Pseudo-SQL) |
| :--- | :--- | :--- |
| **Completeness (Полнота)** | Отсутствие обязательных значений | `SELECT COUNT(*) FROM table WHERE user_id IS NULL HAVING count = 0` |
| **Uniqueness (Уникальность)** | Дублирование сущностей | `SELECT id, COUNT(*) FROM table GROUP BY id HAVING COUNT(*) > 1` |
| **Timeliness (Своевременность)** | Данные слишком старые | `SELECT MAX(loaded_at) FROM table HAVING MAX < NOW() - INTERVAL '1 HOUR'` |
| **Validity (Валидность)** | Неверный формат или домен | `SELECT COUNT(*) FROM table WHERE email NOT LIKE '%@%'` |
| **Consistency (Согласованность)** | Нарушение ссылочной целостности | `SELECT COUNT(*) FROM orders o LEFT JOIN users u ON o.user_id = u.id WHERE u.id IS NULL` (Anti-Join) |
| **Accuracy (Точность)** | Нарушение бизнес-логики | `SELECT COUNT(*) FROM orders WHERE total_amount != (item_price * quantity) + tax` |

### 2.3. Паттерн WAP (Write-Audit-Publish)

Это "Золотой стандарт" 2025 года для предотвращения попадания "плохих" данных к пользователю.
Раньше мы делали: *Загрузили в Прод -> Запустили тесты -> Увидели ошибку -> Поздно, CEO уже видит кривой дашборд.*

Паттерн **WAP** меняет порядок:

1.  **Write (Запись)**:
    *   ETL пишет данные не в целевую таблицу, а в **Staging Area** (временную таблицу) или в **новую ветку** (если используется Iceberg/Delta Lake).
2.  **Audit (Аудит)**:
    *   Запускаются DQ-тесты (блокирующие) по Staging-данным.
    *   Проверяются Primary Keys, Foreign Keys и бизнес-правила.
3.  **Publish (Публикация)**:
    *   *Если Audit = PASS*: Мы делаем атомарную операцию **Swap** (подмену таблиц) или **Merge/Fast-Forward** (в Iceberg). Пользователь мгновенно видит новые чистые данные.
    *   *Если Audit = FAIL*: Данные в прод не попадают. Staging помечается как "Quarantine". Пайплайн падает с алертом.

**Техническая реализация (Пример на dbt + Snowflake):**
В dbt это реализуется через Blue/Green deployment или использование схем.
*   Run dbt model -> создает таблицу `analytics_staging.fact_orders`.
*   Run dbt test -> проверяет `analytics_staging.fact_orders`.
*   Если успех -> `ALTER TABLE analytics.fact_orders SWAP WITH analytics_staging.fact_orders`.

### 2.4. Severity: Warning vs Error (Управление шумом)

Не все тесты должны останавливать пайплайн. Архитектор настраивает уровни серьезности:

1.  **Severity: Error (Blocking)**
    *   *Критерий*: Данные физически сломаны или критически неверны.
    *   *Пример*: `Order_ID` is NULL, `Total_Amount` < 0.
    *   *Действие*: Stop Pipeline. Откат транзакции (WAP). PagerDuty Call.
2.  **Severity: Warning (Non-Blocking)**
    *   *Критерий*: Данные подозрительны, но процесс может продолжаться.
    *   *Пример*: 1% email-ов невалидны. 0.5% заказов не имеют привязки к региону.
    *   *Действие*: Данные проходят в прод. Запись в таблицу `dq_issues`. Алерт в Slack-канал (без звонка ночью).

### 2.5. Инструментарий 2025 (Tooling Landscape)

Как Практик, вы выбираете инструмент под задачу:

*   **dbt tests**: Стандарт де-факто.
    *   *Плюсы*: Встроено в процесс трансформации. Простота (YAML + SQL).
    *   *Минусы*: Сложно делать сложные проверки (например, сравнение таблиц).
*   **Great Expectations (GX)**:
    *   *Плюсы*: Богатая библиотека проверок ("expect column values to be between..."), Data Docs (HTML отчеты).
    *   *Минусы*: Тяжеловесный конфиг, сложность внедрения в SQL-пайплайны.
*   **Soda Core / SodaCL**:
    *   *Плюсы*: Декларативный язык (YAML), очень читаемый. Легко встраивается в Airflow.
    *   *Пример*:
        ```yaml
        checks for orders:
          - row_count > 0
          - duplicate_count(order_id) = 0
          - invalid_count(email) < 5%  # Допускаем небольшой процент ошибок (Warning)
        ```

### Резюме раздела 2

Data Quality Testing — это **Circuit Breaker** (предохранитель) вашей платформы данных.
1.  Тестируйте **код** (Unit tests) до деплоя.
2.  Тестируйте **данные** (Data tests) при каждой загрузке.
3.  Используйте паттерн **WAP**, чтобы "плохие" данные никогда не достигали "хороших" таблиц.
4.  Разделяйте **Блокирующие ошибки** (ID is Null) и **Предупреждения** (Data Drift), чтобы не будить команду зря.

## 3. Anomaly Detection: Вероятностный мониторинг

**Тестирование качества (DQ Testing)** — это проверка на соответствие *известным* правилам ("Email должен содержать @").
**Обнаружение аномалий (Anomaly Detection)** — это поиск *неизвестных* проблем ("Почему средний чек сегодня упал на 15%?").

Это **вероятностный** подход. Мы не говорим "Данные сломаны". Мы говорим "Данные выглядят подозрительно (Anomaly Score = 0.95)".

### 3.1. Анатомия аномалий в данных

Чтобы ловить аномалии, их нужно классифицировать. У каждой категории своя математика.

#### А. Аномалии Объема (Volume & Freshness)
Самый простой, но критичный слой.
*   **Volume Anomaly**: Резкий спад (Downtime на источнике) или всплеск (DDOS, Duplicate loop) количества строк.
*   **Freshness Anomaly**: Данные перестали поступать. "Last update was 45 minutes ago", хотя обычно интервал 15 минут.
*   *Сложность*: **Сезонность**.
    *   *Пример*: В 3 часа ночи трафик всегда падает. Если вы настроите статический порог "Минимум 1000 строк в час", вы будете получать алерты каждую ночь.
    *   *Решение*: Сравнивать "Текущий час" с "Этим же часом неделю назад" (WoW — Week over Week), а не с предыдущим часом.

#### Б. Дрейф Данных (Data Drift / Distribution Shift)
Данные приходят, объем в норме, типы верные. Но *суть* данных изменилась.
*   **Field Health**: Доля NULL в поле `category` выросла с 1% до 30%.
*   **Value Distribution**: Обычно заказы лежат в диапазоне $10-$500. Вдруг пошли заказы по $0.01 или по $1,000,000.
*   *Пример*: Фронтенд изменил логику и стал слать `country_code` как "United States" вместо "US". DQ тест на `IS NOT NULL` проходит. Аномалия распределения (исчез код "US", появился "United States") детектируется.

#### В. Аномалии Схемы (Schema Drift)
*   Удаление колонки, добавление колонки, изменение типа.
*   В Schema-on-Read системах (Data Lake) это происходит молча и ломает отчеты постфактум.

---

### 3.2. Математический аппарат (The Engine)

Как Практик, вы должны знать, какой алгоритм применить, чтобы избежать **Alert Fatigue** (усталости от алертов).

1.  **Z-Score (Standard Score)**:
    *   *Суть*: Насколько текущее значение отличается от среднего в единицах стандартного отклонения.
    *   *Формула*: `(X - Mean) / StdDev`. Если Z > 3 (правило 3-х сигм), это аномалия.
    *   *Ограничение*: Работает только для **Нормального распределения** (Гауссиана). Реальные данные (продажи, трафик) часто не нормальны.

2.  **IQR (Interquartile Range) / MAD (Median Absolute Deviation)**:
    *   *Суть*: Использование медианы и квартилей (25-й и 75-й перцентили).
    *   *Применение*: Гораздо устойчивее к выбросам, чем Z-Score. Используется для мониторинга объемов и задержек.

3.  **Расстояние Вассерштейна (Wasserstein Distance) / PSI (Population Stability Index)**:
    *   *Суть*: Сравнение формы двух гистограмм (распределений).
    *   *Применение*: Детекция Data Drift. Сравниваем гистограмму колонки `age` за "Вчера" (Reference) и "Сегодня" (Current).
    *   *PSI > 0.2* означает существенный дрейф.

### 3.3. Реализация в потоке: Streaming Observability

В 2025 году мы не можем ждать ночного батча, чтобы узнать об аномалии. Мы используем **Approximation Algorithms** (Вероятностные структуры данных) прямо в памяти Kafka Streams / Flink.

Посчитать точный медианный чек на потоке в 1 млн RPS невозможно (требует сортировки).
Мы используем **Sketches (Скетчи)**:

1.  **t-Digest** или **KLL Sketch**:
    *   Позволяет оценить любой перцентиль (p50, p95, p99) с ошибкой < 1% и минимальным потреблением памяти.
    *   *Сценарий*: Мониторинг распределения времени отклика API или сумм транзакций в реальном времени.
2.  **HyperLogLog (HLL)**:
    *   Оценка кардинальности (количества уникальных значений).
    *   *Сценарий*: Если HLL показывает, что количество уникальных `device_id` резко упало (при том же объеме трафика), возможно, сломалась генерация ID на клиенте (все шлют один и тот же ID).

### 3.4. Архитектура: Build vs Buy

Это главное стратегическое решение Практика.

**Вариант А: Самописное решение (SQL-based)**
*   *Как*: dbt макрос, который считает `row_count` и пишет в таблицу `metadata.metrics`. Другой джоб сравнивает `today` vs `avg(last_7_days)`.
*   *Плюсы*: Бесплатно, полный контроль.
*   *Минусы*: Вы устанете настраивать пороги (Thresholds) для 1000 таблиц. Вы будете получать ложные алерты в праздники.
*   *Рекомендация*: Подходит для старта (Key Metrics Monitoring).

**Вариант Б: Специализированные платформы (Data Observability)**
*   *Инструменты*: Monte Carlo, Bigeye, Metaplane.
*   *Как*: Они подключаются к `Information Schema` и `Query Logs` вашего DWH. Используют ML для автоматического обучения "норме" (учитывают сезонность, праздники).
*   *Плюсы*: Zero-config. Автоматический Lineage (показывает, какой дашборд умрет из-за этой аномалии).
*   *Рекомендация*: Обязательно для Enterprise масштаба (>500 таблиц).

### 3.5. Пример из жизни: Инцидент с валютой

*   **Контекст**: Глобальный маркетплейс. Цены в поле `amount` (Decimal).
*   **Инцидент**: В одной из стран (Уганда) сменился провайдер данных. Вместо USD начали слать суммы в UGX (Угандийский шиллинг). Курс 1 USD ~ 3700 UGX.
*   **DQ Тесты**: `amount > 0` — **PASS**. `amount IS NOT NULL` — **PASS**. Тесты зеленые.
*   **Anomaly Detection**:
    *   Алгоритм дрейфа распределения (Distribution check) заметил, что медианное значение (p50) для сегмента `country='UG'` выросло в 3500 раз.
    *   Сработал алерт: **"Numeric Distribution Drift detected on table orders column amount"**.
    *   Автоматический Lineage показал: "Риск для финансового отчета Revenue Q4".
    *   Команда остановила пайплайн до того, как "мусорные" миллионы попали в отчетность инвесторам.

### Резюме раздела 3

1.  **Anomaly Detection** — это страховочная сеть для проблем, которые вы не можете предсказать тестами.
2.  Используйте **статистику (MAD, PSI)**, а не жесткие пороги, чтобы избежать шторма алертов.
3.  Для потоковых данных используйте **Скетчи (t-Digest, HLL)**.
4.  Если данных много — **покупайте** готовое решение (Monte Carlo и др.), не пытайтесь написать свой ML для аномалий, это отдельный продукт.

## 4. Governance Architecture: Data Mesh Context

**Governance в монолите**: Центральная команда "Data Stewards" вручную проверяет качество и выдает доступы. Это бутылочное горлышко.
**Governance в Data Mesh**: Это **Федеративная модель**. Центр устанавливает "Правила дорожного движения" (Стандарты, Безопасность), а Домены управляют своими "Автомобилями" (Качество, Моделирование, Доступы).

Главный принцип 2025 года: **Policies as Code** (Политики как код). Если правило нельзя проверить автоматически в CI/CD пайплайне или на уровне платформы, оно не работает.

### 4.1. Федеративная Операционная Модель

Как разделить ответственность, чтобы не создать хаос? Мы используем модель "Федерация - Платформа - Домены".

1.  **The Federated Council (Законодательная власть)**:
    *   Состоит из представителей доменов (Lead Data Engineers) и Платформенной команды.
    *   *Задача*: Договориться о стандартах. "Мы используем формат даты ISO-8601" или "Мы используем URN для именования продуктов".
    *   Встречаются раз в месяц. Решения фиксируются как ADR (Architecture Decision Records).

2.  **The Platform Team (Исполнительная власть)**:
    *   *Задача*: Предоставить **Self-Service инструменты**, которые делают соблюдение правил "путем наименьшего сопротивления".
    *   Не "проверяйте качество руками", а "вот вам Github Action, который сам запускает dbt test".

3.  **The Domain Teams (Владельцы)**:
    *   *Задача*: Применять инструменты для обеспечения **Локального Качества**.
    *   Команда "Маркетинг" лучше знает, что такое "валидный лид", чем центральная команда.

---

### 4.2. Computational Governance (Вычислительное управление)

Это сердце архитектуры. Мы внедряем проверки (Guardrails) непосредственно в инфраструктуру.

#### А. Global Policies (Глобальные Политики - Non-Negotiables)
Правила, которые обязательны для всех. Реализуются Платформой.
*   **Security & PII**: "Любая колонка, помеченная тегом `pii`, должна быть замаскирована (masked) для пользователей без роли `dpo`".
*   **Interoperability**: "Все выходные данные должны быть в формате Parquet или Iceberg".
*   **Discovery**: "Нельзя задеплоить таблицу в Prod без заполненного поля `description` в Data Catalog".

*   *Реализация*:
    *   **Open Policy Agent (OPA)**: Проверяет Terraform/K8s манифесты при деплое.
    *   **Tag-Based Masking**: Политики Dynamic Data Masking в Snowflake/Databricks, привязанные к тегам, а не к именам колонок.

#### Б. Local Policies (Локальные Политики)
Правила, специфичные для домена. Реализуются Доменом.
*   **Quality**: "Для домена Финансов точность `amount` должна быть до 4 знаков. Для Маркетинга достаточно целых чисел".
*   **Retention**: "Логи храним 3 дня, Клиентов — вечно".

---

### 4.3. Data Catalog как Control Plane (Active Metadata)

В старом мире Каталог (Amundsen, Atlas) был "пассивной библиотекой" — местом, где можно *поискать* данные.
В Data Mesh Каталог (DataHub, Atlan, Alation) становится **Control Plane** — пультом управления. Это называется **Active Metadata**.

**Сценарии Active Metadata для Практика:**

1.  **Automated Lineage & Impact Analysis**:
    *   Платформа автоматически парсит SQL-логи.
    *   *Сценарий*: Тест качества упал в `Raw_Orders`. Каталог видит по графу Lineage, что эта таблица питает дашборд `CEO_Revenue`.
    *   *Действие*: Каталог автоматически вешает плашку **"Status: Unhealthy"** на дашборд в BI-системе (через API), чтобы CEO не принял решение на основе битых данных.

2.  **Tag Propagation (Распространение тегов)**:
    *   Вы пометили поле `email` как `PII` на входе (Bronze).
    *   Каталог автоматически пробрасывает этот тег через все трансформации (Silver -> Gold) до витрин.
    *   Вам не нужно вручную искать, где этот email всплыл в витрине маркетинга.

---

### 4.4. Scalable Access Control: ABAC vs RBAC

В монолите мы использовали **RBAC** (Role-Based Access Control): создавали роль `Marketing_Analyst` и давали ей гранты.
В Data Mesh с 50 доменами это приводит к **Role Explosion** (взрыву ролей). Тысячи ролей, которыми невозможно управлять.

**Решение 2025: ABAC / PBAC (Attribute/Policy-Based Access Control)**

Мы управляем доступом через **Теги (Attributes)** и **Политики**.

1.  **Tagging**: Владелец данных (Domain Owner) вешает теги на свои Data Products.
    *   Tags: `domain:finance`, `classification:confidential`, `sensitivity:high`.
2.  **User Attributes**: У пользователя (из Active Directory / Okta) есть атрибуты.
    *   User: `dept:finance`, `clearance:high`.
3.  **Policy**: Платформа содержит *одну* глобальную логику.
    *   *Rule*: `ALLOW READ IF (resource.domain == user.dept AND resource.classification <= user.clearance)`.

*Результат*: Когда Финансы создают новую таблицу, им не нужно просить админов создать роли. Они просто вешают тег `domain:finance`, и все сотрудники фин-департамента получают доступ автоматически.

---

### 4.5. Пример "Life of a Data Product" в Mesh Governance

Чтобы закрепить, пройдем путь создания Продукта Данных:

1.  **Create (Код)**: Инженер домена пишет dbt-модель.
    *   *Governance Check (Pre-commit)*: Линтер проверяет, что у модели есть `description` и `owner`.
2.  **Deploy (CI/CD)**:
    *   *Governance Check (OPA)*: Проверяется, что модель не пишет в схему чужого домена (Isolation).
    *   *Contract Check*: Проверяется совместимость схемы с заявленным контрактом.
3.  **Run (Runtime)**:
    *   *Observability*: Если данные не обновились вовремя, Каталог понижает "Health Score" продукта.
4.  **Consume (Access)**:
    *   Пользователь запрашивает доступ. Система видит тег `finance-sensitive`. Проверяет, прошел ли пользователь тренинг по безопасности. Если да — выдает временный токен.

### Резюме раздела 4

Governance в Data Mesh — это **автоматизация стандартов**.
1.  **Shift Right**: Используйте **Active Metadata** для отслеживания здоровья и Lineage "на лету".
2.  **Shift Left**: Используйте **Data Contracts** и **Policy-as-Code** (OPA) для блокировки нарушений до деплоя.
3.  Забудьте про ручное создание ролей (RBAC). Переходите на **Tag-based Policies (ABAC)** для масштабирования доступа.
4.  Платформа должна делать "правильный путь" (The Right Way) самым "легким путем" (The Easy Way).

## 5. Практический пример (Use Case): End-to-End Data Quality Pipeline

**Контекст**:
*   **Producer**: Микросервис `Loan Origination` (выдача займов).
*   **Consumer**: Команда Рисков (Risk Team), обучающая ML-модели скоринга.
*   **Tech Stack**: Kafka (Stream), Snowflake (DWH), dbt (Transform), Monte Carlo (Observability), DataHub (Catalog).

Наша цель — проследить путь данных от "рождения" до "потребления" и увидеть, как работают защитные механизмы на каждом этапе.

### Этап 1: "Shift Left" — Контракт на Источнике

Все начинается не в DWH, а в репозитории микросервиса `loan-service`.
Разработчик добавляет новое поле `debt_to_income_ratio`.

**1.1. Определение Контракта (YAML)**
В репозитории лежит файл `contracts/loan_application.yaml`.

```yaml
dataContract:
  id: "urn:contract:loans:application:v3"
  domain: "lending"
  model:
    - name: "loan_application_events"
      type: "topic"
      format: "protobuf" # Жесткая бинарная схема
      fields:
        - name: "applicant_id"
          type: "string(uuid)"
          tags: ["pii"] # Тег для Governance
        - name: "annual_income"
          type: "decimal(18,2)"
          constraints: ["value > 0"] # Простейшая проверка
        - name: "debt_to_income_ratio"
          type: "float"
          description: "Calculated ratio: monthly_debt / monthly_income"
          quality_expectations:
             - "between(0.0, 100.0)" # Бизнес-правило в контракте
```

**1.2. CI/CD Enforcement**
Когда бэкендер делает Pull Request:
1.  **Contract Linter**: Проверяет синтаксис YAML.
2.  **Schema Check**: Проверяет, что Protobuf-схема в коде соответствует описанию в YAML.
3.  **Breaking Change Check**: Если разработчик удалил обязательное поле `annual_income`, пайплайн падает с ошибкой: *"Backward incompatible change detected. Bump major version required."*

---

### Этап 2: Ingestion & Circuit Breakers (Защита от мусора)

Данные летят через Kafka в DWH (Snowflake).

**2.1. Schema Registry Validation (Runtime)**
Микросервис пытается отправить событие, где `debt_to_income_ratio = "high"`.
*   **Результат**: Kafka Producer получает ошибку сериализации (SerializerException).
*   **Эффект**: "Грязные" данные (тип String вместо Float) даже не попадают в трубу. Источник обязан исправить баг.

**2.2. Dead Letter Queue (DLQ)**
Данные с верной схемой, но нарушающие логические ограничения (например, `annual_income = -5000`), отфильтровываются на входе ETL-процесса.
*   Они не ломают пайплайн.
*   Они падают в таблицу `RAW_LOANS_DLQ` для ручного разбора.

---

### Этап 3: Transformation & WAP Pattern (Середина трубы)

Данные попали в Bronze слой. Теперь dbt трансформирует их в Silver/Gold. Здесь работает паттерн **Write-Audit-Publish**.

**3.1. WRITE (Запись)**
dbt создает временную таблицу (или новую ветку) `STAGING_LOANS`.

**3.2. AUDIT (Тестирование)**
Запускаются блокирующие тесты (`dbt test`).

```sql
-- test_loan_logic.sql
-- Блокирующий тест (Severity: Error)
-- Займ не может быть одобрен, если доход равен нулю
SELECT *
FROM {{ ref('staging_loans') }}
WHERE status = 'APPROVED' AND annual_income = 0
```

*   **Сценарий провала**: Тест нашел 5 записей.
*   **Действие**: dbt возвращает код выхода `1`. Шаг `Publish` отменяется.
*   **Оповещение**: В Slack канал `#data-lending-alerts` летит сообщение: *"Critical Logic Breach: Approved loans with zero income detected."*

**3.3. PUBLISH (Публикация)**
Если тесты прошли, выполняется атомарная подмена:
```sql
ALTER TABLE PROD_LOANS SWAP WITH STAGING_LOANS;
```
Потребители всегда видят только проверенные данные.

---

### Этап 4: Observability (Ловля "Неизвестных")

Данные в проде. Тесты прошли. Но что-то не так.

**Сценарий**: Из-за бага во фронтенде (перепутали валюты) все доходы пользователей из Вьетнама стали приходить в донгах, но с кодом USD. Числа стали гигантскими.
*   Тест `income > 0` проходит (миллион больше нуля).
*   Тест `income is not null` проходит.

**4.1. Anomaly Detection (Monte Carlo / Custom)**
Система Observability автоматически отслеживает метрику **Distribution (PSI)** поля `annual_income`.
1.  Алгоритм видит, что медиана (p50) дохода выросла с $50,000 до $5,000,000 за один час.
2.  Z-Score > 5. Это аномалия.

**4.2. Impact Analysis (Automated Lineage)**
Система строит граф влияния:
*   Аномальная таблица: `PROD_LOANS`.
*   Зависимые объекты: Витрина `RISK_MART` -> ML-модель `Credit_Score_v4`.
*   **Действие**: Система Observability автоматически помечает ML-модель тегом **"Data Quality Issue"** в Model Registry, чтобы предотвратить переобучение модели на мусорных данных.

---

### Этап 5: Governance & Access (Потребление)

Data Scientist Алиса хочет исследовать эти данные, чтобы починить модель.

**5.1. Tag-Based Access Control (ABAC)**
Алиса делает `SELECT * FROM PROD_LOANS`.
*   В метаданных (DataHub) поле `applicant_id` помечено тегом `PII`.
*   В политике доступа (Snowflake Policy) сказано:
    `IF user_role != 'DPO' THEN MASK column WITH '***'`.
*   **Результат**: Алиса получает данные, но видит `applicant_id` как `***`. Ей не нужно запрашивать доступ, она получает его мгновенно, но в безопасном виде.

**5.2. Data Mesh Usage**
Алиса находит ошибку, исправляет её и хочет создать новую фичу `income_stability`.
Она создает **новый Data Product** в своем домене (Risk), наследуясь от `PROD_LOANS`. Благодаря Lineage, Платформа видит связь и распространяет теги безопасности на её новую витрину.

### Резюме практического примера

Этот пайплайн демонстрирует зрелость уровня **Practitioner**:
1.  **Preventative**: Контракты не пускают "чужие" баги в систему.
2.  **Deterministic**: WAP гарантирует, что прод не сломается от явных ошибок.
3.  **Probabilistic**: Anomaly Detection ловит бизнес-сбои (валюты, дрейф).
4.  **Automated**: Governance работает прозрачно (маскирование), не замедляя работу аналитика.

### Резюме для Практика [P]

*   **Data Contracts** предотвращают пожары, заставляя Producer-ов отвечать за схему.
*   **Data Quality Tests** (в dbt/GX) ловят *ожидаемые* ошибки (Nulls, Duplicates).
*   **Anomaly Detection** ловит *неожиданные* изменения в поведении данных.
*   Качество данных — это не состояние, это **процесс**, встроенный в CI/CD.

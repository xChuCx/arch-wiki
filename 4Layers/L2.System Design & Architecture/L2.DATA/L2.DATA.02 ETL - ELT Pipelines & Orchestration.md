**TL;DR**:
*   **ELT победил ETL** в облаках. Мы грузим "сырые" данные, а трансформируем их мощностями Warehouse (Snowflake/BigQuery).
*   **dbt** — это компилятор, который превращает Jinja+SQL в DDL/DML команды, автоматически строя граф зависимостей (Lineage) через функцию `ref()`.
*   **Orchestration (Airflow)** — это не просто запускалка скриптов. Это система управления состоянием задач (State Management) через метаданные, где Scheduler — это бесконечный цикл парсинга и планирования.

## 1. The Paradigm Shift: From ETL to ELT

Понимание сдвига архитектуры критично для выбора инструментов.
### 1.1. ETL (Extract, Transform, Load): Архитектура "Тяжелого Атлета"

**ETL** — это архитектурный паттерн, в котором трансформация данных происходит **на выделенном сервере приложений** (ETL Server) *до* того, как данные будут записаны в целевое хранилище (DWH).

В этой модели Хранилище (Target DWH) рассматривается как "священный сосуд", куда должны попадать только идеально чистые, готовые к употреблению данные.

#### А. Физическая топология (The Physics of ETL)

В отличие от ELT, где вычисления происходят внутри базы данных, ETL — это трехзвенная архитектура:

1.  **Source (Источник)**: ERP, CRM, Files.
2.  **Processing Engine (ETL Server)**: Выделенный кластер (Informatica PowerCenter, IBM DataStage, Talend, SSIS или Apache Spark в режиме ETL).
    *   *Важно*: Данные выкачиваются из источника, проходят по сети в оперативную память ETL-сервера, трансформируются процессором ETL-сервера и только потом летят по сети в DWH.
3.  **Target (DWH)**: Oracle Exadata, Teradata, SQL Server. Выступает пассивным приемником данных.

#### Б. Глубокое погружение в "Transform" (In-flight Processing)

На уровне Практика вы должны понимать, как работает движок ETL. Это не SQL-запрос.

*   **Row-by-Row Processing (Pipelining)**: Классические ETL-инструменты работают потоково. Они читают строку из источника, прогоняют через цепочку функций (Map, Filter, Lookup) в памяти и пишут в таргет.
*   **Стейджинг в памяти (In-Memory Staging)**: ETL пытается сделать всё в RAM. Если объем данных превышает RAM сервера трансформации, происходит **Spill to Disk** (сброс на диск), и производительность падает на порядки.
*   **Lookups (Обогащение)**: Самая тяжелая операция. Чтобы обогатить "Транзакцию" данными "Клиента", ETL-сервер должен подгрузить справочник клиентов в свой кэш (Lookup Cache).

#### В. Концепция Schema-on-Write (Схема при Записи)

Это главная характеристика ETL, делающая его "жестким" (Rigid).
*   **Определение**: Вы должны жестко определить структуру целевой таблицы и типы данных *до* запуска процесса.
*   **Последствия**: Если источник добавил поле `discount_code` в JSON, а в вашей ETL-схеме (Mapping) его нет — пайплайн упадет или поле будет молча отброшено. Любое изменение требует перекомпиляции ETL-джоба и часто — `ALTER TABLE` в хранилище.

#### Г. Почему ETL все еще нужен? (Use Cases 2025)

Не спешите списывать ETL в утиль. Есть сценарии, где ELT (загрузка сырых данных) недопустим:

1.  **Security & Compliance (PII Masking)**:
    *   Вы *не имеете права* сохранять номера кредитных карт или SSN на диск хранилища даже в сыром виде (требования PCI-DSS / GDPR).
    *   ETL позволяет маскировать/хешировать чувствительные данные *в полете* (in-memory). На диск попадает уже `Obfuscated Data`.
2.  **Complex Parsing (Mainframe/Binary)**:
    *   SQL плох в парсинге бинарных форматов (EBCDIC, Avro, Protobuf) или сложного XML.
    *   Специализированный ETL-движок (код на Java/C++) делает это в разы эффективнее, отдавая в БД уже готовые строки.
3.  **Heterogeneous Sources (Гетерогенные источники)**:
    *   Если вам нужно сджойнить данные из Kafka и данные из старого DB2, ETL-сервер выступает отличным хабом, который вычитывает оба источника, мерджит их в памяти приложения и кладет результат.

#### Д. Пример для наглядности: "Банковский День"

Представьте закрытие операционного дня в банке (Close of Business).

*   **Задача**: Обработать 50 миллионов транзакций с Мейнфрейма, проверить их на фрод, обогатить данными филиалов и положить в Oracle DWH.
*   **ETL Подход**:
    1.  Informatica вычитывает файл выгрузки с Мейнфрейма.
    2.  **В памяти** расшифровывает EBCDIC-кодировку.
    3.  **В памяти** маскирует ФИО клиентов.
    4.  **В памяти** проверяет баланс (через кэшированный Lookup).
    5.  Готовые чистые записи вставляются в Oracle через `Bulk Insert` (Direct Path Load).
    *   *Результат*: Oracle не нагружен вычислениями, он только пишет на диск. В хранилище нет "грязных" данных.

#### Е. Главные недостатки (Почему мы уходим от этого)

1.  **The Bottleneck (Узкое место)**: ETL-сервер сложно масштабировать. Это, как правило, вертикальное масштабирование (Scale Up — купить сервер мощнее).
2.  **Data Gravity (Гравитация данных)**: Мы гоняем огромные объемы данных по сети (Source -> ETL -> Target). В облаках, где данные измеряются петабайтами, это дорого и долго. (В ELT мы приносим вычисления к данным, а не наоборот).
3.  **High Maintenance**: Логика размазана. Часть логики в GUI ETL-инструмента, часть в Stored Procedures базы. Версионировать визуальные квадратики Informatica (`.xml` экспорты) в Git — мучение.

### Резюме раздела 1.1
ETL — это подход **"Очисти, потом сохрани"**. Он идеален для безопасности и сложных не-SQL трансформаций, но проигрывает в гибкости и скорости разработки (Time-to-Market) современному ELT.

### 1.2. ELT (Extract, Load, Transform): Cloud-Native Стандарт

**ELT** — это архитектурный паттерн, использующий вычислительную мощь самого хранилища данных (Target DWH) для выполнения трансформаций. Мы отказываемся от выделенного ETL-сервера и переносим логику обработки данных в SQL (или Python/Java UDFs), выполняемый внутри кластера базы данных.

Этот сдвиг стал возможен благодаря двум технологическим прорывам: **разделению вычислений и хранения** (Separation of Compute and Storage) и удешевлению объектного хранилища (S3/Blob).

#### А. Физическая топология: Inversion of Control

В отличие от ETL, где DWH — это пассивное хранилище, в ELT DWH — это активный вычислительный движок.

1.  **Extract (Извлечение)**:
    *   Максимально "глупый" и быстрый процесс.
    *   Инструменты: Fivetran, Airbyte, DMS.
    *   Задача: Скопировать байты из Source (Postgres WAL, API JSON, CSV) и положить их в **Staging Area** (обычно S3 или внутренняя таблица DWH) без изменений.
2.  **Load (Загрузка)**:
    *   Команда `COPY INTO` (Snowflake) или `LOAD DATA` (BigQuery).
    *   Данные загружаются в **Raw/Bronze Layer**.
    *   *Важно*: Используются типы данных `VARIANT`, `JSONB` или `SUPER`. Мы не парсим JSON, мы кладем его целиком в одну ячейку.
3.  **Transform (Трансформация)**:
    *   Выполняется SQL-движком хранилища.
    *   Source-to-Target маппинг превращается в `CREATE VIEW AS SELECT ...` или `INSERT INTO ... SELECT ...`.
    *   Инструмент оркестрации (dbt) управляет порядком выполнения этих SQL-запросов.

#### Б. Schema-on-Read (Схема при Чтении)

Это киллер-фича ELT, обеспечивающая ту самую **Agility** (Гибкость).

*   **Концепция**: В момент загрузки (Load) нам плевать на структуру данных. Мы сохраняем сырой пейлоад. Структура определяется только в момент написания запроса (Transform/Read).
*   **Пример**: Источник начал присылать новое поле `user_mood` внутри JSON-объекта.
    *   *ETL*: Пайплайн падает, так как схема на входе не совпадает с маппингом. Инженер просыпается ночью.
    *   *ELT*: Данные молча сохраняются в столбец `raw_json`. Поле `user_mood` уже лежит в хранилище. Аналитик просто добавляет `json_extract_path_text(raw_json, 'user_mood')` в свою витрину, когда ему это понадобится. **Zero Downtime**.

#### В. Pushdown Optimization и MPP

Почему раньше так не делали? Потому что Oracle/SQL Server были дорогими и плохо масштабировались.
ELT опирается на архитектуру **MPP (Massively Parallel Processing)**.

*   **Физика процесса**: Когда вы запускаете трансформацию в Snowflake/BigQuery:
    1.  Запрос разбивается на тысячи микро-задач.
    2.  Поднимается кластер (Virtual Warehouse) из 64, 128 или 512 узлов.
    3.  Каждый узел обрабатывает свой кусочек данных (Micro-partition).
    4.  **Data Gravity (Гравитация данных)**: Мы приносим легкий код (SQL) к тяжелым данным, лежащим на дисках кластера, вместо того чтобы гонять терабайты через узкое сетевое горлышко на внешний ETL-сервер.

#### Г. The "Replayability" Argument (Аргумент Воспроизводимости)

Это главный аргумент Архитектора за внедрение ELT.

*   **Сценарий**: Вы обнаружили баг в логике расчета "Чистой Прибыли", который существовал полгода.
*   **В ETL**: У вас проблема. Исходные сырые данные уже трансформированы и, возможно, агрегированы. Оригиналы потеряны или лежат в холодных архивах лент. Восстановление истории — это проект на месяц.
*   **В ELT**: У вас в Raw Layer лежит полная копия исходников за все время.
    *   Действие: Исправляем SQL-код в dbt.
    *   Команда: `dbt run --full-refresh`.
    *   Результат: Хранилище пересчитывает всю историю с нуля за пару часов, используя мощный кластер. Историческая правда восстановлена без потери данных.

#### Д. Пример для наглядности: "Clickstream Analytics"

Представьте поток событий с мобильного приложения (10 ТБ/день).

1.  **Extract/Load**: Kinesis Firehose сбрасывает JSON-файлы в S3. Snowpipe (Snowflake) автоматически засасывает их в таблицу `EVENTS_RAW` (одна колонка `payload` типа VARIANT).
2.  **Transform 1 (Silver)**: dbt запускает SQL, который парсит JSON, извлекает `event_type`, `user_id`, `timestamp`, дедублицирует события и кладет в таблицу `EVENTS_CLEAN`.
3.  **Transform 2 (Gold)**: dbt запускает агрегацию, считая DAU/MAU, и обновляет витрину `FACT_DAILY_STATS`.

Вся нагрузка легла на Snowflake. Инженерам не пришлось менеджить кластер Spark или сервер Informatica.

#### Е. Недостатки и Риски ELT

На уровне Practitioner вы должны знать цену:
1.  **Cost Spikes (Скачки стоимости)**: Плохой SQL-запрос в ETL-сервере положит сервер. Плохой SQL-запрос в BigQuery/Snowflake "сожжет" вам $10,000 за час, так как облако радостно выделит столько ресурсов, сколько вы попросите. Нужен строгий **FinOps** (квоты, мониторинг).
2.  **Data Swamp (Болото данных)**: Поскольку грузить данные легко ("вали всё в кучу"), Raw слой может превратиться в помойку без документации и владельцев.

### Резюме раздела 1.2
ELT — это подход **"Сохрани всё, разберись позже"**. Он стал стандартом благодаря разделению Compute/Storage. Он обеспечивает **гибкость схемы** и **возможность пересчета истории**, но требует дисциплины в написании SQL и управлении облачными расходами.

## 2. dbt (data build tool): Архитектура и Внутреннее устройство

**dbt** — это среда разработки (Framework), которая позволяет аналитикам и инженерам трансформировать данные в хранилище, используя практики Software Engineering (версионирование, модульность, CI/CD, тестирование).

Фундаментально dbt выполняет две функции:
1.  **Компилятор (Compiler)**: Превращает код на SQL+Jinja в исполняемый SQL (Raw SQL).
2.  **Исполнитель (Runner)**: Выполняет этот SQL в целевой БД в правильном порядке.

### 2.1. Жизненный цикл выполнения (Compilation Lifecycle)

Для отладки пайплайнов важно понимать, что происходит, когда вы пишете `dbt run`.

1.  **Parsing (Парсинг)**:
    *   dbt сканирует директорию проекта, читает `.sql` и `.yml` файлы.
    *   Он **не выполняет** SQL на этом этапе. Он ищет блоки конфигурации `{{ config(...) }}` и, самое главное, вызовы `{{ ref(...) }}` и `{{ source(...) }}`.
    *   **Результат**: Строится **DAG (Directed Acyclic Graph)** — граф зависимостей всех моделей. Если есть циклические зависимости (A -> B -> A), dbt упадет здесь.
2.  **Compilation (Компиляция)**:
    *   dbt берет Jinja-шаблон модели и "рендерит" его.
    *   Переменные заменяются значениями.
    *   `ref('model_a')` заменяется на физическое имя таблицы в БД (например, `prod_analytics.dim_users`).
    *   **Artifact**: Генерируется файл `manifest.json` (полное описание графа и настроек) и скомпилированные SQL-файлы в папке `target/compiled`.
3.  **Execution (Выполнение)**:
    *   Runner берет скомпилированный SQL и оборачивает его в DDL/DML (шаблон материализации).
    *   *Пример*: Вы написали `SELECT ...`. Runner отправляет в БД: `CREATE TABLE x AS SELECT ...` или `MERGE INTO x ...`.
    *   Используется пул соединений (Multithreading) для параллельного запуска независимых веток графа.

### 2.2. The Magic of `ref()` & Lineage

В dbt запрещено писать `FROM my_schema.my_table`. Вы обязаны писать `FROM {{ ref('my_model') }}`.

*   **Dependency Injection**: Функция `ref()` сообщает dbt: "Эта модель зависит от той модели". Именно так строится Lineage.
*   **Environment Awareness**: `ref()` автоматически подставляет нужную схему.
    *   В проде: `prod_dwh.orders`
    *   В деве (на ноутбуке разработчика): `dev_ivan_dwh.orders`
    *   Это позволяет разработчикам работать изолированно ("Sandbox"), не ломая прод.

### 2.3. Стратегии Материализации (Materialization Internals)

На уровне Practitioner вы должны выбирать стратегию осознанно, понимая Cost & Performance.

#### A. View (Представление)
*   **Механика**: `CREATE OR REPLACE VIEW ...`.
*   **Плюсы**: Мгновенный деплой. Всегда свежие данные. Занимает 0 места.
*   **Минусы**: Медленное чтение (запрос вычисляется каждый раз при обращении). Не подходит для тяжелых трансформаций.

#### B. Table (Таблица)
*   **Механика**: `CREATE TABLE ... AS SELECT` (CTAS). Обычно делается через swap: создается временная таблица, потом переименовывается (atomically swap) для Zero Downtime.
*   **Плюсы**: Быстрое чтение.
*   **Минусы**: Долгий пересчет (Full Refresh). Высокая нагрузка на БД при каждом запуске.

#### C. Incremental (Инкрементальная загрузка) — *Самое сложное*
Позволяет обрабатывать только новые или измененные данные.

*   **Механика**:
    ```sql
    {{
      config(
        materialized='incremental',
        unique_key='order_id'
      )
    }}
    SELECT * FROM {{ source('raw', 'orders') }}
    {% if is_incremental() %}
      -- Этот блок работает только при повторных запусках
      WHERE updated_at > (SELECT MAX(updated_at) FROM {{ this }})
    {% endif %}
    ```
*   **Стратегии обновления (Incremental Strategies)**:
    1.  **Append (Insert)**: Просто добавляет новые строки. Быстро, но дублирует данные при перезаливах.
    2.  **Delete+Insert**: Удаляет строки за загружаемый период и вставляет новые. Хорошо для партиционированных данных.
    3.  **Merge (Upsert)**: Использует `MERGE` команду БД. Сравнивает по `unique_key`. Обновляет измененные, вставляет новые. Самая дорогая, но точная операция.

#### D. Ephemeral (Эфемерная)
*   **Механика**: Не создает объект в БД. Код модели компилируется и внедряется как **CTE** (Common Table Expression) в зависимые модели.
*   **Use Case**: Переиспользуемая логика очистки адресов, которую не нужно хранить отдельно, но нужно использовать в 10 витринах. Осторожно: может привести к гигантским SQL-запросам, которые планировщик БД не сможет переварить.

### 2.4. Data Quality Tests (Тестирование)

dbt превращает TDD (Test Driven Development) в реальность для данных.

*   **Generic Tests (Schema Tests)**:
    *   Описываются в YAML (`unique`, `not_null`, `accepted_values`, `relationships` (FK check)).
    *   Компилируются в SQL: `SELECT count(*) FROM table WHERE id IS NULL`. Если результат > 0, тест падает.
*   **Singular Tests (Data Tests)**:
    *   Отдельный `.sql` файл. Вы пишете запрос, который выбирает "плохие" данные.
    *   *Пример*: `SELECT * FROM orders WHERE total_amount < 0`. Отрицательных заказов быть не должно.

### 2.5. Snapshots (SCD Type 2 из коробки)

Один из самых мощных инструментов dbt для инженеров.
*   **Проблема**: В источнике `Users` перезаписывается поле `Status`. Истории изменений нет. Аналитикам нужно знать, когда статус изменился.
*   **Решение dbt Snapshot**:
    *   Вы указываете стратегию (`timestamp` или `check_cols`).
    *   dbt при каждом запуске сравнивает источник с целевой таблицей.
    *   Если видит изменение, он "закрывает" старую запись (ставит `dbt_valid_to = now()`) и вставляет новую (`dbt_valid_from = now()`).
    *   **Результат**: Вы получаете SCD Type 2 таблицу автоматически.

### 2.6. Artifacts & State Management (Advanced)

*   **manifest.json**: Это "бинарник" вашего проекта. Содержит хэши всех моделей.
*   **Slim CI (State Comparison)**:
    *   При запуске CI в Pull Request, dbt может скачать `manifest.json` из ветки `master`.
    *   Команда `dbt run --select state:modified` запустит *только* те модели, которые вы изменили, и их прямых потомков (+1 level children).
    *   Это экономит часы времени и деньги на облачных вычислениях.

### Резюме раздела 2
dbt — это больше чем SQL-runner. Это компилятор, который:
1.  Строит граф зависимостей через `ref()`.
2.  Абстрагирует DDL (Create/Merge) через стратегии материализации.
3.  Обеспечивает качество через тесты.
4.  Позволяет реализовать инкрементальную логику, критичную для обработки Big Data.

## 3. Orchestration: Airflow Internals & Architecture

**Apache Airflow** — это платформа для программного создания, планирования и мониторинга рабочих процессов (workflow).
Это **не** ETL-инструмент (он не должен обрабатывать гигабайты данных).
Это **Оркестратор** (Дирижер). Его задача — знать, *какую* задачу запустить, *когда* (время + зависимости) и *где* (Executor).

### 3.1. Компоненты Архитектуры (The 4 Pillars)

Airflow — это распределенная система. Понимание роли каждого компонента критично для отладки.

1.  **Metadata Database (Postgres/MySQL)**:
    *   **Роль**: Единый источник правды (Single Source of Truth).
    *   **Internals**: Здесь хранится состояние каждого TaskInstance (`RUNNING`, `QUEUED`, `SUCCESS`), определения DAG-ов, переменные (Variables) и соединения (Connections).
    *   *Важно*: Если БД недоступна или перегружена (CPU/IOPS), Airflow останавливается полностью. Webserver и Scheduler общаются **только** через БД.

2.  **Webserver**:
    *   **Роль**: UI для пользователя.
    *   **Internals**: Flask/Gunicorn приложение. Оно **ничего не запускает**. Оно просто читает состояние из БД и отображает его. Вы можете убить Webserver, и пайплайны продолжат работать.

3.  **Scheduler (Планировщик)**:
    *   **Роль**: "Мозг" системы. Определяет, что нужно запустить.
    *   **Internals**: Это многопоточный процесс, который работает в бесконечном цикле. В современных версиях (2.0+) он состоит из двух подсистем:
        *   **DagFileProcessor**: Парсит Python-файлы, ищет ошибки, обновляет определение DAG в БД.
        *   **SchedulerJob**: Проверяет состояние задач в БД и создает новые события запуска.

4.  **Executor (Исполнитель)**:
    *   **Роль**: Механизм запуска задач. Это *интерфейс*, а не конкретный процесс.
    *   *Типы*:
        *   **LocalExecutor**: Запускает задачи как подпроцессы на той же машине, что и Scheduler. (Для тестов).
        *   **CeleryExecutor**: Распределенная очередь. Scheduler кидает задачу в Redis/RabbitMQ. Воркеры (на других серверах) забирают задачи. (Стандарт для Prod).
        *   **KubernetesExecutor**: Для каждой задачи создается отдельный Pod в K8s кластере. Поднимается, делает работу, умирает. (Максимальная изоляция).

### 3.2. Жизненный цикл задачи (The Task State Machine)

Почему задача висит и не запускается? Ответ в переходах состояний.

1.  **No Status** -> **Scheduled**:
    *   Scheduler видит, что подошло время (`start_date` + `schedule_interval`). Создается `DagRun` (экземпляр запуска всего графа).
    *   Задачи первого уровня (без зависимостей) получают статус `SCHEDULED`.
2.  **Scheduled** -> **Queued**:
    *   Scheduler проверяет глобальные лимиты:
        *   `parallelism` (всего задач в системе).
        *   `concurrency` (задач внутри этого DAG).
        *   `pool slots` (свободные слоты в пуле ресурсов).
    *   Если ресурсы есть, задача отправляется в **Очередь Эгзекьютора** (например, в Redis). Статус меняется на `QUEUED`.
3.  **Queued** -> **Running**:
    *   Воркер (Celery Worker) забирает задачу из очереди.
    *   Воркер рапортует в БД: "Я взял задачу". Статус меняется на `RUNNING`.
    *   Выполняется метод `execute()` оператора.
4.  **Running** -> **Success / Failed / Upstream_Failed**:
    *   По завершении воркер обновляет статус в БД.
    *   Если задача упала, Scheduler проверяет `retries`. Если попытки есть -> `UP_FOR_RETRY`.

> **Zombie Tasks (Зомби)**: Ситуация, когда задача имеет статус `RUNNING` в БД, но процесс воркера на самом деле умер (OOM Kill, Segfault). Scheduler периодически запускает "Zombie Finder", сравнивая время последнего "хартбита" (heartbeat) задачи. Если хартбит старый — задача помечается как failed.

### 3.3. Главная проблема производительности: Top-Level Code

Это ошибка #1, которую допускают даже Senior разработчики.

**Как работает DagFileProcessor**:
Scheduler сканирует папку `dags/` постоянно (настройка `min_file_process_interval`, обычно 30 сек). Для этого он **импортирует** (выполняет) каждый Python-файл.

*   **Плохой код**:
    ```python
    # Top-level code
    from airflow import DAG
    import requests
    
    # ВОТ ОШИБКА: Этот запрос выполняется каждые 30 секунд Scheduler-ом!
    data = requests.get("https://api.my-service.com/config").json() 
    
    with DAG(...) as dag:
        ...
    ```
    *   *Результат*: Scheduler тормозит, API сервиса ложится под DDoS атакой от вашего планировщика.
*   **Правильный код**:
    Вся тяжелая логика, запросы к БД/API должны быть **внутри** операторов (в методе `execute`) или в шаблонах Jinja. Вне DAG-контекста должны быть только импорты и объявление структуры.

---

### 3.4. Передача данных: XComs vs External Storage

Airflow задачи изолированы. Задача A (Extract) и Задача B (Transform) могут выполняться на разных серверах. Как передать данные?

1.  **XCom (Cross-Communication)**:
    *   Механизм для передачи метаданных.
    *   `task_instance.xcom_push(key, value)` пишет запись в таблицу `xcom` в базе метаданных.
    *   **Лимиты**: Строго ограничено размером. (MySQL ~64KB, Postgres ~1GB, но на практике больше 50KB — антипаттерн).
    *   *Риск*: Если вы попытаетесь передать Pandas DataFrame через XCom, вы "взорвете" базу метаданных Airflow (bloat tables) и положите Scheduler.
2.  **External Storage (Паттерн для Practitioner)**:
    *   Задача A пишет файл в S3/GCS: `s3://bucket/data/2025-01-01.csv`.
    *   Задача A делает `xcom_push` только **пути** к файлу (строка).
    *   Задача B делает `xcom_pull`, получает путь и скачивает файл.

---

### 3.5. Time Travel: `execution_date`

Самый запутанный концепт Airflow.

*   **Ситуация**: У вас есть DAG с расписанием `@daily`.
*   **Запуск**: Пайплайн запускается **2 января в 00:00**.
*   **Logical Date (`execution_date` / `data_interval_start`)**: Будет равна **1 января**.
    *   *Почему?* Airflow считает, что 2 января мы обрабатываем данные *за прошедший период* (то есть за 1 января).
*   **Идемпотентность**: Ваш ETL-код должен использовать именно `{{ ds }}` (logical date) для фильтрации данных (`WHERE date = '2025-01-01'`), а не `datetime.now()`. Это позволяет перезапускать (Backfill) пайплайны за прошлый год, и они корректно обработают исторические данные.

### 3.6. Airflow vs. Prefect vs. Dagster (Сравнение 2025)

| Характеристика | Airflow | Prefect | Dagster |
| :--- | :--- | :--- | :--- |
| **Парадигма** | Task-based (Сделай X, потом Y) | Dynamic Task-based (Python code is the workflow) | Asset-based (Мне нужна таблица Z, построй её) |
| **DAG Structure** | Static (определена до запуска) | Dynamic (циклы, ветвления во время выполнения) | Static/Dynamic |
| **Data Passing** | XCom (Implicit) | Native Results (First-class citizen) | I/O Managers (Data Aware) |
| **Scheduler** | Centralized loop (Monolithic) | Hybrid (Cloud orchestrates, Agent executes) | Centralized |
| **Вердикт [P]** | Стандарт индустрии. Огромное комьюнити. Если нужен ETL "по расписанию" — берите Airflow. | Лучше для Data Science пайплайнов и сложной динамики. | Лучше для построения Data Platform (Data Mesh), где важны зависимости данных, а не задач. |

### Резюме раздела 3
Airflow — это система управления зависимостями.
1.  **Не пишите код на верхнем уровне**.
2.  **База данных — узкое место**, берегите её (не пишите большие XCom).
3.  **Идемпотентность** — используйте `logical_date` вместо `now()`.
4.  Понимайте **жизненный цикл задачи**, чтобы отличать нехватку ресурсов (Queued) от зависания воркера (Zombie).

## 4. Modern Challengers: Prefect & Dagster

Airflow был создан в 2014 году (эпоха Hadoop), когда мир был статичным: "Запусти эту джобу в 2 ночи".
Новые инструменты возникли как ответ на боли Airflow: сложность тестирования, проблемы с передачей данных и статичность графа.

### 4.1. Prefect: "Pure Python" и Гибридная модель

**Философия**: *"Ваш код — это и есть пайплайн"*.
Prefect пытается устранить разрыв между локальной разработкой и запуском в облаке. Если в Airflow вы пишете на DSL (Операторы, DAG контексты), то в Prefect вы пишете обычный Python, оборачивая его в декораторы.

#### А. Динамические графы (Dynamic Workflows)
В Airflow граф (DAG) строится **до** выполнения (во время парсинга).
В Prefect граф строится **во время** выполнения.

*   **Сценарий**: Прочитать папку, и для каждого из 1000 файлов запустить обработку.
*   **Airflow**: Требует `Dynamic Task Mapping` (появился недавно и сложен) или генерации DAG-файлов скриптом.
*   **Prefect**: Это просто цикл `for` или `.map()` в коде.
    ```python
    @flow
    def process_all_files():
        files = get_files() # Возвращает список неизвестной длины
        # Prefect создаст 10 или 1000 задач на лету
        process_file.map(files) 
    ```

#### Б. Hybrid Execution Model (Гибридная модель безопасности)
Это киллер-фича для Enterprise-сектора (Банки, Финтех).

*   **Control Plane (Облако Prefect)**: Оркестратор. Хранит историю запусков, UI, логи, расписание. Он говорит "Пора запускать".
*   **Data Plane (Ваша инфраструктура)**: Агент (Worker) внутри вашего K8s кластера или VPC.
*   **The Difference**: Код и **Данные никогда не покидает ваш периметр**. Облако Prefect видит только метаданные ("Task A started", "Task A failed"). Оно не видит содержимое `customer_data.csv`. Это решает проблему Compliance (GDPR/SecOps), избавляя от необходимости менеджить свой Airflow Webserver.

#### В. Управление состоянием (State Handlers)
Prefect возводит состояние в абсолют. Задача может быть не просто `Success/Failed`, но и `Retrying`, `Cached`, `Cancelled`, `AwaitingApproval`. Кэширование результатов (на основе хэша входных аргументов) работает из коробки, позволяя перезапускать флоу с середины без повторных вычислений.

---

### 4.2. Dagster: Asset-Centric Orchestration (Ориентация на Данные)

**Философия**: *"Пайплайн — это деталь реализации. Главное — это Ассет (Таблица)"*.
Dagster меняет парадигму с **императивной** ("Сделай задачу А, потом Б") на **декларативную** ("Мне нужна таблица `Users`, актуальная на сейчас").

#### А. Software-Defined Assets (SDA)
В Airflow вы видите граф задач: `extract_task` -> `load_task`. Вы не знаете, *что* эти задачи производят, пока не прочитаете код.
В Dagster граф состоит из Ассетов (Таблиц, ML-моделей, JSON-файлов).

```python
@asset
def raw_users():
    return read_csv("users.csv")

@asset
def clean_users(raw_users): # Dagster сам понимает зависимость!
    return raw_users.dropna()
```
*   **Impact**: Вы видите Lineage данных прямо в оркестраторе. Вы знаете, что если `raw_users` сломался, то `clean_users` будет устаревшим.

#### Б. Разделение IO и Логики (IO Managers)
Это архитектурный шедевр Dagster, решающий проблему тестирования.

*   **Проблема**: В коде задач мы часто смешиваем логику (`df['age'] * 2`) и IO (`df.to_parquet('s3://...')`). Чтобы протестировать логику, нужно мокать S3.
*   **Решение**: IO Manager — это интерфейс.
    *   В коде ассета вы просто возвращаете DataFrame/объект.
    *   Dagster (через конфигурацию) решает, куда его сохранить:
        *   *Local Dev*: `Pickle` на локальный диск.
        *   *Prod*: `Parquet` в S3 + `Snowflake Table`.
*   **Результат**: Юнит-тесты пишутся без моков внешних систем. Вы просто проверяете трансформацию данных.

#### В. Declarative Scheduling
Вместо "Запускать в 09:00", Dagster позволяет сказать: "Запускать `clean_users`, когда обновится `raw_users`" (Event-driven) или "Обеспечить, чтобы данные были не старее 1 часа" (Freshness policy).

---

### 4.3. Сравнительная матрица: Что выбрать Практику?

На уровне Practitioner выбор инструмента — это выбор компромиссов.

| Характеристика | **Apache Airflow** | **Prefect** | **Dagster** |
| :--- | :--- | :--- | :--- |
| **Ментальная модель** | **Task-based**. Списки задач. | **Python-based**. Функции и декораторы. | **Asset-based**. Таблицы и файлы. |
| **Кривая обучения** | Средняя. Нужно знать Operators, Sensors, XCom. | Низкая. "Просто Python". | Высокая. Новые концепции (Assets, Ops, Resources). |
| **Передача данных** | XCom (плохо подходит для больших данных). | Native results (лучше, но не идеально). | **IO Managers** (лучшее решение). |
| **Тестируемость** | Сложно (нужно поднимать DAGBag, мокать контекст). | Легко (обычные функции). | **Идеально** (разделение ресурсов и логики). |
| **Динамика** | Статичный граф (Dynamic Mapping появился, но сложен). | **Полностью динамический** (runtime loops). | Статичный граф ассетов / динамические партиции. |
| **Use Case 2025** | Стандартные ETL-батчи. Легаси миграции. Когда есть DevOps команда. | Data Science, ML-пайплайны, сложная динамическая логика. | Построение Data Platform, сложный ELT (dbt heavy), Data Mesh. |

### 4.4. Пример: Эволюция "Hello World"

**Airflow (Verbose & Boilerplate):**
```python
with DAG('example', start_date=...) as dag:
    t1 = PythonOperator(task_id='extract', python_callable=extract)
    t2 = PythonOperator(task_id='transform', python_callable=transform)
    t1 >> t2  # Зависимость задается явно
```

**Prefect (Pythonic):**
```python
@flow
def example_flow():
    data = extract()  # Вызов функции = Task
    transform(data)   # Зависимость через передачу данных
```

**Dagster (Asset Awareness):**
```python
@asset
def extracted_data(): ...

@asset
def transformed_data(extracted_data): ... # Зависимость через аргументы
```

### Резюме раздела 4
*   **Airflow** — это надежный "дизельный генератор". Старый, шумный, но проверенный.
*   **Prefect** — это "Python на стероидах". Выбирайте, если у вас ML-задачи или сложная динамика.
*   **Dagster** — это "Инженерный подход к данным". Выбирайте, если строите платформу данных с dbt и хотите видеть Lineage и иметь строгую типизацию.

## 5. Связка dbt + Airflow: Паттерны Интеграции

Главный вызов: Airflow ничего не знает о логике dbt (модели, тесты, сиды). dbt ничего не знает о расписании и ретраях. Наша задача — синхронизировать эти системы.

### 5.1. Контекст исполнения (Execution Context): Где запускать dbt?

Прежде чем говорить о паттернах графа, нужно решить, *где* физически выполняется команда `dbt run`.

1.  **Local Execution (`BashOperator` / `VirtualenvOperator`)**:
    *   *Механика*: dbt устанавливается (`pip install dbt-snowflake`) прямо в окружение Airflow Worker.
    *   *Антипаттерн*: **Dependency Hell**. Airflow и dbt могут требовать разные версии библиотек (например, `protobuf`, `jinja2`). Обновление dbt может сломать Airflow.
    *   *Вердикт*: Допустимо только для маленьких проектов или при использовании `VirtualenvOperator` (изолированный venv).
2.  **Containerized Execution (`KubernetesPodOperator` / `DockerOperator`)**:
    *   *Механика*: dbt упаковывается в отдельный Docker-образ. Airflow просто командует Кубернетесу: "Запусти этот под с командой `dbt run`".
    *   *Плюс*: Полная изоляция. Можно запускать разные версии dbt для разных пайплайнов.
    *   *Вердикт*: **Стандарт для Production**.

---
### 5.2. Pattern 1: The Monolith (Черный ящик)

Самый простой и (часто) самый надежный подход.

*   **Суть**: Весь dbt-проект запускается как **одна** задача Airflow.
*   **Реализация**:
    ```python
    dbt_run = KubernetesPodOperator(
        task_id='dbt_run_all',
        image='my-dbt-image:latest',
        cmds=["dbt", "build", "--select", "tag:daily"] 
    )
    ```
*   **Плюсы**:
    *   Минимальная нагрузка на Scheduler Airflow (1 задача вместо 500).
    *   dbt сам оптимизирует порядок выполнения (внутренний граф).
*   **Минусы (Visibility Gap)**:
    *   Если упала 99-я модель из 100, в Airflow задача горит красным целиком.
    *   Чтобы понять, *что* упало, нужно лезть в логи (текстовая портянка на 10,000 строк).
    *   Нельзя перезапустить (Retry) только упавшую модель через UI Airflow (только весь батч целиком или ручками через CLI).

---
### 5.3. Pattern 2: The Decomposition (Манифест-парсинг)

Попытка перенести граф dbt в граф Airflow 1-к-1.

*   **Механика**:
    1.  На этапе CI/CD мы компилируем dbt (`dbt compile`) и сохраняем `manifest.json`.
    2.  DAG-файл Airflow читает этот JSON.
    3.  Python-скрипт итерируется по узлам (`nodes`) в JSON и динамически создает `AirflowTask` для каждой модели.
    4.  Скрипт выстраивает зависимости (`>>`) на основе поля `depends_on` из манифеста.
*   **Плюсы**:
    *   **Granular Visibility**: Каждая модель — отдельный квадратик в UI Airflow. Зеленый/Красный статус виден сразу.
    *   **Granular Retry**: Можно перезапустить только одну упавшую витрину.
*   **Минусы (Scheduler Overload)**:
    *   Если у вас 1000 моделей, Airflow создаст 1000 задач. Это создает огромную нагрузку на мета-базу и планировщик. Рендеринг UI будет тормозить.
    *   Задержка (Latency): Между задачами Airflow есть накладные расходы (overhead) на запуск пода/процесса (от 5 до 60 секунд). 1000 задач * 10 секунд = 3 часа простого ожидания ресурсов.

---
### 5.4. Pattern 3: The Grouped Approach (Astronomer Cosmos) — Стандарт 2025

Библиотека `astronomer-cosmos` (или аналогичные самописные решения) объединяет лучшее из двух миров.

*   **Концепция**: Использовать `TaskGroup` (группировку задач) в Airflow для визуализации, но умный рендеринг для исполнения.
*   **Механика**:
    *   Cosmos автоматически парсит проект dbt.
    *   Он конвертирует модели dbt в задачи Airflow внутри `TaskGroup`.
    *   Поддерживает **Execution Mode**:
        *   *Local*: Выполняет в venv (быстро, но зависимо).
        *   *K8s*: Запускает поды.
*   **Ключевая фича**: Cosmos умеет умно группировать задачи, чтобы не создавать 1000 подов, но сохранять видимость.

```python
# Пример использования Cosmos
from cosmos import DbtDag, ProjectConfig, ProfileConfig

my_dbt_dag = DbtDag(
    project_config=ProjectConfig("/path/to/dbt/project"),
    profile_config=ProfileConfig(...),
    operator_args={"install_deps": True},
    # Cosmos сам построит граф на основе dbt
)
```

### 5.5. Продвинутые техники интеграции (Practitioner Tips)

Для уровня Expert/Practitioner важны нюансы:

1.  **`dbt build` vs `dbt run`**:
    *   Никогда не используйте `dbt run` в проде. Используйте `dbt build`.
    *   *Почему*: `build` запускает: Run Model -> Run Tests (сразу для этой модели) -> Snapshot -> Seed.
    *   Если тесты для модели А упали, модель Б (зависящая от А) **не запустится** (Skipped). Это предотвращает загрязнение хранилища плохими данными (Data Pollution).

2.  **Идемпотентность и `vars`**:
    *   Передавайте дату запуска из Airflow в dbt:
        `dbt build --vars '{"date": "{{ ds }}"}'`
    *   Внутри dbt модели используйте эту переменную для инкрементальной логики.

3.  **State Management (Slim CI в Airflow)**:
    *   Если вы перезапускаете упавший DAG, вы не хотите пересчитывать успешные модели.
    *   dbt не хранит состояние сам. Airflow хранит.
    *   Паттерн: при ретрае задачи Airflow (если используется Monolith pattern), команда должна быть:
        `dbt build --select result:error+ --defer --state /path/to/artifacts`
        (Это сложно настроить, поэтому Decomposed паттерн часто выигрывает в удобстве эксплуатации).

### Резюме: Матрица выбора

| Критерий | Monolith (BashOperator) | Decomposed (Manifest Parsing) | Cosmos (Library) |
| :--- | :--- | :--- | :--- |
| **Кол-во моделей** | < 5000 | < 200 | Любое (с группировкой) |
| **Visibility** | Низкая (логи) | Высокая (UI) | Высокая (UI) |
| **Overhead** | Низкий (1 под) | Высокий (N подов) | Средний |
| **Сложность настройки**| Низкая | Высокая (свой парсер) | Средняя (готовая либа) |
| **Рекомендация** | **Start here**. Используйте `--select` по тегам (hourly/daily). | Только для критичных DAG-ов, где важен точечный ретрай. | **Target state**. Лучший баланс. |

### Резюме для Практика [P]

1.  **ELT > ETL**: Грузим сырое, трансформируем в БД.
2.  **dbt**: Используем `ref()` для построения графа. Инкрементальные модели — ключ к производительности на больших данных.
3.  **Airflow**: Помните про Scheduler Loop. Не пишите тяжелый код на верхнем уровне DAG-файла. Используйте XCom только для метаданных.
4.  **Связка**: Не запускайте dbt как черный ящик, используйте интеграции (Cosmos) для видимости каждой модели в оркестраторе.

**TL;DR**:
*   **Star Schema (Kimball)**: Стандарт де-факто для **Data Marts (Витрин)** и слоя Presentation. Оптимизирована для чтения и понятна людям (BI-аналитикам).
*   **Snowflake Schema**: Нормализованная версия Звезды. Используется редко, для специфичных случаев экономии места или очень сложной иерархии измерений.
*   **Data Vault 2.0 (Linstedt)**: Стандарт для **Integration Layer (Raw Vault)** в крупных Enterprise-системах. Оптимизирован для гибкости, аудита и параллельной загрузки. Ужасен для прямого чтения BI-инструментами.

## 1. Dimensional Modeling (Размерное моделирование)

**Философия**: Размерное моделирование — это техника организации данных вокруг **бизнес-процессов**, оптимизированная для *понятности* человеком и *производительности* агрегации машиной. В отличие от 3NF (ER-модели), которая борется с дублированием данных (Write-Optimized), размерная модель *приветствует* контролируемое дублирование ради скорости чтения (Read-Optimized).

### 1.1. Четыре шага проектирования (The 4-Step Process)

Прежде чем рисовать схемы, архитектор обязан пройти алгоритм Кимбалла:

1.  **Select the Business Process (Выбор процесса)**: Не "Продажи", а конкретное событие: "Оформление строки заказа" (Order Line Creation) или "Получение платежа" (Payment Receipt).
2.  **Declare the Grain (Определение Гранулярности/Зерна)**: Критически важный шаг. Что означает одна строка в таблице фактов?
    *   *Пример*: Одна строка = Один товар в чеке (Line Item).
    *   *Ошибка*: Смешивание гранулярности (хранить и суммы по чеку, и товары в одной таблице).
3.  **Identify the Dimensions (Определение Измерений)**: Контекст "Кто, Где, Когда, Что, Почему".
4.  **Identify the Facts (Определение Фактов)**: Числовые показатели (Меры), которые мы будем суммировать/усренять (Количество, Сумма, Скидка).

---
### 1.2. Анатомия Star Schema (Схема Звезды)

Это стандарт де-факто для Presentation Layer.

#### A. Fact Table (Таблица Фактов) — "Центр гравитации"
Хранит результаты измерений бизнес-процесса.

*   **Типы фактов**:
    1.  **Transactional (Транзакционные)**: Событие в момент времени. Самая высокая детализация. (Пример: Клик по баннеру, пробитие товара).
    2.  **Periodic Snapshot (Периодический снимок)**: Состояние на конец периода. (Пример: Остаток на складе на 23:59 каждого дня).
    3.  **Accumulating Snapshot (Накапливающий снимок)**: Используется для процессов с началом и концом. Строка обновляется по мере прохождения этапов. (Пример: Заявка на кредит -> Одобрена -> Выдана. В одной строке даты всех этапов).
*   **Состав полей**:
    *   **Foreign Keys (FK)**: Ссылки на измерения (`product_key`, `date_key`).
    *   **Measures (Меры)**: Числа (`sales_amount`).
    *   **Degenerate Dimensions (Вырожденные измерения)**: Идентификаторы транзакций, которые не выносятся в отдельную таблицу (например, `Invoice Number`).

#### B. Dimension Table (Таблица Измерений) — "Душа хранилища"
Хранит контекст. Это таблицы, по которым мы делаем `GROUP BY` и `WHERE`.

*   **Surrogate Keys (Суррогатные ключи)**:
    *   Вместо использования ID из исходной системы (Natural Key, например `UUID` или `VARCHAR`), мы генерируем свой `Integer ID` (1, 2, 3...).
    *   *Зачем?*
        1.  **Производительность**: `JOIN` по `INT` быстрее, чем по `UUID`/String.
        2.  **SCD (Slowly Changing Dimensions)**: Если товар изменил название, у нас может быть две строки для одного `Product_SKU`: старая версия (Key=101) и новая (Key=102).
*   **Атрибуты**: Широкие таблицы (50-200 колонок) с текстовыми описаниями.
    *   *Пример `Dim_Date`*: Не просто дата, а: День недели, День года, Квартал, Праздник ли это, Фискальный месяц.

#### C. Conformed Dimensions (Согласованные измерения)
Главный секрет Enterprise-архитектуры.
*   Если `Dim_Customer` используется и в "Продажах", и в "Доставке", и в "Поддержке" — это **одна и та же таблица** (или view).
*   Это позволяет делать **Drill-Across**: строить отчеты, коррелирующие данные из разных бизнес-процессов ("Сколько купил клиент X и сколько тикетов в саппорт он создал").

### 1.3. Star Schema vs. 3NF: Почему Звезда побеждает в BI?

Многие бэкенд-разработчики интуитивно тяготеют к нормализации (Snowflake/3NF), чтобы избежать дублирования. Пример: *Не хранить `Category Name` в таблице `Product`, а вынести в `Category`.*

**Почему это плохо для аналитики (пример наглядности):**
Запрос: *"Сумма продаж по Категориям за 2024 год"*.

*   **В схеме Snowflake (Нормализованной)**:
    ```sql
    SELECT c.category_name, SUM(f.amount)
    FROM fact_sales f
    JOIN dim_product p ON f.product_id = p.id      -- JOIN 1 (Huge)
    JOIN dim_subcategory s ON p.sub_id = s.id      -- JOIN 2
    JOIN dim_category c ON s.cat_id = c.id         -- JOIN 3
    GROUP BY 1
    ```
    Оптимизатор базы данных должен "протащить" данные через 3 соединения. Если `fact_sales` — это 10 млрд строк, это больно.

*   **В схеме Star (Денормализованной)**:
    В таблице `dim_product` уже есть поле `category_name`. Да, оно дублируется миллион раз. Но в 2025 году хранение стоит копейки, а сжатие (Run-Length Encoding в Parquet) сжимает этот дубляж почти в ноль.
    ```sql
    SELECT p.category_name, SUM(f.amount)
    FROM fact_sales f
    JOIN dim_product p ON f.product_key = p.key    -- JOIN 1
    GROUP BY 1
    ```
    **Star Join Optimization**: Современные движки (Spark, BigQuery, Snowflake DB) видят этот паттерн и используют **Broadcast Hash Join** (отправляют маленькую таблицу измерений на все узлы кластера), что дает линейную масштабируемость.

---
### 1.4. Snowflake Schema (Схема Снежинки) — Когда все-таки нужна?

Снежинка — это Звезда, у которой измерения нормализованы (разбиты на подтаблицы).

**Use Cases для Практика [P]:**
1.  **Monster Dimensions**: Если у вас есть измерение `Dim_Customer` на 500 миллионов строк (например, B2C телеком), и вы часто меняете атрибуты (адреса). Денормализация может стать дорогой при обновлении. Нормализация части атрибутов может помочь.
2.  **Разреженность данных**: Если у вас иерархия атрибутов, где 90% полей пусты для определенных типов продуктов.
3.  **Low-Cardinality Aggregates**: Некоторые BI-инструменты (например, старые версии Cognos/BO) лучше работали со снежинкой для генерации SQL.

**Вердикт 2025**: Избегайте Снежинки по умолчанию. Начинайте со Звезды. Современные колоночные базы (Columnar Stores) делают штраф за чтение "широкой" таблицы измерений минимальным, так как читают только запрошенные колонки.

---
### 1.5. One Big Table (OBT) vs Star Schema

*Примечание: Это важный контекст для 2025 года.*

В системах типа ClickHouse или BigQuery часто идут дальше и отказываются даже от одного JOIN-а, сливая Факты и Измерения в одну гигантскую плоскую таблицу (**OBT**).

*   **Star Schema**: Логическая модель для гибкости (можно обновить название категории в одной строке `Dim_Category`, и оно обновится для всех исторических продаж).
*   **OBT**: Физическая оптимизация для скорости. Если нужно обновить категорию, придется перезаписать (Mutate) миллиарды строк фактов.

**Совет Архитектора**: Храните данные в слое Gold как **Star Schema** (для гибкости и ad-hoc запросов). Для конкретных дашбордов, которые тормозят, создавайте материализованные представления в виде **OBT**.

## 2. Data Vault 2.0 (Моделирование для Enterprise)

**Data Vault 2.0** (автор Дэн Линстедт) — это методология моделирования данных, разработанная специально для **аудируемости**, **гибкости** и **параллельной загрузки**.

В отличие от Kimball (который оптимизирован для *вывода* данных/BI), Data Vault оптимизирован для *ввода* данных (Ingestion) и устойчивости к изменениям бизнес-логики.

### 2.1. Фундаментальные принципы (The Core Tenets)

1.  **100% Auditability (Полная аудируемость)**: Raw Vault (Сырой слой) хранит данные "как есть" из источника. Если в источнике мусор — мы грузим мусор. Мы никогда не исправляем данные при загрузке в Raw Vault.
2.  **Insert-Only Architecture (Только вставка)**: Мы никогда не делаем `UPDATE` или `DELETE`. Изменение телефона клиента — это новая строка (INSERT) с новым временным штампом.
3.  **Separation of Keys, Relationships, and Context**: В обычных моделях (3NF/Star) ключ, связь и атрибуты живут в одной таблице. В DV мы разрезаем таблицу на три типа сущностей.

---

### 2.2. Анатомия сущностей Data Vault (The Primitives)

Представьте таблицу `Customer` из CRM, где есть ID, Имя, Телефон и ID Менеджера. В Data Vault мы "взрываем" эту таблицу на атомы.

#### A. Hub (Хаб) — "Бизнес-ключ"
Хранит список уникальных бизнес-объектов. Отвечает на вопрос: *"Видели ли мы этот объект раньше?"*

*   **Business Key (BK)**: Натуральный ключ из реального мира (VIN номер, E-mail, Номер паспорта, Номер заказа). Это "золотая нить", связывающая системы.
*   **Hash Key (HK)**: Первичный ключ Хаба. В DV 2.0 это всегда **MD5** или **SHA-256** хэш от Business Key.
*   **Структура**:
    *   `Hub_Customer_HK` (PK)
    *   `Customer_Number` (BK)
    *   `Load_Date` (Когда мы впервые увидели этот ключ)
    *   `Record_Source` (Откуда пришел: 'SAP', 'CRM')
*   *Важно*: Хаб не содержит описательных данных. Имя клиента здесь не хранится.

#### B. Link (Линк) — "Отношения"
Хранит связи между Хабами. Отвечает на вопрос: *"Как связаны объекты?"*

*   **Всегда Many-to-Many**: Даже если связь сейчас 1:1, в DV мы моделируем её как Линк. Это защищает от изменений бизнеса (Re-engineering proof).
*   **Структура**:
    *   `Link_Order_Customer_HK` (PK - Хэш от комбинации ключей Хабов)
    *   `Hub_Order_HK` (FK)
    *   `Hub_Customer_HK` (FK)
    *   `Load_Date`
    *   `Record_Source`
*   *Особенность*: Линк может связывать 2 и более Хабов (Multi-way Link).

#### C. Satellite (Сателлит) — "Контекст и История"
Хранит атрибуты (описания) и их историю изменений. Отвечает на вопрос: *"Какой был телефон у клиента 1 января?"*

*   **Родитель**: Всегда крепится к Хабу или Линку.
*   **Hash Diff**: Ключевое поле для DV 2.0. Это хэш от *всех атрибутов* строки. Используется для быстрого сравнения (Delta detection) при загрузке.
*   **Структура**:
    *   `Hub_Customer_HK` (FK - к кому относится)
    *   `Load_Date` (часть PK - когда стало актуальным)
    *   `Hash_Diff` (контрольная сумма данных)
    *   `Customer_Name`
    *   `Phone_Number`
    *   `Record_Source`

---

### 2.3. Data Vault 2.0 vs 1.0: Революция Хэширования

Для Практика [P] это критическое различие.
*   **В DV 1.0** использовались `Sequence ID` (автоинкремент БД). Чтобы загрузить Линк "Клиент-Заказ", нужно было сначала загрузить Хаб Клиентов, получить ID, загрузить Хаб Заказов, получить ID, и только потом грузить Линк. Это блокировало параллелизм.
*   **В DV 2.0** используются **Хэши**. Вы можете вычислить `MD5('Cust_123')` на стороне ETL (Spark/Kafka) *до* обращения к БД.
    *   *Результат*: Вы можете грузить Хабы, Линки и Сателлиты **абсолютно параллельно**. Скорость загрузки ограничена только шириной канала.

---

### 2.4. Архитектура слоев: Raw vs. Business Vault

Где писать бизнес-правила?

1.  **Raw Vault (Сырой Хранилище)**:
    *   Жесткие правила (Hard Rules): типы данных, длина строк.
    *   Никаких изменений значений. Если в источнике "USA", а в другом "U.S.A.", мы грузим как есть в разные сателлиты или строки.
    *   Цель: Аудит и возможность пересчета.

2.  **Business Vault (Бизнес Хранилище)**:
    *   Это надстройка над Raw Vault (часто виртуальная, в виде Views, или материализованная).
    *   Здесь применяются мягкие правила (Soft Rules): дедупликация, маппинг "USA" -> "US", расчет KPI.
    *   Здесь создаются **PIT** и **Bridge** таблицы (см. ниже).

---

### 2.5. Проблема производительности и её решение (PIT & Bridge)

Главный страх новичка в DV: *"Чтобы получить данные, мне нужно сделать 15 JOIN-ов. Это убьет базу"*.
Да, чистый Data Vault **не предназначен** для прямых запросов BI-инструментов.

**Инструменты ускорения (Performance Boosters):**

1.  **Point-In-Time (PIT) Table**:
    *   Проблема: У Хаба "Клиент" есть 3 сателлита (Персональные данные, Адрес, Скоринг) с разной частотой обновлений. Собрать их состояние на "1 января 2024" через SQL сложно (нужны подзапросы с `MAX(Date) <= '2024-01-01'`).
    *   Решение: Таблица PIT — это индекс. Она хранит готовые снимки ключей и дат для всех сателлитов на каждый момент времени.
    *   *Эффект*: Заменяет сложные подзапросы на простой Equi-Join.

2.  **Bridge Table**:
    *   Уплощает (Flattens) сложные цепочки Линков для быстрого доступа. Например, связь "Клиент -> Заказ -> Товар" сохраняется в одну широкую таблицу ключей.

---

### 2.6. Пример для наглядности: "Эволюция Схемы"

Представьте интернет-магазин.
**День 1**: У Клиента один Адрес.
*   *Kimball*: Поле `Address` в таблице `Dim_Customer`.
*   *Data Vault*: `Sat_Customer_Address` привязан к `Hub_Customer`.

**День 100**: Бизнес говорит: "У клиента теперь может быть много адресов (Доставка, Биллинг)".
*   *Kimball*: Паника. Нужно переделывать `Dim_Customer` в Snowflake или создавать Bridge-таблицу. Ломается обратная совместимость.
*   *Data Vault*:
    1.  Старый `Sat_Customer_Address` помечается как deprecated (но данные доступны).
    2.  Создается новый `Hub_Address`.
    3.  Создается `Link_Customer_Address`.
    4.  Новые данные льются в новую структуру. Старые отчеты работают на старом сателлите, новые — на Линке.
    *   **Результат**: Zero Downtime Migration.

### Резюме для Практика [P]

Используйте Data Vault 2.0, если:
1.  У вас **много систем-источников** (3+), которые нужно интегрировать по ключевым полям.
2.  Вам нужен **100% аудит** изменений (Time Travel).
3.  Бизнес-требования меняются быстрее, чем вы успеваете переписывать ETL.
4.  Вы используете **ELT** (Hadoop/Spark/Snowflake/BigQuery) и можете использовать мощь параллельного хэширования.

Не используйте DV, если вы делаете простую витрину для одного департамента. Оверхед на моделирование (количество таблиц x3) вас задушит.

## 3. Сравнительная Архитектура: Куда и что ставить?

В 2025 году стандартом де-факто является **Medallion Architecture** (Bronze -> Silver -> Gold), популяризированная Databricks, но применимая в любом стеке (Snowflake, BigQuery, ClickHouse). Вы должны понимать, какую модель применять на каждом слое и *почему* именно её.

---

Как архитектор, вы должны балансировать между тремя конфликтующими целями:
1.  **Скорость записи** (Ingestion Latency).
2.  **Гибкость интеграции** (Integration Agility).
3.  **Скорость чтения** (Query Performance).

Ни одна модель не решает все три задачи одновременно. Поэтому мы используем многослойную архитектуру.

### 3.1. Bronze Layer (Raw / Landing Zone)
*Цель: Не потерять ни байта исходной информации.*

*   **Модель данных**: **Отсутствует (Schema-on-Read)**.
    *   Мы не навязываем структуру. Если источник прислал JSON с новым полем — мы его сохраняем. Если CSV "поехал" — мы сохраняем битый CSV.
*   **Реализация**:
    *   Data Lake (S3 / ADLS) с файлами Parquet/Avro/JSON.
    *   Append-Only таблицы в DWH (Variant type в Snowflake, JSONB в Postgres).
*   **Историчность**: Храним полную историю изменений источника (CDC stream или daily snapshots).
*   **Почему так**: Если мы ошибемся в логике парсинга в Silver-слое, мы всегда сможем "переиграть" (Replay) данные из Bronze.

### 3.2. Silver Layer (Integration / Enterprise Data Warehouse)
*Цель: Создать единую, очищенную, интегрированную версию правды.*

Это самый сложный слой. Здесь данные из CRM (Salesforce), ERP (SAP) и Веба (Google Analytics) должны подружиться.

*   **Модель данных**: **Data Vault 2.0** (для Enterprise) или **3NF** (для простых систем).
*   **Почему Data Vault 2.0 — стандарт для Silver в 2025?**
    *   **Устойчивость к изменениям (Resilience)**: Если SAP добавил новое поле в "Клиента", в 3NF (3-я нормальная форма) вам нужно делать `ALTER TABLE` и мигрировать терабайты данных. В Data Vault вы просто добавляете новый Сателлит `Sat_SAP_Customer_Extension`.
    *   **Интеграция ключей**: Хаб (`Hub_Customer`) позволяет собрать ID из разных систем (Cookie ID, Email, Phone) в одну сущность, не сливая их атрибуты в одну широкую таблицу (что привело бы к конфликтам).
    *   **Аудит**: Мы храним техническую историю. Мы знаем, что 1 января имя было "Ivan", а 2 января стало "John".
*   **Очистка**: Здесь происходит дедупликация, стандартизация (US = USA), валидация типов.

### 3.3. Gold Layer (Presentation / Data Marts)
*Цель: Дать бизнесу ответы с максимальной скоростью.*

Бизнес-аналитик не должен писать SQL с 15 джойнами к Data Vault. Ему нужны понятные витрины.

*   **Модель данных**: **Star Schema (Kimball)** или **One Big Table (OBT)**.
*   **Процесс (Projection)**:
    *   Мы трансформируем данные из Silver (Data Vault) в Gold.
    *   Хабы и Линки превращаются в измерения (`Dim_Customer`, `Dim_Product`).
    *   Сателлиты "схлопываются" на нужную дату (используя PIT-таблицы) и превращаются в атрибуты измерений.
    *   Транзакционные Линки превращаются в Факты (`Fact_Sales`).
*   **Почему Star Schema**:
    *   BI-инструменты (PowerBI, Tableau, Looker) генерируют наиболее эффективный SQL именно для схемы звезды.
    *   Бизнес мыслит "Метриками" и "Разрезами".

### 3.4. Визуализация потока данных (The Data Flow Pipeline)

Пример: Интернет-магазин запускает новую программу лояльности.

| Слой | Действие и Структура | Что происходит |
| :--- | :--- | :--- |
| **Source** | JSON event | Прилетает событие `{user_id: 101, action: "loyalty_join", level: "gold"}` |
| **Bronze** | `raw_events` table (Variant/JSON) | Сохраняем JSON как есть. Добавляем `ingestion_timestamp`. |
| **Silver** | **Data Vault 2.0** | 1. Вычисляем хэш от `user_id`.<br>2. Если хэша нет в `Hub_User`, вставляем.<br>3. Вставляем атрибуты (level) в `Sat_Loyalty_Program`.<br>4. Создаем связь в `Link_User_Loyalty`. |
| **Gold** | **Star Schema** `Dim_User` | Обновляем таблицу измерения `Dim_User`. Теперь у пользователя 101 в колонке `loyalty_level` стоит "Gold". (SCD Type 1 или 2). |
| **BI** | Dashboard | Аналитик видит обновление уровня лояльности и строит график "Продажи Gold-пользователей". |

---

### 3.5. Архитектурная развилка: Virtual vs Materialized Gold

На уровне Practitioner вы столкнетесь с дилеммой: **хранить** Gold физически или **вычислять** на лету?

1.  **Materialized Gold (Классика)**:
    *   ETL-процесс (например, dbt) раз в сутки/час создает физические таблицы `Fact_Sales` и `Dim_User`.
    *   *Плюс*: Мгновенное чтение. Изоляция нагрузки.
    *   *Минус*: Задержка данных (Latency). Данные "протухают" до следующего запуска ETL. Дублирование данных (Storage costs).

2.  **Virtual Gold (Data Mesh подход / View-based)**:
    *   Gold — это просто набор SQL Views (`CREATE VIEW Fact_Sales AS SELECT ... FROM Silver_Vault`).
    *   *Плюс*: Real-time данные. Нулевое дублирование.
    *   *Минус*: Каждый запрос дэшборда нагружает Silver-слой и выполняет тяжелые джойны Data Vault.
    *   *Решение 2025*: Использовать **PIT (Point-in-Time)** таблицы в Silver слое для ускорения джойнов, но оставлять Gold виртуальным, пока производительность позволяет.

### Резюме для архитектора [P]

*   **Bronze**: Хаос в исходном формате.
*   **Silver**: Порядок и История (Data Vault). Это фундамент, который переживет смену BI-инструмента.
*   **Gold**: Скорость и Красота (Star Schema). Продукт для потребителя.

Никогда не пускайте BI-аналитиков в Silver слой. Они не поймут Data Vault и напишут "убийственные" запросы. Gold слой — это контракт (API) между Data Engineering и Business Intelligence.

## 4. One Big Table (OBT) — Современный тренд

**One Big Table (OBT)** — это архитектурный паттерн, при котором нормализация полностью устраняется путем объединения фактов и всех относящихся к ним измерений в одну экстремально широкую таблицу (часто 100–500+ колонок).

В эпоху Oracle/Postgres это считалось антипаттерном (из-за раздувания объема данных на диске). В эпоху Snowflake/ClickHouse/BigQuery это стало стандартом производительности.

### 4.1. Почему это работает: Физика колоночных СУБД

Чтобы понять OBT, нужно понять, как современные системы читают данные.

1.  **Сжатие данных (RLE — Run-Length Encoding)**:
    *   В строковой БД хранение строки "Electronics" в 1 миллиарде транзакций — это катастрофа для диска.
    *   В колоночной БД (Parquet/ClickHouse) колонка `Category` хранится отдельно. Значение "Electronics" встречается подряд 1,000,000 раз. Алгоритм RLE сжимает это в пару байт: `Value: "Electronics", Count: 1000000`.
    *   **Вывод**: Дублирование данных в OBT практически **не стоит денег** и места на диске.

2.  **Векторное исполнение (Vectorized Execution / SIMD)**:
    *   Процессор не обрабатывает строку за строкой. Он берет вектор (массив) значений одной колонки и применяет операцию ко всем сразу.
    *   При `JOIN` (в Star Schema) движок вынужден делать "Shuffle" (пересылку данных по сети) или Hash Join (построение хэш-таблицы в памяти), что ломает конвейер процессора.
    *   В OBT операция фильтрации `WHERE category = 'Electronics'` — это молниеносный скан одного сжатого вектора. Никаких прерываний, никаких пересылок.

---

### 4.2. OBT vs Star Schema: The Trade-off Matrix

Как архитектор, вы выбираете между **скоростью чтения** и **стоимостью обслуживания обновлений**.

| Характеристика | Star Schema (Fact + Dims) | One Big Table (Flat) |
| :--- | :--- | :--- |
| **Join Latency** | Есть (нужно время на соединение) | **Нулевая** (данные уже соединены) |
| **Storage Size** | Минимальный | Средний (сжатие нивелирует разницу, но все же больше) |
| **Update Anomaly** | **Нет**. Изменили `Dim_Product.Name` в одной строке — обновилось везде. | **Катастрофа**. Изменилось имя продукта — нужно перезаписать (Mutate) 100 млн строк в архиве продаж. |
| **Consistency** | Single Source of Truth | Risk of Drift (данные могут рассинхронизироваться при сбоях ETL) |
| **User Experience** | Требует понимания связей (Data Model aware) | "Excel-style". Пользователь видит все колонки сразу. |

---

### 4.3. Сложные типы данных: Nested & Repeated Fields

На уровне **Practitioner** важно знать: OBT в 2025 году — это не всегда "плоский CSV".
Современные хранилища (BigQuery, Snowflake, Databricks) поддерживают **полуструктурированные типы** (`ARRAY`, `STRUCT`, `MAP`).

Это решает проблему "взрыва строк" (Row Explosion) при отношениях 1:N.

*   *Сценарий*: Один Заказ (Order) -> Много Товаров (Items).
*   *Плоский OBT (Naive)*: Дублируем данные заказа для каждого товара.
    ```text
    Row 1: OrderID=1, Date='2025-01-01', Item='iPhone', Price=1000
    Row 2: OrderID=1, Date='2025-01-01', Item='Case',   Price=50
    ```
    *Проблема*: Если аналитик сделает `SUM(OrderTotal)`, он получит задвоенную сумму.
*   *Nested OBT (Advanced)*: Используем вложенные структуры.
    ```text
    Row 1: 
      OrderID=1, 
      Date='2025-01-01', 
      Items=[
        {Item='iPhone', Price=1000},
        {Item='Case',   Price=50}
      ]
    ```
    *   **Преимущество**: Гранулярность строки сохраняется ("Одна строка = Один заказ"), но детали доступны внутри массива. BigQuery (`UNNEST`) и ClickHouse (`ArrayJoin`) умеют работать с этим нативно.

---

### 4.4. Архитектурный паттерн: "Star to OBT Pipeline"

Не пытайтесь строить OBT сразу из источников (Bronze -> OBT). Это приведет к хаосу (Spaghetti Code).
Правильный паттерн в 2025 году выглядит так:

1.  **Silver Layer**: Нормализованные данные (Data Vault / 3NF). Здесь мы обеспечиваем целостность и историю.
2.  **Gold Layer (Logical)**: Star Schema. Здесь мы формируем бизнес-логику (Измерения и Факты).
3.  **Platinum Layer (Physical)**: **OBT**.
    *   Это **материализованный результат** джойна Star Schema.
    *   Создается инструментом типа **dbt** (Data Build Tool).
    *   Команда: `CREATE TABLE platinum.sales_flat AS SELECT * FROM gold.fact_sales JOIN gold.dim_product ...`

**Почему так?**
Если изменится логика расчета "Маржи", вы меняете её один раз в Gold слое (в SQL представлении). Затем запускаете пайплайн dbt, который пересчитывает (Full Refresh или Incremental) таблицу OBT.
OBT — это **кэш**, а не источник правды.

---

### 4.5. Use Cases: Когда OBT обязателен?

1.  **Embedded Analytics / User-Facing Dashboards**:
    *   Когда вы показываете аналитику конечному клиенту в личном кабинете.
    *   Требование: < 200ms на ответ при 1000 RPS.
    *   Star Schema не вытянет такой concurrency. OBT в ClickHouse — вытянет.
2.  **Data Science / ML**:
    *   Data Scientists ненавидят джойны. Им нужен "DateFrame" — плоская широкая матрица фичей для обучения модели. OBT — идеальный интерфейс для DS команды.
3.  **Self-Service BI для нетехнических пользователей**:
    *   Маркетолог в Tableau пугается, когда видит 10 таблиц и связи. Ему проще дать одну таблицу `Marketing_Everything`, где есть и Клики, и Кампании, и Бюджеты.

### Резюме раздела

**One Big Table (OBT)** — это физическая оптимизация Presentation-слоя.
*   Используйте **Star Schema** для гибкости и внутренней отчетности.
*   Используйте **OBT** (генерируемый из Star Schema) для "горячих" данных, ML-моделей и внешних пользователей.
*   Помните про **Nested Types**, чтобы избежать ошибок агрегации при отношениях 1:N.

## 5. 3NF (Third Normal Form): Классическая Нормализация

**3NF** — это метод моделирования, направленный на устранение избыточности данных путем их декомпозиции.
Главная мантра архитектора (повторяя за Биллом Кентом):
> *"Каждый атрибут (не-ключ) должен зависеть от Ключа, от Всего Ключа и Ни от чего, кроме Ключа. Так поможет мне Кодд."*

### 5.1. Физический смысл правил: Анатомия Аномалий

Нормальные формы (NF) — это не правила этикета. Это инженерные требования к **разделению жизненных циклов** различных бизнес-сущностей.
Если вы смешиваете сущности с разными жизненными циклами в одной таблице, вы получаете **Аномалии (Anomalies)**.

#### 1NF: First Normal Form (Атомарность и Гранулярность)

*   **Академическое правило**: "Значения в ячейках должны быть атомарными. Никаких повторяющихся групп или массивов".
*   **Пример нарушения**: Таблица `Users` с полем `emails`: `"work@corp.com, home@gmail.com"`.
*   **Физический смысл (The Why)**:
    1.  **SARGability (Index Usage)**: База данных не может построить B-Tree индекс по *части* строки. Поиск `WHERE emails LIKE '%gmail%'` приведет к **Full Table Scan** (полному перебору таблицы), что убьет производительность.
    2.  **Join Logic**: Вы не можете сделать `JOIN` с таблицей `Blacklist` по email, так как поле содержит мусор вокруг самого email-а.
    3.  **Type Safety**: Вы не можете гарантировать, что внутри строки валидный email, а не "12345".

> **Архитектурная ремарка 2025**: Современные БД (Postgres JSONB, Snowflake Variant) позволяют нарушать 1NF контролируемо. Мы храним массивы в JSON, но *только* если мы не планируем делать по ним частые джойны или если схема этих атрибутов крайне нестабильна.

---

#### 2NF: Second Normal Form (Зависимость от *Всего* Ключа)

*   **Контекст**: Применяется *только* к таблицам с **Составным Первичным Ключом** (Composite Primary Key). Например, таблица связи `Order_Items` (ключ: `Order_ID` + `Product_ID`).
*   **Академическое правило**: "Все неключевые атрибуты должны зависеть от *всего* составного ключа, а не от его части".
*   **Пример нарушения**:
    Таблица `Order_Items`:
    *   `Order_ID` (PK, Part 1)
    *   `Product_ID` (PK, Part 2)
    *   `Quantity` (Зависит от обоих: сколько *этого* товара в *этом* заказе) — **OK**.
    *   `Product_Name` (Зависит *только* от `Product_ID`) — **Нарушение!**
    *   `Product_Price` (Текущая цена в каталоге) — **Нарушение!**

*   **Физический смысл (The Why): Аномалии Жизненного Цикла**
    1.  **Insertion Anomaly (Аномалия Вставки)**: Вы не можете создать новый Товар в системе, пока его кто-то не купит. У вас нет места для хранения `Product_Name`, кроме как внутри строки заказа. Нет заказа — нет товара.
    2.  **Deletion Anomaly (Аномалия Удаления)**: Если вы удалите все заказы с товаром "iPhone 15", вы удалите из базы знание о том, что "iPhone 15" вообще существует. Вы стерли справочник вместе с транзакциями.
    3.  **Redundancy**: Имя товара "iPhone" повторяется миллион раз. Это увеличивает I/O нагрузку на буферный кэш.

---

#### 3NF: Third Normal Form (Разрыв транзитивных связей)

*   **Академическое правило**: "Никакой неключевой атрибут не должен зависеть от другого неключевого атрибута". (A -> B -> C).
*   **Пример нарушения**:
    Таблица `Employees`:
    *   `Emp_ID` (PK)
    *   `Emp_Name`
    *   `Dept_Code` (Код отдела - например, 'IT')
    *   `Dept_Name` (Название отдела - 'Information Tech') — **Нарушение!**
    *   `Dept_Location` (Офис отдела - 'Bldg 5') — **Нарушение!**
    *Здесь `Dept_Name` зависит от `Dept_Code`, а не от `Emp_ID`.*

*   **Физический смысл (The Why): Защита от Data Drift и Блокировок**
    1.  **Update Anomaly (Аномалия Обновления)**:
        Представьте, что отдел 'IT' переименовали в 'Digital Transformation'.
        *   *Без 3NF*: Вам нужно найти все 10,000 сотрудников этого отдела и сделать `UPDATE Employees SET Dept_Name = ...`.
        *   *Риск*: Если транзакция упадет на середине, у половины сотрудников будет "IT", у другой — "Digital". Данные стали **неконсистентными**.
    2.  **Lock Contention (Конкуренция блокировок)**:
        Массовый апдейт 10,000 строк в таблице `Employees` заблокирует работу HR-системы (нельзя нанимать/увольнять), пока идет переименование отдела.
        *   *В 3NF*: Вы обновляете **одну** строку в таблице `Departments`. Блокировка длится миллисекунду.
    3.  **Single Source of Truth**:
        Если адрес офиса 'Bldg 5' хранится в каждом сотруднике, высока вероятность, что у кого-то останется старый адрес. 3NF гарантирует, что адрес хранится в одном месте.

### Резюме: Как думать о Нормальных Формах

Как Практик, используйте следующую мнемонику для проверки таблиц:

1.  **1NF (Списки)**: Не храните списки в строках. Нужен список? Создай дочернюю таблицу 1:N.
2.  **2NF (Справочники внутри связей)**: Если у вас таблица "многие-ко-многим", не храните в ней описания связываемых объектов. Храните только факты самой связи (дата, количество).
3.  **3NF (Цепочки зависимостей)**: Если поле B описывает поле A, а не ID строки — вынесите A и B в отдельный справочник.

> **"Каждый атрибут должен быть фактом о Ключе (1NF), о Всем Ключе (2NF) и Ни о чем, кроме Ключа (3NF)"**.

---
### 5.2. 3NF в Хранилищах Данных: Подход Билла Инмона (CIF)

В мире DWH есть два лагеря:
*   **Кимбалл (Bottom-Up)**: Строим витрины (Star Schema) сразу для бизнеса.
*   **Инмон (Top-Down)**: Сначала строим идеальную нормализованную модель всего предприятия (EDW в 3NF), а потом нарезаем из неё витрины.

**Роль 3NF в Silver Layer:**
В архитектуре Инмона (Corporate Information Factory) слой интеграции (Silver) строится именно в 3NF.
*   **Преимущества**:
    *   **Single Version of Truth**: Данные хранятся один раз. Нет риска, что в таблице Продаж город один, а в таблице Доставки — другой.
    *   **Нейтральность**: Модель не зависит от того, как строятся отчеты. Она отражает структуру бизнеса, а не структуру дэшборда.
*   **Недостатки (Почему Data Vault побеждает)**:
    *   **Cascading Changes**: Добавление нового отношения может потребовать изменения структуры многих таблиц (ALTER TABLE).
    *   **Performance**: Для сборки бизнес-объекта нужны десятки JOIN-ов (еще больше, чем в Star Schema, так как справочники сильно раздроблены).

---
### 5.3. 3NF vs Data Vault 2.0: Битва за Integration Layer

Это самый частый вопрос на Architecture Review Board. Что выбрать для ядра хранилища?

| Характеристика | 3NF (Normalized) | Data Vault 2.0 |
| :--- | :--- | :--- |
| **Отношение к связям** | Жесткие Foreign Keys. Связи "зашиты" в структуру таблиц. | Связи вынесены в отдельные таблицы Links. Структура гибкая. |
| **История изменений** | Обычно SCD Type 2 (доп. колонки start/end date). Сложно поддерживать. | Нативная (Satellites). Каждый INSERT — новая версия правды. |
| **Загрузка** | Требует строгого порядка (Сначала Parent, потом Child). Плохо параллелится. | Полностью параллельная (Hash Keys). |
| **Сложность модели** | Средняя (понятна DBA). | Высокая (в 3 раза больше таблиц). |
| **Рефакторинг** | Болезненный. Изменение бизнес-правил = миграция данных. | Легкий. Добавляем новый Линк/Сателлит, старые не трогаем. |

**Вердикт Архитектора**:
В 2025 году **3NF умирает в слое DWH Integration**. Data Vault выигрывает за счет гибкости (Agility).
Однако, **3NF живет в ODS (Operational Data Store)** — операционных репликах, которые используются для интеграции приложений "в реальном времени", а не для аналитики.

### 5.4. Пример эволюции: От Excel к 3NF

Представьте данные о продажах.

**Stage 0: Unnormalized (Excel / OBT)**
| Order_ID | Customer | Customer_City | Product | Supplier | Supplier_Phone |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 101 | Ivan | Moscow | Laptop | TechCorp | 555-01 |
| 102 | Ivan | Moscow | Mouse | TechCorp | 555-01 |

*Проблемы*: Дублирование "Moscow", дублирование телефона поставщика. Если TechCorp сменит телефон, нужно менять везде.

**Stage 3: 3NF Implementation**

1.  **Table `Customers`**:
    *   `Cust_ID` (PK), `Name`, `City_ID` (FK).
    *   *Note*: `City` вынесли, так как Город — это отдельная сущность.
2.  **Table `Cities`**:
    *   `City_ID` (PK), `Name`, `Region`.
3.  **Table `Products`**:
    *   `Prod_ID` (PK), `Name`, `Supplier_ID` (FK).
4.  **Table `Suppliers`**:
    *   `Supp_ID` (PK), `Name`, `Phone`.
5.  **Table `Orders`** (Header):
    *   `Order_ID` (PK), `Cust_ID` (FK), `Date`.
6.  **Table `Order_Details`** (Line Items):
    *   `Order_ID` (FK), `Prod_ID` (FK), `Quantity`.

Теперь, если поставщик меняет телефон, мы делаем `UPDATE` в **одной** строке таблицы `Suppliers`. Это и есть цель 3NF — **Write Optimization**.

### Резюме раздела 5

Используйте **3NF** в архитектуре данных, если:
1.  Вы проектируете **OLTP-систему** (микросервис, бэкенд приложения).
2.  Вы строите **ODS** (операционный слой) с требованиями строгой консистентности и частых обновлений (Updates).
3.  У вас **маленькое хранилище** (не Enterprise scale), и оверхед Data Vault (x3 таблиц) избыточен.

Не используйте 3NF для **аналитических витрин** (Presentation Layer) — замучаете пользователей джойнами. Для этого есть Star Schema.

## 6. Практические нюансы реализации (Practitioner Tips)

1.  **Surrogate Keys (Суррогатные ключи)**:
    *   *Kimball*: Обычно `Integer` (Sequence). Экономит память, но требует lookup при загрузке.
    *   *Data Vault*: Строго `Hash` (MD5/SHA-256) от Business Key. Позволяет считать ключи на стороне ETL (Spark/dbt) детерминированно.
2.  **SCD (Slowly Changing Dimensions)**:
    *   В **Star Schema** вы мучаетесь с выбором: SCD Type 1 (перезапись), Type 2 (история строк), Type 3 (доп. колонка).
    *   В **Data Vault** SCD встроено архитектурно. Любое изменение атрибута — новая строка в Сателлите. При выгрузке в Mart вы сами решаете, какой тип SCD проецировать (актуальное состояние или срез на дату).
3.  **Bridge Tables**:
    *   В Star Schema для связи M-to-M (Врачи <-> Пациенты) используются Bridge-таблицы. Это убивает производительность.
    *   В Data Vault это нативный Link.

**Итоговый совет архитектора**:
Используйте **Data Vault** в ядре хранилища, если у вас сложный ландшафт (5+ систем-источников) и высокие требования к аудиту. Используйте **Star Schema** на выходе для потребителей. Если у вас стартап с одной базой MySQL — Data Vault будет оверхедом, стройте сразу Star Schema.

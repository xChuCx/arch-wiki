**TL;DR**:
*   **Shuffle** — самая дорогая операция (Disk I/O + Network I/O + Serialization). Ваша цель — отложить его, устранить или уменьшить объем данных перед ним.
*   **Skew (Перекос)** — главный убийца производительности. Если 99 задач завершились за минуту, а одна висит час — у вас Skew. Решение: AQE или Salting.
*   **Broadcast Join** — превращает распределенный Join в локальный (Map-side), убирая Shuffle. Но может убить Driver (OOM).

## 1. Фундаментальные основы и Анатомия Spark Shuffle

Прежде чем лезть "под капот" перемешивания данных, мы должны синхронизировать понимание контекста.

## 1.1. Batch Processing и Архитектура Spark

**Batch Processing (Пакетная обработка)** — это метод обработки ограниченного (bounded) набора данных, где приоритетом является **пропускная способность (Throughput)** — количество байт в секунду, а не латентность (Latency).
*   В отличие от стриминга, мы знаем "конец" файла. Это позволяет движку строить глобальный план оптимизации (Cost-Based Optimizer) и делать массивные сортировки.

**Архитектура Apache Spark (The Physical View):**

Spark — это **MPP (Massively Parallel Processing)** система, работающая в памяти.
1.  **Driver (Мозг)**: JVM процесс, где живет `SparkContext`. Он компилирует код в DAG (граф задач), запрашивает ресурсы у Cluster Manager (YARN/K8s) и раздает задачи.
2.  **Executor (Мускулы)**: JVM процессы на рабочих узлах. Они хранят данные (Cache) и выполняют задачи (Tasks).
3.  **Slot / Core**: Единица параллелизма внутри Экзекьютора. 1 Core = 1 активный поток (Thread), обрабатывающий 1 Партицию данных.

**Ключевая концепция: The DAG & Stages**
Spark не выполняет операции по одной. Он строит **DAG (Directed Acyclic Graph)**.
*   **Narrow Dependency (Узкая зависимость)**: Данные для вычисления остаются на том же узле (Map, Filter, Union). Не требует сети.
*   **Wide Dependency (Широкая зависимость)**: Данные для вычисления должны быть собраны с разных узлов (GroupBy, Join, Distinct, Sort). **Это и есть Shuffle**.
*   **Stage (Этап)**: Границы этапов проходят *только* там, где случается Shuffle.

## 1.2. Spark Shuffle Internals: Механика Хаоса

**Shuffle** — это процесс физического перераспределения данных (re-partitioning) между экзекьюторами. Это единственная точка в Spark, где нарушается принцип "Data Locality" (вычисления идут к данным). Здесь данные идут к вычислениям.

Это "Ахиллесова пята" Spark. 90% проблем производительности (OOM, зависания, Stragglers) живут здесь.

### Эволюция (для контекста)
*   *Hash Shuffle (Spark < 1.2)*: Создавал M*R файлов (M мапперов * R редьюсеров). На больших кластерах это убивало файловую систему миллионами мелких файлов. **Deprecated**.
*   **Sort-Based Shuffle (Текущий стандарт)**: Map-задача создает всего **2 файла** (Data + Index). Это радикально снижает нагрузку на inode файловой системы и Random I/O.

---
### Фаза 1: Map Side (Write Path) — Сортировка и Сброс

Представьте, что Executor A обрабатывает партицию данных и должен разбросать её на 200 целевых партиций (Reducer-ов).

1.  **Buffering (Наполнение буфера)**:
    *   Данные поступают в память. Используется специальная структура данных: `PartitionedAppendOnlyMap` (если есть агрегация, например `.reduceByKey`) или `PartitionedPairBuffer` (если просто `.sortByKey`).
    *   **Критично**: Эти буферы живут в **Execution Memory**.

2.  **In-Memory Sort (Сортировка)**:
    *   По мере поступления, Spark сортирует записи *внутри буфера* по `PartitionId` (кому отправить?).
    *   *Зачем?* Чтобы потом записать данные для Reducer 1, потом для Reducer 2 и т.д. последовательными кусками.

3.  **Spill to Disk (Сброс на диск)**:
    *   Если буфер заполнен (достигнут порог `spark.memory.fraction`), Spark не падает с OOM. Он делает **Spill**.
    *   Буфер сортируется и сбрасывается на диск во временный файл.
    *   *Performance Impact*: Spill — это убийца скорости. Это (а) Сериализация, (б) Disk Write, (в) потом Disk Read.
    *   *Метрика*: В Spark UI смотрите "Disk Spill (Memory)" vs "Disk Spill (Data)". Разница показывает коэффициент десериализации.

4.  **Final Merge (Слияние)**:
    *   Задача завершена. На диске лежит 50 мелких spill-файлов.
    *   Spark сливает их в **Один большой файл данных (Data File)**.
    *   Параллельно создается **Индексный файл (Index File)**. Он содержит смещения (offsets): "Данные для Partition 0 лежат с 0 по 1024 байт. Для Partition 1 — с 1024 по 5000".

---
### Фаза 2: Reduce Side (Read Path) — Сбор урожая

Теперь стартует следующий Stage. Редьюсеры (новые задачи) должны собрать свои данные.

1.  **MapOutputTracker**:
    *   Редьюсер обращается к Драйверу: "Я отвечаю за Партицию №5. На каких узлах лежат данные для меня?"
    *   Драйвер отдает список адресов и смещений (спасибо индексному файлу).

2.  **Block Transfer (Вытягивание)**:
    *   Редьюсеры открывают соединения к нужным Экзекьюторам (Map-side) и скачивают свои куски данных.
    *   Используется **Netty** (асинхронный I/O).
    *   *Настройка*: `spark.reducer.maxSizeInFlight` (по умолчанию 48MB) определяет, сколько данных мы тянем одновременно. Если сеть забита — уменьшаем.

3.  **Aggregation / Sort**:
    *   Прилетающие данные снова попадают в буфер (`ExternalAppendOnlyMap`), где они мерждатся и агрегируются.
    *   Если данных больше, чем памяти у Редьюсера — снова происходит Spill на диск.

---
### 1.3. Специализированные оптимизации Shuffle

На уровне Expert [E] вы не просто используете дефолтный шаффл, вы знаете его вариации.

#### A. Bypass Merge Sort Shuffle (Прямая запись)
*   **Условие**: Количество партиций шаффла мало (<= 200, конфиг `spark.shuffle.sort.bypassMergeThreshold`) И нет Map-side агрегации (например, просто `.repartition` или `.join` без предварительной группировки).
*   **Механизм**:
    *   Мы **не сортируем** данные в памяти.
    *   Мы сразу открываем N файлов (по числу партиций) и пишем в них.
    *   Потом просто склеиваем файлы (concatenation).
*   **Выигрыш**: Нет дорогой CPU-операции сортировки.
*   **Риск**: Если партиций 10,000, мы откроем 10,000 файловых дескрипторов и получим "Too many open files".

#### B. Tungsten Sort (Unsafe Shuffle)
Spark использует проект **Tungsten** для управления памятью.
*   Вместо Java Objects (`Integer`, `String`), которые имеют огромный оверхед (заголовок объекта 12-16 байт), Spark использует **UnsafeRow**.
*   Это "сырые" байты в Off-Heap памяти (как в C++).
*   **Сортировка**: Spark сортирует массивы указателей (Pointer Arrays) на бинарные данные, используя **Radix Sort** (поразрядная сортировка). Она работает за O(N), а не O(N log N) как TimSort. Это работает только если схема данных позволяет (примитивные типы, не UDF).

### 1.4. Пример для наглядности (The Data Journey)

Представьте `JOIN` таблицы Заказов (`Orders`, 1TB) и Клиентов (`Customers`, 50GB) по `ClientID`.

1.  **Map Stage (Executor 1, обрабатывает кусок Orders)**:
    *   Читает строку: `{ID:100, ClientID:5, Amount:50}`.
    *   Хэширует ключ: `hash(5) % 200 (partitions) = Partition 5`.
    *   Кладет в буфер.
    *   Буфер переполнен -> Сортирует -> Пишет на диск кусок для Partition 5.
    *   В конце: Создает файл `shuffle_data_1.0` где кусок для Partition 5 лежит по адресу 0x5000.
2.  **Network**:
    *   Executor 2 (отвечает за Reduce Partition 5) стучится к Executor 1.
    *   Скачивает кусок по адресу 0x5000.
3.  **Reduce Stage (Executor 2)**:
    *   Получает куски для `ClientID:5` со всех узлов.
    *   Получает куски для `ClientID:5` из таблицы Customers.
    *   Джойнит их в памяти (SMJ).

### Резюме раздела 1

*   **Shuffle — это IO-барьер**. Пока он не завершится, следующая стадия не начнется.
*   **Spill — это враг**. Если вы видите Spill в UI, значит, вы выделили мало памяти на задачу или у вас перекос (Skew).
*   **Маленькие файлы — это смерть**. Огромное количество партиций шаффла (например, дефолтные 200 на петабайтах данных) приведет к созданию гигантских файлов и Spill. Малое количество — к неиспользованию ядер. Тюнинг `spark.sql.shuffle.partitions` — первая обязанность инженера.

## 2. Join Strategies: Выбор оружия

В распределенных системах `JOIN` — это самая тяжелая операция. В отличие от монолитных СУБД (Postgres), где джойн происходит локально, в Spark данные разбросаны по 1000 узлам.

Чтобы соединить таблицу A и таблицу B, Spark должен гарантировать, что строки с одинаковым ключом окажутся **на одном физическом узле** (Co-location).

### 2.1. Broadcast Hash Join (BHJ) — "Map-Side Join"

Самая быстрая стратегия. Полностью исключает Shuffle.

*   **Механизм**:
    1.  **Broadcast**: Spark берет *меньшую* из двух таблиц (Build Side), скачивает её на Driver, а затем рассылает копию на *каждый* Executor.
    2.  **Hash Map**: На каждом экзекьюторе маленькая таблица превращается в хэш-карту (в памяти).
    3.  **Local Join**: Большая таблица (Stream/Probe Side) читается потоково. Каждая строка проверяется на наличие в хэш-карте.
*   **Сетевой протокол (TorrentBroadcast)**:
    *   Чтобы Драйвер не "лопнул" от отдачи данных всем, используется P2P протокол (BitTorrent-like). Первые экзекьюторы, скачавшие куски, начинают раздавать их остальным.
*   **Условия применения**:
    *   Размер одной таблицы < `spark.sql.autoBroadcastJoinThreshold` (по дефолту 10MB, в 2025 году часто ставят 100MB-1GB, если позволяет память).
    *   **Hint**: `/*+ BROADCAST(small_table) */` форсирует эту стратегию.
*   **Ограничения Эксперта**:
    *   **Memory Pressure**: Хэш-карта должна целиком влезать в память экзекьютора *плюс* оверхед.
    *   **Max Size**: Нельзя сбродкастить таблицу больше 8GB (ограничение блока Spark).
    *   **No Full Outer Join**: BHJ не поддерживает полный внешний джойн (техническое ограничение потоковой обработки).

### 2.2. Sort-Merge Join (SMJ) — "Танк"

Стратегия по умолчанию для соединения двух больших таблиц (с Spark 2.3+). Самая надежная, но не самая быстрая.

*   **Механизм**:
    1.  **Shuffle (Exchange)**: Данные обеих таблиц пересылаются по сети. Ключи `K` попадают в одну партицию.
    2.  **Sort**: Обе стороны *сортируются* по ключу джойна на диске/в памяти.
    3.  **Merge**: Spark бежит двумя итераторами по отсортированным спискам (Zip-like operation).
*   **Почему это Default? (OOM Resistance)**:
    *   Главное преимущество SMJ — он **Spillable**. Если данные не лезут в память, сортировка сбрасывается на диск, и мердж идет с диска.
    *   Spark жертвует CPU (на сортировку) ради стабильности (чтобы не падать с OOM на терабайтных джойнах).
*   **Стоимость**:
    *   Двойной Shuffle + Двойная Сортировка. Очень дорого по CPU.

### 2.3. Shuffle Hash Join (SHJ) — "Забытый герой"

Используется редко, но в определенных кейсах рвет SMJ по скорости.

*   **Механизм**:
    1.  **Shuffle**: Данные пересылаются по сети (как в SMJ).
    2.  **No Sort**: Мы НЕ сортируем данные.
    3.  **Hash Build**: Из данных *меньшей* партиции строится Хэш-карта.
    4.  **Hash Probe**: Данные большей партиции "протыкают" (probe) эту карту.
*   **Когда применять?**
    *   Когда таблицы большие (не влезают в Broadcast), но **одна значительно меньше другой**.
    *   Когда сортировка (Sort) слишком дорогая (например, ключи — длинные строки).
*   **Риск (Expert Warning)**:
    *   В отличие от SMJ, построение Хэш-карты в SHJ **плохо спиллится**. Если в одну партицию прилетит перекос (Skew) данных, построение карты упадет с OOM.
    *   Нужно включать принудительно: `spark.sql.join.preferSortMergeJoin = false` или через хинт `/*+ SHUFFLE_HASH(t) */`.

### 2.4. Broadcast Nested Loop Join (BNLJ) — "Звезда Смерти"

Если вы видите это в плане запроса без явного намерения — у вас проблемы.

*   **Механизм**:
    *   Берет таблицу А, бродкастит её.
    *   Для *каждой* строки таблицы Б пробегает *всю* таблицу А (Nested Loop).
*   **Сложность**: `O(N * M)`. Это Декартово произведение (Cartesian Product).
*   **Когда возникает**:
    *   Не-равностные джойны (`ON a.id > b.id`).
    *   Джойны без условия (`CROSS JOIN`).
    *   Ошибки статистики (Spark думает, что таблицы пустые).
*   **Результат**: Задача висит вечно, кластер греет воздух.

### 2.5. Bucketed Join — "Святой Грааль" оптимизации

Единственный способ убрать Shuffle при джойне двух *больших* таблиц.

*   **Идея**: Мы заранее (на этапе записи ETL) разбиваем данные на N бакетов по ключу и сортируем их.
*   **Запись**: `df.write.bucketBy(100, "user_id").sortBy("user_id").saveAsTable("bucketed_users")`.
*   **Чтение**:
    *   Если мы джойним две бакетированные таблицы (по тому же ключу и с тем же числом бакетов), Spark видит: "Ого, данные уже лежат на нужных местах и отсортированы!".
    *   **Shuffle — пропускается**.
    *   **Sort — пропускается**.
    *   Сразу начинается Merge.
*   **Expert Caveat**: Работает только для Hive-таблиц (не для простых Parquet-файлов). Количество бакетов должно совпадать (или быть кратным в Spark 3.x).

### Сравнительная матрица (Decision Matrix)

| Стратегия | Shuffle? | Sort? | OOM Risk | Скорость | Условие выбора Catalyst |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Broadcast Hash** | Нет (Copy) | Нет | High (Driver/Exec RAM) | 🚀🚀🚀 | Одна таблица < 10MB (config) |
| **Shuffle Hash** | Да | Нет | High (Skew kills it) | 🚀🚀 | Одна партиция влезает в память, Sort выключен |
| **Sort Merge** | Да | Да | Low (Spills to disk) | 🚜 (Reliable) | Дефолт для больших таблиц |
| **Cartesian (BNLJ)** | Нет (Copy) | Нет | Extreme (CPU death) | 🐌 | Non-equi joins |

### Пример для наглядности: "Почему Catalyst ошибается?"

Вы джойните таблицу `Users` (100 MB) и `Logs` (1 TB).
1.  **Сценарий А**: Вы сделали `ANALYZE TABLE Users COMPUTE STATISTICS`. Spark знает, что `Users` весит 100MB. Лимит Broadcast = 10MB. Spark выбирает **SMJ**.
    *   *Expert Action*: Вы знаете, что 100MB влезут в память. Вы даете хинт `/*+ BROADCAST(u) */` или повышаете лимит. Скорость x10.

2.  **Сценарий Б**: Вы отфильтровали `Users`: `Users.filter(city = 'Moscow')`. Spark не знает, сколько пользователей в Москве (статистика есть только по всей таблице). Он может перестраховаться и выбрать SMJ, хотя в Москве всего 1000 юзеров.
    *   *Expert Action*: AQE (Adaptive Query Execution) в Runtime увидит реальный размер и переключит SMJ на BHJ на лету. Включите `spark.sql.adaptive.enabled = true`.

## 3. Data Skew: Главный враг SLA

**Data Skew (Перекос)** — это неравномерное распределение нагрузки между экзекьюторами, вызванное природой данных.
В идеальном мире: $Time_{Job} \approx \frac{TotalWork}{N_{Cores}}$.
В мире Skew: $Time_{Job} \approx Time_{SlowestTask}$.

**Закон Амдала в действии**: Если 1000 задач завершились за 5 секунд, а одна задача (Straggler) обрабатывает "жирный" ключ 1 час, то время выполнения всего этапа — 1 час. Остальные 999 ядер простаивают, сжигая деньги облачного провайдера.

### 3.1. Диагностика: Как увидеть Skew в Spark UI?

Эксперт не гадает, он смотрит на метрики **Stages**.
1.  **Duration Distribution**: Смотрим на перцентили времени выполнения задач.
    *   *Норма*: Max Time ≈ 1.2-1.5 x Median Time.
    *   *Skew*: Median = 10s, **Max = 45min**.
2.  **Shuffle Read Size**:
    *   *Skew*: Большинство задач прочитали по 100MB, одна задача — **15GB**.
3.  **Spill (Memory/Disk)**:
    *   Перекошенная задача почти всегда вылетает за лимиты памяти и начинает спиллить на диск.

### 3.2. Типология Перекосов

1.  **Null Skew (Самый частый)**:
    *   При `LEFT JOIN` по ключу `user_id`, если в левой таблице 50% записей имеют `user_id = NULL`, все они попадут в **одну** хэш-партицию (так как `hash(null)` константа).
2.  **Key Skew (Естественный)**:
    *   Ритейл: Один B2B-клиент делает 1 млн заказов, обычные люди — по 5.
    *   Веб-логи: IP-адрес поискового бота генерирует в 1000 раз больше хитов, чем живой пользователь.
3.  **Partition Skew (Файловый)**:
    *   Данные лежат в S3, один файл GZIP весит 2GB (не сплитится), остальные по 100MB. Одна задача на чтение получит гигантский кусок.

---
### 3.3. Strategy A: Adaptive Query Execution (AQE) — Автопилот

В Spark 3.x+ это стандарт де-факто. AQE вмешивается в план выполнения **между стейджами** (at runtime).

**Как AQE лечит Skew Join:**
1.  **Detection**: После завершения Map-стадии, Driver смотрит на статистику размеров Shuffle-файлов (MapOutputTracker).
2.  **Criteria**: Партиция считается перекошенной, если:
    *   Её размер > `spark.sql.adaptive.skewJoin.skewedPartitionFactor` (def: 5) * Median Size.
    *   И её размер > `spark.sql.adaptive.skewJoin.skewedPartitionThresholdInBytes` (def: 256MB).
3.  **Mitigation (Split & Replicate)**:
    *   Spark **расщепляет (Splits)** большую партицию (например, Partition 0 таблицы А) на N мелких задач (Sub-partitions).
    *   Чтобы Join сошелся, Spark **дублирует (Replicates)** соответствующую партицию таблицы Б N раз.
    *   Вместо 1 задачи "Huge Join Small" мы получаем N задач "Small Join Small".

*Expert Config*: Включите `spark.sql.adaptive.enabled=true` (по дефолту в 3.2+). Если перекос не чинится, уменьшите порог `skewedPartitionThresholdInBytes`.

---
### 3.4. Strategy B: Salting (Соление) — Ручная Оптимизация

Если AQE не справляется (например, перекос в `GROUP BY`, который AQE лечит хуже, или ключи настолько огромны, что даже сплит не помогает), применяем **Salting**.

**Суть метода**: Искусственно размазать "жирный" ключ по кластеру.

**Алгоритм для JOIN (Таблица А [Skewed] join Таблица B [Small/Uniform]):**

1.  **Add Salt (Таблица А)**: Добавляем колонку с случайным числом от 0 до N (где N — фактор соления, например 100).
    *   Ключ меняется с `Key` на `(Key, Salt_Random)`.
    *   Строки с `Key='PowerUser'` теперь разлетаются в 100 разных партиций.
2.  **Explode (Таблица B)**: Таблицу-справочник нужно размножить. Каждую строку копируем N раз, добавляя соль от 0 до N-1.
    *   `Key='PowerUser'` превращается в 100 строк: `('PowerUser', 0), ('PowerUser', 1)...`
3.  **Join**: Джойним по составному ключу `(Key, Salt)`.
4.  **Drop Salt**: Убираем соль после джойна.

**Пример кода (PySpark):**
```python
# N = 20 (солим на 20 бакетов)
df_skewed = df_skewed.withColumn("salt", (rand() * 20).cast("int"))

# Размножаем справочник (Explode)
df_uniform = df_uniform.withColumn("salt_array", array([lit(i) for i in range(20)])) \
                       .withColumn("salt", explode("salt_array"))

# Теперь джойн равномерный
result = df_skewed.join(df_uniform, ["key", "salt"])
```

**Цена вопроса**: Мы увеличиваем размер таблицы B в N раз. Метод применим, только если Таблица B достаточно компактна.

---
### 3.5. Strategy C: Iterative Broadcast (Изоляция)

Элегантный метод для случаев, когда перекошенных ключей мало (топ-10 клиентов).

1.  **Identify**: Найти топ ключей (через `approx_count_distinct` или сэмплинг).
2.  **Branching**:
    *   **Ветка 1 (Skewed)**: Отфильтровать только эти ключи. Сделать **Broadcast Join** (он устойчив к перекосу на стороне Probe, так как нет шаффла ключей).
    *   **Ветка 2 (Normal)**: Отфильтровать `Key NOT IN (Top Keys)`. Сделать обычный **Sort-Merge Join**.
3.  **Union**: Объединить результаты.

*Плюс*: Не раздуваем данные (как в Salting).
*Минус*: Два прохода по данным.

---
### 3.6. Strategy D: Особый случай — NULL Handling

Никогда не делайте `JOIN` по полям, где возможен `NULL`, без предварительной обработки.
В Spark `NULL` — это тоже значение. Все `NULL` летят в одну партицию.

**Решение:**
1.  **Filter**: Если джойн внутренний (`INNER`), просто сделайте `.filter(col("key").isNotNull())` **до** джойна. Это радикально уменьшит объем шаффла.
2.  **Coalesce (Synthetic Key)**: Если джойн внешний (`LEFT`), и нужно сохранить строки — замените `NULL` на уникальную случайную строку для левой таблицы:
    ```python
    # Для левой таблицы (Skewed)
    key_col = when(col("key").isNull(), concat(lit("null_"), rand())).otherwise(col("key"))
    # Для правой (ничего не меняем, там NULL не сматчится)
    ```
    *Результат*: Null-ы разлетаются по кластеру и просто не находят пару (как и ожидается), но не кладут экзекьютор.

### Резюме раздела 3

1.  **AQE** — ваш лучший друг. Включите его.
2.  **Salting** — "ядерное оружие", когда AQE не помогает. Используйте осторожно, так как раздуваете данные (Cartesian Explosion).
3.  **Nulls** — тихие убийцы. Всегда фильтруйте или солите NULL-значения перед Join/GroupBy.
4.  **Диагностика**: Если видите `Max Time >> Median Time` — это Skew. Не пытайтесь просто добавить памяти (Vertical Scaling), лечите распределение данных.

## 4. Глубокая оптимизация памяти (Expert Tweaks)

В Spark память — это не просто ресурс хранения, это рабочее пространство для алгоритмов (Sort, Join, Aggregate). Если алгоритму тесно, он начинает сбрасывать данные на диск (Spill), превращая In-Memory движок в MapReduce 2004 года.

### 4.1. Анатомия Unified Memory Manager (Менеджер Объединенной Памяти)

С версии 1.6 Spark использует динамическую модель памяти. Это не жесткие границы, а "мягкие" соглашения с правилами вытеснения.

Память контейнера (`spark.executor.memory`) делится на три зоны:

1.  **Reserved Memory (300MB)**: Жесткий резерв движка. Не обсуждается.
2.  **User Memory (40%)**:
    *   *Формула*: `(Heap - 300MB) * (1 - spark.memory.fraction)`.
    *   *Что там живет*: Ваши собственные объекты (`HashMap`, списки), созданные внутри UDF, глобальные переменные и метаданные RDD.
    *   *Expert Note*: Если вы делаете `map(lambda x: enormous_dict[x])` — этот словарь живет здесь. Spark **не контролирует** эту память. Если переполните — получите `java.lang.OutOfMemoryError: Java heap space`.
3.  **Spark Unified Memory (60%)**:
    *   *Формула*: `(Heap - 300MB) * spark.memory.fraction` (def: 0.6).
    *   Здесь живут и **Execution** (вычисления), и **Storage** (кэш).

#### Конфликт Execution vs Storage (The Eviction Rules)
Внутри Unified Memory (те самые 60%) есть под-граница: `spark.memory.storageFraction` (def: 0.5).
Но она работает хитро:
*   **Execution has Priority**: Если задаче нужна память для сортировки (Execution), она может **вытеснить (Evict)** кэшированные блоки (Storage) из памяти. Кэш "дропается" (или уходит на диск, если уровень кэширования позволяет).
*   **Storage is Weak**: Storage **не может** вытеснить занятую Execution память.
*   **Immunity**: Память Storage гарантирована только в объеме `storageFraction`. Всё, что выше — в опасности.

**Сценарий катастрофы**: Вы закэшировали `.persist(MEMORY_ONLY)` огромную таблицу. Она заняла 90% Unified Memory. Запускается тяжелый `JOIN`. Ему нужна память. Spark выкидывает кэш. Вы теряете время на кэширование, а потом на повторное вычисление.
**Решение**: Для тяжелых ETL используйте меньший `spark.memory.storageFraction` или вообще не кэшируйте без нужды.

---
### 4.2. Off-Heap Memory и Project Tungsten

Java Objects (POJO) ужасны для Big Data. Строка `"abcd"` (4 байта) в Java занимает 48 байт (заголовки, хэш, padding).
Spark решает это через **Tungsten**.

1.  **Unsafe Row**: Spark хранит данные в бинарном формате (как C struct), управляя памятью вручную через `sun.misc.Unsafe`. Это устраняет оверхед Java-объектов.
2.  **Off-Heap Execution**:
    *   *Config*: `spark.memory.offHeap.enabled=true`, `spark.memory.offHeap.size=10g`.
    *   Если включено, данные для сортировки и хэш-таблиц (Shuffle maps) аллоцируются **вне Heap** (напрямую в RAM ОС).
    *   **Преимущество**: Garbage Collector (GC) **не видит** эту память. Ему не нужно сканировать 100GB графа объектов. GC Pauses сокращаются с минут до миллисекунд.
    *   *Use Case*: Огромные джойны, сортировки, сложные агрегации на терабайтах данных.

---
### 4.3. Garbage Collection Tuning (Когда Java мешает)

В Batch-процессинге главная проблема GC — это "Stop-The-World" (пауза всего приложения). Если пауза > таймаута хартбита, Executor считается мертвым и убивается драйвером.

**Default**: Spark использует `ParallelGC`. Он оптимизирован на пропускную способность (Throughput), но дает длинные паузы на больших кучах (>30GB).

**G1GC (Garbage First) — Выбор Эксперта для Heap > 32GB**:
G1GC разбивает кучу на тысячи мелких регионов и чистит их инкрементально.
*   **Config**:
    ```bash
    --conf "spark.executor.extraJavaOptions=-XX:+UseG1GC -XX:InitiatingHeapOccupancyPercent=35"
    ```
*   `InitiatingHeapOccupancyPercent=35`: Начинать сборку мусора, когда куча заполнена на 35% (а не ждать 70%, когда уже поздно и нужна полная остановка).

---
### 4.4. Memory Overhead (Скрытый убийца контейнеров)

Выделили `spark.executor.memory=10g`. Контейнер в YARN/K8s потребляет 12GB. Почему?
Потому что есть **Overhead**.

*   **Что там живет**:
    1.  **Off-Heap memory** (если включена).
    2.  **Direct Buffers (Netty)**: Сетевые буферы для передачи Shuffle-блоков.
    3.  **Thread Stacks**: Каждый поток (Core) требует 1MB стека.
    4.  **Native Code**: Библиотеки компрессии (Snappy, Zstd), Python worker-ы.

*   **Проблема**: Если использование Overhead превышает лимит, **OOM Killer** (операционной системы или K8s) убивает контейнер с Exit Code 137. Это *не* Java OOM, это Hard Kill.
*   **Formula**: `spark.executor.memoryOverhead` = `Max(384MB, 0.10 * executorMemory)`.
*   **Expert Tweak**: Если у вас много Shuffle (много сетевых буферов) или используется PySpark (Python процессы жрут память вне JVM), **увеличивайте Overhead** вручную.
    *   *Пример*: Для 64GB Heap ставьте 6-8GB Overhead (вместо дефолтных 6.4GB).

---
### 4.5. Serialization: Kryo vs Java

Сериализация — это процесс превращения объектов в байты для отправки по сети (Shuffle) или записи на диск (Spill).

*   **Java Serialization (Default)**: Медленная, жирная, сохраняет имена классов.
*   **Kryo Serialization**: Компактная (в 10x меньше), быстрая.
*   **Expert Rule**: Всегда включайте Kryo в продакшене.
    ``` 
    spark.serializer=org.apache.spark.serializer.KryoSerializer
    spark.kryoserializer.buffer.max=512m
    ```
*   *Нюанс*: Если вы используете кастомные классы внутри RDD/DataFrame, их нужно зарегистрировать (`kryo.register(MyClass.class)`), иначе Kryo будет работать, но менее эффективно (будет писать полные имена классов). Для DataFrame (Row objects) Spark делает это сам.

### 4.6. Пример расчета конфигурации (Sizing)

У вас есть нода: 64 GB RAM, 16 Cores. Как нарезать Spark Executors?

**Вариант А: "Fat Executor" (1 Executor на ноду)**
*   Executor: 56 GB RAM (оставляем 8GB на OS), 15 Cores (1 на OS).
*   *Проблема*: GC пауза на 56GB куче будет длиться 10-20 секунд. HDFS клиент может потерять коннект.

**Вариант Б: "Tiny Executors" (15 Executors по 1 Core)**
*   *Проблема*: Нет шаринга переменных (Broadcast копируется 15 раз). Дикий оверхед на JVM процессы.

**Вариант В: "Balanced" (Выбор эксперта — 3-5 ядер на Executor)**
*   Делим на 3 Executor-а:
    *   Cores: 5 per executor (5 * 3 = 15).
    *   RAM: ~18 GB per executor (18 * 3 = 54GB + Overhead).
*   **Результат**:
    *   Куча 18GB отлично собирается ParallelGC (или G1GC).
    *   Достаточно слотов для параллелизма.
    *   Broadcast таблицы шарятся между 5 ядрами внутри процесса.

### Резюме раздела 4

1.  **Monitor Overhead**: Если джоба падает без логов в Spark UI (контейнер исчез) — это Overhead. Увеличьте `spark.executor.memoryOverhead`.
2.  **Tungsten is King**: Используйте SQL/DataFrames, а не RDD. RDD используют Java-объекты, DataFrames используют Unsafe Row и Off-Heap.
3.  **Beware of Caching**: Кэш (Storage) — это "младший брат". Execution (Shuffle) выгонит его при первой же нехватке памяти. Используйте `MEMORY_AND_DISK`, чтобы кэш не исчезал бесследно.
4.  **GC Tuning**: Если GC Time > 10% от Task Time (в UI), переключайтесь на G1GC или уменьшайте размер кучи (увеличивая число экзекьюторов).

## 5. Практический чеклист оптимизации (Troubleshooting)

Когда джоба тормозит:

1.  **Проверь Skew**: Посмотри Summary Metrics задач. Если Max >> Median — включай AQE или делай Salting.
2.  **Проверь Spill**: В вкладке Stage найди "Disk Spill (Data)". Если > 0, значит не хватает Execution Memory.
    *   *Fix*: Увеличь `spark.sql.shuffle.partitions` (сделать куски меньше) или добавь RAM.
3.  **Убей UDF**: Если видишь PythonUDF, знай — это тормоз (сериализация в Python процесс). Перепиши на Native Spark SQL или Scala/Java UDF.
4.  **Broadcast Timeout**: Если падает BHJ, увеличь `spark.sql.broadcastTimeout` или выключи broadcast (`spark.sql.autoBroadcastJoinThreshold = -1`).
5.  **Small File Problem**: Если на выходе миллион мелких файлов — добавь `.repartition(N)` или включи `spark.sql.adaptive.coalescePartitions.enabled`.

**Резюме**: Spark оптимизация — это управление физикой. Вы должны понимать, где лежат данные, сколько весит партиция и как она летит по сети.

**TL;DR**: Контрактное тестирование — это **превентивный удар** по интеграционным багам.
*   **Consumer-Driven Contracts (Pact)** — это для синхронного мира (REST/gRPC). Оно переворачивает ответственность: Потребитель (Consumer) диктует, какие поля ему нужны, а Поставщик (Provider) в рамках своего CI-пайплайна доказывает, что он выполняет этот контракт. Это позволяет деплоить сервисы независимо, имея уверенность, что вы никого не сломали.
*   **Schema Registry Pattern** — это для асинхронного мира (Kafka/Pulsar). Это **централизованный gatekeeper**, который физически не дает Продюсеру (Producer) отправить "ломающее" сообщение в топик. Это "Shift-Left" для качества данных.

## 1. Проблема: Ад End-to-End (E2E) тестов

В монолитной архитектуре End-to-End (E2E) тесты были золотым стандартом. Вы поднимали приложение, базу данных, запускали Selenium/Cypress сценарий и получали 100% уверенность.

В микросервисной архитектуре эта парадигма превращается в **антипаттерн "Тестирование Мороженого" (Testing Ice Cream Cone)**: мало unit-тестов, мало интеграционных и огромная, тяжелая шапка из E2E тестов. Это путь к коллапсу процессов доставки (Delivery Pipeline).

### 1.1. Фундаментальная проблема: Недетерминизм и Хрупкость (Flakiness)
**Определение:** Тест называется "хрупким" (flaky), если он может пройти и упасть на одном и том же коммите без изменений кода.

В распределенной системе хрупкость не случайность, а свойство системы.
*   **Сетевые задержки:** E2E тест ожидает ответ за 500мс. В CI/CD агенте скакнула нагрузка CPU, ответ пришел за 501мс. Тест упал.
*   **Асинхронность и Eventual Consistency:**
    *   *Сценарий:* Тест создает `Order`, затем сразу запрашивает статус `Payment`.
    *   *Реальность:* `OrderService` отправил событие в Kafka. `PaymentService` еще не успел его вычитать.
    *   *Результат:* Тест получает `404 Not Found`. Разработчик добавляет `Thread.sleep(5000)`. Это замедляет пайплайн и не гарантирует результат.
*   **Инфраструктурный шум:** Перевыборы лидера в БД, холодный старт Lambda/JVM, Garbage Collection паузы.

**Инсайт Архитектора:** Если у вас 50 микросервисов, и каждый имеет доступность 99.9%, то доступность тестового окружения (вероятность того, что *все* сервисы живы одновременно для прогона теста) составляет $0.999^{50} \approx 95\%$. Это значит, что **каждый 20-й прогон падает сам по себе**.

### 1.2. Ад управления данными (Data State Pollution)
Самая сложная проблема E2E тестов — управление состоянием (State Management).

*   **Shared Mutable State:** E2E тесты обычно запускаются против одного тестового окружения (Staging/QA).
*   **Конфликт сценариев:**
    *   Тест А: "Проверить, что баланс пользователя X = 100".
    *   Тест Б (параллельный): "Списать у пользователя X 50 монет".
    *   Результат: Оба теста падают (Race Condition).
*   **Накопление мусора:** Тесты создают тысячи заказов, пользователей и транзакций. База данных раздувается, запросы замедляются, тесты начинают падать по таймауту.

*Попытки решения и их цена:*
1.  *Изолированные БД для каждого прогона:* Дорого и долго поднимать.
2.  *Очистка данных (Teardown):* Ненадежно (если тест упал посередине, очистка не сработала).
3.  *Уникальные данные:* Генерировать `User_GUID` для каждого теста. Работает, но усложняет отладку и не спасает от глобальных справочников.

### 1.3. Комбинаторный взрыв путей (Combinatorial Explosion)
Пытаться проверить все сценарии через E2E в микросервисах — математически провальная затея.

Представьте цепочку вызовов: `Service A -> Service B -> Service C`.
*   Сервис A имеет 3 состояния (Valid, Invalid, Empty).
*   Сервис B имеет 4 состояния (Success, Timeout, Error, Declined).
*   Сервис C имеет 2 состояния.
Чтобы проверить все варианты интеграции, нужно $3 \times 4 \times 2 = 24$ E2E теста.
Добавьте сюда версии API (Service B v1 и Service B v2). Сложность растет экспоненциально.

**Staff Engineer Note:** E2E тесты проверяют не столько бизнес-логику (она проверена unit-тестами), сколько **корректность конфигурации** (правильные ли URL, открыты ли порты, верные ли креды). Использовать для этого тяжелый браузерный тест — это как "забивать гвозди микроскопом".

### 1.4. Петля обратной связи и "Интеграционный паралич"
*   **Время выполнения:** E2E сьют может бежать 2-4 часа.
*   **Стоимость отладки:** Тест упал с ошибкой `ElementNotFound` на фронтенде.
    *   Причина? Может быть баг во фронте, ошибка 500 на бэкенде, ошибка в базе данных, упавшая Kafka или просто лаг сети.
    *   Инженер тратит день на раскопки логов (Distributed Tracing), чтобы найти, что в сервисе №15 поменяли имя поля в JSON.

Это приводит к **"Интеграционному параличу"**:
1.  Пайплайн красный.
2.  Никто не может задеплоить (Feature Freeze).
3.  Команды перестают доверять тестам ("А, это опять флаки тест, перезапусти").
4.  Дефекты пролезают в продакшен.

### 1.5. Локализация ответственности (Ownership Blur)
Кто владеет E2E тестом "Оформление заказа"?
*   Команда Заказов?
*   Команда Платежей?
*   Команда Склада?
*   QA Automation отдел?

Когда тест падает, ни одна продуктовая команда не считает это *своей* проблемой. "Это сервис Платежей тормозит, пусть они чинят". E2E тесты размывают границы ответственности (Bounded Contexts), которые мы так старательно строили в DDD.

**Резюме раздела:**
E2E тесты необходимы как **Smoke Tests** (проверка дыма) — пройтись по 2-3 критическим путям (Happy Path), чтобы убедиться, что система в целом поднялась.
Но строить на них стратегию обеспечения качества интеграции в микросервисах — **архитектурная ошибка**. Нам нужен способ проверить корректность взаимодействия `Service A -> Service B`, не поднимая при этом `Service C`, базу данных и Kafka.

Именно эту задачу решает **Contract Testing**.

## 2. Consumer-Driven Contracts (CDC) и Pact: Мир синхронных API

**Pact** — это не просто библиотека для моков. Это методология, которая формализует отношения между микросервисами, превращая неявные ожидания в **строгие, версионируемые артефакты**.

В мире CDC мы переворачиваем традиционную пирамиду ответственности. Вместо того чтобы Поставщик (Provider) гадал: "Как клиенты используют мой API?", Потребители (Consumers) явно заявляют: "Вот сценарии, которые мы выполняем, и поля, которые нам нужны".

### 2.1. Философия: Закон Постела в CI/CD
CDC — это архитектурное воплощение **Закона Постела** (Robustness Principle): *"Будь строг к тому, что отправляешь, и либерален к тому, что принимаешь"*.

*   **Provider-Driven (OpenAPI):** Поставщик публикует огромный контракт ("У меня есть 50 полей"). Потребитель может использовать 3 из них, но если Поставщик удалит 4-е (неиспользуемое), это формально считается Breaking Change, хотя фактически никого не ломает.
*   **Consumer-Driven (Pact):** Потребитель фиксирует в контракте только те 3 поля, которые реально читает.
    *   *Результат:* Поставщик может свободно удалять или менять остальные 47 полей. Эволюция API становится гибкой и безопасной.

---

### 2.2. Анатомия Pact-теста (The Workflow)

Процесс CDC асинхронен. Тесты Потребителя и Поставщика не запускаются одновременно. Их связывает **Pact File** (JSON-артефакт).

#### Фаза 1: Consumer Side (Генерация контракта)
Это обычный **Unit-тест** вашего HTTP-клиента (Gateway/Adapter), но с побочным эффектом.

1.  **Определение ожиданий (Interaction):**
    Разработчик Consumer'а описывает сценарий.
    *   *Given (State):* "Пользователь с ID 42 существует и имеет положительный баланс".
    *   *When (Request):* `GET /users/42`
    *   *Then (Response):* Status `200`, Body `{ "id": 42, "role": "ADMIN" }`.
    *   *Matching Rules (Ключевой момент):* Мы не хардкодим значения. Мы говорим: "поле `id` должно быть *целым числом* (example: 42), поле `role` должно быть *строкой*".

2.  **Mock Server Execution:**
    Pact поднимает локальный Mock Server. Unit-тест делает реальный запрос на этот Mock.
    *   Если запрос совпадает с описанным в `When`, Mock возвращает ответ из `Then`.
    *   Если код клиента работает корректно с этим ответом, тест проходит.

3.  **Artifact Generation:**
    После успешного прохождения теста фреймворк сохраняет JSON-файл (Pact File). Это и есть **Контракт**.

> **Важно:** На этом этапе мы доказали только то, что Consumer *умеет обрабатывать* ответ, который он *сам себе придумал*. Мы еще не знаем, способен ли Provider реально выдать такой ответ.

#### Фаза 2: Broker (Центральный репозиторий)
JSON-файл загружается в **Pact Broker**. Это не просто файлохранилище, это **Матрица Версий**.
Broker знает:
*   Версия Consumer `v1.2.0` требует контракт `Hash(A)`.
*   Версия Provider `v3.5.0` верифицировала контракт `Hash(A)`.

#### Фаза 3: Provider Side (Верификация контракта)
Это **функциональный тест** API Поставщика, но сгенерированный автоматически.

1.  CI Поставщика скачивает контракт.
2.  **Replay Mechanism:** Pact-фреймворк читает контракт и начинает "бомбить" запущенный сервис Поставщика запросами из контракта.
3.  **Validation:** Фреймворк перехватывает ответ сервиса и сверяет его с ожиданиями Consumer'а (`Matching Rules`).
    *   Пришел ли статус 200?
    *   Есть ли поле `role`?
    *   Является ли оно строкой?
    *   *Лишние поля в ответе игнорируются (Postel's Law).*

Если всё ок, Provider публикует в Broker статус: "Я, версия `v3.5.1`, совместим с контрактом от Consumer `v1.2.0`".

### 2.3. Provider States: Управление данными без боли

Самый сложный технический аспект CDC. Consumer ожидает, что "Пользователь 42 существует". Но база данных Provider'а в CI пуста или содержит случайные данные.

Как гарантировать состояние? Через механизм **Provider States**.

1.  В контракте Consumer пишет: `given("User 42 exists")`.
2.  На стороне Provider'а разработчики реализуют **State Handler** (хук).
3.  Перед запуском теста Pact-фреймворк видит `given("User 42 exists")` и вызывает этот хук.
4.  **Реализация хука:**
    *   *Вариант А (Инъекция в БД):* `INSERT INTO users (id, ...) VALUES (42, ...)`
    *   *Вариант Б (Mocking слоя сервиса):* `when(userService.findById(42)).thenReturn(...)`.

**Инсайт Архитектора:** Используйте Mocking (Вариант Б) для Contract Tests.
Вам не нужно проверять, работает ли база данных Postgres (это задача интеграционных тестов Provider'а). Вам нужно проверить, соблюдает ли ваш Controller/Handler формат JSON-контракта. Это делает тесты мгновенными.

### 2.4. `can-i-deploy`: Гейткипер релизов

Это команда CLI инструмента Pact, которая ставится в CI/CD пайплайны. Она защищает прод.

*   **Сценарий:** Вы хотите выкатить `Consumer v1.3.0` в среду `Production`.
*   **Действие:** CI выполняет `pact-broker can-i-deploy --pacticipant Consumer --version 1.3.0 --to Production`.
*   **Логика Брокера:**
    1.  Находит, какая версия Provider сейчас работает в `Production` (например, `v3.5.1`).
    2.  Смотрит в Матрицу: "Верифицировал ли Provider `v3.5.1` контракт, сгенерированный Consumer `v1.3.0`?"
    3.  Если **Да**: `Exit Code 0` (Deploy).
    4.  Если **Нет** (контракт не проверен или проверка провалилась): `Exit Code 1` (Stop Deploy).

**Результат:** Вы физически не можете задеплоить версию, которая сломает интеграцию, даже если все unit-тесты зеленые.

### 2.5. Пример контракта (JSON)

Чтобы вы понимали физику, вот как выглядит фрагмент Pact-файла. Обратите внимание на разделение тела и правил матчинга.

```json
{
  "description": "A request for user details",
  "providerState": "User 42 exists",
  "request": {
    "method": "GET",
    "path": "/users/42"
  },
  "response": {
    "status": 200,
    "headers": { "Content-Type": "application/json" },
    "body": {
      "id": 42,
      "username": "senior_dev",
      "level": "EXPERT"
    },
    "matchingRules": {
      "body": {
        "$.username": { "match": "type" },  // Любая строка
        "$.id": { "match": "integer" },     // Любое целое число
        "$.level": { "match": "regex", "regex": "(JUNIOR|MIDDLE|EXPERT)" } // Enum проверка
      }
    }
  }
}
```

### Резюме для Staff Engineer

1.  **Consumer-Driven Contracts** — это тесты *интерфейса*, а не бизнес-логики. Они отвечают на вопрос: "Понимаем ли мы друг друга?", а не "Правильно ли работает калькулятор?".
2.  **Изоляция:** CDC позволяют командам Consumer и Provider работать асинхронно. Provider может делать рефакторинг, Consumer может добавлять фичи — до тех пор, пока `can-i-deploy` дает зеленый свет.
3.  **Замена E2E:** Покрыв 90% взаимодействий контрактами, вы можете оставить 2-3 сквозных E2E теста "для галочки", радикально ускорив Time-to-Market.

## 3. Schema Registry Pattern: Мир асинхронных событий

Если Pact — это "рукопожатие" между живыми сервисами, то **Schema Registry** — это **паспортный контроль** для данных. Это инфраструктурный компонент, который гарантирует, что в ваш Event Log (Kafka, Pulsar) никогда не попадет "ядовитое сообщение" (Poison Pill), которое невозможно десериализовать.

### 3.1. Фундаментальная проблема: Неизменяемость истории

В Kafka (и других Log-based брокерах) данные персистентны.
*   **Сценарий:** Сервис `Billing` год назад писал события `PaymentCreated` со схемой v1. Полгода назад перешел на v2. Вчера выкатил v3 с ошибкой (несовместимым изменением).
*   **Проблема:** Новый сервис `Analytics`, который вы запускаете сегодня, должен вычитать топик **с самого начала** (offset 0). Он должен уметь десериализовать и v1, и v2, и v3.
*   Если v3 несовместима с v2, ваш консьюмер упадет с `SerializationException` посередине ночи.

**Schema Registry решает эту проблему, перемещая проверку совместимости "влево" (Shift Left) — на момент записи (Produce).**

---

### 3.2. Архитектура: Как это работает на уровне байтов

Многие инженеры думают, что Schema Registry — это просто хранилище JSON/Avro файлов. На самом деле это **участник протокола сериализации**.

#### The Wire Format (Формат на проводе)
Чтобы не передавать схему целиком в каждом сообщении (это дорого), Confluent/Avro используют специальный бинарный формат. Сообщение в Kafka выглядит так:

`[Magic Byte (1 byte)] [Schema ID (4 bytes)] [Payload (N bytes)]`

1.  **Magic Byte (`0x00`):** Маркер версии протокола Confluent. Говорит десериализатору: "Дальше идет ID схемы, а не данные".
2.  **Schema ID:** Глобально уникальный идентификатор (целое число), который Registry присвоил этой конкретной версии схемы.
3.  **Payload:** Сами данные (Avro binary, Protobuf binary), сериализованные *без* метаданных.

#### Рабочий процесс (The Producer Workflow)
Когда вы делаете `producer.send(record)`:
1.  **Сериализатор (SerDes):** Берет схему вашего объекта.
2.  **Local Cache Lookup:** Проверяет, отправляли ли мы уже данные с такой схемой? Если да — берем её ID из кэша.
3.  **Registration (если нет в кэше):** Отправляет схему в Schema Registry через HTTP.
    *   Registry сверяет схему с **правилами совместимости** (об этом ниже).
    *   Если совместима: возвращает ID (новый или существующий).
    *   Если **не совместима**: возвращает `409 Conflict`.
4.  **Exception:** Сериализатор выбрасывает исключение. Сообщение **не отправляется** в Kafka. Топик остается чистым.

---

### 3.3. Subjects: Стратегии привязки схем

В Schema Registry есть понятие **Subject**. Это "пространство имен" для версионирования схем. Как схема привязывается к топику Kafka? Это определяет **Naming Strategy**.

1.  **TopicNameStrategy (Default):**
    *   Subject = `topic-name-value`.
    *   *Суть:* Все сообщения в топике `orders` должны соответствовать эволюции одной и той же схемы.
    *   *Ограничение:* Вы не можете положить в один топик `OrderCreated` и `OrderCancelled`, если у них разные структуры полей.

2.  **RecordNameStrategy:**
    *   Subject = `com.example.events.OrderCreated` (имя класса записи).
    *   *Суть:* Схема привязана к типу события, а не к топику.
    *   *Результат:* В одном топике могут лежать разные события. Каждое валидируется по своей ветке версий в Registry.

3.  **TopicRecordNameStrategy:**
    *   Комбинация обоих подходов.

**Совет Архитектора:** Используйте `TopicNameStrategy` (один топик = один тип событий). Это упрощает жизнь потребителям. Смешивание типов в одном топике (Heterogeneous Topics) часто приводит к сложности в фильтрации и десериализации.

---

### 3.4. Матрица совместимости (Compatibility Modes)

Это настройки на стороне Registry, которые определяют, разрешить ли регистрацию новой схемы.

| Режим | Описание | Кто обновляется первым? | Пример (Avro) |
| :--- | :--- | :--- | :--- |
| **BACKWARD** (Стандарт) | Consumer с **новой** схемой может читать данные, записанные со **старой** схемой. | **Сначала Consumer**, потом Producer. | Удалить поле. Добавить поле с `default`. |
| **FORWARD** | Consumer со **старой** схемой может читать данные, записанные с **новой** схемой. | **Сначала Producer**, потом Consumer. | Добавить поле (даже без default). Удалить поле (если был default). |
| **FULL** | И Backward, и Forward. Старые и новые клиенты понимают данные друг друга. | Порядок не важен. | Добавлять/удалять поля только с `default`. |
| **NONE** | Проверок нет. Анархия. | На свой страх и риск. | - |

**Transitive Modes (`BACKWARD_TRANSITIVE`, etc.):**
Критически важны!
*   Обычный `BACKWARD` проверяет v3 только против v2.
*   `BACKWARD_TRANSITIVE` проверяет v3 против v2, v1 и всех остальных.
*   *Почему это важно:* Если вы читаете топик с начала времен, ваш Consumer должен быть совместим со **всей** историей, а не только с последней версией.

---

### 3.5. Пример катастрофы (Почему это нужно)

Представьте, что Schema Registry нет.

1.  **День 1:** Producer пишет JSON: `{"price": 100}` (Int).
2.  **День 2:** Разработчик решил, что нужна точность, и поменял на `{"price": "100.50"}` (String).
3.  **Consumer:** Код Java ожидает `Integer`.
    *   При чтении сообщения День 1: ОК.
    *   При чтении сообщения День 2: `JsonParseException` (не могу привести строку к int).
4.  **Результат:** Consumer падает в бесконечном цикле (Retry loop), пытаясь обработать "битое" сообщение. Пайплайн обработки данных встал. Исправить это в Kafka сложно (надо пропускать оффсеты вручную или удалять данные).

**С Schema Registry:**
На шаге 2, при попытке отправить `price` как String (вместо Int), Registry вернет ошибку несовместимости (Type Mismatch). Продюсер упадет на этапе тестов или деплоя, но **данные в Kafka останутся чистыми**.

### Резюме для Staff Engineer

1.  **Schema Registry — это контракт в рантайме.** В отличие от Pact (проверка в CI), Registry физически блокирует запись некорректных данных.
2.  **Выбор режима совместимости диктует стратегию деплоя.**
    *   Хотите обновлять консьюмеры когда угодно? Ставьте `BACKWARD`.
    *   Хотите делать Rolling Update продюсеров без простоя консьюмеров? Ставьте `FULL`.
3.  **Single Source of Truth.** Registry становится единым местом документации всех событий в компании. Вы можете генерировать Java/Go классы для всей компании, просто скачивая схемы из Registry.

Чтобы выбрать инструмент, нужно понять природу взаимодействия ваших сервисов: **с кем**, **как** и **зачем** они общаются.

### 4.1. Сравнительная матрица (Architectural Impact)

| Характеристика | **Pact (Consumer-Driven Contracts)** | **Schema Registry Pattern** |
| :--- | :--- | :--- |
| **Философия** | **Behavioral Contract.** "Я (Потребитель) ожидаю, что если попрошу X, ты вернешь Y в формате Z". | **Structural Contract.** "Я (Продюсер) гарантирую, что данные соответствуют схеме версии N". |
| **Направление контроля** | **Consumer $\to$ Provider.** Потребитель диктует требования. Если Потребителю нужно поле, Провайдер обязан его дать (или договориться). | **Provider $\to$ Consumers.** Провайдер диктует структуру. Потребители подстраиваются под изменения схемы. |
| **Топология связи** | **Point-to-Point (1:1 или 1:N).** Мы точно знаем, кто кого вызывает. Pact Broker строит граф зависимостей. | **Broadcast (1:∞).** Продюсер не знает (и не должен знать) всех своих потребителей. |
| **Тип проверки** | **Логическая + Структурная.** Проверяет типы, форматы (Regex), конкретные значения (state matching). | **Только Структурная.** Проверяет бинарную совместимость типов полей (Int vs String). Не проверяет бизнес-логику. |
| **Момент проверки** | **Build Time (CI/CD).** Блокирует деплой (`can-i-deploy`). В рантайме проверок нет (Zero overhead). | **Write Time (Runtime).** Блокирует запись некорректного сообщения. Есть небольшой оверхед на обращение к Registry (кэшируется). |
| **Цена ошибки** | Сломанный HTTP-клиент, 500 ошибка, откат релиза. | "Отравленный" топик (Poison Pill), который невозможно прочитать; остановка ETL-процессов. |
| **Главный Use Case** | REST/gRPC микросервисы внутри компании. | Kafka, Event Sourcing, Data Mesh. |

### 4.2. Глубокий анализ различий (Deep Dive)

#### A. Валидация логики vs Валидация типов
Это критическое различие, которое часто упускают.

*   **Schema Registry (Avro):** Гарантирует, что поле `email` — это **String**.
    *   *Проблема:* Продюсер может отправить пустую строку `""` или `"not-an-email"`. С точки зрения Avro — это валидная строка. Консьюмер упадет с `ValidationException` уже внутри бизнес-логики.
*   **Pact:** Позволяет задать **Matching Rule** (RegEx).
    *   `"email": matching(regex='.+@.+\..+')`.
    *   Если Провайдер вернет строку, не соответствующую маске email, контракт Pact упадет на этапе тестов.

**Инсайт Архитектора:** Schema Registry защищает от *Serialization Errors*. Pact защищает от *Logical/Semantic Errors*.

#### B. Проблема "Избыточных данных" (Fat Payloads)
*   **Сценарий:** У сервиса `User` есть объект с 50 полями. Сервису `Notification` нужны только `email` и `name`.
*   **Schema Registry:** Заставляет `Notification` знать о полной схеме (все 50 полей). Если `User` удалит поле `birthDate` (которое `Notification` не использует), это может считаться несовместимым изменением (в зависимости от режима совместимости), и это заблокирует релиз Продюсера.
*   **Pact:** `Notification` фиксирует в контракте только `email` и `name`. Продюсер может удалять `birthDate`, менять его тип — Pact-тест останется зеленым. Это обеспечивает **Loose Coupling** (слабую связность).

#### C. Known vs Unknown Consumers
*   **Pact** работает только тогда, когда вы можете перечислить всех потребителей. Вы должны знать, чей CI запускать для верификации. Это невозможно для Публичных API.
*   **Schema Registry** работает для анонимных потребителей. Вы публикуете схему, гарантируете обратную совместимость, и любой (даже неизвестный вам) сервис из Data Team может безопасно читать топик.

### 4.3. Выбор архитектора: Decision Framework

Когда и что применять? Следуйте этому алгоритму:

#### Сценарий А: Внутренние REST/gRPC микросервисы
*   *Контекст:* Команда А вызывает Команду Б. Обе внутри периметра.
*   *Решение:* **Только Pact.**
    *   Вам нужна гибкость. Pact позволит Команде Б менять API агрессивно, ломая только тех, кто реально использует измененные поля. Schema Registry здесь создаст бюрократию.

#### Сценарий Б: Событийная архитектура (Kafka / Data Lake)
*   *Контекст:* Сервис шлет Domain Events ("OrderPlaced"). Их читают 5 микросервисов и Data Warehouse (Hadoop).
*   *Решение:* **Обязательно Schema Registry.**
    *   Вы не можете собрать пакты со всех аналитиков. Вам нужна жесткая гарантия на входе (Producer), что данные в топике структурно валидны вечно.

#### Сценарий В: "Contract Testing on Steroids" (Гибрид)
*   *Контекст:* Критически важная интеграция через Kafka (например, Платежный шлюз). Цена ошибки в логике запредельна. Одной схемы Avro недостаточно (нужна проверка значений).
*   *Решение:* **Schema Registry + Pact Message.**
    *   **Pact Message** — это расширение Pact для асинхронных сообщений.
    *   Используйте Schema Registry для базовой защиты типов (Type Safety).
    *   Используйте Pact Message для проверки семантики (например, "если статус `COMPLETED`, то поле `paidAt` должно быть заполнено").

#### Сценарий Г: Публичный API (Partner API)
*   *Контекст:* Вы банк, предоставляете API для партнеров.
*   *Решение:* **Ни то, ни другое.**
    *   Партнеры не будут писать Pact-тесты для вас.
    *   Используйте **Provider-Driven подход**: Open API Specification (Swagger) + утилиты типа `Dredd` или `Schemathesis` для проверки соответствия вашей реализации вашей же спецификации. Обеспечьте строгую политику версионирования (v1, v2).

### 4.4. Checklist архитектора: Готовы ли вы к Pact?

Внедрение Pact дороже, чем Schema Registry. Проверьте себя:

1.  **Зрелость CI/CD:** Есть ли у вас единый пайплайн, где можно запустить тесты Провайдера, когда меняется Потребитель? (Требуются Webhooks между репозиториями).
2.  **Mocking Culture:** Умеют ли ваши разработчики писать тесты с моками внешних систем, или они привыкли поднимать Docker-контейнеры для всего? Pact требует моков.
3.  **Организационная связь:** Могут ли разработчики Consumer и Provider поговорить? Pact — это инструмент **коммуникации**. Если команды враждуют или изолированы стеной, Pact превратится в оружие ("Ты сломал мой билд!").

### Заключение раздела
*   Используйте **Schema Registry** как фундамент для **хранения данных** и широкого вещания. Это "Конституция" ваших данных.
*   Используйте **Pact** как инструмент для **безопасной эволюции API** в тесно связанных системах. Это "Договор аренды" между конкретными сервисами.

Staff Engineer понимает, что 100% покрытие контрактами невозможно. Начните с самых критичных (Core Domain) стыков сервисов, где цена регрессии максимальна.

---
### Чек-лист уровня Expert

1.  **Тестирование Passthrough сервисов:** Если сервис A вызывает B, а тот вызывает C, как протестировать контракт A-C?
    *   *Ответ:* Pact поддерживает **Bi-Directional Contracts**. B становится и Consumer'ом для C, и Provider'ом для A. Broker может отследить всю цепочку и убедиться, что контракт не нарушен транзитивно.
2.  **Stateful vs Stateless:**
    *   Pact идеально подходит для **stateless** API. Для сложных **stateful** взаимодействий ("сначала создай, потом обнови, потом проверь") контракты становятся громоздкими.
    *   Schema Registry по своей природе **stateful**, так как хранит всю историю эволюции схемы.
3.  **Связь с DDD:**
    *   **Published Language** из Context Mapping — это ваша Avro/Protobuf схема.
    *   **Open Host Service** — это API, который вы верифицируете с помощью Pact.

### Заключение
Контрактное тестирование — это не о технологиях, а об **организационной масштабируемости**. Оно заменяет медленные циклы ручного тестирования и хрупкие E2E-скрипты на быстрые, надежные и автоматизированные проверки, которые позволяют десяткам команд двигаться параллельно, не боясь сломать друг друга. Для Staff Engineer внедрение этих практик — это прямой путь к повышению **Developer Velocity** и **System Reliability**.

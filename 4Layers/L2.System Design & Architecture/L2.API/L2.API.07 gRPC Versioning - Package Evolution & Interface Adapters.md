В gRPC версионирование — это **архитектурный паттерн**, зашитый в структуру ваших `.proto` файлов. Здесь нет "Query Params" или "Accept Headers". Версия является частью полного имени метода (Fully Qualified Name).

## 1. Фундаментальный принцип: Версия в Пакете

Вы должны понимать: в gRPC пакет — это **часть сетевого адреса**. Ошибка в именовании пакета на старте проекта приведет к тому, что через 2 года вам придется переписывать конфигурации всех балансировщиков (Envoy/NGINX) и ломать обратную совместимость на уровне L7.

---

В мире REST API версия часто является метаданными (путь `/v1/`, заголовок `X-Ver`, параметр `?v=1`). В gRPC версия — это **неотъемлемая часть идентичности** сервиса. Она запекается в бинарный контракт и в сетевой маршрут.

### 1.1. Анатомия gRPC-вызова (HTTP/2 Path Mapping)

Чтобы понять важность пакета, нужно посмотреть, как gRPC транслируется в HTTP/2. gRPC не использует привычные URL. Он использует **Fully Qualified Names (FQN)**.

Пусть у нас есть определение:

```protobuf
syntax = "proto3";
package my.company.payments.v1; // <--- КРИТИЧЕСКАЯ СТРОКА

service PaymentService {
  rpc Process (PaymentRequest) returns (PaymentResponse);
}
```

Когда клиент делает вызов, на сетевом уровне (в HTTP/2 фрейме `HEADERS`) путь (`:path`) будет выглядеть так:

$$ \text{Path} = / \underbrace{\text{my.company.payments.v1}}_{\text{Package}} . \underbrace{\text{PaymentService}}_{\text{Service}} / \underbrace{\text{Process}}_{\text{Method}} $$

**Инсайт:**
С точки зрения сети, `/...payments.v1.PaymentService/...` и `/...payments.v2.PaymentService/...` — это **два абсолютно разных, не связанных между собой ресурса**.
*   Они не "перегружают" друг друга.
*   Они не конфликтуют.
*   Они могут маршрутизироваться на разные IP-адреса.

### 1.2. Стратегия именования пакетов (The Google Style Guide)

Не изобретайте велосипед. Используйте стандарт, принятый Google Cloud APIs и Uber.

**Формат:** `<company>.<product>.<feature>.v<MajorVersion>`

*   ✅ `package uber.trip.v1;` — Хорошо. Четко, коротко.
*   ✅ `package google.spanner.admin.database.v1;` — Хорошо. Иерархично.
*   ❌ `package trip.v1;` — Плохо. Слишком общее, возможен конфликт с зависимостями.
*   ❌ `package uber.trip;` — **Катастрофа**. Версия не указана. Это "v0".

**Семантика версий:**
1.  `v1`, `v2` — **Стабильные версии**. Гарантия обратной совместимости. EOL (End of Life) объявляется за год.
2.  `v1beta1`, `v1beta2` — **Бета**. Контракт может меняться, но мы стараемся этого не делать.
3.  `v1alpha1` — **Альфа**. Контракт может быть сломан в любой момент без уведомления.

### 1.3. Влияние на Кодогенерацию (Code Gen Artifacts)

Версия в пакете напрямую влияет на структуру папок и классов в сгенерированном коде клиента/сервера. Это позволяет держать в одном монолите код для v1 и v2 одновременно (**Side-by-Side Coexistence**).

**Java:**
```java
// Сгенерированный класс для v1
import com.company.payments.v1.PaymentServiceGrpc;

// Сгенерированный класс для v2
import com.company.payments.v2.PaymentServiceGrpc;

public class PaymentGateway {
    // Мы можем использовать оба клиента в одном классе!
    private PaymentServiceGrpc.PaymentServiceBlockingStub v1Client;
    private PaymentServiceGrpc.PaymentServiceBlockingStub v2Client;
}
```

**Go:**
В Go это диктует `import path`:
```go
import (
    paymentv1 "github.com/company/repo/gen/go/payments/v1"
    paymentv2 "github.com/company/repo/gen/go/payments/v2"
)
```

**Если вы не укажете версию в пакете:**
Вы получите классы `com.company.payments.PaymentService`. Когда придет время делать v2, вы создадите `com.company.payments.v2`. Это будет выглядеть неаккуратно ("корневая" версия и "v2" сбоку), и рефакторинг "корневой" версии будет мучительным, так как она уже размазана по всему коду.

### 1.4. Организация репозитория (Filesystem Layout)

Архитектура `.proto` файлов должна зеркалировать структуру пакетов. Это стандарт `buf` (современный тулинг для Protobuf) и `protoc`.

```text
api-repo/
├── my/
│   └── company/
│       └── payments/
│           ├── v1/                <-- Package: my.company.payments.v1
│           │   ├── payment.proto
│           │   └── invoice.proto
│           └── v2/                <-- Package: my.company.payments.v2
│               ├── payment.proto
│               └── invoice.proto
```

**Почему это важно:**
Инструменты линтинга (`buf lint`) и детекторы ломающих изменений (`buf breaking`) работают на уровне директорий. Если вы положите `v2` логику в папку `v1`, тулинг сойдет с ума.

### 1.5. Инфраструктурные последствия (L7 Routing Example)

Поскольку версия является частью пути, мы можем настраивать канареечные релизы (Canary) и миграции на уровне **Envoy Proxy** или **Istio**, даже не трогая код приложения.

**Сценарий:** Мы хотим, чтобы все запросы к `v1` шли на старый кластер, а `v2` — на новый.

*Конфигурация Envoy (упрощенно):*
```yaml
routes:
  - match:
      prefix: "/my.company.payments.v2" # Матчинг по префиксу пакета
    route:
      cluster: payment-service-new-cluster # Направляем в новый K8s namespace
  - match:
      prefix: "/my.company.payments.v1"
    route:
      cluster: payment-service-legacy-cluster # Направляем на старые VM
```

**Вывод:**
Версионирование через пакеты дает вам **инфраструктурную суперсилу**: вы можете маршрутизировать разные мажорные версии сервиса на физически разное железо, разные регионы или разные языковые стеки (переписали v2 с Java на Rust), и клиенту не нужно менять ничего, кроме импорта пакета.

## 2. Стратегия 1: Additive Evolution (Minor Changes)

Вы должны понимать: **лучшая миграция — это та, которой не было**. Создание `v2` пакета — это огромные накладные расходы (дублирование кода, поддержка двух баз данных или адаптеров, переключение клиентов).

Ваша задача — растянуть жизнь `v1` на 5-10 лет, используя стратегию **Аддитивной Эволюции**

---

**Аддитивная эволюция** — это подход, при котором вы изменяете сервис так, что **старые клиенты продолжают работать с новым сервером (Backward Compatibility)**, а **новые клиенты могут работать со старым сервером (Forward Compatibility)**.

В gRPC это достигается не магией, а специфическим поведением парсера Protobuf при встрече с неизвестным.

### 2.1. Физика совместимости (Unknown Fields)

Чтобы уверенно менять `.proto`, нужно понимать, что происходит в бинарном потоке.

**Сценарий:**
*   **Server (v1.1):** Добавил новое поле `string nickname = 5;`.
*   **Client (v1.0):** Ничего не знает о поле 5.

Когда старый клиент получает сообщение от нового сервера:
1.  Парсер читает поток: `[Tag 1: ...] [Tag 2: ...] [Tag 5: "Maverick"]`.
2.  Он видит тег `5`. В его сгенерированном коде (Client Stub) нет поля для этого тега.
3.  **Proto2:** Поле молча отбрасывается (и теряется при повторной сериализации).
4.  **Proto3 (Modern):** Поле сохраняется в специальную область памяти — **`UnknownFieldSet`**.
    *   Если клиент (proxy) пересылает это сообщение дальше, **поле 5 сохранится**, даже если клиент не знает, что это.

Именно этот механизм позволяет нам добавлять поля без страха сломать старых потребителей.

---
### 2.2. Правила выживания `v1` (Rules of Engagement)

Чтобы не сломать контракт, следуйте строгому алгоритму.

#### Правило 1: Теги — это константы
Номер поля (Tag ID) — это первичный ключ в базе данных вашего API.
*   **Никогда** не меняйте номер у существующего поля.
*   **Никогда** не меняйте тип данных под существующим номером (исключение: совместимые типы, например `int32` -> `int64`, но это тоже риск).

#### Правило 2: "Мягкое" удаление (Deprecate & Reserve)
В gRPC нельзя просто удалить строку из файла. Это мина замедленного действия.

**Неправильно:**
```protobuf
// Было: string email = 3;
// Стало: (просто удалили строку)
```
*Риск:* Через год новый разработчик (Junior) добавит `string phone_number = 3;`. Старый клиент, который не обновлялся, пришлет в поле 3 email ("bob@mail.com"). Новый сервер попытается интерпретировать это как телефон. В лучшем случае — мусор в БД, в худшем — падение бизнес-логики валидации.

**Правильно (Паттерн Tombstone):**
```protobuf
message User {
  // 1. Помечаем как устаревшее (для документации и IDE)
  string email = 3 [deprecated = true];

  // ИЛИ, если удаляем физически:
  // 2. Бронируем номер и имя навсегда
  reserved 3;
  reserved "email";
}
```
Директива `reserved` заставляет компилятор `protoc` выдавать ошибку, если кто-то попытается использовать тег 3 снова. Это ваша страховка от человеческого фактора.

#### Правило 3: Shadow Fields (Теневые поля) для изменения типов
Что делать, если `int32 id = 1` переполнился и нужен `string` (UUID), а ломать `v1` нельзя?
Используйте паттерн **Shadow Fields**.

1.  Оставляем старое поле, помечаем `deprecated`.
2.  Добавляем новое поле с новым типом и *новым* тегом.
3.  На сервере реализуем логику **Dual Mapping**.

```protobuf
message Order {
  int32 id = 1 [deprecated = true]; // Старый ID
  string uuid = 10;                 // Новый ID
}
```

**Логика сервера (Java):**
```java
public void createOrder(Order req) {
    String orderId;
    if (!req.getUuid().isEmpty()) {
        orderId = req.getUuid(); // Пришел новый клиент
    } else {
        orderId = String.valueOf(req.getId()); // Пришел старый клиент
    }
    // ...
}
```
**Логика ответа:** Сервер обязан заполнять **оба** поля (и `id`, и `uuid`), пока 100% клиентов не мигрируют на использование поля `10`. Только после этого поле `1` можно перестать заполнять (но оставить `reserved`).

### 2.3. Ловушка JSON Transcoding (gRPC-Gateway)

Если вы используете **gRPC-Gateway** или **Envoy JSON Transcoder** для превращения gRPC в REST/JSON, правила становятся жестче.

В чистом gRPC (Protobuf) имена полей не важны, важны теги. Вы можете переименовать `full_name` в `fullName` в `.proto`, и бинарная совместимость сохранится.

**НО:** В JSON ключами являются **имена**.
*   Было: `{"full_name": "Bob"}`
*   Стало: `{"fullName": "Bob"}` (после переименования в .proto)

Старый REST-клиент, ожидающий `snake_case`, сломается.

**Решение:**
Всегда используйте опцию `json_name`, если вам нужно изменить имя поля в коде, но сохранить JSON-контракт.

```protobuf
string full_name = 1 [json_name = "full_name"]; 
// Даже если вы переименуете поле в `string fullName = 1`, 
// в JSON оно останется как "full_name".
```

### 2.4. Поведение `oneof` при эволюции

Добавлять поля в `oneof` (Union) можно, но с осторожностью.
*   **Старый клиент** при чтении нового поля внутри `oneof` просто не увидит, что `oneof` установлен (так как тег ему неизвестен).
*   **Риск:** Если ваша бизнес-логика полагается на то, что "одно из полей обязательно установлено" (`switch case default -> error`), старый клиент может упасть с ошибкой валидации, получив новое поле.

### Резюме раздела

1.  **Additive Evolution** — это продление жизни мажорной версии за счет расширения, а не изменения.
2.  **`reserved`** — это главный инструмент безопасности. Используйте его при каждом удалении.
3.  **Shadow Fields** позволяют менять типы данных без создания `v2` пакета, ценой временного дублирования данных.
4.  Если используете JSON-транскодинг, имена полей становятся частью неизменяемого контракта, как и теги.

## 3. Стратегия 2: Major Versioning (Side-by-Side Deployment)

Многие инженеры путают **Major Versioning** с ветвлением в Git. Они думают: "Мы выпустим v2 в новой ветке, а v1 оставим в старой". Это ошибка. В мире микросервисов вы не можете заставить всех клиентов обновиться одновременно.

Вы должны спроектировать систему так, чтобы один и тот же инстанс сервера обслуживал и легаси-клиентов (v1), и модерн-клиентов (v2) **одновременно**, используя общую базу данных, но разную семантику API.

---

Когда изменения становятся **ломающими** (Breaking Changes) — например, изменение типа первичного ключа, удаление обязательной бизнес-логики или кардинальная смена workflow — стратегия "аддитивных изменений" перестает работать.

Вам нужно ввести **новую версию контракта**, не убивая старую. В gRPC это реализуется через паттерн **Side-by-Side** (Бок-о-бок).

### 3.1. Архитектура: "Один Сервер, Два Лица"

Главная идея: **gRPC Server** (физический процесс) регистрирует внутри себя **несколько реализаций gRPC Service** (логических интерфейсов).

Поскольку `package v1` и `package v2` генерируют разные интерфейсы (в Java/Go/C++), они не конфликтуют.

*   **Клиент А (Legacy)** соединяется с портом 9090 и вызывает `/com.example.v1.UserService/GetUser`.
*   **Клиент Б (Modern)** соединяется с тем же портом 9090 и вызывает `/com.example.v2.UserService/GetUser`.

Это позволяет проводить миграцию плавно, в течение месяцев или лет.

---
### 3.2. Физическая организация (Repo Layout)

Хаос начинается в файловой системе. Чтобы инструменты сборки (Bazel, Gradle, Buf) работали корректно, вы должны строго разделить версии.

**Правильная структура:**
```text
proto/
├── my/
│   └── payment/
│       ├── v1/
│       │   └── payment.proto  <-- package my.payment.v1;
│       └── v2/
│           └── payment.proto  <-- package my.payment.v2;
```

**Что происходит при сборке:**
1.  Компилятор создает два набора классов.
2.  В Go это будут два разных импорта:
    *   `paymentv1 "github.com/org/repo/gen/payment/v1"`
    *   `paymentv2 "github.com/org/repo/gen/payment/v2"`
3.  Это позволяет вам использовать типы `v1.Transaction` и `v2.Transaction` в одной функции, не получая конфликта имен.

---
### 3.3. Паттерн реализации: "Адаптер" (The Shim Pattern)

Самая дорогая ошибка — скопировать код бизнес-логики из `ServiceV1Impl` в `ServiceV2Impl`. Это приводит к **Drift'у логики**: баг, исправленный в v2, остается в v1.

**Правильный подход: V1 как фасад над V2.**

Мы объявляем V2 "Истиной в последней инстанции" (Source of Truth). V1 превращается в слой совместимости (Translation Layer).

**Пример (Java):**

```java
// 1. Core Implementation (V2) - Здесь живет реальная логика
public class PaymentServiceV2Impl extends PaymentServiceV2Grpc.PaymentServiceV2ImplBase {
    private final DomainLogic domain;

    @Override
    public void processPayment(PaymentRequestV2 req, StreamObserver<PaymentResponseV2> res) {
        // Чистая новая логика
        Transaction tx = domain.execute(req.getAmount(), req.getCurrency());
        res.onNext(toProtoV2(tx));
        res.onCompleted();
    }
}

// 2. Compatibility Adapter (V1) - Это "Shim"
public class PaymentServiceV1Impl extends PaymentServiceV1Grpc.PaymentServiceV1ImplBase {
    // Внедряем V2 сервис (или доменную логику V2)
    private final PaymentServiceV2Impl coreService;

    @Override
    public void makePayment(PaymentRequestV1 req, StreamObserver<PaymentResponseV1> res) {
        // ШАГ 1: Up-conversion (Адаптация запроса)
        // Старый клиент прислал "USD 100". Новый сервис ждет "10000 cents".
        PaymentRequestV2 newReq = PaymentRequestV2.newBuilder()
            .setAmountCents(req.getAmount() * 100)
            .setCurrency(req.getCurrency())
            .build();

        // ШАГ 2: Делегирование (Вызов ядра)
        // Мы не дублируем логику транзакции!
        // Используем CountDownLatch или Future для синхронизации, если V2 асинхронный
        coreService.processPaymentInternal(newReq, new StreamObserver<>() {
            @Override
            public void onNext(PaymentResponseV2 newRes) {
                // ШАГ 3: Down-conversion (Адаптация ответа)
                // Конвертируем новый богатый ответ в старый бедный формат
                PaymentResponseV1 oldRes = PaymentResponseV1.newBuilder()
                    .setStatus(mapStatus(newRes.getStatus())) // MAP: APPROVED -> OK
                    .build();
                
                res.onNext(oldRes);
            }
            // ... error handling
        });
    }
}
```

**Терминология:**
*   **Up-conversion:** Преобразование старого, "бедного" запроса в новый, "богатый". Часто требует подстановки дефолтных значений.
*   **Down-conversion:** Преобразование нового ответа в старый формат. Это **Lossy operation** (с потерей данных). Если v2 возвращает поле `cashback_amount`, а в v1 его не было — старый клиент просто не узнает о кэшбэке.

---
### 3.4. Регистрация и Запуск

В точке входа приложения (`main`) вы регистрируете **оба** сервиса.

```java
Server server = ServerBuilder.forPort(9090)
    .addService(new PaymentServiceV1Impl(coreLogic)) // Старый API
    .addService(new PaymentServiceV2Impl(coreLogic)) // Новый API
    .build()
    .start();
```

**Инсайт Staff Engineer:**
Включите **gRPC Server Reflection**. Это позволит утилите `grpcurl` или Postman увидеть, что сервер поддерживает сразу два семейства методов. Это критично для отладки.

---
### 3.5. Жизненный цикл Клиента (Client Migration)

Как клиенту перейти на v2?
Это не мгновенный процесс ("Big Bang Rewrite"). Это **Strangler Fig Pattern** (Удушение) на стороне клиента.

1.  Клиент обновляет библиотеку `client-sdk`, получая доступ к классам v2.
2.  Клиент импортирует оба стаба: `BlockingStubV1` и `BlockingStubV2`.
3.  Новые фичи пишутся на `StubV2`.
4.  Старые вызовы постепенно рефакторятся на `StubV2`.
5.  Когда использование `StubV1` падает до нуля, зависимость удаляется.

### 3.6. Цена решения (Trade-offs)

Почему мы не делаем это для каждого чиха?

1.  **Maintenance Cost:** Вы обязаны поддерживать маппинг (конвертеры) вечно, пока жив v1. Если бизнес-логика v2 меняется, адаптер v1 может сломаться.
2.  **Performance Overhead:** Двойная конвертация объектов (Proto V1 -> Java -> Proto V2) + аллокация памяти. Для High Frequency Trading это может быть неприемлемо.
3.  **Semantic Mismatch:** Иногда v2 меняется так сильно, что v1 просто невозможно эмулировать (например, переход от синхронного ответа к асинхронному Long Polling). В этом случае `ServiceV1Impl` будет возвращать ошибку для новых сценариев.

### Резюме раздела

**Major Versioning (Side-by-Side)** — это мощнейший инструмент, позволяющий разорвать порочный круг "мы не можем обновить API, потому что клиенты не готовы".

Вы строите **Анти-коррупционный слой (ACL)** внутри своего же сервиса:
*   V2 — это чистая модель будущего.
*   V1 — это грязный адаптер прошлого.

Это позволяет вам развивать ядро системы (Core Domain), не будучи скованным ошибками проектирования пятилетней давности.

---
## 4. Стратегия 3: Visibility Rules (Управление видимостью)

В gRPC мы не можем рассчитывать на то, что разработчик клиента прочитает `Sunset` заголовок, потому что gRPC-клиенты — это обычно типизированные объекты (Stubs), которые скрывают транспортный слой. Разработчик вызывает метод `client.getUser()`, он не парсит HTTP-ответы.

Вы должны построить систему, которая **активно мешает** использовать устаревшие методы, эскалируя давление от "предупреждения компилятора" до "ошибки в рантайме".

---

В REST API мы используем заголовки для общения с *инфраструктурой*. В gRPC мы используем сигналы для общения с *компилятором* и *рантаймом*.
Цель этой стратегии — провести API через три стадии смерти: **Deprecation** (Мягкое предупреждение) $\to$ **Brownout** (Операционное давление) $\to$ **Shutdown** (Отключение).

### 4.1. Стадия 1: Static Signals (Уровень Компилятора)

Это первая линия обороны. Мы помечаем контракт как "грязный", чтобы разработчик клиента узнал о проблеме еще до запуска кода — прямо в IDE или CI/CD.

**Инструмент:** `option deprecated = true`

Эта аннотация встроена в сам язык Protobuf. Она применяется к полям, методам, сервисам и даже `enum` значениям.

```protobuf
service PaymentService {
  // Метод устарел. Используйте ProcessPaymentV2.
  rpc ProcessPayment (PaymentRequest) returns (PaymentResponse) {
    option deprecated = true;
  }
}

message PaymentRequest {
  // Поле устарело. Мы перешли на ISO коды валют.
  string currency_name = 2 [deprecated = true];
}
```

**Как это работает (Under the hood):**
Когда вы запускаете `protoc` (компилятор), он переносит эту метку в сгенерированный код целевого языка.
*   **Java:** Генерируется аннотация `@java.lang.Deprecated`. IDE зачеркивает метод. Компилятор (`javac`) выдает ворнинги при сборке.
*   **Go:** Генерируется комментарий `// Deprecated: Do not use.`. Линтеры (golangci-lint) могут быть настроены на фейл билда при использовании таких методов.
*   **C# / C++:** Генерируются соответствующие атрибуты (`[Obsolete]`, `[[deprecated]]`).

**Совет Эксперта:** Не надейтесь только на IDE. Настройте в CI пайплайне правило (например, через `buf lint`), которое запрещает *добавление* новых вызовов deprecated-методов, но разрешает существующие (ratcheting).

---
### 4.2. Стадия 2: Dynamic Signals (Уровень Рантайма)

Если разработчики игнорируют предупреждения компилятора (а они игнорируют), мы переходим к активным действиям на сервере.

В gRPC нет стандартного механизма "Sunset", но мы можем реализовать его через **Server Interceptor** (Middleware).

#### Паттерн: The Deprecation Interceptor

Этот перехватчик инспектирует каждый входящий вызов. Он знает, какие методы находятся в "черном списке" и применяет к ним политики.

**Реализация (Концептуальная Java):**

```java
public class LifecycleInterceptor implements ServerInterceptor {
    // Карта смерти: Метод -> Дата отключения
    private static final Map<String, Instant> SUNSET_SCHEDULE = Map.of(
        "my.payment.v1.PaymentService/ProcessPayment", Instant.parse("2025-12-31T23:59:59Z")
    );

    @Override
    public <Req, Resp> ServerCall.Listener<Req> interceptCall(
            ServerCall<Req, Resp> call, Metadata headers, ServerCallHandler<Req, Resp> next) {

        String fullMethodName = call.getMethodDescriptor().getFullMethodName();

        if (SUNSET_SCHEDULE.containsKey(fullMethodName)) {
            // 1. Алертинг (Observability)
            // Мы пишем в метрики, КТО вызывает старый метод (User-Agent, Peer IP)
            Metrics.counter("grpc.deprecated_usage")
                .tag("method", fullMethodName)
                .tag("client", headers.get(USER_AGENT_KEY))
                .increment();

            // 2. Brownout (Веерное отключение)
            if (isBrownoutWindow()) {
                // Возвращаем ошибку с деталями
                call.close(
                    Status.UNAVAILABLE.withDescription("Method is sunsetting. Brownout active."),
                    createMigrationTrailers() // Ссылка на доку в метаданных
                );
                return new ServerCall.Listener<>() {};
            }
        }
        return next.startCall(call, headers);
    }
}
```

**Нюансы реализации:**
1.  **Trailers вместо Headers:** В gRPC метаданные об ошибке передаются в **Trailers** (хвост ответа). Вы можете передать ссылку на доку по миграции именно там.
2.  **Status Code:** Во время Brownout (временного отключения) используйте `UNAVAILABLE`. Это заставит правильные клиенты сделать Retry (возможно, на другой инстанс), а разработчиков — заметить спайки ошибок. Не используйте `UNIMPLEMENTED`, пока метод не удален окончательно.

---
### 4.3. Стадия 3: Schema Hiding (Сокрытие Схемы)

Это продвинутая техника для публичных API.

gRPC поддерживает механизм **Server Reflection** — это то, как утилиты вроде `grpcurl`, Postman или UI-документация узнают, какие методы есть на сервере.

**Задача:** Сделать так, чтобы метод работал для старых клиентов (у которых уже сгенерирован код), но был **невидим** для новых разработчиков, которые исследуют ваш API.

**Реализация:**
В большинстве реализаций gRPC (Java, Go, C++) сервис Reflection настраивается. Вы можете написать кастомный `ProtoDescriptorProvider`, который фильтрует дескрипторы перед отдачей.
*   *Алгоритм:* Если метод помечен `option deprecated = true`, удаляем его из списка экспортируемых символов Reflection.
*   *Результат:* `grpcurl list` не покажет этот метод. Новый разработчик даже не узнает о его существовании. Старый бинарник продолжит работать.

---
### 4.4. Стадия 4: Hard Shutdown (Отключение)

Когда дата EOL наступила.

1.  **Логическое удаление:** Вы оставляете метод в `.proto` (чтобы не сломать сборку), но внутри реализации (`Impl`) удаляете тело метода.
2.  **Stub implementation:**
    ```java
    @Override
    public void processPayment(Req req, StreamObserver<Res> res) {
        // UNIMPLEMENTED - это аналог 404/501.
        // Говорит: "Сервер знает этот метод, но реализации больше нет".
        res.onError(Status.UNIMPLEMENTED
            .withDescription("EOL reached on 2025-12-31. Upgrade to v2.")
            .asRuntimeException());
    }
    ```
3.  **Очистка Proto:** Спустя еще 6 месяцев, когда трафик упадет до абсолютного нуля, вы удаляете метод из `.proto` файла, заменяя его на `reserved`.

### Резюме для Staff Engineer

Управление видимостью в gRPC — это игра в долгую.
1.  **Compiler Warning** (`option deprecated`) — работает на совесть разработчика.
2.  **Metrics & Logs** (Interceptor) — работают на совесть DevOps (кто-то должен увидеть логи).
3.  **Brownout** (`UNAVAILABLE`) — работает на страх бизнеса перед простоем.
4.  **Reflection Hiding** — работает на чистоту документации.

Используйте все 4 слоя, чтобы миграция с v1 на v2 не превратилась в пятилетнюю стройку века.

## 5. Инфраструктурный слой (Envoy / Service Mesh)

Вы должны не полагаться на то, что клиенты обновят свои конфиги DNS. Вы переносите сложность маршрутизации из "толстых" клиентов (SDK) в инфраструктуру (Service Mesh / Gateway). Это позволяет вам физически разделять легаси (v1) и модерн (v2), даже если для клиента они выглядят как один DNS-адрес.

---

В gRPC имя метода и версия зашиты в HTTP/2 путь. Это дает инфраструктурным прокси (Envoy, NGINX, HAProxy) возможность принимать решения о маршрутизации с точностью до конкретного RPC-вызова, не расшифровывая тело сообщения.

Это переносит версионирование из плоскости **Кода** (Codebase) в плоскость **Топологии** (Topology).

### 5.1. Физика процесса: gRPC over HTTP/2

Чтобы понять, как Envoy маршрутизирует gRPC, нужно взглянуть на заголовки HTTP/2 фрейма.

*   **Method:** `POST`
*   **Path (`:path`):** `/my.package.v1.Service/Method`
*   **Content-Type:** `application/grpc`

**Инсайт Архитектора:**
Поскольку путь строго структурирован (`/Package/Service/Method`), мы можем применять **Regex** или **Prefix Match** правила.
*   Префикс `/my.package.v1` $\to$ указывает на легаси кластер.
*   Префикс `/my.package.v2` $\to$ указывает на новый кластер.

Это позволяет реализовать паттерн **Strangler Fig** (Удушение монолита) на сетевом уровне. Вы можете "выпиливать" методы из монолита по одному, перенаправляя трафик на микросервисы, и клиент этого не заметит.

---
### 5.2. Стратегия 1: Path-Based Routing (Разделение по версиям)

**Сценарий:** У вас есть огромный Java-монолит, обслуживающий `v1`. Вы написали новый микросервис на Go, реализующий `v2`. Вы хотите, чтобы трафик `v2` шел на Go, а `v1` остался на Java.

**Реализация (Istio / VirtualService):**
В мире Kubernetes мы используем абстракции Service Mesh.

```yaml
apiVersion: networking.istio.io/v1alpha3
kind: VirtualService
metadata:
  name: payment-service-route
spec:
  hosts:
  - payment.prod.svc.cluster.local # Единый DNS для клиента
  http:
  # Правило 1: Трафик V2 -> Go Service
  - match:
    - uri:
        prefix: "/my.company.payment.v2" # Матчинг по пакету
    route:
    - destination:
        host: payment-service-go # K8s Service для Go
        port:
          number: 9090

  # Правило 2: Трафик V1 (и всё остальное) -> Legacy Monolith
  - match:
    - uri:
        prefix: "/my.company.payment.v1"
    route:
    - destination:
        host: payment-monolith # K8s Service для Java
        port:
          number: 8080
```

**Результат:** Клиент продолжает стучаться на один и тот же адрес. Сетка сама раскидывает пакеты.

---
### 5.3. Стратегия 2: Traffic Shadowing (Dark Launch)

Это **самый безопасный** способ выкатить `v2`, если он обратно совместим или если `v2` — это просто рефакторинг `v1` (оптимизация производительности).

**Задача:** Проверить, выдержит ли новый сервис реальную нагрузку и не падает ли он на реальных данных, но **не влиять** на ответы пользователю.

**Решение:** Envoy поддерживает **Request Mirroring**.

```yaml
# Пример фрагмента Envoy Config (Raw)
routes:
- match:
    prefix: "/my.company.payment.v1" # Ловим основной трафик
  route:
    cluster: legacy_v1_cluster       # Отправляем на боевой
    request_mirror_policies:
    - cluster: experimental_v2_cluster # Копируем (Fire-and-forget) на новый
      runtime_fraction:
        default_value:
          numerator: 100             # 100% трафика зеркалируется
          denominator: HUNDRED
```

**Как это работает:**
1.  Envoy получает запрос.
2.  Отправляет его в `legacy_v1_cluster`. Ждет ответ. Возвращает ответ клиенту.
3.  **Асинхронно** отправляет копию запроса в `experimental_v2_cluster`.
4.  Ответ от `v2` **игнорируется** (discarded).
5.  **Внимание:** Если запрос изменяющий (POST/Create), убедитесь, что `v2` идемпотентен или пишет в тестовую базу/логает в `/dev/null`, иначе вы задублируете транзакции!

---
### 5.4. Стратегия 3: Header-Based Canary (Тестирование на "своих")

Иногда нужно дать доступ к `v2` только QA-отделу или бета-тестерам, не меняя код клиента. В gRPC заголовки передаются через **Metadata**.

**Сценарий:** Если в метаданных есть `x-beta-user: true`, отправить на `v2`.

```yaml
# Istio VirtualService
http:
- match:
  - headers:
      x-beta-user:
        exact: "true"
  route:
  - destination:
      host: payment-service-v2 # Beta cluster
- route:
  - destination:
      host: payment-service-v1 # Stable cluster
```

**Применение:** Разработчик может использовать утилиту `grpcurl` с флагом `-H "x-beta-user: true"`, чтобы протестировать новый API на проде, в то время как обычные пользователи продолжают работать со старым.

---
### 5.5. gRPC-Web и Транскодинг

Если ваш клиент — браузер (JS), он не может слать чистый gRPC. Он шлет `gRPC-Web` (HTTP/1.1 + base64 payload).
Envoy здесь выступает не просто роутером, а **протокольным адаптером**.

**Envoy gRPC-JSON Transcoder:**
Это фильтр Envoy, который позволяет вам посылать обычный JSON REST, а Envoy конвертирует его в gRPC вызов к бэкенду.
*   Позволяет поддерживать "виртуальную" REST v1 версию API для легаси-клиентов, в то время как бэкенд уже полностью на gRPC.
*   Конфигурация требует загрузки `proto descriptor set` (.pb файла) в Envoy.

---

### Резюме раздела

1.  **Инфраструктура умнее клиента.** Используйте Envoy/Istio для маршрутизации версий. Это позволяет декомпозировать бэкенд физически, сохраняя логическую целостность для клиента.
2.  **Prefix Matching.** Роутинг по префиксу пакета (`/package.v1` vs `/package.v2`) — это самый надежный и быстрый способ разделения трафика.
3.  **Mirroring (Shadowing).** Используйте зеркалирование для безопасного тестирования `v2` на проде. Это "бесплатный" нагрузочный тест на реальных данных.
4.  **Idempotency Warning.** При зеркалировании трафика помните про побочные эффекты (запись в БД). V2 должен уметь работать в режиме "Dry Run" или писать в изолированную базу.

---
## 6. Резюме для gRPC

1.  **Версия — это Пакет.** Всегда начинайте `.proto` файл с `package x.y.v1`.
2.  **Shim Pattern.** Реализуйте старую версию (`v1`) как обертку над новой (`v2`), конвертирующую типы данных. Не дублируйте логику.
3.  **Изоляция.** `v1` и `v2` могут (и часто должны) жить в одной кодовой базе и на одном сервере во время миграции.
4.  **`reserved` — ваш лучший друг.** Никогда не переиспользуйте номера полей, даже спустя 5 лет. Бинарный формат этого не прощает.

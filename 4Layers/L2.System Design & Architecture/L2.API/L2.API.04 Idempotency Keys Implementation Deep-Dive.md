**TL;DR**: Идемпотентность — это механизм обеспечения **Exactly-Once Semantics** (или, точнее, "эффективно однократного выполнения") в ненадежной сети.
Главная сложность не в проверке ключа, а в **атомарности** проверки и бизнес-операции, а также в обработке состояния **"In-Progress"** (когда повтор прилетел, пока первый запрос еще выполняется).

---

Идемпотентность гарантирует, что многократное повторение одного и того же запроса приведет к **тому же состоянию системы** и (желательно) к **тому же ответу**, что и первый запрос.

## 1. Контракт API (Header Contract)

Реализация идемпотентности начинается не с базы данных, а с **API-контракта**. Это соглашение между клиентом и сервером о том, как интерпретировать намерения.

Хотя идемпотентность часто ассоциируется со Stripe API, сейчас существует активный черновик стандарта IETF — **"The Idempotency-Key HTTP Header Field"**, который формализует поведение. Эксперт должен следовать спецификации, чтобы обеспечить совместимость с API Gateway и прокси.

### 1.1. Заголовок `Idempotency-Key`

Клиент отправляет уникальный токен в HTTP-заголовке.
*   **Standard:** `Idempotency-Key` (согласно IETF Draft).
*   **Legacy:** `X-Idempotency-Key` (используется во многих старых системах, но `X-` префиксы официально deprecated в RFC 6648).

**Формат ключа:**
Стандарт не навязывает формат, но рекомендует использовать строку достаточной энтропии.
*   **Best Practice:** UUID v4 (36 символов).
*   **Bad Practice:** Последовательные ID (`req_1`, `req_2`) — предсказуемы, уязвимы для атак и коллизий в распределенных системах.

### 1.2. Область действия (Scope of Uniqueness)

Архитектор должен решить, в каких границах ключ должен быть уникальным. Это влияет на стратегию шардинга БД.

1.  **Global Scope:** Ключ уникален на всю систему.
    *   *Проблема:* Требует глобального индекса (Global Secondary Index) в БД, что дорого и плохо масштабируется при шардинге по `user_id`.
2.  **User/Account Scope (Рекомендовано):** Ключ уникален только в рамках конкретного пользователя (или API-токена).
    *   *Реализация:* Первичный ключ в БД — композитный `(user_id, idempotency_key)`.
    *   *Плюс:* Идеально ложится на шардинг. Данные хранятся там же, где и данные пользователя.

### 1.3. Идемпотентный "Отпечаток" (Fingerprint)

**Критически важный нюанс:** Идемпотентность определяется не только ключом, но и **параметрами запроса**.
Если клиент присылает тот же ключ, но меняет параметры — это **нарушение контракта**, а не идемпотентный повтор.

Сервер обязан валидировать "тройку":
$$ \text{Fingerprint} = (\text{Idempotency-Key}, \text{HTTP Method}, \text{Request Path}, \text{Hash(Body)}) $$

Если `Key` совпал, но `Hash(Body)` отличается — это атака или ошибка клиента.

### 1.4. Протокол взаимодействия (HTTP States)

Вот строгая диаграмма состояний, которую должен реализовать ваш API Gateway или Middleware:

#### Сценарий А: Первый запрос (Happy Path)
*   **Request:** `POST /charge`, `Idempotency-Key: uuid-1`, Body: `{amount: 100}`.
*   **Server:**
    1.  Проверяет наличие ключа `uuid-1` в хранилище. Не найдено.
    2.  Создает запись со статусом `LOCKED`.
    3.  Выполняет операцию.
    4.  Обновляет запись на `COMPLETED` и сохраняет ответ.
*   **Response:** `200 OK` или `201 Created`.

#### Сценарий Б: Идемпотентный повтор (Retry)
*   **Request:** `POST /charge`, `Idempotency-Key: uuid-1`, Body: `{amount: 100}` (То же самое).
*   **Server:**
    1.  Находит ключ `uuid-1`.
    2.  Проверяет хеш тела. Совпадает.
    3.  Видит статус `COMPLETED`.
    4.  **Важно:** Возвращает *кэшированный* ответ (те же заголовки, то же тело), не запуская бизнес-логику.
*   **Response:** `200 OK` (копия первого ответа).
    *   *Совет:* Добавьте заголовок `Idempotent-Replayed: true`, чтобы клиент знал, что это не новое выполнение.

#### Сценарий В: Конфликт параметров (Misuse)
*   **Request:** `POST /charge`, `Idempotency-Key: uuid-1`, Body: `{amount: 999}` (**Другая сумма!**).
*   **Server:**
    1.  Находит ключ `uuid-1`.
    2.  Сравнивает хеш тела. **Не совпадает.**
*   **Response:** `422 Unprocessable Entity` (или `409 Conflict`).
    *   *Сообщение:* "Idempotency key reused with different payload."

#### Сценарий Г: Гонка (Concurrent Request)
*   **Request:** Дубликат приходит, пока первый запрос еще выполняется (статус `LOCKED`).
*   **Server:** Видит статус `LOCKED`.
*   **Response:** `409 Conflict`.
    *   *Header:* `Retry-After: 5` (подсказка клиенту подождать).
    *   *Стандарт IETF:* В черновике предлагается возвращать ошибку `409` с типом проблемы `urn:ietf:params:idempotency:race`.

### 1.5. К каким методам применять?

*   **GET / DELETE:** Идемпотентны по определению HTTP. Заголовок обычно игнорируется (хотя для тяжелых GET-запросов можно использовать для кэширования).
*   **POST / PATCH:** Главные цели. Это неидемпотентные методы, создающие ресурсы или меняющие состояние.
*   **PUT:** Теоретически идемпотентен (полная замена ресурса). Однако, если `PUT` триггерит side-effects (отправку email), ключ идемпотентности все равно необходим.

### Пример (HTTP Transaction)

**Request:**
```http
POST /v1/payments HTTP/1.1
Host: api.bank.com
Authorization: Bearer sk_live_...
Idempotency-Key: 82649032-7264-4632-ae6d-556353284090
Content-Type: application/json

{
  "amount": 2000,
  "currency": "usd"
}
```

**Response (First time):**
```http
HTTP/1.1 201 Created
Idempotency-Key: 82649032-7264-4632-ae6d-556353284090
Location: /v1/payments/pay_12345

{ "id": "pay_12345", "status": "succeeded" }
```

**Response (Retry):**
```http
HTTP/1.1 201 Created
Idempotency-Key: 82649032-7264-4632-ae6d-556353284090
Idempotent-Replayed: true  <-- Маркер для отладки
Original-Date: Tue, 15 Nov 1994 08:12:31 GMT

{ "id": "pay_12345", "status": "succeeded" }
```

## 2. Проблема Гонки: "Check-then-Act" и TOCTOU

В распределенных системах наивная проверка состояния перед действием является классическим антипаттерном. В безопасности и системном программировании этот класс уязвимостей называется **TOCTOU** (Time-of-Check to Time-of-Use).

Суть проблемы: между моментом **проверки** условия ("ключа нет") и моментом **использования** этого факта (создание записи/выполнение операции) проходит время. В этот временной зазор (Gap) состояние системы может измениться другим потоком или запросом.

### 2.1. Анатомия Катастрофы (Sequence Analysis)

Рассмотрим, почему код, выглядящий логично, приводит к дублированию транзакций.

**Наивная реализация (Python-like pseudocode):**
```python
# АНТИПАТТЕРН: Никогда так не делайте в продакшене
def handle_payment(idempotency_key, payload):
    # 1. CHECK (Time-of-Check)
    record = repo.find_by_key(idempotency_key)
    
    if record:
        return record.saved_response
    
    # --- [ THE RACING GAP ] ---
    # Здесь происходит переключение контекста, 
    # GC пауза, или просто сетевая задержка к БД.
    
    # 2. ACT (Time-of-Use)
    result = payment_gateway.charge(payload) 
    repo.save(idempotency_key, result)
    return result
```

**Сценарий гонки (The Race):**
Представьте, что клиент отправил запрос, не получил ответ из-за тайм-аута и тут же (через 10 мс) отправил повтор.

1.  **Thread A (Запрос 1):** Выполняет `repo.find_by_key("key-1")`. Результат: `null`.
2.  **Thread B (Запрос 2):** Выполняет `repo.find_by_key("key-1")`. Результат: `null` (Тред А еще ничего не записал!).
3.  **Thread A:** Входит в критическую секцию. Списывает деньги ($100).
4.  **Thread B:** Входит в критическую секцию. Списывает деньги ($100). **DOUBLE CHARGE**.
5.  **Thread A:** Сохраняет результат в БД.
6.  **Thread B:** Перезаписывает результат в БД (или падает с ошибкой Unique Key, но деньги уже ушли).

**Вывод эксперта:** Проверка и блокировка должны быть **одной атомарной операцией**.

### 2.2. Решение 1: Атомарность на уровне БД (Pessimistic locking via Constraints)

Самый надежный способ (Hard Consistency) — переложить ответственность за атомарность на движок базы данных (PostgreSQL, MySQL).

Мы используем ограничение уникальности (**Unique Constraint**) по полю `idempotency_key`.

**Паттерн "Insert-First":**
Вместо "проверь, потом вставь", мы пытаемся "вставить сразу".

```sql
-- Пытаемся занять слот атомарно
INSERT INTO idempotency_keys (key, user_id, status, created_at)
VALUES ('uuid-1', 101, 'LOCKED', NOW())
ON CONFLICT (key, user_id) DO NOTHING;
```

*   **Если вставка прошла (1 row affected):** Мы захватили "лок". Мы — владельцы этого ключа. Можно безопасно выполнять бизнес-логику.
*   **Если вставка не прошла (0 rows affected):** Значит, ключ уже существует (гонка проиграна или это повтор). Мы должны сделать `SELECT`, чтобы узнать текущий статус (`LOCKED` или `COMPLETED`).

Этот подход гарантирует, что только **одна** транзакция перейдет к выполнению логики, даже если миллион запросов придут одновременно.

### 2.3. Решение 2: Атомарность в Key-Value (Redis SETNX)

Если вы используете Redis для идемпотентности (обычно для нефинансовых операций или как first-level cache), нельзя использовать `GET` потом `SET`.

Используйте команду `SET` с флагами `NX` (Not Exists) или Lua-скрипты.

**Команда:**
`SET idempotency:uuid-1 "LOCKED" NX EX 86400`

*   **Возвращает "OK" (True):** Вы захватили ключ. Выполняйте логику.
*   **Возвращает (nil) (False):** Ключ занят. Читайте значение, чтобы понять статус.

**Важный нюанс Lua:**
Для полноценной реализации (вернуть результат, если он есть, ИЛИ захватить лок) нужен Lua-скрипт, так как это *две* операции (проверка + запись или чтение), которые должны быть атомарны на стороне Redis.

```lua
-- Пример атомарного скрипта
local key = KEYS[1]
local val = redis.call("GET", key)

if val then
  return val -- Возвращаем сохраненный ответ или статус
else
  redis.call("SET", key, "LOCKED", "EX", 3600)
  return nil -- Сигнал, что лок захвачен, можно работать
end
```

### 2.4. Сравнение подходов (Trade-offs)

| Характеристика | Application-side Check (Антипаттерн) | DB Unique Constraint (Insert-First) | Redis Distributed Lock (SETNX) |
| :--- | :--- | :--- | :--- |
| **Атомарность** | ❌ Нет (TOCTOU) | ✅ Да (ACID) | ✅ Да (Single-threaded) |
| **Надежность** | Низкая | Максимальная (Durability) | Средняя (In-memory, Eviction) |
| **Производительность** | Высокая | Средняя (Disk I/O, WAL) | Очень высокая |
| **Сложность** | Низкая | Средняя | Высокая (требует Lua/Redlock) |
| **Вердикт** | **Запрещено** | **Стандарт для Финтеха** | **Для High-Load / Low-Value** |

### 2.5. Что защищает блокировка? (Critical Section Scope)

Понимание того, *что именно* вы блокируете, критично.
Идемпотентный ключ защищает от **параллельного выполнения** (execution), а не только от дублирования данных.

*   Если бы мы просто проверяли существование заказа в таблице `orders`, мы бы пропустили ситуацию, когда заказ *еще не создан*, но процесс оплаты уже идет.
*   Именно поэтому нужна отдельная сущность (таблица `idempotency_keys` или запись в Redis), которая создается **до** начала любых действий. Это классический паттерн **Semaphores / Mutexes**, перенесенный в распределенную среду.

## 3. Архитектура Хранения: In-Memory vs Database

Где хранить состояние ключа (`LOCKED`, `COMPLETED`, `Response Payload`)? Ответ зависит от цены ошибки.

Если ваша система отправляет пуш-уведомления — дубликат неприятен, но допустим.
Если ваша система переводит деньги — дубликат недопустим.

### 3.1. Вариант А: RDBMS (ACID Transactions) — "Золотой стандарт"

Для финансовых и критически важных операций (Booking, Inventory) это **единственно верный** выбор.
Суть подхода: **Атомарность бизнес-операции и сохранения состояния ключа.**

#### Физика процесса
Мы используем транзакционную модель базы данных (PostgreSQL, MySQL, Oracle) для связи ключа идемпотентности с порождаемыми им данными (Заказом, Платежом).

**Схема таблицы `idempotency_keys`:**
```sql
CREATE TABLE idempotency_keys (
    id              BIGSERIAL PRIMARY KEY,
    key             UUID NOT NULL, -- The Idempotency Key
    user_id         BIGINT NOT NULL, -- Sharding Key
    request_hash    CHAR(64) NOT NULL, -- SHA-256(Method + Path + Body)
    status          VARCHAR(20) NOT NULL, -- LOCKED, SUCCESS, FAILED
    response_body   JSONB, -- Кэшированный ответ для ретраев
    recovery_point  JSONB, -- (Optional) Снэпшот для восстановления
    created_at      TIMESTAMPTZ DEFAULT NOW(),
    locked_until    TIMESTAMPTZ, -- Dead Man's Switch
    CONSTRAINT uq_idempotency_key UNIQUE (user_id, key)
);
```

**Алгоритм (Transactional Locking):**

1.  **Start Transaction (`BEGIN`)**.
2.  **Acquire Lock (Insert-First):** Пытаемся вставить запись ключа.
    *   Если получаем ошибку уникальности (`UniqueViolation`) $\to$ делаем `SELECT ... FOR UPDATE`.
    *   Если статус `SUCCESS` $\to$ `ROLLBACK` и возвращаем сохраненный JSON.
    *   Если статус `LOCKED` и `locked_until` в будущем $\to$ Ждем или `409 Conflict`.
    *   Если статус `LOCKED` и `locked_until` в прошлом $\to$ Перехватываем управление (Recovery).
3.  **Perform Logic:** Вставляем записи в таблицу `orders`, `payments` и т.д. В этой же транзакции!
4.  **Finalize:** Обновляем `idempotency_keys` (статус `SUCCESS`, payload ответа).
5.  **Commit Transaction (`COMMIT`)**.

**Почему это надежно?**
Если сервер упадет (питание, OOM-killer) на шаге 3 или 4, база данных сделает автоматический `ROLLBACK`. Ни заказ, ни запись о ключе не сохранятся. Клиент повторит запрос, и он будет обработан как новый. **Состояние "Повисший заказ без ключа" невозможно.**

**Минусы:**
*   **Write Amplification:** Каждая бизнес-операция удваивает нагрузку на запись (WAL, I/O).
*   **Database Bloat:** Таблица ключей растет бесконечно. Требуется партиционирование по времени (Time-Partitioning) и удаление старых партиций (TTL).

### 3.2. Вариант Б: Distributed Key-Value (Redis / DynamoDB) — "Скорость и Риск"

Подходит для высоконагруженных систем с низкими требованиями к строгой консистентности (Social features, Analytics, non-critical Notifications).

#### Механизм
Используется примитив `SETNX` (Redis) или `PutItem` с `ConditionExpression` (DynamoDB).

**Сценарий провала (The Split-Brain / Data Loss):**
Redis (в стандартной конфигурации) — это **асинхронная** репликация.
1.  Master принимает `SETNX key "LOCKED"`. Успех.
2.  Master падает *до* репликации ключа на Slave.
3.  Sentinel/Cluster выбирает Slave новым мастером.
4.  На новом мастере ключа нет.
5.  Дубликат запроса захватывает лок на новом мастере.
6.  **Итог:** Двойное выполнение.

**Сценарий провала (Eviction):**
Если память Redis заполнена, политика вытеснения (Eviction Policy, например `allkeys-lru`) может удалить ваш ключ идемпотентности, даже если у него есть TTL.
*   *Решение:* Использовать отдельный кластер Redis, сконфигурированный как `noeviction` (возвращать ошибку при переполнении).

**Когда применять Redis?**
Когда вы реализуете паттерн **Distributed Lock** для защиты ресурсов, которые *терпят* редкие коллизии, или как первый слой защиты (см. Гибридный подход).

### 3.3. Вариант В: Гибридный подход (Staff Engineer Pattern)

В системах масштаба Uber или Stripe нагрузка на БД слишком высока, чтобы каждый "чих" клиента (включая паразитные ретраи) бил в диск базы данных.

**Паттерн: Redis Fence + DB Source of Truth**

1.  **Layer 1 (Fast Fail):** Входящий запрос сначала идет в Redis.
    *   `SET idempotency:key "LOCKED" NX EX 30`.
    *   Если занято $\to$ `409 Conflict`.
    *   Это отсекает 99% "Thundering Herd" (когда клиент случайно нажал кнопку 10 раз).
2.  **Layer 2 (Consistency):** Если Redis дал добро, идем в БД.
    *   Выполняем транзакцию по сценарию "Вариант А".
    *   БД остается истиной в последней инстанции.
3.  **Layer 3 (Cache Result):** После коммита в БД, обновляем Redis.
    *   `SET idempotency:key JSON_RESULT XX`.
    *   Теперь повторные запросы будут получать ответ из Redis (миллисекунды), не нагружая БД.

**Преимущество:** Снимает `SELECT`-нагрузку с БД на повторах. Защищает БД от спайков конкурентных запросов.
**Сложность:** Требует управления рассинхроном кэша и БД (Cache Invalidation).

### Сравнительная таблица (Decision Matrix)

| Характеристика | **RDBMS (Postgres)** | **Redis / Memcached** | **DynamoDB / Cassandra** |
| :--- | :--- | :--- | :--- |
| **Гарантии** | **ACID (Strong Consistency)**. Полная защита от дублей. | **Eventual Consistency**. Возможна потеря ключей. | **Tunable Consistency**. Можно настроить Strong Read, но нет ACID транзакций с другими таблицами (обычно). |
| **Атомарность с логикой** | **Да**. Ключ и данные в одной TX. | **Нет**. Dual Write problem. | **Нет** (если данные не в той же таблице). |
| **Производительность** | Средняя (Disk I/O). Бутылочное горлышко. | Высокая (RAM). | Высокая (Scale out). |
| **Жизненный цикл (TTL)** | Сложно (требует DELETE job / Partition drop). | Нативно (TTL на ключе). | Нативно (TTL attribute). |
| **Применимость** | Платежи, Заказы, Склад. | Rate Limiting, Дедупликация событий, Уведомления. | High-scale идемпотентность (например, webhook delivery logs). |

### Терминология Эксперта

*   **Linearizability (Линеаризуемость):** Свойство системы, при котором все наблюдатели видят обновления в одном и том же порядке. RDBMS обеспечивает это для ключа. Redis Cluster — нет (в случае сбоев).
*   **Fencing Token:** Значение, которое мы пишем в лок (например, UUID). В гибридном подходе Redis выступает как Fencing механизм.
*   **Dual Write Problem:** Проблема синхронизации состояния между двумя хранилищами (БД и Redis). Если записали в БД, но не успели обновить Redis — в кэше старые данные. Если обновили Redis, но транзакция БД откатилась — в кэше фантомный успех.
    *   *Решение:* Redis используется только как оптимизация, а БД всегда проверяется при отсутствии данных в кэше или критических операциях.

## 4. Обработка состояния "In-Progress" (Concurrent Request Folding)

**Сценарий:** Первый запрос ($R_1$) успешно захватил лок (статус `LOCKED`) и начал выполнение бизнес-логики. В этот момент (спустя 50мс) приходит дубликат ($R_2$) с тем же `Idempotency-Key`.

Это происходит по двум причинам:
1.  **Aggressive Retries:** Клиент не получил ACK за 50мс и решил, что пакет потерян (хотя сервер просто медленный).
2.  **User Errors:** Пользователь неистово кликает кнопку "Оплатить".
3.  **Distributed Consistency:** Eventual consistency прокси или очередей доставила сообщение дважды почти одновременно.

Если $R_2$ просто проигнорирует лок и начнет выполнение — мы получим гонку. Если $R_2$ упадет с ошибкой — мы ухудшим UX.

Архитектор должен выбрать одну из трех стратегий:

### 4.1. Стратегия A: Fail Fast (Рекомендуемая IETF)

Самый честный и ресурсоэффективный подход для синхронных HTTP API. Сервер отказывается обрабатывать дубликат, пока оригинал не завершен.

*   **HTTP Status:** `409 Conflict`.
*   **Semantics:** "Конфликт состояния ресурса: операция с этим ключом уже выполняется".
*   **Headers:** Обязательно добавьте `Retry-After`.

**Пример ответа:**
```http
HTTP/1.1 409 Conflict
Content-Type: application/problem+json
Retry-After: 5

{
  "type": "https://example.com/probs/concurrent-request",
  "title": "Operation in progress",
  "detail": "Processing for idempotency key 'uuid-1' is currently running. Please do not retry immediately.",
  "instance": "/transactions/uuid-1"
}
```

*   **Плюсы:**
    *   **Stateless:** Сервер не хранит состояние соединения для $R_2$.
    *   **Resource Safety:** Мы не занимаем поток (Thread) сервера ожиданием.
*   **Минусы:**
    *   Клиент должен быть умным. Ему нужно распарсисть `409`, подождать `Retry-After` и повторить запрос (чтобы получить финальный `200 OK`).

### 4.2. Стратегия B: Request Coalescing (Wait & Return)

Эта стратегия имитирует "однократное" выполнение для клиента. $R_2$ "подвешивается" и ждет, пока $R_1$ завершится, а затем возвращает результат $R_1$.

**Реализация (Distributed Pub/Sub):**
1.  $R_1$ ставит статус `LOCKED` в БД.
2.  $R_2$ видит `LOCKED`.
3.  $R_2$ подписывается на канал Redis Pub/Sub: `idempotency:notify:uuid-1` и засыпает (блокирует соединение).
4.  $R_1$ завершает работу, обновляет БД на `SUCCESS` и публикует сообщение в `idempotency:notify:uuid-1`.
5.  $R_2$ просыпается, читает результат из БД/Кэша и возвращает его клиенту.

*   **Плюсы:** Идеальный UX. Клиент послал два запроса, оба вернули `200 OK` (один чуть позже). Клиенту не нужно реализовывать сложную логику ретраев.
*   **Минусы:** **Thread Starvation**. Если $R_1$ выполняется 10 секунд, то поток, обрабатывающий $R_2$, будет заблокирован на 10 секунд. В языках с Thread-per-Request (Java Spring MVC, Python Django) это может убить сервер (C10K problem). В асинхронных рантаймах (Go, Node.js, Netty) это дешевле, но всё равно держит открытым TCP-сокет и File Descriptor.

### 4.3. Стратегия C: Busy Wait / Spin-Lock (Антипаттерн)

Частая ошибка начинающих:
```python
while get_status(key) == 'LOCKED':
    sleep(0.1) # Ожидание в цикле
return get_result(key)
```
**Вердикт Эксперта:** **Никогда так не делайте.**
*   Это сжигает CPU (если sleep короткий).
*   Это забивает пул соединений к БД (постоянные polling запросы `SELECT`).
*   Если $R_1$ зависнет, $R_2$ будет висеть до таймаута шлюза (504 Gateway Timeout).

### 4.4. Проблема Зомби-Локов (Dead Man's Switch)

Что произойдет, если сервер, обрабатывающий $R_1$, **внезапно умрет** (OOM Killer, Power Failure) после установки статуса `LOCKED`, но до завершения?
Запись в БД останется в статусе `LOCKED` навечно. Все повторные запросы (и по стратегии А, и по стратегии B) будут вечно получать 409 или висеть.

**Механизм защиты: Lock Expiration + Recovery**

1.  **Passive Expiration (Ленивое восстановление):**
    При вставке `LOCKED` мы пишем `locked_until = now() + 30s`.
    Приходит $R_2$. Видит `LOCKED`.
    *   Если `now() < locked_until` $\to$ `409 Conflict`.
    *   Если `now() > locked_until` $\to$ Мы считаем, что $R_1$ умер. $R_2$ перехватывает лок (Atomic CAS: `UPDATE ... SET locked_until = new_time WHERE key = ... AND locked_until < now()`).
    *   **Риск:** Если $R_1$ был просто медленным (GC pause на 35 секунд), а не мертвым, $R_2$ начнет выполнение параллельно. Это нарушает изоляцию. Требуется **Fencing Token** (монотонно возрастающий счетчик), чтобы БД отвергла поздний коммит от $R_1$.

2.  **Active Recovery (Фоновый сборщик):**
    Отдельный процесс (Sweeper) сканирует таблицу на предмет протухших `LOCKED` записей.
    *   Он проверяет статус транзакции (если это возможно) или помечает их как `FAILED_TIMEOUT`.
    *   Клиент при следующем ретрае увидит `FAILED` и сможет создать **новый** запрос с **новым** ключом.

### Резюме для Staff Engineer

Для высоконагруженных публичных API:
1.  Используйте **Стратегию A (409 Conflict)**. Это масштабируемо и безопасно.
2.  Обязательно реализуйте поле `locked_until` (Dead Man's Switch).
3.  Не пытайтесь делать Request Coalescing (Стратегия B) на уровне приложения без острой необходимости (например, для очень дорогих вычислений, кэширование которых критично). Лучше переложите ожидание на клиента.

## 5. Валидация Payload (Request Hash)

Идемпотентность — это привязка результата к **намерению**. Ключ `Idempotency-Key` является лишь *идентификатором* этого намерения. Если идентификатор тот же, а суть намерения (параметры) изменилась — это нарушение контракта.

Без валидации Payload ваша система уязвима для двух сценариев:
1.  **Logical Bugs:** Клиент сделал Retry, но случайно изменил timestamp, ID товара или сумму в теле запроса. Если вы вернете старый ответ, клиент будет думать, что прошла *новая* сумма.
2.  **Hijacking Attacks:** Злоумышленник угадывает или крадет успешный `Idempotency-Key` и пытается выполнить *свой* зловредный запрос, надеясь, что сервер пропустит его из-за наличия ключа (если валидация слабая) или вернет данные чужой транзакции.

### 5.1. Что входит в "Отпечаток" (Fingerprint Scope)?

Хешировать только тело (`Body`) недостаточно. Отпечаток должен уникально определять операцию.

**Формула Fingerprint:**
$$ H = \text{SHA256}(\text{Method} + \text{Path} + \text{QueryParams} + \text{CanonicalBody} + \text{AuthContext}) $$

*   **Method + Path:** Критично. Один и тот же UUID не может быть использован для `POST /create-order` и `POST /refund-order`.
*   **CanonicalBody:** Нормализованное тело запроса (см. п. 5.2).
*   **AuthContext (User ID):** **Обязательно.** Это защищает от атак, когда User A пытается использовать ключ, созданный User B. Ключ идемпотентности должен быть изолирован в пространстве пользователя.

### 5.2. Проблема Канонизации (JSON Normalization)

Это самая частая ошибка реализации. В JSON порядок ключей не гарантирован, а пробелы (whitespace) не значимы.

**Пример:**
Два семантически идентичных JSON, которые дадут **разные** SHA-256 хеши, если считать "в лоб" от сырой строки:

*   Запрос А: `{"amount": 100, "currency": "USD"}`
*   Запрос Б: `{"currency": "USD", "amount": 100}`

Если вы используете наивное хеширование, Запрос Б будет отвергнут (так как хеш не совпадет), хотя клиент просто использовал другую библиотеку сериализации при ретрае.

**Решение Архитектора:**
Перед хешированием необходимо привести структуру к **Каноническому виду** (Canonicalization).
1.  **Парсинг:** Десериализуем JSON в объект/Map.
2.  **Сортировка:** Рекурсивно сортируем все ключи в алфавитном порядке.
3.  **Сериализация:** Превращаем обратно в строку без пробелов.

Существует стандарт **RFC 8785 (JSON Canonicalization Scheme - JCS)**. Используйте библиотеки, реализующие его, вместо написания велосипедов.

### 5.3. Стратегия обработки коллизий

Что делать, если ключ найден, но `Fingerprint` не совпал?

**Ответ: 422 Unprocessable Entity.**

Не используйте `409 Conflict` (он зарезервирован для гонки/состояния ресурсов) и не используйте `400 Bad Request` (синтаксис верный). Ошибка `422` семантически точна: "Сервер понимает формат, но не может выполнить инструкции из-за логического противоречия".

**Пример ответа:**
```http
HTTP/1.1 422 Unprocessable Entity
Content-Type: application/problem+json

{
  "type": "https://api.system.com/probs/idempotency-mismatch",
  "title": "Idempotency Key Mismatch",
  "detail": "The idempotency key 'uuid-1' was previously used with different request parameters.",
  "idempotency_key": "uuid-1"
}
```

### 5.4. Хранение: Hash vs Payload

Нужно ли хранить полный JSON запроса в таблице `idempotency_keys` для сверки?

*   **Вариант А (Хранить полный JSON):**
    *   *Плюс:* Удобно для отладки. Можно показать клиенту diff ("Ты прислал 100, а было 200").
    *   *Минус:* TOAST (Postgres) оверхед. Если пейлоады большие, таблица распухнет. GDPR риски (персональные данные в технической таблице).
*   **Вариант Б (Хранить только Hash):**
    *   *Плюс:* Эффективно. `CHAR(64)` (HEX SHA-256) занимает мало места. Индекс работает быстро.
    *   *Минус:* Невозможно сказать клиенту, *какое именно* поле отличается.
    *   **Рекомендация:** Хранить только **Hash**. Безопасность и производительность важнее подробной диагностики ошибки клиента (клиент сам должен знать, что он шлет).

### 5.5. Edge Case: Ротация ключей (Ignorable Fields)

Иногда в запросе меняются поля, которые *не влияют* на идемпотентность.
Например, поле `requestTimestamp` или `clientTraceId` внутри JSON-тела.

Если вы включите их в хеш, то ретрай (с обновленным timestamp) будет отвергнут как Mismatch.

**Решение:**
1.  **Игнорировать:** Настроить канонизатор на исключение специфических полей (`timestamp`, `trace_id`) перед хешированием.
2.  **Strict Mode (Рекомендуется):** Считать любое изменение тела изменением намерения. Клиент при ретрае **обязан** присылать байт-в-байт тот же запрос. Это проще в поддержке и безопаснее, чем поддерживать "белые списки" игнорируемых полей.

### Резюме реализации

```python
def validate_idempotency(key, user_id, raw_body, method, path):
    # 1. Canonicalize
    payload_obj = json.loads(raw_body)
    canonical_str = jcs.serialize(payload_obj) # RFC 8785 implementation
    
    # 2. Compute Hash
    context_str = f"{method}:{path}:{user_id}:{canonical_str}"
    fingerprint = hashlib.sha256(context_str.encode()).hexdigest()
    
    # 3. Check DB
    stored_record = db.get_key(key)
    
    if stored_record:
        if stored_record.fingerprint != fingerprint:
            raise UnprocessableEntity("Idempotency mismatch")
        return stored_record.response
        
    return None # New Key
```

## 6. Обработка ошибок (The Failure Scenarios)

В наивной реализации ключи сохраняются только при успехе (`200 OK`). В экспертной реализации мы классифицируем ошибки на **Terminal** (Терминальные) и **Transient** (Временные).

### 6.1. Терминальные ошибки (Deterministic Failures)
Это ошибки бизнес-логики или валидации. Они зависят от *данных* запроса, а не от состояния среды.

*   **Примеры:**
    *   `400 Bad Request` (Неверный формат).
    *   `402 Payment Required` (Недостаточно средств на карте).
    *   `422 Unprocessable Entity` (Валидация бизнес-правил).
*   **Стратегия:** **COMMIT (Сохранять результат).**
    *   Мы помечаем ключ как использованный (`status: FAILED` или `SUCCESS` с телом ошибки).
    *   Мы сохраняем JSON ответа с ошибкой.
*   **Почему:** Если у пользователя нет денег сейчас, через 100 миллисекунд (на авто-ретрае) денег у него не появится. Если мы не сохраним ошибку, мы заставим процессинг снова стучаться в банк, платить комиссию за вызов API и получать тот же отказ. Идемпотентность должна возвращать *тот же* отказ.

**Пример (Псевдокод транзакции):**
```python
try:
    validate_balance(user, amount) # Выбрасывает InsufficientFunds
    create_order(...)
    db.commit(key_status="SUCCESS", response={...})
except InsufficientFunds as e:
    # МЫ КОММИТИМ ТРАНЗАКЦИЮ, но только с обновлением ключа!
    # Заказ не создан, но ключ "сгорел".
    error_json = {"error": "low_balance"}
    db.commit(key_status="FAILED", response=error_json)
    return 402, error_json
```

### 6.2. Временные ошибки (Transient Failures)
Это ошибки инфраструктуры. Они зависят от *времени* и *среды*.

*   **Примеры:**
    *   `503 Service Unavailable` (Внешний API лежит).
    *   `504 Gateway Timeout` (База данных тормозит).
    *   `429 Too Many Requests` (Rate Limiting).
    *   `DeadlockDetected` (В БД).
    *   Любые сетевые исключения (`ConnectionRefused`).
*   **Стратегия:** **ROLLBACK (Стирать попытку).**
    *   Мы откатываем транзакцию базы данных. Запись `idempotency_key` (которая была в статусе `LOCKED`) удаляется или откатывается.
    *   *Альтернатива:* Если вы используете Redis/NoSQL, вам нужно явно удалить ключ (`DEL key`).
*   **Почему:** Если база данных лежала в 12:00:01, в 12:00:05 она может подняться. Если мы закэшируем ошибку `500` на ключ идемпотентности, пользователь *навсегда* останется с этой ошибкой для данного заказа, даже когда система починится. Он не сможет совершить покупку, пока не сгенерирует *новый* ключ (что обычно требует перезагрузки страницы или очистки корзины). Это UX-катастрофа.

**Пример (Псевдокод):**
```python
try:
    payment_gateway.charge(...) # Выбрасывает TimeoutError
    db.commit(key_status="SUCCESS", ...)
except TimeoutError:
    # МЫ ОТКАТЫВАЕМ ВСЁ.
    # Ключ исчезает из БД (или остается LOCKED до истечения TTL, см. п. 4).
    db.rollback() 
    return 504, {"error": "upstream_timeout"}
```

### 6.3. "Серая зона" (Unknown Unknowns)

Самый страшный сценарий для архитектора: **Timeout при получении ответа, но неизвестность о выполнении.**

**Сценарий:**
1.  Мы отправили запрос в банк на списание денег.
2.  Банк списал деньги.
3.  Сетевое соединение разорвалось *до* того, как мы получили подтверждение.
4.  Наш сервер ловит `ReadTimeout`.

Это `Transient` ошибка (сеть), но операция (списание) *могла* пройти.

**Решение (Staff Level):**
Здесь нельзя делать простой `ROLLBACK`.
1.  Если мы сделаем `ROLLBACK`, клиент повторит запрос. Мы снова пойдем в банк $\to$ Двойное списание (если банк не поддерживает идемпотентность).
2.  **Правильный подход:** Сохранить статус `FAILED_RETRYABLE` (или оставить `LOCKED` с пометкой).
3.  При повторном запросе клиента (с тем же ключом):
    *   Видим статус `FAILED_RETRYABLE`.
    *   Запускаем процедуру **Reconciliation (Сверка)** с внешним сервисом (проверяем статус транзакции в банке), а не создаем новую.
    *   Если в банке "Успех" $\to$ обновляем у себя на "Успех" и отдаем клиенту.
    *   Если в банке "Нет такой транзакции" $\to$ создаем новую.

### 6.4. Матрица Решений (Error Mapping Table)

| Тип ошибки | Пример | Действие с Ключом | HTTP Ответ клиенту |
| :--- | :--- | :--- | :--- |
| **Success** | Order Created | `COMMIT` ("SUCCESS") | 200/201 |
| **Logic Error** | Invalid Amount | `COMMIT` ("FAILED") | 400/422 |
| **Business Rule** | Insufficient Funds | `COMMIT` ("FAILED") | 402/403/409 |
| **Infrastructure** | DB Connection Lost | `ROLLBACK` (Delete) | 500 |
| **Upstream** | Gateway Timeout | `ROLLBACK` (Delete) | 503/504 |
| **Ambiguous** | Read Timeout (после Write) | `COMMIT` ("PENDING/RECOVERY") | 504 (с Retry-After) |

### 6.5. Исключение: Poison Pill (Ядовитая таблетка)

Существует редкий класс ошибок, когда *сам запрос* вызывает крэш сервера (например, баг в парсере XML или переполнение стека).
*   Если мы сделаем `ROLLBACK`, клиент (или очередь сообщений) будет бесконечно повторять этот запрос.
*   Каждый повтор будет убивать воркер/под.
*   Это приведет к **Crash Loop Backoff** всего сервиса.

**Защита:**
Очереди сообщений (Kafka/SQS) имеют механизм **Dead Letter Queue (DLQ)**.
В синхронном API это сложнее. Если один и тот же ключ вызывает 5 крэшей подряд (нужен счетчик попыток в Redis), его следует пометить как `FAILED_POISON` и прекратить обработку, возвращая `422`.

## 7. Жизненный цикл ключа (TTL)

Ключи идемпотентности не могут жить вечно. Это создает бесконечный рост базы данных (Unbounded Growth). Архитектор должен определить **"Окно Идемпотентности"** (Idempotency Window) — период времени, в течение которого сервер гарантирует дедупликацию.

### 7.1. Окно Идемпотентности (The Contract)

Стандарт индустрии (Stripe, Adyen, PayPal) — **24 часа**.
Почему 24 часа?
1.  **Покрытие Ретраев:** 99.99% автоматических сетевых ретраев (Exponential Backoff) происходят в первые 15 минут.
2.  **Человеческий фактор:** Если пользователь забыл вкладку открытой и нажал "Оплатить" на следующий день — это, скорее всего, *новое* намерение, а не дубль старого.
3.  **Operations:** Суточная партиция удобна для ротации данных.

**Семантический сдвиг (The Semantic Shift):**
После истечения TTL ключ "исчезает".
*   Если клиент пришлет тот же ключ через 25 часов, сервер воспримет его как **совершенно новый запрос**.
*   **Риск:** Replay Attack. Злоумышленник может записать трафик и повторить запрос через сутки.
*   **Защита:** Идемпотентность должна работать в паре с валидацией заголовка `Date` или `X-Request-Timestamp`. Сервер должен отвергать запросы старше, чем окно идемпотентности (например, "Request is too old").

### 7.2. Стратегия очистки в RDBMS (Database Vacuuming)

Наивное удаление старых строк — убийца производительности PostgreSQL/MySQL.

**Проблема `DELETE`:**
В MVCC-базах (Postgres) операция `DELETE` не освобождает место физически сразу. Она помечает строки как "мертвые" (Dead Tuples).
*   Это вызывает **Write Amplification** (запись в WAL).
*   Это заставляет процесс `VACUUM` работать на износ, вычищая миллионы строк.
*   Индексы распухают (Index Bloat), замедляя вставку новых ключей.

**Решение Архитектора: Time-Partitioning (Партиционирование)**
Вместо удаления строк мы удаляем **таблицы**.

1.  Создаем таблицу `idempotency_keys` как партиционированную по `created_at`.
    *   `idempotency_keys_2023_10_25`
    *   `idempotency_keys_2023_10_26`
2.  При вставке данные автоматически попадают в нужную партицию (сегодняшнюю).
3.  Фоновый процесс (Drop Job) просто делает:
    `DROP TABLE idempotency_keys_2023_10_24;`
4.  **Эффективность:** Это операция $O(1)$ на уровне файловой системы (unlink files). Никакого WAL bloat, никакой нагрузки на вакуум.

**SQL Пример (PostgreSQL 14+):**
```sql
CREATE TABLE idempotency_keys (
    key UUID NOT NULL,
    -- ... остальные поля
    created_at TIMESTAMPTZ NOT NULL
) PARTITION BY RANGE (created_at);

-- Создаем партиции заранее (через cron или pg_partman)
CREATE TABLE keys_2023_10_27 PARTITION OF idempotency_keys
    FOR VALUES FROM ('2023-10-27 00:00:00') TO ('2023-10-28 00:00:00');
```

### 7.3. Стратегия очистки в NoSQL (TTL Indexes)

Если вы используете DynamoDB, Cassandra или MongoDB, используйте нативные механизмы.

*   **DynamoDB:** Включить TTL на атрибут `expires_at`. Удаление происходит "бесплатно" в фоне (без потребления WCU - Write Capacity Units).
*   **Redis:** `EXPIRE` выставляется при создании ключа. Это самый простой вариант, но Redis хранит всё в RAM, что дорого для хранения истории за 24 часа при высоком RPS.

### 7.4. Оптимизация "Тяжелых" Ответов (Payload Offloading)

Что если ответ API весит 1 МБ (большой JSON)? Хранить его в базе данных (или Redis) накладно.

**Паттерн: Двухуровневый TTL**

Мы разделяем хранение **статуса** (Lock) и **пейлоада** (Response).

1.  **Status Record:** Храним 24 часа. (Мелкая запись: Key, Status, Hash).
    *   *Цель:* Защита от повторного выполнения (Logic Safety).
2.  **Payload Record:** Храним, например, 1 час. (Тяжелый JSON).
    *   *Цель:* Возврат кэшированного ответа для немедленных ретраев.

**Поведение:**
*   Если клиент пришел через 5 минут $\to$ Вернуть полный JSON из кэша.
*   Если клиент пришел через 5 часов $\to$
    *   Запись есть? Да.
    *   Статус `SUCCESS`? Да.
    *   Пейлоад есть? Нет (удален для экономии места).
    *   **Действие:** Вернуть `200 OK` с пустым телом или ссылкой `GET /orders/{id}`. Или `204 No Content`.
    *   *Логика:* Мы гарантируем, что *не выполнили* дубль, но мы не обязаны вечно хранить копию старого ответа. Главное — мы сообщили клиенту, что "всё хорошо, операция уже была выполнена".

### 7.5. Compliance & Privacy (GDPR/CCPA)

В таблице `idempotency_keys` часто оседает PII (Personal Identifiable Information) — email, адрес, телефон (внутри `request_hash` или `response_body`).

*   **Право на забвение:** Если пользователь требует удалить данные, вы должны почистить не только таблицу `users`, но и `idempotency_keys`.
*   **Шифрование:** В идеале, `response_body` должен храниться зашифрованным, либо не содержать PII.
*   **Рекомендация:** Храните в `response_body` только ID созданных ресурсов (`{"order_id": "123", "status": "created"}`), а не полную копию объекта с данными пользователя. Это снимает большинство проблем с комплаенсом.

### Резюме стратегии TTL

| Слой хранения | Метод очистки | Сложность | Рекомендация |
| :--- | :--- | :--- | :--- |
| **PostgreSQL / MySQL** | `DELETE WHERE ...` | 🔴 Высокая нагрузка | ⛔️ Только для малых объемов |
| **PostgreSQL** | **Partitioning (`DROP TABLE`)** | 🟢 $O(1)$ | ✅ **Стандарт для Highload** |
| **Redis** | `EXPIRE` | 🟢 Нативно | ✅ Для краткосрочных локов |
| **DynamoDB** | TTL Attribute | 🟢 Бесплатно (BG process) | ✅ Отличный выбор |
| **Payload Storage** | S3 Lifecycle / Separate Table | 🟡 Средняя | ✅ Для больших ответов (>10KB) |

## 8. Чек-лист уровня Expert

1.  **Response Caching:**
    Вы сохраняете не только тело ответа, но и **HTTP Headers** и **Status Code**. Если первый запрос вернул `201 Created` с хедером `Location: /orders/1`, дубликат должен вернуть то же самое.
2.  **Scope ключей:**
    Ключ должен быть уникален в рамках `User` или `Account`. Глобальный индекс по `key` может быть дорогим, композитный `(user_id, key)` лучше партиционируется.
3.  **Side Effects за пределами БД:**
    Если ваша операция — это вызов внешнего API (например, отправка email), транзакция в БД вас не спасет.
    *   *Паттерн:* Сначала коммитим "Намерение отправить" (Idempotency Key + Status: PENDING_EMAIL), потом фоновый воркер отправляет и обновляет статус.
4.  **Recovery:**
    Что если процесс упал в состоянии `LOCKED` и не обновил запись?
    *   Ключ "зависнет" навсегда. Нужен фоновый процесс (Sweeper), который находит старые `LOCKED` записи (старше 5 минут) и либо помечает их как `FAILED`, либо перезапускает (если операция может быть продолжена).

### Заключение

Для **Staff Engineer** реализация идемпотентности — это упражнение в управлении распределенным состоянием.
Не используйте Redis для критически важных данных (платежей). Используйте **ACID-транзакции** базы данных с паттерном `Insert-or-Return`, хешируйте пейлоады и не забывайте про очистку зависших локов.

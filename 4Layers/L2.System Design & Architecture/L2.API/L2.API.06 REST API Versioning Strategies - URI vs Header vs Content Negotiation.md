**TL;DR**: Версионирование API — это не спор о красоте URL. Это спор между **DX (Developer Experience)** и **Инфраструктурой (Caching/Routing)**.
*   **URI Versioning** (`/v1/users`) — это выбор прагматика. Это "не по REST", но это дешево для CDN, понятно разработчику и легко маршрутизируется.
*   **Header Versioning** — это выбор корпоративного архитектора. Позволяет сохранить URI чистыми, но превращает настройку кэширования (Vary Headers) и отладку в ад.
*   **Content Negotiation** — это "академический" выбор. Идеален в теории, но на практике (кроме GitHub) используется редко из-за чудовищной сложности тулинга.

Правило Эксперта: **Версионируйте как можно позже и поддерживайте как можно меньше версий.** Каждая активная версия `vN` — это технический долг, умноженный на коэффициент поддержки.

---

На уровне Staff Engineer вы выбираете стратегию версионирования не для того, чтобы было "красиво", а чтобы минимизировать **Mean Time To Recovery (MTTR)** при деплое и максимизировать **Cache Hit Ratio** на Edge-серверах.

## 1. Стратегия 1: URI Versioning (Path)

**Стандарт индустрии:** Google, Twitter, Stripe (частично), Facebook.
**Формат:** `https://api.example.com/v1/resources/123`

### 1.1. Архитектурная анатомия
В этом подходе номер версии становится частью **иерархического пространства имен** (Namespace).
URL ментально разбивается на три части:
1.  **Routing Base:** `api.example.com/v1` — определяет, *какой кластер* или *какой код* будет обрабатывать запрос.
2.  **Resource Path:** `/products/123` — определяет бизнес-сущность.
3.  **Query Params:** `?sort=desc` — модификаторы представления.

**Почему пуристы REST ненавидят это:**
Согласно диссертации Роя Филдинга, URI (Uniform Resource Identifier) должен быть **постоянным (Immutable)** идентификатором ресурса.
*   Если `/v1/products/1` и `/v2/products/1` указывают на один и тот же товар (ID=1), то у вас два разных идентификатора для одной сущности (**Aliasing**).
*   Это нарушает принцип "Cool URIs don't change".

**Почему инженеры выбирают это:**
Мы жертвуем семантической чистотой ради **эксплуатационной простоты**. Мы трактуем `/v1` не как свойство ресурса, а как **контракт доступа** к нему.

### 1.2. Механика маршрутизации (L7 Routing) — Киллер-фича

Главное преимущество URI Versioning — возможность разруливать трафик на самых ранних этапах входа в систему (Ingress).

**Сценарий:** Вы выкатываете `v2` API, который написан на Go вместо Java и имеет другую структуру БД.

*   **Конфигурация NGINX / Envoy / AWS ALB:**
    Маршрутизация по пути (Path-based routing) — это самая дешевая операция для балансировщика (обычно префиксное дерево / trie).

    ```nginx
    # Пример конфигурации NGINX
    location /v1/ {
        proxy_pass http://legacy-java-cluster; # Старый монолит
    }

    location /v2/ {
        proxy_pass http://new-go-microservices; # Новый кластер
    }
    ```

*   **Результат:** Вы можете держать две совершенно разные инфраструктуры параллельно. При *Header Versioning* вам пришлось бы либо ставить умный (и дорогой по CPU) API Gateway, который инспектирует заголовки и делает сложный роутинг, либо направлять весь трафик в один сервис, который внутри себя содержит `if (version == 2) ...`.

### 1.3. Влияние на Кэширование (CDN & Browser Cache)

Это то, что часто упускают при проектировании.
Для любого HTTP-кэша (будь то Cloudflare, Varnish или браузер) **Primary Cache Key** — это URL.

1.  **Cache Locality:**
    *   Запрос `/v1/news` $\to$ Ключ `api.com/v1/news`
    *   Запрос `/v2/news` $\to$ Ключ `api.com/v2/news`
    Объекты физически разделены в памяти кэша. Вероятность **Cache Poisoning** (когда клиент `v1` получает ответ формата `v2`) равна **нулю**.

2.  **Отсутствие `Vary`:**
    Вам не нужно настраивать заголовок `Vary: Accept` или `Vary: X-API-Version`. Это экономит нервы, так как неправильная настройка `Vary` часто приводит к тому, что CDN перестает кэшировать вовсе.

### 1.4. Гранулярность: Global vs Resource Versioning

Внутри стратегии URI есть развилка, которую нужно выбрать на старте:

**А. Global Versioning (`/v1/users`, `/v1/orders`)**
*   **Суть:** Версия относится ко всему API целиком.
*   **Проблема:** Если вы меняете формат `Orders` (выпускаете `v2`), вы обязаны выпустить и `/v2/users`, даже если User не изменился. Вам придется дублировать код или делать алиасы.
*   **Плюс:** Консистентность. Клиент знает: "Я использую SDK v1".

**Б. Resource Versioning (`/users/v1`, `/orders/v3`)**
*   **Суть:** Каждый микросервис версионируется независимо.
*   **Проблема:** API Gateway превращается в "лоскутное одеяло". Клиентское приложение должно знать: "Пользователей я беру из v1, а Заказы из v3".
*   **Совет Архитектора:** Избегайте варианта Б для публичных API. Это создает чудовищный **DX (Developer Experience)**. Клиенты хотят "Platform Version", а не разбираться в жизненных циклах ваших микросервисов.

### 1.5. Проблема Hypermedia (HATEOAS)

Если вы используете HATEOAS (возвращаете ссылки `_links` в ответе), URI Versioning создает сложность.

*   *Запрос:* `GET /v1/users/10`
*   *Ответ (неправильный):*
    ```json
    {
      "id": 10,
      "orders_url": "/orders?user_id=10" // Куда это ведет? В v1 или v2?
    }
    ```
*   *Решение:* Бэкенд должен знать свой "контекст версии" и генерировать ссылки относительно него.
    ```json
    "orders_url": "/v1/orders?user_id=10" // Жесткая привязка
    ```
Это усложняет миграцию: когда клиент переключается на `v2`, все ссылки в ответах тоже должны начать указывать на `v2`.

### Резюме раздела

**URI Versioning** — это выбор **прагматика**.
*   Это **Namespace**, а не Resource ID.
*   Это **бесплатная** изоляция кэша.
*   Это **дешевая** маршрутизация на уровне L7 балансировщиков.

Выбирайте этот метод, если вам важнее **стабильность инфраструктуры** и **простота отладки** (curl-ability), чем академическая чистота REST.

## 2. Стратегия 2: Header Versioning (Custom Header)

**Стандарт индустрии:** Microsoft (Graph API), Amazon (частично), многие Enterprise SaaS.
**Формат:** `GET https://api.example.com/products/123`
**Заголовок:** `X-API-Version: 2` (или `api-version: 2`)

### 2.1. Архитектурная анатомия: Разделение Идентичности и Представления

В отличие от URI Versioning, этот подход строго следует философии REST:
*   **URI (Uniform Resource Identifier)** — определяет **идентичность** ресурса. Ресурс "Товар №123" неизменен.
*   **Header** — определяет **контракт (представление)**. То, в каком виде вы хотите получить этот ресурс.

**Ментальная модель:** Это похоже на паттерн "Strategy" в ООП. Объект один (`/products/123`), но стратегия его сериализации выбирается в рантайме на основе контекста (заголовка).

### 2.2. Инфраструктурный налог: Проблема `Vary` и CDN

Это самый критичный аспект для архитектора. Если вы выбираете Header Versioning, вы обязаны быть экспертом в HTTP-кэшировании.

**Механика катастрофы (Cache Poisoning):**
Представьте, что вы используете CDN (Cloudflare, Akamai) или NGINX Cache.
1.  **Клиент A (Legacy)** запрашивает `/products/123` с заголовком `X-Ver: 1`.
2.  Кэш видит ключ `/products/123` (по умолчанию заголовки не входят в ключ кэширования). Кэш пуст. Запрос идет на бэкенд.
3.  Бэкенд возвращает JSON версии 1. Кэш сохраняет его под ключом `/products/123`.
4.  **Клиент B (Modern)** запрашивает `/products/123` с заголовком `X-Ver: 2`.
5.  Кэш видит ключ `/products/123`. **Cache Hit!** Кэш отдает сохраненный JSON версии 1.
6.  **Результат:** Клиент B падает, так как получил старую структуру данных.

**Решение (Header `Vary`):**
Сервер *обязан* отвечать с заголовком `Vary: X-API-Version`.
Это инструкция для всех промежуточных кэшей: *"Внимательно! Ключ кэширования состоит не только из URL, но и из значения заголовка X-API-Version"*.

**Скрытая цена решения (Cache Fragmentation):**
*   **Normalization:** Если Клиент A шлет `X-Ver: 1`, а Клиент C шлет `X-Ver: 1.0` (и ваш бэкенд понимает оба варианта), для CDN это **два разных объекта**. Эффективность кэширования (Hit Ratio) падает.
*   **Permutations:** Если вы кэшируете с учетом `Vary: X-Ver, Authorization, Accept-Language`, количество вариаций одного URL взрывается факториально. Кэш переполняется.

### 2.3. Маршрутизация (L7 Routing Complexity)

Как направить трафик `v1` на старый кластер, а `v2` на новый?
При URI Versioning это тривиальный префиксный матчинг (`location /v1/`).
При Header Versioning ваш API Gateway (Ingress Controller) должен уметь инспектировать заголовки.

*   **Проблема:** Инспекция заголовков дороже для CPU балансировщика, чем парсинг URL.
*   **Конфигурация:** В Kubernetes Ingress или AWS ALB правила становятся сложнее:
    ```yaml
    # Пример псевдо-конфига
    - match:
        path: /products
        headers:
          X-API-Version: "2"
      action: forward_to_service_v2
    - match:
        path: /products
        # Нет заголовка или "1"
      action: forward_to_service_v1
    ```
*   **Риск:** Если правило настроено неверно (например, опечатка в имени заголовка), трафик может молча уйти на дефолтный (старый) кластер, и вы получите логические ошибки вместо 404.

### 2.4. Политики управления версиями (Governance)

При использовании заголовков возникает вопрос "дефолтного поведения".

**Стратегия А: Implicit Latest (Опасная)**
Если заголовок не передан $\to$ вернуть самую новую версию.
*   *Почему плохо:* Вы деплоите `v3`. Все клиенты, которые "ленились" слать заголовок, мгновенно ломаются.
*   *Вердикт:* **Запрещено** для публичных API.

**Стратегия Б: Implicit Oldest (Pinned)**
Если заголовок не передан $\to$ вернуть первую версию (`v1`).
*   *Почему плохо:* Вы никогда не сможете убить `v1`. Она станет "вечным" легаси, которое тянет вас на дно.

**Стратегия В: Explicit Mandatory (Строгая)**
Если заголовок не передан $\to$ `400 Bad Request` ("Header X-API-Version is required").
*   *Плюс:* Полная предсказуемость.
*   *Минус:* Ужасный DX. Нельзя просто открыть ссылку в браузере или скинуть коллеге. Нужен плагин-модификатор заголовков.

### 2.5. Проблема документации (OpenAPI / Swagger)

Инструментарий OpenAPI (до версии 3.0 включительно) исторически плохо поддерживал этот паттерн.
Описать "Один Endpoint `/users` возвращает схему A, если заголовок X=1, и схему B, если заголовок X=2" — это боль.
Вам часто приходится создавать **два разных spec-файла** (openapi-v1.yaml, openapi-v2.yaml), что приводит к рассинхрону документации, так как код контроллера, скорее всего, один.

### Резюме раздела

**Header Versioning** — это выбор **корпоративного архитектора**, который готов платить сложностью инфраструктуры за чистоту URL.

*   **Выбирайте этот метод, если:**
    1.  У вас "умный" API Gateway (Kong, Apigee, Tyk), который берет на себя нормализацию и роутинг.
    2.  Ваш API очень велик, и дублирование `/v1`, `/v2` в URL выглядит неэстетично.
    3.  Вы готовы к сложной отладке кэширования (Vary headers).
*   **Избегайте, если:**
    1.  Вам нужен простой CDN-кэш.
    2.  Ваш приоритет — DX (Developer Experience) и простота использования API из консоли/браузера.

## 3. Стратегия 3: Content Negotiation (Media Type)

**Стандарт индустрии:** GitHub (до недавнего времени), немецкие Enterprise-системы.
**Формат:** `GET https://api.example.com/products/123`
**Заголовок:** `Accept: application/vnd.mycompany.v2+json`

### 3.1. Архитектурная анатомия: MediaType как Контракт

В основе этого подхода лежит концепция **MIME-типов**. Мы перестаем притворяться, что возвращаем абстрактный `application/json`. Мы декларируем, что возвращаем специфический бизнес-объект, сериализованный в JSON.

Разберем структуру заголовка: `application/vnd.mycompany.product.v2+json`

1.  **`application`**: Тип медиа (Top-level type).
2.  **`vnd` (Vendor)**: Указывает, что это проприетарный формат, специфичный для вендора, а не стандарт IANA.
3.  **`mycompany.product.v2` (Subtype)**: Самая важная часть. Здесь вы кодируете домен (`mycompany`), сущность (`product`) и версию (`v2`).
4.  **`+json` (Structured Syntax Suffix)**: Подсказка для парсера. "Даже если ты не знаешь схему `mycompany.product`, ты можешь распарсить это как обычный JSON".

**Ментальная модель:** Это **Resource Versioning** (версионирование ресурсов), а не **API Versioning**.
*   Вы можете запросить `User` версии 1 и `Order` версии 3 в рамках одной сессии.
*   Это позволяет эволюционировать систему гранулярно, не объявляя "глобальную версию 2.0 всего API".

### 3.2. Инфраструктурный ад: Парсинг и `q`-факторы

Если в *URI Versioning* роутинг — это простой префиксный поиск, то здесь это полноценный **парсинг строк**.

**Проблема `q` (Quality Values):**
Стандарт HTTP (RFC 7231) разрешает клиенту указывать приоритеты:
`Accept: application/vnd.mycompany.v2+json;q=1.0, application/json;q=0.5`

**Задача балансировщика (Gateway):**
Чтобы направить запрос на правильный микросервис, API Gateway должен:
1.  Распарсить строку заголовка (Regex или лексер).
2.  Отсортировать типы по убыванию `q`.
3.  Найти лучший матч, который поддерживает сервер.
4.  Смаршрутизировать запрос.

*   **Реальность:** NGINX и HAProxy "из коробки" делают это плохо или медленно (требуется Lua/JS скриптинг). Большинство команд скатываются к простой проверке подстроки, игнорируя стандарт HTTP, что приводит к багам интеграции.

### 3.3. Кэширование: "Vary" и проблема нормализации

Как и в *Header Versioning*, здесь критичен заголовок `Vary: Accept`. Но ситуация хуже.

*   **Проблема:** Браузеры и HTTP-клиенты любят слать "мусор" в `Accept`.
    *   Chrome: `Accept: text/html,application/xhtml+xml,application/xml;q=0.9,image/webp,*/*;q=0.8`
    *   Curl: `Accept: */*`
    *   Ваш клиент: `Accept: application/vnd.v2+json`
*   **Cache Miss:** С точки зрения тупого кэша (CDN), каждая из этих строк — это **уникальный ключ**.
*   **Решение:** Вам нужен слой **нормализации** на Edge (Lambda@Edge / Varnish VCL), который приведет заголовок к единому каноническому виду *перед* тем, как запрос попадет в кэш. Без этого эффективность кэширования стремится к нулю.

### 3.4. Сложность тестирования (Testing Combinatorics)

При глобальном версионировании (`/v1`, `/v2`) у вас есть два состояния мира.
При версионировании через Media Types у вас есть матрица состояний.

Представьте endpoint `/orders`, который возвращает заказ и вложенного пользователя.
*   Клиент просит: `Accept: application/vnd.order.v2+json`
*   Внутри заказа есть User. Какой версии он должен быть? `v1`? `v2`?
*   Если клиент ожидает Order v2, но User v1, а вы вернули User v2 — контракт нарушен.
*   Вам приходится либо жестко связывать версии вложенных сущностей, либо поддерживать адскую комбинаторику сериализаторов.

### 3.5. Инструментарий (Tooling Gap)

Это главная причина, почему Content Negotiation проигрывает.

1.  **Swagger UI / OpenAPI:** Хотя OpenAPI 3.0 поддерживает `content` map для описания разных схем под разные MediaType, UI-инструменты часто делают это неудобно. Нет простой кнопки "Переключить всё API на v2". Нужно переключать каждый эндпоинт отдельно.
2.  **Отладка:** Разработчик не может просто открыть ссылку в браузере. Ему нужно использовать Postman/Curl и каждый раз вручную прописывать сложный заголовок. Копирование `curl` команд из документации становится обязательным ритуалом.

### 3.6. Вердикт Архитектора

**Content Negotiation** — это **академический идеал**, который слишком дорог в эксплуатации.

*   **Когда применять:**
    1.  Вы строите **Hypermedia API (HATEOAS)**, где состояние приложения действительно управляется типами ресурсов, а не URL-ами.
    2.  У вас очень долгоживущая система (10+ лет), где разные части домена эволюционируют с разной скоростью, и понятие "глобальной версии" вредно.
    3.  Вы — GitHub или AWS, и у вас есть ресурсы на написание собственных API Gateways и SDK генераторов.

*   **Когда избегать:**
    1.  В 99% случаев разработки обычных микросервисов. Сложность настройки NGINX, кэширования и Swagger'а не окупается гибкостью.

**Совет Staff Engineer:** Если вы хотите чистоты, но без боли — используйте **Custom Header** (`X-API-Version`). Он проще парсится, легче читается глазами и не заставляет воевать со стандартом `Accept`-заголовков браузеров.

## 4. Сравнительный анализ (Trade-off Matrix)

Вместо простых оценок "хорошо/плохо" мы разберем влияние каждой стратегии на конкретные слои вашей архитектуры.

### 4.1. Сводная матрица (Architectural Impact Matrix)

| Вектор оценки | **URI Path** (`/v1/...`) | **Custom Header** (`X-Ver: 1`) | **Content Negotiation** (`Accept: ...v1`) |
| :--- | :--- | :--- | :--- |
| **Идентификация кэша (Cache Key)** | **Native**. URL уникален сам по себе. Не требует настройки. | **Complex**. Требует добавления заголовка в ключ кэширования (Cache Key Variation). | **High Entropy**. Требует сложной нормализации из-за `q`-факторов и мусора браузеров. |
| **Сложность Маршрутизации (L7 Routing)** | **Low ($O(1)$)**. Префиксный поиск (Trie). Поддерживается любым L7-балансировщиком. | **Medium**. Инспекция заголовков (Map lookup / Regex). | **High**. Требует парсинга строки `Accept`, сортировки весов. Часто требует Lua/Scripting. |
| **Developer Experience (DX)** | **High**. "Curl-ability", кликабельные ссылки, простота шаринга. | **Medium**. Требует плагинов или CLI-флагов. | **Low**. Сложно конструировать заголовки вручную. |
| **Документация (Swagger/OpenAPI)** | **Simple**. Разные spec-файлы или группы. | **Hard**. Сложно описать разные схемы для одного URL в одном файле. | **Native (OpenAPI 3)**. Поддерживает `content` map, но UI часто неудобен. |
| **Гранулярность изменений** | **Platform Level**. Версия меняется для всего API. | **Platform / Resource**. Можно комбинировать. | **Resource Level**. Версия меняется для конкретной сущности. |

### 4.2. Детальный разбор векторов (Deep Dive)

#### 1. Вектор: Экономика Кэширования (Cache Economics)

Кэширование — это не просто сохранение ответа. Это управление ключами.

*   **URI Path:**
    *   *Механика:* `CacheKey = Host + Path + Query`.
    *   *Плюс:* **Zero Configuration**. Любой CDN (Cloudflare, Akamai, Fastly) и любой браузер кэшируют это "из коробки" максимально эффективно. Нет риска коллизий.
    *   *Риск:* Нулевой.

*   **Header / Content Neg:**
    *   *Механика:* `CacheKey = Host + Path + Query + Hash(Selected_Headers)`.
    *   *Обязательство:* Сервер обязан слать `Vary: X-API-Version` или `Vary: Accept`.
    *   *Проблема Нормализации (Cache Fragmentation):*
        *   Клиент A: `X-Ver: 1`
        *   Клиент B: `X-Ver: 1.0`
        *   Для бэкенда это одно и то же. Для кэша — это **два разных объекта**. Вы храните дубликаты в памяти кэша, снижая его полезную емкость (Eviction rate растет).
    *   *Решение:* Вам нужно писать логику на Edge (Lambda@Edge, Varnish VCL), которая канонизирует заголовки *до* обращения к кэшу (например, превращает `1.0` в `1`). Это дополнительный код, который нужно поддерживать.

#### 2. Вектор: Стоимость Маршрутизации (Ingress Performance)

Когда к вам прилетает 100k RPS, логика выбора бэкенда (Service A v1 vs Service A v2) становится значимой.

*   **URI Path:**
    *   Использует алгоритм **Longest Prefix Match** (Radix Tree / Trie).
    *   Это экстремально быстрая операция, оптимизированная на уровне железа и ядра (eBPF).
    *   Конфиг NGINX тривиален: `location /v1/ {}`.

*   **Content Negotiation:**
    *   Заголовок `Accept` может выглядеть так: `application/vnd.v2+json;q=0.9, application/json;q=1.0`.
    *   Чтобы понять, куда отправить запрос, балансировщик должен:
        1.  Распарсить строку.
        2.  Понять, что `q=1.0` (дефолтный json) приоритетнее, чем `v2` (0.9).
        3.  Принять решение.
    *   Большинство Ingress-контроллеров (стандартный NGINX Ingress) **не умеют** делать математику `q`-факторов "из коробки". Вам придется писать Lua-скрипты или использовать "глупый" Regex, который ломается на сложном `Accept`.

#### 3. Вектор: Смешанный контент и HATEOAS

Как ссылки внутри ответа (Hypermedia) указывают на другие ресурсы?

*   **URI Path:**
    *   Ответ `v1` содержит ссылки с префиксом `/v1/...`.
    *   Ответ `v2` содержит ссылки с префиксом `/v2/...`.
    *   Все ссылки **абсолютны** и самодостаточны. Вы можете сохранить JSON в файл, открыть его через год, и ссылки будут валидны (указывают на конкретную версию).

*   **Header / Content Neg:**
    *   Ссылки в ответе обычно выглядят как `/orders/123` (без версии).
    *   Версия определяется **контекстом текущего запроса** (заголовком).
    *   *Риск:* Если вы скопируете ссылку из ответа и отправите другу (без заголовка), он получит **дефолтную** (возможно, новую v3) версию ресурса, а не ту, которую видели вы. Ссылки становятся **context-dependent**, что нарушает принцип *Self-descriptive messages*.

#### 4. Вектор: Эксплуатация "Зоопарка" (Operational Complexity)

Что происходит через 3 года, когда у вас живут v1, v2 и v3 одновременно?

*   **URI Path:**
    *   В логах (ELK/Splunk) вы мгновенно видите распределение трафика: `count by url_path`.
    *   В мониторинге (Prometheus) метрики автоматически разбиты: `http_requests_total{path="/v1/..."}`.
    *   Вы можете легко задепрекейтить `v1` на уровне роутера (вернуть 410 для `/v1/*`).

*   **Headers:**
    *   В логах URL одинаковый. Вам нужно парсить и индексировать заголовки, чтобы понять, кто какую версию использует.
    *   В метриках нужно специально добавлять cardinality по версии, что увеличивает нагрузку на Prometheus.
    *   Сложнее "отключить" версию: нужна логика "если header == v1, то 410".

### Вердикт для Design Doc

Когда вы заполняете раздел "Alternatives Considered" в вашем архитектурном документе (RFC), используйте следующую формулировку:

> "Мы выбираем **URI Versioning** как основной подход, несмотря на нарушение семантики REST, по следующим причинам:
> 1.  **Надежность кэширования:** Гарантирует отсутствие коллизий в CDN без сложной конфигурации `Vary`.
> 2.  **Прозрачность:** Позволяет однозначно идентифицировать версию ресурса в логах, метриках и при обмене ссылками.
> 3.  **Производительность:** Использует эффективный L7-роутинг по пути, избегая дорогого парсинга заголовков на Ingress."

Используйте **Header Versioning** только если у вас жесткое требование от бизнеса "URL не должны меняться" (бренд, SEO для API) и у вас есть ресурсы DevOps для настройки сложного кэширования.

## 5. Влияние на кэширование (Deep Dive)

Кэширование — это фундамент масштабируемости API. Выбирая стратегию версионирования, вы фактически выбираете алгоритм построения **Ключа Кэширования (Cache Key)**.

### 5.1. Анатомия Ключа (The Cache Key Anatomy)

Любой HTTP-кэш (Cloudflare, Akamai, NGINX, Varnish) работает как гигантская хеш-таблица.
По умолчанию ключ строится так:

$$ \text{CacheKey} = \text{Method} + \text{Host} + \text{URI (Path + Query)} $$

*   **URI Versioning:** Версия (`v1`, `v2`) является частью `URI`.
    *   Запрос `/v1/item` и `/v2/item` создают **два разных, непересекающихся ключа**.
    *   *Результат:* Абсолютная изоляция. Вероятность коллизии = 0.

*   **Header Versioning:** Версия находится в заголовках (`X-Ver`, `Accept`).
    *   Запрос `/item` с `X-Ver: 1` и `/item` с `X-Ver: 2` имеют **одинаковый URI**.
    *   По умолчанию кэш видит их как **один и тот же запрос**.

### 5.2. Катастрофа №1: Cache Poisoning (Отравление кэша)

Самый страшный сон архитектора. Происходит, когда разработчик забывает настроить заголовок `Vary`.

**Сценарий:**
1.  **Legacy Client** делает `GET /users/1` с заголовком `X-Ver: 1`.
2.  **CDN** видит ключ `GET:/users/1`. В кэше пусто (MISS). Идет на Origin.
3.  **Origin** видит заголовок, генерирует JSON v1. **Важно:** Origin *забыл* добавить заголовок `Vary: X-Ver`.
4.  **CDN** сохраняет JSON v1 под ключом `GET:/users/1`.
5.  **Mobile App (New)** делает `GET /users/1` с заголовком `X-Ver: 2`.
6.  **CDN** видит ключ `GET:/users/1`. Это HIT! Отдает сохраненный JSON v1.
7.  **Mobile App** падает, пытаясь распарсить старый формат (CrashLoop).

**Вердикт:** Если вы используете Header Versioning, отсутствие корректного `Vary` — это **P0 Incident**.

### 5.3. Механика спасения: Заголовок `Vary`

Чтобы избежать отравления, сервер обязан отвечать:
`Vary: X-API-Version`

Это инструкция для кэша: *"Уважаемый CDN, пожалуйста, добавь значение заголовка X-API-Version в свой составной ключ кэширования"*.

Теперь формула ключа меняется:
$$ \text{CacheKey} = \text{Method} + \text{URI} + \text{Hash(Header[X-API-Version])} $$

Это решает проблему отравления, но порождает новую — проблему фрагментации.

### 5.4. Катастрофа №2: Cache Fragmentation (Фрагментация)

Проблема Header-based подходов в том, что заголовки имеют высокую энтропию (много вариаций).

**Сценарий (Нормализация):**
Ваш бэкенд умный. Он понимает версии `1`, `1.0` и `1.0.0` как одно и то же.
1.  Клиент A: `X-Ver: 1` $\to$ Кэш сохраняет объект A.
2.  Клиент B: `X-Ver: 1.0` $\to$ Кэш видит *другой* ключ (строки не равны). Идет на Origin. Сохраняет объект B (дубликат A).
3.  Клиент C: `X-Ver: 1.0.0` $\to$ Идет на Origin. Сохраняет объект C (дубликат A).

**Результат:**
1.  **Падение Hit Ratio:** Вместо того чтобы обслуживать всех из одной ячейки, кэш дробится.
2.  **Origin Overload:** Бэкенд получает в 3 раза больше запросов, генерируя одни и те же данные.
3.  **Memory Waste:** Память CDN забита дубликатами, полезные данные вытесняются (Eviction).

**Особый ад Content Negotiation:**
Если вы используете `Vary: Accept`, ситуация становится критической. Браузеры шлют в `Accept` безумные комбинации (`application/xml,application/xhtml+xml,...`). Каждый уникальный порядок токенов в `Accept` создает **новую копию в кэше**. Это фактически убивает кэширование для публичных клиентов.

### 5.5. Решение Архитектора: Edge Normalization

Если вы все же выбрали Header Versioning, вы **обязаны** внедрить слой нормализации на Edge (до попадания в кэш).

**Инструменты:** Cloudflare Workers, AWS Lambda@Edge, NGINX Lua, Varnish VCL.

**Алгоритм (Edge Logic):**
1.  Перехватить входящий запрос.
2.  Прочитать "грязный" заголовок: `X-Ver: v1.0`.
3.  Применить бизнес-логику: `if (val.startsWith("v1")) return "1"`.
4.  Переписать заголовок запроса на канонический: `X-Ver: 1`.
5.  Только теперь передать запрос в движок кэширования.

**Цена решения (TCO):**
Вы платите за **Compute** на каждом запросе (даже при Cache Hit). Это увеличивает latency (на 5-50мс) и счет за облако.

### Резюме

*   **URI Versioning:** Кэширование работает **бесплатно** и максимально эффективно.
*   **Header Versioning:** Кэширование требует **внимательной настройки** (`Vary`) и **активной нормализации** на Edge, иначе эффективность стремится к нулю.

Как Staff Engineer, вы должны задать команде вопрос: *"Готовы ли мы писать и поддерживать Edge Workers для нормализации заголовков, или мы просто добавим `/v1` в URL?"*

## 6. Deprecation Strategies (Как убивать версии)

Жизненный цикл API не заканчивается релизом. Он заканчивается **выводом из эксплуатации (EOL — End of Life)**. Если вы не умеете убивать старые версии, ваша команда превратится в археологов, поддерживающих 15 версий легаси-кода, вместо разработки новых фич.

Стратегия EOL состоит из трех фаз: **Коммуникация (RFC Standards)**, **Операционное давление (Brownouts)** и **Терминация (Tombstoning)**.

---

### 6.1. Фаза 1: Стандартизированная Коммуникация (RFC 8594)

Рассылать email-рассылки "Мы отключаем v1" бесполезно. Разработчики их не читают. Инженерный подход — сообщать о смерти API **в самом ответе API**.

В 2019 году IETF принял стандарт **RFC 8594**, который вводит два ключевых заголовка. Вы *обязаны* их использовать.

#### Заголовок `Deprecation`
Сигнализирует, что эндпоинт устарел, но **все еще работает**.
*   **Значение:** Дата (когда устарел) или `true`.
*   **Семантика:** "Пожалуйста, начни миграцию. Прямо сейчас ничего не сломается, но поддержки больше нет".

#### Заголовок `Sunset`
Сигнализирует **точную дату и время смерти**.
*   **Значение:** HTTP-Date (как в заголовке `Date`).
*   **Семантика:** "После этой даты этот эндпоинт начнет возвращать 410 Gone или 404 Not Found".

#### Заголовок `Link` (для автоматизации)
Указывает, куда мигрировать.

**Пример ответа сервера (за полгода до EOL):**
```http
HTTP/1.1 200 OK
Deprecation: @1704067200         <-- Устарело 01.01.2024 (Unix Timestamp или Date)
Sunset: Wed, 31 Dec 2025 23:59:59 GMT  <-- Перестанет работать в конце 2025
Link: <https://api.example.com/v2/users>; rel="successor-version"
Link: <https://api.example.com/migration-guide>; rel="deprecation"
```

**Зачем это нужно:**
Современные HTTP-клиенты и API Gateways могут автоматически парсить эти заголовки и писать `WARN` логи в системе клиента.
*   *Сценарий:* DevOps клиента видит в Datadog рост логов "Usage of deprecated API", хотя функционал работает. Это триггерит создание задачи на техдолг.

---

### 6.2. Фаза 2: Операционное давление (The Scream Test / Brownouts)

Заголовки игнорируют. Письма удаляют. Единственный способ заставить клиента мигрировать — **сломать ему прод, но ненадолго**.

Этот метод называется **Brownout** (по аналогии с падением напряжения в сети).

#### Механика Brownout
Вместо бинарного отключения ("Вчера работало, сегодня нет"), вы начинаете искусственно деградировать качество обслуживания для старой версии.

**Расписание эскалации (Пример):**
*   **T-60 дней:** Добавляем **Artificial Latency** (искусственную задержку) 100мс к каждому запросу v1.
    *   *Эффект:* Клиенты с жесткими таймаутами начинают замечать проблемы. SLA формально не нарушен (обычно).
*   **T-30 дней:** Увеличиваем задержку до 1-2 секунд.
    *   *Эффект:* UI у клиентов начинает тормозить. Пользователи жалуются. Разработчики клиента начинают искать причину.
*   **T-14 дней:** Начинаем возвращать ошибку `429 Too Many Requests` или `503 Service Unavailable` для **1%** трафика в течение 5 минут в час пик.
*   **T-7 дней:** Blackout Windows. API полностью недоступен (возвращает ошибку) на 1 час в день.
*   **T-0:** EOL.

**Важный нюанс (HTTP Status):**
Во время Brownout лучше возвращать `429` или `503`, а не `404` или `410`.
*   `429/503` говорят клиенту: "Ошибка временная, попробуй позже (Retry)". Это позволяет их системам восстановиться после окончания окна отключения.
*   `404/410` говорят: "Ресурс удален навсегда". Умный клиент может перестать делать запросы совсем, что нам пока не нужно.

---

### 6.3. Фаза 3: Терминация (Tombstoning)

Час X настал. Вы выключаете роутинг на бэкенд v1.

**Какую ошибку возвращать?**
*   ❌ `404 Not Found`: Плохо. Клиент думает: "Может я ошибся в URL? Может сервис переехал?". Это двусмысленность.
*   ✅ `410 Gone`: Идеально. Семантика: "Ресурс был здесь, но удален навсегда, и переадресации не будет". Клиент обязан удалить этот код.

**Архитектурный паттерн "Могильный камень" (Tombstone):**
Даже после удаления кода v1, на API Gateway должна остаться конфигурация, которая для пути `/v1/*` отдает `410 Gone` с телом ответа:
```json
{
  "error": "gone",
  "message": "API v1 was shut down on 2025-12-31. Please upgrade to v2.",
  "documentation_url": "https://developer.example.com/migration"
}
```
Держите этот "могильный камень" минимум 6-12 месяцев после отключения, чтобы ловить "зомби-клиентов".

---

### 6.4. Мониторинг и Observability (Знай своего врага)

Вы не можете отключить версию, если не знаете, **кто** ей пользуется.
Перед началом процесса EOL настройте дашборд:

1.  **Cardinality by User-Agent:** Кто это? Старый скрипт на Python 2.7 или мобильное приложение v1.0, которое не обновляли 5 лет?
2.  **Cardinality by Auth Token / API Key:** Конкретные имена клиентов.
    *   *Action:* Если вы видите, что 80% трафика v1 генерирует один крупный B2B-партнер, Brownout делать нельзя. Нужен звонок аккаунт-менеджера.

### 6.5. Юридический аспект (Staff Engineer Responsibility)

Прежде чем внедрять Brownout, вы обязаны прочитать **SLA (Service Level Agreement)** и контракт.
*   Если в контракте написано "доступность 99.9%" без оговорок о версиях, ваши "веерные отключения" v1 могут привести к судебному иску.
*   **Совет:** В новых контрактах всегда прописывайте "Support Window" — обязанность клиента мигрировать на новую версию в течение X месяцев после объявления Deprecation.

### Резюме раздела

1.  **RFC 8594** (`Sunset`, `Deprecation`) — это база вежливой коммуникации.
2.  **Brownout (Chaos Engineering)** — это единственный способ достучаться до тех, кто не читает заголовки.
3.  **410 Gone** — единственный правильный статус смерти.
4.  Никогда не выключайте API в пятницу.

## 7. Рекомендация архитектора

1.  Для **Public API** (B2B, Mobile App): Используйте **URI Path** (`/v1/...`).
    *   Простота интеграции и кэширования важнее семантической чистоты.
    *   Мобильные приложения обновляются медленно, вам придется поддерживать `v1` годами. URI позволяет легко маршрутизировать трафик на старый кластер (`backend-v1-service`).
2.  Для **Internal Microservices**: Используйте **gRPC (Protobuf)**.
    *   Там версионирование решается на уровне пакетов (`package com.example.v1`) и обратной совместимости полей. HTTP-холивары там не нужны.
3.  Если вы **Stripe** (Платформа): Используйте **Date-based Versioning** в заголовке (`Stripe-Version: 2023-10-16`).
    *   Это требует сложнейшей архитектуры "Middleware chain", где запрос проходит через цепочку трансформеров, конвертирующих ответ из текущей версии в версию, запрошенную клиентом. Это высший пилотаж (и огромные затраты).

### Итог

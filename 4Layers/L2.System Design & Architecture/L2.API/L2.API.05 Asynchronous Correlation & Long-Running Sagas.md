**TL;DR**: Для асинхронных процессов "найти и продолжить" — это задача **State Machine (Orchestrator)**.
*   Не используйте `Trace-ID` (инфраструктурный трейсинг) как `Correlation-ID` (бизнес-сцепку).
*   Для эффективного поиска используйте **Reverse Mapping Tables** (когда внешний провайдер не возвращает ваш ID).
*   Для надежного "продолжения" используйте паттерн **Claim Check** или современные движки **Durable Execution** (Temporal/Cadence).

## 1. Типология ID: Trace vs Correlation vs Business

В распределенной системе идентификатор — это контекст. Без правильного ID сообщение — это просто набор байтов без прошлого и будущего.

Мы разделим идентификаторы на три уровня: **Инфраструктурный**, **Транспортный** и **Доменный**.

### 1.1. Trace ID (Инфраструктурный слой)
**Цель:** Observability (Наблюдаемость). Отладка производительности и построение графа вызовов.

*   **Определение:** Уникальный идентификатор, который генерируется на **самом входе** в систему (обычно на Ingress Controller или API Gateway) и передается через *все* микросервисы, базы данных и очереди сообщений до самого конца обработки.
*   **Стандарт:** W3C Trace Context (`traceparent` header). Это стандарт индустрии, который понимают OpenTelemetry, Datadog, Dynatrace.
*   **Жизненный цикл:** Эфемерный. Живет ровно столько, сколько обрабатывается запрос (миллисекунды или секунды).
*   **Хранение:** Обычно **Sampled** (Сэмплируется). В Jaeger/Elasticsearch сохраняется только 1-5% трейсов, чтобы не разориться на дисках.
*   **Антипаттерн Архитектора:** Никогда не завязывайте бизнес-логику на `Trace ID`.
    *   *Почему:* Trace ID может не сохраниться (из-за сэмплинга). Trace ID может измениться, если цепочка прервалась. Вы не сможете найти платеж по Trace ID через месяц, так как логи уже ротировались.

### 1.2. Correlation ID (Транспортный слой / Messaging)
**Цель:** Техническая связность асинхронных сообщений (Request-Reply pattern).

*   **Определение:** Идентификатор, позволяющий связать **конкретное сообщение-запрос** с **конкретным сообщением-ответом** в асинхронной среде.
*   **Контекст:** Используется внутри брокеров сообщений (RabbitMQ, Kafka, JMS, ActiveMQ).
*   **Механика:**
    1.  Сервис А (Producer) посылает сообщение в очередь `Requests`. Генерирует `cid = UUID()`. Ставит заголовок `reply_to = "queue_A_responses"`.
    2.  Сервис А сохраняет `cid` в локальной памяти (или Redis) и ждет.
    3.  Сервис Б (Consumer) обрабатывает сообщение.
    4.  Сервис Б шлет ответ в `reply_to` и **копирует** входящий `cid` в заголовок ответа.
    5.  Сервис А получает ответ, видит `cid` и понимает: "Ага, это ответ на тот самый запрос".
*   **Жизненный цикл:** Техническая транзакция. Обычно короче, чем бизнес-процесс, но длиннее, чем один HTTP-запрос.
*   **Пример:** `JMSCorrelationID` в Java JMS или свойство `correlation_id` в протоколе AMQP (RabbitMQ).

### 1.3. Business Transaction ID (Доменный слой)
**Цель:** Целостность данных (Data Integrity), Идемпотентность и Аудит.

*   **Определение:** Идентификатор сущности или процесса, имеющий смысл для бизнеса. Он является **Canonical Source of Truth**.
*   **Свойства:**
    *   **Persistent:** Хранится в базе данных вечно (ACID).
    *   **Indexed:** По нему построен индекс в БД для мгновенного поиска.
    *   **Human-Readable (опционально):** Может быть не UUID, а чем-то вроде `ORD-2025-10-XK`.
*   **Жизненный цикл:** От создания заявки до закрытия компании (годы).
*   **Пример:** `order_id`, `payment_reference`, `application_number`.
*   **Важно:** Именно этот ID используется для идемпотентности. Если пользователь нажимает "Повторить", Trace ID будет новым, Correlation ID будет новым, но **Business ID обязан остаться тем же**.

---

### Сводная таблица различий

| Характеристика | **Trace ID** | **Correlation ID** | **Business ID** |
| :--- | :--- | :--- | :--- |
| **Главный вопрос** | "Где тормозило?" | "На какой запрос этот ответ?" | "Где мои деньги?" |
| **Кто генерирует** | Load Balancer / Ingress | Producer сообщения | Клиент (для идемпотентности) или Домен |
| **Где живет** | Logs / Tracing System (Jaeger) | Message Headers / Ephemeral State | Database (Primary Key / Unique Index) |
| **Срок жизни** | Секунды (до ротации логов) | Минуты (пока идет RPC) | Вечность |
| **Гарантии** | Best effort (может потеряться) | Tech consistency | ACID / Strong consistency |
| **Пример** | `0af7651916cd43dd...` | `msg-550e8400...` | `txn_123456789` |

---

### Практический пример: "Покупка кофе"

Чтобы закрепить материал, проследим путь одного заказа через призму этих ID.

1.  **Start:** Пользователь в мобильном приложении нажимает "Оплатить". Приложение генерирует идемпотентный ключ **Business ID**: `BID-777`.
2.  **Ingress:** Запрос прилетает на Nginx. Nginx генерирует **Trace ID**: `TID-abc`.
    *   *Лог Nginx:* `[TID-abc] POST /orders (BID-777)`
3.  **Order Service:** Получает HTTP запрос.
    *   Пишет в БД: `INSERT INTO orders (id, ...) VALUES ('BID-777', ...)`.
    *   Решает списать деньги асинхронно. Генерирует сообщение для Billing Service.
    *   Создает технический **Correlation ID**: `CID-101` для отслеживания ответа от биллинга.
    *   Публикует в Kafka: `Payload: { order_id: BID-777 }, Headers: { trace_id: TID-abc, correlation_id: CID-101 }`.
4.  **Billing Service:** Читает Kafka.
    *   Видит `trace_id: TID-abc` -> пишет его в свои логи (связность логов сохранена).
    *   Видит `order_id: BID-777` -> проверяет в своей БД, не списывали ли уже по этому заказу (дедупликация по бизнес-ID).
    *   Проводит транзакцию.
    *   Шлет ответ в Kafka: `Payload: { status: PAID }, Headers: { correlation_id: CID-101 }`.
5.  **Order Service:** Читает ответ.
    *   Видит `correlation_id: CID-101`. Находит в памяти, какой HTTP-запрос ждал этого ответа (или обновляет статус в БД).

**Где возникает ошибка инженера?**
Инженер пытается использовать `TID-abc` как номер заказа.
Через неделю клиент звонит в поддержку: "Где мой заказ?".
Поддержка ищет `TID-abc`. А логи уже удалены (Retention policy 3 дня). Или этот конкретный трейс не попал в сэмплинг. **Данные потеряны, контекст не восстановить.**

**Вывод:** Используйте Business ID для логики, Correlation ID для склейки асинхронности, Trace ID для отладки. Не смешивайте их.

## 2. Сценарий: Валютный контроль (Human-in-the-Loop)

**Human-in-the-Loop (HITL)** в архитектуре — это паттерн, при котором автоматизированный процесс приостанавливает свое выполнение (`SUSPENDED`), делегируя принятие решения человеку или внешней неавтоматизированной системе, и ожидает асинхронного сигнала для возобновления (`RESUMED`).

В отличие от программных сбоев, задержки здесь измеряются не миллисекундами, а **днями**. Это делает невозможным использование синхронных ожиданий (блокировка потоков) и требует персистентного хранения состояния.

### 2.1. Анатомия процесса: "Разрыв контекста"

Рассмотрим канонический пример Fintech-системы: международный перевод (SWIFT) или прохождение KYC (Know Your Customer).

**Фаза 1: Инициация (The Handoff)**
1.  **Internal State:** Пользователь инициирует перевод. В нашей системе создается транзакция с неизменным **Business ID**: `TX-100`.
2.  **Export:** Система формирует пакет документов (XML/JSON) и отправляет его во внешний контур (АБС Банка, AML-платформа).
3.  **Acknowledgement (ACK):** Внешняя система принимает документы и возвращает *свой* локальный идентификатор — **External Ref ID**: `BANK-REF-999`.
    *   *Критический момент:* Именно здесь происходит "рукопожатие". Если мы не сохраним связь `TX-100 <-> BANK-REF-999` атомарно, мы потеряем управление процессом.

**Фаза 2: "Черная дыра" (The Gap)**
Процесс переходит в состояние ожидания.
*   **Длительность:** От 1 часа (AML-бот) до 5 рабочих дней (валютный контролер банка).
*   **Неопределенность:** Мы не знаем, что происходит внутри. Внешняя система — "черный ящик".
*   **Человеческий фактор:** Операционист может вручную изменить детали платежа, отклонить его с комментарием или запросить дополнительные документы.

**Фаза 3: Воссоединение (The Re-entry)**
Внешняя система (или операционист, нажавший кнопку в админке банка) генерирует обратный сигнал (Callback/Webhook).
*   **Payload:** `{ "ref": "BANK-REF-999", "status": "APPROVED", "operator_note": "Ok" }`.
*   **Проблема:** Входящий сигнал часто **не содержит** наш `TX-100`. Легаси-системы банков могут обрезать поля, терять метаданные или просто не поддерживать передачу клиентских ID (`pass-through fields`).

### 2.2. Проблема потери идентичности (Identity Loss)

Это главная архитектурная боль HITL. Мы отправляем богатый контекст (ID пользователя, ID заказа, Trace ID), а получаем обратно "голый" статус по чужому номеру.

**Почему `Pass-through` ID не работают надежно:**
1.  **Legacy Constraints:** Поле `Payment Details` в SWIFT ограничено по длине. Операционист может стереть ваш ID, чтобы вписать "Оплата по счету №5".
2.  **Protocol Mismatch:** Вы шлете JSON, банк работает с XML/ISO-20022, оператор смотрит в GUI на Windows Forms. При конвертациях "лишние" поля отбрасываются.
3.  **Human Error:** Если процесс требует ручного ввода (например, оператор набирает ответное письмо), он перепечатает `BANK-REF-999` (он короткий), но никогда не перепечатает UUID `550e8400-e29b...`.

### 2.3. Решение: Паттерн "Correlation Mapping"

Вместо надежды на то, что внешний мир сохранит наш ID, мы строим **однонаправленный шлюз состояния**.

**Структура таблицы маппинга (`correlation_log`):**

| Поле | Тип | Описание | Пример |
| :--- | :--- | :--- | :--- |
| **`external_ref_id`** | `VARCHAR` (PK) | ID, присвоенный внешней системой. Ключ поиска. | `BANK-REF-999` |
| **`provider_code`** | `VARCHAR` (PK) | Код системы (для уникальности `external_ref`). | `CITIBANK_UK` |
| **`internal_biz_id`** | `UUID` (Index) | Ссылка на наш Агрегат (Транзакцию). | `TX-100` (UUID) |
| **`workflow_state`** | `JSONB` | Снапшот контекста, нужный для возобновления. | `{"step": "AML_CHECK", "attempt": 1}` |
| **`valid_until`** | `TIMESTAMP` | TTL для очистки (SLA процесса). | `Now() + 7 days` |

**Алгоритм работы:**

1.  **При отправке (Outbound):**
    *   Получаем `BANK-REF-999`.
    *   Атомарно пишем в `correlation_log`.
2.  **При получении (Inbound Webhook):**
    *   Входящий JSON: `{"id": "BANK-REF-999", ...}`.
    *   **Point Query:** `SELECT internal_biz_id FROM correlation_log WHERE external_ref_id = 'BANK-REF-999' AND provider_code = 'CITIBANK_UK'`.
    *   Это запрос $O(1)$ или $O(\log N)$. Он не нагружает основную таблицу транзакций.
3.  **Восстановление:**
    *   Используем найденный `TX-100` для загрузки Агрегата Платежа.
    *   Применяем событие `Approved`.

### 2.4. Обработка сложных сценариев (Edge Cases)

Staff Engineer обязан предусмотреть, что HITL процесс пойдет не по плану.

1.  **Partial Match (Частичное совпадение):**
    *   Оператор ошибся и ввел `BANK-REF-99` (опечатка). Автоматический матчинг не сработает.
    *   *Решение:* Требуется UI для администраторов ("Ручной разбор полетов"), где можно найти "потерянный" вебхук и вручную связать его с транзакцией `TX-100`.
2.  **Late Arrival (Гонка состояний):**
    *   Пользователь отменил транзакцию `TX-100` (статус `CANCELLED`).
    *   Через час приходит вебхук `APPROVED` по `BANK-REF-999`.
    *   *Решение:* Стейт-машина должна быть идемпотентной и защищенной. Получение `APPROVED` для `CANCELLED` транзакции должно либо игнорироваться, либо создавать инцидент для саппорта ("Деньги ушли, а заказ отменен").
3.  **SLA Breach (Нарушение сроков):**
    *   Человек просто забыл. Вебхука нет.
    *   *Решение:* **Reconciliation Loop (Сверка)**. Крон-процесс сканирует таблицу `correlation_log` на предмет просроченных записей (`valid_until < NOW`) и делает активный запрос в API банка `GET /status/BANK-REF-999`, чтобы "пнуть" процесс.

### Резюме раздела
В сценариях Human-in-the-Loop ваша архитектура должна исходить из **презумпции потери контекста**. Внешняя система — враждебная среда для ваших данных. Единственный способ надежно связать асинхронный ответ человека с исходным процессом — это ведение собственного реестра соответствий (`External ID` -> `Internal ID`), оптимизированного для поиска по внешнему ключу.

## 3. Эффективный поиск (The Lookup Strategy)

Задача кажется тривиальной: по входящему `external_ref` найти наш `internal_id`.
Сложность возникает из-за **Кардинальности (Cardinality)** и **Замусоривания (Bloat)**.

Если ваша система живет 5 лет, в таблице `orders` лежат миллиарды строк. Из них "активных" (ждущих вебхука) — всего 10 тысяч. Искать по всей исторической таблице ради 0.001% активных операций — это архитектурное преступление.

### 3.1. Антипаттерн: "JSON Search" (The Metadata Trap)

Разработчики часто любят NoSQL-подход в SQL базах:
```sql
-- Таблица orders весит 5 TB
ALTER TABLE orders ADD COLUMN metadata JSONB;
-- Пишем туда: {"bank_ref": "BK-999", "ip": "..."}
```

**Наивный запрос:**
```sql
SELECT id FROM orders WHERE metadata->>'bank_ref' = 'BK-999';
```

**Почему это убьет прод:**
1.  **Full Table Scan:** Без специального индекса Postgres будет читать все 5 TB данных с диска, чтобы распарсить JSON в каждой строке.
2.  **TOAST Overhead:** В Postgres большие JSONB выносятся в TOAST-таблицы. Чтение строки становится дорогим (Random I/O).
3.  **Index Bloat:** Даже если вы создадите `GIN` индекс по JSONB, он будет индексировать *все* ключи внутри JSON. Индекс станет огромным и медленным на запись (Write Amplification).

---

### 3.2. Стратегия A: "Эхо-идентификатор" (Pass-through / Round-Trip)

Это **Святой Грааль** интеграции. Мы навязываем внешней системе *наш* контекст.

**Механика:**
Большинство платежных шлюзов (Stripe, PayPal, Adyen) имеют поле `metadata` или `merchant_reference`.
1.  **Request:** `{ "amount": 100, "merchant_reference": "TX-UUID-550e..." }`
2.  **Webhook:** `{ "event": "charge.succeeded", "merchant_reference": "TX-UUID-550e..." }`

**Преимущества:**
*   **Zero Lookup Cost:** Нам не нужно искать. Мы просто читаем `TX-UUID` из пейлоада и делаем `SELECT ... WHERE id = ...` (Primary Key Lookup). Это максимально быстро.
*   **Stateless:** Нам не нужно хранить промежуточную таблицу маппинга.

**Ограничения (The Reality Check):**
*   **Truncation:** Легаси-системы (особенно банковские ISO-8583) часто обрезают это поле до 12-20 символов. Ваш UUID туда не влезет.
*   **Sanitization:** Банки могут запретить спецсимволы (дефисы в UUID).
*   **Human Factor:** Если в цепочке есть человек, он не будет перепечатывать UUID вручную.

---

### 3.3. Стратегия B: "Sidecar Index" (Таблица обратного индекса)

Это **промышленный стандарт** для высоконагруженных систем, когда Pass-through невозможен. Мы отделяем "оперативные" данные от "архивных".

Вместо того чтобы искать по таблице `orders` (которая растет бесконечно), мы создаем маленькую, горячую таблицу **Active Routings**.

**Схема `integration_routings`:**

| Column | Type | Index Strategy | Description |
| :--- | :--- | :--- | :--- |
| **`provider_ref`** | `VARCHAR` | **Composite PK (1)** | Внешний ID (`BK-999`). Первая часть ключа для быстрого поиска. |
| **`provider_id`** | `SMALLINT` | **Composite PK (2)** | ID провайдера (Сбер, Альфа), т.к. `BK-999` может повториться в разных банках. |
| **`internal_id`** | `UUID` | None | Наш целевой ID транзакции. |
| **`shard_key`** | `BIGINT` | Partition Key | Если мы используем шардинг (обычно `user_id`). |
| **`expires_at`** | `TIMESTAMP` | TTL Index | Время жизни записи. |

**Почему это эффективно:**
1.  **Index-Only Scan:** Таблица узкая (всего 4 колонки). Весь индекс влезает в RAM. Поиск происходит без обращения к диску (Heap Fetch).
2.  **Hot Set:** Эта таблица содержит *только* те операции, которые сейчас в полете (Pending). Как только операция завершена (или протухла), запись удаляется.
    *   Если у вас 1 млрд платежей, но только 5000 в обработке, размер этой таблицы — 5000 строк. Поиск мгновенный.

**Жизненный цикл записи:**
1.  `INSERT` при отправке запроса в банк.
2.  `SELECT` (Point Query) при получении вебхука.
3.  `DELETE` сразу после успешной обработки вебхука.

---

### 3.4. Стратегия C: "Functional Indexing" (Компромисс)

Если вы не хотите создавать отдельную таблицу (административный оверхед) и ваша таблица `orders` не шардирована.

В PostgreSQL можно создать **частичный функциональный индекс**:

```sql
CREATE UNIQUE INDEX idx_orders_bank_ref 
ON orders ( (metadata->>'bank_ref') ) 
WHERE status = 'WAITING_FOR_BANK'; -- <--- Ключевой момент
```

**Детали:**
*   **Partial (`WHERE`):** Индекс содержит только активные заказы. Он крошечный, даже если таблица огромная.
*   **Functional (`->>`):** Мы индексируем результат извлечения из JSON, а не весь JSON.
*   **Минус:** При каждом обновлении строки `orders` (даже если меняется не статус) базе придется проверять предикат индекса. Это создает небольшую нагрузку на запись (CPU overhead).

---

### 3.5. Стратегия D: "Search Engine" (Elasticsearch / OpenSearch)

Иногда критерии поиска сложнее, чем точное совпадение ID.
*   *Сценарий:* Оператор банка присылает реестр в Excel, где имена перепутаны, а ID транзакции написан в поле "Комментарий" вместе с текстом.
*   *Задача:* "Найти транзакцию, похожую на..." (Fuzzy Search).

Здесь реляционная БД бессильна.
1.  Мы стримим все события изменения платежей (CDC) в Elasticsearch.
2.  Поиск происходит в поисковом движке.
3.  **Главный риск:** Eventual Consistency. Вебхук может прийти *до* того, как Elasticsearch проиндексировал запись о создании платежа (задержка 1-2 сек).
    *   *Решение:* Если не нашли в Elastic — делаем фолбэк (Fallback) на прямой поиск в БД или ставим задачу в очередь на повтор через 5 секунд (Retry later).

---

### Резюме архитектора (Staff Engineer Verdict)

1.  **Default Choice:** Если внешний API возвращает метаданные — используйте **Pass-through** (Стратегия A). Это бесплатно и надежно.
2.  **Reliability Choice:** Если API "глупый", стройте **Sidecar Index Table** (Стратегия B). Обязательно настраивайте очистку (TTL), иначе эта таблица станет новой точкой отказа.
3.  **Optimization:** Никогда не ищите по "сырому" JSON в основной таблице. Если очень хочется — используйте **Partial Indexes**, которые покрывают только активные состояния.

## 4. Как "продолжить" (Resuming Execution)

Когда сервис получает сигнал (вебхук), он страдает от "амнезии". У него нет памяти (RAM) о том, что было до этого. Ему нужно **регидрировать (rehydrate)** контекст из диска.

### 4.1. Подход A: Event-Driven State Machine (Классика)

В этом подходе состояние процесса явно моделируется через колонку `status` в базе данных. Логика размазана между обработчиком вебхука, доменной моделью и воркерами очереди.

**Архитектурный паттерн: Internal Event Decoupling**

Никогда не выполняйте бизнес-логику прямо в HTTP-контроллере вебхука. Это нарушает границы транзакций и делает систему хрупкой (например, если БД занята, вы потеряете вебхук).

**Алгоритм:**

1.  **Ingestion (Webhook Handler):**
    *   Принимает HTTP запрос.
    *   Находит `internal_id` (через Lookup таблицу).
    *   **Единственная задача:** Сохранить "сырой" факт получения сигнала в **Transactional Outbox** или очередь.
    *   `INSERT INTO events (aggregate_id, type, payload) VALUES ('TX-100', 'BankResponseReceived', '{...}')`.
    *   Отвечает банку `200 OK`.

2.  **Processing (Async Worker):**
    *   Читает событие `BankResponseReceived`.
    *   **Rehydration:** Загружает Агрегат `Payment` из БД. `SELECT * FROM payments WHERE id = 'TX-100'`.
    *   **Validation:** Проверяет инварианты.
        *   *Пример:* "Можно ли применить `APPROVED`, если текущий статус `CANCELLED`?"
    *   **Mutation:** Изменяет статус: `WAITING_KYC` $\to$ `READY_TO_PAY`.
    *   **Persist:** Сохраняет изменения с **Optimistic Locking**.

**Проблема Optimistic Locking (Критично для эксперта):**
Что если банк прислал два вебхука одновременно (дубликаты)? Или оператор нажал "Отмена" в ту же секунду?
```sql
UPDATE payments 
SET status = 'READY_TO_PAY', version = version + 1
WHERE id = 'TX-100' AND version = 5; -- 5 было прочитано при загрузке
```
Если `Rows Affected = 0`, значит, кто-то изменил состояние параллельно. Воркер должен перечитать данные и повторить попытку (Retry) или сдаться.

**Оценка:**
*   *Плюсы:* Понятно, работает на любой SQL БД, полный контроль.
*   *Минусы:* "Accidental Complexity". Вы пишете кучу бойлерплейта: таблицы событий, ретраи, дедупликацию, обработку версий. Логика процесса "размазана".

---

### 4.2. Подход B: Durable Execution (The Modern Standard)

На уровне Staff Architect в 2025 году вы должны рассматривать платформы **Durable Execution** (Temporal, Cadence, Uber Infinitic) как дефолтный способ реализации длинных процессов.

**Философия:** "Код как состояние".
Вы пишете процедурный код, который выглядит как обычная синхронная функция. Платформа гарантирует, что переменные в этом коде "выживут" даже при перезагрузке серверов.

**Пример на Temporal (Go/Java SDK):**

```go
// Это Workflow. Он может выполняться месяц.
func MoneyTransferSaga(ctx Context, transfer TransferDetails) error {
    // Шаг 1: Списание (вызов Activity)
    // Temporal сохраняет факт выполнения в Event History
    activity.DebitAccount(ctx, transfer.From)

    // Шаг 2: Отправка во внешний мир
    refID := activity.SendToSwift(ctx, transfer)

    // Шаг 3: ТОЧКА ОСТАНОВКИ (Suspension Point)
    // Процесс полностью выгружается из памяти воркера.
    // В базе Temporal остается запись: "Жду сигнала 'KYC_SIG' для workflow ID ..."
    var bankResponse BankResponse
    
    // Selector - это как 'select' в Go, но на стероидах и персистентный
    selector.AddReceive(channel_KYC_SIG, func(c Channel, ok bool) {
        c.Receive(ctx, &bankResponse)
    })
    
    // Ждем. (CPU usage = 0)
    selector.Select(ctx)

    // --- ПРОШЛО 3 ДНЯ ---
    // Когда пришел сигнал, Temporal:
    // 1. Находит историю этого workflow.
    // 2. "Проигрывает" (Replay) код с начала, пропуская уже выполненные Activity (возвращая их результаты из истории).
    // 3. Восстанавливает стек и переменные (refID).
    // 4. Продолжает выполнение с этой строки.

    if bankResponse.Status == "APPROVED" {
        activity.CreditAccount(ctx, transfer.To)
    } else {
        activity.RollbackDebit(ctx, transfer.From)
    }
    return nil
}
```

**Механизм Replay (Магия под капотом):**
Главный вопрос на собеседовании: "Как Temporal восстанавливает переменную `refID` через 3 дня?".
*   Он **не** сериализует RAM процесса (это ненадежно).
*   Он использует **Event Sourcing**. В базе лежит лог:
    1.  `WorkflowStarted`
    2.  `ActivityTaskScheduled (SendToSwift)`
    3.  `ActivityTaskCompleted (Result: "BK-999")`
*   При пробуждении воркер берет код Workflow и запускает его заново. Когда код доходит до `SendToSwift`, Temporal не делает реальный вызов, а смотрит в историю: "Ага, это уже было, результат 'BK-999'". И просто присваивает переменной значение.

**Сигнализация (Signal Method):**
Обработчик вебхука просто вызывает API Temporal:
`client.SignalWorkflow(workflowID, "KYC_SIG", payload)`.
Ему не нужно знать текущий статус процесса, поднимать базу или думать о локах. Temporal сам поставит сигнал в очередь и применит к workflow строго последовательно.

**Оценка:**
*   *Плюсы:* Линейная бизнес-логика. Локальные переменные "бессмертны". Автоматические ретраи и тайм-ауты.
*   *Минусы:* Требует инфраструктуры (Кластер Temporal/Cassandra/Elastic). Требует дисциплины кодинга (детерминизм в Workflow коде).

---

### 4.3. Versioning (Проблема "Летящего самолета")

Это самый сложный аспект Resuming Execution.
**Сценарий:**
1.  Вы запустили Сагу `V1`. Она зависла на ожидании Вебхука (Шаг 3).
2.  Вы выкатили новый код `V2`, где добавили логику *между* Шагом 2 и Шагом 3.
3.  Пришел Вебхук.

*   **В Event Machine (Подход A):** Обычно безопасно, так как мы грузим агрегат и просто дергаем метод. Если логика внутри метода изменилась, применится новая.
*   **В Durable Execution (Подход B):** **ОПАСНО.** Replay сломается. Воркер запустит историю V1 на коде V2. История скажет "тут был ActivityCall", а код скажет "тут теперь if/else". Воркер выдаст **Non-Deterministic Error** и процесс умрет.
    *   *Решение:* Использовать `workflow.GetVersion()`.
    *   `if version == 1 { ...old logic... } else { ...new logic... }`.
    *   Старые процессы доживают по старой ветке, новые идут по новой.

---

### Резюме Архитектора

1.  **State Machine:** Используйте для процессов с простой линейной логикой и малым числом шагов (3-5). Не забывайте про Optimistic Locking.
2.  **Durable Execution (Temporal):** Используйте для сложных бизнес-процессов (20+ шагов, циклы, ветвления, таймеры ожидания). Это снижает сложность кода на порядок, убирая необходимость вручную сохранять состояние между шагами.
3.  **Decoupling:** В любом случае, "прием сигнала" и "обработка сигнала" должны быть разделены очередью или outbox-таблицей. Вебхук должен отвечать `200 OK` за миллисекунды, а поиск и восстановление саги могут занимать секунды.

## 5. Проблема "Потерянного ответа" (The Lost Signal)

В асинхронном взаимодействии (особенно с участием людей) гарантировать доставку обратного вызова (Callback/Webhook) невозможно.
*   **Сетевой раздел:** Банк пытался отправить вебхук, но ваш балансировщик вернул 502.
*   **Баг Провайдера:** Их очередь событий переполнилась, и сообщение было отброшено (Silent Drop).
*   **Человеческий фактор:** Операционист закрыл задачу в UI, но система "забыла" триггернуть ивент.

Ваша система не может бесконечно находиться в состоянии `WAITING`. Это утечка ресурсов и бизнес-риск.

### 5.1. Паттерн: Active Reconciliation (Активная сверка)

Вместо пассивного ожидания мы внедряем механизм **Anti-Entropy** — процесс, который активно устраняет расхождения между нашей моделью мира и реальностью провайдера.

**Стратегия "Pull over Push" (Опрос вместо Ожидания):**
Если вебхук — это оптимизация латентности (узнать мгновенно), то поллинг (Polling) — это гарантия надежности.

#### Реализация Sweeper (Мусорщик/Сборщик)

Не делайте просто `CRON` скрипт, который делает `SELECT *`. Это убьет базу. Используйте паттерн **Outbox Sweeper**.

1.  **Индекс ожидания:**
    Таблица транзакций должна иметь индекс: `CREATE INDEX idx_reconcile ON payments (next_check_at) WHERE status IN ('PENDING', 'WAITING_BANK')`.
2.  **Adaptive Backoff (Адаптивный интервал):**
    Мы не опрашиваем банк каждую минуту. Мы увеличиваем интервал проверки.
    *   `T0` (Создание): `next_check_at = NOW() + 1 min`
    *   `Check 1` (Статус все еще Pending): `next_check_at = NOW() + 5 min`
    *   `Check 2`: `+ 1 hour`
    *   `Check 3`: `+ 6 hours`
    *   ...
    *   `Check N`: `Manual Intervention` (Сдаемся).
3.  **Алгоритм воркера:**
    ```sql
    -- Transactional Fetch
    UPDATE payments
    SET next_check_at = NOW() + interval '5 minutes' -- Сразу сдвигаем, чтобы другие воркеры не взяли
    WHERE id IN (
        SELECT id FROM payments
        WHERE status = 'WAITING_BANK' AND next_check_at <= NOW()
        LIMIT 100
        FOR UPDATE SKIP LOCKED -- Критично для конкурентности!
    )
    RETURNING id, external_ref;
    ```
4.  **Внешний вызов:**
    Для каждой записи делаем `GET /api/v1/payments/{external_ref}`.

### 5.2. Проблема Гонки: "Webhook vs Poller"

Это классический **Race Condition** в распределенных системах.
Что если мы сделали `GET` запрос, получили статус `SUCCESS`, начали обновлять базу, и **в ту же миллисекунду** пришел запоздалый вебхук `SUCCESS`?

Если не защититься, мы можем:
1.  Дважды начислить деньги пользователю (если логика не идемпотентна).
2.  Получить ошибку `Optimistic Lock Failure` и заспамить логи.
3.  Перевести стейт-машину в некорректное состояние.

**Решение: Idempotent State Transition**

Переход состояния должен быть идемпотентным относительно источника сигнала.

*   **Сценарий:** Текущий статус `WAITING`. Целевой `PAID`.
*   **Poller:** Видит `PAID` в банке. Шлет команду `CompletePayment(TX-100)`.
*   **Webhook:** Приносит `PAID`. Шлет команду `CompletePayment(TX-100)`.

**Реализация в Domain Model:**
```java
class PaymentAggregate {
    void complete() {
        if (this.status == PAID) {
            return; // Идемпотентный игнор. Мы уже там.
        }
        if (this.status != WAITING) {
            throw new InvalidTransitionException();
        }
        this.status = PAID;
        // Emit Event...
    }
}
```
Благодаря транзакциям БД, только один поток (или Poller, или Webhook) сможет выполнить переход. Второй получит "ничего не делаем".

### 5.3. Сценарий: "The Zombie Transaction" (404 Not Found)

Самый страшный сон архитектора: Poller делает `GET /status/BK-999`, а банк отвечает **404 Not Found**.

**Что это значит?**
1.  **Вариант А (Optimistic):** Банк отклонил транзакцию на входе и не сохранил её. Транзакция отменена.
2.  **Вариант Б (Pessimistic):** У банка сбой репликации, он временно "не видит" транзакцию, но она обработается позже.
3.  **Вариант В (Critical):** Мы думали, что отправили транзакцию (получили 200 OK при создании), но на самом деле банк её потерял. Или мы сохранили `BK-999`, но это был ID ошибки, а не транзакции.

**Стратегия Staff Engineer:**
Никогда не переводите транзакцию в `FAILED` автоматически при 404, если речь идет о деньгах.
*   Переведите в статус `MANUAL_CHECK` (Требует внимания).
*   Создайте алерт для саппорта.
*   Пусть человек зайдет в личный кабинет банка и проверит.
*   *Исключение:* Если API банка документировано возвращает 404 для "Отмененных" заявок (плохой дизайн API, но бывает).

### 5.4. Сценарий: "Ghost Webhook" (Сигнал без запроса)

Обратная ситуация: приходит вебхук об успехе транзакции, которой **нет** в нашей базе.
*   Причина: Баг в нашей системе (упали после отправки запроса, но до коммита в БД) или повторная отправка вебхуков банком за прошлый год.
*   Решение:
    1.  Проверить `correlation_log` (см. Раздел 3).
    2.  Если не найдено: ответить `200 OK` (чтобы банк отстал и не ретраил) и записать в лог `UNMAPPED_WEBHOOKS` для анализа. Не пытайтесь "создать" транзакцию задним числом — контекст потерян.

### Резюме раздела

1.  **Trust, but Verify:** Вебхуки — это для скорости (UI/UX). Поллинг (Reconciliation) — это для консистентности (Бухгалтерия). У вас должны быть **оба** механизма.
2.  **Smart Polling:** Используйте `next_check_at` с экспоненциальным откладыванием (Exponential Backoff), чтобы не создать DDoS-атаку на партнера.
3.  **Concurrency Control:** Обработайте ситуацию, когда Поллер и Вебхук приходят одновременно. Идемпотентность стейт-машины — ключ к успеху.
4.  **Observability:** Обязательно имейте метрику "Количество транзакций в статусе WAITING более 24 часов". Это главный индикатор здоровья интеграции.

## 6. Чек-лист уровня Expert

1.  **Race Condition (Callback vs Redirect):**
    В платежах часто бывает: юзер платит картой, его редиректит на `success_url` (браузер) И ОДНОВРЕМЕННО платежка шлет `webhook` (сервер-сервер).
    *   Кто придет первым? Неизвестно.
    *   Оба потока попытаются обновить статус. Используйте **Optimistic Locking** (`UPDATE payments SET status='PAID', version=2 WHERE id='A' AND version=1`). Кто не успел — получает ошибку (или игнорирует, если статус уже целевой).
2.  **Cardinality индексов:**
    Никогда не делайте индекс по `status`, если у вас 99% записей в статусе `COMPLETED` и 1% в `WAITING`. Индекс будет бесполезен (Postgres planner его проигнорирует). Используйте **Partial Indexes**: `CREATE INDEX idx_waiting ON payments(created_at) WHERE status = 'WAITING_KYC'`. Это ускоряет Polling в 100 раз.
3.  **Security Correlation:**
    Входящий вебхук должен быть аутентифицирован. Недостаточно найти транзакцию по ID. Нужно проверить подпись запроса (HMAC header), чтобы злоумышленник не смог послать фейковый `APPROVED` для транзакции `A100`, просто перебрав ID.

### Заключение
Для архитектора "Correlation" — это клей распределенной системы.
Для мгновенных ответов используйте **ID в заголовках**.
Для длительных (Human) процессов — используйте **Mapping Tables** для быстрого поиска и **Durable Execution (Temporal)** или **Sagas** для надежного восстановления контекста. Никогда не полагайтесь на то, что внешний мир сохранит ваш ID — стройте свои таблицы соответствия.

**TL;DR**: OpenAPI (Swagger) решил проблему документации для REST, сделав HTTP-контракты читаемыми и машиноисполняемыми. **AsyncAPI** делает то же самое для Event-Driven Architecture (Kafka, RabbitMQ, MQTT, WebSockets).
Как практик, вы должны внедрять AsyncAPI не для красоты, а для **Governance**: чтобы остановить хаос, когда никто не знает, кто пишет в топик `user.created`, какой там JSON-формат и кто этот топик читает.

---

Событийные системы страдают от проблемы "Неявных контрактов". Если в REST API у вас есть эндпоинт `/users` и глагол `POST`, то в Kafka у вас есть просто именованная труба, в которую кто-то кидает байты. AsyncAPI — это спецификация (формат YAML/JSON), которая превращает эту трубу в строгий контракт.

## 1. Анатомия спецификации (Structure)

AsyncAPI — это спецификация, описывающая интерфейс **конкретного приложения** (микросервиса), а не топологию всего брокера сообщений.

### 1.1. Application-Centric View (Взгляд изнутри приложения)
Самая частая ошибка новичков — попытка описать в одном файле весь Kafka-кластер. Это неправильно.
*   **OpenAPI** описывает HTTP-сервер: "Я принимаю GET запросы здесь".
*   **AsyncAPI** описывает асинхронный компонент: "Я подключаюсь к этому брокеру, слушаю этот топик и пишу в тот топик".

Спецификация отвечает на три вопроса:
1.  **Куда** подключиться? (`servers`)
2.  **Что** можно делать? (`channels` / `operations`)
3.  **Как** выглядят данные? (`components`)

### 1.2. Структура документа (v2 vs v3)

На данный момент индустрия находится в переходном периоде. Большинство инструментов (Backstage, генераторы кода) работают на версии **2.6.0**, но версия **3.0.0** уже вышла и меняет структуру ради устранения двусмысленности.

Мы разберем структуру на примере v2 (как стандарта де-факто), но с пометками о v3.

#### Корневые элементы
```yaml
asyncapi: '2.6.0'
id: 'urn:com:company:userservice' # Уникальный ID сервиса (важно для Data Catalog)
info: ...
servers: ...
channels: ...
components: ...
```

#### A. Info (Метаданные)
Стандартный блок. Важен для **Developer Portal**.
*   `description`: Поддерживает **Markdown**. Здесь вы пишете бизнес-назначение сервиса, SLA и ссылки на команду поддержки.

#### B. Servers (Точки подключения)
Описывает брокеры сообщений.
*   Важно: Можно указать несколько сред (`dev`, `staging`, `prod`) и протоколов (`kafka`, `mqtt`, `amqp`, `ws`).
*   **Security:** Здесь же привязываются схемы безопасности (SASL_SSL, OAuth2), определенные в `components`.

#### C. Channels (Каналы передачи данных)
Это "эндпоинты" вашей асинхронной системы. В Kafka это топики, в AMQP — очереди/эксчейнджи.
Канал описывает:
1.  **Адрес:** Имя топика.
2.  **Параметры:** Если топик динамический (см. ниже).
3.  **Действия:** `publish` (публикация) или `subscribe` (подписка).

#### D. Components (Переиспользуемые блоки)
Секция `dry` (Don't Repeat Yourself).
*   `schemas`: Структуры данных (Payload).
*   `messages`: Конверт сообщения (Заголовки + Payload).
*   `securitySchemes`: Настройки аутентификации.
*   `parameters`: Переиспользуемые параметры путей.

### 1.3. Расширенный пример (Real-world Scenario)

Рассмотрим сервис `PaymentService`, который слушает команды на оплату и публикует события результата. Пример демонстрирует использование **Parameters**, **Headers** и **Kafka Bindings**.

```yaml
asyncapi: '2.6.0'
info:
  title: Payment Processor
  version: '1.2.0'
  description: |
    Сервис обработки платежей. 
    Слушает команды, процессит через эквайринг, кидает события.

servers:
  production:
    url: kafka.prod.corp:9092
    protocol: kafka
    description: Основной кластер Kafka

channels:
  # 1. ДИНАМИЧЕСКИЙ ТОПИК (Smart Routing)
  # Приложение слушает топики вида 'payments.v1.region-us', 'payments.v1.region-eu'
  'payments.v1.region-{regionId}':
    description: Канал входящих команд на оплату
    parameters:
      regionId:
        description: Код региона (изоляция данных)
        schema:
          type: string
          enum: ['us', 'eu', 'asia']
    subscribe: # <--- Приложение СЛУШАЕТ (Input)
      message:
        $ref: '#/components/messages/ProcessPaymentCmd'

  # 2. СТАТИЧЕСКИЙ ТОПИК
  'payments.v1.completed':
    publish: # <--- Приложение ПУБЛИКУЕТ (Output)
      message:
        $ref: '#/components/messages/PaymentCompletedEvent'
      # Специфичные настройки Kafka для топика
      bindings:
        kafka:
          topicConfiguration:
            cleanup.policy: compact
            retention.ms: 604800000

components:
  messages:
    ProcessPaymentCmd:
      name: ProcessPayment
      title: Команда на списание средств
      # Описание ЗАГОЛОВКОВ (Metadata)
      headers:
        type: object
        properties:
          correlationId:
            type: string
            description: ID для трассировки (OpenTelemetry)
      payload:
        $ref: '#/components/schemas/PaymentRequestPayload'
      # Настройки ключа партицирования Kafka
      bindings:
        kafka:
          key:
            type: string
            description: Оплата партицируется по ID пользователя

    PaymentCompletedEvent:
      name: PaymentCompleted
      payload:
        $ref: 'http://schema-registry/schemas/payment_completed.json'

  schemas:
    PaymentRequestPayload:
      type: object
      required: [amount, currency]
      properties:
        amount:
          type: integer
          minimum: 1
        currency:
          type: string
          example: USD
```

### 1.4. Детальный разбор ключевых концепций

#### Protocol Bindings (Привязки протоколов)
AsyncAPI абстрактен. Он говорит "канал". Но в реальности у Kafka есть `groupId`, `partitionKey`, `log compaction`, а у MQTT есть `QoS` и `Retain flag`.
*   **Решение:** Поле `bindings`. Оно позволяет вставить специфичные для протокола настройки на уровне Сервера, Канала, Операции или Сообщения.
*   *В примере выше:* Мы указали `cleanup.policy: compact` для Kafka-топика. Генератор инфраструктуры (Terraform) может прочитать это и создать топик с нужными настройками.

#### Message vs Schema
Многие путают `components/messages` и `components/schemas`.
*   **Schema:** Это только "тело" (бизнес-данные). Например, JSON объект `{ "amount": 100 }`.
*   **Message:** Это **конверт**. Он включает в себя:
    1.  `payload` (ссылка на Schema).
    2.  `headers` (системные метаданные: trace-id, timestamp).
    3.  `bindings` (ключ сообщения для Kafka).
    4.  `correlationId`.

#### Parameters (Параметризованные каналы)
В REST URI часто бывают параметры: `/users/{id}`. В Messaging это тоже есть!
*   MQTT: `sensors/+/temperature`.
*   Kafka: Часто используется паттерн `domain.{env}.event`.
AsyncAPI позволяет описать это через секцию `parameters` в канале, валидируя, что `{regionId}` может быть только `us` или `eu`.

### 1.5. Эволюция: v2 vs v3 (Что меняется?)

На уровне Practitioner вы должны знать о главном изменении в v3.
В **v2** канал жестко связан с операцией (`subscribe` внутри `channels`). Это вызывало проблему переиспользования: если один топик используется для чтения и записи разными частями приложения, описание дублировалось.

В **v3**:
1.  **Channels:** Описывают только адрес (Топик).
2.  **Operations:** Отдельная секция. Описывает действие (`action: send`, `action: receive`) и ссылается на канал.
*   *Итог:* v3 чище и логичнее, но пока меньше поддерживается тулингом. Если вы начинаете сегодня — используйте v2.6, но держите в уме миграцию.

## 2. Главная боль: Publish vs Subscribe (Семантика)

В 9 из 10 случаев, когда джуниор пишет AsyncAPI, он путает `publish` и `subscribe`. Почему? Потому что он мыслит категориями брокера ("Я публикую в топик Kafka"), а спецификация требует мыслить категориями приложения.

### 2.1. Золотое правило: "Взгляд изнутри приложения"

AsyncAPI описывает интерфейс **конкретного приложения** (микросервиса), файл которого вы пишете. Назовем его **"Приложение А"**.

Запомните мантру: **Глаголы описывают действия Приложения А.**

*   **`publish` (Публикация):**
    *   **Значение:** Приложение А **отправляет** сообщения в этот канал.
    *   **Направление данных:** Приложение А $\to$ Брокер $\to$ Мир.
    *   **Аналог в коде:** `kafkaProducer.send(...)`, `mqttClient.publish(...)`.
    *   **Роль:** Producer / Egress.

*   **`subscribe` (Подписка):**
    *   **Значение:** Приложение А **ожидает/слушает** сообщения из этого канала.
    *   **Направление данных:** Мир $\to$ Брокер $\to$ Приложение А.
    *   **Аналог в коде:** `@KafkaListener`, `mqttClient.on('message', ...)`.
    *   **Роль:** Consumer / Ingress.

---

### 2.2. Парадокс генерации клиента (The Client Inversion Trap)

Путаница возникает, когда вы используете AsyncAPI файл не для документации самого сервиса, а для **генерации клиента** к нему (SDK).

Представьте, что вы описали `NotificationService`.
*   Сервис **слушает** топик `send_email`. В YAML вы пишете:
    ```yaml
    channels:
      send_email:
        subscribe: ... # Сервис ПОДПИСАН на команды
    ```

Теперь вы отдаете этот файл команде Биллинга, чтобы они сгенерировали себе Java-клиент для отправки писем.
Генератор кода читает файл: "Ага, в спецификации написано `subscribe`. Это значит, что *Сервис* подписывается. Следовательно, *Клиент* (Биллинг) должен **публиковать** (publish) в этот топик".

**Зеркальное отражение:**
*   Если в YAML написано `subscribe` $\to$ Сгенерированный метод клиента будет `publish()`.
*   Если в YAML написано `publish` $\to$ Сгенерированный метод клиента будет `onMessage()` (подписка).

**Совет Архитектора:** Если вы пишете спецификацию, всегда игнорируйте существование клиентов. Описывайте **только** поведение вашего сервиса. Пусть генераторы кода сами занимаются инверсией.

### 2.3. Пример для наглядности

Рассмотрим **Сервис Заказов (Order Service)**.
1.  Пользователь нажимает "Купить" $\to$ Сервис получает команду и **публикует** событие `OrderCreated`.
2.  Сервис **слушает** топик `PaymentStatus`, чтобы узнать, прошла ли оплата.

Как это выглядит в AsyncAPI v2:

```yaml
asyncapi: '2.6.0'
info:
  title: Order Service
  version: '1.0.0'

channels:
  # Топик для исходящих событий (Output)
  # Мы (Order Service) ПУБЛИКУЕМ сюда.
  'orders.lifecycle.created':
    publish: 
      message:
        $ref: '#/components/messages/OrderCreatedEvent'

  # Топик для входящих событий (Input)
  # Мы (Order Service) ПОДПИСАНЫ на него.
  'finance.payments.status':
    subscribe:
      message:
        $ref: '#/components/messages/PaymentProcessedEvent'
```

*Если бы вы перепутали и написали `subscribe` для `orders.lifecycle.created`, генератор кода создал бы сервис, который пытается слушать свои же события, вместо того чтобы отправлять их.*

### 2.4. Эволюция: AsyncAPI v3 (Решение проблемы)

Комитет AsyncAPI осознал, что семантика `publish/subscribe` вызывает слишком много когнитивной нагрузки. В версии 3.0.0 (релиз 2024 года) подход был радикально изменен.

**Концепция v3: Separation of Channel and Operation**
В v3 определение канала (адреса) отделено от действия, которое приложение выполняет над этим каналом. Глаголы `publish/subscribe` заменены на более однозначные `send/receive`.

**Маппинг v2 $\to$ v3:**

| Действие приложения | v2 Keyword | v3 Operation Action | Смысл |
| :--- | :--- | :--- | :--- |
| **Отправка** данных | `publish` | `action: send` | Приложение шлет сообщение брокеру |
| **Получение** данных | `subscribe` | `action: receive` | Приложение получает сообщение от брокера |

**Пример того же Order Service в v3:**

```yaml
asyncapi: '3.0.0'
info:
  title: Order Service
  version: '1.0.0'

channels:
  # Просто определение адресов, без действий
  orderCreatedChannel:
    address: 'orders.lifecycle.created'
  paymentStatusChannel:
    address: 'finance.payments.status'

operations:
  # Явное описание действий
  sendOrderCreation:
    action: send  # Мы отправляем
    channel:
      $ref: '#/channels/orderCreatedChannel'
    messages:
      - $ref: '#/components/messages/OrderCreatedEvent'

  receivePaymentStatus:
    action: receive # Мы получаем
    channel:
      $ref: '#/channels/paymentStatusChannel'
    messages:
      - $ref: '#/components/messages/PaymentProcessedEvent'
```

### 2.5. Резюме для Практика

1.  **Пока используйте v2:** Тулинг для v3 еще сырой. Но держите в уме новую ментальную модель.
2.  **Мнемоника для v2:** Представьте, что файл AsyncAPI — это **резюме сотрудника**.
    *   Если в резюме написано "Я *публикую* статьи", значит сотрудник пишет (Output).
    *   Если написано "Я *подписан* на рассылку", значит сотрудник читает (Input).
3.  **Client Generation Check:** После генерации кода всегда проверяйте: метод `send()` должен вести в топик, помеченный как `subscribe` в YAML (если вы генерируете клиента), или `publish` (если вы генерируете заглушку сервера). *Да, это все еще взрывает мозг, поэтому см. пункт 1.*

## 3. Интеграция со схемами (Payloads)

AsyncAPI спроектирован как **агностик** по отношению к формату данных. Спецификация берет на себя роль "конверта" (метаданные, заголовки, роутинг), а содержимое письма (`payload`) может быть написано на любом языке описания данных (IDL).

### 3.1. Ключевое поле: `schemaFormat`

Это самый важный технический нюанс раздела.
По умолчанию, если вы просто описываете поля внутри `payload`, парсер AsyncAPI считает, что это **AsyncAPI Schema** (надмножество JSON Schema).

Если вы хотите использовать Avro или Protobuf, вы **обязаны** явно сказать об этом парсеру через поле `schemaFormat`. Если этого не сделать, парсер попытается прочитать ваш Avro-JSON как JSON Schema, найдет несоответствия (например, поле `type` в Avro работает иначе) и выдаст ошибку или сгенерирует мусорный код.

**Таблица форматов (MIME types):**

| Формат | Значение `schemaFormat` | Описание |
| :--- | :--- | :--- |
| **Default** | (отсутствует) или `application/vnd.aai.asyncapi;version=2.6.0` | AsyncAPI Schema (JSON Schema + расширения). |
| **Avro** | `application/vnd.apache.avro;version=1.9.0` | Apache Avro (JSON representation). |
| **Protobuf** | `application/vnd.google.protobuf;version=3.0.0` | Protocol Buffers (исходный текст .proto). |
| **JSON Schema**| `application/schema+json;version=draft-07` | Чистая JSON Schema (без расширений AsyncAPI). |

---

### 3.2. Сценарий A: AsyncAPI / JSON Schema (WebSockets & REST-like events)

Используется, когда у вас "легкая" событийная система, например, WebSocket уведомления для фронтенда или вебхуки. Здесь не нужна жесткость Avro.

```yaml
channels:
  user/notifications:
    subscribe:
      message:
        name: UserNotification
        # schemaFormat НЕ указан -> используется AsyncAPI Schema
        payload:
          type: object
          properties:
            message:
              type: string
            severity:
              type: string
              enum: [info, warn, error]
```
*   **Плюс:** Нативная поддержка любым тулингом.
*   **Минус:** Плохо подходит для Kafka/Big Data, так как JSON Schema не описывает бинарную упаковку.

---

### 3.3. Сценарий B: Apache Avro (Enterprise Standard)

Это основной кейс для Kafka. Здесь у вас есть развилка: **Inline** (встраивание) или **Remote** (ссылка).

#### Вариант 1: Inline (Встраивание схемы)
Вы копируете JSON-структуру Avro прямо в YAML файл AsyncAPI.
*   *Где уместно:* В маленьких проектах или если схема уникальна для этого сообщения и никогда не меняется.

```yaml
channels:
  orders.shipped:
    subscribe:
      message:
        schemaFormat: 'application/vnd.apache.avro;version=1.9.0' # <--- ВАЖНО
        payload:
          type: record # Это Avro-синтаксис, а не JSON Schema
          name: OrderShipped
          fields:
            - name: orderId
              type: string
            - name: timestamp
              type: long
```

#### Вариант 2: Remote Reference (Ссылка на файл/Registry)
Это **Production-Ready** подход. Схема живет отдельно (в `.avsc` файле или в Schema Registry), AsyncAPI лишь ссылается на неё.

```yaml
channels:
  orders.shipped:
    subscribe:
      message:
        schemaFormat: 'application/vnd.apache.avro;version=1.9.0'
        payload:
          $ref: './schemas/OrderShipped.avsc' 
          # ИЛИ ссылка на Schema Registry (требует поддержки плагином)
          # $ref: 'http://registry.corp/subjects/orders.shipped-value/versions/latest'
```

**Нюанс кодогенерации:**
Когда генератор (например, Java Spring Cloud Stream) видит `$ref` на Avro файл, он:
1.  Загружает этот файл.
2.  Запускает **Avro Compiler** (а не JSON Schema to POJO mapper).
3.  Генерирует класс, наследующийся от `SpecificRecordBase` (стандарт Avro), а не простой POJO.
Это дает вам доступ к нативной сериализации Avro.

### 3.4. Сценарий C: Protobuf (gRPC & Binary Performance)

Интеграция Protobuf сложнее, так как это не JSON-подобный формат. Обычно схема вставляется как **строка** (string).

```yaml
channels:
  telemetry.sensors:
    publish:
      message:
        schemaFormat: 'application/vnd.google.protobuf;version=3.0.0'
        payload:
          type: string # AsyncAPI считает это строкой...
          contentEncoding: text/plain
          # ...но генератор распознает синтаксис внутри
          default: |
            syntax = "proto3";
            package sensors;
            message Telemetry {
              int32 temperature = 1;
              int32 humidity = 2;
            }
```
*   **Реальность:** Поддержка Protobuf в AsyncAPI-генераторах все еще отстает от Avro. Часто проще сгенерировать DTO через `protoc` отдельно, а AsyncAPI использовать только как документацию.

---

### 3.5. Архитектурный паттерн: Message Envelope (Конверт)

Важно различать `payload` (бизнес-данные) и `headers` (инфраструктурные данные).
В Kafka заголовки передаются отдельно от тела.

```yaml
components:
  messages:
    TransactionEvent:
      # 1. Заголовки (Kafka Headers)
      # Описываются всегда как AsyncAPI Schema (JSON Schema)
      headers:
        type: object
        properties:
          traceId:
            type: string
            description: OpenTelemetry Trace ID
          sourceSystem:
            type: string
      
      # 2. Формат тела (Avro)
      schemaFormat: 'application/vnd.apache.avro;version=1.9.0'
      payload:
        $ref: './schemas/Transaction.avsc'
```

### 3.6. Валидация и тулинг

Как практик, вы столкнетесь с проблемой валидации.
Стандартный CLI `asyncapi validate` отлично проверяет структуру YAML и JSON Schema внутри `payload`.
Но если вы укажете `schemaFormat: Avro` и допустите ошибку внутри Avro-схемы, стандартный валидатор может:
1.  **Пропустить это** (посчитав "черным ящиком").
2.  **Упасть**, если у него нет плагина для Avro.

**Совет:** Используйте специализированные парсеры (например, парсер от Epam или Red Hat), которые умеют "заглядывать" внутрь альтернативных форматов схем.

### Резюме раздела
1.  **Всегда указывайте `schemaFormat`**, если вы не используете JSON Schema.
2.  **Не смешивайте IDL:** Если у вас Kafka на Avro, храните схемы в `.avsc` файлах и ссылайтесь на них через `$ref`. Не делайте "Inline" в больших проектах.
3.  **Разделяйте Headers и Payload:** Заголовки описываются схемой AsyncAPI (так как это метаданные протокола), а тело — схемой вашего сериализатора (Avro/Proto).

## 4. Сценарии использования (Workflows)

Внедрение AsyncAPI меняет процесс разработки с хаотичного "Code-First" (сначала написали, потом забыли обновить Wiki) на управляемый "Contract-First" или "Contract-based".

### 4.1. Workflow A: Code Generation & Type Safety (Design Phase)

Это самый очевидный сценарий: превращение спецификации в работающий код. Однако здесь есть тонкий момент, отличающий новичка от эксперта.

*   **Naive Approach (Генерация всего):** Вы используете генератор (например, для Spring Boot), который создает весь каркас приложения: слушатели, роутеры, конвертеры.
    *   *Проблема:* При повторной генерации (обновили API) вы рискуете затереть бизнес-логику, если генератор не поддерживает паттерн "Gap" (generation gap pattern).
*   **Practitioner Approach (Генерация моделей/DTO):** Вы используете специализированные библиотеки (например, **Modelina**), чтобы генерировать **только DTO** (Data Transfer Objects) и интерфейсы.
    *   *Процесс:*
        1.  Архитектор обновляет `asyncapi.yaml`.
        2.  `npm run generate:models` создает классы `OrderCreatedEvent.java` или `structs.go`.
        3.  Разработчик обновляет бизнес-логику, используя эти типизированные классы.
    *   *Ценность:* Если поле переименовали в YAML, код компиляции упадет **до** того, как приложение уйдет в деплой. Это Strong Type Safety для асинхронных коммуникаций.

### 4.2. Workflow B: Governance & Linting (Build Phase)

Это критический сценарий для больших компаний. Как запретить командам называть топики как попало (`user_created`, `UserCreated`, `NEW_USER`)?

*   **Инструмент:** **Spectral** (линетр для JSON/YAML).
*   **Сценарий:** Вы пишете набор правил (Ruleset) для AsyncAPI.
    *   *Правило 1:* Имя канала должно соответствовать regex `^[a-z]+\.[a-z]+\.v[0-9]+$`.
    *   *Правило 2:* У каждого сообщения должно быть поле `description`.
    *   *Правило 3:* Поле `messageId` в заголовках обязательно.
*   **CI Pipeline:** Если PR с изменением AsyncAPI нарушает правила Spectral, сборка блокируется.

### 4.3. Workflow C: Mocking & Simulation (Test Phase)

Как протестировать микросервис, который слушает Kafka, без поднятия настоящего Kafka?
Как фронтенд-разработчику протестировать WebSocket, если бэкенд еще не готов?

*   **Инструмент:** **Microcks** или **AsyncAPI CLI Mocks**.
*   **Суть:** Инструмент читает `asyncapi.yaml`, находит секцию `examples` в сообщениях и поднимает **виртуальный брокер**.
    *   Для Kafka: Microcks эмулирует брокер, который по расписанию "пушит" примеры событий в топик.
    *   Для WebSocket: Поднимается сервер, к которому можно подключиться и получать фейковые данные.
*   **Ценность:** Команды становятся автономными. Consumer может написать и протестировать свой код, пока Producer еще даже не начал разработку, опираясь только на контракт.

### 4.4. Workflow D: Change Management (Deploy Phase)

Как узнать, сломает ли ваше изменение API других потребителей? В REST у нас есть инструменты проверки совместимости (OpenAPI Diff). В AsyncAPI они тоже появляются.

*   **Инструмент:** **AsyncAPI Diff**.
*   **Сценарий:** В CI пайплайне сравнивается `asyncapi.yaml` из ветки `main` и из текущего PR.
*   **Логика проверки:**
    *   Добавили обязательное поле в payload? $\to$ **Breaking Change** (старые консьюмеры упадут).
    *   Удалили канал? $\to$ **Breaking Change**.
    *   Добавили необязательное поле? $\to$ **Safe**.
*   **Результат:** Бот пишет комментарий в Pull Request с предупреждением о нарушении обратной совместимости.

### 4.5. Workflow E: Service Discovery (Run Phase)

В микросервисной архитектуре никто не знает, кто и что публикует. "Где найти событие создания заказа?"

*   **Инструмент:** **Backstage** (или любой Developer Portal) + AsyncAPI Plugin.
*   **Суть:** AsyncAPI файлы агрегируются в единый каталог.
*   **Граф зависимостей:** Портал строит граф:
    `[OrderService] --(pub)--> [orders.created] --(sub)--> [EmailService]`
    `[OrderService] --(pub)--> [orders.created] --(sub)--> [AuditLog]`
*   **Ценность:** Это дает **Observability архитектуры**. Вы визуально видите, какие сервисы зависят от конкретного топика, что критически важно при инцидентах или рефакторинге.

### Резюме раздела

На уровне Practitioner вы должны внедрять AsyncAPI в таком порядке:
1.  **Documentation:** Сделайте API видимым (Workflow E).
2.  **Linting:** Наведите порядок в именовании (Workflow B).
3.  **Code Gen:** Упростите жизнь разработчикам (Workflow A).
4.  **Mocking/Diff:** Автоматизируйте качество (Workflow C, D).

Без интеграции в Workflows файл AsyncAPI быстро устаревает и становится "мертвым грузом".

## 5. AsyncAPI vs CloudEvents

Чтобы понять разницу, используем аналогию с почтой:
*   **CloudEvents** — это стандартный **почтовый конверт**. Он определяет, где писать адрес отправителя, где индекс, и где клеить марку. Он не говорит, *как* это письмо будет доставлено (самолетом или поездом) и не знает, что лежит внутри (письмо бабушке или налоговая декларация).
*   **AsyncAPI** — это **расписание логистической компании**. Оно говорит: "В 9:00 грузовик выезжает из Терминала А в Терминал Б". В этом расписании может быть указано: "Мы принимаем только стандартные конверты (CloudEvents)".

### 5.1. CloudEvents: Проблема интероперабельности (Envelope)

**CloudEvents (CE)** — это спецификация от CNCF (Cloud Native Computing Foundation). Её цель — унифицировать метаданные событий, чтобы middleware (Serverless платформы, Event Mesh, брокеры) могли маршрутизировать сообщения, не заглядывая в их бизнес-данные.

**Что определяет CloudEvents:**
Стандартный набор атрибутов (заголовков):
*   `specversion`: Версия стандарта (напр. "1.0").
*   `type`: Тип события (напр. `com.github.pull_request.opened`).
*   `source`: Источник события (URI, напр. `/projects/123`).
*   `id`: Уникальный ID сообщения (для дедупликации).
*   `time`: Timestamp.
*   `datacontenttype`: Тип контента внутри (напр. `application/avro` или `application/json`).

**Чего НЕ делает CloudEvents:**
*   Не описывает бизнес-схему (какие поля лежат внутри `data`).
*   Не описывает транспорт (Kafka, HTTP, AMQP) — хотя имеет "биндинги" к ним.
*   Не описывает операции (`subscribe` vs `publish`).

### 5.2. AsyncAPI: Карта местности (Interface Definition)

**AsyncAPI** — это IDL (Interface Definition Language). Его задача — задокументировать точки входа и выхода вашего приложения.

**Синергия:**
Вы используете AsyncAPI, чтобы сказать: *"Мой сервис `OrderService` в канале `orders` публикует сообщения, которые упакованы в формат **CloudEvents**, а внутри в поле `data` лежит JSON-схема заказа"*.

---

### 5.3. Практическая реализация: Как скрестить ужа и ежа

Существует два способа описать CloudEvents внутри AsyncAPI. Выбор зависит от того, как вы сериализуете данные (Structured vs Binary mode).

#### Сценарий А: Structured Mode (JSON Envelope)
Вы передаете событие как единый JSON-объект, где метаданные CloudEvents лежат на одном уровне с полем `data`. Это часто используется в HTTP-хуках или когда Kafka не поддерживает заголовки.

В AsyncAPI вы описываете структуру конверта явно:

```yaml
channels:
  orders.created:
    subscribe:
      message:
        name: OrderCreatedEvent
        contentType: application/cloudevents+json # MIME-type для CE
        payload:
          type: object
          required: [specversion, id, source, type, data]
          properties:
            # 1. Стандартные поля CloudEvents
            specversion:
              type: string
              const: '1.0'
            id:
              type: string
              format: uuid
            source:
              type: string
              format: uri
            type:
              type: string
              const: 'com.company.orders.created' # Семантический тип
            
            # 2. Бизнес-данные (Payload внутри Envelope)
            data:
              $ref: '#/components/schemas/OrderPayload'

components:
  schemas:
    OrderPayload:
      type: object
      properties:
        orderId:
          type: integer
```

#### Сценарий Б: Binary Mode (Headers Mapping)
Это **Standard Practice** для Kafka и RabbitMQ.
Метаданные CloudEvents (`ce-type`, `ce-id`, `ce-source`) передаются в **заголовках** протокола (Kafka Headers), а тело сообщения (`payload`) содержит **только** бизнес-данные (`OrderPayload`).

В AsyncAPI это разделяется на секции `headers` и `payload`:

```yaml
channels:
  orders.created:
    subscribe:
      message:
        name: OrderCreatedEvent
        # Метаданные CloudEvents живут в заголовках
        headers:
          type: object
          required: [ce_specversion, ce_id, ce_source, ce_type]
          properties:
            ce_specversion:
              type: string
              const: '1.0'
            ce_type:
              type: string
              const: 'com.company.orders.created'
            ce_id:
              type: string
        
        # Payload чистый, без обертки
        payload:
          $ref: '#/components/schemas/OrderPayload'
```

### 5.4. Вердикт Архитектора

1.  **Зачем нужен CloudEvents?**
    *   Чтобы построить **Event Mesh**. Если все ваши сервисы используют CE, вы можете поставить инфраструктурный слой (например, Knative Eventing или SAP Event Mesh), который будет автоматически фильтровать и роутить события, не зная бизнес-логики.
    *   *Пример:* "Отправь все события с `type=alert.*` в Slack-бота". Middleware прочитает заголовок и сделает работу.

2.  **Зачем нужен AsyncAPI поверх CE?**
    *   CloudEvents стандартизирует "обертку", но ничего не говорит о том, что лежит в поле `data`.
    *   AsyncAPI документирует именно **бизнес-смысл** (`payload`) и **топологию** (где искать этот поток данных).

3.  **Совет Практику:**
    Если вы строите современную EDA (Event-Driven Architecture), примите **CloudEvents** как корпоративный стандарт конверта, а **AsyncAPI** — как стандарт документации.
    *   В коде используйте SDK CloudEvents (Java/Go/JS) для создания конверта.
    *   В CI/CD используйте AsyncAPI для валидации того, что `data` внутри конверта соответствует схеме.

## 6. Чек-лист уровня Practitioner

1.  **Protocol Bindings:**
    Знаете ли вы, как описать специфику Kafka (partitions, group.id) или MQTT (QoS, Retain) в AsyncAPI?
    *   *Ответ:* Используйте `bindings`. Это расширения спецификации.
    *   Пример: `channels: my-topic: bindings: kafka: topicConfiguration: cleanup.policy: compact`.
2.  **Central Catalog:**
    Где вы храните AsyncAPI файлы?
    *   *Плохо:* В каждом git-репозитории сервиса, никто их не видит.
    *   *Хорошо:* Агрегируются в центральный каталог (Developer Portal) или лежат в едином репозитории контрактов.
3.  **Human-Readable Descriptions:**
    Валидный YAML бесполезен, если в `description` пусто.
    *   *Задача:* Описать *бизнес-смысл* события (когда оно происходит?), а не просто "Event for User".

### Заключение
Внедрение **AsyncAPI** сложнее, чем OpenAPI, потому что событийные системы более децентрализованы.
Начните с малого:
1.  Опишите публичные события ваших Core-сервисов.
2.  Сгенерируйте из них HTML-документацию и опубликуйте на внутреннем портале.
3.  Только потом думайте о кодогенерации и валидации в CI.

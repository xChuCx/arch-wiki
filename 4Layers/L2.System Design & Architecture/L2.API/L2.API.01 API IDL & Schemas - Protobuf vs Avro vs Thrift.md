**TL;DR**: Выбор IDL (Interface Definition Language) — это не вопрос "кто быстрее сериализует". Это вопрос **управления изменениями** на горизонте 5-10 лет.
*   **Protobuf** — стандарт для Service-to-Service (gRPC). Он оптимизирован под совместимость тегов.
*   **Avro** — стандарт для Data-at-Rest и Event Streaming (Kafka). Он требует доступа к схеме писателя (Schema Registry) и идеален для динамической типизации.
*   **Thrift** — мощный, но тяжеловесный RPC-фреймворк, теряющий популярность в пользу gRPC, но незаменимый в экосистемах Meta/Uber.

Главное правило эксперта: **Данные живут дольше, чем код.** Вы можете передеплоить сервис, но вы не можете "передеплоить" терабайты логов в S3, записанных 3 года назад.

## 1. Protocol Buffers (Protobuf)

**Protobuf** — это не просто формат сериализации. Это строго типизированный бинарный контракт, оптимизированный для минимизации объема передаваемых данных и обратной совместимости. В отличие от самоописываемых форматов (JSON, XML), сообщение Protobuf бесполезно без `.proto` определения, так как бинарный поток не содержит имен полей, только их числовые идентификаторы.

### 1.1. Физическая структура (The Wire Format)

Сообщение Protobuf — это последовательность пар **Key-Value**.
Ключ (Tag) кодирует в себе две единицы информации: номер поля и тип кодирования на проводе (Wire Type).

$$ \text{Key} = (\text{Field\_Number} \ll 3) \ | \ \text{Wire\_Type} $$

Где `Wire_Type` занимает последние 3 бита. Это фундаментальное ограничение, которое определяет совместимость типов.

**Таблица Wire Types:**

| Wire Type | Значение | Описание | Примеры типов в .proto |
| :--- | :--- | :--- | :--- |
| **0** | `VARINT` | Числа переменной длины | `int32`, `int64`, `uint32`, `bool`, `enum`, `sint32` |
| **1** | `I64` | Фиксированные 8 байт | `fixed64`, `sfixed64`, `double` |
| **2** | `LEN` | Длина + Данные | `string`, `bytes`, `embedded messages`, `packed repeated` |
| **3, 4** | `GROUP` | Deprecated (Start/End group) | Не использовать |
| **5** | `I32` | Фиксированные 4 байта | `fixed32`, `sfixed32`, `float` |

**Инсайт Архитектора:**
Парсер смотрит **только** на Wire Type.
*   Ему все равно, было поле в `.proto` объявлено как `bool` или как `int64`. Если Wire Type = 0 (Varint), он сможет прочитать данные.
*   Именно поэтому `int32` и `float` (Wire Type 5) несовместимы: парсер ожидает Varint, а видит фиксированные 4 байта, и наоборот. Это приведет к ошибке парсинга ("Protocol message tag had invalid wire type").

### 1.2. Varint и ZigZag: Магия сжатия чисел

Понимание Varint критично для оценки размера сообщений.

#### Base-128 Varint
Используется для Wire Type 0. Каждый байт имеет флаг **MSB** (Most Significant Bit):
*   `1`: "за этим байтом следует еще один байт этого числа".
*   `0`: "это последний байт".
Остальные 7 бит — полезная нагрузка. Порядок байтов: **Little Endian**.

**Пример:** Число `300`.
В бинарном виде: `100101100` (9 бит).
1.  Разбиваем на группы по 7 бит: `0000010` (старшие) и `0101100` (младшие).
2.  Разворачиваем (Little Endian): сначала младшие.
3.  Добавляем MSB:
    *   Первый байт: `1` (есть продолжение) + `0101100` $\to$ `10101100` (`0xAC`)
    *   Второй байт: `0` (конец) + `0000010` $\to$ `00000010` (`0x02`)
**Итог:** Число 300 занимает 2 байта (`AC 02`), а не 4 или 8.

#### Проблема отрицательных чисел и ZigZag (`sint`)
В обычном `int32` число `-1` в дополнении до двух выглядит как `111...111` (FFFFFFFF).
Varint воспримет это как **огромное** беззнаковое число и потратит **10 байт** на запись `-1`.

Для решения этой проблемы существуют типы `sint32` / `sint64`. Они используют **ZigZag кодирование**, отображая знаковые числа в беззнаковые:
*   $0 \to 0$
*   $-1 \to 1$
*   $1 \to 2$
*   $-2 \to 3$
*   $n \to (n \ll 1) \oplus (n \gg 31)$

**Вердикт:** Если в вашем поле возможны отрицательные значения, используйте `sint32/sint64`. Если используете обычный `int32` для отрицательных чисел, вы тратите трафик впустую.

### 1.3. Repeated поля и Packed Encoding

До Proto3 поля `repeated` (массивы) кодировались наивно:
`[Tag|Type] [Value1] [Tag|Type] [Value2] ...`
Если у вас массив из 1000 `int32`, тег поля повторяется 1000 раз.

В Proto3 (и опционально в Proto2) по умолчанию включен **Packed Encoding** для скалярных типов:
`[Tag|Type=2 (LEN)] [Length] [Value1] [Value2] [Value3] ...`
Тег пишется один раз, затем общая длина байт, затем сами значения подряд (как дамп памяти). Это значительно экономит место и ускоряет парсинг.

### 1.4. Эволюция полей: Тонкости совместимости

Правила добавления и удаления полей просты, но есть нюансы, которые "стреляют" в продакшене.

#### Переименование полей (Renaming)
*   В бинарном формате имен нет. Вы можете переименовать `int32 user_id = 1;` в `int32 id = 1;`.
*   **Риск:** Это ломает сериализацию в **JSON** (через `JsonFormat`), так как там ключами являются имена. Если у вас есть HTTP-клиенты, использующие JSON-транскодинг (gRPC-Gateway), переименование сломает API.

#### Изменение типа (Type Promotion)
Вы можете безопасно менять типы, если их Wire Type совместим:
1.  `int32`, `int64`, `uint32`, `bool` $\to$ совместимы.
    *   *Опасность:* Если вы поменяли `int64` на `int32`, парсер просто "отрежет" старшие биты. Данные испортятся (truncation), но ошибки парсинга не будет.
2.  `sint32` $\leftrightarrow$ `sint64` $\to$ совместимы.
3.  `string` $\leftrightarrow$ `bytes` $\to$ совместимы (если байты валидный UTF-8).
4.  `int32` $\leftrightarrow$ `sint32` $\to$ **НЕСОВМЕСТИМЫ**. (Разное кодирование значений, хотя Wire Type один).

#### `reserved` — Пояс безопасности
При удалении поля **обязательно** резервируйте его номер и имя.
```protobuf
message User {
  reserved 2, 15, 9 to 11;
  reserved "foo", "bar";
  // int32 foo = 2; // Компилятор выдаст ошибку
}
```
Без этого другой разработчик может через год добавить `string email = 2;`. Если сервис получит старое сообщение, где под тегом 2 лежал `int32`, парсинг упадет (Wire Type mismatch: ожидал LEN, получил VARINT) или, что хуже, прочитает мусор.

### 1.5. Proto2 vs Proto3: Идеология Nullability

Это главный источник холиваров и багов.

*   **Proto2:** Имел концепцию `has_field()`. Поля могли быть `required`, `optional` (с дефолтом) или `repeated`. Мы точно знали: поле пришло от клиента или это дефолт?
*   **Proto3 (ранний):** Убрал `required` и `optional`. Все поля имеют **Zero Value** (0, false, empty string).
    *   *Проблема:* Если `price = 0`, это "бесплатно" или "цена не указана"? Невозможно отличить.
*   **Proto3 (современный, v3.15+):** Вернули ключевое слово `optional`.
    *   Под капотом это реализуется через `oneof` (синтетический union). Теперь можно проверить `has_price()`.
    *   **Совет Архитектора:** Для всех полей, где `0` является валидным бизнес-значением (цена, координаты, статус), используйте `optional` или **Wrapper Types** (`google.protobuf.Int32Value`).

### 1.6. `Oneof`: Объединения (Unions)

Позволяет иметь несколько полей, из которых установлено только одно.
```protobuf
message Auth {
  oneof method {
    string password = 1;
    string token = 2;
    OAuth oauth = 3;
  }
}
```
*   **Память:** Поля `oneof` делят одну область памяти (в C++/Go).
*   **Backward Compat:** Вы можете добавлять новые поля в `oneof`.
*   **Риск:** Нельзя сделать поле внутри `oneof` `repeated`.

### 1.7. Рекомендация для Staff Engineer

Когда вы проектируете API на 5 лет вперед, следуйте правилу **"Additive Changes Only"**:
1.  Никогда не меняйте номера тегов.
2.  Удаляя поля, используйте `reserved`.
3.  Избегайте `uint32/uint64` в публичных API, если нет гарантии, что клиенты (Java) корректно с ними работают (Java не имеет unsigned типов, что вызывает боль при конвертации больших чисел).
4.  Используйте `Wrapper Types` (`StringValue` вместо `string`) для полей, которые должны быть Nullable в базе данных (Partial Updates).

## 2. Apache Avro

**Apache Avro** — это система сериализации данных, ориентированная на высокую пропускную способность и компактность. В отличие от Protobuf, который спроектирован для RPC, Avro спроектирован для **Batch Processing** (Hadoop) и **Streaming** (Kafka).

### 2.1. Физическая структура (The Binary Encoding)

Avro производит **самый компактный** бинарный формат среди "большой тройки" (Proto, Thrift, Avro).
Почему? Потому что в бинарном потоке **полностью отсутствуют метаданные полей**.

#### Отсутствие Тегов (Tagless Serialization)
В Protobuf поток выглядит так: `[Tag:1][Value] [Tag:2][Value]`.
В Avro поток выглядит так: `[Value] [Value]`.

Парсер Avro **слеп**. Он не знает, где заканчивается одно поле и начинается другое. Он опирается исключительно на предоставленную ему **Схему Писателя (Writer Schema)**, которая говорит: "Сначала идет `long`, потом `string`, потом массив".

**Пример:**
Схема: `{"type": "record", "fields": [{"name": "id", "type": "long"}, {"name": "active", "type": "boolean"}]}`
Данные: `id=100`, `active=true`.

1.  `id` (long): Используется **ZigZag Varint** (как в Protobuf `sint64`). Число 100 $\to$ `0xC8 0x01`.
2.  `active` (bool): 1 байт $\to$ `0x01`.
**Итог:** Всего 3 байта (`C8 01 01`). Никаких заголовков, никаких идентификаторов полей.

**Инсайт Архитектора:**
Именно эта "слепота" делает Avro хрупким без управления схемами. Если вы попытаетесь прочитать данные не той схемой (например, поменяли поля местами), вы получите не ошибку, а мусор (парсер интерпретирует байты строки как число и пойдет дальше).

### 2.2. Schema Resolution: Алгоритм согласования

Это главная "киллер-фича" Avro. При чтении всегда участвуют **две** схемы.
1.  **Writer Schema ($S_W$):** Схема, с которой данные были записаны (историческая правда).
2.  **Reader Schema ($S_R$):** Схема, которую ожидает приложение сейчас (актуальный код).

Алгоритм Resolution выполняет **проекцию** данных из $S_W$ в $S_R$:

1.  **Matching (Сопоставление):** Поля сопоставляются **по именам** (используются также алиасы). Порядок полей в $S_R$ может отличаться от $S_W$ — Avro это разрулит (но это затратно, так как требует буферизации/скипа).
2.  **Projection (Проекция):**
    *   Если поле есть в $S_W$, но нет в $S_R$ $\to$ поле пропускается (Skipping).
    *   Если поле есть в $S_R$, но нет в $S_W$ $\to$ подставляется `default` значение из $S_R$.
3.  **Type Promotion:**
    *   Если в $S_W$ написано `int`, а в $S_R$ — `long`, Avro автоматически расширит тип.
    *   Наоборот (`long` $\to$ `int`) — ошибка.

### 2.3. Schema Evolution: Правила выживания

Чтобы система жила годами, вы должны соблюдать правила совместимости.

#### Forward Compatibility (Старый код читает новые данные)
*   **Сценарий:** Вы добавили поле в Producer, но Consumer еще не обновился.
*   **В Avro:** Consumer (Reader) просто игнорирует неизвестные поля, так как их нет в его схеме.
*   **Условие:** Работает "из коробки".

#### Backward Compatibility (Новый код читает старые данные)
*   **Сценарий:** Вы обновили Consumer, но в Kafka лежат события годичной давности.
*   **В Avro:** Consumer видит новое поле в своей схеме ($S_R$), но не находит его в данных ($S_W$).
*   **Условие:** Новое поле **ОБЯЗАНО** иметь свойство `"default"`.
    *   Если дефолта нет — исключение `AvroTypeException`.

**Пример безопасного добавления поля:**
```json
{
  "name": "email",
  "type": "string",
  "default": ""  // <--- Критически важно!
}
```

#### Full Compatibility
Поддерживается и то, и другое. Требует наличия `default` при добавлении полей и запрещает удалять поля, у которых не было `default`.

### 2.4. Union Types и "Ловушка Null"

Avro не имеет концепции `optional` (как Protobuf) или `nullable` (как SQL). Вместо этого используются **Unions** (Объединения).

Типичное объявление nullable поля:
```json
{"name": "description", "type": ["null", "string"], "default": null}
```
Это означает: "Тип поля может быть ЛИБО `null`, ЛИБО `string`".

**Expert Trap (Порядок имеет значение):**
Значение свойства `default` должно соответствовать **первому** типу в Union.
*   `type: ["null", "string"], default: null` — ✅ Верно.
*   `type: ["string", "null"], default: null` — ❌ **Ошибка компиляции/рантайма**. Дефолт `null` не соответствует типу `string`.
*   `type: ["string", "null"], default: "empty"` — ✅ Верно.

### 2.5. OCF: Object Container Files (Avro at Rest)

Когда мы пишем Avro в S3 или HDFS, мы не можем писать "голые" бинарные данные (мы потеряем схему). Используется формат **OCF**.

Структура файла `.avro`:
1.  **Header:**
    *   Magic bytes (`Obj\1`).
    *   **Metadata:** Содержит **полный JSON Writer Schema**. Файл самодостаточен!
    *   **Sync Marker:** 16 случайных байт.
2.  **Data Blocks:**
    *   Количество объектов в блоке.
    *   Размер блока в байтах.
    *   Сериализованные объекты.
    *   **Sync Marker** (повторяется после каждого блока).

**Зачем нужен Sync Marker?**
Для **MapReduce / Spark splitting**. Если у вас файл на 1 ТБ, Spark может разрезать его на части произвольно. Если "разрез" попал на середину данных, воркер сканирует байты, пока не найдет Sync Marker, и начинает читать с начала следующего блока. Это позволяет параллельно обрабатывать один файл.

### 2.6. Schema Registry: Архитектура для Kafka

В потоковой передаче (Kafka) нельзя прикреплять схему к каждому сообщению (схема на 2 КБ убьет перформанс для сообщений в 100 байт).

**Паттерн:**
1.  **Producer:** Хеширует схему (или берет ее MD5/ID). Отправляет схему в сервис **Schema Registry**. Получает `Schema ID` (4 байта, int).
2.  **Kafka Message:** `[Magic Byte (0x00)] [Schema ID (4 bytes)] [Avro Binary Payload]`.
3.  **Consumer:** Читает первые 5 байт. Видит ID. Идет в локальный кэш или Schema Registry, достает JSON схемы. Выполняет десериализацию.

**Стратегии именования (Subject Name Strategies):**
*   `TopicNameStrategy`: Одна схема на топик. (Просто, но жестко).
*   `RecordNameStrategy`: Схема привязана к имени Record. Позволяет класть разные типы событий в один топик (Multi-schema topic).

### 2.7. Logical Types (Расширение семантики)

Базовых типов Avro мало (`null, boolean, int, long, float, double, bytes, string`).
Как хранить дату, время, UUID или Decimal?

Используются **Logical Types** — аннотации над примитивами.
*   **Decimal:** Хранится как `bytes` + метаданные `scale` и `precision`.
*   **Date:** Хранится как `int` (дней с epoch).
*   **Timestamp-millis:** Хранится как `long`.
*   **UUID:** Хранится как `string`.

**Важно:** Клиентская библиотека должна уметь конвертировать эти "логические" типы в нативные объекты языка (`java.time.Instant`, `BigDecimal`). Если библиотека старая, она вернет вам просто `int` или `bytes`.

### Резюме для Staff Engineer

1.  **Avro — это динамика.** Вы можете писать обобщенный код (`GenericRecord`), который обрабатывает данные без кодогенерации POJO-классов. Это идеально для платформенных команд (Data Platform), пишущих универсальные инджесторы.
2.  **Схема — это контракт.** Используйте Schema Registry с режимом **"Forward Transitive"** или **"Full Transitive"** compatibility check в CI/CD. Это не позволит разработчику закоммитить схему, которая сломает потребителей.
3.  **Дефолты — наше всё.** Добавляя поле, всегда ставьте `default`. Нет дефолта — нет обратной совместимости.

## 3. Apache Thrift

Apache Thrift (изначально разработанный в Facebook в 2007 году) — это фреймворк для масштабируемой кросс-языковой разработки сервисов.

### 3.1. Архитектура: Слоеный пирог (The Layered Architecture)

Главное отличие Thrift от конкурентов — модульность. Стек состоит из четырех независимых слоев. Инженер обязан правильно подобрать комбинацию этих слоев под задачу.

1.  **Server (Runtime Model):** Определяет модель многопоточности.
    *   `TSimpleServer`: Однопоточный (для тестов).
    *   `TThreadPoolServer`: Блокирующий I/O, один поток на соединение. Идеален для низкого RPS и длинных тяжелых вычислений.
    *   `TNonblockingServer`: Использует `epoll`/`kqueue` (IO Loop) и пул воркеров. Аналог Netty/Node.js. Нужен для C10K problem.
2.  **Processor (Generated Code):** Сгенерированный код, который превращает байтовые потоки в вызовы методов вашего кода.
3.  **Protocol (Serialization):** Как данные кодируются в байты (JSON, Binary, Compact).
4.  **Transport (I/O Layer):** Как байты передаются по сети.
    *   `TSocket`: Блокирующий TCP сокет.
    *   `TFramedTransport`: Добавляет 4 байта длины сообщения перед данными. **Критически важен** для неблокирующих серверов, так как позволяет читать полный пакет (frame) до начала десериализации.
    *   `TMemoryBuffer`: Чтение/запись в RAM (аналог `ByteArrayOutputStream`).

**Инсайт Архитектора:**
Частая ошибка в проде — несовпадение транспортов. Если клиент использует `TFramedTransport`, а сервер — обычный `TSocket` (Buffered), соединение зависнет или разорвется. В gRPC это невозможно (HTTP/2 стандарт), в Thrift — это ваша ответственность.

### 3.2. IDL и Система Типов (Richer than Proto)

Thrift IDL синтаксически похож на C-структуры, но семантически богаче Protobuf.

```thrift
namespace java com.example.service

// 1. Нативные исключения
exception InvalidRequestException {
  1: required i32 code,
  2: optional string reason
}

struct User {
  1: required i64 id,
  2: optional string username,
  // 3. Нативные контейнеры (Set, Map, List)
  3: optional set<string> roles,
  4: optional map<string, i32> inventory // Item -> Count
}

service UserService {
  User getUser(1: i64 id) throws (1: InvalidRequestException e),
  void ping()
}
```

*   **Exceptions:** Thrift поддерживает `exception` как объект первого класса. В gRPC вы ограничены набором статус-кодов (Status Codes) или должны передавать ошибки через `oneof` / `Any`. В Thrift вы ловите нативные `try-catch`.
*   **Containers:** В Protobuf `map` появился поздно и является синтаксическим сахаром над `repeated Entry`. В Thrift `map`, `set`, `list` существуют изначально и реализованы эффективно.

### 3.3. Внутренности Протоколов (The Physics of Encoding)

Вы должны знать разницу между двумя главными протоколами:

#### TBinaryProtocol
Простой, быстрый, но "рыхлый".
*   Никакого сжатия целых чисел. `i32` всегда занимает 4 байта, `i64` — 8 байт.
*   Структура: `[Type: 1 byte] [Field ID: 2 bytes] [Value]`.
*   **Плюс:** Очень низкая нагрузка на CPU (просто копирование памяти).
*   **Минус:** Большой размер трафика.

#### TCompactProtocol (Аналог Protobuf)
Сложный, компактный, CPU-intensive.
*   Использует **ZigZag Varint** (аналогично Protobuf) для сжатия чисел.
*   **Delta Encoding для Field ID:** Это киллер-фича.
    *   В Protobuf пишется полный Field ID (например, `Tag=15`).
    *   В Thrift Compact пишется **разница** между текущим Field ID и предыдущим.
    *   Если поля идут подряд (1, 2, 3...), разница равна 1. Дельта (до 15) и Тип поля упаковываются в **один байт**.
    *   *Следствие:* Если ваши Field ID идут подряд (1, 2, 3), Thrift Compact экстремально эффективен (1 байт оверхеда на поле). Если ID разбросаны (1, 500, 1000), эффективность падает.

### 3.4. Управление версиями (Versioning & Requiredness)

Правила совместимости в Thrift жестче, чем в Proto3.

1.  **Field IDs:** Священны. Менять нельзя.
2.  **`required`:**
    *   Если поле помечено `required`, оно **должно** быть в потоке.
    *   При чтении: Если поля нет, парсер выбрасывает `TProtocolException`.
    *   **Опасность:** Добавление `required` поля ломает старых клиентов (они не шлют поле $\to$ сервер падает). Удаление `required` поля ломает старые серверы (они ждут поле $\to$ падают).
3.  **`optional`:**
    *   При генерации кода (Java/C++) создаются методы `isSetField()`.
    *   Если поле не установлено, оно не пишется в поток (экономия трафика).

**Совет Эксперта:** В долгоживущих системах **всегда** используйте `optional`. Считайте, что `required` не существует. Это единственная защита от проблем Backward/Forward compatibility.

### 3.5. Скрытая роль Thrift: Parquet

Даже если вы не используете Thrift для RPC, вы, скорее всего, используете его для хранения данных.
**Apache Parquet** — самый популярный колоночный формат для Big Data — использует определения Thrift для хранения **метаданных файла**.
*   Структура файла Parquet, схема колонок, статистика (min/max values) — все это сериализовано через `TCompactProtocol` и зашито в футер файла.
*   Это делает знание Thrift обязательным для инженеров, занимающихся глубокой оптимизацией Data Lake.

### Резюме для Staff Engineer

1.  **Thrift жив в Энтерпрайзе:** Если вы работаете с Hadoop/Hive/Impala или поддерживаете легаси крупных тех-компаний, Thrift неизбежен.
2.  **Богатая типизация:** Если вашему API критически важны сложные структуры (`map<set<i32>, list<string>>`) и нативные исключения, Thrift может быть удобнее gRPC, несмотря на возраст.
3.  **TCompactProtocol и Delta Encoding:** Старайтесь назначать Field ID последовательно (1, 2, 3...), чтобы максимизировать сжатие заголовков полей.
4.  **Transport Mismatch:** Первая причина ошибок в Thrift — клиент шлет `Framed`, сервер ждет `Buffered`. Всегда проверяйте конфигурацию транспорта.

### 4.2. Детальный разбор ключевых отличий

Инженер уровня Expert должен понимать нюансы, скрытые за этими строками.

#### 1. Идентификация полей: Tags vs Names vs Resolution
Это фундаментальное отличие, определяющее сценарии использования.

*   **Protobuf/Thrift (Tag-based):** Вы можете переименовать поле `user_id` в `uid` в `.proto` файле, и **ничего не сломается** на бинарном уровне (так как тег `1` остался `1`).
    *   *Плюс:* Устойчивость к рефакторингу кода.
    *   *Минус:* Нельзя переиспользовать теги. "Кладбище" зарезервированных тегов (`reserved 1, 2, 5 to 10`) растет вечно.
*   **Avro (Resolution-based):** Вы *не можете* просто переименовать поле, так как сопоставление идет по именам.
    *   *Механизм:* Чтобы переименовать поле, вы обязаны добавить в схему список `aliases: ["old_name"]`.
    *   *Плюс:* Бинарный пейлоад экстремально мал (нет оверхеда на теги).
    *   *Минус:* Без доступа к Writer Schema (например, отвалился Schema Registry) вы не прочитаете ни байта.

#### 2. Динамический доступ (Dynamic Access)
Представьте, что вы пишете универсальную утилиту, которая перекладывает данные из Kafka в базу данных (ETL). Она не знает структуру данных заранее.

*   **Avro:** Король этого сценария. Библиотека читает JSON-схему и возвращает `GenericRecord` — словарь (Map), где ключи — это имена полей. Вы можете сделать `record.get("price")` без единого сгенерированного Java-класса.
*   **Protobuf:** Очень больно. Вам нужно использовать `DynamicMessage` и загружать `FileDescriptorSet` (скомпилированные `.proto`) в рантайме. Reflection в Protobuf сложен и медленен.
*   **Thrift:** Практически невозможно без глубокого хакинга протокола.

#### 3. Канонизация (Canonicalization)
Можете ли вы взять бинарное сообщение, посчитать от него `SHA-256` и использовать как ключ дедупликации?

*   **Protobuf:** **НЕТ.**
    *   Порядок ключей в сериализованной `map` не определен.
    *   Неизвестные поля могут быть записаны в разном порядке.
    *   Одно и то же логическое сообщение может дать разные байты.
*   **Avro:** **ДА.**
    *   Спецификация определяет *Parsing Canonical Form* (PCF). Это позволяет вычислять "Fingerprint" схемы и данных для надежного хеширования и дедупликации.

#### 4. Nullability и "Опциональность"

*   **Thrift & Avro:** Имеют явное понятие `null` (через Union в Avro) и явное отсутствие значения. Вы точно знаете: значение не пришло или оно равно нулю.
*   **Protobuf (v3 Default):** Исповедует философию "Zero Value". Если `count == 0`, вы не знаете, прислал ли клиент `0` или не прислал ничего.
    *   *Workaround:* Использовать `google.protobuf.Int32Value` (обертки) или ключевое слово `optional` (которое под капотом создает bitmask присутствия).

### 4.3. Пример: Сценарий эволюции (Evolution Case Study)

Допустим, у нас есть поле `int32 age`. Мы хотим заменить его на `string age_range` ("18-25").

**Сценарий:** Старый Клиент (шлет int) $\to$ Новый Сервер (ждет string).

1.  **Protobuf:**
    *   Вы меняете тип поля `2` с `int32` на `string`.
    *   Старый клиент шлет `WireType=0` (Varint).
    *   Новый сервер ждет `WireType=2` (Length Delimited).
    *   **Результат:** Ошибка парсинга (Exception). Совместимость сломана.
    *   *Правильное решение:* `reserved 2; string age_range = 3;`.

2.  **Avro:**
    *   В новой схеме поле `age` удалено, добавлено `age_range` с дефолтом.
    *   Writer Schema (пришла с данными): есть `age`.
    *   Reader Schema (на сервере): нет `age`, есть `age_range`.
    *   **Результат:** Успех. Поле `age` пропущено (skipped), поле `age_range` заполнено дефолтом.

3.  **Thrift:**
    *   Если поле было `required` — **Крах**.
    *   Если поле было `optional` — Сервер проигнорирует ID старого поля (так как его нет в новой структуре) и оставит новое поле пустым (`null`).
    *   **Результат:** Успех (но данные потеряны, логика должна уметь жить с `null`).

### 4.4. Вердикт Архитектора

1.  Выбирайте **Protobuf** для **внутренних микросервисов**. Экосистема gRPC, Envoy, Istio заточена под него. Скорость разработки и простота ("оно просто работает") перевешивают минусы типизации.
2.  Выбирайте **Avro** для **долговременного хранения (Data Lake)** и **Event Sourcing**. Возможность эволюционировать схему данных, записанных 5 лет назад, есть только у него (благодаря Schema Registry).
3.  Выбирайте **Thrift**, только если вы **вынуждены** (интеграция с легаси, Cassandra, HBase) или если вам критически нужны нативные `Set` и `Exceptions` в высоконагруженном RPC без HTTP/2 оверхеда.

## 5. Выбор архитектора: Decision Framework

Выбор IDL определяется четырьмя векторами: **Временная связность** (Temporal Coupling), **Управление схемой** (Governance), **Паттерн доступа** (Access Pattern) и **Экосистема**.

### Вектор 1: Синхронное взаимодействие (Service-to-Service / RPC)
*Контекст:* Вы контролируете и клиента, и сервер. Латентность критична. Данные живут миллисекунды (в памяти и на проводе).

*   **Рекомендация: Protobuf (через gRPC).**
    *   **Почему:** Экосистема Cloud Native (Kubernetes, Envoy, Istio) построена вокруг gRPC.
    *   **Киллер-фича:** HTTP/2 мультиплексирование и строгая кодогенерация.
    *   **Управление версиями:** "Мягкое". Вы можете добавить поле, и старый клиент не сломается, просто не увидит его. Здесь не нужна жесткая валидация схемы в рантайме, так как сервисы деплоятся часто и рассинхрон версий невелик.
*   **Альтернатива: Thrift.**
    *   **Когда:** Если вы работаете в экосистеме, где HTTP/2 избыточен или недоступен (например, IPC через Shared Memory, Unix Sockets с кастомным фреймингом), или вам критически нужны **нативные исключения** и сложные типы (`Set`, `Map` ключей-объектов), которых нет в Protobuf.

### Вектор 2: Асинхронное взаимодействие и Хранение (Event Streaming / Data Lake)
*Контекст:* Данные живут дольше кода. Сообщение в Kafka может быть прочитано через год. Вы не контролируете всех потребителей (Consumer Decoupling).

*   **Рекомендация: Apache Avro + Schema Registry.**
    *   **Почему:** Схема — это **контракт**, который должен проверяться *до* записи. Schema Registry запрещает Producer'у отправить данные, если они ломают совместимость с Consumers.
    *   **Киллер-фича:** `GenericRecord`.
        *   *Сценарий "ETL Nightmare":* Вам нужно написать сервис, который перекладывает данные из Kafka в S3.
        *   *С Protobuf:* Вам нужно перекомпилировать сервис каждый раз, когда меняется `.proto` любого топика (чтобы сгенерировать классы).
        *   *С Avro:* Вы пишете **один** раз код, который оперирует абстрактной структурой (Map). Он работает с любой схемой, даже той, которой не существовало на момент написания кода.
*   **Альтернатива: Protobuf + Schema Registry.**
    *   **Когда:** Если ваша компания — "Protobuf Shop". Вы хотите использовать одни и те же DTO для gRPC и для Kafka.
    *   *Риск:* Работа с `Unknown Fields` в аналитических пайплайнах (Spark/Flink) сложнее, чем в Avro.

### Вектор 3: Публичный контракт (Frontend / Public API)
*Контекст:* Клиент — браузер или сторонний разработчик. Вы не можете заставить их обновить библиотеку.

*   **Рекомендация: JSON (OpenAPI / Swagger).**
    *   **Почему:** Human-readable, нативная поддержка в JS. Бинарные форматы в браузере (gRPC-Web) создают проблемы с отладкой (Network tab в Chrome) и требуют прокси.
*   **Паттерн Staff Engineer: JSON Transcoding.**
    *   Не пишите REST контроллеры вручную.
    *   Опишите API в **Protobuf**.
    *   Используйте аннотации `google.api.http` (gRPC Gateway).
    *   Разверните **Envoy Proxy**, который автоматически конвертирует внешний JSON/HTTP1.1 во внутренний gRPC/HTTP2.
    *   *Профит:* У вас один источник истины (Proto), но удобный интерфейс для веба.

### Вектор 4: Экстремальная производительность (HFT, Gaming, Embedded)
*Контекст:* Счет идет на наносекунды. GC (Garbage Collector) — враг. Десериализация (парсинг) занимает слишком много CPU.

*   **Рекомендация: FlatBuffers / Cap’n Proto.**
    *   **Суть:** Zero-Copy Serialization (Сериализация без копирования).
    *   **Как это работает:** В отличие от Protobuf, который читает байты и создает Java/C++ объекты (аллокация), FlatBuffers строит байтовый буфер так, что поля в нем выровнены по памяти. Вы обращаетесь к `user.name()` — это просто чтение указателя в памяти буфера. Никакого парсинга.
    *   **Цена:** Ужасная эргономика разработчика (API сложный, построение сообщений трудоемкое).
    *   *Пример:* Facebook использует FlatBuffers в Android-приложении для быстрой загрузки ленты новостей (хранение данных на диске), чтобы не тратить CPU телефона на парсинг JSON/Protobuf.

### "Золотое правило" Архитектора

Не смешивайте цели.
1.  **Code-First** (Protobuf, Thrift) — для сервисов, где важен **интерфейс** (методы, аргументы).
2.  **Data-First** (Avro) — для хранилищ, где важна **структура** (колонки, типы) и возможность прочитать данные без кода писателя.

*Если вы попытаетесь использовать Avro для RPC, вы получите "тормоза" на хендшейках схем. Если вы попытаетесь использовать Protobuf для Data Lake, вы получите "кладбище тегов" и невозможность аналитики без исходников `.proto`.*

## 6. Чек-лист уровня Expert

1.  **Field Renaming:**
    Можно ли переименовать поле в `.proto` файле?
    *   *Ответ:* Да. Бинарный формат опирается только на тег. Но это сломает код, использующий JSON-mapping (где ключи — имена), и сломает исходный код клиентов (нужен рефакторинг).
2.  **Tag Recycling:**
    Почему нельзя использовать тег `id = 2`, если он был удален год назад?
    *   *Ответ:* Где-то в базе могут лежать старые записи с тегом 2, который значил `phoneNumber`. Вы ввели тег 2 как `age`. При чтении старой записи вы получите телефон в поле возраста. Используйте `reserved`.
3.  **ZigZag Encoding:**
    Почему в Protobuf `int32 = -1` занимает 10 байт, а `sint32 = -1` занимает 1 байт?
    *   *Ответ:* Обычный `int32` использует Varint и дополнение до двух. Отрицательное число выглядит как `111...111` (очень большое беззнаковое), требуя 10 байт. `sint32` использует ZigZag (`-1` -> `1`, `1` -> `2`, `-2` -> `3`), отображая знаковые числа в малые беззнаковые.

### Заключение
Идеальный IDL не тот, который быстрее, а тот, который не даст джуниору сломать продакшен изменением поля.
*   В **gRPC** это достигается удалением `required`.
*   В **Kafka** это достигается принудительной проверкой совместимости через **Schema Registry**.

Выбирайте инструмент под жизненный цикл данных, а не под удобство синтаксиса.


В Event Streaming системах данные персистентны (Retention может быть установлен на годы). Вы не можете просто "выключить старую версию API". Сообщение, записанное 3 года назад старой версией Producer, может быть прочитано завтра новым Consumer.

---

В Kafka нет понятий "Запрос" и "Ответ". Есть **Поток Событий (Stream of Events)**.
Главная аксиома архитектора: **Producer и Consumer ничего не знают друг о друге и деплоятся в разное время.**

## 1. Физика проблемы: Magic Byte и Schema ID

В "голой" Kafka нет типов. Это просто распределенный лог, хранящий массивы байтов (`byte[]`). Kafka брокеру абсолютно все равно, записали вы туда JSON, Avro, картинку PNG или случайный шум.

Чтобы построить систему эволюции данных, нам нужен **мета-протокол**, который живет *поверх* протокола Kafka. В экосистеме Confluent (и большинства Enterprise решений) стандартом является **Confluent Wire Format**.

Это соглашение о том, как именно оборачивается полезная нагрузка (Payload) перед отправкой в топик. Без этого обертывания версионирование невозможно.

### 1.1. Анатомия сообщения (Binary Layout)

Любое сообщение, сериализованное через `KafkaAvroSerializer` (или Proto/JSON Serializer с поддержкой Registry), имеет жесткую структуру первых 5 байт.

```
| Magic Byte (1 byte) | Schema ID (4 bytes) | Data Payload (N bytes) |
|---------------------|---------------------|------------------------|
| 0x00                | 0x00 00 00 2A       | ... бинарные данные ...|
```

1.  **Magic Byte (`0x00`)**:
    *   **Роль:** Маркер протокола.
    *   **Зачем нужен:** Позволяет десериализатору мгновенно понять: "Это сообщение упаковано с использованием Schema Registry или это просто мусор?". Если первый байт не `0`, стандартный десериализатор выбросит `SerializationException: Unknown magic byte!`.
    *   *История:* Пока версия всегда `0`. Зарезервировано на будущее для изменения формата заголовка.

2.  **Schema ID (4 bytes)**:
    *   **Роль:** Глобальный уникальный указатель на контракт.
    *   **Тип:** 32-битное целое число (Signed Integer) в сетевом порядке байтов (**Big Endian**).
    *   **Механика:** Это ID, который выдал **Schema Registry** при регистрации схемы. Это не версия (v1, v2), это именно ID (1, 500, 1042). Один и тот же ID гарантирует *бинарную идентичность* схемы JSON.

3.  **Data Payload**:
    *   Сами данные, сериализованные по правилам формата (Avro binary, Protobuf binary и т.д.).
    *   Важно: в Avro-payload **нет** никакой информации о типах или именах полей. Без Schema ID это просто бессмысленный набор байт.

### 1.2. Визуализация "на пальцах" (Hex Dump Example)

Представьте, что мы отправляем объект `User` с именем "Bob".
Схема Avro: `{"type":"record", "name":"User", "fields":[{"name":"name", "type":"string"}]}`.
Допустим, Schema Registry присвоил этой схеме **ID = 7**.

Как это выглядит в Wireshark или при чтении через `kafkacat -C -e`:

```hex
00 00 00 00 07 06 42 6f 62
^  ^.........^ ^...........^
|       |            |
|       |            +-- Payload (Avro)
|       +-- Schema ID = 7 (Big Endian)
+-- Magic Byte
```

Разбор Payload (`06 42 6f 62`):
*   `06`: В Avro строки кодируются как (Длина + Символы). Длина использует ZigZag-кодирование. Число 3 (длина "Bob") в ZigZag $\to$ `06`.
*   `42 6f 62`: ASCII коды 'B', 'o', 'b'.

**Вывод для архитектора:** Оверхед на версионирование составляет ровно **5 байт** на сообщение. Это ничтожно мало по сравнению с отправкой полной схемы (которая может весить 2-5 КБ) в каждом сообщении.

### 1.3. Пайплайн Сериализации (Как ID попадает в байты)

Понимание этого потока критично для отладки производительности (latency).

**Шаг 1: Producer (Write path)**
1.  Приложение вызывает `producer.send(object)`.
2.  Сериализатор берет схему этого объекта (через Reflection или из сгенерированного класса).
3.  **Local Cache Lookup:** Сериализатор проверяет свой локальный `Map<Schema, ID>`.
    *   *Hit:* ID найден. Идем к шагу 5.
    *   *Miss:* Идем к шагу 4.
4.  **Registry Registration (Network Call):** Сериализатор делает HTTP POST в Schema Registry ("Вот схема, дай ID"). Registry возвращает ID (создает новый или возвращает существующий). Сериализатор кэширует пару (Schema $\leftrightarrow$ ID).
5.  **Assembly:** Сериализатор пишет байт `0`, пишет 4 байта ID, пишет сериализованный объект.
6.  Байты улетают в Kafka.

**Шаг 2: Consumer (Read path)**
1.  Consumer вычитывает байты из Kafka.
2.  Читает первый байт. Если `0`, читает следующие 4 байта (ID).
3.  **Local Cache Lookup:** Проверяет свой `Map<ID, Schema>`.
    *   *Hit:* Схема найдена. Идем к шагу 5.
    *   *Miss:* Идем к шагу 4.
4.  **Registry Fetch (Network Call):** Делает HTTP GET в Schema Registry (`/schemas/ids/7`). Скачивает JSON схемы. Кэширует.
5.  **Deserialization:** Используя *Скачанную Схему* (Writer Schema) и *Локальную Схему Класса* (Reader Schema), выполняет Avro Resolution (эволюцию) и создает объект POJO.

### 1.4. Почему это гениально (Architectural Implications)

1.  **Decoupling во времени:** Producer записал сообщение с ID=7 и умер. Схема удалена из кода Producer'а. Через год запускается Consumer. Он видит ID=7, идет в Registry, скачивает схему и **корректно** читает данные. Данные самодостаточны, пока жив Registry.
2.  **Эффективность:** Сетевой вызов в Registry происходит **один раз** на процесс (при первом появлении схемы). Далее работает локальный кэш. Скорость сериализации близка к скорости `memcpy`.
3.  **Блокировка плохих данных:** Если вы настроили Registry на проверку совместимости, Producer физически не сможет получить ID для "плохой" схемы. Он упадет с ошибкой *до* того, как испортит данные в топике.

**Риск Staff-уровня:** Schema Registry становится **Single Point of Failure**.
*   Если Registry упал, Producers (которые еще не закэшировали ID) не могут отправлять данные.
*   Consumers (которые встретили новый ID) не могут читать данные.
*   *Решение:* Registry должен быть высокодоступным (HA Cluster) и стоять рядом с кластером Kafka.

## 2. Стратегия 1: Schema Evolution (Эволюция схемы)

Это "Золотой путь" (Happy Path) в разработке на Kafka. Идея проста: мы изменяем структуру данных, не меняя топик и не ломая существующих потребителей.

Однако, чтобы это работало, нужно понимать три концепции: **Subject**, **Compatibility Mode** и **Deployment Strategy**.

### 2.1. Концепция "Subject" (Контекст Эволюции)

Прежде чем говорить о совместимости, нужно понять: *с чем* мы сравниваем новую схему? В Schema Registry схемы группируются не по топикам (как многие думают), а по **Subjects** (Темам).

Имя Subject определяется стратегией (Naming Strategy), настроенной в Serializer:

1.  **TopicNameStrategy (Default):**
    *   Имя Subject = `topic-name-value`.
    *   *Суть:* Весь топик должен содержать данные, эволюционирующие линейно. Вы не можете положить `Order` и `User` в один топик, так как их схемы несовместимы.
2.  **RecordNameStrategy:**
    *   Имя Subject = `com.example.User` (полное имя класса).
    *   *Суть:* Схемы версионируются независимо от топика. Позволяет хранить разнородные события в одном топике.
3.  **TopicRecordNameStrategy:**
    *   Имя Subject = `topic-name-com.example.User`.

**Инсайт Архитектора:** Выбор стратегии делается *один раз*. Смена стратегии на живом топике приведет к потере связи с историей версий и поломке совместимости. Для 95% случаев используйте дефолтную **TopicNameStrategy**.

### 2.2. Матрица Совместимости (Compatibility Modes)

Режим совместимости — это **SLA**, который Producer дает Consumer'у. Он определяет, **кто должен обновиться первым**.

| Режим (Mode) | Гарантия | Кто обновляется первым? | Правила изменений схемы |
| :--- | :--- | :--- | :--- |
| **BACKWARD** (Default) | **Новый Consumer** может прочитать **Старые Данные**. | **Consumer**. Сначала деплоим читателей, потом писателей. | ✅ Удалять поля<br>✅ Добавлять **опциональные** поля (с дефолтом)<br>❌ Менять типы (int -> string)<br>❌ Добавлять обязательные поля |
| **FORWARD** | **Старый Consumer** может прочитать **Новые Данные**. | **Producer**. Сначала деплоим писателей, потом читателей. | ✅ Добавлять любые поля<br>✅ Удалять **опциональные** поля<br>❌ Удалять обязательные поля |
| **FULL** | Поддерживается и то, и другое. | **Любой порядок**. Можно деплоить вперемешку (Rolling Update). | ✅ Только добавление/удаление **опциональных** полей.<br>Самый безопасный и строгий режим. |
| **NONE** | Никаких проверок. | На свой страх и риск. | "Дикий Запад". Используется только при экспериментах. |

**Разбор нюанса BACKWARD (Почему это дефолт?):**
В большинстве компаний Consumers (аналитика, DWH, другие сервисы) — это зависимые команды. Вы не можете заставить их обновиться *до* того, как вы выкатите новую фичу в Producer.
Однако, `BACKWARD` требует, чтобы вы сначала обновили Consumer, чтобы он *знал* о новом поле? **Нет.**
`BACKWARD` совместимость означает, что если вы обновите Consumer до новой версии схемы, он *сможет* прочитать исторические данные (где нового поля еще не было), подставив `default`.
*   *Риск:* Если вы добавите поле без `default` в режиме BACKWARD, Registry отклонит схему. Почему? Потому что Consumer v2 не сможет прочитать данные v1 (там нет этого поля, и подставить нечего).

### 2.3. Транзитивность (Transitivity): Защита истории

Простая проверка (`BACKWARD`, `FORWARD`) сравнивает новую схему $N$ только с предыдущей схемой $N-1$.
Этого недостаточно для Kafka, где данные хранятся годами.

**Сценарий катастрофы (Не-транзитивная проверка):**
1.  Схема v1: `{ A }`.
2.  Схема v2 (BACKWARD): `{ A, B (default) }` — совместима с v1.
3.  Схема v3 (BACKWARD): `{ B }` (удаляем A) — совместима с v2 (так как в v2 поле A было технически необязательным для чтения B).
4.  **Проблема:** Consumer v3 пытается прочитать сообщение v1.
    *   В сообщении v1 есть только A.
    *   Схема v3 ждет B.
    *   Связи между v1 и v3 нет. Consumer падает.

**Решение: `BACKWARD_TRANSITIVE` / `FULL_TRANSITIVE`**
Registry проверяет новую схему против **всех известных версий** (v1, v2... vN).
**Правило Staff Engineer:** Для любых топиков с `retention.ms > 1 week` или Compacted Topics всегда включайте **TRANSITIVE** режим. Иначе вы потеряете доступ к истории.

### 2.4. Пример Эволюции (Avro Deep Dive)

Давайте посмотрим, как работает `FULL` совместимость на практике.

**Шаг 1. Исходное состояние (v1)**
```json
{
  "type": "record",
  "name": "Order",
  "fields": [
    {"name": "order_id", "type": "string"},
    {"name": "amount", "type": "double"}
  ]
}
```

**Шаг 2. Бизнес требует добавить поле `status`**
Мы хотим добавить статус, но старые сервисы не должны сломаться.
*   Если мы напишем `"type": "string"`, это нарушит **BACKWARD** совместимость (Consumer v2 не сможет прочитать Order v1, где статуса нет).
*   Мы обязаны добавить `default`.

**Новая схема (v2):**
```json
{
  "type": "record",
  "name": "Order",
  "fields": [
    {"name": "order_id", "type": "string"},
    {"name": "amount", "type": "double"},
    {
      "name": "status",
      "type": "string",
      "default": "CREATED" // <--- Магия совместимости
    }
  ]
}
```

**Шаг 3. Рантайм (Schema Resolution)**

*   **Сценарий А (Reader v2 читает данные v1):**
    *   В байтах v1 поля `status` нет.
    *   Reader v2 видит это, смотрит в свою схему, находит `"default": "CREATED"`.
    *   Приложение получает объект: `Order(id="...", amount=10.0, status="CREATED")`.
    *   *Результат:* Успех.

*   **Сценарий Б (Reader v1 читает данные v2):**
    *   В байтах v2 поле `status` есть.
    *   Reader v1 не знает про `status`.
    *   Согласно спецификации Avro, Reader **пропускает** (skips) лишние байты в конце записи (или между известными полями).
    *   Приложение получает объект: `Order(id="...", amount=10.0)`.
    *   *Результат:* Успех.

### 2.5. Рекомендация Архитектора

1.  **Schema Registry в CI/CD:** Не надейтесь, что разработчик проверит совместимость локально. Встройте плагин (maven/gradle/github action), который делает `schema-registry:test-compatibility` при каждом Pull Request.
2.  **Избегайте переименований:** Avro поддерживает `aliases` для переименования полей, но это хрупко. Лучше считайте, что имена полей неизменны.
3.  **Nullable vs Default:** Это разные вещи.
    *   `"type": ["null", "string"], "default": null` — поле опциональное, дефолт null.
    *   `"type": "string", "default": "unknown"` — поле обязательное (не null), но имеет дефолт.
    Оба варианта обеспечивают совместимость, но имеют разную семантику в коде (Java `Optional<String>` vs `String`). Выбирайте осознанно.

## 3. Стратегия 2: Topic Versioning (Nuclear Option)

**Topic Versioning** — это паттерн миграции, при котором мы создаем физически новый топик (`orders.v2`) для новой структуры данных, параллельно существующий со старым (`orders.v1`).

### 3.1. Триггеры: Когда это неизбежно?

Вы обязаны использовать этот метод, если изменения **не транзитивны**:
1.  **Смена типа данных:** `id: Long` $\to$ `id: UUID (String)`. Avro/Protobuf не умеют конвертировать это автоматически.
2.  **Рефакторинг иерархии:** Плоская структура превращается во вложенную.
    *   Было: `{"user_address": "NY"}`
    *   Стало: `{"address": {"city": "NY"}}`
3.  **Смена ключа партиционирования (Rekeying):**
    *   Было: Key = `OrderId`.
    *   Стало: Key = `UserId`.
    *   *Последствие:* События перераспределятся по другим партициям. Порядок для конкретного `OrderId` больше не гарантирован относительно `UserId`. Это требует физического перекладывания данных.

---

### 3.2. Архитектурный паттерн: The Stream Bridge (Мост)

Наивная идея "пусть Producer пишет сразу в два топика" (Dual Write) — это **антипаттерн**.
*   *Почему:* Нет транзакционности между записью в топик A и топик B (если транзакции Kafka не включены). Producer усложняется. Обработка ошибок превращается в ад.

**Правильный подход: The Replicator / Bridge.**

1.  **Producer:** Продолжает писать в `v1`. Никаких изменений кода пока нет.
2.  **Stream Bridge (Kafka Streams / Flink):**
    *   Читает `v1`.
    *   Десериализует (Schema v1).
    *   Трансформирует объект (Map: `Long` $\to$ `String`, обогащение данных).
    *   Пишет в `v2` (Сериализация Schema v2).
3.  **Consumer:** Начинает читать из `v2`.

---

### 3.3. Операционный Playbook (План Миграции)

Миграция — это процесс во времени, занимающий дни или недели.

#### Фаза 1: Подготовка инфраструктуры (Hydration)
Создаем топик `orders.v2`.
*   **Важно:** Количество партиций в `v2` должно совпадать с `v1` (если не меняется ключ партиционирования), чтобы сохранить семантику порядка.
*   Запускаем **Stream Bridge**. Он начинает вычитывать `v1` с `auto.offset.reset = earliest` (с начала времен).
*   *Результат:* Топик `v2` наполняется историческими данными в новом формате. Лаг Бриджа постепенно снижается до 0.

#### Фаза 2: Миграция Потребителей (Consumer Switch)
Здесь лежит главная проблема: **Потеря Оффсетов**.
Оффсет `10500` в топике `v1` не соответствует оффсету `10500` в `v2` (из-за фильтрации или разного размера сжатия).

**Стратегия А: "Big Bang" (Остановка мира)**
1.  Остановить всех Consumers v1. Зафиксировать время/состояние.
2.  Запустить Consumers v2 с настройкой `auto.offset.reset = latest` (если нас интересуют только новые события) или `earliest` (если нужна история).
    *   *Риск:* При `earliest` будет дублирование обработки (re-processing) всей истории. Консьюмер должен быть **идемпотентным**.

**Стратегия Б: "Synthetic Offset" (Сложная)**
Бридж может писать в заголовки сообщения `v2` исходный оффсет из `v1`. Consumer может использовать это для дедупликации, но Kafka не поддерживает это нативно для коммита.

**Стратегия В: Blue-Green Deployment**
Запускаем Consumer v2 параллельно с v1. Consumer v2 работает в режиме "Shadow Mode" (обрабатывает, но не шлет письма/не пишет в БД, или пишет в теневую таблицу), чтобы прогреть кэши и проверить логику.

#### Фаза 3: Переключение Источника (Producer Cutover)
Когда Consumers v2 работают стабильно:
1.  Деплоим новую версию Producer, которая пишет **напрямую** в `v2`.
2.  Останавливаем **Stream Bridge**.
    *   *Нюанс:* В этот момент нужно быть очень осторожным с порядком. Если Бридж отставал, а Продюсер начал писать, в `v2` могут нарушиться таймстампы. Обычно Бридж останавливают *после* того, как он дочитал все сообщения из `v1` (Drain).

#### Фаза 4: Зачистка (Cleanup)
Удаляем топик `v1` и старые схемы из Registry. (Обычно через 2-4 недели после завершения).

---

### 3.4. Особый случай: Compacted Topics (KTable)

Если ваш топик — это состояние (Log Compaction включен, `cleanup.policy=compact`), стратегия "Topic Versioning" становится единственно возможной.

**Почему:**
В Compacted Topic важен только *последний* оффсет для каждого ключа.
При миграции `v1` -> `v2` через Бридж вы фактически выполняете **полную репликацию состояния** (State Store Regeneration).

*   В `v2` попадут только актуальные значения ключей (если Бридж достаточно умен, чтобы игнорировать старые версии, или если Compaction в `v2` сработает быстро).
*   Это отличный шанс "почистить" данные (убрать мусорные ключи, отфильтровать tombstones).

---

### 3.5. Экономика решения (Trade-offs)

Как Staff Engineer, вы должны обосновать стоимость этого решения бизнесу.

1.  **Storage Cost (x2):** Во время миграции вы храните копию всех данных. Если это Петабайты, это дорого.
2.  **Compute Cost:** Сериализация/Десериализация в Бридже потребляет CPU.
3.  **Latency:** Бридж добавляет задержку (обычно < 100мс, но при нагрузке может расти).
4.  **Complexity:** Вы управляете двумя потоками данных. Мониторинг должен покрывать оба топика.

**Вердикт:**
Используйте Topic Versioning только для **Major** релизов (раз в 1-2 года), когда накапливается критическая масса технического долга в структуре данных. Для всего остального боритесь за **Schema Evolution** (BACKWARD/FORWARD).

---
## 4. Стратегия 3: Multi-Schema Topics (Record Name Strategy)

**Контекст:** Обычно в Kafka действует правило "Один топик — Один тип события" (Homogeneous Topics). Топик `users` содержит только `User`, топик `clicks` — только `Click`.
Однако, в сложных бизнес-процессах (E-commerce, FinTech) сущность проходит через цепочку состояний: `OrderCreated` $\to$ `OrderPaid` $\to$ `OrderShipped`.

**Проблема раздельных топиков:**
Если `OrderCreated` летит в Топик А, а `OrderPaid` в Топик Б:
1.  Вы теряете гарантию глобального порядка. Consumer может прочитать "Оплачено" раньше, чем "Создано" (Race Condition), просто потому что в Топике Б меньше лаг.
2.  Вы теряете транзакционность (Kafka Transactions), если хотите атомарно обработать цепочку.

**Решение:** Складывать **все** события, относящиеся к одной сущности (Aggregation Root), в **один** топик (например, `order-events`), используя один и тот же Partition Key (`orderId`).

---
### 4.1. Механика: RecordNameStrategy

Как положить разные объекты (Avro Records) в один топик, если Schema Registry по умолчанию требует одну схему? Мы меняем стратегию именования "Subjects" (тем) в реестре.

По умолчанию (`TopicNameStrategy`) Registry ожидает, что для топика `order-events` схема будет лежать под именем `order-events-value`.

При `RecordNameStrategy` имя Subject отвязывается от имени топика и привязывается к **Namespace + Name** самого Avro-рекорда.

*   Событие 1: Record `com.example.OrderCreated`.
    *   Serializer регистрирует схему под именем: `com.example.OrderCreated`.
    *   Kafka сообщение: `[Magic][ID=10][Payload]`.
*   Событие 2: Record `com.example.OrderPaid`.
    *   Serializer регистрирует схему под именем: `com.example.OrderPaid`.
    *   Kafka сообщение: `[Magic][ID=11][Payload]`.

**Инсайт Архитектора:** В Schema Registry теперь живут независимые ветки эволюции. `OrderCreated` может быть версии 5, а `OrderPaid` версии 1. Они не конфликтуют друг с другом, хотя лежат в одном физическом топике Kafka.

---
### 4.2. Полиморфная Десериализация (Consumer-side Polymorphism)

Самая сложная часть — научить Consumer понимать этот "салат" из событий.

**Сценарий:** Вы используете Java и Avro.
Если вы используете `KafkaAvroDeserializer` с дефолтными настройками, он вернет вам `GenericRecord` (аналог `Map`). Работать с этим неудобно и типо-небезопасно.

Нам нужна **Strong Typing**: чтобы десериализатор возвращал POJO классы `OrderCreated`, `OrderPaid`.

**Конфигурация Consumer:**
```properties
key.deserializer=io.confluent.kafka.serializers.KafkaAvroDeserializer
value.deserializer=io.confluent.kafka.serializers.KafkaAvroDeserializer
# КРИТИЧЕСКИ ВАЖНО:
value.deserializer.specific.avro.reader=true
```

**Код обработки (Pattern Matching):**
```java
while (true) {
    ConsumerRecords<String, Object> records = consumer.poll(Duration.ofMillis(100));
    for (ConsumerRecord<String, Object> record : records) {
        Object event = record.value();

        // Java 17+ Pattern Matching for switch - идеально подходит
        switch (event) {
            case OrderCreated c -> handleCreate(c);
            case OrderPaid p    -> handlePay(p);
            case OrderShipped s -> handleShip(s);
            default -> log.warn("Unknown event type: {}", event.getClass());
        }
    }
}
```

### 4.3. TopicRecordNameStrategy (Гибридный подход)

Существует третий, более редкий вариант: `TopicRecordNameStrategy`.
Имя Subject строится как: `topic-name` + `record-name`.
Пример: `order-events-com.example.OrderCreated`.

**Зачем это нужно?**
Если у вас есть событие `UserUpdated`, и оно используется в топике `auth-events` и в топике `marketing-events`, но вы хотите, чтобы схема в маркетинге могла эволюционировать *отдельно* от схемы в авторизации.
*   `RecordNameStrategy` заставит их иметь одну общую глобальную схему.
*   `TopicRecordNameStrategy` позволит иметь две независимые схемы для одного класса в разных топиках.

---
### 4.4. Риски и Trade-offs (Staff Engineer Analysis)

Использование гетерогенных топиков имеет высокую цену.

1.  **Проблема "Неизвестного типа" (Unknown Type Exception):**
    *   Producer выкатил новый тип события `OrderRefunded`.
    *   Consumer еще не обновился (у него нет скомпилированного класса `OrderRefunded`).
    *   При десериализации с `specific.avro.reader=true`, Consumer упадет с `ClassCastException` или `AvroTypeException`, так как не сможет найти класс для Schema ID.
    *   *Решение:* Consumer должен быть устойчив к неизвестным типам (try-catch в десериализации) или использовать `GenericRecord` как fallback.

2.  **Мониторинг Лага (Consumer Lag):**
    *   Kafka метрики показывают лаг *на партицию*.
    *   Вы не узнаете, что у вас отстает обработка именно `OrderPaid`, а `OrderCreated` летает. Все смешано в одну кучу.

3.  **Schema Registry Explosion:**
    *   Количество Subjects в реестре растет линейно с количеством типов событий. Управлять правами доступа (ACL) к сотням схем сложнее, чем к десятку топиков.

### 4.5. Вердикт

Используйте **Multi-Schema Topics (RecordNameStrategy)**, если:
1.  Вы строите систему **Event Sourcing**.
2.  Вам критически важен **порядок обработки** событий разного типа (Happens-Before relationship).
3.  События логически связаны одним **Aggregate ID** (Partition Key).

Во всех остальных случаях (например, просто "свалка логов") предпочитайте **TopicNameStrategy** (один топик — одна схема) для простоты эксплуатации.

## 5. Операционные паттерны защиты (Defense Patterns)

На уровне Staff Engineer вы должны понимать: Kafka — это **Log**, а не Queue. В очереди (RabbitMQ) "плохое" сообщение можно просто не подтвердить (NACK), и оно уйдет в конец или DLQ. В Логе (Kafka) вы **не можете пропустить сообщение**, не сдвинув оффсет. Если вы не можете прочитать оффсет $N$, вы никогда не прочитаете $N+1$. Партиция встает колом.

---

Ошибки версионирования (несовместимая схема, битый Magic Byte, неизвестный класс) возникают на этапе **Десериализации**. Это происходит *до* того, как ваша бизнес-логика получит управление. Если стандартный десериализатор падает, он убивает поток Consumer'а.

### 5.1. The Poison Pill (Ядовитая пилюля)

**Определение:** Сообщение, которое детерминированно вызывает крах Consumer'а при попытке его прочитать.

**Физика сбоя (Death Loop):**
1.  Consumer запрашивает пакет (`poll`). Kafka отдает сообщение с оффсетом `100`.
2.  Внутри `poll()` вызывается десериализатор.
3.  Десериализатор бросает `SerializationException` (например, "Unknown Schema ID 999").
4.  Поток Consumer'а падает (Crash).
5.  Kubernetes/SupervisorD перезапускает под.
6.  Новый Consumer поднимается, читает committed offset. Это `99` (так как `100` не был обработан).
7.  Kafka снова отдает сообщение `100`.
8.  **GOTO 1.**

**Результат:** Lag партиции растет до бесконечности. Обработка валидных сообщений `101, 102...` заблокирована.

---

### 5.2. Стратегия 1: Safe Deserialization (Обертка-подушка)

Никогда не используйте "голые" десериализаторы (напр. `KafkaAvroDeserializer`) в продакшене напрямую как класс. Они не умеют обрабатывать ошибки.

Используйте паттерн **Error Handling Deserializer**. Это прокси, который ловит исключение и передает его в приложение *вместо* данных.

**Реализация (Spring Kafka):**
Spring предоставляет `ErrorHandlingDeserializer`.
```properties
# Конфигурация Consumer
value.deserializer=org.springframework.kafka.support.serializer.ErrorHandlingDeserializer
# Настоящий десериализатор прячется внутри:
spring.deserializer.value.delegate.class=io.confluent.kafka.serializers.KafkaAvroDeserializer
```

**Механика:**
1.  Если `Delegate` падает, `ErrorHandlingDeserializer` **не роняет** `poll()`.
2.  Вместо этого он возвращает `null` (или специальный объект-маркер) и кладет Exception в заголовок Kafka-сообщения (в памяти).
3.  Ваш `Listener` получает управление, видит ошибку и может принять решение: скинуть в DLQ или залогировать.

---

### 5.3. Стратегия 2: Dead Letter Queue (DLQ) для сырых байтов

Если сообщение нельзя десериализовать, вы не можете переслать его в другой топик как *объект* (у вас его нет). Вы должны переслать его как *массив байт*.

**Архитектура DLQ:**
1.  **Main Topic:** `orders.v1`.
2.  **DLQ Topic:** `orders.v1.dlq`. Важно: у DLQ не должно быть схемы (или схема `bytes`), чтобы принять любой мусор.

**Алгоритм (Recovery Path):**
1.  Ловим `SerializationException`.
2.  Извлекаем **сырые байты** сообщения из буфера ConsumerRecord.
3.  Добавляем хедеры с метаданными ошибки:
    *   `exception.message`: "Unknown magic byte"
    *   `exception.stacktrace`: ...
    *   `original.topic`: "orders.v1"
    *   `original.offset`: "100"
4.  Публикуем байты в DLQ.
5.  **Commit Offset 100.** (Самый важный шаг! Мы пропускаем яд, чтобы разблокировать партицию).

**Инструментарий:**
В Kafka Streams это делается через `default.deserialization.exception.handler = SendToDlqProductionExceptionHandler` (доступно в новых версиях) или кастомный код.

---

### 5.4. Стратегия 3: Schema Registry Resilience (Кэширование)

Schema Registry — это **Single Point of Failure (SPOF)**. Если он недоступен, Consumers не могут скачивать новые ID схем.

**Миф:** "Если Registry упадет, Kafka встанет".
**Реальность:** Сериализаторы и Десериализаторы имеют **локальный кэш** (LRU Map).

*   Если Producer уже отправлял схему X — ID лежит в кэше. Registry не нужен.
*   Если Consumer уже читал схему X — схема лежит в кэше. Registry не нужен.

**Риск Staff-уровня:**
Проблема возникает при **Cold Start** (холодном старте) или **New Deployment** во время падения Registry.
1.  Вы выкатили новый под. Кэш пуст.
2.  Пришло сообщение с ID=50.
3.  Consumer стучится в Registry $\to$ Timeout.
4.  Consumer падает.

**Рекомендация Архитектора:**
1.  Относитесь к Schema Registry как к Tier-0 сервису (High Availability). Минимум 2 ноды.
2.  Настройте алерты на метрику `request_error_rate` клиента Registry.

---

### 5.5. Стратегия 4: The "Headers First" Approach (Бедная альтернатива)

Если вы работаете в среде, где Schema Registry внедрить невозможно (политика безопасности, легаси), используйте **Kafka Headers** для версионирования.

Это позволяет реализовать **Polymorphic Routing** без инспекции пейлоада.

**Механика:**
Producer добавляет заголовок: `Content-Schema-Version: v2`.

**Consumer Router:**
```java
// Псевдокод роутера
String version = record.headers().lastHeader("Content-Schema-Version").value();

if ("v2".equals(version)) {
    parserV2.parse(record.value());
} else if ("v1".equals(version)) {
    parserV1.parse(record.value());
} else {
    sendToDLQ(record, "Unknown version");
}
```

**Плюс:** Дешево, не требует инфраструктуры.
**Минус:** Нет гарантий (Producer может забыть заголовок или прислать `v2` с телом от `v1`). Это перекладывает ответственность за валидацию контрактов с инфраструктуры на код разработчиков.

### Резюме раздела

1.  **Blocker vs Skipper:** Решите, что важнее — консистентность (остановить партицию при ошибке) или доступность (скинуть в DLQ и продолжить). Для финансовых транзакций — Stop. Для кликстрима/логов — Skip/DLQ.
2.  **Raw Bytes DLQ:** DLQ для ошибок сериализации должен принимать `byte[]`. Не пытайтесь писать туда объекты Avro.
3.  **Observability:** Настройте алерт на скорость роста DLQ (`rate(kafka_topic_messages_in_total{topic=".*dlq"}) > 0`). Если DLQ растет — это пожар, требующий вмешательства, даже если основной пайплайн формально "зеленый".

---
## Резюме раздела 

1.  **Schema Registry** — обязательный компонент продакшн-системы. Без него Kafka превращается в помойку неструктурированных байт.
2.  **Transitive Compatibility** — включайте этот режим, если вы планируете хранить данные дольше недели. Он гарантирует, что вы сможете прочитать историю.
3.  **Topic Versioning** — используйте только для радикальных изменений бизнес-логики. Это дорого и сложно.
4.  **DLQ** — обязательная страховка от ошибок версионирования. Без DLQ один баг в схеме остановит весь пайплайн.

**TL;DR**: CDC вычитывает журнал транзакций БД (WAL/Binlog) и стримит каждое изменение (`INSERT`, `UPDATE`, `DELETE`) как событие. Самый надежный паттерн интеграции — **Transactional Outbox** через CDC (Log-based), так как он гарантирует атомарность изменения состояния и отправки события. Главный риск — влияние на Master-БД (WAL retention).

## 1. Механика Change Data Capture (CDC): Глубокое погружение

**Определение эксперта**: CDC — это архитектурный паттерн, который идентифицирует и захватывает изменения данных в источнике (Source DB) и доставляет их в целевые системы (Target) в реальном времени, сохраняя **порядок транзакций** и **атомарность изменений**.

В отличие от ETL (выгрузки батчами), CDC превращает БД в **поток событий** (Stream of Events), позволяя реагировать на изменение состояния (State Transition) в момент его возникновения.

### 1.1. Query-Based (Polling) vs Log-Based (Transaction Mining)

Это фундаментальная дихотомия интеграции данных.

#### A. Query-Based CDC (Polling / JDBC Source)
**Принцип**: Внешний процесс (Kafka Connect JDBC Source, кастомный скрипт) периодически выполняет SQL-запрос вида:
```sql
SELECT * FROM orders 
WHERE updated_at > :last_read_timestamp 
ORDER BY updated_at ASC 
LIMIT 1000;
```

**Почему эксперт считает это антипаттерном для CDC:**

1.  **The "Invisible Delete" Problem (Проблема невидимого удаления)**
    *   *Суть*: Если строка физически удалена (`DELETE FROM orders WHERE id=1`), поллер её не увидит. У него нет критерия для выборки "отсутствующих" строк.
    *   *Костыль*: Внедрение **Soft Deletes** (`is_deleted = true`). Это протечка абстракций: архитектурное требование репликации заставляет менять схему БД и переписывать *все* запросы приложения (`WHERE is_deleted = false`).

2.  **The "Commit Race Condition" (Гонка коммитов)** — *Самый неочевидный баг*.
    *   *Сценарий*:
        *   **T1 (12:00:01)**: Начинается долгая транзакция. Она вставляет строку с `updated_at = 12:00:01`. Но *не коммитится*.
        *   **T2 (12:00:02)**: Начинается быстрая транзакция. Вставляет строку с `updated_at = 12:00:02`. *Коммитится сразу*.
        *   **Poller (12:00:03)**: Читает `WHERE updated_at > 12:00:00`. Он видит только строку от T2 (из-за Read Committed isolation). Строку от T1 он не видит.
        *   **Poller** сохраняет курсор (оффсет): `last_read = 12:00:02`.
        *   **T1 (12:00:04)**: Транзакция наконец *коммитится*. Строка появляется в БД, но её `updated_at` (12:00:01) *меньше* текущего курсора поллера (12:00:02).
    *   *Результат*: **Silent Data Loss**. Строка от T1 никогда не попадет в Kafka.
    *   *Костыль*: Делать выборку с задержкой/перекрытием (lag), что создает дубликаты.

3.  **No "Before" State (Отсутствие дельты)**
    *   Поллер видит только *текущее* состояние строки на момент выборки.
    *   Если поле `status` менялось `NEW` -> `PROCESSING` -> `SHIPPED` между двумя тиками поллера, вы увидите только `NEW` -> `SHIPPED`.
    *   Вы не знаете *предыдущего* значения, поэтому не можете реализовать логику: *"Если статус изменился, отправь уведомление, но если изменилось только описание — игнорируй"*.

4.  **Database Pressure (Нагрузка на БД)**
    *   Частый поллинг (каждые 100мс) не дает базе "спать", забивая кэши и CPU. Редкий поллинг (каждые 5 мин) увеличивает латентность. Вы всегда в проигрыше.

---

#### B. Log-Based CDC (Transaction Mining)
**Определение**: Transaction Mining — это процесс извлечения изменений данных путем парсинга **журнала упреждающей записи** (Write-Ahead Log / Redo Log), который СУБД использует для обеспечения ACID (Durability) и репликации.

**Принцип**: Мы подключаемся к БД как **фиктивная реплика** (Fake Replica). СУБД сама стримит нам изменения по мере их фиксации на диск.

**Архитектурные преимущества (Expert Level):**

1.  **Completeness & Order (Полнота и Порядок)**
    *   В лог транзакций попадает **всё**, что меняет состояние данных.
    *   `INSERT`, `UPDATE`, `DELETE`, `TRUNCATE` и (в некоторых БД) DDL (`ALTER TABLE`).
    *   Порядок событий в стриме строго соответствует порядку коммитов (Commit Order). Проблема "Гонки коммитов" исключена физически.

2.  **No Polling Interval (Push Model)**
    *   События приходят в Real-time. Задержка (Latency) определяется только скоростью записи на диск и сетью. Обычно это миллисекунды.

3.  **Metadata Richness (Богатые метаданные)**
    *   Событие Log-Based CDC содержит не только данные, но и контекст:
        *   **Transaction ID**: Позволяет сгруппировать события, произошедшие в одной транзакции (например, `OrderCreated` и `LineItemAdded`).
        *   **Timestamp**: Точное время коммита.
        *   **Actor**: (В некоторых БД) Имя пользователя, выполнившего транзакцию.

4.  **State Diffs (Before/After Image)**
    *   Главное оружие для Event-Driven систем.
    *   Мы получаем **Pre-image** (значение до update) и **Post-image** (значение после).
    *   *Пример*: `UPDATE users SET email='new@mail.com'`.
        *   Event: `before: {email: 'old@mail.com'}, after: {email: 'new@mail.com'}`.
    *   Это позволяет строить идемпотентные обработчики и вычислять дельты на лету.

5.  **Decoupling (Развязка)**
    *   Чтение логов (обычно последовательное чтение файла) создает минимальную нагрузку на движок запросов БД. Вы не конкурируете с бизнес-транзакциями за блокировки строк (Row Locks) или индексы.

### Сравнительная матрица для принятия решений

| Характеристика | Query-Based (JDBC) | Log-Based (Debezium/CDC) |
| :--- | :--- | :--- |
| **Источник данных** | Таблицы (SQL Layer) | WAL / Binlog (Storage Layer) |
| **Захват DELETE** | Нет (требует Soft Delete) | **Да** (нативно) |
| **Задержка (Latency)** | Высокая (ограничена интервалом) | **Низкая** (Real-time) |
| **Влияние на БД** | Высокое (Polling scans) | Низкое (Sequential Read) |
| **Надежность** | Риск потери данных (Race condition) | **Гарантированная доставка** |
| **Сложность настройки** | Низкая (просто SQL) | Высокая (права админа, конфиг слотов) |
| **Доступ к "Old Value"** | Нет | **Да** |

### Пример из жизни: "Потерянный чек"

Представьте систему лояльности, которая начисляет баллы.

*   **Сценарий с Query-Based**:
    1.  Пользователь делает заказ (Status: PAID).
    2.  Через 10 мс он отменяет заказ (Status: CANCELLED).
    3.  Поллер запускается через 1 секунду. Он видит `updated_at` последней записи. Статус `CANCELLED`.
    4.  **Результат**: Система лояльности видит только "Отмену". Она не знает, что заказ *был* оплачен. Она не начисляет и не списывает баллы. История искажена.

*   **Сценарий с Log-Based**:
    1.  В логе записана транзакция T1: `UPDATE status='PAID'`.
    2.  В логе записана транзакция T2: `UPDATE status='CANCELLED'`.
    3.  Kafka получает **два** события.
    4.  **Результат**: Система лояльности сначала начисляет баллы (по T1), потом списывает их (по T2). Аудиторский след корректен.

**Вердикт Эксперта**:
В 2025 году **Query-Based CDC является техническим долгом** с момента внедрения. Используйте его только для legacy-баз данных, к которым нет админского доступа для настройки репликации, или для View/Materialized Views, у которых нет своего лога транзакций. Во всех остальных случаях — **только Log-Based**.

### 1.2. Реализация в PostgreSQL: Logical Decoding

**Logical Decoding** — это механизм PostgreSQL, позволяющий транслировать физические изменения страниц данных (хранящиеся в WAL) в поток логических изменений (кортежей), понятных внешним потребителям.

В отличие от физической репликации (Physical Streaming Replication), которая копирует байты "как есть" (Block-level) и требует бинарной идентичности версий сервера, логическая репликация работает на уровне абстракции строк (Tuple-level) и позволяет выбирать конкретные таблицы (`Publication`) и даже фильтровать строки (`WHERE` clause в PG 15+).

#### 1.2.1. Инфраструктура: WAL и Слот Репликации

1.  **WAL (Write-Ahead Log)**:
    *   Это "журнал правды". Любая транзакция сначала пишется в WAL (append-only), и только потом данные сбрасываются в кучу (Heap) и индексы.
    *   **Wal Level**: Для работы CDC параметр `wal_level` должен быть установлен в `logical`. Это заставляет Postgres писать в журнал дополнительную информацию, необходимую для реконструкции кортежа (например, идентификаторы строк). *Требует перезагрузки сервера!*

2.  **Replication Slot (Слот репликации)**:
    *   *Определение*: Механизм координации, который гарантирует, что Postgres не удалит старые сегменты WAL, пока они не будут вычитаны потребителем.
    *   *Физика*: Слот хранит `restart_lsn` — адрес самой старой записи WAL, которая нужна потребителю.
    *   **Главный риск (The Disk Fill Hazard)**:
        Если Debezium (Kafka Connect) падает и не возвращается, слот остается активным. `restart_lsn` замирает. Postgres продолжает генерировать новый WAL под нагрузкой, но **не может удалить старый** (так как слот его "держит").
        *   *Итог*: Диск переполняется (`pg_wal` directory). Postgres аварийно останавливается (`PANIC`). Запустить его нельзя, пока вы не удалите файлы вручную (очень рискованно) или не расширите диск.
    *   **Expert Mitigation**: Настройка `max_slot_wal_keep_size` (введена в Postgres 13). Она позволяет Postgres убить слот (и потерять репликацию), если объем накопленного WAL превысит лимит. Лучше сломать CDC, чем убить Мастер.

#### 1.2.2. Плагин декодирования (Output Plugin)

Слот репликации всегда ассоциирован с плагином. Плагин отвечает за формат данных.

*   **wal2json / decoderbufs**:
    *   Сторонние плагины. Ранее были популярны, так как выдавали читаемый JSON/Protobuf.
    *   *Проблемы*: Требуют установки библиотек на сервер БД (нужен root). Сериализация в JSON на стороне БД — это огромный оверхед на CPU.
*   **pgoutput (The Standard)**:
    *   Встроенный плагин (начиная с PG 10). Используется для Native Logical Replication.
    *   Debezium теперь по умолчанию использует именно его.
    *   *Плюсы*: Бинарный протокол (очень быстрый), не требует установки доп. софта, поддерживает новые фичи (например, streaming of large transactions).

#### 1.2.3. Replica Identity (Идентификация строк)

Как приемник узнает, какую строку нужно обновить или удалить?

*   `UPDATE users SET name='Alice' WHERE id=1;`

Postgres должен записать в WAL информацию, позволяющую найти строку с `id=1`. Это регулируется настройкой `REPLICA IDENTITY` на уровне таблицы.

1.  **DEFAULT (Primary Key)**:
    *   В событие `UPDATE/DELETE` попадает только Primary Key (старое значение) и новые значения измененных колонок.
    *   *Минус*: Если вы меняете сам Primary Key, это сложно отследить (Debezium эмулирует это как `DELETE` старого + `CREATE` нового).
2.  **FULL (Все колонки)**:
    *   В событие попадают **все** колонки строки (и старое состояние `before`, и новое `after`).
    *   *Зачем нужно*:
        *   Если у таблицы нет PK.
        *   Если вам нужно знать старое состояние *неключевых* полей (например, для аудита: "какой был email до изменения?").
        *   Если вы используете таблицу как источник для Event Sourcing.
    *   *Цена*: **Write Amplification**. При обновлении 1 байта в WAL пишется вся строка. Если строка весит 10КБ, вы получаете x1000 оверхед на I/O.

#### 1.2.4. Проблема TOAST (The TOAST Trap)

В Postgres большие данные (тексты > 2КБ, JSONB, BLOB) хранятся в отдельных TOAST-таблицах.
В основной таблице лежит лишь ссылка (Chunk ID).

*   **Оптимизация Postgres**: Если операция `UPDATE` не затрагивает TOAST-колонку, Postgres **не пишет** её значение в WAL (экономия места).
*   **Результат для CDC**:
    *   Вы делаете `UPDATE users SET status='Active'`. (Поле `bio` весом 1МБ не меняется).
    *   Debezium получает событие. Поле `status` = 'Active'. Поле `bio` = `null` (или специальный маркер "unchanged").
*   **Риск**: Если вы перекладываете это событие в Kafka, а потом в DWH (ClickHouse), вы затрете поле `bio` нулем. Данные повреждены.
*   **Решение**:
    *   Либо `REPLICA IDENTITY FULL` (заставляет распаковывать TOAST в WAL каждый раз — очень дорого).
    *   Либо использовать SMT в Kafka Connect, который умеет мержить патчи, но это ненадежно.
    *   Либо учитывать семантику "unchanged" на потребителе.

#### 1.2.5. LSN (Log Sequence Number) и Consistency

LSN — это 64-битный адрес байта в WAL файле (например, `16/B374D848`).

*   **Debezium Offset**: Debezium не использует Kafka-оффсеты для управления чтением. Он использует LSN.
*   Kafka Connect периодически сохраняет LSN последнего обработанного события.
*   При рестарте Debezium говорит Postgres: "Дай мне стрим, начиная с LSN X".
*   **Точка согласованности**: Все события с LSN < X гарантированно обработаны.

### Пример конфигурации (Expert Configuration)

Для запуска промышленного CDC на Postgres вам нужно выполнить следующее:

```sql
-- 1. На мастере (postgresql.conf)
wal_level = logical
max_replication_slots = 10 -- Больше, чем планируете коннекторов
max_wal_senders = 10
max_slot_wal_keep_size = 50GB -- Защита от переполнения диска! (PG 13+)

-- 2. Создание пользователя с правами репликации
CREATE ROLE cdc_user WITH REPLICATION LOGIN PASSWORD 'secret';
GRANT SELECT ON ALL TABLES IN SCHEMA public TO cdc_user;

-- 3. (Опционально, но рекомендуется) Создание публикации
-- Вместо того чтобы Debezium слушал всё, явно укажите таблицы.
CREATE PUBLICATION dbz_publication FOR TABLE orders, order_lines;
```

**Инсайт**: Использование `CREATE PUBLICATION` (PG Native features) предпочтительнее, чем фильтрация таблиц на стороне Debezium (`table.include.list`). Фильтрация на стороне БД снижает нагрузку на сеть и процессор коннектора, так как "мусорные" данные даже не покидают Postgres.

### 1.3. Реализация в MySQL: Binary Log (Binlog)

В MySQL CDC работает через притворный Slave. Debezium подключается к MySQL, притворяясь другой MySQL-репликой.

1.  **Binlog Formats**:
    *   `STATEMENT`: Пишет SQL запросы (`UPDATE users SET ...`). **Бесполезен для CDC** (недетерминирован, `NOW()` и `UUID()` дадут разные значения).
    *   `ROW`: Пишет изменения конкретных строк. **Единственно верный выбор** для CDC.
2.  **GTID (Global Transaction ID)**:
    *   Уникальный ID транзакции, сохраняющийся при фейловере (failover) мастера.
    *   **Expert Requirement**: Debezium обязан использовать GTID. Если вы используете позицию файла бинлога (`mysql-bin.00001`, pos `154`), то при переключении мастера на слейв (где имена файлов другие) CDC сломается и вы потеряете данные.
3.  **binlog_row_image**:
    *   Должен быть установлен в `FULL`. Иначе при `UPDATE name='X'` вы получите событие только с полем `name` и ID, без остальных полей (email, phone). Это сломает построение проекций в Sink-системах.

### 1.4. Архитектура Debezium (Debezium Internals): Анатомия Движка

Debezium — это набор Source-коннекторов для фреймворка **Apache Kafka Connect**. Он работает внутри JVM-процесса Kafka Connect Worker.

#### 1.4.1. Runtime Model: Connector vs Task
В терминологии Kafka Connect есть два уровня абстракции:

1.  **Source Connector**:
    *   Управляющий компонент. Он стартует, читает конфигурацию, проверяет доступность БД и решает, сколько задач (Tasks) запустить.
    *   Для CDC коннекторов (Postgres, MySQL, SQL Server) `tasks.max` всегда равно **1**.
    *   **Почему 1?** Журнал транзакций (WAL/Binlog) — это **строго последовательный поток**. Его нельзя читать параллельно. Вы не можете отдать LSN 100-200 одному потоку, а LSN 201-300 другому, так как транзакция может начаться в первом диапазоне и закончиться во втором.
    *   *Следствие*: Debezium — это **Single Threaded** решение на каждый инстанс БД. Вертикальное масштабирование (CPU Core speed) здесь важнее горизонтального.

2.  **Source Task**:
    *   Рабочая лошадка. Именно этот поток держит открытое соединение с БД (Replication Connection) и бесконечный цикл чтения лога.
    *   Он формирует объекты `SourceRecord` и складывает их во внутреннюю очередь Kafka Connect.

#### 1.4.2. Schema History Topic (Память о прошлом)
Это критический компонент, уникальный для Debezium (особенно для MySQL/SQL Server).

*   **Проблема**: Бинарный лог (Binlog) содержит "сырые" значения данных, но часто не содержит метаданных схемы.
    *   Пример: В бинлоге написано "Колонка 3 = 'Active'". Но как называлась колонка 3 в прошлый вторник? `status` или `state`? А какой у неё был тип?
*   **Решение**: Debezium перехватывает все DDL-команды (`CREATE TABLE`, `ALTER TABLE`), которые проходят через лог, и записывает их в специальный топик Kafka — **Schema History Topic**.
*   **Механизм восстановления (Startup Sequence)**:
    1.  Коннектор стартует.
    2.  Подключается к Schema History Topic.
    3.  Вычитывает **весь топик** с начала времен (от offset 0).
    4.  Воспроизводит DDL-команды в памяти, воссоздавая точную структуру таблиц на каждый момент времени.
    5.  Только после этого начинает читать Binlog/WAL.
*   **Expert Warning**: Если Schema History Topic удален или его Retention Policy настроено неправильно (не `infinite`), Debezium **не запустится**. Данные потеряны.

#### 1.4.3. Snapshotting Engine (Механизм начальной загрузки)

Как перенести существующие 10ТБ данных, прежде чем начать читать новые изменения?

**A. Initial Snapshot (Legacy / Blocking)**
*   *Алгоритм*:
    1.  Ставит блокировку (Global Read Lock для MySQL или Transaction Snapshot для PG).
    2.  Читает структуру таблиц.
    3.  Делает `SELECT * FROM table`.
    4.  Отпускает блокировку (или завершает транзакцию).
*   *Минусы*: Долго. При сбое начинает сначала. Удерживает ресурсы БД.

**B. Incremental Snapshotting (Watermarking Algorithm)**
Это "State of the Art" в мире CDC (реализация алгоритма из paper Netflix DBLog). Позволяет делать снапшоты **параллельно** со стримингом изменений, не останавливая процесс и не блокируя таблицы.

*   *Механизм*:
    1.  Пользователь посылает сигнал (через специальную таблицу `debezium_signal`): "Сделай снапшот таблицы `Orders` с ключа 1000 по 2000".
    2.  Debezium открывает "окно" в потоке WAL.
    3.  Делает выборку чанка данных (`SELECT * FROM Orders WHERE id BETWEEN 1000 AND 2000`) обычным SQL-запросом.
    4.  Вставляет результаты этого SELECT-а в поток событий Kafka, помечая их как `op: r` (read).
    5.  Дедуплицирует события: если во время чтения чанка пришел `UPDATE` из WAL для того же ID, Debezium корректно разрешает конфликт (WAL имеет приоритет).
*   *Expert Insight*: Это позволяет делать **Resnapshot** отдельных таблиц на лету. Если вы потеряли топик Kafka с заказами, вы можете попросить Debezium перечитать таблицу `Orders` заново, не перезапуская коннектор и не трогая другие таблицы.

#### 1.4.4. Event Envelope (Структура сообщения)

Debezium оборачивает данные в стандартный конверт. Эксперт должен знать каждое поле.

```json
{
  "schema": { ... }, // Описание типов полей (Avro/JSON Schema)
  "payload": {
    "before": { "id": 100, "status": "PENDING" }, // State BEFORE change
    "after":  { "id": 100, "status": "PAID" },    // State AFTER change
    "source": {
      "version": "2.5.0",
      "connector": "postgresql",
      "name": "prod-db-1",
      "ts_ms": 1678890000123,  // Время совершения транзакции в БД
      "snapshot": "false",
      "db": "postgres",
      "schema": "public",
      "table": "orders",
      "lsn": 3452345,         // Точная позиция в логе
      "txId": 555             // ID транзакции (для группировки)
    },
    "op": "u",                // c=create, u=update, d=delete, r=read, t=truncate
    "ts_ms": 1678890000000,   // Время процессинга внутри Debezium
    "transaction": null       // Блок метаданных транзакции (если включено)
  }
}
```

**Ключевые поля для аналитики:**
1.  **Lag Monitoring**: `payload.ts_ms` (время Kafka) минус `payload.source.ts_ms` (время БД) = **End-to-End Latency**. Это главная метрика здоровья пайплайна.
2.  **Transaction Metadata**: Если включить опцию `provide.transaction.metadata`, Debezium будет генерировать отдельные события начала (`BEGIN`) и конца (`END`) транзакции. Это позволяет потребителю собрать атомарную пачку изменений на своей стороне.

#### 1.4.5. Offset Management (Точки сохранения)

Debezium не использует механизм Kafka Consumer Offsets для отслеживания своего прогресса (так как он Producer).

*   Он использует **Kafka Connect Offset Storage** (топик `connect-offsets`).
*   **Ключ**: Имя коннектора + Имя БД.
*   **Значение**: `lsn` (Postgres) или `binlog_filename` + `position` (MySQL).
*   *Процесс*: После того как Kafka Broker подтверждает получение батча сообщений (ACK), Connect Worker асинхронно обновляет оффсет в топике.
*   **Риск**: `connect-offsets` — это единственный источник правды о том, "где мы остановились". Если вы удалите этот топик, Debezium начнет читать с самого начала (или упадет, если старых логов нет).

### Пример восстановления после сбоя (Crash Recovery)

1.  **Crash**: Kafka Connect Worker падает (OOM). Последнее отправленное событие было с LSN 500. Последний закоммиченный оффсет — LSN 400.
2.  **Restart**: Kubernetes перезапускает под.
3.  **Read Offset**: Debezium читает `connect-offsets`, видит LSN 400.
4.  **Request Log**: Debezium просит Postgres: "Дай стрим с LSN 400".
5.  **Replay**: Postgres отправляет события 400...500 повторно.
6.  **Duplicate Handling**: Kafka Connect отправляет их в топик. В Kafka появляются дубликаты событий 400-500.
    *   **Вывод**: Поэтому ваши потребители (Consumers) **обязаны** быть идемпотентными! CDC гарантирует `At-Least-Once`, но не `Exactly-Once` на уровне транспорта.

### 1.5. Сериализация: Битва за I/O и Контракты (JSON vs Avro/Protobuf)

**Проблема CDC**: События CDC структурно избыточны. Каждое сообщение содержит схему таблицы (имена колонок, типы), метаданные источника и два состояния строки (`before` и `after`).
*   Если передавать описание схемы в *каждом* сообщении, оверхед (накладные расходы) может достигать **95%**. Вы платите за передачу схемы, а не данных.

#### 1.5.1. JSON: Антипаттерн для High Load

Kafka Connect поддерживает два режима работы с JSON. Оба плохи для высоконагруженного CDC, но по разным причинам.

**А. JSON with Schemas (`value.converter.schemas.enable=true`)**
Это дефолтное поведение Kafka Connect, и это **ловушка**.
*   *Механика*: В *каждое* сообщение Kafka вкладывается полный JSON-объект схемы (`schema: {...}`) и данные (`payload: {...}`).
*   *Математика катастрофы*:
    *   Данные: `{"id": 1, "status": "OK"}` (~20 байт).
    *   Схема: Описание всех полей, типов, optional-флагов (~1-2 КБ).
    *   **Overhead**: 5000%. Вы забиваете диск и сеть описанием того, что `id` — это integer.
*   *Вердикт*: Непригодно для продакшна.

**Б. JSON Schemaless (`value.converter.schemas.enable=false`)**
*   *Механика*: Передается только `payload`.
*   *Плюсы*: Читаемо глазами, легко отлаживать `kafkacat`-ом.
*   *Минусы*:
    1.  **Потеря типов**: `100` — это Int, Long или String? Дата `"2025-01-01"` — это строка или Timestamp? Потребитель должен "угадывать".
    2.  **Verbose**: Текстовый формат всегда тяжелее бинарного. Повторение ключей (`"first_name"`, `"last_name"`) в каждой записи.
    3.  **CPU Intensive**: Парсинг JSON — дорогая операция для CPU.

#### 1.5.2. Avro / Protobuf + Schema Registry (Золотой Стандарт)

Это единственный архитектурно верный подход для CDC. Мы отделяем **определение** данных от самих **данных**.

**Архитектура решения:**
1.  **Schema Registry (SR)**: Отдельный сервис (например, Confluent Schema Registry или Apicurio), который хранит версионированные схемы.
2.  **Producer (Debezium)**:
    *   При старте или изменении схемы БД генерирует схему (Avro/Protobuf).
    *   Отправляет её в SR и получает уникальный `Schema ID` (например, 42).
    *   Сериализует данные в бинарный формат.
    *   **Wire Format**: Первые 5 байт сообщения — это "Magic Byte" (0x00) + 4 байта `Schema ID`. Дальше идут сжатые данные без имен полей.
3.  **Consumer**:
    *   Читает первые 5 байт. Видит ID=42.
    *   Идет в SR (или берет из локального кэша), скачивает схему №42.
    *   Десериализует байты, используя схему.

**Преимущества уровня Expert:**
*   **Compactness**: Сообщение сжимается в 10-50 раз по сравнению с JSON.
*   **Strong Typing**: Строгая типизация. Нет гадания "число или строка".
*   **Schema Evolution (Эволюция схемы)**: Самый важный пункт для CDC.

#### 1.5.3. Schema Evolution: Когда DBA делает `ALTER TABLE`

CDC-пайплайн ломается не тогда, когда вы его пишете, а тогда, когда DBA накатывает миграцию через полгода.

**Сценарий**: В таблицу `users` добавили колонку `phone`.
1.  **JSON**: Потребитель получает новое поле. Если он мапит JSON в Java POJO с `failOnUnknownProperties=true`, он падает.
2.  **Avro + Schema Registry**:
    *   Debezium обнаруживает изменение в WAL.
    *   Генерирует новую версию схемы (v2).
    *   Регистрирует v2 в Schema Registry.
    *   *Важно*: SR проверяет **Compatibility Rules** (Правила совместимости).
        *   **BACKWARD Compatibility**: Потребитель со старой схемой (v1) сможет прочитать данные, записанные с новой схемой (v2)? (Да, если поле `phone` имеет дефолтное значение или помечено как optional).
        *   **FORWARD Compatibility**: Потребитель с новой схемой (v2) сможет прочитать старые данные (v1)?

**Expert Advice**:
Для CDC всегда настраивайте Schema Registry в режим **FULL_TRANSITIVE** совместимости. Это гарантирует, что и старые, и новые потребители смогут читать и старые, и новые данные.

#### 1.5.4. Avro vs Protobuf: Что выбрать для CDC?

Оба формата бинарные и требуют Schema Registry. Разница в экосистеме.

| Характеристика | Apache Avro | Google Protobuf |
| :--- | :--- | :--- |
| **Экосистема Big Data** | **Родной формат** для Hadoop, Spark, Iceberg, Hive. | Поддержка хуже, требует конвертации. |
| **Экосистема Microservices** | Слабая (мало кто использует Avro для RPC). | **Родной формат** для gRPC. |
| **CDC (Debezium)** | **Исторический стандарт**. Debezium лучше всего работает с Avro. | Поддержка добавлена позже, но стабильна. |
| **Схема** | JSON-based (`.avsc`). Читаемо, но громоздко. | IDL-based (`.proto`). Лаконично, удобно для разработчиков. |
| **Скорость (CPU)** | Быстро, но чуть медленнее Proto. | Экстремально быстро (Zero-copy parsing). |

**Рекомендация Эксперта**:
1.  Если потребители ваших CDC данных — это **Data Lake / DWH** (Spark, Flink, Trino) -> Выбирайте **Avro**. Это сэкономит вам годы боли с интеграцией в Big Data тулы.
2.  Если потребители — это **Go/C++/Java микросервисы** (Event Driven Architecture) -> Выбирайте **Protobuf**. Генерация кода (POJO/Structs) в Protobuf на порядок удобнее.

#### 1.5.5. Пример катастрофы: Удаление поля

*   **Действие**: DBA удаляет колонку `email` из таблицы.
*   **Debezium**: Генерирует новую схему без поля `email`.
*   **Schema Registry (режим BACKWARD)**: Отвергает новую схему!
    *   *Почему?* Потому что старый потребитель ожидает поле `email`. Если его нет, он не сможет десериализовать сообщение (если у поля нет `default`).
*   **Результат**: Debezium останавливается. Пайплайн стоит.
*   **Решение**:
    1.  Сначала сделать поле `Nullable` (Optional) в схеме (soft delete).
    2.  Обновить всех потребителей.
    3.  Только потом удалять колонку.

**Резюме**: Сериализация в CDC — это управление контрактами. JSON — это отсутствие контракта (хаос). Avro/Protobuf — это принуждение к порядку через Schema Registry. Без SR вы не построите надежный CDC пайплайн.

## 2. Debezium Pitfalls: Где вы потеряете продакшн

Внедрение CDC меняет профиль надежности вашего монолита. Теперь доступность Kafka влияет на доступность Master-БД.

### 2.1. The "Replication Slot" Disk Kill (PostgreSQL) — Инцидент P0

Это самая распространенная причина смерти баз данных при внедрении CDC.

*   **Механика**:
    В PostgreSQL `Replication Slot` — это механизм защиты WAL. Он говорит базе: *"Не удаляй сегменты WAL старше LSN `X`, они мне еще нужны"*.
*   **Сценарий катастрофы**:
    1.  Kafka Connect падает (OOM, Network Split, баг в плагине) или Kafka недоступна.
    2.  Debezium перестает подтверждать чтение (commit LSN).
    3.  Postgres продолжает работать. Приложение пишет данные, генерируя 10 ГБ WAL в час.
    4.  Процесс `checkpointer` хочет удалить старые WAL, но Слот блокирует удаление.
    5.  Папка `pg_wal` растет бесконечно.
    6.  **Disk Full**. Postgres вызывает `PANIC` и останавливается.
    7.  **Recovery Hell**: Вы не можете просто запустить Postgres, потому что места нет даже для старта. Вам нужно вручную удалять файлы (риск коррупции) или расширять диск (если это VM/Cloud).

*   **Expert Mitigation**:
    1.  **Monitor Slot Lag**: Алерт на `pg_replication_slots.wal_status` и размер отставания в байтах.
    2.  **Safety Valve (PG 13+)**: Обязательно настройте `max_slot_wal_keep_size`.
        *   *Пример*: `max_slot_wal_keep_size = 100GB`.
        *   *Эффект*: Если отставание превысит 100 ГБ, Postgres **убьет слот** (статус станет `lost`). Debezium сломается, но **Мастер выживет**.
    3.  **Low Traffic Hazard**: Если в БД нет записи, LSN не двигается. Debezium может держать старые WAL файлы просто потому, что нет новых событий для подтверждения оффсета.
        *   *Решение*: `heartbeat.interval.ms`. Debezium будет периодически обновлять `dummy` запись в своей таблице, форсируя генерацию WAL и движение LSN.

### 2.2. The "Huge Transaction" OOM (Буферизация транзакций)

Что произойдет, если кто-то выполнит `UPDATE orders SET status='ARCHIVED'` для 10 миллионов строк в одной транзакции?

*   **Механика**:
    Debezium не отправляет события в Kafka сразу. Он должен буферизировать транзакцию, чтобы:
    1.  Отбросить её, если случится `ROLLBACK`.
    2.  Сгруппировать события (если нужны метаданные транзакции).
*   **Сценарий сбоя**:
    1.  Debezium вычитывает WAL. Видит начало транзакции.
    2.  Начинает складывать 10 миллионов событий `UPDATE` в Heap-память JVM (Kafka Connect Worker).
    3.  Память кончается. **OutOfMemoryError**.
    4.  Воркер падает и перезапускается.
    5.  Начинает читать тот же WAL с начала... снова OOM. **Death Loop**.

*   **Expert Mitigation**:
    1.  **Heap Size**: Kafka Connect для CDC требует много памяти (Xmx4G+).
    2.  **Streaming Buffering**: Использовать File-based buffering (настройки Debezium), чтобы сбрасывать огромные транзакции на диск воркера, а не держать в RAM.
    3.  **Governance**: Запретить разработчикам делать Massive Updates в одной транзакции. Бить на батчи (Batching).

### 2.3. The "Schema Change" Death Loop (Зацикливание на миграциях)

Debezium чувствителен к структуре бинарного лога. Если он встречает данные, которые не может распарсить согласно известной ему схеме, он падает.

*   **Сценарий**:
    1.  DBA меняет тип колонки `amount` с `NUMERIC(10,2)` на `VARCHAR` (бывает всякое).
    2.  Приложение пишет "100.00".
    3.  Debezium пытается прочитать бинлог. Его внутренний кэш схемы говорит, что это число. В бинлоге строка.
    4.  **Exception**: `ConnectException: ... cannot deserialize ...`.
    5.  Коннектор падает. Kafka Connect его перезапускает.
    6.  Он снова читает ту же позицию. Снова падает.
*   **Проблема**: Вы не можете просто пропустить это сообщение, потому что Debezium должен поддерживать целостность последовательности.
*   **Expert Fix**:
    1.  **Schema History Topic**: Убедиться, что он работает корректно. Debezium должен был увидеть `ALTER TABLE` до того, как увидел `INSERT`.
    2.  **Handling Mode**: `event.processing.failure.handling.mode=warn` (пропустить и залогировать) — опасно, но спасает прод.
    3.  **Manual Surgery**: В худшем случае придется вручную двигать оффсет в топике `connect-offsets`, пропуская "битую" позицию.

### 2.4. Snapshotting Impact (Блокировка Вакуума)

Даже с инкрементальными снапшотами (Incremental Snapshotting), долгие транзакции чтения опасны для PostgreSQL.

*   **Механика**: Postgres использует MVCC. Старые версии строк (Dead Tuples) нельзя удалить (`VACUUM`), пока существует хотя бы одна активная транзакция, которая *могла бы* их видеть (даже если это `REPEATABLE READ` снапшот Debezium).
*   **Сценарий**:
    1.  Debezium делает начальный снапшот таблицы на 5 ТБ. Транзакция висит 24 часа.
    2.  В это время в БД идет активная запись/обновление.
    3.  Автовакуум приходит, но видит открытую транзакцию Debezium (`xmin` horizon). Он **не может** вычистить мусор.
    4.  **Table Bloat**: Таблицы физически распухают, индексы деградируют. Производительность БД падает.
    5.  **Transaction ID Wraparound**: В экстремальных случаях риск остановки базы для защиты от переполнения счетчика транзакций.

*   **Expert Strategy**:
    *   Никогда не делайте полный снапшот (`snapshot.mode=initial`) на живой нагруженной базе.
    *   Используйте только **Incremental Snapshots** (через DDD-сигналы), которые бьют чтение на короткие чанки, позволяя Вакууму работать в перерывах.

### 2.5. Ordering & Partitioning Keys (Хаос порядка)

Kafka гарантирует порядок *только внутри партиции*.
*   **Проблема**: По умолчанию Debezium использует Primary Key таблицы как ключ сообщения Kafka.
*   **Риск**:
    1.  Если у таблицы *нет* PK, Debezium может генерировать случайный ключ (или null).
    2.  События одной строки (`INSERT`, затем `UPDATE`) попадают в *разные* партиции Kafka.
    3.  Консьюмер вычитывает их параллельно. Из-за сетевых задержек `UPDATE` обрабатывается *раньше* `INSERT`.
    4.  Ошибка в консьюмере: `EntityNotFoundException`.
*   **Expert Fix**:
    *   Обязательное требование PK для всех таблиц под CDC.
    *   Если PK составной или меняется, используйте `message.key.columns`, чтобы явно зафиксировать неизменяемый бизнес-ключ (например, `user_uuid`), по которому будет идти шардирование в Kafka.

### 2.6. TOAST Columns & `REPLICA IDENTITY` (Postgres Specifc)

Повторим для закрепления, так как это частая боль.
*   **Симптом**: В Kafka приходят события `UPDATE`, где большие текстовые поля равны `null`, хотя в базе они заполнены.
*   **Причина**: Postgres не распаковывает неизмененные TOAST-значения в WAL.
*   **Решение**:
    *   `ALTER TABLE table REPLICA IDENTITY FULL;`
    *   **Цена**: Увеличение объема WAL в 2-5 раз. Увеличение нагрузки на CPU репликации. Это архитектурный Trade-off, который нужно обосновать.

### Summary: Чек-лист выживания

1.  **Мониторинг**: Дашборд с `Replication Slot Lag`, `WAL Size`, `Connect Heap Usage`.
2.  **Alerting**: Звонок инженеру, если слот отстает на 50% от лимита диска.
3.  **Config**: `max_slot_wal_keep_size` настроен.
4.  **Snapshot Strategy**: Инкрементальные снапшоты вместо полных.
5.  **Transactions**: Лимит на размер транзакции в приложении.

## 3. Transactional Outbox Pattern: Гарантия согласованности

**Проблема**: В микросервисной архитектуре действия часто требуют изменения локального состояния (запись в БД) и уведомления внешнего мира (отправка сообщения в Kafka).
**Фундаментальная теорема**: Невозможно атомарно выполнить запись в БД и отправку в сеть, используя стандартные драйверы.
*   Если сначала БД, потом Сеть: Сеть может упасть -> Сообщение потеряно -> Рассинхрон.
*   Если сначала Сеть, потом БД: БД может упасть (Constraint Violation) -> Сообщение "призрак" отправлено -> Рассинхрон.

**Transactional Outbox** решает это, превращая отправку сообщения в запись в БД.

### 3.1. Анатомия Log-Based Outbox

Существует два подхода к реализации Outbox: **Polling** (опрос таблицы) и **Log-Based** (чтение WAL).
На масштабе (At Scale) допустим **только Log-Based**, так как Polling убивает базу данных запросами и создает задержки.

Мы используем **Debezium**, который слушает таблицу `outbox` через WAL.

#### Схема таблицы (PostgreSQL Optimized)
Экспертная схема включает поддержку партицирования, трассировки и гибкого роутинга.

```sql
CREATE TABLE outbox (
    id UUID NOT NULL,            -- Уникальный ID события (для идемпотентности)
    aggregatetype VARCHAR(255) NOT NULL, -- Тип агрегата ("Order")
    aggregateid VARCHAR(255) NOT NULL,   -- ID сущности ("100500") -> Будет Kafka Key
    type VARCHAR(255) NOT NULL,          -- Тип события ("OrderCreated")
    payload JSONB NOT NULL,              -- Бизнес-данные
    headers JSONB,                       -- Метаданные (TraceID, UserID)
    created_at TIMESTAMPTZ DEFAULT NOW() -- Время возникновения
) PARTITION BY RANGE (created_at);       -- ВАЖНО для очистки!
```

### 3.2. Debezium SMT (Single Message Transform) — Магия маршрутизации

Это самый сложный для понимания момент.
Debezium по умолчанию читает строку таблицы `outbox` и отправляет в Kafka сообщение вида:
```json
{ "before": null, "after": { "id": "...", "payload": "{...}" } }
```
Это **не то**, что нам нужно. Мы хотим получить чистое доменное событие, а не "событие вставки в техническую таблицу".

Для этого используется специальный класс внутри Kafka Connect: `io.debezium.transforms.outbox.EventRouter`.

**Что делает этот SMT:**
1.  **Unwrap**: Берет поле `payload` из строки и делает его телом (Value) сообщения Kafka.
2.  **Key Routing**: Берет поле `aggregateid` и делает его ключом (Key) сообщения Kafka. Это гарантирует, что все события одного заказа попадут в одну партицию.
3.  **Header Injection**: Берет поле `headers` (JSON) и превращает их в нативные Kafka Headers (для OpenTelemetry).
4.  **Topic Routing**: Генерирует имя топика на основе `aggregatetype` (например, `outbox.event.Order`).

**Конфигурация Kafka Connect (Expert Snippet):**
```properties
transforms=outbox
transforms.outbox.type=io.debezium.transforms.outbox.EventRouter
transforms.outbox.table.fields.additional.placement=type:header:eventType
transforms.outbox.route.topic.replacement=events.${routedByValue}
```

### 3.3. Проблема "Вакуума" и Очистки (The Vacuum Hazard)

Это "убийца производительности" №1 для паттерна Outbox на High Load.

*   **Сценарий**: Вы пишете 1000 событий в секунду. Debezium их читает. Чтобы таблица не росла вечно, вы должны их удалять.
*   **Наивный подход**: Job, который делает `DELETE FROM outbox WHERE created_at < NOW() - 1min`.
*   **Последствия**:
    1.  Postgres помечает строки как мертвые (Dead Tuples).
    2.  `Autovacuum` сходит с ума, пытаясь очистить страницы.
    3.  **Table Bloat**: Таблица и индексы "пухнут", I/O растет, производительность записи падает.
    4.  **WAL Amplification**: Операция `DELETE` тоже пишется в WAL! Вы удваиваете нагрузку на Debezium (он видит INSERT, а потом DELETE).

**Expert Solution: Partition Pruning (Drop Partition)**
1.  Создаем партиции таблицы `outbox` по времени (например, 1 час или 1 день).
2.  Пишем в текущую партицию.
3.  Debezium читает из всех.
4.  **Очистка**: Вместо `DELETE` мы делаем `DROP TABLE outbox_p_2023_10_25_1000`.
    *   Это мгновенная операция файловой системы.
    *   Она почти не генерирует WAL.
    *   Вакуум не нужен.

### 3.4. Distributed Tracing (Сквозная трассировка)

Как связать HTTP-запрос `POST /create-order` с сообщением в Kafka, если они разделены базой данных?
Обычные перехватчики (Jaeger/Zipkin) здесь ломаются, так как контекст теряется при записи в БД.

**Реализация**:
1.  Сервис читает `traceparent` из HTTP-заголовка.
2.  При записи в таблицу `outbox` сервис **явно** пишет этот `traceparent` в колонку `headers`.
3.  Debezium SMT извлекает его и кладет в Kafka Header.
4.  Consumer читает Kafka Header и восстанавливает спан.
**Итог**: Вы видите в Jaeger единый трейс: `HTTP Controller -> DB Insert -> (Async Gap) -> Kafka Consumer`.

### 3.5. Работа с несколькими топиками (Routing Strategy)

Частая ошибка: слать всё в один гигантский топик `events`.
*   **Проблема**: Консьюмеру, которому нужны только "Платежи", приходится вычитывать и отбрасывать миллионы событий "Логов".
*   **Решение**: Динамический роутинг в SMT.
    *   В таблице `outbox` поле `aggregatetype` = 'Order' -> Топик `events.order`.
    *   В таблице `outbox` поле `aggregatetype` = 'Payment' -> Топик `events.payment`.
    *   Kafka Connect сам раскидает сообщения по нужным топикам на лету.

### Пример кода (Java + Spring)

```java
@Transactional
public void createOrder(CreateOrderCommand cmd) {
    // 1. Бизнес-логика (Локальное состояние)
    Order order = new Order(cmd);
    orderRepository.save(order); // INSERT INTO orders ...

    // 2. Подготовка события (Outbox)
    OrderCreatedEvent event = new OrderCreatedEvent(order.getId(), order.getStatus());
    
    // 3. Сериализация и запись в Outbox
    // Обратите внимание: это та же @Transactional транзакция!
    OutboxEntity outbox = new OutboxEntity();
    outbox.setId(UUID.randomUUID());
    outbox.setAggregateType("Order");
    outbox.setAggregateId(order.getId().toString()); // Kafka Key
    outbox.setType("OrderCreated");
    outbox.setPayload(objectMapper.writeValueAsString(event));
    
    // Проброс трейсинга вручную
    outbox.setHeaders(Map.of("traceparent", Span.current().getSpanContext().getTraceId()));

    outboxRepository.save(outbox); // INSERT INTO outbox ...
}
// 4. COMMIT происходит здесь. 
// Если упадет БД - не запишется ни заказ, ни событие.
// Если упадет Kafka - событие останется в БД и будет прочитано позже Debezium.
```

### Резюме раздела 3
1.  **Transactional Outbox** — единственный способ обеспечить **At-Least-Once** доставку бизнес-событий без 2PC.
2.  Используйте **Log-Based (Debezium)** подход, а не Polling.
3.  **SMT (EventRouter)** — ключевой компонент, превращающий записи БД в чистые события.
4.  **Table Partitioning** обязателен для решения проблемы очистки таблицы (Vacuum problem) на высоких нагрузках.

## 4. Архитектурные паттерны внедрения (Deployment Topologies)

Выбор топологии определяет TCO (Total Cost of Ownership) и Radius of Blast (Радиус поражения) при сбоях.

### 4.1. Topology Choices: Где запускать Debezium?

Существует три способа запуска, и эксперт выбирает их осознанно.

#### А. Kafka Connect Distributed Cluster (The Enterprise Standard)
*   **Архитектура**: Отдельный кластер JVM-процессов (Workers), управляемый через REST API. Коннекторы распределяются по воркерам.
*   **Плюсы**:
    *   **High Availability**: Если воркер падает, задачи (Tasks) автоматически переезжают на живые ноды.
    *   **Isolation**: CDC-нагрузка вынесена за пределы приложения. Утечка памяти в Debezium не убивает бизнес-сервис.
    *   **Operability**: Интеграция с K8s через операторы (Strimzi). Автоматический рестарт при сбоях.
*   **Минусы**: Требует управления отдельным кластером (инфраструктурный оверхед).
*   **Рекомендация**: Стандарт для продакшна. Используйте **Strimzi Operator** в Kubernetes.

#### Б. Debezium Server (The Cloud-Native / Sidecar)
*   **Архитектура**: Облегченное приложение (Quarkus), которое читает БД и пишет *не только* в Kafka, но и в Kinesis, Pub/Sub, Pulsar или Redis Streams.
*   **Плюсы**:
    *   Не требует Kafka Connect и Zookeeper.
    *   Позволяет строить CDC без Kafka (сразу в облачную очередь).
*   **Минусы**: Нет кластеризации и Rebalance. Один инстанс на одну БД.
*   **Рекомендация**: Использовать для Non-Kafka архитектур или как **Sidecar** к базе данных в малых инсталляциях.

#### В. Embedded Engine (The Anti-Pattern for Ops)
*   **Архитектура**: Библиотека `debezium-embedded`, подключенная прямо в Java-код вашего микросервиса.
*   **Риски**:
    *   **Coupling**: Жизненный цикл CDC связан с деплоем сервиса. Хотите обновить версию Debezium? Передеплойте весь монолит.
    *   **Resource Contention**: CDC конкурирует за CPU/Heap с бизнес-логикой. OOM в CDC убивает сервис.
    *   **Scaling Conflict**: Если вы отскейлили сервис до 5 подов, у вас запустится 5 CDC-читателей. А БД (Postgres) позволяет читать слот только *одному*. 4 пода упадут с ошибкой.
*   **Рекомендация**: Только для **Unit/Integration тестов** и очень специфичных сценариев Edge/IoT.

---

### 4.2. HA & Failover Strategy (Проблема потерянного слота)

Это самый критичный архитектурный нюанс для PostgreSQL CDC, о котором молчат в туториалах.

*   **Проблема**: Слот репликации в PostgreSQL — это локальный объект инстанса. Он **не реплицируется** на физические стэндбаи (до PG 16/17 это было невозможно штатно).
*   **Сценарий сбоя**:
    1.  Master (Primary) умирает.
    2.  Patroni/Stolon переключает трафик на Standby.
    3.  Standby становится новым Master.
    4.  Debezium подключается к новому Мастеру... и **падает**.
    5.  **Причина**: На новом мастере *нет слота репликации* и нет информации о LSN, на котором остановился Debezium.
*   **Результат**: Вам нужно делать **Resnapshot** (перечитывать всю БД), что на терабайтных базах означает простой пайплайна на сутки.

*   **Expert Solution**:
    1.  **Failover Slots**: Использовать расширения типа `pg_failover_slots` или функционал Patroni, который копирует позицию слота на стэндбай.
    2.  **PG 17+**: В новых версиях добавлена нативная синхронизация слотов. Требуйте апгрейда БД до актуальных версий.

---

### 4.3. Topic Partitioning Strategy (Сохранение порядка)

CDC бесполезен, если вы нарушаете порядок событий (`UPDATE` пришел раньше `INSERT`). Kafka гарантирует порядок только в рамках партиции.

*   **Default Behavior**: Debezium использует Primary Key таблицы как ключ партицирования.
    *   `Hash(PK) % N_Partitions`.
*   **Проблема (Business Aggregate)**:
    *   Таблица `OrderLines` имеет PK `line_id`.
    *   Таблица `Orders` имеет PK `order_id`.
    *   События одной бизнес-сущности (Заказ + его Позиции) летят в *разные* партиции Kafka.
    *   Консьюмер может получить "Позицию" до того, как увидит "Заказ". Ошибка `ForeignKeyViolation` в целевой системе.
*   **Expert Solution (Custom Partitioning)**:
    *   Настроить SMT или конфигурацию Debezium так, чтобы для `OrderLines` ключом партицирования был `order_id` (Foreign Key), а не `line_id`.
    *   **Результат**: Весь агрегат (Заказ + Строки) летит в одну партицию и обрабатывается последовательно.

---

### 4.4. Filtering at Source (Фильтрация на входе)

Не тащите в Kafka мусор. Это стоит денег.

1.  **Publication Filtering (Postgres Native)**:
    *   Вместо `SELECT *` в Debezium, создайте публикацию:
        ```sql
        CREATE PUBLICATION dbz_pub FOR TABLE orders WHERE (region = 'US');
        ```
    *   *Плюс*: Postgres даже не декодирует и не шлет в сеть события других регионов. Максимальная производительность.
2.  **Column Masking (SMT)**:
    *   Никогда не передавайте PII (паспорта, телефоны) в сыром виде.
    *   Используйте SMT `Masking` или `ColumnDrop`, чтобы вырезать колонку `password_hash` *до* сериализации в Kafka.
    *   *Важно*: SMT работает на Kafka Connect Worker. Это нагружает CPU воркера, но защищает шину данных.

---

### 4.5. The "Schema Leakage" Anti-Pattern

*   **Антипаттерн**: Называть топики `server1.public.orders`.
    *   Это привязывает вас к физической структуре БД. Если вы переименуете схему `public` в `sales`, топик изменится, консьюмеры сломаются.
*   **Expert Pattern**: Использовать **Logical Topic Routing** (SMT).
    *   Настроить роутер так, чтобы таблица `public.orders` писалась в топик `domain.order.events`.
    *   Это позволяет менять БД под капотом, не уведомляя команду Data Lake, пока контракт данных (Avro Schema) соблюдается.

### Пример конфигурации Strimzi (K8s)

```yaml
apiVersion: kafka.strimzi.io/v1beta2
kind: KafkaConnector
metadata:
  name: pg-connector
spec:
  class: io.debezium.connector.postgresql.PostgresConnector
  tasksMax: 1  # Строго 1 для CDC!
  config:
    database.hostname: postgres-primary-service
    slot.name: debslot_01
    publication.name: dbz_publication # Используем Native Publication
    plugin.name: pgoutput
    
    # Защита от потери слота
    slot.drop.on.stop: false 
    
    # Трансформации (SMT)
    transforms: "unwrap,route"
    
    # 1. Unwrap - убираем метаданные 'before/after', оставляем только данные
    transforms.unwrap.type: io.debezium.transforms.ExtractNewRecordState
    transforms.unwrap.drop.tombstones: false
    transforms.unwrap.delete.handling.mode: rewrite # Превращает DELETE в сообщение с полем __deleted=true
    
    # 2. Routing - отвязываемся от имени схемы
    transforms.route.type: org.apache.kafka.connect.transforms.RegexRouter
    transforms.route.regex: ".*\\.public\\.(.*)"
    transforms.route.replacement: "domain.$1.v1"
```

### Резюме раздела 4

1.  Запускайте Debezium только в **Kafka Connect Cluster** (желательно через K8s Operator).
2.  Решите проблему **Failover слотов** на уровне DBA (Patroni/PG17) до выхода в прод.
3.  Используйте **Postgres Publications** для фильтрации трафика на источнике.
4.  Проектируйте ключи партицирования (**Partition Keys**) исходя из бизнес-агрегатов, а не Primary Keys таблиц.

## 5. Summary для Эксперта 

1.  **Monitoring First**: Прежде чем включать Debezium в проде, настройте алерт на `Replication Slot Lag` и `Disk Space Usage` на мастере БД.
2.  **Outbox is King**: Для межсервисного взаимодействия используйте **только** Outbox Pattern. Прямой стриминг таблиц (CDC на доменные таблицы) оставьте для DWH/Analytics репликации.
3.  **Replica Identity**: Будьте готовы к `REPLICA IDENTITY FULL` и увеличению IOPS.
4.  **At-Least-Once**: Ваши консьюмеры должны быть идемпотентны. Debezium *будет* слать дубли при рестарте коннектора.

CDC — это мощнейший инструмент, но он превращает DBA и Разработчиков в одну команду. Без понимания внутренностей Postgres/MySQL вы не сможете эксплуатировать это на масштабе.

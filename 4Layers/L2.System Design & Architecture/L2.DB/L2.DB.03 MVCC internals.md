**TL;DR**: Для уровня Senior/Staff понимание MVCC — это не просто знание об уровнях изоляции. Это понимание физики данных на диске.
*   **PostgreSQL**: Использует **MGA (Multi-Generation Architecture)**. Версии строк хранятся в основной куче (Heap). Плюсы: быстрый откат. Минусы: Write Amplification, Bloat, необходимость Vacuum.
*   **MySQL (InnoDB)**: Использует **Undo Log**. В таблице всегда только актуальная версия, старые версии реконструируются из логов отмены. Плюсы: компактность основной таблицы. Минусы: медленное чтение старых версий (оверхед на реконструкцию), риск разрастания History List.
*   **Ключевой навык (Expert)**: Умение выбирать БД и тюнить её под паттерн нагрузки (Write-heavy vs Read-heavy), понимая цену создания снэпшотов и очистки мусора.

## 1. PostgreSQL: Append-Only Storage (The Heap Approach)

### 1.1. Физическая структура страницы и кортежа (The Physics of Rows)

Данные хранятся в страницах (Pages) фиксированного размера (по умолчанию **8kB**).
Архитектор должен знать, что "строка" (Tuple) — это дорогая структура.

#### A. Page Layout (Анатомия страницы)
Страница состоит из:
1.  **Header (24 байта):** Метаданные страницы (LSN для WAL, контрольные суммы, флаги).
2.  **ItemIdData (Line Pointers):** Массив указателей (по 4 байта) сразу за заголовком. Индексы ссылаются именно на номер этого указателя (Offset Number), а не на физический адрес байта. Это позволяет дефрагментировать данные внутри страницы без перестройки индексов.
3.  **Free Space:** "Дырка" между указателями и данными.
4.  **Items (Tuples):** Сами данные, растут с конца страницы к началу.

#### B. Tuple Header (Накладные расходы на строку)
Каждая строка имеет заголовок `HeapTupleHeaderData`. Минимальный размер — **23 байта**, но из-за выравнивания (alignment) на 64-битных системах это обычно **24 байта + Padding**.

Ключевые поля для понимания MVCC:

*   **`t_xmin` (Transaction ID Created):** XID транзакции, которая сделала INSERT или UPDATE этой версии.
*   **`t_xmax` (Transaction ID Expired):**
    *   При INSERT: 0.
    *   При DELETE/UPDATE: XID транзакции, которая удалила/обновила строку.
    *   *Важный нюанс:* Это поле также используется для Row-Level Locking (например, `SELECT FOR UPDATE`). Если строка заблокирована, но не удалена, XID блокирующей транзакции пишется сюда, а в `t_infomask` ставятся специальные флаги.
*   **`t_cid` (Command ID):** Счетчик команд внутри *одной* транзакции (cmin/cmax).
    *   *Зачем:* Если вы сделали `UPDATE...; SELECT...` внутри одной транзакции, вы должны видеть свои изменения. `t_xmin` будет равен вашему текущему XID, и только `t_cid` позволит понять, какая версия была раньше, а какая позже.
*   **`t_ctid` (Current Tuple ID):** Физическая ссылка `(BlockNumber, OffsetNumber)` на *следующую* более свежую версию этой строки. Это создает связный список версий (version chain).
*   **`t_infomask` & `t_infomask2`:** Битовые маски. Содержат:
    *   Количество атрибутов (колонок).
    *   **Hint Bits** (см. ниже — это критично для performance).
    *   Статус NULL-значений (NULL bitmap).

**Expert Insight (Data Alignment):**
Архитектор должен знать про **Padding**. Данные в кортеже выравниваются.
*   *Плохо:* `int8, bool, int8` -> 8 байт + 1 байт (+ 7 байт мусора) + 8 байт = 24 байта.
*   *Хорошо:* `int8, int8, bool` -> 8 байт + 8 байт + 1 байт = 17 байт.
Порядок колонок в `CREATE TABLE` влияет на плотность хранения и эффективность кэша!

### 1.2. Механика DML операций (Life of a Tuple)

Postgres использует **Snapshot Isolation**. Рассмотрим физику процессов.

#### Сценарий: UPDATE account SET balance = 200 WHERE id = 1;

Предположим, текущая строка (Version 1) находится в блоке 5, оффсет 2. (`(5,2)`).

1.  **Lookup & Lock:**
    *   PG находит строку по индексу.
    *   Проверяет видимость.
    *   Пытается установить **Exclusive Lock** на строку. Это делается не в памяти (как Lock Manager), а **прямо в данных**: в поле `t_xmax` строки `(5,2)` записывается XID текущей транзакции. Устанавливаются биты в `t_infomask`.

2.  **Creation of New Version (Version 2):**
    *   PG ищет свободное место. Сначала на той же странице (Block 5).
    *   Если места нет — смотрит в **FSM (Free Space Map)**, чтобы найти другую страницу с местом.
    *   Записывает новую версию строки (Version 2) в, скажем, `(5,9)` (или `(6,1)`).
    *   `Version 2`: `t_xmin` = Current XID, `t_xmax` = 0, `t_ctid` = `(5,9)`.

3.  **Chaining (Связывание):**
    *   В старой `Version 1` `t_xmax` уже равен Current XID (установлен на шаге блокировки).
    *   Поле `t_ctid` в `Version 1` меняется с `(5,2)` на `(5,9)`. Цепочка замкнулась.

4.  **Index Maintenance (Боль):**
    *   Если не сработала оптимизация HOT (см. ниже), Postgres должен добавить **новую запись в каждый индекс** таблицы.
    *   Индекс теперь содержит две записи для `id=1`: одна указывает на `(5,2)`, вторая на `(5,9)`.

**Архитектурное следствие (Write Amplification):**
В отличие от InnoDB, где обновляется только измененное, в Postgres `UPDATE` одной колонки копирует **всю строку**. Если у вас строка 2KB и вы меняете 1 boolean флаг, вы пишете 2KB в WAL и 2KB в Heap. Это "налог" на версионность.
*Решение:* Использовать TOAST для больших полей (тексты, JSONB). Если TOAST-поле не меняется при апдейте, новая версия строки будет ссылаться на *старый* TOAST-объект (экономия I/O).

### 1.3. Hint Bits: "Ленивая" фиксация статуса

Это концепция, которую часто упускают на собеседованиях Staff уровня.

Когда транзакция делает `COMMIT`, она пишет это событие в **WAL** и меняет статус своего XID в **CLOG** (Commit Log, ныне `pg_xact`). Она **не** возвращается в файлы данных, чтобы пометить свои строки как "committed". Это было бы слишком дорого (random write I/O по всему диску).

**Проблема:**
Когда следующая транзакция (Reader) читает строку, она видит в `t_xmin` число, например, `1050`. Она не знает, закоммичена ли `1050`.

**Решение (Lazy Check):**
1.  Reader идет в CLOG (в shared buffers или на диск) проверить статус `1050`.
2.  Видит, что `1050` — COMMITTED.
3.  Reader (даже если это `SELECT`!) **делает запись в страницу данных**: устанавливает специальный бит в `t_infomask` ("XMIN_COMMITTED").
4.  Страница помечается как "грязная" (dirty) и будет сброшена на диск чекпоинтером.

**Expert Insight:**
Первый `SELECT` после массового обновления работает медленнее и генерирует **Write I/O**, потому что он "проставляет хинт-биты" за писателя.

### 1.4. HOT Updates (Heap Only Tuples)

Это главная оптимизация для борьбы с Write Amplification в индексах.

**Условия срабатывания:**
1.  UPDATE не меняет столбцы, по которым построены индексы.
2.  На текущей странице (Page) достаточно места для новой версии строки.

**Механика:**
Вместо создания новой записи в индексе, Postgres создает "цепочку" внутри страницы через Line Pointers.
*   Индекс указывает на `LP1` (Line Pointer 1).
*   `LP1` указывает на `Tuple 1` (старая версия).
*   При HOT-update создается `Tuple 2`, и на него заводится `LP2`.
*   Header `Tuple 1` помечается флагом `HEAP_HOT_UPDATED` и ссылается на `Tuple 2`.
*   **Магия:** `LP1` перенаправляется (Redirect) сразу на `LP2`.

**Результат:** Индексы трогать не нужно. `VACUUM` может удалять мертвые `Tuple 1` даже без удаления ссылок из индексов (pruning).
**Совет архитектора:** Устанавливайте `FILLFACTOR` (например, 80-90%) для интенсивно обновляемых таблиц, чтобы оставить "воздух" внутри страницы для работы HOT.

### 1.5. Visibility Map (Карта видимости)

Еще одна критичная структура (появилась в 8.4, улучшена в 9.x). Это битовая карта, где 2 бита отвечают за каждую страницу кучи.

1.  **All-Visible:** Все строки на странице видны всем активным транзакциям (нет мертвых строк, нет незавершенных транзакций).
2.  **All-Frozen:** Все строки на странице "заморожены" (защита от wraparound).

**Зачем это нужно:**
Позволяет делать **Index-Only Scans**.
Обычно, найдя запись в индексе, PG обязан пойти в Heap ("Heap Fetch"), чтобы проверить `t_xmin/t_xmax` (вдруг транзакция не закоммичена?).
Если бит `All-Visible` для страницы установлен, PG **доверяет индексу** и не читает кучу. Это дает ускорение чтения в 10-100 раз.

---
### Резюме для Senior/Staff Architect:

Постгресовый "Append-Only" подход — это гениальный компромисс.
*   **Плюс:** Моментальный ROLLBACK (просто выкинуть XID, ничего не надо восстанавливать).
*   **Плюс:** Высокая скорость конкурентного чтения (читатели не блокируют писателей, писатели не блокируют читателей).
*   **Цена:** Агрессивный расход места и необходимость сборки мусора.

**Ключевой вывод:** Эффективность PostgreSQL на записи прямо пропорциональна вашей способности обеспечить работу **HOT updates** (правильный `FILLFACTOR`, не индексировать часто обновляемые поля) и настроить **Autovacuum** так, чтобы он чистил мусор быстрее, чем вы его производите.

## 2. MySQL (InnoDB): Update-in-Place (The Undo Log Approach)

В отличие от PostgreSQL, InnoDB — это **Clustered Index Organized Table**. Сама таблица — это B+Tree индекс (Primary Key).
Философия InnoDB: **"Актуальные данные — граждане первого сорта. Прошлое архивируется"**. Это означает, что чтение *последней* версии всегда максимально быстрое, а чтение *прошлого* требует вычислительных затрат на реконструкцию.

### 2.1. Скрытая анатомия строки (Clustered Index Row Structure)

Каждая запись в Clustered Index (то есть каждая строка вашей таблицы) расширяется движком. К пользовательским данным добавляются системные поля.

1.  **`DB_TRX_ID` (6 байт):** Transaction ID.
    *   Это глобальный счетчик. Каждая транзакция, которая *модифицирует* данные, получает этот номер. (Транзакции только на чтение (RO) не увеличивают глобальный счетчик, что является важной оптимизацией).
    *   Указывает на транзакцию, которая создала *текущее* состояние этой строки.

2.  **`DB_ROLL_PTR` (7 байт):** Rollback Pointer.
    *   Это не просто адрес памяти. Это структурный указатель: `Space ID` (табличное пространство) + `Page No` (номер страницы) + `Offset` (смещение) внутри **Undo Log**.
    *   Он указывает на **Undo Log Record** — структуру, необходимую для отмены последнего изменения.

3.  **`DB_ROW_ID` (6 байт):**
    *   Существует только если у таблицы нет явного Primary Key. (Совет эксперта: *Всегда* создавайте явный PK, иначе вы создаете hotspot на глобальном мьютексе при генерации этого ID).

### 2.2. Архитектура Undo Log: Insert vs Update

Многие инженеры считают Undo Log единым монолитом. Это ошибка. InnoDB разделяет их на два типа, что критично для конкурентности.

1.  **Insert Undo Log:**
    *   Хранит записи для отмены `INSERT`.
    *   **Важно:** Новая строка видна *только* транзакции, которая её вставила. Другим транзакциям старая версия не нужна (её не существовало).
    *   **Optimization:** Этот лог можно удалять (truncate) **сразу после коммита**. Он не нужен для MVCC.

2.  **Update Undo Log:**
    *   Хранит записи для отмены `UPDATE` и `DELETE`.
    *   Содержит *предыдущее значение* измененных колонок.
    *   **Важно:** Этот лог **нельзя** удалять после коммита, если есть активные транзакции (Read Views), стартовавшие раньше этого коммита. Им нужны эти данные для построения старых версий. Именно этот лог вызывает разрастание `History List`.

### 2.3. Жизненный цикл DML (Anatomy of a Change)

Рассмотрим `UPDATE users SET age = 30 WHERE id = 1` (старый age = 25). Транзакция TRX_ID = 100.

1.  **Locking:** Транзакция берет **X-Lock** (Exclusive Record Lock) на строку `id=1` в кластерном индексе.
2.  **Copy to Undo:**
    *   InnoDB выделяет место в **Undo Page**.
    *   Копирует туда *старое* значение (`age=25`) и *предыдущий* `DB_TRX_ID` и `DB_ROLL_PTR` (которые были в строке до нас).
    *   Формируется запись Undo Log Record.
3.  **In-Place Update:**
    *   В самой странице данных (Buffer Pool) значение `age` меняется на 30.
    *   `DB_TRX_ID` обновляется на 100.
    *   `DB_ROLL_PTR` обновляется, указывая на только что созданную запись в Undo Log.
4.  **Logging:** Изменения (и страницы данных, и страницы Undo Log) пишутся в **Redo Log** (для Durability).

**Ключевой момент (DELETE Marking):**
Операция `DELETE` физически не удаляет строку. Она делает `UPDATE`, устанавливая специальный бит **delete-mark** в заголовке записи. Физическое удаление делает Purge Thread (см. ниже).

### 2.4. Реконструкция версий (CR — Consistent Read)

Это самое "магическое" место в InnoDB. Если вы читаете данные в режиме `REPEATABLE READ` или `READ COMMITTED`, и натыкаетесь на строку, измененную *после* начала вашей транзакции, InnoDB запускает процедуру **версионирования на лету**.

**Алгоритм для Senior Architect:**

1.  **Read View:** При первом чтении (или старте транзакции) создается "снимок" мира.
    *   `m_ids`: список активных транзакций.
    *   `min_trx_id` / `max_trx_id`: границы видимости.
2.  **Fetch:** Читаем строку из таблицы (всегда самую свежую!).
3.  **Check Visibility:** Сравниваем `DB_TRX_ID` строки с нашим Read View.
    *   Если ID "наш" или "старый" — возвращаем строку.
    *   Если ID "чужой" (активный или из будущего) — **версия невидима**.
4.  **Pointer Chasing (Time Travel):**
    *   Движок берет `DB_ROLL_PTR`.
    *   Делает **Random Read** в страницу Undo Log (если её нет в Buffer Pool — это диск!).
    *   Читает Undo Record. Применяет "обратную дельту" к текущей строке в памяти (во временном буфере), получая предыдущую версию.
    *   Получает виртуальную строку с *восстановленным* `DB_TRX_ID`.
    *   Снова проверяет видимость.
5.  **Loop:** Повторяет шаг 4 рекурсивно, пока не найдет версию, удовлетворяющую Read View, или пока не дойдет до `NULL` (версия insert).

**Цена производительности:**
Если у вас есть "Long Running Transaction" и строка часто обновлялась ("Hot Row"), читателю придется пройти цепочку из сотен Undo-записей. Это сжигает CPU и генерирует огромное количество Random IO.

### 2.5. Проблема вторичных индексов (The Achilles' Heel)

Это самый тонкий момент, который отличает Senior от Expert.
**Вторичные индексы в InnoDB НЕ содержат системных колонок (`DB_TRX_ID`, `DB_ROLL_PTR`).**

**Следствие:** Вторичный индекс не знает, актуальна запись или нет. Он знает только `(Secondary Key, Primary Key)`.

**Как это работает (Index Condition Pushdown limitation):**
1.  Вы ищете `WHERE status = 'active'`. Индекс по `status`.
2.  InnoDB находит запись в индексе.
3.  Но он не знает, видна ли она вам! (Может, TRX=200 удалила её минуту назад, но вы TRX=150).
4.  **Оптимизация `MAX_TRX_ID`:** На каждой странице вторичного индекса в заголовке записан максимальный ID транзакции, менявшей эту страницу.
    *   Если `Page MAX_TRX_ID` < вашего `min_trx_id` — ура, все записи на странице "старые" и точно видны вам. Читаем индекс (Covering Index работает).
    *   Если `Page MAX_TRX_ID` >= вашего `min_trx_id` — **Covering Index не работает**. Движок обязан взять Primary Key, пойти в кластерный индекс (Look up), найти строку, проверить `DB_TRX_ID` и, возможно, откатиться по Undo Log.

**Практический вывод:** Интенсивная запись в таблицу убивает эффективность "Covering Index" сканирований на чтение, даже если вы читаете другие колонки, потому что поднимает `MAX_TRX_ID` на страницах индекса.

### 2.6. Purge System: Сборщик мусора

В PostgreSQL VACUUM запускается явно или по таймеру. В InnoDB **Purge** — это непрерывный поток (или несколько потоков).

**Задачи Purge Thread:**
1.  **Physical Delete:** Находит записи с битом `delete-mark`, которые больше не видны ни одной активной транзакции (Oldest View), и физически удаляет их из страниц индексов (освобождает место).
2.  **Undo Log Truncate:** Удаляет страницы Undo Log, которые стали слишком старыми.

**History List Length (HLL):**
Это метрика "технического долга" базы данных.
*   Если транзакция висит открытой часами, Purge не может удалить Undo Logs, созданные *после* начала этой транзакции (так как они могут понадобиться ей для Consistent Read).
*   Undo Tablespace пухнет.
*   Чтение замедляется (из-за длинных цепочек версий).
*   **Смерть производительности:** Когда HLL достигает миллионов, InnoDB начинает тратить больше времени на обход списков версий, чем на полезную работу.

---
### Резюме для Solution Architect:

MySQL InnoDB (в отличие от PG) оптимизирован под **READ COMMITTED** коротких транзакций и **UPDATE-in-Place**.

*   **Плюс:** Компактность данных (нет bloat в основной таблице).
*   **Плюс:** Невероятно быстрый доступ к *последней* версии данных.
*   **Цена:** Сложность при чтении *старых* данных (Random I/O в Undo Log).
*   **Риск:** Вторичные индексы требуют lookup в основную таблицу, если данные меняются.
*   **Главный враг:** Длинные транзакции. В Postgres длинная транзакция мешает вакууму вычистить *мертвые* строки. В InnoDB длинная транзакция заставляет хранить *историю изменений* всего мира, что может положить I/O подсистему при попытке чтения.

## 3. LSM-Tree MVCC (RocksDB, CockroachDB, ClickHouse)

LSM-деревья (Log-Structured Merge-trees) — это не просто "другой способ хранения". Это смена парадигмы с "изменяемого состояния" (Mutable State, как B-Tree) на "неизменяемую историю событий" (Immutable Event History). MVCC здесь — это не дополнительная фича, а **естественное состояние данных**.

В B-Tree движках (Postgres/InnoDB) мы пытаемся поддерживать иллюзию, что у записи есть *одно* текущее состояние, пряча старые версии в Undo Log или Heap.
В LSM-движках мы принимаем тот факт, что данные — это река изменений. Файлы на диске (SSTables) **неизменяемы** (Immutable). Мы никогда не перезаписываем старые данные, мы лишь перекрываем их новыми слоями.

### 3.1. Internal Key: Генетика MVCC
В LSM-движке, когда приложение пишет `Key="User1"`, база данных физически сохраняет совсем другое. Понятие "Ключ" трансформируется.

**Физический ключ (Internal Key):**
Это композитная структура: `User Key` + `Sequence Number` + `Value Type`.

```text
| User Key (Var) | Sequence Number (8 bytes) | Type (1 byte) |
| "User1"        | 1050                      | PUT           |
```

*   **User Key:** То, что видит приложение.
*   **Sequence Number (SeqNum):** Глобально монотонно возрастающий счетчик (аналог LSN или TRX_ID). Каждая операция записи получает свой уникальный номер. Это и есть временная метка версии.
*   **Value Type:** Тип операции (`PUT`, `DELETE`, `MERGE`, `RANGE_DELETE`).

**Сортировка (Критически важно!):**
Ключи сортируются так:
1.  По `User Key` (возрастание): "A" перед "B".
2.  По `Sequence Number` (**убывание**): 1050 перед 1049.

**Зачем убывание?**
Когда итератор ищет `User1`, он сначала натыкается на запись с *наибольшим* SeqNum (самую свежую). Это позволяет прервать поиск сразу, как только найдена первая валидная запись, не сканируя всю историю вглубь.

### 3.2. Write Path: Слепая запись (Blind Writes)
В отличие от B-Tree, где для UPDATE часто нужно сначала прочитать страницу (чтобы заблокировать запись), LSM делает "слепую запись".

**Сценарий:** `UPDATE users SET val=2 WHERE id=1` (SeqNum транзакции = 200).
1.  Движок **не проверяет**, существует ли `id=1` (если нет уникальных констрейнтов).
2.  Он просто добавляет в MemTable (структура в памяти, обычно SkipList) новую запись:
    `InternalKey("id=1", 200, PUT) -> Value(2)`

**Сценарий:** `DELETE FROM users WHERE id=1` (SeqNum = 201).
1.  Ничего не удаляется с диска.
2.  В MemTable добавляется **Tombstone** (Могильный камень):
    `InternalKey("id=1", 201, DELETE) -> (empty)`

**Архитектурное следствие (Write Amplification = 1):**
Запись в LSM экстремально быстрая. Это просто append в память + append в WAL. Нет случайного чтения. MVCC здесь не создает оверхеда на запись (в отличие от PG, где нужно копировать кортеж).

### 3.3. Read Path & Snapshot Isolation
Чтение в LSM — это сложная процедура слияния (Merge) данных из разных уровней (MemTable, L0, L1...). Именно здесь мы платим цену за быструю запись.

**Понятие Snapshot:**
Снэпшот в LSM — это просто одно число: `SnapshotSequenceNumber`.
Например, если мы начали транзакцию на `SeqNum=150`, мы хотим видеть базу данных в состоянии "как она была на шаге 150".

**Алгоритм чтения (Point Lookup for "id=1"):**
Движок создает `MergingIterator`, который смотрит параллельно в MemTable и все перекрывающиеся SSTables.

1.  Кандидаты сортируются по Internal Key.
    *   Кандидат А: `("id=1", 200, PUT)` — из MemTable
    *   Кандидат Б: `("id=1", 140, PUT)` — из L1 SSTable
    *   Кандидат В: `("id=1", 100, PUT)` — из L2 SSTable
2.  **Фильтрация видимостью:**
    *   Наш `Snapshot = 150`.
    *   Кандидат А имеет `SeqNum 200`. Это > 150. Это данные "из будущего". **Игнорируем (Skip).**
    *   Кандидат Б имеет `SeqNum 140`. Это <= 150. **Это наша версия!**
    *   Кандидат В имеет `SeqNum 100`. Он "затенен" (shadowed) кандидатом Б. Мы его не видим.
3.  **Результат:** Возвращаем значение Кандидата Б.

**Проблема Tombstones (Delete Amplification):**
Если бы Кандидат Б был типом `DELETE` (Tombstone), движок понял бы, что на момент 150 запись удалена, и вернул бы `Not Found`.
*Опасность:* Если вы удалили миллион записей, у вас на диске лежат миллионы Tombstones. Range Scan (сканирование диапазона) будет вынужден читать и обрабатывать эти "пустышки", чтобы понять, что данных нет. Это убивает производительность запросов вида `SELECT * ... LIMIT 10`, если в начале диапазона много удалений.

### 3.4. Compaction: Сборщик мусора и Хранитель времени
Compaction (уплотнение) — это единственный механизм, который физически удаляет старые версии данных. Это аналог `VACUUM` в PG и `Purge` в MySQL, но работает глобально над файлами.

Процесс Compaction берет файлы с уровня N, сливает их с файлами уровня N+1, и создает новые файлы уровня N+1.

**Логика очистки (MVCC Garbage Collection):**
Во время слияния движок смотрит на каждую запись:
1.  **Drop Rule 1 (Shadowing):** Если у нас есть `("id=1", 200)` и `("id=1", 100)`, и *самый старый активный снэпшот* в системе > 200, то версию 100 можно безопасно выбросить. Она никому не нужна.
2.  **Drop Rule 2 (Tombstones):** Если мы видим Tombstone `("id=1", DELETE)`, и под ним (на более низких уровнях) больше нет записей с ключом `id=1`, то сам Tombstone можно выбросить (мы стерли историю существования ключа). *Нюанс:* Это можно делать только на самом последнем уровне (Bottommost Level).

**Space Amplification (Раздувание места):**
Пока Compaction не прошел, старые версии (Garbage) хранятся на диске. В LSM-движках Space Amplification (отношение размера данных на диске к реальному размеру данных) обычно выше, чем в B-Tree, и может достигать 1.1x - 2x в зависимости от стратегии.

### 3.5. Оптимизация: Bloom Filters
Для MVCC в LSM критически важны фильтры Блума.
Каждый SSTable файл имеет свой Bloom Filter — вероятностную структуру, отвечающую на вопрос: *"Может ли ключ X быть в этом файле?"*.

**Сценарий чтения:**
Мы ищем `id=1` (Snapshot 150).
У нас есть 10 файлов SSTable на уровне L0 (они перекрываются по диапазонам ключей). Без фильтров нам пришлось бы читать каждый файл (Random Read).
С фильтрами:
1.  Проверяем фильтр Файла 1 -> "Нет". (Пропускаем файл, экономим I/O).
2.  Проверяем фильтр Файла 2 -> "Возможно". (Читаем блок индекса, ищем ключ).
3.  Находим `("id=1", 145)`. Это валидная версия. Стоп.

### 3.6. Сравнение стратегий Compaction для Архитектора

Staff Engineer должен уметь выбирать стратегию под нагрузку:

| Характеристика          | Leveled Compaction (RocksDB default)                                         | Tiered / Universal Compaction (Cassandra/Scylla)             |
| :---------------------- | :--------------------------------------------------------------------------- | :----------------------------------------------------------- |
| **Структура**           | Один файл на уровень (кроме L0). Строго упорядочено.                         | Много файлов на уровень. Ленивое слияние.                    |
| **Read Amplification**  | **Низкая**. Минимум файлов для проверки. Хорошо для чтения.                  | **Высокая**. Нужно проверять много файлов при чтении.        |
| **Write Amplification** | **Высокая**. Одна запись перезаписывается 10-20 раз при движении по уровням. | **Низкая**. Файлы сливаются редко. Идеально для Write-Heavy. |
| **Space Amplification** | **Низкая** (оверхед ~10-20%). Старые версии убиваются быстро.                | **Высокая** (оверхед до 100% во время уплотнения).           |
| **MVCC Implications**   | Быстрее очищает старые версии данных.                                        | Старые версии живут дольше, занимая место.                   |
### 3.7. RocksDB: MVCC in Embedded Key-Value
RocksDB (и его форки) — это "ассемблер" современного базстроения. Он не дает ACID транзакций "из коробки" в привычном понимании (на несколько ключей), но дает примитивы для их построения.

**A. Snapshots & Pinned Data**
В RocksDB объект `Snapshot` — это легковесный указатель на конкретный `SequenceNumber`.
*   **Механика:** Когда вы создаете Снэпшот (Sequence=100), вы сообщаете процессу Compaction: *"Никогда не удаляй версии данных с Sequence >= 100, даже если есть более новые версии"*.
*   **Архитектурный риск:** Если приложение "забыло" отпустить (release) старый снэпшот, Compaction не сможет вычищать мусор во всей базе. Это приведет к **Space Amplification** и замедлению чтения (так как итераторам придется пропускать горы старых версий). В продакшене это частая причина инцидентов "out of disk space".

**B. Column Families (CF) & Atomicity**
RocksDB позволяет делить данные на "семейства колонок" (аналог таблиц или партиций).
*   **MVCC нюанс:** У каждого CF свой собственный LSM-дерево и свои Sequence Numbers.
*   **WriteBatch:** Чтобы обеспечить атомарность записи *между* разными CF (например, Index и Data), используется `WriteBatch`. Он гарантирует, что все записи получат *одинаковый* Sequence Number в WAL, обеспечивая согласованное чтение (All-or-Nothing).

**C. Merge Operators (Read-Modify-Write)**
Уникальная фича RocksDB. Вместо цикла `Get -> (in memory modify) -> Put`, который создает конфликты (Race Condition), вы делаете `Merge(Key, Delta)`.
*   **MVCC реализация:** Операция `Merge` записывается как новая версия (новый SeqNum). При чтении RocksDB собирает цепочку: `Base Value` + `Merge1` + `Merge2`... и "схлопывает" их на лету.
*   **Цена:** Сильно бьет по Read CPU, если цепочка мержей длинная.

### 3.8. CockroachDB: MVCC в распределенной системе (Pebble)
CockroachDB использует Pebble (Go-порт RocksDB), но слой MVCC там реализован значительно сложнее, так как система распределенная (Shared Nothing).

**A. Hybrid Logical Clock (HLC) вместо Sequence Number**
В распределенной системе нет единого атомного счетчика (это точка отказа). CockroachDB использует HLC — комбинацию физического времени (NTP) и логического счетчика.
*   **Ключ MVCC:** `Key + HLC Timestamp`.
*   **Смысл:** Это позволяет сравнивать порядок событий на разных узлах кластера с высокой точностью и поддержкой причинно-следственной связи (Causal Ordering).

**B. Write Intents (Намерения записи)**
В CockroachDB запись происходит в два этапа (2PC).
1.  **Write Intent:** Когда транзакция пишет данные, она кладет в LSM специальную запись-флаг "Intent" с временной меткой. Эта запись содержит ссылку на Transaction Record (статус транзакции).
2.  **Resolution:** Если другая транзакция (читатель) натыкается на Intent с меткой времени *ниже* своего снэпшота, она не может просто прочитать или игнорировать его. Она должна проверить статус транзакции-автора (Pending, Committed, Aborted).
    *   Если Committed — читатель "докатывает" значение (превращает Intent в обычное значение).
    *   Если Aborted — игнорирует.
    *   Если Pending — читатель ждет (или пытается сделать Push Transaction — отменить конкурента, если приоритет позволяет).

**C. Follower Reads & Closed Timestamps**
Это магия масштабирования чтения. Leader реплики (Raft Group) регулярно рассылает Followers метку **Closed Timestamp** (например, T-5 секунд).
*   **Суть:** "Я обещаю не принимать запись с временем меньше T-5s".
*   **MVCC профит:** Любой фолловер может обслуживать запросы на чтение с `AS OF SYSTEM TIME (T-6s)` локально, не обращаясь к лидеру. MVCC гарантирует, что данные неизменны.

### 3.9. ClickHouse: Async MVCC for OLAP
ClickHouse — это аналитическая база (Columnar Store). Здесь MVCC служит не для изоляции транзакций (ACID), а для **дедупликации и обновления данных** в асинхронном режиме.

**A. Mutation вместо Update**
В ClickHouse нет классического Update. Таблицы (обычно `MergeTree`) неизменяемы.
*   Команда `ALTER TABLE UPDATE` — это тяжелая операция (**Mutation**). Она асинхронно переписывает целые куски данных (Parts). Это не MVCC в транзакционном смысле, это пакетная обработка.

**B. Engines: ReplacingMergeTree & CollapsingMergeTree**
Для имитации поведения OLTP (Upsert) используются специальные движки:
*   **ReplacingMergeTree:** При слиянии (Merge) кусков данных оставляет только последнюю версию строки (по ключу сортировки), опираясь на колонку `ver` (версия).
    *   *Нюанс:* До момента слияния дубликаты физически существуют. `SELECT` вернет их все, если не добавить `FINAL` (что убивает производительность, так как форсирует merge-on-read).
*   **CollapsingMergeTree:** Реализует идею Tombstones вручную. Вы добавляете колонку `Sign` (+1 для Insert, -1 для Delete).
    *   Пользователь должен сам писать две строки при обновлении: старую с `-1` и новую с `+1`.
    *   При слиянии пары `+1/-1` аннигилируют (исчезают).

**C. Отсутствие Read Consistency**
Архитектор должен понимать: в ClickHouse (по умолчанию) **нет** глобальной консистентности снимка.
Если вы читаете данные во время активной вставки, вы можете увидеть часть данных из одного блока, и не увидеть из другого. MVCC здесь работает на уровне "Part" (куска данных), а не на уровне глобального состояния транзакции.

---
### Резюме для Solution Architect:

*   **LSM-Tree** реализует MVCC через добавление `Timestamp` к ключу. Это превращает базу данных в упорядоченный лог событий.
*   **Чтение в прошлое (Time Travel)** здесь работает "из коробки" и не требует Undo Logs или грязных страниц, просто нужно игнорировать записи с `SeqNum > Snapshot`.
*   **Главный компромисс:** LSM меняет Random I/O при записи (как в B-Tree) на CPU-интенсивный процесс Compaction и сложный Read Path.
*   **Эксплуатация:** Вы должны мониторить **количество Tombstones** (замедляют Range Scans) и **задержку Compaction** (если отстает, диск переполняется старыми версиями, а чтение деградирует).

Вы обладаете экспертным уровнем, если понимаете, как выбрать инструмент под задачу, основываясь на реализации MVCC:

1.  **PostgreSQL (MGA/Heap):** Идеален для сложных запросов, FK, и смешанной нагрузки. *Болевая точка:* Update-heavy workload (VACUUM не справляется, Bloat).
2.  **MySQL (Undo Log):** Идеален для OLTP с короткими транзакциями и updates по PK. *Болевая точка:* Long transactions (History List раздувается, убивает чтение).
3.  **RocksDB/LSM:** Идеален для Write-Intensive (IoT, Logs). *Болевая точка:* Read/Space Amplification и тюнинг Compaction.
4.  **CockroachDB:** Идеален для гео-распределенных транзакций. *Болевая точка:* Оверхед на разрешение конфликтов (Intents) и синхронизацию часов (Clock Skew).
5.  **ClickHouse:** Идеален для аналитики (Append-only). *Болевая точка:* Real-time Updates (их нет, есть костыли через ReplacingMergeTree, которые требуют CPU на слияние).

## 4. Enterprise & Cloud Patterns (Краткий обзор)

На уровне Staff Engineer вы столкнетесь с системами, где MVCC реализован нетривиально ради специфических целей: совместимости с легаси или экстремальной эластичности.

### 4.1. MS SQL Server: The "Side-Storage" Model (Row Versioning)

Исторически SQL Server был "блокировочником" (Pessimistic Concurrency: 2PL). MVCC (Snapshot Isolation / RCSI) был прикручен к нему позже (в 2005 году). Это породило уникальную архитектуру **Version Store**.

**Механика:**
В отличие от PostgreSQL (версии в той же таблице) или Oracle/InnoDB (версии в Undo сегментах движка), SQL Server сбрасывает старые версии строк в **TempDB**.

1.  **Tagging:** При включении RCSI, к каждой строке в основной таблице добавляется 14 байт метаданных (указатель + timestamp).
2.  **Copy-on-Write:** Когда транзакция обновляет строку:
    *   Старая версия целиком копируется в системную базу `tempdb` (в область Version Store).
    *   В основной странице остается новая версия с указателем на `tempdb`.
3.  **Traversal:** Читатели (Snapshot Readers) натыкаются на "свежую" версию, видят, что она изменена активной транзакцией, и идут по ссылке в `tempdb`.

**Architectural Consequence (The TempDB Bottleneck):**
Для архитектора это критический паттерн.
*   **Проблема:** `tempdb` — это глобальный общий ресурс. В нем живут временные таблицы, сортировки, хэш-джойны и... *версии строк всех баз данных инстанса*.
*   **Сценарий отказа:** Интенсивный UPDATE в одной базе данных может положить производительность *всего сервера*, забив пропускную способность дисков `tempdb`.
*   **Отличие от PG/MySQL:** В Postgres "мусор" размазан по таблицам. В MySQL — по Undo Tablespaces. В MSSQL он концентрируется в одном узком месте.

### 4.2. Oracle Database: The Cyclic Buffer (Undo Segments)

Oracle — это "отец" коммерческого MVCC. Его реализация построена на **SCN (System Change Number)** и циклических буферах.

**Механика:**
Undo данные пишутся в специально выделенные сегменты (Undo Tablespace). Эти сегменты работают как кольцевой буфер.
*   Транзакция пишет старое значение в Undo Segment.
*   Если место заканчивается, Oracle начинает перезаписывать самые старые, *уже закоммиченные* транзакции.

**Феномен ORA-01555 (Snapshot Too Old):**
Это кошмар любого DBA.
1.  Вы запускаете долгий отчет (Long Query) в 12:00 (SCN=100).
2.  В 12:30 агрессивный OLTP процесс обновляет таблицу и часто коммитит. Он заполняет весь Undo Tablespace и заходит на второй круг, перезаписывая Undo-записи от 12:05.
3.  В 12:45 ваш отчет доходит до блока, измененного в 12:05. Он видит ссылку на Undo, идет туда, чтобы восстановить версию на 12:00, но там *уже лежат данные от 12:35*.
4.  **Результат:** Данные физически потеряны. Oracle не может реконструировать прошлое. Транзакция падает с ошибкой.

**Tuning для архитектора:**
Параметр `UNDO_RETENTION` — это обещание базы хранить старые версии не менее N секунд. Архитектор должен рассчитывать размер диска под Undo так: `(Max Write TPS) * (Max Query Duration)`. В Postgres старые версии хранятся вечно (пока не придет Vacuum), в Oracle — пока их не вытеснят.

### 4.3. Cloud Native Storage (AWS Aurora, Alibaba PolarDB, Google AlloyDB)

Это современный стандарт для Highload ("The Log is the Database"). Здесь MVCC интегрирован в распределенный слой хранения.

**Проблема классики в облаке:**
В классике (PG/MySQL) при репликации Leader отправляет на Replica поток изменений (WAL/Binlog). Реплика должна прочитать этот поток, прочитать свои страницы с диска, применить изменения, записать страницы обратно. Это **Full Duplicate Execution**. Реплики всегда отстают и нагружают CPU/IO.

**Решение: Log-Structured Storage (Separation of Compute and Storage)**
1.  **Compute Node (Writer):** Генерирует только Redo Log записи. Он *не сбрасывает* (checkpoint) грязные страницы на диск. Он просто шлет лог на 6 узлов хранения (Storage Nodes).
2.  **Storage Node:** Это не просто диск. Это умный процесс. Он получает логи, складывает их в очередь.
3.  **Page Materialization (MVCC on demand):**
    *   Когда Compute Node (или Read Replica) хочет прочитать страницу `P` на момент времени `LSN=100`:
    *   Он посылает запрос стораджу: "Дай мне P @ 100".
    *   Сторадж берет базовую версию страницы (Snapshot) и накатывает на нее цепочку логов до LSN 100.
    *   Отдает готовую версию страницы.

**Global Consistency & Read Replicas:**
В этой архитектуре у реплик нет своих дисков и своих Undo-логов.
*   Writer периодически рассылает репликам метку "Consistency Point" (LSN, до которого безопасно читать).
*   Если Реплике нужны старые данные (Undo), она (в зависимости от реализации):
    *   (Aurora PostgreSQL) Использует Undo Segments, которые лежат в общем сторадже (как обычные данные).
    *   (Aurora MySQL) Использует Undo, управляемый кластером.

**Architectural Insight:**
*   **Плюс:** Crash Recovery мгновенный (не нужно проигрывать Redo Log, сторадж делает это фоново).
*   **Плюс:** Реплики почти не отстают (millisecond lag), так как им не нужно писать на диск.
*   **Минус:** Write Latency может быть выше из-за кворумной записи (4 из 6 узлов) по сети.

### 4.4. HTAP & In-Memory (SAP HANA / MS SQL Hekaton)

Отдельная ветвь эволюции, где MVCC оптимизирован для отсутствия блокировок (Lock-Free) в оперативной памяти.

**Механика:**
Нет дисковых страниц. Данные — это указатели в памяти.
*   Версии строк связаны в однонаправленный список прямо в памяти.
*   Каждая строка имеет Timestamp создания и Timestamp удаления.
*   **Валидация:** Вместо блокировок используется оптимистичная валидация при коммите. Если данные были изменены параллельной транзакцией — "First Committer Wins", проигравший получает Abort.

**Use Case:** Сверхбыстрый процессинг (Trading, Real-time Analytics), где overhead на буферный пул и дисковый I/O недопустим.

## 5. Architectural Decision Framework: Trade-offs & Anti-Patterns

Как архитектора, вас не должно волновать, какая база "лучше". Вас должно волновать, какая база обладает **Least Worst** (наименее болезненным) набором компромиссов для вашей специфической нагрузки.

Мы будем оценивать системы через призму трех фундаментальных метрик усиления (Amplification Factors):
1.  **Write Amplification (WA):** Сколько байт пишется на диск на 1 байт полезных данных.
2.  **Read Amplification (RA):** Сколько страниц/блоков нужно прочитать, чтобы найти 1 конкретную строку.
3.  **Space Amplification (SA):** Сколько места на диске занимают данные по сравнению с "чистым" объемом.

### 5.1. Матрица фундаментальных различий (The Physics of Data)

| Характеристика | PostgreSQL (Heap + MGA) | MySQL InnoDB (B+Tree + Undo) | LSM-Trees (RocksDB/Cockroach) |
| :--- | :--- | :--- | :--- |
| **Структура хранения** | **Heap (Куча)**. Данные лежат неупорядоченно. Индекс — это отдельная сущность. | **Clustered Index**. Данные лежат внутри B+Tree Первичного ключа. | **LSM-Tree**. Сортированные файлы (SST) + MemTable. |
| **Secondary Indexes** | Указывают на физический адрес (TID). **Быстрое чтение**, дорогая поддержка при Split страниц. | Указывают на Primary Key. **Требуют Double Lookup** (проход по PK), но стабильны при перемещении данных. | Указывают на Primary Key. Double Lookup. |
| **MVCC Read Cost** | **Низкая (RA ~ 1)**. Версии лежат в том же блоке (обычно). Hint Bits ускоряют проверки. | **Вариативная (RA >= 1)**. Требует прыжков в Undo Log (Random I/O) для старых версий. | **Высокая (RA >> 1)**. Merge-on-Read. Нужно проверить MemTable + L0...LN файлы. |
| **MVCC Write Cost** | **Высокая (WA High)**. Update копирует всю строку + обновляет индексы (если не HOT). | **Средняя (WA Medium)**. Update in-place. Пишется только REDO + UNDO record. | **Минимальная (WA Low)**. Append-only в память. Идеально для записи. |
| **Space Waste (Bloat)** | **High**. Мертвые кортежи в основных файлах. Требует Vacuum. | **Low**. Мертвые версии в Undo Log (удаляются быстро). Возможна фрагментация страниц. | **Medium**. Старые версии живут до Compaction. Space Amp ~1.1x - 2x. |
| **Traffic Pattern** | Mixed OLTP, Complex Queries, GIS, Arrays. | Point-Lookup, Update-Heavy (Single Row), "WebScale". | High Ingest Rate, Time-Series, Geo-Distributed. |

### 5.2. Сценарии и Архитектурные Выборы (Use Cases)

Разберем конкретные паттерны нагрузки и поведение движков.

#### Сценарий А: "The Queue" (БД как очередь задач)
*Нагрузка:* Massive Insert -> Short Wait -> Delete.
*   **PostgreSQL:** ☠️ **Смерть**. Интенсивные DELETE порождают огромное количество мертвых кортежей. Autovacuum будет работать нон-стоп, сжигая I/O. Индексы распухнут.
*   **MySQL:** ⚠️ **Плохо**. Удаление оставляет "дырки" в страницах индекса. Требуется периодическая перестройка таблицы (`OPTIMIZE TABLE`), иначе Buffer Pool будет забит полупустыми страницами.
*   **LSM:** ✅ **Хорошо (с оговоркой)**. Insert и Delete — это просто append. Compaction вычистит мусор эффективно, если настроен TTL.
    *   *Совет архитектора:* Не используйте БД как очередь. Используйте Kafka/RabbitMQ. Если *приходится* — используйте Партиционирование (Partitioning) и удаляйте партиции целиком (`DROP TABLE`), это O(1).

#### Сценарий Б: "User Counters" (High-Frequency Updates)
*Нагрузка:* `UPDATE stats SET hits = hits + 1 WHERE id = X`.
*   **PostgreSQL:** ⚠️ **Рискованно**. Если поле индексировано — это катастрофа (Write Amplification). Если не индексировано (HOT update) — работает отлично, пока строка помещается на странице. Вам нужно выставить `FILLFACTOR = 70`, теряя 30% места на диске превентивно.
*   **MySQL:** ✅ **Идеально**. Изменение происходит in-place. Размер Undo записи минимален. Блокировки строк эффективны.
*   **LSM:** ❌ **Проблема**. Каждый `+1` создает новую запись. Read-Modify-Write цикл. При чтении придется мержить тысячи версий одной записи. Нужен специфический оператор `Merge` (как в RocksDB).

#### Сценарий В: "Wide Table / JSON Document Store"
*Нагрузка:* Таблица с 50 колонками или тяжелым JSONB. Часто обновляется только *одно* поле (status).
*   **PostgreSQL:** ❌ **Write Amplification**. Обновление статуса (1 байт) копирует всю строку (2 КБ) в новый блок. Генерирует 2 КБ WAL. Генерирует I/O.
    *   *Mitigation:* Вынести часто обновляемые поля в отдельную таблицу (1:1 relation).
*   **MySQL:** ✅ **Эффективно**. Обновляет только измененную колонку (если она не переменной длины, вызывающей сплит страницы).
*   **LSM:** ⚠️ **Зависит от реализации**. Обычно пишет полный новый ключ-значение.

#### Сценарий Г: "Pagination & Scans" (Глубокий офсет)
*Нагрузка:* `SELECT * FROM data ORDER BY id LIMIT 10 OFFSET 1000000`.
*   **MySQL:** ✅ **Быстро**. Кластерный индекс гарантирует, что данные лежат физически рядом. Sequential Read.
*   **PostgreSQL:** ⚠️ **Средне**. Данные в куче могут быть разбросаны (корреляция физического порядка и логического id падает со временем).
*   **LSM:** ☠️ **Опасно**. Если в диапазоне много Tombstones (удаленных записей), скан будет читать и отбрасывать мусор, тратя CPU и I/O впустую. Чтение может быть в 10-50 раз медленнее записи.

### 5.3. Failure Modes (Как системы умирают в продакшене)

Staff Engineer отличается тем, что знает не только как система работает, но и как она ломается.

1.  **PostgreSQL: Transaction ID Wraparound & Vacuum Freeze**
    *   *Симптом:* База переходит в режим Read-Only, требуя остановки и Single User Mode вакуума.
    *   *Причина:* Автовакуум не успевал "морозить" старые транзакции из-за высокой нагрузки или долгих блокировок.
    *   *Превенция:* Мониторинг `age(datfrozenxid)`. Отсутствие транзакций длиннее нескольких минут.

2.  **MySQL: History List Length Explosion**
    *   *Симптом:* Простейший `SELECT * FROM small_table WHERE id=1` начинает выполняться секунды. CPU 100%.
    *   *Причина:* Одна забытая открытая транзакция (аналитик ушел на обед, не закрыв консоль, или повисший бэкап) держит старый Read View. Undo Log вырос до гигабайт. При чтении InnoDB бежит по цепочке версий.
    *   *Превенция:* `Kill idle transactions`. Мониторинг HLL.

3.  **LSM (RocksDB): Write Stall & Compaction Debt**
    *   *Симптом:* Запись внезапно падает до 0 или становится очень медленной.
    *   *Причина:* MemTable забита, L0 забит. Compaction threads не успевают разгребать завалы (диск медленный или CPU не хватает). Движок блокирует запись ("Stall"), чтобы дать Compaction шанс догнать.
    *   *Превенция:* Тюнинг количества потоков компакции, быстрые диски (NVMe), контроль размера записи.

### 5.4. Итоговая рекомендация по выбору БД

**Выбирайте PostgreSQL, если:**
*   Вам нужен "швейцарский нож": SQL, JSON, GIS, Foreign Data Wrappers.
*   Нагрузка — сложная аналитика + OLTP (HTAP).
*   Вы готовы инвестировать время в настройку Autovacuum и архитектуру индексов.
*   У вас надежные быстрые диски (Random I/O будет много).

**Выбирайте MySQL (InnoDB), если:**
*   У вас классический Web-профиль: 90% чтение по PK, 10% запись.
*   Вам нужна максимальная плотность данных (Clustered Index).
*   Вы хотите предсказуемую производительность простых запросов.
*   Вы используете репликацию (GTID и Binlog replication проще в эксплуатации для HA).

**Выбирайте LSM (CockroachDB/Scylla/RocksDB), если:**
*   **Write Throughput** — ваше главное требование (IoT, Event Logging).
*   Данных больше, чем влезает на один сервер (нужен Sharding из коробки).
*   Вам нужна Geo-Distribution (Active-Active в разных дата-центрах).

Понимание этих внутренних механик MVCC переводит вас из разряда "пользователь БД" в разряд "архитектор систем хранения".

## 6. Practical Engineering: Troubleshooting & Tuning

Проблемы с MVCC (Bloat, HLL, Stalls) коварны тем, что они **не линейны**.
Система работает стабильно при нагрузке 40%, 50%, 60%... а на 65% происходит "обрыв скалы" (Cliff Edge): сборщик мусора перестает успевать, I/O забивается чтением старых версий, производительность падает в 100 раз.

Ваша задача — обнаружить приближение к обрыву.

## 6.1. PostgreSQL: Vacuum Engineering & Bloat Management

В Postgres "мусор" (Dead Tuples) лежит в тех же файлах, что и полезные данные. Если Autovacuum проигрывает гонку с записью, таблица превращается в "швейцарский сыр", где 90% объема — воздух.

### A. Observability: Правильные метрики (KPIs)
Не смотрите просто на `n_dead_tup`. Этого мало.

1.  **Dead Tuple Ratio (Коэффициент раздувания):**
    ```sql
    SELECT relname, n_live_tup, n_dead_tup,
           ROUND(n_dead_tup::numeric / GREATEST(n_live_tup, 1), 2) AS bloat_ratio,
           last_autovacuum
    FROM pg_stat_user_tables
    WHERE n_dead_tup > 10000
    ORDER BY bloat_ratio DESC;
    ```
    *   *Threshold:* Если Ratio > 0.1 (10%) на таблицах > 10GB — это повод для вмешательства. Если Ratio > 1.0 (мусора больше, чем данных) — это пожар.

2.  **Vacuum Gap (Отставание вакуума):**
    Мониторьте транзакции, которые блокируют очистку.
    ```sql
    SELECT pid, datname, usename, state, backend_xmin, query_start, query
    FROM pg_stat_activity
    WHERE backend_xmin IS NOT NULL
    ORDER BY age(backend_xmin) DESC;
    ```
    *   *Staff Insight:* Поле `backend_xmin` показывает "горизонт событий" этой транзакции. Пока она жива, Postgres **не может удалить** ни одну версию строки, созданную или удаленную *после* этого xmin. Одна висящая транзакция `IDLE IN TRANSACTION` может за сутки раздуть базу в 2 раза.

3.  **IO Impact:**
    Включите `log_autovacuum_min_duration = 0` (или 250ms) временно, чтобы видеть в логах, сколько страниц вакуум прочитал и сколько выкинул. Если `removed` мало, а `scanned` много — вакуум работает вхолостую (кто-то держит старый снимок).

### B. Tuning Strategy: Aggressive Autovacuum
Дефолтные настройки Postgres (`autovacuum_vacuum_scale_factor = 0.2`) сделаны для баз размером 100 МБ. Для терабайтных баз они **вредны**. Вакуум приходит слишком редко и работает слишком медленно.

**Production Checklist:**
1.  **Снизьте порог запуска:**
    *   `autovacuum_vacuum_scale_factor`: 0.01 (1%) или 0.02.
    *   `autovacuum_vacuum_threshold`: 10000.
    *   *Цель:* Чистить чаще, но мелкими порциями.

2.  **Увеличьте бюджет I/O:**
    *   `autovacuum_vacuum_cost_limit`: Поднимите с дефолтных 200 до 1000-5000 (в зависимости от SSD/NVMe).
    *   `autovacuum_vacuum_cost_delay`: 2ms (стандарт).
    *   *Физика:* Это "дроссель". Если лимит низкий, вакуум постоянно спит, давая фору писателям. На быстрых дисках вакуум должен работать агрессивно.

3.  **Параллелизм:**
    *   `autovacuum_max_workers`: Не ставьте много (по дефолту 3). Каждый воркер потребляет `maintenance_work_mem` и I/O. Лучше 3 агрессивных воркера, чем 10 вялых, которые дерутся за диск.

### C. Advanced Troubleshooting: pg_repack
Если таблица уже раздулась (`bloat_ratio > 0.5`), обычный `VACUUM` не вернет место операционной системе (он лишь пометит его свободным для новых данных). `VACUUM FULL` блокирует таблицу эксклюзивно.

*   **Инструмент:** Используйте **pg_repack** (или `pg_squeeze`).
*   **Механика:** Он создает новую таблицу, строит индексы, копирует данные, и подменяет файлы, удерживая лишь короткую блокировку в конце.
*   **Риск:** Требует свободного места на диске x2 от размера таблицы. Генерирует огромный WAL трафик (влияет на репликацию!).

## 6.2. MySQL (InnoDB): Purge Lag & History List Horror

В InnoDB главная проблема — не физический размер файла (хотя `ibdata` тоже пухнет), а **длина цепочки версий** в Undo Log.

### A. Observability: The Kill Metric
Метрика №1 для любого MySQL DBA: **History List Length (HLL)**.

```sql
SHOW ENGINE INNODB STATUS\G
-- Ищем в секции TRANSACTIONS:
-- History list length 2540
```
Или через `information_schema`:
```sql
SELECT count
FROM information_schema.innodb_metrics
WHERE name = 'trx_rseg_history_len';
```

**Interpretation:**
*   **< 10,000:** Здоровая система.
*   **> 100,000:** Начинается деградация чтения (CPU растет, так как нужно пробегать длинные списки Undo).
*   **> 1,000,000:** "Спираль смерти". Purge Thread не справляется. Буферный пул забивается грязными страницами undo. Shutdown может занять часы (пока не вычистит undo).

### B. Troubleshooting: Кто держит Purge?
Purge Thread не может удалить Undo Logs, которые старше самого старого активного Read View.

1.  **Найти виновника:**
    ```sql
    SELECT trx_id, trx_state, trx_started, trx_query,
           TIME_TO_SEC(TIMEDIFF(NOW(), trx_started)) as duration_sec
    FROM information_schema.innodb_trx
    ORDER BY trx_started ASC;
    ```
2.  **Типичные убийцы:**
    *   `mysqldump` без `--single-transaction --quick` (или просто долгий дамп).
    *   Аналитический запрос (OLAP) на слейве? Нет, внимание: **Репликация!**
    *   *Expert Trap:* Если у вас Replica Lag (SQL Thread отстает), и вы используете `log_slave_updates` или каскадную репликацию, Undo Log на реплике может не очищаться. Но чаще проблема на мастере: долгая транзакция просто блокирует вычистку.

### C. Tuning: Backpressure (Обратное давление)
Что делать, если Purge не успевает за потоком INSERT/UPDATE? Нужно замедлить писателей.

1.  **`innodb_max_purge_lag`**:
    *   Установите значение (например, 1000000).
    *   Если HLL превысит это значение, InnoDB начнет добавлять искусственную задержку (sleep) к каждой DML операции (`dml_delay`).
    *   *Результат:* TPS записи падает, но система не умирает, давая Purge шанс догнать.

2.  **`innodb_purge_threads`**:
    *   По умолчанию 4. На многоядерных серверах с NVMe можно ставить 8-16. Но следите за `mutex contention` на `dict_sys` (системный словарь).

## 6.3. LSM-Trees (RocksDB/CockroachDB): Write Stalls

В LSM мире "смерть" наступает, когда диск не успевает "уплотнять" (Compact) файлы. Система включает защиту и **останавливает запись**.

### A. Observability: Stalls & L0 Saturation
В RocksDB (и аналогах) есть уровни (Levels). L0 — самый опасный.
Если MemTable сбрасывается на диск быстрее, чем L0 компактится в L1, количество файлов на L0 растет.

**Метрики для мониторинга:**
1.  **L0 File Count:** Если приближается к `level0_slowdown_writes_trigger` — это желтая зона. Если достигло `level0_stop_writes_trigger` — это полная остановка (Stall).
2.  **Compaction Pending Bytes:** Очередь байт, ожидающих слияния.
3.  **Write Stall Duration:** Время, которое приложение простояло в ожидании.

### B. Tuning: Managing the Shape of the Tree
Ваша цель — баланс между Write Amp (WA) и скоростью сброса.

1.  **Parallelism:**
    *   `max_background_jobs` (или `max_background_compactions`): Увеличьте, если CPU простаивает, а L0 растет.
    *   *Риск:* Компакция — это "IO storm". Слишком много потоков могут положить диск, и тогда `User Read Latency` улетит в космос.

2.  **Write Buffer Size (MemTable):**
    *   Увеличение размера MemTable (например, с 64MB до 256MB) уменьшает частоту сбросов на L0 -> уменьшает давление на компакцию L0->L1.
    *   *Цена:* Потребление RAM и дольше Recovery при рестарте (нужно проиграть больший WAL).

3.  **Compression:**
    *   Используйте легкое сжатие (LZ4/Snappy) на верхних уровнях (L0-L2) и сильное (Zstd) на нижних (Lmax). Это снижает нагрузку на CPU при частых компакциях верхних уровней.

## 6.4. Summary Checklist for Solution Architect

Если вас вызвали на инцидент "База тормозит", действуйте по алгоритму MVCC:

1.  **Postgres:**
    *   `pg_stat_activity` -> Ищем долгие транзакции (`xact_age`). Убиваем.
    *   `pg_stat_user_tables` -> Ищем Bloat. Планируем `pg_repack`.
    *   Проверяем диск: `iostat`. Если 100% util, и это VACUUM — тротлим вакуум (уменьшаем cost limit).
2.  **MySQL:**
    *   `SHOW ENGINE INNODB STATUS` -> Смотрим `History List Length`.
    *   `information_schema.innodb_trx` -> Ищем старую транзакцию. Убиваем.
    *   Если HLL растет, а транзакций нет — проверяем Purge threads.
3.  **RocksDB/LSM:**
    *   Смотрим логи: ищем ключевое слово `Stall` или `Stop`.
    *   Смотрим граф L0 files.
    *   Если Stall — временно увеличиваем лимиты триггеров или добавляем потоков компакции (если есть CPU).

## 7. MVCC Internals: The Architect’s Summary Checklist 

Этот чек-лист разделен на этапы жизненного цикла системы: от выбора движка до эксплуатации.

### 7.1. Phase 1: Architectural Selection (Выбор движка под физику MVCC)
*Вы не выбираете базу по синтаксису SQL. Вы выбираете её по тому, как она платит налог на конкурентность (Concurrency Tax).*

*   [ ] **Оцените профиль записи (Write Pattern):**
    *   **Update-Heavy (In-Place):** Если вы постоянно обновляете счетчики или статусы по Primary Key — **MySQL (InnoDB)** выиграет за счет Update-in-Place и коротких Undo-цепочек.
    *   **Insert-Only / Log Data:** Если это поток событий — **LSM (RocksDB/ClickHouse)**. B-Tree умрет от фрагментации и Random Writes.
    *   **Complex Mixed Workload:** Если нужны FK, сложные индексы и транзакции, затрагивающие много таблиц — **PostgreSQL**. Но закладывайте +30-50% диска на Bloat и WAL.
*   [ ] **Оцените цену "чтения прошлого" (Time Travel Cost):**
    *   Нужны ли долгие аналитические запросы на OLTP мастере?
    *   Если **ДА**: Oracle или Postgres (версии лежат в данных, доступ быстрый, но риск Bloat/Snapshot Too Old).
    *   Если **НЕТ**: MySQL (Undo Log оптимизирован под быстрый откат, а не долгое чтение).
*   [ ] **Secondary Indexes Impact:**
    *   Помните: в **PostgreSQL** любой не-HOT апдейт пишет во *все* индексы.
    *   В **MySQL/LSM** апдейт некластерных полей дешевле (не трогает PK), но чтение требует Double Lookup (Index -> PK -> Row).

### 7.2. Phase 2: Schema & Code Design (Разработка с учетом MVCC)
*Как писать код, чтобы не убить сборщик мусора.*

*   [ ] **Transaction Hygiene (Гигиена транзакций):**
    *   **Strict Limit:** Никаких транзакций длительностью > 5-10 секунд в OLTP.
    *   **No User Input:** Никогда не держите транзакцию открытой, ожидая ввода пользователя или ответа внешнего HTTP API. Это остановит Vacuum/Purge.
    *   **Batching:** Разбивайте массивные `DELETE` / `UPDATE` на пачки (по 1000-5000 строк). Это даст шанс Autovacuum/Purge подчистить хвосты между пачками.
*   [ ] **PostgreSQL Specific:**
    *   **HOT Optimization:** Если таблица часто обновляется, создавайте её с `FILLFACTOR = 70-80`.
    *   **Indexing:** Не индексируйте колонки, которые часто обновляются (timestamp, status), если это не критически необходимо. Это убивает HOT.
*   [ ] **MySQL Specific:**
    *   **Primary Key:** Он должен быть маленьким (int/bigint). Он копируется во все вторичные индексы и в Undo Log. UUID в качестве PK — это убийство производительности MVCC и I/O.
*   [ ] **LSM Specific:**
    *   **Blind Writes:** Используйте идемпотентность. `INSERT ON CONFLICT DO UPDATE` дороже, чем простой `INSERT` (нужно чтение). Избегайте `Read-Modify-Write` циклов на клиенте.

### 7.3. Phase 3: Operational Guardrails (Эксплуатация)
*Метрики, которые отличают "живую" базу от "зомби".*

*   [ ] **PostgreSQL Monitoring:**
    *   [ ] `pg_stat_activity.xact_age` — алерт на транзакции старше 1 минуты.
    *   [ ] `pg_stat_user_tables.n_dead_tup` / `n_live_tup` — алерт на Bloat Ratio > 20%.
    *   [ ] `pg_stat_progress_vacuum` — мониторинг прогресса вакуума.
*   [ ] **MySQL Monitoring:**
    *   [ ] `History List Length` (HLL) — критический алерт при > 100,000.
    *   [ ] `Innodb_rows_read` vs `Innodb_rows_updated` — если отношение растет при простых запросах, значит, мы сканируем длинные Undo-цепочки.
*   [ ] **LSM Monitoring:**
    *   [ ] `L0 Files Count` — индикатор Write Stall.
    *   [ ] `Compaction Pending Bytes` — если растет, диск не справляется.
    *   [ ] `Number of Tombstones` — если много, Range Scan деградирует.

### 7.4. The Golden Rules of MVCC (Ментальная модель)

1.  **Удаление — это Ложь:** `DELETE` не освобождает место мгновенно. Это `INSERT` (tombstone/dead tuple). Место освобождается только асинхронным процессом (Vacuum/Purge/Compaction).
2.  **Обновление — это Копирование:** В мире MVCC нет "перезаписи". Есть создание новой версии. Это всегда стоит I/O.
3.  **Читатели блокируют Очистку:** Если кто-то читает прошлое, база не может удалить мусор. Конфликт Reader vs Garbage Collector — главная причина раздувания баз.
4.  **Write Amplification неизбежен:** Вы всегда платите либо местом (Postgres), либо CPU при чтении (LSM), либо сложным I/O паттерном (MySQL). Серебряной пули нет.

**TL;DR**: Выбор между строкой и колонкой — это выбор между **Latnecy** (доставка одной записи) и **Throughput** (сканирование миллиардов).
*   **Columnar (DSM)**: Идеально для OLAP. Данные сжаты по типу, CPU использует SIMD (Vectorization) для обработки массивов. Главная проблема — **Tuple Reconstruction** (сборка атрибутов обратно в строку).
*   **Row-oriented (NSM)**: Идеально для OLTP. Данные лежат локально для кэша CPU при доступе к одной сущности.
*   **Dremel Algorithm**: Революция от Google. Позволила хранить **иерархические** (вложенные) данные в плоском колоночном формате, используя *Repetition* и *Definition Levels*. Это основа Parquet и ORC.
*   **Vectorized Execution**: Отказ от модели Volcano (row-by-row) в пользу обработки батчей данных, чтобы амортизировать оверхед виртуальных вызовов и утилизировать конвейер процессора.

## 1. Физика хранения: NSM vs DSM

Выбор модели хранения (Storage Model) — это выбор того, как многомерная таблица проецируется на одномерное адресное пространство (файл на диске или массив в RAM).

### 1.1. NSM (N-ary Storage Model) — Row-Oriented
Классическая модель, используемая в OLTP движках (PostgreSQL Heap, MySQL InnoDB, Oracle). Данные хранятся последовательно запись за записью.

**Физическая раскладка (Page Layout):**
Представьте страницу памяти 4KB. В NSM кортеж хранится как непрерывный блок байтов:
`[Header | ID (8b) | Name (var) | Age (4b) | Salary (8b) | ... | Next Tuple]`

#### A. Преимущества: Локальность записи и CRUD
*   **Write-Optimized:** Вставка (`INSERT`) — это одна операция добавления в конец файла (или в свободное место страницы). Это максимально дешево.
*   **Cache Locality для OLTP:** Когда вы делаете `SELECT * FROM users WHERE id=1`, процессор загружает **Cache Line** (обычно 64 байта).
    *   В NSM, загрузив начало строки, вы с высокой вероятностью загрузили и остальные поля этой же строки в L1 кэш.
    *   Доступ к полям объекта происходит за такты процессора (L1 cache hit).

#### B. Проблема: Cache Pollution (Загрязнение кэша)
Для аналитики NSM катастрофичен.
Запрос: `SELECT AVG(Salary) FROM employees`.
1.  CPU запрашивает блок памяти.
2.  В L1 кэш попадает: `ID` (не нужно), `Name` (не нужно), `Salary` (нужно), `Bio` (не нужно, но занимает 1KB).
3.  **Wasted Bandwidth:** Если полезные данные (`Salary`) занимают 5% от размера строки, то 95% пропускной способности RAM и Диска тратятся на перекачку "мусора".
4.  **Vectorization Barrier:** SIMD инструкции не могут эффективно работать, так как данные лежат с "шагом" (stride), равным длине строки, а не подряд.

---
### 1.2. DSM (Decomposition Storage Model) — Column-Oriented
Модель для OLAP (ClickHouse, Vertica, Snowflake). Вертикальная декомпозиция: каждая колонка хранится в своей собственной структуре данных (файле или наборе страниц).

**Физическая раскладка:**
`File_ID:     [1, 2, 3, ...]`
`File_Name:   [Bob, Alice, John, ...]`
`File_Salary: [5000, 6000, 5500, ...]`

#### A. Преимущества: Плотность и Векторизация
*   **I/O Efficiency:** Для `AVG(Salary)` мы читаем *только* файл зарплат. Если таблица имеет 100 колонок, а нам нужно 3, мы сокращаем I/O в 33 раза.
*   **Data Skipping (Min/Max Index):** В заголовке блока колонки хранятся min/max значения. Если мы ищем `WHERE Salary > 10000`, а в блоке `max=6000`, мы пропускаем весь блок целиком, не читая его с диска.
*   **SIMD Friendly:** Массив зарплат в памяти лежит непрерывно. Мы можем загрузить 8 значений в 512-битный регистр AVX-512 одной инструкцией и сложить их.

#### B. Проблема: Tuple Reconstruction (Сборка кортежа)
Это "ахиллесова пята" колоночных баз.
Запрос: `SELECT Name, Salary, Age FROM users WHERE ID = 1`.
1.  Движок ищет смещение (RowID) для `ID=1` в колонке `ID`. Допустим, это RowID #500.
2.  Теперь нужно прыгнуть в файл `Name` по смещению #500. (Random Seek / Page Fault).
3.  Прыгнуть в файл `Salary` по смещению #500.
4.  Прыгнуть в файл `Age`.
5.  **Materialization:** Склеить эти куски в одну строку, чтобы отдать клиенту.
*   *Результат:* Для точечных чтений (`SELECT *`) DSM работает на порядки медленнее NSM из-за Random I/O и промахов кэша.

#### C. Compression as Performance Booster
В NSM данные гетерогенны: `Int -> String -> Date`. Они плохо жмутся.
В DSM колонка `Salary` содержит только `Integers`. У них низкая энтропия (информационная насыщенность).
*   **Пример:** Если зарплаты часто повторяются (5000, 5000, 5000), алгоритм RLE сжимает их в `(5000, 3)`.
*   **Expert Insight:** В современном железе **CPU быстрее, чем Память**. Чтение сжатых данных и распаковка их в L1 кэше часто *быстрее*, чем чтение несжатых данных из RAM. Сжатие в DSM — это способ увеличить эффективную пропускную способность памяти.

### 1.3. PAX (Partition Attributes Across) — Гибридная эволюция

В 2001 году (Ailamaki et al.) была предложена модель, ставшая стандартом де-факто для современных форматов Data Lake (Apache Parquet, ORC).

**Идея:** Сохранить преимущества колоночного доступа, но минимизировать стоимость реконструкции кортежа.

**Физическая раскладка (Row Groups):**
Файл делится на горизонтальные группы строк (Row Groups), например, по 10,000 строк.
*Внутри* каждой группы данные хранятся *поколонно*.

`[ -- Row Group 1 (Rows 1-10000) -- ]`
`  [ Column ID Chunk ... ]`
`  [ Column Name Chunk ... ]`
`  [ Column Salary Chunk ... ]`
`[ -- Row Group 2 (Rows 10001-20000) -- ]`
`  ...`

**Почему это стандарт:**
1.  **Limited Seek:** При сборке строки (Reconstruction) нам не нужно прыгать по всему диску. Все колонки для конкретной строки гарантированно лежат внутри одного блока (Row Group), который, скорее всего, уже в кэше.
2.  **Columnar Speed:** Внутри группы мы все еще можем использовать векторизацию и сжатие.
3.  **Parallelism:** Разные Row Groups можно обрабатывать параллельно на разных ядрах или машинах (как в Hadoop/Spark).

### Резюме для Архитектора

| Характеристика | NSM (Row Store) | DSM (Column Store) | PAX (Parquet/ORC) |
| :--- | :--- | :--- | :--- |
| **Основной паттерн** | OLTP (Write + Point Read) | OLAP (Deep Analytics) | Hybrid / Data Lake |
| **Узкое место** | RAM Bandwidth (читаем лишнее) | Tuple Reconstruction (клеим разное) | CPU (декомпрессия) |
| **Cache Behavior** | Good for single entity | Good for arrays/scans | Balanced |
| **Compression** | Слабое (Page compression) | Экстремальное (Lightweight + Heavy) | Высокое |
| **SIMD** | Сложно (Strided Access) | Нативно (Contiguous Memory) | Нативно (внутри чанков) |

## 2. Google Dremel: Nested Data in Columnar (The "Hard" Part)

До 2010 года считалось, что колоночное хранение (DSM) применимо только к плоским ("широким") таблицам. Хранение сложных иерархий (JSON, XML, Protobuf) требовало либо нормализации (взрыв Join-ов), либо хранения BLOB-ов (потеря колоночной скорости).

Google Dremel (paper 2010) совершил революцию, доказав, что **любую вложенную структуру можно "нашинковать" (Shredding) на плоские колонки без потери информации о структуре**, используя два целочисленных мета-значения: **Repetition Level** и **Definition Level**. Это легло в основу Apache Parquet и Apache ORC.

### 2.1. Фундаментальная проблема: Неоднозначность (Ambiguity)

Представьте схему: `Document (Repeated) -> Link (Repeated) -> URL (String)`.
У нас есть два документа:
1.  Doc1: `[ "a.com", "b.com" ]`
2.  Doc2: `[ "c.com" ]`

Если мы просто сохраним колонку `URL` как `["a.com", "b.com", "c.com"]`, мы потеряем границы.
*   Это `Doc1: [a, b], Doc2: [c]`?
*   Или `Doc1: [a], Doc2: [b, c]`?
*   Или `Doc1: [a, b, c], Doc2: []`?

Традиционный подход (разделители) или `Length`-префиксы неудобны для сжатия и произвольного доступа. Dremel решает это математически.

### 2.2. Repetition Level (R) — "Где начинается новый список?"

**Определение:** Уровень повторения (R) указывает, на какой глубине иерархии мы **продолжаем** существующий список, вместо того чтобы начать новый.
*   `R = 0`: Это начало совершенно новой записи (Root).
*   `R = Max`: Мы добавляем элемент в самый глубокий текущий список.
*   `0 < R < Max`: Мы закрыли текущий глубокий список и начали новый список на уровне R.

**Пример:**
Схема: `Message (Repeated) -> Language (Repeated) -> Code (String)`.
Данные:
1.  Msg1: `[ {Code: "en-us"}, {Code: "en-gb"} ]`  *(Два языка в одном сообщении)*
2.  Msg2: `[ ]` *(Пустое сообщение)*
3.  Msg3: `[ {Code: "ru"} ]`

Колонка `Code` и уровни `R`:
*   `"en-us"`: **R=0**. (Новое сообщение).
*   `"en-gb"`: **R=2** (Уровень `Language` повторяется. Мы все еще внутри Msg1).
*   `NULL` (для Msg2): **R=0** (Новое сообщение). *Примечание: как отличить пустой список от NULL, см. Definition Level.*
*   `"ru"`: **R=0** (Новое сообщение Msg3).

### 2.3. Definition Level (D) — "Это NULL или просто Отсутствие?"

В SQL `NULL` — это просто "нет значения". В деревьях "нет значения" может означать три разные вещи:
1.  Значение поля само по себе `NULL`?
2.  Родительский объект существует, но это опциональное поле пропущено?
3.  Родительский объект сам по себе не существует?

**Определение:** Уровень определения (D) показывает, сколько **опциональных** или **повторяющихся** полей в пути к значению **действительно существуют**.

**Пример:**
Схема: `Doc (Opt) -> Links (Opt) -> URL (Opt)`.
Максимальный D = 3 (существует Doc, существует Links, существует URL).

*   Значение `"google.com"`: **D=3**. (Путь полон).
*   Объект `Doc { Links { URL: null } }`: **D=2**. (`Links` существует, но `URL` не задан).
*   Объект `Doc { Links: null }`: **D=1**. (`Doc` существует, но `Links` не задан).
*   Объект `Doc: null` (или пустая строка): **D=0**.

**Expert Insight (Empty Lists):**
Именно Definition Level позволяет Parquet хранить **пустые списки**.
Если у вас есть `Links (Repeated) -> URL (String)`:
*   Пустой список `Links: []` кодируется как `NULL` с **D=1** (Links определен, но внутри ничего нет).
*   Отсутствующий список `Links: null` кодируется как `NULL` с **D=0**.

### 2.4. Reconstruction: The Finite State Machine (Конечный Автомат)

Как прочитать это быстро? Dremel предлагает строить FSM (Finite State Machine) для сборки записей.

1.  Мы читаем колонки параллельно.
2.  Для каждого значения смотрим на **R**.
    *   Если `R=0`, FSM сбрасывает состояние стека — началась новая запись.
    *   Если `R=Max`, FSM добавляет значение в текущий "хвост".
    *   Если `R < Max`, FSM "всплывает" (pop) по стеку вверх до уровня R и создает там новый список.
3.  Смотрим на **D**.
    *   Если `D < Max`, мы вставляем `NULL` или пустой объект на соответствующую глубину.

Это позволяет читать Parquet со скоростью **миллионы строк в секунду на одно ядро**, используя только дешевые целочисленные сравнения.

### 2.5. Bit-Packing Efficiency (Почему это не оверхед?)

Может показаться, что хранить два числа (R, D) для каждого значения — это накладно.
*   **Реальность:** Глубина вложенности JSON редко превышает 10-15 уровней.
*   Значит, `Max Definition Level` и `Max Repetition Level` обычно помещаются в 4 бита (или даже 1-2 бита).
*   Parquet использует **RLE + Bit-Packing** для R и D уровней.
*   Если у вас плоская таблица (нет вложенности), то R=0, D=1 для всех строк. RLE сжимает это в пару байт на миллион строк. Оверхед равен нулю.

### Резюме для раздела:

1.  **Column Striping (Shredding):** Процесс разложения JSON/Protobuf на плоские колонки.
2.  **R-Level:** Решает проблему границ списков (где кончается один и начинается другой).
3.  **D-Level:** Решает проблему различия между `NULL`, `Empty List` и `Missing Parent`.
4.  Эта технология позволяет BigQuery и ClickHouse (через `Array/Nested` типы) выполнять аналитику над полу-структурированными данными без предварительной нормализации.

## 3. Compression Techniques: Больше, чем Gzip

В колоночных базах сжатие выполняет две функции:
1.  **I/O Reduction:** Снижение нагрузки на диск.
2.  **Vectorized Execution Enabler:** Возможность выполнять фильтрацию (`WHERE`) и агрегацию (`SUM`) **прямо над сжатыми данными**, не распаковывая их в нативный формат. Это "Святой Грааль" производительности.

### 3.1. Lightweight Encoding (Оставляем данные в регистрах)

Эти алгоритмы работают на микро-уровне (массивы чисел) и часто позволяют CPU обрабатывать данные, не разжимая их полностью.

#### A. RLE (Run-Length Encoding)
Идеально для колонок с низкой кардинальностью (Status, Country, Gender), особенно если данные **отсортированы**.
*   **Механика:** Заменяем последовательность повторяющихся значений на пары `(Value, Count)`.
*   **Пример:** `[A, A, A, A, B, B]` -> `[(A, 4), (B, 2)]`.
*   **Direct Execution:**
    *   `SELECT count(*) WHERE col = 'A'` выполняется за O(1) для блока — просто берем число `4`.
    *   `SELECT val + 1` — выполняем сложение один раз для значения `A`, а не 4 раза.
*   **Expert Warning:** RLE бесполезен и вреден на случайных данных. Если данные не отсортированы по этой колонке (Cluster Key), последовательности будут короткими (`A, B, A, C` -> `(A,1), (B,1)...`), что увеличит размер данных (Negative Compression).

#### B. Bit-Packing & PFOR (Patched Frame of Reference)
Стандарт для хранения целых чисел в Parquet и Lucene.
*   **Bit-Packing:** У вас массив `int32`, но реальные значения лежат в диапазоне 0-7. Вместо 32 бит мы используем 3 бита.
    *   *SIMD:* Процессор может загрузить 512-битный регистр и выполнить операции над 170-ю трехбитными числами одновременно (используя маски).
*   **PFOR (Patched Frame of Reference):**
    *   *Проблема:* Что если 99% чисел влезают в 3 бита, но одно число (выброс) требует 10 бит? Из-за него придется расширять все числа до 10 бит?
    *   *Решение:* Кодируем 99% чисел в 3 бита. Выбросы (Exceptions) вырезаем и складываем отдельно в конец блока ("Patch"). В основной поток вставляем маркер, указывающий на патч.
    *   Это позволяет сжимать данные агрессивно, не боясь выбросов.

#### C. Delta Encoding & ZigZag
Идеально для `Timestamp` и `Auto-Increment ID`.
*   **Delta:** Храним не значения, а разницу между ними.
    *   `[1000, 1001, 1005, 1010]` -> `Base: 1000, Deltas: [0, 1, 4, 5]`.
    *   Дельты занимают меньше бит, чем исходные числа, поэтому поверх Delta часто накатывают Bit-Packing.
*   **ZigZag Encoding:** (Используется в Protobuf/Avro). Эффективное сжатие знаковых (signed) дельт.
    *   Отрицательные числа в `int32` (two's complement) имеют много единиц в старших разрядах (напр, `-1` это `111...111`). Это плохо жмется.
    *   ZigZag переносит знаковый бит в младший разряд (`0 -> 0`, `-1 -> 1`, `1 -> 2`, `-2 -> 3`), возвращая нули в старшие разряды.

### 3.2. Dictionary Encoding (Словарь) — Workhorse аналитики

Самый мощный метод для строковых данных (`UserAgent`, `City`, `URL`).
Строки заменяются на целочисленные ID.

1.  **Локальный словарь (Parquet/ORC):** Словарь строится для каждого блока (Row Group) или файла.
    *   *Плюс:* Высокая параллельность записи.
    *   *Минус:* `ID=1` в файле А и `ID=1` в файле Б — это разные строки. При чтении нужно перекодировать.
2.  **Глобальный словарь (ClickHouse LowCardinality):**
    *   Словарь хранится глобально или асинхронно мержится.
    *   *Плюс:* `GROUP BY` работает над `int` ID. Сравнение строк заменяется сравнением чисел.
3.  **Order-Preserving Dictionary:**
    *   ID выдаются так, чтобы порядок сохранялся: `Apple -> 1`, `Banana -> 2`.
    *   *Суперсила:* Можно выполнять Range-фильтры (`WHERE Fruit > 'Apple'`) прямо над ID (`WHERE ID > 1`), не обращаясь к словарю.

**Late Materialization (Ленивая материализация):**
Мы выполняем `JOIN`, `GROUP BY`, `ORDER BY` над ID. Превращаем ID обратно в строки ("материализуем") только в самом конце, перед отправкой клиенту. Это экономит гигабайты трафика памяти.

### 3.3. Heavyweight Compression (Блочное сжатие)

Поверх Encoding (который структурирован) накладывается общецелевое сжатие блоков байтов.

1.  **LZ4 / Snappy:**
    *   Ориентированы на **скорость декомпрессии** (> GB/s).
    *   Используются для "горячих" данных, которые часто читаются.
2.  **Zstd (Zstandard):**
    *   Современный стандарт (Facebook). Дает сжатие уровня Gzip при скорости близкой к LZ4.
    *   Имеет адаптивные уровни сжатия.
    *   Используется для холодного хранения или архивов.

### 3.4. SIMD & Vectorized Decoding

Почему это Expert level? Потому что современные движки (ClickHouse, Velox) пишут декодеры вручную на интринсиках (Intrinsics).

**Сценарий:** У нас есть массив 4-битных упакованных чисел. Мы хотим найти все значения `> 5`.
1.  **Scalar:** Цикл, распаковка каждого числа (битовые сдвиги), сравнение. Куча ветвлений.
2.  **SIMD (AVX-512):**
    *   `vpmovzxbq`: Распаковываем 16 значений из 4-битных в 8-битные за один такт.
    *   `vpcmpgtb`: Сравниваем все 16 значений с числом 5 за один такт. Получаем маску.
    *   `vpopcnt`: Считаем количество совпадений.

**Вывод:** Сжатие в колоночных базах — это способ "накормить" широкие векторные регистры процессора данными, минуя узкое горлышко пропускной способности памяти (Memory Wall).

## 4. Vectorized Execution vs Volcano Model

В аналитических СУБД узкое место сместилось с диска (I/O) на процессор и пропускную способность памяти. Классические модели исполнения, созданные в 80-х (Volcano), тратят до 90% циклов CPU на "административные расходы" (overhead), а не на полезную работу.

### 4.1. Volcano Model (Tuple-at-a-Time) — Классика

Эта модель (предложенная Goetz Graefe в 1990) используется в PostgreSQL, MySQL и большинстве row-store баз.

**Механика:**
Каждый оператор (Scan, Filter, Project, Join) реализует интерфейс итератора с методом `next()`.
```cpp
// Виртуальный вызов в дереве операторов
Tuple* Filter::next() {
    while (Tuple* t = child->next()) { // Виртуальный вызов вниз
        if (predicate(t)) return t;    // Проверка условия
    }
    return nullptr;
}
```

**Проблемы на современном железе:**
1.  **Virtual Function Dispatch Overhead:** Вызов виртуальной функции в C++ — это дорого (поиск адреса в vtable, косвенный переход). В Volcano мы делаем это *для каждой строки*.
2.  **Instruction Cache (I-Cache) Thrashing:**
    *   Код оператора `Scan` лежит в одном месте памяти, `Filter` — в другом, `Project` — в третьем.
    *   Вызывая их по очереди для *одной* строки, мы заставляем CPU постоянно прыгать по коду, вымывая полезные инструкции из L1 I-Cache.
3.  **Branch Misprediction:** Внутри `next()` много ветвлений (`if`, `while`). Процессор не может предсказать поток выполнения, так как контекст постоянно меняется. Это ломает **Instruction Pipelining** (суперскалярное выполнение).

**Вердикт:** Volcano модель имеет огромный **CPI (Cycles Per Instruction)**. Полезная работа (сложение двух чисел) занимает 1 такт, а инфраструктура доставки этих чисел — 100 тактов.

---
### 4.2. Vectorized Execution (Batch-at-a-Time) — Монетизация локальности

Модель, популяризированная в **MonetDB/X100** (сейчас Vectorwise/Actian) и используемая в **ClickHouse**, **Snowflake**, **Velox**.

**Механика:**
Операторы обмениваются не строками, а **векторами** (батчами) данных. Обычно размер вектора — 1024 или 4096 элементов. Это число выбрано не случайно: вектор должен влезать в **L1 Data Cache**.

```cpp
// Векторная обработка
void Filter::next_batch(Batch& output) {
    Batch input;
    child->next_batch(input); // 1 виртуальный вызов на 1024 строки

    // Tight Loop (Плотный цикл)
    for (int i = 0; i < input.size; i++) {
        if (predicate(input.col[i])) {
           output.append(input.col[i]);
        }
    }
}
```

**Архитектурные преимущества (Why it works):**
1.  **Amortization of Overhead:** Стоимость виртуального вызова делится на 1024. Она становится пренебрежимо малой.
2.  **Compiler Friendliness:** Код внутри цикла (`for`) простой и линейный. Компилятор (GCC/Clang) видит, что это обработка массива, и может применить:
    *   **Loop Unrolling:** Развернуть цикл, уменьшив накладные расходы на проверку счетчика `i`.
    *   **Auto-Vectorization:** Автоматически применить SIMD инструкции.
3.  **Branch Prediction:** В цикле обработки вектора условие (например, `age > 18`) проверяется подряд 1000 раз. Паттерн переходов становится предсказуемым для процессора.

**SIMD (Single Instruction, Multiple Data):**
Векторизация программная (Batching) открывает путь к векторизации аппаратной (SIMD).
*   Вместо `a[i] + b[i]` мы загружаем регистры `YMM` (256 бит) и делаем `vaddps`, складывая 8 чисел float за один такт.
*   ClickHouse использует это экстремально, вручную выбирая реализации функций под AVX2/AVX-512 через `CPUID` в рантайме (Dynamic Dispatch).

---
### 4.3. JIT Compilation (Code Generation) — Слияние операторов

Альтернативный подход (используется в **Postgres 11+**, **SingleStore**, **Hyper**).
Если Vectorization оптимизирует *циклы*, то JIT пытается избавиться от *циклов* вообще, "сплавляя" (fusing) операторы.

**Механика:**
Вместо того чтобы гонять данные между функциями `Scan -> Filter -> Project`, движок генерирует машинный код (обычно через **LLVM IR**), который делает всё в одном цикле.

**Сравнение подхода:**
Запрос: `SELECT (a + b) * c FROM t`

*   **Vectorized:**
    1.  `Temp1[] = a[] + b[]` (Пишем в память/L1 кэш).
    2.  `Result[] = Temp1[] * c[]` (Читаем из памяти, пишем в память).
    *   *Минус:* Лишние обращения к памяти (Materialization overhead) для промежуточных результатов.

*   **JIT (Data-Centric):**
    ```cpp
    // Сгенерированный код
    for (int i = 0; i < count; i++) {
        // Все вычисления в регистрах CPU!
        register int val = col_a[i];
        val += col_b[i];
        val *= col_c[i];
        result[i] = val;
    }
    ```
    *   *Плюс:* Данные загружаются в регистры один раз и живут там до конца вычислений. Максимальная локальность данных (Data Locality).

---
### 4.4. The Great Debate: Vectorization vs JIT

Архитектор должен знать, когда какой подход выигрывает.

| Характеристика | Vectorization (ClickHouse, Snowflake) | JIT / CodeGen (Hyper, SingleStore) |
| :--- | :--- | :--- |
| **Сложность выражений** | **Слабость.** Сложные формулы `(a+b*c/d...)` создают много проходов по памяти для временных векторов. | **Сила.** Все вычисления фьюзятся в один проход. Идеально для сложной математики. |
| **Сборка (Compilation Time)** | **0.** Код прекомпилирован (C++). Готов к работе мгновенно. | **Высокая.** Нужно сгенерировать IR, оптимизировать и скомпилировать. Плохо для коротких запросов (< 100ms). |
| **SIMD** | **Легко.** Explicit SIMD в прекомпилированных ядрах. | **Сложно.** Полагается на авто-векторизатор LLVM, который часто ошибается или не может векторизовать сложный fused-код. |
| **Профилирование** | **Легко.** Видно в `perf` как обычные функции C++. | **Ад.** Стек-трейсы ведут в динамически сгенерированный код без символов. |

**Современный тренд (Velox / Photon):**
Гибридные движки. Использовать векторизацию для "тяжелых" операторов (Scan, Aggregation, Join), где важен SIMD, и использовать JIT (или expression evaluation optimization) для сложных проекций и фильтров, чтобы держать данные в регистрах.

### Резюме раздела:

1.  **Volcano** мертва для аналитики из-за оверхеда виртуальных вызовов.
2.  **Vectorization** амортизирует оверхед, обрабатывая данные пачками, влезающими в L1 кэш.
3.  **JIT** максимизирует использование регистров CPU, сплавляя операции.
4.  Выбор между ними — это выбор между **эффективностью памяти** (JIT) и **простотой использования SIMD** (Vectorization).

## 5. Architectural Patterns & Trade-offs

Колоночная архитектура — это не серебряная пуля. Она накладывает жесткие ограничения на дизайн схемы данных и паттерны запросов. Если вы попытаетесь использовать ClickHouse или Snowflake как Postgres, вы "убьете" кластер.

### 5.1. Materialization Strategy: Early vs Late

Главный архитектурный вопрос при выполнении запроса: **"В какой момент мы собираем разрозненные колонки обратно в строку?"**

Представьте запрос:
```sql
SELECT p.Name, p.Bio, s.Salary
FROM Person p
JOIN Salaries s ON p.ID = s.PersonID
WHERE p.Age > 30 AND s.Amount > 100k
ORDER BY s.Amount DESC
LIMIT 10
```

#### A. Early Materialization (Naive Approach)
1.  Сканируем `p.Age`, находим подходящие RowID.
2.  **Сразу** идем и достаем `p.Name`, `p.Bio` для этих RowID. Собираем частичные строки.
3.  Джойним с `Salaries`.
4.  Сортируем.
*   **Проблема:** Мы таскаем тяжелое поле `p.Bio` (TEXT, 2KB) через Join и Sort. Мы тратим гигабайты пропускной способности памяти на перекладывание данных, которые, возможно, даже не попадут в `LIMIT 10`.

#### B. Late Materialization (The Expert Way)
1.  **Column Processing:** Работаем только с колонками, участвующими в фильтрации (`p.Age`, `s.Amount`). Оперируем массивами `RowID` (или битовыми масками).
2.  **Sideways Information Passing:** Передаем фильтры между этапами джойна (Bloom Filters).
3.  **Late Fetch:** Выполняем `ORDER BY` и `LIMIT` над легкими данными (числа/ID).
4.  **Materialization Point:** Получаем финальные 10 идентификаторов. И только **в самый последний момент** идем на диск/в память за `p.Name` и `p.Bio` для этих 10 строк.
*   **Trade-off:** Late Materialization требует сложной логики движка (нужно хранить Intermediate RowIDs) и может вызвать Random I/O в конце, но экономия на Memory Bandwidth окупает это в 100 раз.

### 5.2. Schema Design: OBT (One Big Table) vs Star Schema

В мире OLTP (Row-store) мы нормализуем данные (3NF), чтобы избежать аномалий обновления и сэкономить место.
В мире OLAP (Column-store) правила меняются.

1.  **Star Schema (JOINs):**
    *   Колоночные базы *ненавидят* JOIN'ы.
    *   **Shuffle:** Чтобы соединить две большие таблицы, нужно пересылать данные по сети между нодами кластера. Это убивает латентность.
    *   **Broadcast:** Если одна таблица маленькая (Dimension), её можно разослать всем.

2.  **OBT (One Big Table / Denormalization):**
    *   Мы заранее джойним данные и пишем их в одну широкую таблицу (100-500 колонок).
    *   **Сжатие спасает:** Дублирование данных (например, `CountryName` в каждой строке) в колоночной базе **бесплатно**. RLE или Dictionary Encoding сожмут миллион повторов `'USA'` в несколько байт.
    *   **Vectorization:** Нет джойнов -> нет разрывов пайплайна -> процессор работает на максимальной скорости.
*   **Совет Архитектора:** В ClickHouse/Druid всегда стремитесь к OBT. Используйте JOIN только для редко обновляемых справочников небольшого размера.

### 5.3. Sorting Key as Primary Index

В B-Tree (Row-store) индекс — это отдельная структура.
В Column-store (Parquet/MergeTree) индекс — это **физический порядок сортировки данных**.

*   **Data Skipping:** Если данные отсортированы по `Timestamp`, то в каждом блоке (Granule) будут лежать близкие значения (напр. `min=10:00`, `max=10:05`). Запрос `WHERE time = 12:00` пропустит этот блок, просто глянув в заголовок.
*   **Secondary Index Problem:** Если данные отсортированы по `Timestamp`, то по колонке `UserID` они разбросаны хаотично. Блоки будут иметь `min=User1`, `max=User999999`. Data Skipping перестает работать.
*   **Z-Order Curve (Space-filling curves):**
    *   Продвинутая техника для создания "многомерной сортировки".
    *   Позволяет сортировать данные так, чтобы они были локальны и по `Timestamp`, и по `UserID` одновременно (компромисс). Критично для эффективности Data Skipping в сложных схемах.

### 5.4. The Interchange Formats: SerDe Tax

Архитектор должен различать форматы **хранения** и форматы **передачи**.

#### A. Storage Formats (Parquet, ORC)
Оптимизированы для **холодного хранения** на диске (S3/HDFS).
*   **Heavy Compression:** Используют энтропийное кодирование (RLE, BitPack) + блочное сжатие (Zstd/Snappy).
*   **Cost:** Чтение требует CPU для декомпрессии и десериализации (Dremel assembly). Нельзя просто взять байты с диска и работать с ними.

#### B. In-Memory / Transport Formats (Apache Arrow)
Оптимизированы для **обмена данными** между системами (Spark <-> Pandas <-> ClickHouse) и обработки в CPU/GPU.
*   **Zero-Copy:** Данные в памяти лежат в том же формате, в котором они передаются по сети. Не нужно парсить, не нужно перекладывать.
*   **No Compression (по умолчанию):** Данные "раздуты" для максимальной скорости доступа по смещению (Offset).
*   **Use Case:** Если вы строите платформу, где Python (Pandas) читает из базы, использование протокола Arrow (ADBC) вместо ODBC/JDBC ускоряет передачу данных в 10-50 раз за счет устранения шага сериализации.

### 5.5. The Mutability Myth (Ограничение на обновление)

Колоночные форматы (Parquet) и движки **неизменяемы (Immutable)**.
*   Нельзя обновить значение в середине колонки: это сдвинет все биты (из-за RLE/BitPacking) и потребует перезаписи всего файла.
*   **LSM-подобный подход:** Аналитические базы (ClickHouse, Vertica, Snowflake) обрабатывают `UPDATE` и `DELETE` как вставку новых версий или масок удаления.
*   **Тяжелые последствия:** Частые одиночные `UPDATE` в колоночной базе приводят к фрагментации и необходимости постоянной фоновой "мутации" (перезаписи) гигантских кусков данных.

### Итоговый вердикт

| Паттерн | Row-Store (Postgres) | Column-Store (ClickHouse/Parquet) |
| :--- | :--- | :--- |
| **Materialization** | Early (построчная) | Late (векторная, отложенная) |
| **Schema** | Star Schema (3NF) | Denormalized (Wide Table / OBT) |
| **Primary Index** | B-Tree (отдельная структура) | Sort Order (физическое расположение) |
| **Updates** | In-place (быстро) | Merge-on-Read / Copy-on-Write (медленно) |
| **Join** | Nested Loop (эффективно для малых) | Hash Join / Broadcast (дорого для больших) |

Выбирая колоночную архитектуру, вы подписываетесь на: **Денормализацию**, **Пакетную загрузку** и **Отсутствие точечных обновлений**.

## 6. Troubleshooting & Tuning

В отличие от Row-store, где проблемы обычно связаны с блокировками или Random I/O, в Column-store проблемы носят характер **ресурсного голодания** (Resource Starvation). Один "плохой" запрос может съесть всю оперативную память кластера.

### 6.1. The Small File Problem (Fragmentation Hell)

Это убийца №1 для Hadoop (HDFS), S3-based Data Lakes (Delta Lake, Iceberg) и ClickHouse.

**Физика проблемы:**
Колоночные форматы (Parquet, ORC, MergeTree parts) имеют тяжелый **Header/Footer**.
1.  **Metadata Overhead:** Чтобы прочитать 1 строку из Parquet, нужно прочитать Footer, распарсить Thrift-структуру схемы, найти смещения Column Chunks. Если файл весит 10KB, метаданные занимают 50% объема и времени чтения.
2.  **Compression Context:** Алгоритмы сжатия (Zstd, Snappy) работают контекстно. Чтобы эффективно сжать, нужно видеть паттерны. В файле на 10 строк паттернов нет. Сжатие не работает.
3.  **S3 API Costs:** В облаке вы платите за каждый `GET`/`PUT` запрос. Чтение 1TB данных, разбитых по 100KB, будет стоить состояние и займет часы из-за latency на открытие соединения.

**Решение (Compaction / Async Insert):**
*   **Buffer Tables:** Никогда не пишите по одной строке (`INSERT VALUES`). Используйте буферные таблицы (Kafka Engine, Buffer Engine), которые накапливают пачку в RAM и сбрасывают её, когда наберется 100MB или 10 секунд.
*   **Partitioning Hygiene:** Не делайте партиционирование слишком мелким (по минутам). Партиция должна содержать достаточно данных (сотни MB), чтобы сформировать эффективные файлы.

### 6.2. Dictionary Explosion (Взрыв кардинальности)

Колоночные базы полагаются на **Dictionary Encoding**.
Строка `"Mozilla/5.0 ..."` заменяется на `ID=5`.

**Сценарий отказа:**
У вас есть колонка `URL`. Обычно кардинальность низкая. Но вдруг начинается DDoS-атака со случайными параметрами в URL.
1.  **Unique Values Spike:** Количество уникальных строк становится миллиардным.
2.  **Dictionary Overflow:** Словарь перестает влезать в L3 кэш процессора, затем в RAM.
3.  **Encoding Fallback:** Движок (например, Parquet writer или ClickHouse) вынужден переключиться с `DictEncoding` на `PlainString`.
4.  **Размер данных взрывается:** Вместо 4 байт на строку мы пишем 100 байт. Скорость записи падает в 20 раз. Память сервера переполняется.

**Тюнинг:**
*   **LowCardinality Data Types:** Явно указывайте движку, где ожидать словарь (например, `LowCardinality(String)` в ClickHouse). Но следите за лимитами.
*   **Sorting Key:** Если данные отсортированы по этой колонке, локальность значений повышается. Даже если глобальных уникальных значений много, внутри одного блока (Row Group) их будет мало, и локальный словарь Parquet будет компактным.

### 6.3. Memory Management: OOM Killers & Spilling

Векторное выполнение требует памяти.
`SELECT A, count(B) FROM T GROUP BY A`.
Движок создает Hash Table в памяти для агрегации.

**Проблема:** В OLAP запросах хэш-таблица может вырасти до сотен гигабайт.
*   В Postgres запрос просто станет медленным (используя temp files).
*   В ClickHouse/Impala запрос **упадет** с ошибкой `Memory limit exceeded` или положит весь сервер через OOM Killer.

**Тюнинг:**
*   **External Sort / Spill to Disk:** Настройте триггеры (`max_bytes_before_external_group_by`), когда движок должен сбрасывать промежуточные результаты на диск. Запрос станет медленным, но не упадет.
*   **Approximate Algorithms:** Используйте `uniqCombined` (HyperLogLog) вместо `count(distinct)`. Это снижает потребление памяти с Гигабайт до Килобайт.

### 6.4. Sparse Index Granularity (Настройка "Шага")

В колоночных базах индекс — это не дерево для каждой строки. Это **разреженный индекс** (Sparse Index).
Он хранит метки (Marks) для каждого N-го блока данных (Granule).
*   *Default:* 8192 строки (ClickHouse).

**Сценарий:** Вы храните тяжелые логи (TEXT, 10KB на строку).
*   Гранула (8192 строки) весит 80 MB.
*   Чтобы найти *одну* запись, база должна прочитать и декомпрессировать 80 MB. Это **Read Amplification**.

**Тюнинг:**
*   Для "жирных" строк уменьшайте гранулярность (например, до 1024), чтобы снизить оверхед на чтение лишнего.
*   Для "тонких" строк (числа, метрики) увеличивайте гранулярность, чтобы уменьшить размер индекса в памяти.

### 6.5. Concurrency vs Parallelism

Архитектор должен понимать разницу между OLTP и OLAP конкурентностью.
*   **OLTP (Postgres):** Тысячи мелких запросов параллельно. Высокая Concurrency.
*   **OLAP (ClickHouse/Snowflake):** Один запрос пытается занять **все ядра** процессора (Parallelism), чтобы прожевать терабайт данных.

**Проблема:** Если вы запустите 100 тяжелых OLAP-запросов одновременно, они будут драться за CPU/Disk, вызывая Context Switching Hell. Производительность упадет почти до нуля.
**Решение:**
*   **Resource Pools / Queues:** Ограничивайте количество одновременных тяжелых запросов (например, `max_concurrent_queries = 10`). Остальные пусть стоят в очереди. Для аналитики лучше, чтобы 10 запросов прошли быстро по очереди, чем 100 висели вечно одновременно.

### Summary Checklist for Troubleshooting

1.  **Check File Counts:** Если файлов в партиции тысячи — нужен Compaction.
2.  **Check Dictionary Size:** Если колонка `String` занимает больше места, чем ожидалось — проверьте кардинальность (`uniq(col)`).
3.  **Check Memory Limits:** Убедитесь, что настроен `spill-to-disk` для `JOIN` и `GROUP BY`.
4.  **Check Data Skew:** В распределенных системах (Spark/Trino) проверьте, не выполняет ли одна нода 90% работы из-за перекоса ключа распределения.

## 7. Summary Checklist for Solution Architect

Используйте этот раздел для валидации архитектурных решений (Design Review) и аудита существующих аналитических платформ.

## 7.1. Architectural Selection Matrix (Выбор инструмента)

Не выбирайте колоночную базу только потому, что она "быстрая". Выбирайте её, если ваш паттерн доступа оправдывает накладные расходы на сборку кортежей.

| Критерий | Row-Store (Postgres/MySQL) | Column-Store (ClickHouse/Vertica) | Data Lake (Parquet/S3/Spark) |
| :--- | :--- | :--- | :--- |
| **Основной паттерн** | **Point Queries**. `SELECT * WHERE id=X`. | **Aggregations**. `SELECT sum(A) GROUP BY B`. | **Batch Scan / ML**. Обучение моделей, ETL. |
| **Latency** | **Low (< 10ms)**. Прямой доступ к строке. | **Medium (50-200ms)**. Оверхед на старт запроса и сборку колонок. | **High (Seconds/Minutes)**. Холодный старт, S3 latency. |
| **Updates** | **Mutable**. `UPDATE` дешев и ACID-ен. | **Immutable**. `UPDATE` — это тяжелая мутация (перезапись партиции). | **Append-Only**. Обновление невозможно без перезаписи файла. |
| **Concurrency** | **High**. Тысячи запросов параллельно. | **Low**. Десятки запросов (каждый утилизирует все ядра). | **Low**. Пакетная обработка. |
| **Throughput** | Ограничен Random I/O. | Ограничен CPU (Decompression/SIMD) и Memory Bandwidth. | Ограничен Network Bandwidth (S3). |

## 7.2. Schema & Ingestion Design Checklist

*Как не убить колоночную базу на старте.*

1.  **Ingestion Hygiene (Гигиена вставки):**
    *   [ ] **Strict Batching:** Никаких `INSERT` по одной строке. Минимум 1000 строк или 1MB в батче. Иначе вы получите "Small File Problem" и Metadata Overhead.
    *   [ ] **Async Buffer:** Если источник потоковый (Kafka), используйте буферные таблицы или нативные коннекторы с flush-интервалом.

2.  **Sorting Key Strategy (Сортировка — это Индекс):**
    *   [ ] **Low Cardinality First:** Первой в ключе сортировки должна идти колонка, по которой чаще всего фильтруют (`Timestamp`, `TenantID`).
    *   [ ] **Compression Impact:** Сортировка по колонке с низкой кардинальностью превращает RLE-сжатие в супер-оружие (сжимает гигабайты в килобайты).
    *   [ ] **Granularity:** Размер гранулы (блока) должен соответствовать размеру данных. Для тяжелых строк — меньше строк в грануле.

3.  **Data Types & Vectorization:**
    *   [ ] **Avoid Strings:** Векторизация лучше всего работает на числах фиксированной длины. Заменяйте `String` на `Enum` или `LowCardinality(String)` (словарное кодирование), если уникальных значений < 10,000.
    *   [ ] **Nullable Kill Performance:** `Nullable` колонки требуют отдельной битовой маски (null map). Это усложняет SIMD-оптимизации и добавляет ветвлений. Используйте дефолтные значения (0, empty string), где это семантически допустимо.

## 7.3. Operational Guardrails (Эксплуатационные триггеры)

*Метрики, на которые нужно настроить PagerDuty.*

1.  **Memory Pressure:**
    *   Мониторинг `Memory Tracking` на запрос. OLAP запросы прожорливы. Настройте `spill-to-disk` (сброс на диск) для `GROUP BY` и `JOIN`, иначе один запрос убьет весь сервер (OOM).

2.  **Part count (Фрагментация):**
    *   Алерт на количество активных кусков данных (Parts) в таблице. Если их > 3000, значит фоновый Merge (Compaction) не справляется. Чтение деградирует.

3.  **Dictionary Size:**
    *   Для глобальных словарей (Global Dictionary) следите за потреблением RAM. Если словарь перестанет влезать в кэш CPU, производительность упадет в 10 раз.

## 7.4. Expert Self-Check: War Games

Реальные сценарии, которые проверяют глубину понимания физики.

#### Scenario 1: The "Select Star" Trap
**Ситуация:** Аналитики жалуются, что `SELECT * FROM big_table LIMIT 100` в ClickHouse работает медленнее, чем в MySQL, хотя данных там терабайты.
**Вопрос:** Почему колоночная база проигрывает на выборке всего 100 строк?
<details>
<summary><b>Ответ (нажмите для просмотра)</b></summary>
<b>Tuple Reconstruction Cost.</b> В Row-store (MySQL) 100 строк лежат в 1-2 страницах диска. Это 1-2 IOPS.
В Column-store, если у таблицы 50 колонок, движок должен открыть 50 разных файлов (или стримов), прочитать из каждого по кусочку, декомпрессировать их и склеить (Materialize) в памяти. Это 50 IOPS + Random Seek + CPU overhead. Колоночные базы не предназначены для выгрузки сырых строк.
</details>

#### Scenario 2: The "Compression Paradox"
**Ситуация:** У вас есть колонка `Status` (значения 'Active', 'Inactive'). Вы отсортировали таблицу по `CreatedDate`. Сжатие колонки `Status` ужасное (почти как raw data).
**Вопрос:** Почему сжатие не работает, ведь значений всего два?
<details>
<summary><b>Ответ</b></summary>
<b>Entropy & High Frequency switching.</b> Так как таблица отсортирована по Времени, статусы 'Active' и 'Inactive' перемешаны случайно. RLE (Run-Length Encoding) видит последовательность `A, I, A, A, I, A`. Длины серий равны 1. RLE увеличивает размер данных (добавляя счетчик к каждому значению).
<i>Решение:</i> Добавить `Status` в ключ сортировки (сортировать по `Status, CreatedDate`). Тогда RLE сожмет данные в две записи: `(Active, N), (Inactive, M)`.
</details>

#### Scenario 3: The SIMD Brake
**Ситуация:** Вы храните данные в JSON-строках внутри колоночной базы. Запрос `SELECT count(*) WHERE json_extract(data, 'id') = 5` загружает CPU на 100%, но скорость сканирования низкая.
**Вопрос:** Почему не работает магия векторизации?
<details>
<summary><b>Ответ</b></summary>
<b>Parser Overhead.</b> JSON — это текстовый формат. Чтобы извлечь поле, нужно распарсить строку. Парсинг — это сложная логика с ветвлениями (Switch/Case), которая <b>не векторизуется</b> (SIMD инструкции не могут парсить произвольный JSON). Процессор тратит 90% времени на парсинг текста, а не на фильтрацию.
<i>Решение:</i> Использовать `Shredding` (вытащить `id` в отдельную колонку `Int32`) при вставке.
</details>

#### Scenario 4: The Late Materialization Win
**Ситуация:** Запрос `SELECT ExtremelyHeavyColumn FROM table WHERE ID > 1000 AND ID < 2000 LIMIT 5`.
В движке A это занимает 10 секунд. В движке B — 0.1 секунды. Оба колоночные.
**Вопрос:** Какую оптимизацию использует движок B?
<details>
<summary><b>Ответ</b></summary>
<b>Late Materialization.</b>
Движок A прочитал `ExtremelyHeavyColumn` для всех 1000 строк, попавших под условие `WHERE`, а потом применил `LIMIT 5` и выкинул 995 тяжелых значений.
Движок B сначала применил `LIMIT 5` к легкой колонке `ID`, получил 5 RowID, и только потом пошел читать `ExtremelyHeavyColumn` только для этих 5 строк.
</details>

## 7.5. The Golden Rules of Columnar Physics

1.  **CPU is the new Disk:** В современных колоночных базах узкое место — это не скорость чтения с SSD, а скорость декомпрессии и обработки данных в L3 кэше процессора.
2.  **Sort Order IS the Index:** Главный инструмент оптимизации — это физический порядок данных. Нет сортировки — нет Data Skipping — нет сжатия.
3.  **Batch Everything:** Колоночная база ненавидит атомарность. Любая операция должна быть массовой.

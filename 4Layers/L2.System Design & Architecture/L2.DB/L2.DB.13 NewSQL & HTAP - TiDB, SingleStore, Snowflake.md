**TL;DR**: Мы наблюдаем смерть парадигмы "ETL".
*   **TiDB**: Это **MySQL на стероидах** с архитектурой Google Spanner. Разделяет Row-store (TiKV) и Column-store (TiFlash) через Raft-репликацию. Идеален для **Scale-Out OLTP** с потребностью в аналитике.
*   **SingleStore**: Король **Ingestion**. Использует "Universal Storage" (гибрид памяти и диска), позволяя писать миллионы строк в секунду и тут же их агрегировать. Лучший выбор для **Real-time Dashboards**.
*   **Snowflake**: Изобретатель **Disaggregated Storage/Compute**. Изначально OLAP, теперь идет в OLTP через **Unistore**. Лучший выбор для **Massive Data Warehousing** с элементами транзакционности.

## 1. Физика HTAP: Конфликт Доступа к Памяти

Чтобы понять, почему HTAP (Hybrid Transactional/Analytical Processing) считался невозможным 40 лет, мы должны спуститься на уровень железа. Проблема не в SQL синтаксисе. Проблема в том, как процессор (CPU) общается с оперативной памятью (RAM).

В основе всего лежит **"Von Neumann Bottleneck"**: процессор считает быстрее, чем память может подавать ему данные. Современный Core i9 может выполнить сотни операций сложения за то время, пока данные едут из RAM в L1 Cache.
**HTAP — это попытка обмануть эту физику.**

### 1.1. Row Store (OLTP): Диктатура Кэш-Линии

Традиционные реляционные базы данных (PostgreSQL, MySQL, Oracle, SQL Server) построены на архитектуре **NSM (N-ary Storage Model)**.
В этой модели атрибуты одной сущности (строки) хранятся в памяти и на диске **смежно** (contiguously).

Чтобы понять, почему это идеально для транзакций и ужасно для аналитики, нужно посмотреть на то, как процессор "пьет" данные из памяти.

#### A. Анатомия доступа: 64 Байта или ничего
Процессор (CPU) не умеет читать 1 байт или 4 байта (Integer).
Минимальная единица обмена данными между RAM и L1 Cache процессора — это **Кэш-линия (Cache Line)**. В архитектуре x86-64 она равна **64 байтам**.

Даже если вам нужна одна переменная `bool` (1 байт), контроллер памяти обязан вычитать из RAM блок в 64 байта и передать его по шине.

#### B. Физическая раскладка (Memory Layout)
Представьте таблицу `Users` с широкой схемой:
```sql
CREATE TABLE Users (
    ID BIGINT,        -- 8 bytes
    Name VARCHAR(50), -- ~50 bytes
    Age INT,          -- 4 bytes
    Bio TEXT,         -- ~500 bytes (хранится TOAST/Blob или inline)
    ...
);
```
В Row-Store эти данные лежат на странице памяти "вплотную":
`[Row 1: ID|Name|Age|Bio] [Row 2: ID|Name|Age|Bio] ...`

#### C. Сценарий 1: OLTP (The Happy Path) — Spatial Locality
Запрос: `SELECT * FROM Users WHERE ID = 105`.

1.  **Index Seek:** B-Tree индекс находит адрес страницы.
2.  **Fetch:** CPU запрашивает адрес начала строки.
3.  **Cache Line Fill:** В кэш L1 прилетают 64 байта.
    *   В этих 64 байтах содержатся: `ID`, `Name` (частично), `Age`.
    *   Мы запрашивали `SELECT *` (всё). Мы получили кусок всего сразу.
4.  **Utilization:** Эффективность близка к **100%**. Каждый байт, переданный по шине, нужен приложению.
5.  **Write Efficiency:** Чтобы сделать `INSERT`, нам нужно дописать байты в конец страницы (Sequential Write). Это одна операция копирования памяти (`memcpy`), которая прекрасно ложится в кэш.

Это называется **High Spatial Locality** (Высокая пространственная локальность). Данные, к которым мы обращаемся логически одновременно, лежат физически рядом.

#### D. Сценарий 2: OLAP (The Bus Tragedy) — Cache Pollution
Запрос: `SELECT AVG(Age) FROM Users`.

Нам нужно прочитать только 4 байта (`Age`) для каждого миллиона пользователей.

1.  **Fetch Row 1:** CPU запрашивает адрес, где лежит `Age` первого юзера.
2.  **Overhead:** Контроллер памяти приносит 64 байта.
    *   Полезная нагрузка (Payload): 4 байта (`Age`).
    *   Мусор (Waste): 60 байт (`ID`, кусок `Name`, кусок `Bio`).
3.  **Pollution (Загрязнение):** Этот "мусор" занимает драгоценное место в L1 кэше (всего 32KB-48KB на ядро), вытесняя оттуда полезные данные.
4.  **Bandwidth Saturation:**
    *   Чтобы посчитать среднее по 1 млн строк, мы должны прокачать через шину памяти `1,000,000 * (размер строки)`.
    *   Если строка весит 200 байт, мы качаем **200 MB**.
    *   Полезных данных из них: `1,000,000 * 4 байта` = **4 MB**.

**Математический приговор:**
$$Efficiency = \frac{Useful\_Data}{Total\_Data\_Transferred} = \frac{4}{200} = 2\%$$

Мы утилизируем 2% пропускной способности канала. Остальные 98% времени CPU простаивает, ожидая, пока шина привезет очередную порцию "мусора", чтобы извлечь из нее одно число.

#### E. Почему Prefetching не спасает?
Современные CPU имеют **Hardware Prefetcher**, который пытается угадать следующий шаг и подгрузить данные заранее.
В Row-Store при сканировании таблицы Prefetcher работает идеально... **идеально загружая мусор**. Он будет агрессивно забивать кэш ненужными полями `Name` и `Bio`, ускоряя процесс доставки мусора, но не увеличивая полезную плотность данных.

### Резюме раздела 1.1
Row Store — это архитектура, оптимизированная под **Entity Access** (доступ к сущности целиком).
*   **Плюс:** Идеально для транзакций (ACID), так как строка — это атомарный блок.
*   **Минус:** Убивает производительность аналитики из-за низкой плотности полезных данных в кэш-линии. Вы платите за I/O (Disk & Memory) полного объема базы, даже если читаете одну колонку.

### 1.2. Column Store (OLAP): Векторизация и Сжатие

Колоночные базы данных (ClickHouse, Snowflake, Vertica, TiFlash) используют архитектуру **DSM (Decomposition Storage Model)**.
В этой модели мы физически разрезаем таблицу на вертикальные файлы. Все значения колонки `Age` хранятся вместе, отдельно от `Name` и `ID`.

Это меняет правила игры для процессора.

#### A. Плотность данных: 100% Cache Line Utilization
Вспомним нашу кэш-линию (64 байта).
Если мы сканируем колонку `Age` (тип `INT32` = 4 байта) в колоночном хранилище:

1.  **Fetch:** CPU запрашивает блок памяти.
2.  **Payload:** В одной кэш-линии приходит массив: `[Age_1, Age_2, ..., Age_16]`.
3.  **Efficiency:** В 64 байтах содержится **16 полезных значений**.
4.  **Math:** Чтобы обработать 1,000,000 строк, нам нужно скачать из RAM:
    $$Size = 1,000,000 \times 4 \text{ bytes} = 4 \text{ MB}$$
    В Row-Store мы качали 200 MB. Разница в **50 раз** только за счет того, что мы не читаем мусор.

#### B. SIMD и Векторизованное Исполнение (Vectorized Execution)
Колоночное хранение бесполезно без **Векторизованного Движка**.
Старые базы (PostgreSQL, MySQL) используют **Volcano Model** (Row-at-a-time):
*   Функция `next()` вызывается для каждой строки.
*   Оверхед на вызов функции (Virtual function call) и проверку типов может быть дороже, чем само сложение чисел.

Колоночные движки используют **Batch Processing**:
*   Функция `next_batch()` берет сразу 1000 или 10,000 значений.
*   Здесь в игру вступает **SIMD (Single Instruction, Multiple Data)**.
    *   Современные CPU (AVX2/AVX-512) могут сложить 8 или 16 чисел за **один процессорный такт**.
    *   Движок загружает данные в широкие регистры (ZMM registers) и выполняет `VPADDD` (Vector Packed Add Doubleword).
    *   **Результат:** Вместо 16 тактов цикла, мы тратим 1 такт.

#### C. Сжатие и Информационная Энтропия
Колонки сжимаются лучше строк. Это закон **информационной энтропии**.
Данные в одной колонке **гомогенны** (однородны): даты похожи на даты, страны на страны.

**Основные техники сжатия (Lightweight Compression):**
В отличие от тяжелого GZIP, эти алгоритмы позволяют CPU читать данные *без полной распаковки*.

1.  **RLE (Run-Length Encoding):**
    *   Данные: `[US, US, US, US, UK, UK]`
    *   Сжатие: `[(US, 4), (UK, 2)]`
    *   *Эффект:* Если данные отсортированы (Cluster Key), колонка сжимается в тысячи раз.
2.  **Delta Encoding / Frame of Reference:**
    *   Данные (Timestamp): `[16000001, 16000002, 16000005]`
    *   Сжатие (Base: 16000000): `[+1, +2, +5]`
    *   *Эффект:* Вместо 8 байт (Long) мы тратим 1 байт на значение.
3.  **Bit-Packing:**
    *   Колонка `IsActive` (Boolean). В Row-Store она занимает 1 байт (8 бит).
    *   В Column-Store мы пакуем 8 значений в 1 байт. Экономия памяти в 8 раз.

**Virtual Bandwidth:** Если сжатие 10x, то диск со скоростью 500 MB/s "виртуально" подает данные со скоростью 5 GB/s.

#### D. The Materialization Cost (Tuple Reconstruction)
У всего есть цена. Ахиллесова пята колоночных баз — это **Materialization** (или Tuple Reconstruction).
Запрос: `SELECT * FROM Users WHERE ID = 500`.

Движок должен собрать Франкенштейна:
1.  Найти смещение строки №500.
2.  Сходить в файл `col_id.bin` -> прочитать.
3.  Сходить в файл `col_name.bin` -> прочитать.
4.  Сходить в файл `col_age.bin` -> прочитать.
...и так 50 раз (по числу колонок).

Если файлы не лежат в кэше, это порождает **Random Seek Storm**. Головка диска (или контроллер SSD) сходит с ума, прыгая по разным файлам.
Именно поэтому `SELECT *` в аналитических базах работает медленно, а в Row-Store — мгновенно.

### Резюме раздела 1.2
Column Store — это архитектура, оптимизированная под **Scan & Aggregate** (сканирование и агрегацию).
*   **Плюс:** Экстремальная утилизация кэша (100% hit rate полезных данных) и возможность использовать суперсилу CPU (SIMD).
*   **Минус:** Дорогая сборка полной строки (Materialization). Не подходит для точечных запросов ("Дай мне профиль юзера X").

### 1.3. HTAP Dilemma: Конфликт Сжатия и Мутаций

Почему нельзя просто создать базу данных, которая хранит данные в колонках (для скорости аналитики) и позволяет их обновлять (для транзакций)?
Ответ кроется в **Несовместимости Сжатия и Произвольного Доступа**.

#### A. Физика сжатия: Зависимость данных
В Row-Store (B-Tree, PostgreSQL) каждая страница (8KB) независима. Вы можете обновить строку в Странице №5, и это никак не повлияет на Страницу №6.

В Column-Store (Parquet, ORC, TiFlash, Columnstore) эффективность достигается за счет **Heavyweight Compression**, где данные зависят друг от друга.

**Пример (RLE Encoding):**
Представьте колонку `Status`, где значения идут так: 1000 раз "Active", потом 1 раз "Banned".
Физически на диске это хранится как пара чисел: `[(Value: "Active", Count: 1000), (Value: "Banned", Count: 1)]`.
Вес: **~10 байт**.

**Сценарий Update:**
Приходит транзакция: `UPDATE Users SET Status = 'Banned' WHERE ID = 500`.
Мы хотим изменить 500-й элемент.
1.  **Проблема:** У нас нет "500-й ячейки". У нас есть запись "1000 штук Active".
2.  **Разрыв структуры:** Чтобы вставить "Banned" в середину, нам нужно расщепить сжатый блок на три части:
    *   `("Active", 499)`
    *   `("Banned", 1)` — *наша вставка*
    *   `("Active", 500)` — *хвост*
3.  **Cascading Writes:** Это изменение меняет смещения (Offsets) всех последующих данных в файле.

**Вывод:** В колоночном формате невозможно изменить 1 байт. Вы вынуждены переписать **весь блок** (Column Chunk), который может занимать мегабайты.

#### B. Write Amplification (Усиление записи)
Это главная метрика, убивающая производительность.
$$WA = \frac{Bytes\_Written\_To\_Disk}{Bytes\_Modified\_By\_User}$$

*   **OLTP (B-Tree):** Вы меняете 100 байт. База пишет страницу 4KB (плюс WAL). $WA \approx 40$. Это нормально.
*   **OLAP (Naive Update):** Вы меняете 100 байт. База вынуждена распаковать, изменить и снова сжать колоночный чанк размером 10MB. $WA \approx 100,000$.
    *   **Результат:** Диск (SSD) умирает, I/O канал забит, база "висит" на простейшем `UPDATE`.

#### C. Архитектурное решение: L1/L2 Delta Architecture

Чтобы решить эту дилемму, все современные NewSQL/HTAP системы (TiDB, SingleStore, Snowflake Unistore, ClickHouse) используют гибридную архитектуру, вдохновленную **LSM-Tree**.

Они разделяют данные на две физические зоны с разными законами физики:

1.  **L1: Delta Store (The "Row" Buffer)**
    *   **Назначение:** Принимать новые вставки, обновления и удаления.
    *   **Структура:** Row-Oriented (B-Tree или SkipList). Хранится в **RAM** (или в Write-Optimized формате на SSD).
    *   **Сжатие:** Отсутствует или слабое.
    *   **Мутации:** In-place updates поддерживаются эффективно.

2.  **L2: Main Store (The "Column" Archive)**
    *   **Назначение:** Хранить 99% исторических данных для быстрого сканирования.
    *   **Структура:** Column-Oriented (Sorted runs, Parquet-like).
    *   **Сжатие:** Максимальное (ZSTD, RLE, Bit-packing).
    *   **Мутации:** **Запрещены.** Файлы иммутабельны (Immutable).

#### D. Жизненный цикл данных (The Merge Process)

Как данные попадают из L1 в L2?

1.  **Ingestion:** `INSERT` пишет в L1 (Delta). Транзакция подтверждается мгновенно (Latency микросекунды).
2.  **Spill / Flush:** Когда L1 заполняется (например, > 100MB), он "замораживается" и сбрасывается на диск.
3.  **Compaction (Background Merge):** Фоновый процесс берет несколько файлов L1 и "старые" файлы L2, сливает их, сортирует, сжимает в колонки и записывает новый файл L2. Старые файлы удаляются.

**Как работает `DELETE`?**
Мы не удаляем строки из колонок (это дорого). Мы пишем **Tombstone** (Могильный камень) в L1: *"ID 500 удален"*.
При чтении движок видит запись в L2, но видит Tombstone в L1 и отфильтровывает строку.

#### E. The "Merge-on-Read" Penalty (Цена чтения)

За HTAP приходится платить сложностью чтения.
Запрос `SELECT SUM(amount) FROM sales` теперь не может просто прочитать колоночный файл.

Движок должен выполнить логическую операцию:
$$Result = (Query(L2\_Main) \cup Query(L1\_Delta)) \setminus Tombstones(L1)$$

1.  Сканируем гигантский Main Store (быстро, SIMD).
2.  Сканируем маленький Delta Store (медленно, Row-scan).
3.  **Merge:** Объединяем результаты, учитывая, что версия строки в Delta Store "свежее" и перекрывает версию в Main Store.

**Expert Insight:**
Именно эффективность этого слияния ("Merge-on-Read") определяет качество базы данных.
*   **TiFlash** делает это на уровне движка хранения.
*   **SingleStore** делает это настолько быстро, что пользователь не замечает разницы.
*   Плохие реализации (ранние версии Hadoop) умирали на этом этапе, создавая "Read Amplification".

### Резюме раздела 1.3
HTAP Дилемма — это выбор между **Write Amplification** (если обновлять колонки напрямую) и **Read Complexity** (если использовать Delta-архитектуру).
Индустрия выбрала **Delta-архитектуру**. Мы позволяем данным быть "грязными" и "не сжатыми" короткое время в Delta Store, чтобы получить экстремальную скорость записи, и асинхронно превращаем их в эффективные колонки.

## 2. TiDB: The Spanner of the Open Source World

**TiDB (Titanium DB)** — это Open-Source реализация архитектуры **Google Spanner** и **Google F1**.
Ее главная архитектурная победа — это доказательство того, что можно построить глобально распределенную, строго согласованную (Strongly Consistent) базу данных, не имея атомных часов (TrueTime API), как у Google.

TiDB решает задачу **Infinite Horizontal Scale** (бесконечное горизонтальное масштабирование) для транзакций, сохраняя при этом совместимость с протоколом MySQL.

### 2.1. Architecture: The Disaggregated Trinity

TiDB реализует **Cloud-Native Architecture** с полным разделением слоев. Это не просто "Master-Slave" репликация, это оркестрация трех независимых систем, работающих как единый организм.

Кластер TiDB — это реализация паттерна **Shared-Nothing**: ни один узел не делит память или диск с другим. Все общение происходит через сеть (gRPC).

### A. TiDB Server (Compute Layer): The Stateless Brain
Этот компонент эмулирует поведение MySQL сервера. Для приложения он выглядит как MySQL 5.7/8.0 (работает на том же порту 4000, поддерживает протокол MySQL Wire).

1.  **Stateless Nature:**
    *   TiDB Server **не хранит данные**. Вообще. Даже временно на диске.
    *   Это позволяет масштабировать вычислительную мощность (Compute) мгновенно. Если у вас "тяжелый" аналитический запрос или всплеск соединений — вы просто запускаете новый контейнер с TiDB Server. Kubernetes делает это за секунды.

2.  **SQL to KV Mapping (Кодирование схемы):**
    *   Главная магия TiDB — трансляция реляционной модели в плоский Key-Value (потому что TiKV, лежащий ниже, понимает только KV).
    *   **Table Data:** Каждая строка таблицы превращается в Key-Value пару.
        *   `Key`: `tablePrefix{TableID}_recordPrefix{RowID}`
        *   `Value`: `[col1, col2, col3...]` (сжатый массив значений строки).
    *   **Index Data:** Каждый индекс превращается в отдельную KV-запись.
        *   `Key`: `tablePrefix{TableID}_indexPrefix{IndexID}_{IndexValues}`
        *   `Value`: `RowID` (ссылка на строку).
    *   *Expert Insight:* Это объясняет, почему `Secondary Index Lookups` в TiDB дороже, чем в MySQL. Сначала нужно найти `RowID` в индексном регионе (1-й сетевой запрос), а потом саму строку в табличном регионе (2-й сетевой запрос).

3.  **Cost-Based Optimizer (CBO):**
    *   Оптимизатор TiDB решает, как выполнять запрос: использовать ли Index Scan, Table Scan или TiFlash (колонки).
    *   Он использует механизм **Coprocessor API**: TiDB Server не вытягивает все данные к себе. Он отправляет "микро-программы" (фильтры `WHERE`, агрегаты `SUM`) прямо на узлы хранения (TiKV), чтобы фильтрация шла там, где лежат данные ("Push-down computation").

### B. PD (Placement Driver): The Cluster Manager & Time Authority
PD — это не просто хранилище метаданных, это "Дирижер" и "Часовщик". Обычно развертывается кластером из 3 узлов (на базе встроенного etcd).

1.  **Timestamp Oracle (TSO):**
    *   Чтобы обеспечить **External Consistency** (линеаризуемость) без атомных часов (как у Google Spanner), TiDB использует централизованный генератор времени.
    *   Каждая транзакция (начало и коммит) должна получить **TSO** (64-bit integer: физ. время + лог. счетчик) от Лидера PD.
    *   *Физика:* PD способен выдавать миллионы TSO в секунду (батчинг). Но это создает теоретический предел масштабирования для Write-интенсивных систем, если сеть до PD перегружена.

2.  **Region Scheduling (Балансировщик):**
    *   PD хранит карту: "Где лежит Регион №100500?".
    *   Он получает `Heartbeats` от узлов хранения.
    *   Если PD видит, что TiKV-Node-1 перегружена или заполнена, он отправляет команду: *"Перенеси Лидера Региона X на Node-2"*. Это происходит автоматически и прозрачно для SQL-слоя.

### C. TiKV (Storage Layer): The Distributed Row Store
Это фундамент. TiKV — это распределенная транзакционная Key-Value база данных.

1.  **Regions (Единица масштабирования):**
    *   Всё пространство ключей (Key Space) разбито на непрерывные диапазоны — **Regions** (по умолчанию 96MB).
    *   В отличие от шардинга в MongoDB (где чанки большие), мелкие регионы TiDB позволяют очень гранулярно балансировать нагрузку.
    *   Кластер на 100TB может содержать более 1 миллиона регионов.

2.  **Multi-Raft Architecture:**
    *   В традиционных системах (Zookeeper, Etcd) один Raft-лог управляет всеми данными. Это бутылочное горлышко (Sequential IO).
    *   TiKV использует **Multi-Raft**: Каждый Регион — это отдельная, независимая группа Raft (consensus group).
    *   Если у вас 20,000 регионов на узле, у вас концептуально 20,000 Raft-групп.
    *   *Optimization:* Чтобы не убить сеть `Heartbeat`-ами от 20k групп, TiKV мультиплексирует сообщения (Raft Batching).

3.  **RocksDB Inside:**
    *   Каждый узел TiKV использует **RocksDB** (LSM-Tree engine от Facebook) для физического хранения данных на SSD.
    *   На самом деле, внутри одного TiKV есть **два** инстанса RocksDB:
        1.  **Raft Log Engine:** Хранит журнал операций Raft (Write-Ahead Log).
        2.  **KV Engine:** Хранит сами данные.

### D. The Lifecycle of a Query (Пример взаимодействия)

Разберем запрос: `SELECT Name FROM Users WHERE ID = 500`.

1.  **Client:** Подключается к любому TiDB Server.
2.  **TiDB (Parse & Plan):**
    *   Парсит SQL.
    *   Вычисляет Ключ (Key): `t{UsersID}_r{500}`.
    *   Запрашивает TSO (время старта) у PD.
3.  **TiDB (Locate):**
    *   Спрашивает PD (или смотрит в свой кэш): "Где лежит ключ `t..._r500`?"
    *   PD отвечает: "Этот ключ в Регионе №42, Лидер на TiKV-Node-3".
4.  **TiKV (Seek & Read):**
    *   TiDB отправляет RPC запрос на TiKV-Node-3.
    *   TiKV ищет ключ в RocksDB. Проверяет, что версия записи валидна для полученного TSO (MVCC check).
5.  **Return:** TiKV возвращает "сырые байты" строки.
6.  **TiDB (Decode):** Декодирует байты в `Name='Alice'` и отдает клиенту.

### Резюме раздела 2.1
Архитектура TiDB — это триумф декомпозиции.
*   **TiKV** дает надежное хранение и распределение данных (Sharding + Replication).
*   **PD** дает глобальное время и координацию (Consistency + Balancing).
*   **TiDB** дает совместимость с SQL и оптимизацию запросов (Compute).
Эта архитектура позволяет системе пережить потерю любого компонента (кроме кворума PD/TiKV) без потери данных и деградации консистентности.

### 2.2. Distributed Transactions: The Percolator Model

Самая большая проблема распределенных баз данных — это **Атомарность**.
Если вы переводите деньги от Алисы (Шард А) к Бобу (Шард Б), и Шард А записал списание, а Шард Б упал до зачисления — деньги исчезли.

TiDB решает эту проблему, реализуя модель **Percolator**. В отличие от классического XA (где есть тяжелый менеджер транзакций), в TiDB координатором транзакции выступает **сам TiDB Server** (клиентский драйвер), а состояние хранится распределенно в TiKV.

### A. The "Atomic Switch" Concept (Primary Lock)
В классическом 2PC есть момент неопределенности: если координатор падает после отправки `COMMIT` первому узлу, но до отправки второму, система застревает.

Percolator решает это гениально:
1.  Из всех ключей, участвующих в транзакции (Алиса, Боб, Комиссия...), один выбирается случайным образом как **Primary Key**.
2.  Все остальные ключи (**Secondaries**) содержат физическую ссылку (указатель) на Primary.
3.  **Атомарное переключение:** Статус **всей** транзакции (Committed или Aborted) определяется статусом **одного** ключа — Primary Key.

### B. Anatomy of a Transaction (Step-by-Step)

Разберем транзакцию: `UPDATE accounts SET bal = bal - 10 WHERE id = 'Alice'; UPDATE accounts SET bal = bal + 10 WHERE id = 'Bob';`

**Фаза 1: Подготовка (Get & Prewrite)**
1.  **StartTS:** TiDB запрашивает у PD метку времени начала ($T_{start} = 100$).
2.  **Snapshot Read:** TiDB читает текущие балансы Алисы и Боба по состоянию на $T_{start}=100$.
3.  **Selection:** TiDB выбирает `'Alice'` как **Primary Key**. `'Bob'` становится **Secondary**.
4.  **Prewrite (Параллельная запись):**
    *   TiDB шлет команду в TiKV (Шард Алисы): *"Запиши (-10), поставь ЛОК, пометь как Primary"*.
    *   TiDB шлет команду в TiKV (Шард Боба): *"Запиши (+10), поставь ЛОК, ссылка на Primary = 'Alice'"*.
    *   **Важно:** Данные записаны, но они **невидимы** для других транзакций (они под замком).

**Фаза 2: Фиксация (Commit)**
1.  **CommitTS:** Если все Prewrite прошли успешно, TiDB запрашивает у PD метку времени фиксации ($T_{commit} = 110$).
2.  **Commit Primary (The Point of No Return):**
    *   TiDB шлет команду Шарду Алисы: *"Сними замок с Алисы и сделай запись видимой с временем $T_{commit}=110$"*.
    *   Как только этот запрос выполнен успешно в RocksDB — **Транзакция считается закомиченной**. Даже если свет выключится во всем дата-центре.
3.  **Commit Secondaries (Async):**
    *   TiDB шлет команду Шарду Боба: *"Закомить Боба"*.
    *   *Expert Nuance:* Это делается **асинхронно**. TiDB может вернуть клиенту `Success` сразу после шага 2.

### C. Обработка сбоев (Lazy Recovery)
Что, если TiDB упал между шагом 2 и 3?
*   Алиса в статусе `Committed`.
*   Боб в статусе `Locked` (висит замок, указывающий на Алису).

Приходит **читатель** (другая транзакция) читать Боба:
1.  Видит замок на Бобе.
2.  Читает содержимое замка: *"Primary Key = Alice"*.
3.  Идет проверять статус Алисы.
4.  Видит, что Алиса `Committed` с $T_{commit}=110$.
5.  **Roll Forward:** Читатель понимает, что транзакция на самом деле успешна. Он сам (вместо упавшего координатора) "накатывает" коммит на Боба (снимает замок) и читает новое значение.
*   Это называется **Lazy Cleanup**. Система самовосстанавливается при чтении.

### D. Physical Storage (RocksDB Column Families)
Как это выглядит на диске в RocksDB? TiKV использует 3 Column Families (CF) для реализации MVCC:

1.  **CF_DEFAULT (Data):** Хранит большие данные.
    *   Key: `Alice_Key + StartTS(100)` -> Value: `Balance=90`.
2.  **CF_LOCK (Locks):** Хранит текущие блокировки.
    *   Key: `Alice_Key` -> Value: `LockType=Put, Primary=..., TTL=...`
3.  **CF_WRITE (Metadata):** Хранит информацию о коммитах.
    *   Key: `Alice_Key + CommitTS(110)` -> Value: `WriteType=Put, Ref=StartTS(100)`.

**Как происходит чтение (MVCC Read):**
Запрос с $T_{read}=120$.
1.  Ищем в `CF_WRITE` запись с $TS \le 120$. Находим запись от 110.
2.  Из нее узнаем, что данные лежат с $StartTS=100$.
3.  Идем в `CF_DEFAULT` и читаем данные по ключу `Alice + 100`.

### E. Latency Trade-off (Цена 2PC)
Как архитектор, вы должны понимать цену этой магии.
Транзакция Percolator требует сетевых вызовов (RTT):
1.  Получить StartTS (PD).
2.  Prewrite (Parallel TiKV).
3.  Получить CommitTS (PD).
4.  Commit Primary (TiKV).
5.  (Async) Commit Secondaries.

**Итого:** Минимум **3-4 RTT** для последовательной записи.
*   Если Ping между серверами 0.2ms (LAN) — транзакция длится ~1ms.
*   Если Ping 10ms (Cross-Region) — транзакция длится 40ms.
*   **Вывод:** TiDB идеально работает внутри одного DC или AZ (Availability Zone). Растягивать кластер TiDB между континентами для OLTP нагрузки — архитектурная ошибка (из-за физики света).

### Резюме раздела 2.2
Модель транзакций TiDB — это:
*   **Optimistic locking** (по умолчанию) или **Pessimistic locking** (для совместимости с MySQL).
*   **Percolator:** Децентрализованный координатор + "умные" блокировки с Primary Key.
*   **Resilience:** Система устойчива к падению координатора транзакции. Состояние всегда детерминировано состоянием Primary Key в RocksDB.

### 2.3. HTAP Mechanics: TiFlash & Raft Learner

TiFlash — это компонент, превращающий TiDB в HTAP платформу. Это не просто кэш, это **Updatable Column Store**.

#### A. The Raft Learner Pattern
В классическом Raft есть Leader (пишет) и Follower (реплицирует и голосует).
TiFlash подключается к Raft-группе каждого региона как **Learner**:
*   **Non-Voting:** Он получает лог репликации (AppendEntries), но **не голосует**.
*   **Zero Write Penalty:** Если TiFlash медленный или упал, это **не тормозит** транзакционную запись в TiKV (Row Store). Лидеру достаточно кворума из обычных TiKV узлов.

#### B. Real-time Transformation
Внутри TiFlash происходит магия трансформации форматов "на лету":
1.  Получает Raft Log (строчные изменения Key-Value).
2.  Применяет их к локальному хранилищу.
3.  Трансформирует в **Columnar Format** (Delta Tree engine, похожий на ClickHouse MergeTree).

#### C. Strong Consistency (Snapshot Isolation on Columns)
Обычно асинхронная репликация означает "Eventual Consistency" (аналитика отстает). TiDB ломает этот стереотип, используя механизм **Read Index**.

**Сценарий:** Пользователь делает `UPDATE` в 12:00:01 (TSO=100). Аналитик делает `SELECT` в 12:00:02 (TSO=105).
1.  Запрос приходит в TiFlash.
2.  TiFlash видит, что у него данные только до TSO=99.
3.  TiFlash делает легкий RPC-запрос к Лидеру Raft (в TiKV): *"Какой индекс лога соответствует TSO=105?"*
4.  Лидер отвечает: *"Индекс 5000"*.
5.  **Wait:** TiFlash ждет, пока он доиграет свой локальный лог репликации до индекса 5000.
6.  **Serve:** Только после этого он отдает данные.

**Результат:** Аналитик видит данные, согласованные на момент начала запроса. Никаких "фантомных" или "старых" данных. Задержка ожидания (Wait) обычно составляет миллисекунды.

### 2.4. Sharding Physics: Range vs. Hash

В основе любой распределенной системы лежит вопрос: **"Как определить, на каком сервере лежит ключ `User:10500`?"**
Существует два фундаментальных подхода: **Hashing** (Cassandra, DynamoDB, Redis Cluster) и **Range Partitioning** (HBase, Spanner, TiDB).

TiDB выбрал **Range Sharding**. И это решение диктует всю физику производительности.

### A. Range Sharding: Why TiDB chose Order
В TiDB все данные (Таблицы и Индексы) глобально отсортированы по Ключу.
Пространство ключей разбито на непрерывные отрезки — **Regions**.
*   `Region 1`: `[Key 0 ... Key 1,000,000)`
*   `Region 2`: `[Key 1,000,000 ... Key 2,000,000)`

**Почему это было выбрано (The "Scan" Argument):**
Бизнес-приложениям редко нужны случайные ключи (`get(5), get(900)`). Им нужны диапазоны.
*   *Query:* `SELECT * FROM Orders WHERE Date BETWEEN '2026-01-01' AND '2026-01-02'`.
*   *Range Physics:* В TiDB эти данные лежат в соседних регионах (или в одном). Запрос идет на 1-2 сервера. Это эффективно.
*   *Hash Physics:* В Hash-системах (Cassandra) данные за 2 дня "размазаны" случайным образом по всему кластеру. Запрос превращается в **Scatter-Gather** (опросить все 100 узлов), что убивает латентность.

### B. The "Auto-Increment" Suicide (Sequential Write Hotspot)
У Range Sharding есть фатальный недостаток: **Уязвимость к монотонной записи**.

**Сценарий:** Вы мигрируете с MySQL. У вас таблица `Orders` с `PRIMARY KEY AUTO_INCREMENT`.
1.  **Поток данных:** `INSERT ID=100`, `101`, `102` ... `999999`.
2.  **Физика Регионов:**
    *   Все новые ключи всегда больше предыдущих.
    *   Они попадают в **последний** доступный диапазон (Region N).
3.  **The Hotspot:**
    *   В кластере 50 серверов TiKV.
    *   Но запись идет **только в один** сервер (тот, где живет Лидер последнего Региона).
    *   Остальные 49 серверов простаивают на запись (хотя могут читать старые данные).
    *   Когда Регион заполняется (96MB), он расщепляется (Split), и нагрузка переходит на новый "хвостовой" регион. Но это все равно **один** активный регион в любой момент времени.

**Результат:** Вы купили кластер, чтобы масштабировать запись, но получили производительность одного диска.

### C. Mitigation Strategies (Архитектурные решения)

Чтобы "размазать" запись по кластеру в Range-based системе, нужно внести энтропию (хаос) в ключи.

#### Strategy 1: `AUTO_RANDOM` (The Recommended Way)
TiDB 4.0+ ввел специальный тип столбца. Это не случайное число, это **Bit-Manipulation**.

*   **Logic:**
    `ID = <Shard Bits (5 bits)> + <Timestamp/Sequence (59 bits)>`
*   **Physics:**
    *   Первые биты числа (которые определяют сортировку и Регион) — случайны.
    *   Запись `INSERT INTO t VALUES ()` генерирует ID, который может попасть в любой из $2^5 = 32$ диапазонов.
    *   **Write Throughput:** Увеличивается в 32 раза (распараллеливается по 32 регионам/серверам).
*   **Trade-off:** Вы теряете непрерывность ID. Нельзя полагаться на то, что `ID_new > ID_old`.

```sql
CREATE TABLE t (
    id BIGINT PRIMARY KEY AUTO_RANDOM(5), -- 5 бит на шардинг
    data VARCHAR(255)
);
```

#### Strategy 2: `SHARD_ROW_ID_BITS` (Implicit Sharding)
Если у вас нет Primary Key типа Integer (или вы используете UUID), TiDB внутри создает скрытый суррогатный ключ `_tidb_rowid`.
По умолчанию он тоже монотонный.
*   Опция `SHARD_ROW_ID_BITS = 4` заставляет TiDB разбивать этот скрытый ID на $2^4 = 16$ бакетов.
*   Используется, когда вы не можете менять схему Primary Key, но хотите убрать хотспот внутренней вставки.

#### Strategy 3: Hash Partitioning (Hybrid Approach)
В современных версиях TiDB можно использовать партиционирование таблиц, похожее на MySQL.
*   `PARTITION BY HASH(UserID) PARTITIONS 64`.
*   **Физика:** Таблица разбивается на 64 независимых "мини-таблицы" (Партиции). Каждая партиция — это набор Range-регионов.
*   **Плюс:** Вы явно контролируете распределение данных. `UserID=1` всегда в Partition 1.
*   **Минус:** Cross-partition запросы становятся дороже.

### D. Index Hotspots (Скрытая угроза)

Даже если вы используете UUID (случайный) как Primary Key, вы можете убить базу **Индексом**.

**Пример:** `CREATE INDEX idx_created_at ON Orders(created_at);`
*   `created_at` — монотонно возрастающее поле (время всегда идет вперед).
*   **Физика:** Индекс в TiDB — это тоже KV-map, отсортированная по значению индекса.
*   Все новые записи индекса летят в **конец** диапазона индекса.
*   **Результат:** Вы получаете Hotspot на узле, который держит индекс, даже если сами данные размазаны по кластеру.

**Решение:** Не индексировать монотонные поля без композита. Или использовать Partitioning.

### Резюме раздела 2.4

*   **TiDB = Global Sort.** Это дает быстрые `Range Scans`, но наказывает за `Sequential Writes`.
*   **Anti-Pattern:** Никогда не используйте стандартный `AUTO_INCREMENT` в высоконагруженных таблицах TiDB.
*   **Solution:** Используйте `AUTO_RANDOM` для PK. Это компромисс: вы получаете распределение записи (Hash-like performance), сохраняя локальность данных внутри сгенерированных префиксов.

TiDB — это инженерный шедевр, объединивший:
*   **LSM-Tree** (RocksDB) для быстрой записи.
*   **Multi-Raft** для масштабирования консенсуса.
*   **Percolator** для распределенных транзакций.
*   **Raft Learner** для асинхронной, но консистентной аналитики (HTAP).

## 3. SingleStore: The Real-Time Translytical Engine

SingleStore — это база данных, которая отказалась от компромисса "или быстро писать, или быстро читать". Изначально созданная как **In-Memory Rowstore**, она эволюционировала в гибридную платформу, использующую **Universal Storage**.

Ее архитектурная ниша: **Fast Ingest + Instant Analytics**. Это мост между Kafka и Дашбордом.

### 3.1. Architecture: Aggregators & Leaves (Classic MPP)

SingleStore — это классическая **Shared-Nothing MPP (Massively Parallel Processing)** система.
В отличие от монолитного MySQL, где SQL-парсер и движок хранения (InnoDB) живут в одном процессе, SingleStore физически разделяет эти роли на два типа узлов.

### A. Aggregators (The Compute & Control Plane)
Агрегаторы — это "фасад" кластера. Они говорят на протоколе MySQL Wire (совместимы с драйверами MySQL/MariaDB), но не хранят пользовательских данных.

1.  **Master Aggregator (MA):**
    *   **Cardinality:** 1 на кластер (но может быть заменен при сбое).
    *   **Role:** Это "Диктатор". Только он имеет право выполнять DDL операции (`CREATE TABLE`, `ALTER`, `ADD LEAF`).
    *   **Orchestration:** Он мониторит здоровье листьев (Heartbeats) и решает, когда выбросить мертвый узел из кластера.

2.  **Child Aggregators (CA):**
    *   **Cardinality:** От 0 до сотен.
    *   **Role:** Это "Рабочие лошадки" для чтения/записи (DML).
    *   **Scale-Out:** Если у вас 10,000 конкурентных клиентов, вы добавляете больше CA. Они берут на себя нагрузку по парсингу SQL, генерации кода и сборке результатов.
    *   **Smart Routing:** Агрегатор знает карту шардинга. Если запрос идет к конкретному ID (`WHERE id = 5`), агрегатор вычисляет хэш и отправляет запрос **только** на тот Leaf-узел, где лежат данные. Никакого Broadcast.

### B. Leaves (The Data & Execution Plane)
Листья — это "мышцы" системы. Они хранят данные и исполняют скомпилированный код запросов.

1.  **Partitions (The Unit of Sharding):**
    *   Физический сервер (Leaf Node) — это просто контейнер.
    *   Реальная единица хранения — **Partition** (Партиция/Шард).
    *   По умолчанию SingleStore создает `N_CORES / 8` партиций на базу данных на каждом листе.
    *   **Database:** Логическая база данных `mydb` физически представляет собой набор из, скажем, 64 партиций, разбросанных по всем листьям.

2.  **Availability Groups (High Availability):**
    *   Чтобы пережить потерю сервера, Листья объединяются в **Availability Groups (AG)**.
    *   **Redundancy 1 (Dev):** 1 копия данных. Узел умер -> данные потеряны.
    *   **Redundancy 2 (Prod):** Каждый шард имеет **Master Partition** (на Листе А) и **Replica Partition** (на Листе Б).
    *   *Sync/Async:* Репликация может быть синхронной (гарантия данных) или асинхронной (скорость).

### C. Sharding Physics: Hash vs. Reference

Как архитектор, вы должны выбрать стратегию распределения данных для каждой таблицы. В SingleStore это необратимое решение (в отличие от TiDB, где шардинг автоматический).

#### 1. Sharded Tables (Distributed)
Это дефолтный режим для больших данных.
```sql
CREATE TABLE clicks (
    user_id BIGINT,
    url TEXT,
    SHARD KEY (user_id) -- The Magic
);
```
*   **Hash Distribution:** Строка отправляется на партицию `Hash(user_id) % Total_Partitions`.
*   **Co-location:** Все клики одного юзера гарантированно лежат на одной партиции.
*   **Performance:**
    *   `JOIN` двух таблиц по `user_id` происходит **локально** (без сети), если они обе шардированы по `user_id`. Это молниеносно.
    *   `JOIN` по *другому* полю вызывает **Reshuffle** (пересылку данных между листьями). Это дорого.

#### 2. Reference Tables (Replicated)
Используется для маленьких справочников (Страны, Валюты, Категории товаров).
```sql
CREATE REFERENCE TABLE currencies (
    code CHAR(3),
    rate DECIMAL(10,4)
);
```
*   **Broadcast Replication:** Полная копия этой таблицы хранится **на каждом Агрегаторе и каждом Листе**.
*   **Write Penalty:** Запись медленная (нужно обновить все узлы через 2PC).
*   **Read Superpower:** Вы можете джойнить Reference Table с любой шардированной таблицей **локально**. Сетевой оверхед равен нулю.

### D. Distributed Query Execution (Anatomy of a Join)

Разберем, что происходит внутри, когда вы делаете "неправильный" JOIN.

*Query:* `SELECT * FROM users u JOIN clicks c ON u.email = c.email`
*Fact:* `users` шардированы по `user_id`. `clicks` шардированы по `user_id`.
*Problem:* Мы джойним по `email`, который **не является** ключом шардинга.

**Этапы выполнения (The Reshuffle Storm):**
1.  **Aggregator:** Анализирует план. Видит, что ключи не совпадают (Non-colocated join).
2.  **Code Gen:** Компилирует код, который говорит листьям: "Пересчитайте хэш от `email` и перешлите строки друг другу".
3.  **Leaf Execution (Scatter):**
    *   Каждый лист читает свои `users` и `clicks`.
    *   Для каждой строки вычисляет `Hash(email)`.
    *   Отправляет строку по сети на "правильный" лист, отвечающий за этот хэш.
4.  **Network Saturation:** Если таблицы большие, весь кластер встает, забивая 100% сетевого канала (N-to-N communication).
5.  **Leaf Execution (Local Join):** После пересылки происходит локальный джойн.

**Expert Takeaway:**
В MPP системах типа SingleStore **сеть — это бутылочное горлышко**.
Архитектор обязан проектировать схему так, чтобы 90% джойнов были **Co-located** (по Shard Key) или использовали Reference Tables. "Случайные" джойны убьют производительность.

### Резюме раздела 3.1
Архитектура SingleStore требует ручного управления топологией данных:
*   **Aggregators** масштабируют коннекты и парсинг.
*   **Leaves** масштабируют хранение и IO.
*   **Shard Key** — это самое важное решение при создании таблицы. Ошибка здесь приведет к постоянному **Reshuffle** (пересылке данных) при каждом запросе.

### 3.2. Universal Storage: The Physics of "Unification"

Исторически SingleStore (MemSQL) имел "биполярное расстройство": вы должны были выбирать тип таблицы при создании — `Rowstore` (в памяти, для OLTP) или `Columnstore` (на диске, для OLAP). Это создавало головную боль при джойнах и миграции данных.

**Universal Storage** — это архитектурный прорыв, объединивший эти миры. Теперь таблица — это живой организм, который меняет свою физическую форму по мере "старения" данных.

### A. Tier 1: The In-Memory Row Segment (Hot Data)
Все новые данные (`INSERT`, `UPDATE`) попадают сначала сюда.

1.  **Structure:** Это не просто буфер. Это полноценный сегмент таблицы в формате **Row-Store**, хранящийся в RAM.
2.  **Indexing:** Внутри используется **Lock-Free SkipList** (или BW-Tree вариации). Это позволяет конкурентным потокам писать миллионы строк в секунду без блокировок.
3.  **Durability (WAL):** Чтобы не потерять данные при отключении питания, транзакция синхронно пишется в **Transaction Log** на SSD перед ответом клиенту.
    *   *Физика:* Задержка записи = `RAM Write` (наносекунды) + `Seq Disk Write` (микросекунды). Нет случайного I/O.
4.  **Availability:** Данные в этом сегменте доступны для `SELECT` немедленно.

### B. Tier 2: The Disk Column Segment (Warm Data)
Память дорога и конечна. Когда In-Memory сегмент заполняется (например, достигает 100MB), срабатывает триггер **Flush**.

1.  **Transformation:** Фоновый процесс берет "горячий" сегмент из RAM.
2.  **Transposition:** Данные переворачиваются из строк в колонки.
3.  **Compression:** Применяется RLE, Bit-Packing, Dictionary Encoding.
4.  **Write:** Сжатый блок (LSM Component) записывается на SSD как **Immutable File**.
    *   *Важно:* После записи сегмент в RAM очищается. Память освобождается для новых вставок.

### C. Tier 3: The Background Merger (Compaction)
Со временем на диске накапливается много мелких файлов. Это убивает производительность чтения.

**LSM Compaction:**
*   SingleStore имеет фоновый процесс ("Merger"), который берет несколько мелких колоночных файлов.
*   Сливает их в один большой, оптимизированный файл.
*   **Garbage Collection:** Именно в этот момент физически удаляются строки, помеченные как удаленные (Tombstones), и применяются `UPDATE` (которые реализованы как `DELETE` + `INSERT`).

### D. The "Seekable" Columnstore (Secret Sauce)
Это то, что отличает SingleStore от Snowflake или ClickHouse.

В обычных колоночных базах (Parquet/ORC) нельзя быстро найти "Строку №5". Нужно сканировать блок.
SingleStore реализует **Secondary Indexes** прямо поверх сжатых колонок.

1.  **Hash Index:** Для каждого колоночного файла строится хэш-карта (в метаданных), указывающая, в каком блоке лежит `UserID=123`.
2.  **Point Lookups:**
    *   Запрос `SELECT * FROM t WHERE id=123` не сканирует гигабайты колонок.
    *   Он использует индекс, прыгает (Seek) в нужный сжатый блок, распаковывает *только его* и отдает строку.
    *   **Latency:** Sub-millisecond. Это позволяет использовать Universal Storage для **OLTP** нагрузок (обслуживание профилей пользователей), чего не умеет ClickHouse.

### E. The Hybrid Scan (Merge-on-Read)
Как выполняется `SELECT count(*) FROM t`?

Движок SingleStore создает итератор, который "на лету" объединяет данные:
$$Result = Query(RAM\_Segment) \cup Query(Disk\_Segments) \setminus Deleted\_Bitmap$$

1.  **SIMD Scan:** Дисковые сегменты сканируются с использованием AVX2 инструкций (векторизация).
2.  **Row Scan:** Сегмент в памяти сканируется обычным циклом.
3.  **Union:** Результаты суммируются.

Пользователь не видит этой сложности. Он просто видит всегда свежие данные.

### F. Example: IoT Ingestion Scenario
Представьте датчики, шлющие 5 млн событий в секунду.

1.  **Ingest:** Данные залетают в RAM-сегменты. Скорость ограничена только пропускной способностью сети и Sequential Write лога транзакций.
2.  **Real-time Dashboard:** Аналитик делает запрос "Средняя температура за последние 5 секунд".
    *   База читает эти данные **прямо из RAM** (они еще не успели сброситься на диск). Ответ мгновенный.
3.  **Historical Report:** Аналитик просит "Тренды за год".
    *   База поднимает сжатые исторические архивы с SSD (или S3) и сканирует их.

### Резюме раздела 3.2
**Universal Storage** — это попытка создать "Святой Грааль":
*   Поведение **Row-Store** для записи (быстро, конкурентно).
*   Поведение **Column-Store** для хранения (сжатие, сканирование).
*   Умные **Индексы** для точечного чтения.

Это делает SingleStore уникальным продуктом для **HTAP** (Hybrid Transactional/Analytical Processing), где данные рождаются горячими (транзакции) и умирают холодными (аналитика) в одной таблице.

### 3.3. Pipelines: Database as a Stream Processor

Традиционная архитектура "Lambda" или "Kappa" требует прослойки ETL (Apache Kafka Connect, Spark Streaming, Flink) только для того, чтобы переложить данные из трубы (Kafka) в склад (Database).
SingleStore **Pipelines** — это встроенный в ядро механизм, который позволяет базе данных вести себя как Consumer Group, поглощая данные с линейной скоростью масштабирования.

### A. Architecture: Massively Parallel Ingestion (Физика поглощения)

Главный секрет скорости Pipelines — это **прямой маппинг партиций**.

1.  **Kafka-to-Leaf Topology:**
    *   Представьте топик Kafka с 32 партициями.
    *   В кластере SingleStore 8 Leaf-узлов (всего 32 партиции базы).
    *   SingleStore не гонит трафик через Агрегатор (что стало бы узким местом).
    *   Каждый **Leaf-узел** устанавливает прямое TCP-соединение с брокерами Kafka.
    *   **Parallelism:** 32 потока вычитывают данные параллельно. Если вы добавите Leaf-узлы, скорость поглощения (Ingest Rate) вырастет линейно.

2.  **Micro-batching (Batch vs Stream):**
    *   Pipelines работают в режиме **Micro-batches**.
    *   Движок накапливает пачку сообщений (например, 100мс или 10,000 сообщений) и оформляет их как одну транзакцию `INSERT`.
    *   *Trade-off:* Это добавляет небольшую латентность (sub-second), но радикально снижает оверхед на транзакции и WAL (Write-Ahead Log).

### B. Reliability: The Mechanics of "Exactly-Once"

Как гарантировать, что при падении узла мы не потеряем сообщения и не запишем их дважды?

**Atomicity of Offsets (Атомарность Оффсетов):**
SingleStore хранит метаданные пайплайна (текущий Kafka Offset) **в той же транзакции**, что и сами данные.

1.  **Read:** Leaf читает батч сообщений (Offset 100-200).
2.  **Process:** Обрабатывает их (парсит JSON, фильтрует).
3.  **Commit:** Выполняет распределенную транзакцию:
    *   `INSERT INTO events ...` (Данные)
    *   `UPDATE pipelines_meta SET offset = 201 ...` (Метаданные)
4.  **Recovery:** Если транзакция упала, откатываются и данные, и оффсет. При рестарте Pipeline начнет читать с оффсета 100.
    *   **Result:** Гарантия **Exactly-Once Semantics**. Никаких дубликатов.

### C. Transformations: Stored Procedures as ETL

Вы можете загружать данные не просто в таблицу, а в **Stored Procedure**. Это позволяет реализовать сложнейшую логику трансформации на лету.

**Сценарий:** Обогащение (Enrichment) потока кликов данными о пользователе.

```sql
/* 1. Создаем процедуру трансформации */
CREATE OR REPLACE PROCEDURE process_clicks(batch QUERY(json_data TEXT))
AS
BEGIN
    /* batch - это временная таблица с входными данными */
    INSERT INTO clicks (user_id, region, browser, timestamp)
    SELECT
        json_data::$user_id,
        /* Локальный JOIN со справочником IP-адресов прямо во время вставки! */
        geo.region_code,
        json_data::$ua,
        NOW()
    FROM batch b
    LEFT JOIN geo_ip_mapping geo ON b.json_data::$ip = geo.ip_prefix;
END;

/* 2. Подключаем Pipeline к этой процедуре */
CREATE PIPELINE clickstream_pipe
AS LOAD DATA KAFKA 'kafka://broker:9092/clicks'
INTO PROCEDURE process_clicks;
```

**Expert Insight:**
Поскольку справочник `geo_ip_mapping` (Reference Table) находится в памяти на каждом Leaf-узле, этот JOIN выполняется **локально** без сетевых задержек. Вы получаете скорость Spark Streaming, но на SQL и внутри БД.

### D. Error Handling (Shadow Tables)

В реальном мире в Kafka всегда попадает мусор (битый JSON, неверные типы). Обычный `INSERT` упал бы и остановил весь пайплайн.

SingleStore создает теневые файлы/таблицы ошибок (`_errors`):
1.  Если строка битая, она **не останавливает** батч.
2.  Она скидывается в специальную таблицу ошибок с метаданными (исходный текст, причина ошибки, оффсет).
3.  Пайплайн продолжает работать.
4.  Инженеры могут мониторить таблицу ошибок и перезаливать данные после исправления.

### E. Поддерживаемые источники

Pipelines — это абстракция. Она работает не только с Kafka:
1.  **Kafka / Redpanda:** Основной кейс (Streaming).
2.  **S3 / Azure Blob / GCS:** Пайплайн следит за появлением новых файлов в бакете. Как только файл загружен, база его "всасывает". Идеально для **Bulk Load**.
3.  **HDFS:** Для миграции с Hadoop.

### Резюме раздела 3.3
**SingleStore Pipelines** превращают базу данных в активного потребителя событий.
*   **Убирает:** Необходимость в отдельном ETL кластере (меньше серверов, меньше поддержки).
*   **Добавляет:** Возможность делать `JOIN` и сложные проверки (`IF/ELSE`) прямо на входе.
*   **Скорость:** Позволяет достичь пропускной способности миллионов событий в секунду (EPS) с гарантией целостности данных.

### 3.4. Code Generation & SIMD (Query Execution)

Большинство баз данных (PostgreSQL, MySQL, Oracle) работают как **Интерпретаторы**. Они используют модель исполнения **Volcano Iterator Model**:
*   Есть дерево операторов (Scan -> Filter -> Join).
*   Каждый оператор — это класс с виртуальной функцией `next()`.
*   Чтобы получить одну строку, движок делает серию вызовов функций.
*   **Physics Penalty:** Виртуальные вызовы сбивают предсказатель переходов (Branch Predictor) процессора и засоряют кэш инструкций (I-Cache). Оверхед на "обвязку" может составлять 90% времени выполнения запроса.

SingleStore работает как **Компилятор**.

### A. Just-in-Time (JIT) Compilation Pipeline

Когда вы отправляете SQL-запрос, SingleStore превращает его в машинный код.

1.  **Parsing & Optimization:** Строится абстрактное синтаксическое дерево (AST) и выбирается оптимальный план.
2.  **MPL (MemSQL Programming Language):** План транслируется в промежуточное представление (High-level IR).
3.  **C++ Generation:** Движок генерирует исходный код на C++, который реализует логику конкретно этого запроса.
    *   *Пример:* Вместо универсальной функции `Filter(predicate)`, генерируется жесткий код `if (row.col > 5)`.
4.  **Machine Code (LLVM/GCC):** C++ код компилируется в машинные инструкции (Shared Object / DLL) и динамически загружается в память процесса базы данных.
5.  **Execution:** CPU выполняет этот код. Это "Tight Loop" (тугой цикл), который идеально ложится в кэш инструкций и не имеет оверхеда на вызовы функций.

**The "First Run" Penalty & Plan Cache:**
*   Компиляция стоит дорого (100–500 мс).
*   Чтобы не компилировать каждый раз `SELECT * FROM users WHERE id = 1` и `WHERE id = 2`, SingleStore использует **Parametrization**.
*   Он компилирует шаблон запроса. Первый запрос "прогревает" кэш планов (Plan Cache). Последующие запросы с той же структурой, но другими параметрами, используют уже готовый бинарник и выполняются за микросекунды.

### B. SIMD on Universal Storage (Batch Processing)

Для колоночных данных (на диске) SingleStore использует **Vectorized Execution** в сочетании с **SIMD (Single Instruction, Multiple Data)**.

**Физика процесса (Operations on Encoded Data):**
Обычно базы данных сначала распаковывают данные, а потом фильтруют их. SingleStore (используя библиотеку `SimdJSON` и собственные наработки) умеет фильтровать данные **без распаковки**.

**Пример:** Фильтрация `WHERE status = 3` по сжатой колонке.
Представьте, что колонка `status` сжата методом **Bit-Packing** (3 бита на значение).

1.  **Load:** Процессор загружает 256 бит данных в регистр `YMM` (AVX2). Это сразу ~85 значений статуса.
2.  **Compare:** Одной инструкцией `VPCMPEQ` (Vector Packed Compare Equal) процессор сравнивает все 85 значений с числом `3` (также в битовом представлении).
3.  **Result Mask:** Процессор выдает 85-битную маску (Bitmap), где `1` означает совпадение.
4.  **Branchless Logic:** Мы не используем `if (match) copy()`. Мы используем эту битовую маску, чтобы скопировать нужные строки, используя инструкции перестановки (Permutation).

**Результат:** Скорость сканирования достигает скорости пропускной способности оперативной памяти (десятки ГБ/сек на ядро), так как CPU больше не является узким местом.

### C. TVF & MPSQL: User Logic as First-Class Citizen

Поскольку SingleStore — это компилятор, пользовательские функции (UDF) и хранимые процедуры (Stored Procedures) получают суперсилу.

В PostgreSQL/MySQL вызов UDF внутри `SELECT` — это убийца производительности (Context Switch на каждую строку).
В SingleStore UDF написана на **MPSQL** (диалект SQL).
*   При компиляции запроса код UDF **инлайнится** (Inlining) прямо в тело запроса.
*   Оптимизатор видит код функции насквозь и может применять оптимизации (например, выносить константы).
*   **Table Valued Functions (TVF):** Вы можете написать процедуру, которая возвращает таблицу, и использовать её внутри JOIN. Это будет работать так же быстро, как нативный SQL.

### D. Резюме раздела 3.4
Технология кодогенерации SingleStore — это фундаментальное отличие.
*   **Interpreted DBs:** Гибкие, быстрый старт запроса, но медленное исполнение на больших объемах (CPU bottleneck).
*   **Compiled DBs (SingleStore):** Дорогой старт (компиляция), но экстремально быстрое исполнение (Speed of Light).
*   **SIMD:** Позволяет обрабатывать сжатые данные быстрее, чем распакованные, превращая процессор в "камнедробилку" для аналитики.

### 3.5. Troubleshooting & Limits (Где больно?)

Как архитектор, вы должны знать, где SingleStore сломается.

1.  **Memory Pressure (OOM Killer):**
    *   Несмотря на сброс на диск, индексы и метаданные сегментов живут в RAM.
    *   Тяжелые `JOIN` и `GROUP BY` создают хэш-таблицы в памяти (Spill to disk существует, но убивает производительность).
    *   **Риск:** Один "плохой" запрос может съесть всю RAM на Leaf-ноде, и Linux OOM Killer убьет процесс базы. Кластер уйдет в ребалансировку.
    *   *Mitigation:* Настройка `Resource Governance` (лимиты памяти на пул запросов).

2.  **Snapshot Isolation Cost:**
    *   SingleStore реализует MVCC, но хранение версий строк (особенно в In-Memory сегменте) дорогое.
    *   Длинная транзакция блокирует сборку мусора (Garbage Collection). Если у вас есть `UPDATE`, который висит час, память переполнится старыми версиями строк.

3.  **Sharding Skew:**
    *   Если вы выбрали плохой `SHARD KEY` (например, `Country`, где 90% юзеров из `US`), один Leaf-узел получит 90% данных и трафика. Остальные будут простаивать. Выбор ключа шардирования здесь необратим (требует `REBALANCE` и переливки данных).

### Резюме раздела 3

SingleStore — это "Ferrari" в мире баз данных.
*   **Идеальный Use Case:** AdTech (Real-time bidding logs), IoT мониторинг, Финансовые тикеры, Персонализация в реальном времени. Везде, где нужно писать > 100k EPS (Events Per Second) и тут же агрегировать.
*   **Главное отличие:** В отличие от TiDB, который фокусируется на ACID и консистенции, SingleStore фокусируется на "Raw Speed" (Ingest & Query). Он жертвует дешевизной (требует много RAM) ради скорости.

## 4. Snowflake: The Cloud Data Platform

Snowflake совершил революцию, полностью отделив **Storage** (хранение) от **Compute** (вычисления). До него (Teradata, Hadoop) эти вещи были связаны: чтобы добавить CPU, нужно было добавить сервер с дисками. Snowflake позволил масштабировать их независимо.

С введением **Unistore** (Hybrid Tables) в 2022 году, Snowflake вышел из ниши чистого Data Warehouse (OLAP) и стал претендовать на роль NewSQL/HTAP платформы.

### 4.1. Architecture: The Three-Layer Cake

Архитектура Snowflake — это три независимых слоя, которые масштабируются раздельно и связаны глобальной сетью. Чтобы понять, почему Snowflake может выполнять запросы над петабайтами данных, но при этом иметь задержку (latency) на простых выборках, нужно разобрать физику взаимодействия этих слоев.

#### A. Layer 1: Database Storage (The "Infinite" Drive)
В традиционных БД (Oracle RAC) "Shared Disk" — это SAN-хранилище. В Snowflake это **Object Storage** (Amazon S3, Google Cloud Storage, Azure Blob).

1.  **The Persistence Model:**
    *   Это **Единственный Источник Правды (Single Source of Truth)**.
    *   Данные хранятся в проприетарном формате **Micro-partitions** (сжатые, колоночные файлы размером 16MB–500MB).
    *   **Immutability:** Файлы в S3 никогда не изменяются (S3 не поддерживает `fseek` и частичную перезапись). Любой `UPDATE` или `DELETE` порождает *новые* версии микро-партишенов.

2.  **Physics:**
    *   **Latency:** Высокая. Чтение первого байта с S3 занимает **20–100 мс**. Это на порядки медленнее локального SSD.
    *   **Throughput:** Бесконечная. Вы можете читать тысячи файлов параллельно.
    *   **Durability:** 99.999999999% (11 девяток). Snowflake не делает бэкапы в традиционном смысле, он полагается на избыточность S3.

#### B. Layer 2: Query Processing (Virtual Warehouses)
Это "Мышцы". То, что в Snowflake называется **Virtual Warehouse (VW)** — это, на самом деле, **MPP Cluster** из EC2-инстансов (Worker Nodes).

1.  **T-Shirt Sizing (Физика размеров):**
    *   Размер Warehouse — это абстракция над количеством серверов.
    *   **X-Small:** 1 узел.
    *   **Small:** 2 узла.
    *   **Medium:** 4 узла...
    *   **4-X-Large:** 128 узлов.
    *   *Важно:* При увеличении размера в 2 раза вы удваиваете не только CPU/RAM, но и пропускную способность ввода-вывода (IOPS).

2.  **Stateless with State (The SSD Cache):**
    *   Воркеры формально **Stateless** (если их убить, данные не пропадут, так как они в S3).
    *   Однако, каждый воркер оснащен быстрым локальным **SSD (NVMe)**.
    *   **Lazy Caching:** Когда воркер читает микро-партишен с S3, он сохраняет его копию на локальный SSD.
    *   **Data Affinity:** Планировщик старается отправлять запросы к одним и тем же данным на одни и те же воркеры, чтобы попасть в SSD-кэш.
    *   *Expert Insight:* Именно поэтому "холодный" запуск Warehouse медленный (данные тянутся с S3), а "горячий" — быстрый (данные уже на NVMe).

3.  **Isolation:**
    *   Воркеры из Warehouse "Marketing" не делят ресурсы с воркерами из "Finance".
    *   Блокировки (Locks) происходят на уровне метаданных (Слой 3), поэтому тяжелый запрос одного отдела не может заблокировать CPU другого отдела.

#### C. Layer 3: Cloud Services (The Brain & Transaction Manager)
Это "Мозг". Глобальный, мульти-тенантный слой, который работает всегда.

1.  **Metadata Store (FoundationDB inside):**
    *   Snowflake хранит состояние не в файлах данных, а в высокопроизводительном Key-Value хранилище (в недрах используется FoundationDB).
    *   Здесь хранятся: структура таблиц, пользователи, права доступа и **статистика по каждому микро-партишену** (Min/Max значения, Bloom Filters).
    *   *Query Pruning:* Оптимизатор запросов работает именно здесь. Он отсекает 99% файлов данных, просто глядя в метаданные, еще до запуска Warehouse.

2.  **Transaction Management (ACID):**
    *   Так как S3 не поддерживает транзакции, эту роль берет на себя слой Cloud Services.
    *   Транзакция — это атомарное обновление метаданных. "Теперь таблица `Users` состоит из списка файлов `[A, B, C]`".
    *   Это обеспечивает **Snapshot Isolation**.

#### D. The Caching Hierarchy (Три уровня кэша)

Архитектор обязан знать, где могут застрять данные.

1.  **Metadata Cache (L1):** Живет в Cloud Services. Хранит статистику файлов и планы запросов. Позволяет мгновенно компилировать SQL.
2.  **Result Cache (L2):** Живет в Cloud Services.
    *   Хранит **результат** выполнения запроса (например, таблицу из 10 строк) в течение 24 часов.
    *   *Feature:* Если вы повторите тот же SQL (и данные не менялись), Snowflake вернет ответ мгновенно, не запуская Warehouse (бесплатно).
3.  **Local Disk Cache (L3):** Живет на SSD дисках Virtual Warehouse.
    *   Хранит "сырые" микро-партишены. Это "рабочая память" кластера.

#### E. Анатомия запроса (Life of a Query)

Пример: `SELECT COUNT(*) FROM Events WHERE date = '2026-01-16'`.

1.  **Auth & Plan (Cloud Services):**
    *   Пользователь авторизуется.
    *   Оптимизатор смотрит в метаданные: "Какие микро-партишены содержат дату `2026-01-16`?".
    *   Находит 5 файлов из миллиона (Pruning).
2.  **Dispatch (Cloud Services -> Compute):**
    *   Слой сервисов отправляет инструкции ("Прочитай эти 5 файлов") в активный Virtual Warehouse.
3.  **Execution (Compute):**
    *   Воркеры проверяют свой локальный SSD кэш.
    *   *Miss:* Если файлов нет, читают их с S3 (IO wait).
    *   *Hit:* Если файлы есть, читают с SSD (Instant).
    *   Воркеры распаковывают колонки, считают `COUNT(*)` и отправляют агрегированный результат обратно.
4.  **Result (Cloud Services -> Client):**
    *   Результат сохраняется в Result Cache и отдается клиенту.

#### Резюме раздела 4.1
Архитектура Snowflake уникальна тем, что она вынесла **State (Состояние)** из вычислительных узлов в два внешних хранилища:
1.  **Состояние данных** — в S3 (дешево, надежно, медленно).
2.  **Состояние транзакций/метаданных** — в Cloud Services (быстро, глобально).

### 4.2. Storage Physics: Micro-partitions & Pruning

В традиционных базах данных (PostgreSQL, Oracle) администратор сам решает, как партиционировать таблицу (Range, List, Hash).
Snowflake отобрал это право у людей. Он использует концепцию **Automatic Micro-partitioning**.

### A. The Micro-partition (The Atomic Unit)

Микро-партишен — это фундаментальная единица хранения, ввода-вывода (I/O) и кэширования.

1.  **Physical Size (The "Goldilocks" Zone):**
    *   Файл весит **~16 MB** в сжатом виде.
    *   В разжатом виде (в памяти) это **50–500 MB** данных.
    *   *Почему 16 MB?* Это инженерный компромисс.
        *   Если меньше: Слой метаданных "взорвется" от миллиардов записей о файлах.
        *   Если больше: Операция записи (S3 PUT) станет слишком долгой, а чтение одной строки потребует скачивания гигабайтного блоба.

2.  **Internal Structure (Hybrid Columnar / PAX):**
    *   Внутри файла данные хранятся **поколонно**.
    *   Колонки сжаты индивидуально (используются алгоритмы, специфичные для типов данных: Delta, RLE, Bit-packing).
    *   Заголовок файла содержит смещения (offsets) для каждой колонки. Это позволяет воркеру скачать весь файл, но распаковать только колонки `User_ID` и `Date`, не трогая тяжелую колонку `JSON_Payload`.

3.  **Immutability (Неизменяемость):**
    *   Раз записанный в S3 микро-партишен **никогда не меняется**.
    *   Это позволяет Snowflake использовать агрессивное кэширование (HTTP ETag, SSD Cache) без страха рассинхронизации кэша (Cache Coherency problems).

### B. Pruning: The Art of "Not Reading"

Самая быстрая операция ввода-вывода — та, которой не было.
**Pruning (Отсечение)** — это механизм, позволяющий игнорировать 99% данных.

В отличие от Hive/Spark, где метаданные (Parquet Footer) лежат в самом файле (требуется чтение), Snowflake хранит агрегированную статистику **в глобальном слое Cloud Services** (FoundationDB).

**Metadata Stats (хранятся для каждого файла):**
*   **Min/Max:** Минимальное и максимальное значение для каждой колонки.
*   **NULL Count:** Количество пустых значений.
*   **Distinct Count:** Количество уникальных значений.
*   **Bloom Filters:** Вероятностная структура для проверки "может ли значение X быть в этом файле?".

**Пример Pruning:**
Запрос: `SELECT * FROM Orders WHERE Date = '2026-01-16' AND ClientID = 500`.
Всего в таблице: 10,000 микро-партишенов (160 GB).

1.  **Logical Pruning (Cloud Services):**
    *   Движок смотрит метаданные.
    *   Файл 1: `Date Range: [2025-01-01, 2025-02-01]`. -> **Drop** (диапазон не пересекается).
    *   Файл 2: `Date Range: [2026-01-01, 2026-02-01]`. -> **Keep** (потенциальный кандидат).
    *   *Результат:* Осталось 50 файлов.
2.  **Bloom Filter Check (Cloud Services):**
    *   Для оставшихся 50 файлов проверяем Bloom Filter колонки `ClientID`.
    *   В 48 файлах фильтр говорит: "Значения 500 точно нет". -> **Drop**.
    *   *Результат:* Осталось 2 файла.
3.  **Physical Read (Compute):**
    *   Virtual Warehouse скачивает только эти 2 файла (32 MB).
4.  **Efficiency:** Мы прочитали 32 MB вместо 160 GB. Ускорение в 5000 раз.

### C. The Entropy Problem: Clustering & Sorting

Pruning работает идеально, только если данные **отсортированы**.
Если вы пишете данные в случайном порядке (Random Ingest), то:
*   Файл 1: `Date=[2020...2025]`
*   Файл 2: `Date=[2020...2025]`
*   ...
*   Файл 1000: `Date=[2020...2025]`

При запросе `WHERE Date='2023'` диапазоны Min/Max всех 1000 файлов пересекаются с искомой датой. Pruning не сработает. Система скачает всё.

**Решение: Clustering Keys.**
Вы можете указать `CLUSTER BY (Date)`.
*   Snowflake запускает фоновый процесс **Automatic Clustering**.
*   Он читает "плохие" микро-партишены, сортирует строки и перезаписывает их в новые файлы, где диапазоны дат узкие и не пересекаются.
*   *Trade-off:* Вы платите кредиты (деньги) за эту фоновую пересортировку.

### D. Impact on DML (Write Amplification)

Понимание физики микро-партишенов объясняет, почему Snowflake не любит частые мелкие обновления.

**Сценарий:** `DELETE FROM Users WHERE ID = 1`.
Строка с `ID=1` находится в микро-партишене `File_A` (16MB, 1 миллион строк).

1.  Чтобы удалить 1 строку, Snowflake должен:
    *   Прочитать `File_A`.
    *   Убрать строку в памяти.
    *   Сформировать новый файл `File_B` (15.99 MB).
    *   Записать `File_B` в S3.
    *   Обновить метаданные.
2.  **Write Amplification:** Мы удалили 100 байт, но совершили I/O на 32 MB (16 Read + 16 Write).
3.  **Cost:** Вы платите за S3 PUT запросы и за время работы Warehouse.

**Expert Advice:**
В Snowflake никогда не делайте `INSERT/UPDATE` по одной строке. Используйте **Bulk Load** (`COPY INTO`) или накапливайте изменения и применяйте их пачками (`MERGE`).

### Резюме раздела 4.2
Storage Engine в Snowflake — это система **Copy-on-Write** над иммутабельными блобами.
*   **Скорость чтения** зависит не от скорости диска, а от качества **Pruning** (насколько хорошо метаданные позволяют пропускать файлы).
*   **Clustering** — это критический фактор производительности для больших таблиц. Если "Depth" кластеризации плохая, Snowflake деградирует до скорости Hive.

### 4.3. DML Physics: Copy-on-Write (Почему UPDATE дорогой)

В мире традиционных баз данных (PostgreSQL, Oracle) операция `UPDATE` — это локальное изменение страницы данных (in-place mutation) плюс запись в журнал (WAL). Это дешево.

В Snowflake физическим слоем хранения является **Object Storage (S3, Azure Blob)**.
Главный закон облачного хранения: **Объекты неизменяемы (Immutable)**.
*   Вы не можете открыть файл на S3, найти 5-й байт и заменить его на `1`.
*   Вы можете только записать **новый** файл целиком.

Это диктует архитектуру **Copy-on-Write (CoW)**.

### A. Анатомия `UPDATE` (The 16MB Penalty)

Разберем физику процесса на микро-уровне.
Представьте таблицу `Users` размером 1 ТБ, состоящую из микро-партишенов по 16 МБ.

**Сценарий:** Вы выполняете `UPDATE Users SET Status = 'Banned' WHERE UserID = 105`.

1.  **Pruning (Locate):**
    *   Слой Cloud Services сканирует метаданные и находит, что `UserID = 105` живет в микро-партишене `File_V1_abc` (размер 16 МБ, содержит 500,000 строк).
2.  **Read (Download):**
    *   Virtual Warehouse скачивает весь файл `File_V1_abc` с S3 на локальный SSD. (Cost: 16 MB I/O).
3.  **Mutate (In-Memory):**
    *   В памяти воркера файл распаковывается, строка 105 изменяется, данные снова сжимаются.
4.  **Write (Upload):**
    *   Warehouse создает **новый** микро-партишен `File_V2_xyz`.
    *   Загружает его в S3. (Cost: 16 MB I/O).
5.  **Atomic Swap (Metadata Commit):**
    *   Слой Cloud Services атомарно обновляет указатель: "Для таблицы Users удалить ссылку на `File_V1_abc` и добавить ссылку на `File_V2_xyz`".
    *   *Важно:* Старый файл не удаляется физически сразу (он нужен для Time Travel).

**Математика Усиления Записи (Write Amplification):**
Вы изменили **10 байт** (слово 'Active' на 'Banned').
Система совершила I/O на **32 МБ** (16 Read + 16 Write).
$$WA = \frac{32,000,000}{10} = 3,200,000$$
Вы заплатили (кредитами Snowflake) за обработку 32 мегабайт ради 10 байт.

### B. The Fragmentation Trap (`INSERT` issues)

Если `UPDATE` страдает от перезаписи больших файлов, то `INSERT` страдает от создания "мусора".

**Сценарий:** Вы пишете лог событий по одной строке: `INSERT INTO Logs VALUES (...)`.
1.  Каждый `INSERT` — это транзакция.
2.  Snowflake не может дописать в существующий файл. Он создает **новый** микро-партишен.
3.  Если вы делаете 1 вставку в секунду, через час у вас будет **3600 файлов** размером по 1 КБ.

**Последствия:**
*   **Pruning Failure:** Метаданные раздуваются. Чтобы выполнить `SELECT`, движку нужно проверить 3600 заголовков файлов вместо одного.
*   **Compaction Cost:** Snowflake запускает фоновый процесс (Auto-clustering), который читает эти 3600 мелких файлов и сливает их в один нормальный (16 МБ). Вы платите за эти вычислительные ресурсы.

### C. `DELETE` Physics (Soft vs Hard)

Как работает `DELETE FROM Users WHERE UserID = 105`?
В отличие от некоторых систем, использующих Tombstones (файлы "удалений"), Snowflake обычно использует тот же механизм **Rewrite**.
*   Он читает файл, выбрасывает строку, пишет новый файл (без этой строки).
*   *Исключение:* Если `DELETE` удаляет **весь** микро-партишен (например, `DELETE WHERE Date < '2020'`), это операция над метаданными (Metadata-only drop). Это бесплатно и мгновенно.

### D. Архитектурные паттерны (Best Practices)

Как архитектор, вы должны адаптировать работу с данными под физику CoW:

1.  **Batching is King:** Никогда не пишите по одной строке. Используйте Kafka коннектор или буфер, чтобы писать данные пачками (хотя бы по 10-50 МБ), используя команду `COPY INTO`.
2.  **Staging Tables (Transient):**
    *   Загружайте "сырые" данные во временные таблицы (`TRANSIENT table`). У них нет Time Travel (или он короткий), что экономит место.
    *   Потом делайте тяжелый `MERGE` в основную таблицу.
3.  **Use `MERGE` instead of `UPDATE` loop:**
    *   Вместо цикла из 1000 апдейтов, создайте временную таблицу с изменениями и выполните одну команду `MERGE`.
    *   Snowflake прочитает целевой микро-партишен **один раз**, применит все 1000 изменений в памяти и запишет его обратно **один раз**.

### Резюме раздела 4.3
DML в Snowflake — это процесс **Управления Файлами**, а не изменения ячеек.
*   **Copy-on-Write** гарантирует ACID и Time Travel, но наказывает за мелкие транзакции.
*   **Write Amplification** — главный враг вашего бюджета.
*   Использование Snowflake как OLTP (построчная запись) — это самый дорогой способ сжечь бюджет проекта. Для таких задач используйте **Unistore (Hybrid Tables)**, который использует другой движок хранения (B-Tree), или внешний кэш.

### 4.4. Unistore & Hybrid Tables (The HTAP Evolution)

Традиционный паттерн архитектуры данных — это "Velcro Architecture" (Архитектура на липучке):
1.  **PostgreSQL** держит состояние приложения (User Sessions, Shopping Cart).
2.  **ETL Pipeline (Fivetran/Kafka)** переливает данные в Snowflake.
3.  **Snowflake** делает аналитику.
4.  **Reverse ETL** возвращает сегменты пользователей обратно в Postgres.

**Unistore** пытается убить эту сложность, предлагая **Hybrid Tables**. Это таблицы, которые ведут себя как Postgres (быстрые `INSERT` и `GET`), но живут внутри Snowflake.

### A. The Hidden Row Engine (Двигатель внутри двигателя)

Под капотом Hybrid Tables используют совершенно другую физическую структуру хранения, нежели стандартные Micro-partitions.

1.  **Row-Oriented Storage:**
    *   Данные хранятся построчно (как в InnoDB или RocksDB).
    *   *Физика:* Это позволяет читать "Всё о заказе №105" за одно обращение к диску (1 IOPS), вместо того чтобы собирать данные из 50 колоночных файлов.
2.  **B-Tree Indexes:**
    *   В стандартном Snowflake индексов **нет** (только Pruning метаданных).
    *   В Hybrid Tables есть **настоящие B-Tree индексы**.
    *   Вы можете объявить `PRIMARY KEY` и `SECONDARY INDEX`.
    *   *Enforcement:* В отличие от стандартных таблиц (где PK — это просто декорация для документации), в Hybrid Tables база данных **физически гарантирует** уникальность (Uniqueness Constraint) и ссылочную целостность (Foreign Keys).
3.  **Locking Model:**
    *   Вместо грубой блокировки партиций, Hybrid Tables реализуют **Row-Level Locking**. Это позволяет тысячам пользователей обновлять разные строки одной таблицы одновременно без конфликтов (High Concurrency).

### B. Persistence & Durability (S3 vs SSD)

Как заставить медленный S3 работать быстро для OLTP?

1.  **Log-Structured Storage:**
    *   Изменения сначала пишутся в **Write-Ahead Log (WAL)**.
    *   WAL асинхронно сбрасывается в S3 для надежности (Durability).
2.  **Aggressive SSD Caching:**
    *   Воркеры Virtual Warehouse держат "горячую" часть B-Tree индексов и данных на своих локальных NVMe SSD.
    *   Если данные в кэше, чтение происходит с латентностью **< 10ms** (Single-digit millisecond latency). Это на порядок быстрее, чем чтение с S3.

### C. The "Unified" Query Execution (Joins across Worlds)

Магия Unistore не в том, что это "еще один Postgres", а в том, что вы можете джойнить OLTP и OLAP в одном запросе.

**Сценарий:** У нас есть `Current_Orders` (Hybrid Table, OLTP) и `History_Logs` (Standard Table, 5 PB, OLAP).

```sql
SELECT 
    o.order_id,             -- из быстрого Row Store
    COUNT(h.log_id)         -- из гигантского Column Store
FROM Current_Orders o       -- Hybrid Table
JOIN History_Logs h         -- Standard Table
  ON o.user_id = h.user_id
WHERE o.status = 'PENDING'; -- Point Lookup по индексу
```

**Физика выполнения:**
1.  Движок использует **Index Seek** по Hybrid Table, чтобы мгновенно найти активные заказы.
2.  Движок использует **Column Scan** (с Pruning) по стандартной таблице для истории.
3.  Результаты объединяются в памяти Warehouse.
*   *Без Unistore:* Вам пришлось бы делать запрос в Postgres, получать ID, и передавать их списком `IN (...)` в запрос к Snowflake.

### D. Trade-offs & Limitations (Цена магии)

Как архитектор, вы должны понимать, за что платите.

1.  **Storage Cost:**
    *   Hybrid Tables занимают **больше места**, чем стандартные. Row-формат сжимается хуже колоночного, плюс индексы (B-Trees) занимают значительный объем.
    *   Стоимость хранения Hybrid Tables выше.
2.  **Throughput Limits:**
    *   Хотя это OLTP, это **не** Redis и не ScyllaDB.
    *   Throughput ограничен мощностью Virtual Warehouse. Вы не получите миллион TPS (Transactions Per Second). Рассчитывайте на тысячи.
3.  **Compute Coupling:**
    *   Для обслуживания запросов к Hybrid Tables нужен **запущенный** Warehouse. Если он "спит" (Auto-suspend), первый запрос будет иметь задержку на пробуждение (секунды). Для API приложений это может быть критично.

### E. Example: Inventory Management System

**Задача:** Интернет-магазин. Нужно проверять остатки товара (Inventory) в реальном времени перед покупкой и обновлять их.

*   **Old Way:** Redis/Postgres для Inventory. Snowflake для аналитики продаж. Сложная синхронизация (CDC). Риск продать товар, которого нет, пока данные летят в аналитику.
*   **Unistore Way:**
    *   Таблица `Inventory` создается как Hybrid Table.
    *   Web-сервер делает `UPDATE Inventory SET qty = qty - 1 WHERE id = ...` прямо в Snowflake.
    *   Аналитики видят падение стока **мгновенно** (Real-time visibility).

### Резюме раздела 4.4
**Unistore** превращает Snowflake из "Кладбища данных" (куда данные приходят умирать и анализироваться) в "Операционную платформу".
*   **Используйте Hybrid Tables для:** Состояния сессий, справочников, текущих очередей заказов, метаданных приложений.
*   **Не используйте для:** Логов событий (дорого), исторических архивов (медленно сканировать), высокочастотного трейдинга (недостаточно быстро).

### 4.5. Time Travel & Zero-Copy Cloning (Features from Physics)

В классических БД (PostgreSQL, MySQL) реализация "отката во времени" или "клонирования терабайтной базы" — это кошмар администратора, требующий восстановления из бэкапов (PITR) или физического копирования файлов (rsync).

В Snowflake это метаданные операции, занимающие миллисекунды. Это работает благодаря **MVCC (Multi-Version Concurrency Control)**, доведенному до абсолюта на уровне файловой системы S3.

#### A. Time Travel: Querying Ghosts

**Time Travel** позволяет вам запустить `SELECT` к состоянию базы, каким оно было 5 минут (или 90 дней) назад.

**Физика процесса (Metadata Pointers):**
Слой Cloud Services хранит историю версий метаданных таблицы.
Представьте таблицу `Orders`, состоящую из микро-партишенов `{A, B}`.

1.  **State T1 (12:00):** Метаданные говорят: `Orders = [File_A, File_B]`.
2.  **Operation:** `UPDATE Orders ...` изменяет строки в файле `A`.
3.  **State T2 (12:05):**
    *   Snowflake записывает новый `File_A_v2`.
    *   **Важно:** Старый `File_A` **не удаляется** с S3.
    *   Метаданные обновляются: `Orders = [File_A_v2, File_B]`.
4.  **Time Travel Query:**
    `SELECT * FROM Orders AT(TIMESTAMP => '12:00')`
    *   Движок игнорирует текущее состояние.
    *   Он находит снапшот метаданных на 12:00.
    *   Видит список `[File_A, File_B]`.
    *   Скачивает эти файлы (они все еще лежат в S3) и отдает результат.

**Ограничения и Fail-safe:**
*   **Retention Period:** Вы платите за хранение этих "призрачных" файлов. По умолчанию 1 день (Standard Edition) или до 90 дней (Enterprise).
*   **Fail-safe:** Когда период Time Travel истекает (например, на 91-й день), файлы не удаляются мгновенно. Они переходят в зону **Fail-safe** (еще 7 дней), откуда данные может достать только техподдержка Snowflake (Disaster Recovery). Только после этого S3 Garbage Collector удаляет файлы физически.

#### B. Zero-Copy Cloning: The "Git Branch" for Data

Команда `CREATE TABLE dev_db CLONE prod_db` создает копию петабайтной базы данных за 10 секунд без удвоения счета за хранение.

**Физика процесса (Metadata Copy):**
Клонирование в Snowflake — это создание нового пространства имен (Namespace), которое указывает на **те же самые** микро-партишены в S3.

1.  **Initial State:**
    *   `Table_Prod` points to `[File_1, File_2, File_3]`.
    *   Выполняем `CLONE`.
    *   `Table_Dev` points to `[File_1, File_2, File_3]`.
    *   **Used Storage:** 3 файла. Платим за 3 файла (так как они общие).

2.  **Divergence (Расхождение):**
    *   Разработчик делает `DELETE FROM Table_Dev` (удаляет данные из `File_1`).
    *   Snowflake создает новый файл `File_1_deleted` (где строки помечены как удаленные) или просто обновляет метаданные `Table_Dev`.
    *   `Table_Prod` points to `[File_1, File_2, File_3]`. (Без изменений).
    *   `Table_Dev` points to `[File_2, File_3]`. (Изменено).
    *   **Used Storage:** Теперь мы храним оригиналы + дельту изменений.

**Use Case:** Это киллер-фича для CI/CD. Вы можете поднимать полные копии PROD-окружения для каждого Pull Request, прогонять миграции и тесты, и убивать клон. Это стоит копейки, так как вы платите только за *измененные* данные в клоне.

#### C. The `UNDROP` Miracle

Поскольку удаление — это просто обновление метаданных, Snowflake поддерживает команду `UNDROP TABLE` (или Schema/Database).

**Физика:**
1.  `DROP TABLE Users`: Snowflake помечает таблицу как "Deleted" и запускает таймер Retention (Time Travel). Файлы в S3 не трогаются.
2.  `UNDROP TABLE Users`: Snowflake находит последнюю версию метаданных удаленной таблицы и восстанавливает указатель на нее.
3.  **Result:** Восстановление терабайтов данных происходит мгновенно.

#### D. Cost Implications (Скрытая цена)

Как архитектор, вы должны предупредить бизнес о цене этих чудес.

**High Churn Trap (Ловушка высокой текучести):**
Если у вас есть таблица (10 TB), которую вы полностью перезаписываете (ETL Full Reload) каждый день, и вы включили **Time Travel = 90 дней**:
*   День 1: 10 TB активных + 0 TB Time Travel.
*   День 2: 10 TB активных + 10 TB Time Travel (вчерашних).
*   ...
*   День 90: 10 TB активных + **900 TB** Time Travel.

**Счет за хранение:** Вы будете платить за ~1 Петабайт данных, хотя "активных" данных у вас всего 10 ТБ.
*   *Решение:* Для ETL таблиц (Staging), которые часто перезаписываются, используйте `TRANSIENT` таблицы. У них нет Time Travel (или он равен 0/1 день) и нет Fail-safe.

#### Резюме раздела 4.5
Time Travel и Cloning — это побочные эффекты архитектуры **Copy-on-Write** над иммутабельным объектным хранилищем.
*   **Клон** — это новый указатель на старые данные.
*   **Time Travel** — это старый указатель на старые данные.
*   **Цена:** Вы платите за хранение всех версий файлов, пока они находятся в окне Retention.

Эти функции превращают Snowflake из простого хранилища в **Platform for Data Ops**, позволяя обращаться с данными так же гибко, как с исходным кодом в Git.

---
### Резюме раздела 4
Snowflake — это торжество метаданных над сырой силой.
*   **Pruning** заменяет индексы.
*   **Virtual Warehouses** дают изоляцию нагрузок (Marketing не тормозит Finance).
*   **S3** дает бесконечную емкость.
*   **Unistore** закрывает последний гештальт — потребность в быстрой транзакционной записи.

## 5. Comparative Analysis (The Decision Matrix)

Выбор между TiDB, SingleStore и Snowflake — это не выбор между брендами. Это выбор между тремя разными физическими моделями, каждая из которых оптимизирована под конкретную точку в пространстве **CAP-теоремы** и **Storage Hierarchy**.

### 5.1. The Grand Comparison Table (Technical Deep Dive)

| Характеристика | **TiDB** (PingCAP) | **SingleStore** (ex-MemSQL) | **Snowflake** (Unistore) |
| :--- | :--- | :--- | :--- |
| **Architectural DNA** | **Spanner-like**. Распределенный NewSQL. Row-store с асинхронной Column-репликой. | **In-Memory MPP**. Гибридный движок, ориентированный на скорость RAM и компиляцию кода. | **Disaggregated Data Cloud**. Stateless вычисления поверх Object Storage (S3). |
| **Primary Storage** | **LSM-Tree (RocksDB)** on SSD. | **Universal Storage** (RAM Buffer + Disk Columnar). | **Micro-partitions** (S3 Blob) + B-Tree (Unistore). |
| **Write Latency** | **Medium (2-5 ms)**. Требует Raft Consensus (RTT) и 2PC. | **Ultra Low (µs)**. Пишет в RAM. Лимитировано только WAL на SSD. | **High (s)** для стандартных, **Low (ms)** для Hybrid Tables. |
| **Ingest Throughput** | **High**. Шардируется по регионам. Hotspots возможны на монотонных ключах. | **Extreme**. Параллельное чтение Kafka каждым листом. Лучший в классе. | **Medium**. Оптимизирован под Batch Load (`COPY`). Мелкая вставка дорогая. |
| **Read Latency (Point)** | **Medium**. Дороже чем в MySQL из-за RPC вызовов к TiKV. | **Low**. Если данные в RAM или используют Hash Index на диске. | **High**. Требует прогрева кэша SSD. Холодный старт = S3 latency (50ms+). |
| **Consistency Model** | **Linearizable / Snapshot Isolation**. Глобально строгая (благодаря PD Oracle). | **Strong** внутри партиции. **Eventual** между партициями (по умолчанию). | **Snapshot Isolation**. Глобальная ACID на уровне метаданных. |
| **Concurrency (OLTP)** | **High**. MVCC + Row-level locking. Масштабируется линейно. | **Medium/High**. Lock-free structures, но тяжелые запросы могут забить RAM. | **Medium**. Hybrid Tables дают Row-locking, но пропускная способность ниже. |
| **Protocol** | MySQL 5.7 / 8.0 Wire. | MySQL Wire. | Proprietary (JDBC/ODBC), REST, Python. |
| **Ops Complexity** | **High**. Требует управления PD, TiKV, TiDB, TiFlash. (Или TiDB Cloud). | **Medium**. Агрегаторы + Листья. Требует тщательного сайзинга RAM. | **Zero**. Fully Managed SaaS. Вы управляете только деньгами (Credits). |

---
### 5.2. Decision Dimension 1: The "Workload Physics"

Какая физическая задача стоит перед системой?

#### Scenario A: "The Scalable MySQL" (Core Banking, User Profiles, Gaming)
*   **Задача:** У вас есть MySQL, он вырос до 5TB, шардинг вручную (Vitess/ProxySQL) стал кошмаром. Нужны ACID транзакции, строгая схема, FK. Аналитика вторична.
*   **Winner: TiDB.**
    *   *Почему:* Это единственная система здесь, которая ведет себя как "Бесконечный MySQL". Она гарантирует ACID распределенно. SingleStore слабее в строгой консистенции Cross-Shard транзакций. Snowflake Hybrid Tables слишком дороги и ограничены по TPS.

#### Scenario B: "The Firehose" (AdTech, IoT, Clickstream, Real-time Fraud)
*   **Задача:** В секунду прилетает 500k событий. Их нужно сохранить, проверить правила (Fraud Check) и показать на дашборде с задержкой < 1 сек.
*   **Winner: SingleStore.**
    *   *Почему:* TiDB захлебнется на Write Hotspots при такой нагрузке (или потребует огромного кластера). Snowflake будет иметь латентность в секунды/минуты (Micro-batching). SingleStore "проглатывает" данные в RAM и позволяет делать SQL-запросы по ним немедленно.

#### Scenario C: "The Enterprise Brain" (Corporate DWH, BI, Data Science)
*   **Задача:** Собрать данные из Salesforce, SAP, Logs (50 источников). Хранить вечно (Петабайты). Аналитики запускают тяжелые SQL-запросы раз в час.
*   **Winner: Snowflake.**
    *   *Почему:* Здесь важна **Elasticity**. Аналитики спят ночью — вы не платите за Compute. Нужно прогнать тяжелый отчет — вы подняли 4XL кластер на 5 минут. В TiDB/SingleStore вы платите за сервера 24/7 (так как данные лежат на локальных дисках/RAM).

---
### 5.3. Decision Dimension 2: The Economic Model (FinOps)

Архитектор обязан считать TCO (Total Cost of Ownership).

1.  **TiDB (Infrastructure Heavy):**
    *   *Cost Driver:* **Replication Factor = 3**. Чтобы хранить 1TB данных, вам нужно 3TB SSD (+ TiFlash копии).
    *   *Network:* Много межсерверного трафика (Raft).
    *   *Verdict:* Дорого по железу, но предсказуемый Flat Rate.

2.  **SingleStore (RAM Heavy):**
    *   *Cost Driver:* **RAM**. Лицензирование и железо часто привязаны к объему памяти. In-Memory сегменты требуют дорогих инстансов (например, AWS r6i).
    *   *Verdict:* Самая высокая стоимость за ГБ "горячих" данных. Дешево для исторических (S3 tier).

3.  **Snowflake (Consumption Heavy):**
    *   *Cost Driver:* **Compute Credits**. Вы платите за *секунду* работы Warehouse.
    *   *Storage:* Дешево (Pass-through S3 cost).
    *   *Trap:* "Lazy Query Tax". Один плохой запрос (Full Scan), запущенный в цикле, может сжечь годовой бюджет за неделю.
    *   *Verdict:* Низкий стартовый порог, но потенциально бесконечный чек при плохом управлении.

---
### 5.4. Decision Dimension 3: The "Kill Switch" (Когда НЕ использовать)

Знание анти-паттернов важнее знания фич.

**⛔ Do NOT use TiDB if:**
*   Вам нужна латентность чтения как у Redis (< 1ms). Сетевые хопы (TiDB -> TiKV) добавляют минимум 1-2мс.
*   У вас аналитика на 99% (OLAP). TiKV (Row Store) будет лишним оверхедом. Лучше взять чистый ClickHouse.

**⛔ Do NOT use SingleStore if:**
*   Ваш бюджет жестко ограничен. In-Memory архитектура требует дорогого железа.
*   Вам нужны сложные распределенные транзакции с высочайшим уровнем изоляции (Serializable) между шардами.
*   У вас Blob-данные (большие JSON/Text). Они забьют RAM.

**⛔ Do NOT use Snowflake if:**
*   Вам нужно приложение с интерфейсом для конечного пользователя (User-facing app) с SLA < 100ms. Холодный старт Warehouse убьет UX.
*   У вас поток одиночных `INSERT/UPDATE` (High churn). Write Amplification разорит вас.

### 5.5. Summary Recommendation

*   **TiDB** — это **Evolution**. Выбирайте его, чтобы масштабировать MySQL-подобные нагрузки, сохраняя сон администраторов благодаря ACID.
*   **SingleStore** — это **Velocity**. Выбирайте его, когда время от "события" до "решения" должно быть нулевым.
*   **Snowflake** — это **Gravity**. Выбирайте его как центр притяжения всех данных компании, где сходятся OLAP и (с Unistore) легкий OLTP, и где простота использования важнее "сырой" производительности железа.

## 6. Deep Internals & Troubleshooting

Закон дырявых абстракций (Joel Spolsky) гласит: "Любая достаточно сложная абстракция протекает".
NewSQL/HTAP базы — это сложнейшие абстракции над сетью, дисками и памятью. Когда они "текут", они текут не ошибками SQL, а катастрофической деградацией производительности (Latency spikes, OOM, Hotspots).

### 6.1. TiDB: The Raft Leader Bottleneck (Hotspots)

Главная болезнь TiDB — **Write Hotspot**. Но часто инженеры не понимают, *почему* это происходит. Дело не в месте на диске.

**Физика проблемы (Single Threaded Raft):**
1.  Каждый Регион (96MB) управляется **Raft-группой**.
2.  В Raft запись может делать **только Leader**.
3.  Обработка запросов (propose, replicate, commit) на Лидере — это, по сути, работа **одного потока CPU**.
4.  **Сценарий:** Вы вставляете данные с монотонным ключом (`AUTO_INCREMENT` или `Created_At` индекс).
    *   Все новые ключи попадают в **один** регион (хвостовой).
    *   Этот регион имеет **одного** Лидера на **одном** сервере.
    *   **Результат:** Весь кластер из 100 узлов ждет, пока одно ядро CPU на одном сервере обработает лог Raft.

**Диагностика (TiDB Dashboard):**
*   Откройте **Key Visualizer (Heatmap)**.
*   Если вы видите яркую диагональную линию (Bright Line) — это монотонная запись.
*   Если вы видите яркие точки, которые не двигаются — это статический хотспот (слишком частые апдейты одной строки).

**Лечение:**
1.  **Table Hotspot:** `SHARD_ROW_ID_BITS` (для скрытых ID) или `AUTO_RANDOM` (для PK).
2.  **Index Hotspot:** Это более коварно. Если у вас `PK` случайный (UUID), но есть индекс по `Timestamp`, хотспот переместится в индексный регион. Решение: Партиционирование таблицы по времени или отказ от монотонного индекса.

### 6.2. SingleStore: The "Spill-to-Disk" Cliff

SingleStore — это In-Memory база. Когда ей не хватает памяти, она пытается выжить, но делает это болезненно.

**Физика проблемы (Memory Pressure):**
1.  **High Cardinality Group By/Join:** Запрос `SELECT A, COUNT(*) FROM T GROUP BY A` создает хэш-таблицу в памяти. Если уникальных значений `A` — 100 миллионов, хэш-таблица может занять 50GB RAM.
2.  **OOM Killer:** Если памяти нет, Linux убивает процесс `memsqld`. Узел падает. Кластер переходит в режим восстановления (Recovery), что тормозит всех.
3.  **Spilling (Сброс на диск):** SingleStore умеет сбрасывать данные на диск при нехватке RAM.
    *   **The Cliff:** Память работает со скоростью 50GB/s. NVMe диск — 3GB/s.
    *   Как только запрос начинает "спиллить", его производительность падает в **20-100 раз**.

**Диагностика:**
*   Смотрите метрику `Disk Spilling` в Resource Governor.
*   Следите за `Memory Used by Queries`.

**Лечение:**
1.  **Resource Pools:** Жестко ограничьте память на один запрос (например, `20%`). Лучше убить один запрос ошибкой, чем положить узел.
2.  **Query Rewrite:** Избегайте `DISTINCT` или `GROUP BY` по полям с высокой кардинальностью (UUID, IP) без фильтрации.

### 6.3. Snowflake: The Local Disk Exhaustion (Spilling to S3)

Snowflake продается как "Elastic", но его воркеры имеют фиксированный размер локального SSD.

**Физика проблемы (Local vs Remote Spilling):**
Когда Virtual Warehouse выполняет сортировку (`ORDER BY`) или джойн, он использует память. Когда память кончается, он сбрасывает временные данные на **локальный SSD**.
*   **Stage 1: Local Spilling.** Данные пишутся на NVMe воркера. Это замедление, но терпимое.
*   **Stage 2: Remote Spilling.** Если SSD заполнен (а там всего ~200-400GB на ноду), воркер начинает писать временные данные в **S3**.
    *   *Latency:* Запись на SSD — микросекунды. Запись в S3 — десятки миллисекунд.
    *   **Результат:** Запрос, который работал 1 минуту, начинает работать 2 часа.

**Диагностика:**
*   В Query Profile ищите бары `Bytes Spilled to Local Storage` и (самое страшное) `Bytes Spilled to Remote Storage`.

**Лечение:**
1.  **Scale Up:** Увеличьте размер Warehouse (например, с L до 2XL). Это дает больше памяти и больше места на SSD.
2.  **Filter First:** Убедитесь, что вы фильтруете данные *до* джойна, чтобы уменьшить объем промежуточных результатов.

### 6.4. Distributed Latency Physics (RTT & Locks)

Почему транзакция, которая в PostgreSQL занимает 0.5ms, в TiDB/SingleStore занимает 5ms?

**Физика (Round Trips):**
Распределенная транзакция (2PC) требует общения.
1.  Client -> Gateway (1 hop)
2.  Gateway -> TSO/Metadata (1 hop)
3.  Gateway -> Data Node A (Lock/Prewrite) (1 hop)
4.  Gateway -> Data Node B (Lock/Prewrite) (1 hop)
5.  Gateway -> Data Node A (Commit) (1 hop)
...

**Lock Duration (Время удержания блокировки):**
В локальной БД блокировка держится: `Время_CPU + Время_Диска`.
В распределенной БД блокировка держится: `Время_CPU + Время_Диска + 4 * Network_RTT`.

**Сценарий катастрофы:**
Если сеть "лагает" (скачок пинга с 0.5ms до 10ms), время удержания блокировок вырастает в 20 раз.
*   Очереди на блокировках растут экспоненциально.
*   Активные потоки забиваются.
*   Система встает (Thundering Herd).

**Лечение:**
*   **Network:** 10Gbps+ сеть с низкой латентностью (внутри одной зоны доступности).
*   **Topology:** Никогда не растягивайте OLTP кластер между регионами (US-East и US-West). Физику света не обмануть.

### 6.5. Code Compilation Overhead (JIT)

Специфично для **SingleStore** и **Snowflake**.
Обе системы компилируют SQL в машинный код.

**Физика:**
*   Компиляция занимает CPU и время (100-300ms).
*   Кэш планов (Plan Cache) имеет лимит.

**Анти-паттерн (Literal Spamming):**
```sql
SELECT * FROM users WHERE id = 1;
SELECT * FROM users WHERE id = 2;
SELECT * FROM users WHERE id = 3;
```
Для компилятора это **три разные программы**.
1.  Он тратит CPU на компиляцию каждой.
2.  Он забивает кэш планов уникальными планами.
3.  Когда кэш переполняется, он начинает выбрасывать старые планы.
4.  **Результат:** 50% CPU тратится на компилятор (clang/llvm), а не на выполнение запросов.

**Лечение:**
Используйте **Параметризацию** (Prepared Statements) или включите `auto_parameterization` на уровне БД.
```sql
SELECT * FROM users WHERE id = ?;
```

## 7. Summary Checklist for Solution Architect

Выбор базы данных класса NewSQL/HTAP — это самое дорогое архитектурное решение в проекте. Миграция с PostgreSQL на TiDB или с Oracle на Snowflake занимает годы. Ошибка здесь стоит карьеры.

Используйте этот фреймворк для принятия решений ("Go/No-Go").

### 7.1. The "Physics" Fit: Matching Engine to Workload

Не смотрите на маркетинговые слайды "We do everything". Смотрите на **I/O паттерны**.

#### A. TiDB (The "Infinite MySQL")
*   **Physical DNA:** Distributed Row Store (LSM-Tree) + Paxos/Raft Consensus.
*   **Sweet Spot:**
    *   **Workload:** Massive OLTP (CRUD) с потребностью в транзакциях (ACID) между шардами.
    *   **Scale:** > 5 TB данных, > 50k Write TPS. Тот случай, когда один MySQL уже "трещит", а Vitess слишком сложен в поддержке.
    *   **Latency:** Приемлема задержка **2-10ms** на запись (из-за Raft RTT). Не подходит для HFT (High-Frequency Trading).
*   **Red Flag (Don't use if):**
    *   Вам нужна аналитика как основной кейс (90% OLAP). Row Store будет узким местом.
    *   Вам нужна latency < 1ms (как у Redis/Scylla).
    *   Данных мало (< 1 TB). Оверхед на управление PD/TiKV/TiFlash превысит пользу.

#### B. SingleStore (The "Real-Time" Engine)
*   **Physical DNA:** In-Memory Row Buffer + Disk Columnar Merge. Code Compilation.
*   **Sweet Spot:**
    *   **Workload:** **Ingest & Aggregate**. Поток событий (Clickstream, Logs, IoT), который нужно вставить (Insert) и тут же показать на графике (Select).
    *   **Concurrency:** Высокая конкурентность на чтение сложных дашбордов (благодаря компиляции запросов).
    *   **Latency:** **Microseconds** на запись и чтение (если данные в RAM).
*   **Red Flag (Don't use if):**
    *   Бюджет ограничен. RAM стоит дорого.
    *   Данные — это "Blob" (JSON/Text > 1KB). In-Memory сегменты забьются мгновенно.
    *   Нужна строгая Serializable изоляция между шардами (Distributed ACID здесь дороже, чем в TiDB).

#### C. Snowflake (The "Data Cloud" Platform)
*   **Physical DNA:** Stateless Compute + S3 Object Storage. Micro-partitions (Immutable).
*   **Sweet Spot:**
    *   **Workload:** **Elastic OLAP**. Нагрузка непредсказуема (днем густо, ночью пусто).
    *   **Operations:** "Zero Ops". Нет администраторов баз данных, только Data Engineers.
    *   **Hybrid (Unistore):** Нужен легкий OLTP (справочники, состояние сессий) рядом с петабайтной аналитикой.
*   **Red Flag (Don't use if):**
    *   **High Churn:** Постоянные мелкие `UPDATE/DELETE` отдельных строк. Write Amplification съест бюджет.
    *   **Low Latency App:** Нельзя ставить Snowflake как бэкенд для мобильного приложения (Cold start + Network latency).

### 7.3. The "Production Readiness" Guardrails

Прежде чем идти в прод, проверьте эти пункты. Если хоть один **FAILED** — вы упадете.

**Для TiDB:**
*   [ ] **Hotspot Check:** Используется ли `AUTO_RANDOM` для PK? Есть ли индексы по `Created_At`? (См. раздел 2.4).
*   [ ] **Deployment:** Развернуты ли PD, TiKV и TiDB на разных физических хостах (Anti-affinity)?
*   [ ] **Network:** Latency между узлами < 2ms? (TiDB не работает хорошо через интернет/WAN).

**Для SingleStore:**
*   [ ] **Shard Key:** Проверен ли `SHARD KEY` на data skew? (Нет ли "жирных" ключей, где лежит 50% данных).
*   [ ] **Memory Limits:** Настроены ли Resource Pools, чтобы один `GROUP BY` не убил весь кластер OOM-ом?
*   [ ] **Columnar Conversion:** Хватает ли IOPS диска для фонового слияния (Background Merger) при пиковой записи?

**Для Snowflake:**
*   [ ] **Clustering:** Определены ли `CLUSTER BY` ключи для таблиц > 1TB? Без этого Pruning не работает.
*   [ ] **Resource Monitors:** Установлены ли жесткие лимиты на трату кредитов (Kill Switch), чтобы стажер не сжег $50k за выходные?
*   [ ] **Access Pattern:** Исключены ли одиночные `INSERT/UPDATE`? Переведены ли потоки на `COPY INTO` или `Snowpipe`?

### 7.5. Final Philosophy: The Convergence

HTAP (Hybrid Transactional/Analytical Processing) — это неизбежное будущее. Разделение на "Операционные базы" и "Хранилища данных" было костылем 1990-х годов, вызванным слабостью железа.

Сегодня, когда у нас есть **NVMe SSD** (скорость как у RAM 20 лет назад) и **100Gb Networks**, мы можем хранить данные в одном месте и задавать к ним любые вопросы.
*   **TiDB** делает это через репликацию (Raft).
*   **SingleStore** делает это через унификацию структур (Universal Storage).
*   **Snowflake** делает это через "Hybrid Tables".

Ваша задача как архитектора — выбрать, какой из этих путей конвергенции лучше всего ложится на физику вашей нагрузки и экономику вашей компании.

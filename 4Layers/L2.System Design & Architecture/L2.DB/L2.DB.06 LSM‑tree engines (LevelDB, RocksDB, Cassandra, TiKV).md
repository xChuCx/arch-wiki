**TL;DR**: LSM-деревья — это ответ индустрии на физические ограничения вращающихся дисков и SSD. Они меняют **Random Write** (дорого) на **Sequential Write** (дешево), но переносят стоимость на **CPU** (Compaction) и **Read Latency** (Merge-on-Read).
*   **Главный принцип**: Никогда не менять данные на месте. Всегда дописывать новые версии.
*   **Главная боль**: Write Stalls (остановка записи), когда сброс данных на диск не успевает за потоком вставки.
*   **Сфера**: High-Ingest системы (IoT, Logs), Distributed Databases (TiKV, CockroachDB, Cassandra), Embedded KV (RocksDB).

## 1. Физика LSM (Log-Structured Merge-tree)

Классические БД (B-Tree) сражаются с энтропией: они пытаются поддерживать глобальный порядок на диске в реальном времени (In-place updates).
LSM (Log-Structured Merge-tree) принимает энтропию: мы позволяем данным накапливаться во временных буферах и упорядочиваем их "лениво", в фоне.

**Фундаментальный закон LSM:**
> Мы меняем **Random Disk I/O** (узкое место HDD/SSD) на **CPU & Memory Bandwidth** (сортировка и слияние).

### 1.1. In-Memory Structures: Почему SkipList?

В B-Tree движках (InnoDB) основной структурой в памяти является "грязная страница" B-дерева. В LSM (RocksDB/LevelDB) — это **MemTable**.

*   **Структура:** Почти всегда это **SkipList** (Список с пропусками).
*   **Почему не Red-Black Tree?**
    *   Сбалансированные деревья требуют перебалансировки (Rebalancing) при вставке. Это вызывает блокировки (Lock Contention) и "грязнит" кэш-линии процессора.
    *   **SkipList** — это вероятностная структура. Вставка требует только локальных обновлений указателей (CAS - Compare And Swap). Это позволяет писать **Lock-Free** (или с минимальными блокировками), обеспечивая огромный Write Throughput на многоядерных системах.
*   **Arena Allocation:**
    *   Узлы MemTable не выделяются через системный `malloc`. Они аллоцируются последовательно в большом блоке памяти (**Arena**).
    *   *Цель:* Улучшить локальность кэша (CPU Cache Locality) и избежать фрагментации памяти. Когда MemTable сбрасывается на диск, вся Арена освобождается целиком.

### 1.2. On-Disk Structures: Анатомия SSTable

Когда MemTable сбрасывается на диск (Flush), она превращается в **SSTable (Sorted String Table)**. Это не просто плоский файл. Это сложная иерархическая структура.

**Внутреннее устройство SST файла (RocksDB format):**
1.  **Data Blocks (4KB - 32KB):**
    *   Содержат отсортированные пары Key-Value.
    *   *Prefix Compression:* Ключи `User1`, `User2` хранятся как `User1`, `(len=4, suffix='2')`. Это экономит место, но усложняет бинарный поиск (нужен рестарт-поинт).
2.  **Filter Block (Bloom Filter):**
    *   Вероятностная структура: "Есть ли ключ X в этом файле?".
    *   Ответ: "Точно нет" или "Возможно да".
    *   Позволяет пропустить чтение Data Blocks, если ключа нет.
3.  **Index Block:**
    *   B-Tree подобная структура, отображающая `Key Range -> Data Block Offset`.
    *   Загружается в память при открытии файла.
4.  **Footer:** Ссылки на Index и Filter блоки, Magic Number.

**Immutability (Неизменяемость):**
SSTable никогда не меняется.
*   *Плюс:* Нет блокировок при чтении. Кэширование в OS Page Cache идеально.
*   *Минус:* Нельзя обновить запись. Только записать новую версию в *новый* файл.

### 1.3. The Write Path: "Blind Writes" и Tombstones

Запись в LSM имеет сложность $O(1)$ относительно объема данных на диске (амортизированно).

**Сценарий:** `UPDATE users SET val=2 WHERE id=100`.
1.  **WAL Append:** Запись добавляется в хвост лога (Sequential I/O). Это точка **Durability**.
2.  **MemTable Insert:** Запись добавляется в SkipList ($O(\log N_{memtable})$). Это точка **Visibility**.
3.  **Ack:** Клиент получает подтверждение.

**Сценарий:** `DELETE FROM users WHERE id=100`.
1.  Ничего не удаляется с диска!
2.  В MemTable пишется новая запись: `(Key=100, Type=TOMBSTONE, Time=Now)`.
3.  **Tombstone (Могильный камень):** Это "анти-материя". При чтении, если мы встречаем Tombstone с более свежим Timestamp, чем у данных, мы считаем данные удаленными.

**Expert Insight (Write Stalls):**
LSM быстр, пока MemTables успевают сбрасываться (Flush). Если скорость входящего потока > скорости записи на диск:
1.  Заполняются все слоты MemTable.
2.  Движок **останавливает запись** (Stall), превращая латентность из микросекунд в секунды.

### 1.4. The Read Path: Merge-on-Read & Iterator Heap

Чтение в LSM — это "налог", который мы платим за быструю запись. Мы должны собрать актуальное состояние "на лету".

**Алгоритм Point Lookup `GET(Key)`:**
1.  **MemTable:** Проверяем активную таблицу. (Нашли? Вернули).
2.  **Immutable MemTables:** Проверяем очереди на сброс.
3.  **Level 0 (L0):**
    *   *Особенность:* L0 состоит из файлов, сброшенных прямо из памяти. Ключи в файлах L0 **перекрываются** (Overlapping).
    *   *Следствие:* Нужно проверить **каждый** SSTable файл в L0 (от самого нового к старому). Это дорого!
4.  **Levels L1...LN:**
    *   Здесь файлы **не перекрываются**.
    *   Для каждого уровня делаем бинарный поиск по Index Block, чтобы найти *один* файл-кандидат.
    *   Проверяем Bloom Filter этого файла.
    *   Если "Возможно да" -> читаем Data Block.

**Range Scan (Итераторы):**
Для `SELECT * WHERE id > 100 LIMIT 10` движок создает **Merging Iterator**.
*   Это **Min-Heap (Priority Queue)**, куда складываются итераторы от всех MemTables и всех релевантных SSTables.
*   Движок достает минимальный ключ, сливает версии, выбрасывает скрытые Tombstone-ами данные и отдает результат.
*   *Цена:* CPU usage растет пропорционально количеству файлов SSTables.

### 1.5. L0 vs L1+: Фундаментальная разница

Архитектор должен понимать разницу между "нулевым уровнем" и остальными.

*   **Level 0 (L0):**
    *   Это "свалка" сброшенных MemTables.
    *   **Write Amp = 1** (просто сбросили файл).
    *   **Read Amp = N** (нужно читать все N файлов).
*   **Level 1+ (L1, L2...):**
    *   Это упорядоченные данные (результат Compaction).
    *   **Write Amp = High** (файлы переписывались много раз при слиянии).
    *   **Read Amp = Low** (максимум 1 файл на уровень).

**Compaction** — это процесс перемещения данных из "дешевого для записи" состояния (L0) в "эффективное для чтения" состояние (L1+).

## 2. Compaction Strategies (Сердце LSM)

LSM-дерево работает быстро только до тех пор, пока оно упорядочено. Энтропия (хаос) накапливается в виде перекрывающихся SSTables и Tombstones.
**Compaction (Компакция/Уплотнение)** — это фоновый процесс `Merge Sort`, который восстанавливает порядок, жертвуя CPU и I/O диска (Write Amp) ради скорости чтения (Read Amp) и освобождения места (Space Amp).

### 2.1. Leveled Compaction (LCS): Оптимизация чтения
Это дефолтная стратегия RocksDB/LevelDB (и CockroachDB/TiKV).
**Философия:** "Платим при записи, чтобы читать быстро". Минимизируем количество файлов, в которые нужно заглянуть при чтении.

*   **Структура Уровней (The Shape):**
    *   **L0:** "Свалка" (Tiered). Ключи в файлах перекрываются.
    *   **L1...LN:** Каждый уровень строго **отсортирован**. Ключи в файлах внутри уровня **не перекрываются**.
    *   **Fan-out (Growth Factor):** Каждый следующий уровень в 10 раз больше предыдущего. (L1=256MB -> L2=2.5GB -> L3=25GB).

*   **Механика Слияния (The Merge):**
    1.  *Trigger:* Уровень L1 заполнен. Мы выбираем **один** файл из L1.
    2.  *Overlap:* Мы находим **все** файлы в L2, диапазоны ключей которых пересекаются с этим файлом из L1. (Обычно это ~10 файлов).
    3.  *Merge:* Читаем 1 файл из L1 + 10 файлов из L2, сортируем, удаляем мусор.
    4.  *Write:* Пишем новые файлы в L2. Старые удаляем.

*   **Expert Analysis (Trade-offs):**
    *   **Read Amp (Низкий):** Кроме L0, нам нужно проверить всего 1 файл на уровень (так как они не перекрываются, мы используем бинарный поиск по метаданным уровней). Итого ~7 проверок.
    *   **Space Amp (Низкий ~1.1x):** Мусор живет недолго. Старые версии удаляются при первом же касании компактором.
    *   **Write Amp (Высокий ~10-30x):** Это главная боль. Чтобы "протолкнуть" данные с L1 на L2, мы переписываем данные уровня L2 (которые мы не меняли!) снова и снова. Одна и та же строка может быть перезаписана 30 раз за свою жизнь. Это убивает ресурс SSD.

### 2.2. Tiered / Universal Compaction (STCS): Оптимизация записи
Используется в Cassandra (Size-Tiered), ScyllaDB, HBase и RocksDB (Universal style).
**Философия:** "Пишем быстро, разберемся потом". Откладываем слияние до последнего.

*   **Структура (Sorted Runs):**
    *   Нет строгих "уровней" с неперекрывающимися файлами.
    *   Есть **Sorted Runs** (Серии). Серия — это результат одного сброса MemTable или компакции.
    *   Файлы в одном "Тире" (Tier) **перекрываются** по ключам.

*   **Механика Слияния:**
    1.  Мы ждем, пока накопится **N** файлов (Runs) примерно одинакового размера (например, 4 файла).
    2.  Мы сливаем их **все вместе** в один большой файл следующего размера.
    3.  Мы **никогда** не сливаем 1 файл с N файлами следующего уровня (как в Leveled). Мы сливаем только файлы одного ранга.

*   **Expert Analysis (Trade-offs):**
    *   **Write Amp (Низкий ~3-5x):** Данные переписываются редко. Идеально для тяжелых логов (Write-Intensive).
    *   **Read Amp (Высокий):** Чтобы найти ключ, нужно проверить **каждый** Run (Run 1, Run 2... Run N). Если у вас 50 SSTables, вам нужно сделать 50 проверок (спасают только Bloom Filters, которые должны быть огромными).
    *   **Space Amp (Катастрофический ~2x):** "Проблема временного места". Чтобы слить 4 файла по 10GB в один файл 40GB, вам нужно временно иметь 80GB места на диске (40 входных + 40 выходной). В Leveled компакции мы сливаем мелкими кусками, там такой проблемы нет.

### 2.3. RUM Conjecture (Теорема о хранении)
На уровне архитектора вы должны знать формальное ограничение, предложенное исследователями из Harvard/Facebook.
Оптимизировать можно только **два** параметра из трех:
1.  **R**ead Overhead.
2.  **U**pdate (Write) Overhead.
3.  **M**emory (Space) Overhead.

| Структура | Read | Update (Write) | Memory (Space) | Итог |
| :--- | :--- | :--- | :--- | :--- |
| **B-Tree** | ✅ Good | ❌ **Bad** (Random) | ✅ Good | Стандарт для OLTP. |
| **LSM (Leveled)** | ✅ Good | ⚠️ Medium/Bad (High WA) | ✅ Good (Low SA) | RocksDB Default. Баланс. |
| **LSM (Tiered)** | ❌ **Bad** | ✅ Good (Low WA) | ❌ **Bad** (High SA) | Cassandra/Logs. Максимальная запись. |

### 2.4. Динамическая подстройка (Dynamic Leveling)
Современные движки (CockroachDB Pebble, RocksDB newer versions) используют адаптивные стратегии.
*   **L0 -> L1 Bottleneck:** L0 — это единственное место, где файлы перекрываются в Leveled стратегии. Если L0 растет, чтение деградирует мгновенно.
*   **Intra-L0 Compaction:** Движок может решить слить файлы *внутри* L0, не проталкивая их в L1, чтобы уменьшить количество файлов, но не платить цену за слияние с гигантским L1.
*   **Dynamic Resizing:** Если последний уровень (L6) пуст, движок может динамически считать L5 последним, меняя множители размеров, чтобы уменьшить Write Amp.

## 3. Реализации в дикой природе

### 3.1. RocksDB (The Storage Kernel)

RocksDB (форк Google LevelDB от Facebook/Meta) — это стандарт де-факто для построения современных Storage Engines. Он используется внутри **MyRocks (MySQL)**, **TiKV**, **CockroachDB** (через порт Pebble), **Kafka Streams** и **Flink**.

Понимание RocksDB — это понимание того, как работают все эти системы "под капотом".

#### A. Column Families (CF): Архитектурная изоляция
Самая мощная и часто недопонимаемая концепция RocksDB.
Column Family — это **изолированное LSM-дерево** внутри одной физической базы данных.

*   **Физика:**
    *   У каждого CF **своя** MemTable.
    *   У каждого CF **свои** SSTables (L0...LN).
    *   У каждого CF **своя** конфигурация (размер блоков, сжатие, фильтры Блума).
    *   **НО!** У всех CF **ОБЩИЙ WAL (Write-Ahead Log)**.

*   **Зачем это нужно (Atomicity):**
    Это позволяет делать атомарные записи в разные "таблицы".
    *   *Пример:* Вы пишете Данные в `Data_CF` и Индекс в `Index_CF`.
    *   RocksDB упаковывает это в один `WriteBatch`.
    *   `WriteBatch` пишется в общий WAL одной последовательной записью.
    *   Если питание пропадает — либо восстановится и Данное, и Индекс, либо ничего. Это база для построения SQL-движков поверх KV.

*   **Проблема "Заложника WAL" (Expert Trap):**
    *   Представьте `CF_A` (огромный поток записи) и `CF_B` (одна запись в час).
    *   `CF_A` постоянно сбрасывает (Flush) свои MemTable в SST. Он готов удалить старые сегменты WAL.
    *   Но `CF_B` все еще держит данные в своей MemTable, которая ссылается на *самый старый* сегмент WAL.
    *   **Результат:** RocksDB **не может удалить старые WAL файлы**, пока `CF_B` не сбросится. Диск переполняется логами.
    *   *Тюнинг:* `max_total_wal_size` — форсирует сброс "ленивых" CF, чтобы освободить WAL.

#### B. Pluggable Architecture (Конструктор)
RocksDB позволяет заменить практически любой компонент. Архитектор должен знать, что выбирать.

1.  **MemTable Rep (Представление в памяти):**
    *   **SkipList (Default):** Сбалансирован для чтения/записи. Поддерживает конкурентную вставку.
    *   **Vector:** Для Bulk Load (загрузки данных). Огромная скорость записи, но *нет чтения* до сброса на диск.
    *   **HashSkipList:** Для Prefix-Lookups. Хэш-таблица указывает на SkipList. Ускоряет поиск, но усложняет сканирование.

2.  **Table Format (Формат на диске):**
    *   **BlockBasedTable (Default):** Стандарт. Данные разбиты на блоки (4KB-32KB). Идеально для SSD/HDD.
    *   **PlainTable:** Оптимизировано для **RamFS / PMEM** (Persistent Memory). Нет блоков, нет Block Cache. Адресация через mmap. Нулевое копирование, но требует, чтобы вся база влезала в память.

#### C. Bloom Filters & Prefix Seek
В SQL мы часто делаем запросы `WHERE user_id = X`. В KV-хранилище ключи могут выглядеть как `UserID:Timestamp`.
Как эффективно найти все записи для `UserID`?

*   **Prefix Bloom Filter:** Обычный фильтр Блума хеширует весь ключ. RocksDB умеет хешировать только *префикс* (фиксированной длины или через `SliceTransform`).
*   **Механика:** При вызове `Iterator::Seek("UserID")` RocksDB проверяет префиксный фильтр каждого SST файла. Если фильтр говорит "нет", файл пропускается целиком. Это критически важно для производительности MyRocks и TiKV.

#### D. The Manifest (MetaData Log)
Как RocksDB узнает, какие SST файлы составляют текущую базу данных после рестарта?
*   **MANIFEST:** Это специальный системный лог.
*   Любое изменение структуры LSM (Flush, Compaction) записывается в Manifest как **VersionEdit** ("Добавлен файл X, удален файл Y").
*   **VersionSet:** В памяти RocksDB держит текущую "Версию" (набор активных файлов).
*   *Инцидент:* Если диск поврежден и файл MANIFEST утерян, данные в SST файлах целы, но RocksDB не знает, в каком порядке их читать. Существуют утилиты (`ldb`), чтобы попытаться восстановить Manifest, но это "хирургия".

**Пример для наглядности (SQL on RocksDB):**
Вы создаете таблицу `users (id INT PK, email VARCHAR, INDEX(email))`.

1.  Движок (MyRocks) создает 3 Column Families: `System`, `Default` (для данных), `Index` (для вторичных индексов).
2.  `INSERT INTO users (1, 'me@test.com')`:
    *   В `WriteBatch` добавляется:
        *   `Put(Default_CF, Key="1", Val="me@test.com")`
        *   `Put(Index_CF, Key="me@test.com", Val="1")`
3.  RocksDB пишет Batch в общий WAL.
4.  Обновляет MemTable `Default_CF` и MemTable `Index_CF`.
5.  Пользователь получает `OK`.

### 3.2. Cassandra / ScyllaDB (The Wide Column Store)

Если RocksDB — это локальная библиотека, то Cassandra/Scylla — это распределенная система, где LSM используется для обеспечения экстремальной скорости записи в условиях Eventual Consistency.

#### A. Data Model to LSM Mapping (Физическая раскладка)
Многие архитекторы путаются, пытаясь натянуть реляционный опыт на "Wide Column" модель.
Внутри SSTable данные хранятся как плоский Key-Value, но ключ составной.

*   **Primary Key = ((Partition Key), Clustering Key)**.
    *   **Partition Key (PK):** Определяет, на какой физической ноде (и в каком шарде CPU в случае Scylla) будут лежать данные. Это единица дистрибуции.
    *   **Clustering Key (CK):** Определяет порядок сортировки *внутри* SSTable на этой ноде.

*   **Пример:** `CREATE TABLE readings (sensor_id int, time timestamp, value double, PRIMARY KEY (sensor_id, time))`.
    *   `sensor_id` — Partition Key.
    *   `time` — Clustering Key.
*   **Физическое хранение в LSM:**
    В SSTable это запишется (упрощенно) как серия ячеек:
    `RowKey: Sensor1`
      `Column: 12:00:01:value -> 25.5`
      `Column: 12:00:02:value -> 25.6`
      `...`

*   **The Wide Partition Problem:**
    Если у вас один `sensor_id` (Partition) имеет 100 миллионов записей (временных меток), это создает **одну гигантскую строку** на диске.
    *   В LSM это приводит к тому, что при чтении (особенно если есть range delete или update) движок должен просканировать гигабайты данных в памяти, чтобы собрать "строку".
    *   *Expert Rule:* Партиция не должна превышать 100MB (мягкий лимит) или 1GB (жесткий лимит). Иначе Compaction и Repair захлебнутся.

#### B. Compaction Strategies (STCS vs TWCS)
В отличие от RocksDB, который по умолчанию использует Leveled Compaction (LCS), Cassandra исторически заточена под другие стратегии.

1.  **Size-Tiered Compaction Strategy (STCS):** *Дефолт для Cassandra.*
    *   **Логика:** Сливаем 4 файла по 100MB в один файл 400MB. Потом 4 по 400MB в 1.6GB.
    *   **Плюс:** Экстремально низкий **Write Amplification**. Идеально для Insert-Heavy.
    *   **Минус:** Огромный **Space Amplification** (до 50% диска нужно держать свободным для слияния двух огромных файлов). Высокий **Read Amp** (при чтении нужно проверять много больших файлов).

2.  **Time-Window Compaction Strategy (TWCS):** *Стандарт для IoT/Time-Series.*
    *   **Логика:** Создает SSTables, сгруппированные по временным окнам (например, 1 файл = 1 час).
    *   **Фишка:** Старые окна **никогда** не компактятся повторно.
    *   **Плюс:** Идеальная производительность для Time-Series данных с TTL. Старые данные удаляются путем удаления целого файла (Drop SSTable), без дорогого по-строчного GC.

#### C. Distributed Deletes: Zombies & Doomstones
Удаление в распределенной системе — это самая сложная операция.

*   **Проблема:** Нода A упала. Нода B удалила запись (вставила Tombstone). Нода A поднялась. У Ноды A есть данные, у Ноды B — Tombstone. Кто прав?
*   **Решение:** Tombstone должен жить долго (`gc_grace_seconds`, по умолчанию 10 дней), чтобы успеть реплицироваться на восставшую ноду A во время Repair.
*   **Zombie Data:** Если Нода A лежала 11 дней, а потом поднялась, её данные "воскреснут", так как Tombstone на Ноде B уже удален сборщиком мусора.
*   **Tombstone Overwhelming (Doomstones):**
    *   Сценарий: Вы удалили миллион записей в партиции.
    *   Запрос: `SELECT * ... LIMIT 1`.
    *   LSM-движок начинает сканировать SSTable. Он видит Tombstone -> пропускает. Видит Tombstone -> пропускает.
    *   После 100,000 пропусков Cassandra прерывает запрос с ошибкой: **"Tombstone Overwhelming Exception"**. Это защита от выжигания CPU и Disk I/O на чтении пустоты.

#### D. ScyllaDB Specifics: Shard-per-Core Architecture
ScyllaDB — это переписанная на C++ Cassandra, но её архитектурное отличие глубже, чем просто язык.

*   **Thread-per-Core (Seastar Framework):**
    *   В Cassandra (JVM) потоки конкурируют за ресурсы ОС.
    *   В ScyllaDB каждый CPU Core — это отдельный "шард". Память, сетевой стек и **LSM-дерево** жестко привязаны к ядру.
*   **Lock-Free:** Внутри ядра нет мьютексов. LSM-дерево ядра 0 никогда не трогает память ядра 1. Коммуникация между ядрами — только через асинхронные сообщения.
*   **I/O Scheduler:** Scylla имеет свой планировщик I/O в userspace. Она знает, что "сейчас идет тяжелый Compaction", и автоматически тротлит его, чтобы отдать приоритет "User Reads". В Cassandra на JVM это вечная боль настройки `compaction_throughput_mb_per_sec`.

### Резюме раздела:

1.  **LSM в Cassandra** — это инструмент реализации **Partitioned Row Store**.
2.  **Wide Partition** — это архитектурная ошибка, которая превращает быстрый LSM Lookup в медленный Sequential Scan.
3.  **TWCS** — единственно верная стратегия для Time-Series данных с TTL.
4.  **Tombstones** — это не просто маркеры удаления, это данные, которые нагружают систему при чтении. "Удалять данные дороже, чем хранить" — это про Cassandra.

### 3.3. TiKV (Distributed Transactional KV): Spanner Architecture

TiKV — это распределенное Key-Value хранилище, которое служит слоем хранения для TiDB (SQL Layer), но может использоваться и самостоятельно. Его архитектура построена на четком разделении слоев: **Raft** (консенсус), **RocksDB** (локальное хранение) и **Percolator** (распределенные транзакции).

#### A. The Region: Единица масштабирования
В отличие от Cassandra (vnodes + consistent hashing), TiKV использует **Range-based Partitioning**.
*   Весь диапазон ключей делится на **Регионы (Regions)**.
*   Регион — это непрерывный диапазон ключей `[StartKey, EndKey)`.
*   Дефолтный размер: 96MB.
*   **Динамика:**
    *   **Split:** Если регион вырастает до 144MB, он делится на два.
    *   **Merge:** Если регион пустеет, он сливается с соседом.
    *   **PD (Placement Driver):** Центральный мозг ("Oracle"), который следит за нагрузкой и приказывает нодам перемещать регионы (Leader Transfer / Peer Move) для балансировки Hotspots.

**Expert Insight:** Range-based подход позволяет делать эффективные `SCAN` (Range Queries), чего лишена Cassandra. Но он создает риск **Write Hotspot** (если вы пишете монотонно возрастающие ключи, вся запись летит в один регион).

#### B. Dual RocksDB Architecture (Изоляция I/O)
На каждой физической ноде TiKV запущены **два** экземпляра RocksDB. Это не избыточность, это разделение паттернов I/O.

1.  **Raft Engine (raft-db):**
    *   Хранит **Raft Log** (журнал консенсуса).
    *   Паттерн: *Sequential Write* (Append), быстрое удаление старых логов после применения.
    *   Тюнинг: Минимум сжатия, агрессивное удаление файлов.
2.  **KV Engine (kv-db):**
    *   Хранит **сами данные** (State Machine).
    *   Паттерн: *Random Write* (из-за Percolator), сложные чтения.
    *   Тюнинг: Сильное сжатие, фильтры Блума, разделение на Column Families.

**Зачем два?** Чтобы Flush/Compaction больших данных (KV) не вызывал тормозов (Stall) при записи Raft-лога. Если Raft тормозит, кластер теряет кворум.

#### C. MVCC & Column Families Mapping
TiKV реализует MVCC *поверх* RocksDB, используя специфическую схему кодирования ключей и **3 Column Families (CF)** внутри `kv-db`.

**Физический ключ в RocksDB:**
TiKV добавляет Timestamp (версию) в конец ключа, чтобы версии лежали рядом.
Кодировка: `z{Key}{Desc_Timestamp}` (убывающий TS, чтобы `Seek` находил свежую версию первой).

**Роли Column Families:**
1.  **CF_DEFAULT:** Хранит "жирные" данные (значения).
    *   *Key:* `{Key}{Start_TS}` -> *Value:* `UserPayload`.
2.  **CF_LOCK:** Хранит блокировки (Intents) и незавершенные транзакции.
    *   Самый маленький CF, всегда кэшируется в памяти.
    *   Если здесь есть запись, значит, ключ заблокирован другой транзакцией.
3.  **CF_WRITE:** Хранит метаданные коммита (MVCC Pointer).
    *   *Key:* `{Key}{Commit_TS}` -> *Value:* `Type (Put/Delete) + Start_TS`.

**Алгоритм чтения (Point Get):**
1.  Читаем `CF_LOCK`. Есть лок? -> Ждем или Resolve (см. ниже).
2.  Читаем `CF_WRITE` с `Commit_TS <= My_Snapshot_TS`. Находим запись о том, что "версия от Start_TS=100 закоммичена".
3.  Читаем `CF_DEFAULT` с ключом `{Key}{100}` -> Получаем данные.

#### D. Distributed Transactions: Percolator (Optimistic 2PC)
TiKV использует протокол, вдохновленный Google Percolator. Это **Two-Phase Commit** без центрального координатора транзакций (координатором выступает клиент/TiDB драйвер).

1.  **Prewrite Phase (Фаза 1):**
    *   Клиент выбирает один ключ как **Primary Key** (не путать с PK таблицы, это "якорь" транзакции).
    *   Остальные ключи — **Secondary Keys**.
    *   Клиент пишет данные в `CF_LOCK` + `CF_DEFAULT`.
    *   В `CF_LOCK` вторичных ключей ставится ссылка на Primary Key.

2.  **Commit Phase (Фаза 2):**
    *   **Point of No Return:** Клиент коммитит **Primary Key** (переносит запись из `CF_LOCK` в `CF_WRITE` с текущим Timestamp).
    *   Как только Primary закоммичен — транзакция успешна.
    *   **Async Commit:** Вторичные ключи коммитятся асинхронно.

**Crash Recovery (Lazy Commit):**
Если клиент упал после коммита Primary, но до коммита Secondary:
*   Следующий читатель натыкается на лок на Secondary ключе.
*   Он идет по ссылке к Primary ключу.
*   Видит, что Primary закоммичен.
*   **Roll Forward:** Читатель сам "докатывает" (коммитит) Secondary ключ и читает данные.
*   Это позволяет системе не зависать при падении клиентов.

#### Итоговый пример для наглядности:
`UPDATE money SET val=10 WHERE id=1` (StartTS=100, CommitTS=110).

1.  **RocksDB (Prewrite):**
    *   `CF_DEFAULT`: `z_money_1_100` -> `10`
    *   `CF_LOCK`: `z_money_1` -> `Lock(Primary, StartTS=100)`
2.  **RocksDB (Commit):**
    *   `CF_WRITE`: `z_money_1_110` -> `Put(StartTS=100)`
    *   `CF_LOCK`: `z_money_1` -> (deleted)

## 4. Troubleshooting & Tuning: Survival Guide

В мире LSM "тормоза" имеют дискретную природу. Система работает идеально, а через секунду латентность прыгает с 1ms до 5 секунд. Это **Stall** (Затор).
Ваша задача — диагностировать, в каком именно звене пайплайна образовалась пробка.

### 4.1. Write Stalls: Анатомия Затора

Write Stall — это механизм самозащиты (Backpressure). Если бы его не было, база упала бы с OOM (Out Of Memory). Движок намеренно блокирует или замедляет писателей (`PUT`), чтобы дать фоновым процессам (Flush/Compaction) разгрести завалы.

**Два типа заторов (RocksDB semantics):**

**A. MemTable Stall (Память забита)**
*   **Симптом:** Запись встала, CPU на ноде низкий, диск простаивает (I/O util low).
*   **Физика:** Все активные MemTables (Mutable + Immutable) заполнены. Потоки Flush не успевают сбрасывать их на диск.
*   **Причина:**
    1.  Медленный диск (Sequential Write bottleneck).
    2.  Слишком интенсивная запись (Ingest spike).
    3.  Один поток Flush не справляется (в RocksDB сброс однопоточный по умолчанию для одного Column Family).
*   **Лечение:**
    *   Увеличить количество MemTables (`max_write_buffer_number`). Дает буфер на случай всплесков.
    *   Увеличить размер одной MemTable (`write_buffer_size`). Сбросы будут реже, но крупнее (лучше для HDD/SATA SSD).

**B. L0 Stall (Диск забит метаданными)**
*   **Симптом:** Запись замедлилась (Slowdown) или встала. Диск утилизирован на 100% (чтением и записью одновременно). CPU высокий.
*   **Физика:** MemTable сбрасываются слишком быстро. На уровне L0 скопилось слишком много файлов (например, > 20).
*   **Почему это опасно:** Файлы на L0 перекрываются. Чтобы прочитать ключ, нужно проверить *все* 20 файлов. Read Latency деградирует. Движок останавливает запись, чтобы спасти чтение.
*   **Лечение:**
    *   Увеличить `level0_file_num_compaction_trigger` (оттянуть начало компакции).
    *   Увеличить `max_background_jobs` (добавить воркеров для компакции).
    *   **Внимание:** Если диск уже в полке (100% util), добавление воркеров только ухудшит ситуацию. Нужен более быстрый диск или сжатие посильнее (trade CPU for Disk IO).

### 4.2. Read Latency: Где мы теряем время?

Если чтение медленное, нужно понять, *как* оно медленное.

1.  **CPU-Bound Read (Decompression & Hashing):**
    *   *Симптом:* `top` показывает 100% User CPU. I/O низкий.
    *   *Причина:* Мы постоянно распаковываем блоки данных (Block Cache слишком мал или выключен) или проверяем Bloom Filters.
    *   *Тюнинг:*
        *   Включить `cache_index_and_filter_blocks = true`. (Держать метаданные в блочном кэше, а не в куче ОС).
        *   Использовать более легкий алгоритм сжатия на L0-L1 (LZ4/Snappy) и сильный на Lmax (Zstd).

2.  **I/O-Bound Read (Seeking):**
    *   *Симптом:* `iostat` показывает высокий `await` на чтение.
    *   *Причина:* Bloom Filter пробит (False Positive) или отсутствует. Мы делаем лишние чтения с диска.
    *   *Тюнинг:*
        *   Увеличить битность Bloom Filter (например, 10 бит на ключ дают 1% false positive).
        *   **Partitioned Index/Filters:** Если SST файл огромный, его индекс/фильтр не влезает в кэш. Разбиение индекса позволяет грузить его кусками.

3.  **Compaction Interference:**
    *   *Симптом:* Чтение тормозит только во время компакции.
    *   *Физика:* Компакция — это "I/O Storm". Она забивает очередь диска и вымывает полезные данные из Page Cache ОС.
    *   *Тюнинг:* Использовать `rate_limiter_bytes_per_sec` для фоновых процессов (ScyllaDB делает это автоматически, RocksDB требует настройки).

### 4.3. Tombstone Issues: Проклятие удалений

LSM ненавидит удаления.

**Сценарий:** `DELETE FROM events WHERE ts < '2023-01-01'`.
Вы вставили миллионы Tombstones.
*   **Point Lookup:** Быстрый. Bloom Filter скажет "файла нет" или мы найдем Tombstone в L0 и остановимся.
*   **Range Scan (`SELECT * ...`):** Катастрофа. Итератор должен прочитать *все* удаленные ключи, слить их с Tombstones, понять, что они удалены, и отфильтровать.
*   **Пример:** Вы запрашиваете 10 строк (`LIMIT 10`). Движок читает 1,000,000 строк с диска, понимает, что все они мертвы, и продолжает искать.

**Решение (Compaction Filter):**
В RocksDB/TiKV можно настроить специальную логику: если Tombstone старше определенного времени или файл содержит *только* удаленные данные в диапазоне, форсированно удалить этот файл, не дожидаясь естественной компакции. В Cassandra это `unchecked_tombstone_compaction`.

### 4.4. Memory Management: OOM Killer

LSM движки жадны до памяти. Память делится на 3 кучи:
1.  **MemTable (Write Buffer):** Активные буферы.
2.  **Block Cache (Read Cache):** Кэш разжатых блоков данных.
3.  **Indexes & Bloom Filters:** Метаданные SST таблиц.

**Expert Trap (Pinned Memory):**
В RocksDB индексы и фильтры могут потреблять гигабайты памяти, если база большая. Эти структуры **Pinned** (невыгружаемые), если не настроить иначе.
*   *Сценарий:* Вы выделили 30GB под Block Cache. Но Индексы+Фильтры заняли 20GB *сверх* этого. Пришел OOM Killer.
*   *Решение:* Жестко лимитировать общее потребление памяти. В RocksDB использовать `WriteBufferManager`, который считает MemTables как часть общего Cache Budget.

### 4.5. Hardware Tuning: NVMe & Filesystem

1.  **Disable Swap:** Для LSM (особенно Java-based Cassandra) своп — это смерть. Latency подскакивает до секунд.
2.  **Filesystem:** XFS. EXT4 может тормозить на удалении огромных файлов (unlink stall).
3.  **DISCARD/TRIM:** При удалении SSTables файловая система должна сообщать SSD, что блоки свободны. Иначе Write Amplification на уровне контроллера SSD (Garbage Collection самого диска) убьет производительность. Добавьте `discard` в mount options.

### Summary Checklist for Troubleshooting

1.  **Check Stalls:** `rocksdb.stall.micros` > 0? Где затор: MemTable или L0?
2.  **Check Compaction Lag:** Растет ли `estimated_pending_compaction_bytes`? Если да, диск не вывозит запись.
3.  **Check Tombstones:** Если `scan_bytes` >> `returned_bytes`, у вас проблема с удаленными данными.
4.  **Check Block Cache:** `block_cache_hit` < 90%? Увеличьте кэш или включите Bloom Filters.

## 5. Summary Checklist for Solution Architect

Используйте этот раздел для валидации архитектурных решений (Design Review) и аудита существующих систем.

### 5.1. Architectural Selection Matrix (Выбор инструмента)

Не выбирайте LSM только ради скорости записи. Выбирайте его, понимая, чем вы заплатите.

| Критерий | LSM-Tree (RocksDB / Cassandra / TiKV) | B-Tree (Postgres / MySQL) | Expert Commentary |
| :--- | :--- | :--- | :--- |
| **Write Pattern** | **Ingest-Heavy**. Потоковая вставка, логи, IoT, Time-Series. | **Update-Heavy**. Частые обновления одних и тех же строк. | LSM превращает Random Write в Sequential. Если у вас 100% Random Writes (UUIDs) — LSM спасет ваш диск. |
| **Read Pattern** | **Point Lookup**. Ключ известен. | **Complex Queries**. Joins, Range Scans, Aggregations. | LSM плох для Range Scans (особенно с удалениями). Для сложной аналитики (OLAP) поверх LSM нужен колоночный формат (как в ClickHouse). |
| **Latency Requirement** | **Soft Real-time**. Допустим Jitter (всплески) на p99 из-за компакции. | **Hard Real-time**. Стабильная, предсказуемая латентность. | B-Tree дает стабильный Read Latency. LSM дает *средний* Latency лучше, но хвосты (p99) хуже из-за фоновой работы. |
| **Dataset Size** | **>> RAM**. Данные больше памяти в 10-100 раз. | **<= RAM**. Горячие данные влезают в Buffer Pool. | LSM эффективнее сжимает данные (нет фрагментации страниц, лучше compression ratio). Это экономит $$$ на SSD. |
| **Delete Pattern** | **TTL / Bulk Delete**. Удаление целыми диапазонами или по времени. | **Random Delete**. Удаление отдельных строк. | В LSM удаление по TTL бесплатно (Drop SSTable). Рандомное удаление — это вставка Tombstone (дорого при чтении). |

### 5.2. Production Readiness Checklist (Перед запуском)

Если вы запускаете LSM в прод, проверьте эти пункты. Отсутствие любого из них — гарантия инцидента.

#### A. Hardware & OS
*   [ ] **NVMe SSD Only:** Использование HDD для SSTables (кроме холодных уровней) — это антипаттерн. Компакция генерирует много чтения.
*   [ ] **No Swap:** `vm.swappiness = 0` (или 1). Если процесс компакции уйдет в своп, весь кластер встанет.
*   [ ] **XFS Filesystem:** EXT4 может давать фризы при удалении больших файлов SSTables.

#### B. Compaction Strategy Selection
*   [ ] **Leveled (LCS):** Для систем, где важно **быстрое чтение** и экономия места (RocksDB default, CockroachDB). Готовьтесь к высокому Write Amp (покупайте Server-Grade SSD с высоким DWPD).
*   [ ] **Tiered (STCS/Universal):** Для систем с **бешеной записью** (Cassandra logs). Готовьтесь к Space Amp 200% (нужен запас места x2).
*   [ ] **Time-Window (TWCS):** Только для Time-Series с TTL.

#### C. Memory & Caching
*   [ ] **Block Cache Size:** Выделили память? (Обычно 30-50% RAM).
*   [ ] **High-Priority Cache:** Включили `cache_index_and_filter_blocks = true`? Метаданные (Индексы и Фильтры Блума) должны быть в памяти всегда. Если они вымываются — каждый Point Lookup будет стоить 1 IOPS.
*   [ ] **Bloom Filters:** Включены ли они? (10 бит на ключ = 1% false positive). Без них Read Amp будет равен количеству файлов на L0.

#### D. Observability (Red Flags)
Настройте алерты на эти метрики. Они предсказывают смерть базы.
*   [ ] **Write Stalls:** `rocksdb.stall.micros > 0`. База искусственно тормозит запись.
*   [ ] **L0 File Count:** Если > 20, компакция захлебнулась. Чтение деградирует.
*   [ ] **Pending Compaction Bytes:** Растет ли очередь на компакцию?
*   [ ] **Tombstones per Read:** Если вы читаете 1000 томбстоунов ради 1 живой строки — нужна перестройка данных.

### 5.3. Expert Self-Check: War Games

Реальные сценарии, на которых сыпятся кандидаты.

**Scenario 1: The "Phantom" Disk Usage**
**Ситуация:** Вы используете Cassandra (Tiered Compaction). Размер данных 500GB. Диск 1TB.
Внезапно диск заполняется на 100%, база падает. Вы не добавляли данных.
**Вопрос:** Что произошло?
<details>
<summary><b>Ответ (нажмите для просмотра)</b></summary>
<b>Compaction Space Amplification.</b> При Tiered Compaction движок может решить слить 4 файла по 125GB в один файл 500GB. Во время этого процесса на диске одновременно существуют старые файлы (500GB) и создается новый (растет до 500GB). Итого нужно 1TB + запас. Вам не хватило места для временного файла слияния.
</details>

**Scenario 2: The "Expensive" Non-Existent Key**
**Ситуация:** RocksDB. Вы делаете `GET(Key)`, которого точно нет в базе. Это занимает больше времени и ресурсов CPU, чем чтение существующего ключа.
**Вопрос:** Почему чтение "пустоты" такое дорогое?
<details>
<summary><b>Ответ</b></summary>
Если <b>Bloom Filter</b> настроен плохо (или отключен на последнем уровне), движок обязан проверить <b>каждый</b> уровень SSTables.
Для существующего ключа поиск останавливается, как только он найден (например, на L1).
Для несуществующего ключа движок обязан провалиться до самого дна (L6), декомпрессируя блоки и проверяя их, чтобы убедиться, что ключа действительно нет. Это "худший случай" для LSM.
</details>

**Scenario 3: The "Updates are fast, Scans are slow"**
**Ситуация:** Вы часто обновляете поле `counter` (`UPDATE table SET val=...`). Запись летит мгновенно.
Но запрос `SELECT SUM(val) FROM table` работает в 10 раз медленнее, чем в аналогичной таблице B-Tree.
**Вопрос:** В чем проблема структуры данных?
<details>
<summary><b>Ответ</b></summary>
<b>Space Amplification & Merge-on-Read.</b> В LSM обновление — это новая запись. Старая запись никуда не делась (пока не пройдет компакция).
При сканировании (`SUM`) итератор должен прочитать <b>все версии</b> каждой строки из разных файлов SSTables, слить их в Priority Queue (Heap), отбросить старые версии и выдать результат.
В B-Tree обновление делается in-place, поэтому при сканировании вы читаете только актуальные данные, без оверхеда на слияние версий.
</details>

**Scenario 4: The Recovery Time**
**Ситуация:** Сервер RocksDB упал по питанию. При рестарте он восстанавливается 5 минут, блокируя запросы. WAL файл был 2GB.
**Вопрос:** Как уменьшить время восстановления (RTO), не теряя данных?
<details>
<summary><b>Ответ</b></summary>
Проблема в <b>Replaying WAL</b>. Чтобы восстановить MemTable, нужно прочитать 2GB лога и вставить в SkipList.
<i>Решение:</i> Уменьшить размер MemTable (и соответственно WAL). Сделать MemTable по 64MB. Тогда при падении нужно будет восстановить максимум 64MB (или несколько Immutable MemTables), что займет секунды. Цена — более частые сбросы (Flushes) и нагрузка на L0 компакцию.
</details>

### 5.4. The Golden Rules of LSM Physics

1.  **Sequential Write is King:** Используйте это. LSM идеален для логов.
2.  **Reads pay the Tax:** Чтение всегда сложнее записи. Используйте кэширование и фильтры Блума агрессивно.
3.  **Compaction is the Heartbeat:** Если компакция остановилась — база мертва (просто она еще не знает об этом, пока диск не заполнится). Мониторьте компакцию как пульс пациента.

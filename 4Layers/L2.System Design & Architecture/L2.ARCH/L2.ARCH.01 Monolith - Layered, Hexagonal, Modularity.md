**TL;DR**: Монолит — это **единица развертывания**, а не характеристика качества кода. Современный архитектурный стандарт для старта проектов и большинства Enterprise-систем — **Modular Monolith (Modulith)** с использованием гексагональной архитектуры внутри модулей. Главная задача эксперта — управление **coupling** (связностью) через строгие границы (Boundaries) внутри единого артефакта, используя статический анализ и инверсию зависимостей.

## 1. Анатомия архитектурных стилей монолита: От Слоев к Модулям

На уровне эксперта вы должны понимать архитектуру не как статичную картинку из прямоугольников, а как **набор ограничений (constraints)**, накладываемых на поток управления (Control Flow) и поток зависимостей (Dependency Flow).

### 1.1. Классическая слоистая архитектура (Layered Architecture)

Также известна как **N-Tier** (хотя N-Tier чаще подразумевает физическое разделение серверов, а Layered — логическую структуру кода). Это стиль **горизонтальной нарезки (Horizontal Slicing)**, где код группируется по технической роли, а не по бизнес-функции.

#### 1.1.1. Анатомия и Поток Управления (Control Flow)

Стандартный стандарт де-факто для Enterprise-систем 2000-2015 годов. Структура выглядит так:

1.  **Presentation Layer** (Web/UI/Controllers) — Отвечает за парсинг JSON, валидацию входных данных, HTTP-коды.
2.  **Business / Service Layer** — Гнездо логики. Здесь живут `UserManager`, `OrderService`.
3.  **Persistence / Data Access Layer (DAL)** — ORM, DAO, Репозитории. Знает SQL.
4.  **Database Layer** — Физическая схема данных.

**Ключевая характеристика**: В слоистой архитектуре **поток управления (вызовы методов)** и **поток зависимостей (импорты в коде)** направлены в одну сторону — **сверху вниз**.

> **Top-Down Dependency Rule**: Слой $N$ зависит только от слоев $N-1$. Слой $Persistence$ ничего не знает о $Business$.

#### 1.1.2. Вариации реализации (Expert Nuance)

Как архитектор, вы должны различать два режима работы слоев:

*   **Strict Layering (Закрытые слои)**: Слой может вызывать *только* непосредственно нижележащий слой.
    *   *Плюс*: Изоляция. Замена DAL не влияет на Controller.
    *   *Минус*: "Proxy-hell". Чтобы пробросить данные из БД в UI, нужно создать метод-дублер в Сервисе, который просто вызывает метод DAO.
*   **Relaxed Layering (Открытые слои)**: Слой может вызывать *любой* нижележащий слой. Например, Controller может вызвать Repository напрямую для операции чтения (Read-only), минуя Service.
    *   *Плюс*: Меньше бойлерплейта, выше производительность (меньше стековых вызовов).
    *   *Минус*: Хаос зависимостей. Бизнес-правила начинают утекать в контроллеры.

#### 1.1.3. Патологии слоистой архитектуры (Deep Dive)

На собеседованиях Senior/Staff уровня ожидается, что вы назовете не только плюсы (простота старта), но и фундаментальные проблемы этого подхода в крупных системах.

**А. Database Driven Design (Проектирование от схемы)**
Поскольку `Persistence` находится внизу цепочки, он становится фундаментом.
*   *Сценарий*: Вы меняете тип колонки в БД или денормализуете таблицу для скорости.
*   *Последствие*: Изменяется ORM-сущность -> Ломается Service (который её использует) -> Ломается Controller (который ждет DTO из сервиса).
*   *Вывод*: Вся система жестко связана (High Coupling) со структурой хранения данных. **Это нарушение инкапсуляции на архитектурном уровне.**

**Б. Anemic Domain Model (Анемичная модель)**
Слоистая архитектура структурно поощряет разделение данных и поведения — антипаттерн в ООП.
*   **Entities (Сущности)**: Превращаются в "мешки с данными" (Data Bags) — классы только с `@Column` и геттерами/сеттерами. Никакой логики.
*   **Services (Сервисы)**: Становятся "Божественными классами" (God Classes). Процедурный код ("Транзакционный скрипт"), который берет данные из сущности, меняет их и кладет обратно.
*   *Почему это плохо*: Инварианты (правила валидности объекта) размазаны по сервисам. Нельзя быть уверенным, что объект `Order` находится в валидном состоянии, просто получив ссылку на него.

**В. Architecture Sinkhole (Архитектурная воронка)**
Ситуация, когда запросы просто пролетают сквозь слои без полезной работы.
*   *Пример*: Контроллер вызывает сервис `getById`, сервис вызывает репозиторий `findById`, репозиторий делает `SELECT`.
*   *Проблема*: Вы платите сложностью поддержки слоев, но получаете 0% бизнес-ценности (только CRUD). В микросервисах это часто сигнал, что сервис слишком мелок или архитектура избыточна.

**Г. Транзитивные зависимости и Тестирование**
Если `Service` зависит от `Repository`, а `Repository` зависит от `Hibernate`, то `Service` транзитивно зависит от `Hibernate`.
*   *Последствие*: Нельзя протестировать бизнес-логику без моков (Mocking) базы данных или поднятия TestContainers. Unit-тесты становятся сложными и хрупкими.

#### 1.1.4. Пример кода: Проблема зависимостей

Рассмотрим типичный код. Обратите внимание на `import`.

```java
package com.app.business;

// ОШИБКА АРХИТЕКТУРЫ: Бизнес-слой знает о деталях реализации БД!
import com.app.persistence.SqlOrderRepository; 
import com.app.persistence.entities.OrderEntity; // JPA сущность протекла в бизнес

public class OrderService {
    private final SqlOrderRepository repo;

    public void processOrder(Long id) {
        // Мы зависим от JPA-сущности. Если мы захотим перейти на Mongo или NoSQL,
        // придется переписывать ВЕСЬ бизнес-сервис.
        OrderEntity entity = repo.findById(id); 
        
        if (entity.getStatus() == "NEW") { // Бизнес-логика над структурой БД
             entity.setStatus("PAID");
             repo.save(entity);
        }
    }
}
```

В правильной (Гексагональной) архитектуре `OrderService` зависел бы от интерфейса `OrderRepository` (который лежит в том же пакете `business`), и работал бы с чистым доменом `Order` (POJO), а не `OrderEntity` (JPA).

#### 1.1.5. Организационный аспект (Закон Конвея)

Слоистая архитектура провоцирует создание функциональных команд:
*   Команда фронтенда (UI Layer)
*   Команда бэкенда (Service Layer)
*   Команда DBA (Database Layer)

**Staff-level Insight**: Чтобы добавить одну фичу (например, "Скидочный купон"), нужно согласовать работу трех команд. Это резко снижает **Time-to-Market**. Современные архитектуры (Modulith, Microservices) стремятся к Cross-functional teams, сгруппированным вокруг бизнес-фичи (Vertical Slicing), что противоречит горизонтальной природе слоев.

#### 1.1.6. Вердикт: Когда использовать?

Не стоит демонизировать слои. Это инструмент.

*   **Использовать, когда**:
    *   Простая CRUD-система.
    *   Прототип / MVP со сроком жизни < 6 месяцев.
    *   Команда джуниоров (низкий порог входа, много примеров в сети).
*   **Избегать, когда**:
    *   Сложная предметная область (много правил, состояний).
    *   Долгоживущий проект (Enterprise), требующий сменяемости технологий (например, переезд с Oracle на Postgres).
    *   Требуется высокая скорость доставки фич (Lead Time).

### 1.2. Гексагональная архитектура (Ports & Adapters)
*Синонимы: Hexagonal Architecture, Ports & Adapters pattern.*

Этот стиль, предложенный Алистером Кокберном (Alistair Cockburn), решает фундаментальную проблему энтропии ПО: **утечку деталей реализации в бизнес-логику**. Это стандарт де-факто для построения долгоживущих Enterprise-систем и микросервисов со сложной логикой.

#### 1.2.1. Философия и Концепция
В отличие от слоистой архитектуры (где есть "верх" и "низ"), Гексагональная архитектура рассматривает приложение как **Ядро (Core)**, окруженное интерфейсами.
*   **Агностицизм**: Приложение не знает, кто его вызывает (человек через UI, автотест или Kafka-консьюмер).
*   **Изоляция**: Приложение не знает, куда оно сохраняет данные (в PostgreSQL, в файл или в память).
*   **Симметрия**: Взаимодействие с базой данных (Driven side) архитектурно равнозначно взаимодействию с GUI (Driving side). И то, и другое — внешние детали.

#### 1.2.2. Анатомия: Порты, Адаптеры и Принцип DIP

Ключевой механизм — **Dependency Inversion Principle (DIP)**. Все зависимости указывают **строго внутрь** круга. Ядро никогда не импортирует классы из внешних слоев.

##### A. The Hexagon (Application Core)
Это "Святая святых". Здесь живет бизнес-ценность.
1.  **Domain Entities**: Объекты бизнеса, обладающие состоянием и поведением (не просто DTO!). Не зависят ни от чего.
2.  **Use Cases (Interactors / Application Services)**: Оркестраторы. Они реализуют сценарий (например, "Оформить заказ"), управляя сущностями.

##### B. Ports (Контракты / Границы)
Порты — это интерфейсы, определенные *внутри* гексагона. Это условия, которые ставит Домен внешнему миру.

*   **Primary (Driving) Ports / Inbound Ports**:
    *   *Определение*: Интерфейс, который предоставляет Домен для управления собой.
    *   *Аналогия*: Пульт управления телевизором.
    *   *Пример*: `IOrderService`, `CancelOrderUseCase`.
*   **Secondary (Driven) Ports / Outbound Ports**:
    *   *Определение*: Интерфейс, который нужен Домену, чтобы выполнить работу (сохранить состояние, отправить уведомление).
    *   *Аналогия*: Розетка, в которую телевизор включает вилку. Телевизору все равно, атомная это энергия или ветряная, главное — 220В.
    *   *Пример*: `IOrderRepository`, `IPaymentGateway`, `INotificationService`.

##### C. Adapters (Реализация / Клей)
Адаптеры живут *снаружи* гексагона. Они конвертируют данные из формата внешнего мира в формат портов и обратно.

*   **Driving Adapters (Входящие)**:
    *   Инициируют работу. Конвертируют HTTP запрос, CLI команду или событие таймера в вызов *Primary Port*.
    *   *Примеры*: `OrderController` (REST), `OrderGrpcService`, `OrderKafkaListener`, `CucumberTestHarness`.
*   **Driven Adapters (Исходящие)**:
    *   Реализуют *Secondary Port*. Конвертируют вызов метода интерфейса в SQL запрос, HTTP вызов внешнего API или запись в файл.
    *   *Примеры*: `PostgresOrderRepository` (implements `IOrderRepository`), `SmtpEmailSender`.

#### 1.2.3. Углубленные паттерны реализации

На уровне Staff Engineer возникают вопросы, которые не описаны в базовых туториалах.

**1. Стратегия маппинга (Mapping Strategy)**
Как передавать данные через границу порта? Это главный холивар архитекторов.

*   **Стратегия "Full Mapping" (Двусторонний маппинг)**:
    *   Адаптер (Controller) имеет свои DTO (`WebOrderRequest`).
    *   Он маппит их в DTO порта (`CreateOrderCommand`).
    *   Домен возвращает результат, который снова маппится в `WebOrderResponse`.
    *   Внутри репозитория: Доменная сущность `Order` маппится в `OrderDbEntity` (Hibernate Entity).
    *   *Плюсы*: Полная развязка. Изменение JSON API или схемы БД не трогает Домен.
    *   *Минусы*: Много бойлерплейта (мапперы).
    *   *Вердикт*: Обязательно для сложных долгоживущих систем.

**2. Тестируемость как архитектурное свойство**
Гексагональная архитектура позволяет проводить **Subcutaneous Tests (Подкожные тесты)**.
Вы можете протестировать 100% бизнес-логики без поднятия Spring Context, Docker-контейнеров или реальной базы.
*   *Как*: Тест выступает как *Driving Adapter*, а вместо *Driven Adapters* используются легкие Fake-реализации (In-Memory HashMap вместо Postgres).
*   *Результат*: Тысячи тестов проходят за секунды.

**3. Организация кода (Package by Component)**
Не делите код на `controllers`, `services`, `repositories`. Делите по функциональным зонам.
```text
com.company.app.order/
├── domain/                 # THE HEXAGON
│   ├── model/              # Entities (Order, OrderLine)
│   ├── ports/              # Interfaces
│   │   ├── incoming/       # Primary Ports (Use Cases)
│   │   └── outgoing/       # Secondary Ports (Repository interfaces)
│   └── usecase/            # Implementation of incoming ports
├── infrastructure/         # ADAPTERS
│   ├── persistence/        # Implementation of outgoing ports (JPA, SQL)
│   └── web/                # Driving adapters (REST Controllers)
└── config/                 # Wiring (Dependency Injection configuration)
```

#### 1.2.4. Пример для наглядности (Flow Trace)

Проследим поток управления для операции "Создать пользователя". Обратите внимание на инверсию зависимостей в шаге 3.

1.  **HTTP Request** (Внешний мир) прилетает в `UserController` (**Driving Adapter**).
2.  `UserController` конвертирует JSON в `CreateUserCommand` (DTO) и вызывает интерфейс `CreateUserUseCase` (**Primary Port**).
3.  Реализация `CreateUserService` (внутри **Hexagon**) выполняет бизнес-правила:
    *   Проверяет email.
    *   Создает объект `User` (**Entity**).
4.  `CreateUserService` хочет сохранить пользователя. Он вызывает интерфейс `UserRepository` (**Secondary Port**).
    *   *Важно*: Сервис не знает про SQL. Он просто говорит "Сохрани".
5.  В runtime (во время выполнения) через Dependency Injection подставлен класс `PostgresUserRepository` (**Driven Adapter**).
6.  `PostgresUserRepository` берет доменного `User`, превращает его в `UserJpaEntity` и делает `INSERT` в базу.

#### 1.2.5. Onion & Clean Architecture: Детализация Ядра

**Суть**: Это эволюционные улучшения Гексагональной архитектуры, направленные на борьбу с превращением "Ядра" в "Большой Ком Грязи" (Big Ball of Mud) за счет введения строгих слоев **внутри** бизнес-логики.

Общий закон для обоих стилей (The Dependency Rule): **Зависимости в исходном коде могут указывать только внутрь, в сторону высокоуровневых политик.**

#### А. Onion Architecture (Луковая архитектура)
*Автор: Jeffrey Palermo (2008)*

Луковая архитектура решает проблему **Анемичной модели**, жестко предписывая, где живет логика. Она делит "Ядро" на слои:

1.  **Domain Model (Центр)**:
    *   Только Entities и Value Objects.
    *   Чистое состояние и поведение *одной* сущности.
    *   Никаких зависимостей от внешнего мира.
2.  **Domain Services**:
    *   Бизнес-логика, затрагивающая *несколько* сущностей.
    *   Интерфейсы репозиториев (`IOrderRepository`) определяются здесь.
    *   *Пример*: `ExchangeRateCalculator` (нужно взять две валюты и посчитать).
3.  **Application Services**:
    *   **Оркестрация**. Этот слой *не содержит* бизнес-правил.
    *   Он загружает данные из БД (через интерфейс репозитория), вызывает метод Доменной Модели или Доменного Сервиса, и сохраняет результат.
    *   Аналог "Primary Port Implementation" в Гексагональной.
4.  **Infrastructure (Внешний слой)**:
    *   UI, Тесты, Реализация БД.

**Expert Nuance**: В Onion критически важно отличие **Domain Service** от **Application Service**.
*   *Application Service*: "Возьми транзакцию, отправь письмо." (Координация).
*   *Domain Service*: "Если сумма транзакций > 1000, примени VIP-скидку." (Бизнес-правило).

#### Б. Clean Architecture (Чистая архитектура)
*Автор: Robert C. Martin (Uncle Bob) (2012)*

Это стандартизация терминологии. Дядя Боб объединил идеи Onion и Hexagonal, добавив акцент на **Use Cases** и **Interface Adapters**.

**Слои (Кольца):**

1.  **Entities (Enterprise Business Rules)**:
    *   Бизнес-объекты, содержащие самые общие и высокоуровневые правила. Они должны пережить смену приложения.
2.  **Use Cases (Application Business Rules)**:
    *   Специфичные для конкретного приложения сценарии.
    *   *Пример*: `CreateOrderUseCase`. Он дирижирует потоком данных к Entities и обратно.
    *   Именно Use Case управляет "танцем" данных, но не знает, *откуда* данные пришли (Web или CLI) и *куда* уйдут (SQL или Mongo).
3.  **Interface Adapters (Критически важный слой)**:
    *   Слой **конвертации**. Его единственная цель — преобразовать данные из формата, удобного для Use Cases и Entities, в формат, удобный для внешних агентов (DB, Web).
    *   Здесь живут `Presenters`, `Controllers`, `Gateways` (реализации интерфейсов).
    *   *Expert Insight*: MVC паттерн целиком живет в этом слое (и во внешнем). Контроллер — это Адаптер.
4.  **Frameworks & Drivers**:
    *   Клей-код: DB Drivers, UI Frameworks, HTTP Listeners.

#### В. Flow of Control vs. Dependency Direction (Ключевой паттерн)

Это то, что отличает Senior от Staff — понимание инверсии на уровне потока исполнения.

Представим сохранение данных:
1.  **Flow of Control (Поток управления)**:
    `Controller` (Adapter) -> вызывает -> `UseCase` (App Logic) -> вызывает -> `RepositoryImpl` (Infra).
    *Поток идет: Снаружи -> Внутрь -> Опять Снаружи.*

2.  **Dependency Direction (Зависимости)**:
    `Controller` -> зависит от -> `UseCase`.
    `RepositoryImpl` -> зависит от -> `Repository Interface` (который лежит внутри UseCase/Domain слоя).
    *Зависимости идут: Снаружи -> Внутрь <- Снаружи.*

В точке вызова БД мы используем **полиморфизм**, чтобы развернуть стрелку зависимости против потока управления.

#### Г. Пересечение границ (Crossing Boundaries)

Главная сложность Clean/Onion архитектуры — передача данных между слоями.

**Expert Rule: No Shared Entities across boundaries.**
Нельзя передавать Hibernate Entity (`@Entity`) в UI. Нельзя принимать JSON-объект в Use Case.

1.  **Request Model**: Контроллер упаковывает `HttpServletRequest` в простой POJO `CreateOrderCommand` (или DTO).
2.  **Input Boundary**: Use Case принимает `CreateOrderCommand`.
3.  **Response Model**: Use Case возвращает `OrderResult` (DTO), а не саму доменную сущность `Order`.
4.  **Presenter**: Превращает `OrderResult` в `OrderViewModel` (для отображения в HTML/JSON).

**Зачем эта боль? (Why pay the mapping tax?)**
Чтобы изменения в UI (нам нужно новое поле в JSON) не требовали перекомпиляции бизнес-логики. И чтобы изменения в БД (переименовали колонку) не ломали JSON API. Это называется **Decoupling**.

#### Д. Пример структуры (Clean + Onion Flavor)

```text
/src
  /Domain (Enterprise Business Rules) [No dependencies]
    User.java (Entity, logic only)
    EmailAddress.java (Value Object)
    UserRegistered.event

  /Application (Use Cases) [Depends on Domain]
    /Ports
      IUserRepository.java (Secondary Port Interface)
      IEmailSender.java    (Secondary Port Interface)
    RegisterUserUseCase.java (Primary Port Impl)
    RegisterUserCommand.dto

  /Adapter (Interface Adapters) [Depends on Application]
    /Persistence
      SqlUserRepository.java (Implements IUserRepository)
      UserJpaEntity.java (DB mapping)
    /Web
      UserController.java
      UserViewModel.java

  /Infrastructure (Frameworks) [Depends on Adapter]
    AppConfig.java (Spring/DI setup)
    Main.java
```

### Резюме раздела 1.2.5

*   **Onion** уточняет, что интерфейсы репозиториев должны лежать в слое **Domain/Application**, а не в отдельном слое "Common".
*   **Clean Architecture** формализует понятие **Interface Adapters** как слоя, ответственного за "грязную работу" по перекладыванию байтов.
*   Главная цель обоих подходов — **Screaming Architecture**: глядя на структуру папок, вы должны видеть *намерения системы* (Orders, Users, Payments), а не *инструменты* (Controllers, Models, Views).

**Резюме для эксперта**: Гексагональная архитектура — это цена, которую мы платим (в виде маппинга и количества классов) за возможность отложить принятие технических решений и изолировать сложность бизнеса от сложности инфраструктуры.

### 1.3. Модульный Монолит (Modular Monolith / Modulith)

**Определение**: Архитектурный стиль, при котором система развертывается как **единый артефакт** (Single Deployment Unit — WAR, JAR, DLL, Binary), но на уровне исходного кода спроектирована как набор строго изолированных, независимых вертикальных срезов (**Modules**), взаимодействующих через четко определенные публичные контракты.

Это **НЕ** просто "хорошая структура папок". Это имитация физического разделения микросервисов, но с нулевой сетевой задержкой (Zero Latency).

#### 1.3.1. Анатомия Модуля (Module Anatomy)

На уровне эксперта модуль — это не пакет, а **Bounded Context** (Ограниченный Контекст из DDD). Он должен быть самодостаточным.

**Структура модуля (Canonical Layout):**
Каждый модуль должен иметь структуру, скрывающую детали реализации.

```text
/src
  /Ordering (Module Name)
    /Api          <-- ПУБЛИЧНАЯ ЧАСТЬ (Public API)
       IOrderingService.interface  (Входящий порт)
       OrderCreated.event          (Исходящее событие)
       OrderDto.class              (DTO для обмена данными)
    /Internal     <-- ПРИВАТНАЯ ЧАСТЬ (Implementation Details)
       /Domain    (Entities, Value Objects, Domain Services)
       /App       (Use Cases, Command Handlers)
       /Infra     (Repositories, DB Adapters, 3rd Party Clients)
       OrderingService.class (Реализация интерфейса)
```

*   **Правило инкапсуляции**: Код из модуля `Billing` имеет право видеть *только* содержимое пакета `/Ordering/Api`. Любая попытка импортировать класс из `/Ordering/Internal` должна приводить к ошибке компиляции или падению CI-пайплайна.

#### 1.3.2. Стратегия изоляции данных (Data Sovereignty) — Критический аспект

Самая частая причина провала модульных монолитов — **Shared Database Pattern**. Если модули разделены в коде, но лезут в таблицы друг друга — это не Modulith, это распределенный спагетти-код.

**Требования уровня Expert:**

1.  **Логическое разделение схем (Schema-per-Module)**:
    Даже если физически БД одна (например, PostgreSQL instance), каждый модуль владеет своей схемой: `ordering_schema`, `billing_schema`.
    *   *Constraint*: Пользователь БД модуля `Billing` имеет `GRANT SELECT/INSERT/UPDATE` только на `billing_schema`.
2.  **Запрет на JOIN между модулями**:
    Категорически запрещено делать `JOIN ordering.orders ON billing.invoices.order_id`.
    *   *Решение*: Если Биллингу нужны данные Заказа, он должен запросить их через `Ordering API` (в памяти) или хранить их копию (Data Duplication).
3.  **Отсутствие Foreign Keys (FK) между модулями**:
    FK создают жесткую связность (Hard Coupling) и блокировки. Ссылочная целостность между модулями поддерживается на уровне приложения (Eventual Consistency), а не на уровне движка БД.

#### 1.3.3. Паттерны межмодульной коммуникации

Внутри процесса у нас есть два пути, и выбор определяет характеристики системы:

**А. Синхронный вызов (Direct Method Call)**
*   *Как*: `billingService.processPayment(orderId)` вызывает метод интерфейса напрямую.
*   *Плюсы*: Простота, строгая типизация, единая транзакция (ACID).
*   *Минусы*: Сильная связность (Temporal Coupling). Если Биллинг упал (выбросил Exception), Заказ не создастся.
*   *Expert Note*: Используйте для операций "чтения" или когда атомарность критична.

**Б. Асинхронный вызов (In-Memory Event Bus)**
*   *Как*: `Ordering` публикует `OrderCreatedEvent`. `Billing` (подписчик) ловит его и запускает логику.
*   *Инструменты*: Spring ApplicationEvents, MediatR (.NET), Guava EventBus.
*   *Плюсы*: Слабая связность. Биллинг может сломаться, но Заказ сохранится (если обработка события в отдельной транзакции).
*   *Expert Note*: Это точка расширения. Сегодня это вызов в памяти. Завтра, при переезде на микросервисы, вы просто подмените `EventBus` на `KafkaProducer`, не меняя бизнес-логику модулей.

![[A_visualization_of_202512222114.jpeg]]
#### 1.3.4. Управление транзакциями (Transactional Boundaries)

Это то, что отличает Senior от Staff.

1.  **Strong Consistency (ACID) Default**: В Modulith по умолчанию вызов метода другого модуля происходит в *той же* транзакции БД (Propagation.REQUIRED).
    *   *Риск*: Длинные транзакции. Если модуль А вызывает Б, а Б лезет во внешний API, вся БД блокируется.
2.  **Eventual Consistency (Saga-lite)**:
    *   Используйте **Transactional Outbox Pattern** даже внутри монолита. Сохраняйте событие в БД в той же транзакции, что и изменение состояния, а обрабатывайте его асинхронно (в другом потоке/транзакции). Это позволяет модулям быть действительно независимыми по отказу (Fault Isolation).

#### 1.3.5. Архитектурный надзор (Architecture as Code)

Надежда на дисциплину разработчиков — это не стратегия. Границы должны защищаться автотестами (Fitness Functions).

**Пример (Java / ArchUnit):**
```java
@AnalyzeClasses(packages = "com.myapp.modules")
public class ModularityRules {

    @ArchTest
    static final ArchRule modules_should_respect_boundaries =
        slices().matching("com.myapp.modules.(*)..")
        .should().beFreeOfCycles()
        .andShould().notDependOnEachOther(); // В идеале. На практике разрешаем зависимости только от API пакетов
}
```

#### 1.3.6. Пример эволюции: Extracting a Microservice

Почему Modulith называют "Microservices stepping stone"?
Представьте, что модуль `Reporting` начал потреблять слишком много памяти при генерации PDF.

1.  **В Modulith**:
    *   У `Reporting` уже есть свой API (интерфейс `IReportGenerator`).
    *   У него свои таблицы в БД (нет JOIN-ов, которые надо разрывать).
    *   У него нет зависимостей от внутренностей других модулей.
2.  **Действие**:
    *   Выносим код `Reporting` в отдельный сервис.
    *   В монолите создаем реализацию `GrpcReportGenerator implements IReportGenerator`.
    *   Остальной код монолита **не меняется**.

### Резюме для эксперта

Модульный монолит — это архитектура с **высокой внутренней связностью (High Cohesion)** внутри модулей и **низкой зацепленностью (Low Coupling)** между ними, реализуемая через:
1.  **Сокрытие реализации** (Internal vs Public API).
2.  **Изоляцию данных** (Schema per module).
3.  **Событийную модель** (In-Memory Integration Events).
4.  **Статический анализ** (ArchUnit/NetArchTest).

Это лучший выбор (Default Choice) для большинства стартующих проектов (Greenfield) и единственно верный путь рефакторинга легаси (Brownfield) перед распилом на микросервисы.

### 1.4. The Ultimate Combination: Modulith + Hexagonal

Это "Золотой стандарт" 2025 года для построения сложных Enterprise-систем, которые планируют жить долго.

**Суть паттерна**: Весь монолит состоит из набора модулей. **Каждый отдельный модуль** внутри себя устроен как изолированное Гексагональное приложение.

#### 1.4.1. Концептуальная модель: "Гексагон в Гексагоне"

На уровне Expert [E] вы должны визуализировать это так:
1.  **Макро-уровень (System)**: Система — это контейнер для модулей. Инфраструктура (Web Server, DB Connection Pool) является общей "оболочкой".
2.  **Микро-уровень (Module)**:
    *   У каждого модуля есть свое **Ядро (Domain + Use Cases)**.
    *   У каждого модуля свои **Порты**.
    *   У каждого модуля свои **Адаптеры**.

Самое важное открытие для архитектора: **Другой модуль — это тоже "Внешний Мир"**.
Для модуля `Orders` нет разницы, откуда пришел ответ — от PayPal (внешний сервис) или от модуля `Inventory` (соседняя папка). Оба они находятся в зоне **Infrastructure**.

#### 1.4.2. Детальная анатомия взаимодействия (The Interaction Flow)

Рассмотрим сценарий: *При создании Заказа нужно проверить наличие товара на Складе.*

В "плохом" монолите `OrderService` просто вызывает `InventoryService`.
В **Modulith + Hexagonal** поток выглядит так:

1.  **Order Domain (Inside Hexagon)**:
    *   Бизнес-логика хочет проверить сток. Она вызывает *Интерфейс* (Secondary Port): `StockCheckerPort.hasStock(sku, quantity)`.
    *   Домен `Orders` **не знает** о существовании модуля `Inventory`. Он знает только свой интерфейс.

2.  **Order Infrastructure (Outside Hexagon)**:
    *   Здесь лежит класс-адаптер: `InventoryModuleAdapter implements StockCheckerPort`.
    *   Этот адаптер — единственное место в модуле `Orders`, которое "видит" публичный API модуля `Inventory`.

3.  **Cross-Module Call (The Boundary)**:
    *   Адаптер вызывает `InventoryApi.checkItem(sku)`.

4.  **Inventory Module**:
    *   Запрос попадает в Primary Port модуля `Inventory` и обрабатывается его доменом.

**Зачем такая сложность? (Expert Justification)**
Это реализует паттерн **ACL (Anti-Corruption Layer)** по умолчанию. Если модуль `Inventory` изменит свой API, сломается только `InventoryModuleAdapter` в инфраструктуре `Orders`. Доменная логика `Orders` останется нетронутой.

#### 1.4.3. Структура проекта (Reference Folder Structure)

В этой архитектуре структура папок — это чертеж системы.

```text
/src
  /Modules
    /Ordering              <-- BOUNDED CONTEXT
      /Api                 <-- PUBLIC CONTRACT (Виден другим модулям)
         OrderingFacade.java
         OrderCreatedEvent.java
         OrderDto.java
      /Core                <-- THE HEXAGON (Скрыто, internal)
         /Domain           <-- PURE BUSINESS LOGIC (No Frameworks)
            Order.java
            OrderPolicy.java
         /Application      <-- USE CASES (Ports)
            CreateOrderUseCase.java (Primary Port Impl)
            StockCheckerPort.java   (Secondary Port Interface)
      /Infrastructure      <-- ADAPTERS (Скрыто, internal)
         /Web              <-- DRIVING ADAPTER
            OrderController.java
         /Persistence      <-- DRIVEN ADAPTER (DB)
            PostgresOrderRepo.java
         /Integrations     <-- DRIVEN ADAPTER (Module-to-Module)
            InventoryModuleAdapter.java (Implements StockCheckerPort)

    /Inventory             <-- ANOTHER BOUNDED CONTEXT
       /Api
       /Core
       /Infrastructure
```

#### 1.4.4. Проблема маппинга (Mapping Overhead)

Цена за такую чистоту — маппинг данных. Как эксперт, вы должны принять это осознанно.

В цепочке `Web Request -> Order Module -> Inventory Module` данные трансформируются минимум 4 раза:
1.  `Web JSON` -> `Order Command` (в контроллере `Orders`).
2.  `Order Entity` -> `StockCheckerPort params` (в домене `Orders`).
3.  `StockCheckerPort params` -> `Inventory API DTO` (в адаптере `Orders`).
4.  `Inventory API DTO` -> `Inventory Command/Entity` (на входе в `Inventory`).

**Expert Rule**: Не пытайтесь использовать общие DTO (Shared Kernel) для сокращения маппинга. **DRY (Don't Repeat Yourself) не работает между микросервисами и модулями.** Дублирование кода (DTO) лучше, чем связность (Coupling).

#### 1.4.5. Тестирование в парадигме Modulith + Hexagonal

Эта связка дает уникальную пирамиду тестирования:

1.  **Domain Unit Tests**: Тестируем `/Core/Domain` и `/Core/Application`. Чистый Java/C#, никаких моков БД, никаких Spring Context. Скорость: миллисекунды.
2.  **Module Integration Tests (Isolated)**: Поднимаем контекст *только одного модуля*.
    *   БД: In-memory (H2) или Testcontainers (изолированная схема).
    *   Соседние модули: Мокаем их Public API бины.
    *   Проверяем: Работает ли Порт + Адаптер + БД.
3.  **System E2E Tests**: Поднимаем все модули вместе. Проверяем бизнес-процессы целиком.

#### 1.4.6. Пример кода: Адаптер к чужому модулю

```java
package com.myapp.modules.ordering.infra.integrations;

import com.myapp.modules.ordering.core.ports.StockCheckerPort; // Порт внутри Order Hexagon
import com.myapp.modules.inventory.api.InventoryFacade;      // Public API чужого модуля
import com.myapp.modules.inventory.api.dto.CheckStockRequest;

import org.springframework.stereotype.Component;

/**
 * Этот класс живет в Infrastructure слое модуля Ordering.
 * Это ЕДИНСТВЕННОЕ место, где Ordering знает про Inventory.
 */
@Component
class InventoryModuleAdapter implements StockCheckerPort {

    private final InventoryFacade inventoryFacade;

    // Spring инжектит бин из соседнего модуля
    InventoryModuleAdapter(InventoryFacade inventoryFacade) {
        this.inventoryFacade = inventoryFacade;
    }

    @Override
    public boolean hasStock(String sku, int quantity) {
        // Mapping: Domain params -> External Module DTO
        var request = new CheckStockRequest(sku, quantity);
        
        // Call External Module
        var response = inventoryFacade.checkStock(request);
        
        // Mapping: External Module Response -> Domain boolean
        return response.isAvailable();
    }
}
```

### Резюме раздела 1.4

**Modulith + Hexagonal** — это архитектура максимальной защиты инвестиций.
*   **Hexagonal** защищает бизнес-логику от устаревания фреймворков и баз данных.
*   **Modulith** защищает систему от превращения в монолитный ад, позволяя распиливать или рефакторить части независимо.

Это выбор Expert-уровня, так как он требует высокой дисциплины и понимания, почему мы пишем "лишний" код (адаптеры/мапперы) ради долгосрочной гибкости.

## 2. Deep Dive: Обеспечение модульности (Enforcing Modularity)

Модульность не возникает сама по себе. Это результат борьбы с естественным стремлением кода к связности (coupling). Ваша задача — создать **Architectural Firewall**, который сделает написание "плохого" кода более сложным, чем написание "хорошего".

### 2.1. Изоляция данных (Data Sovereignty & Governance)

Самый сложный аспект. Код разделить легко, данные — больно.

**Принцип:** Модуль владеет своими данными безраздельно. Никто, кроме владельца, не имеет права читать или писать в его таблицы.

#### А. Логическое vs Физическое разделение
*   **Уровень A/P**: Разные таблицы в одной схеме `public`.
*   **Уровень Expert**: **Schema-per-Module**.
    *   В PostgreSQL: `CREATE SCHEMA billing;`, `CREATE SCHEMA catalog;`.
    *   Конфигурация ORM (Hibernate/EF Core): Отдельные `SessionFactory` или контексты для каждого модуля. Это гарантирует, что вы *физически* не сможете создать Entity, ссылающуюся на таблицу другого модуля.

#### Б. Проблема чтений (The Read-Model Challenge)
Если модуль `Orders` хранит `user_id`, но для UI нужно отобразить `user_name` и `user_email`, как быть без JOIN?

**Решения уровня Expert (от простого к сложному):**

1.  **Sync Data Composition (API Composition)**:
    *   `OrderController` вызывает `OrderingService` (получает список заказов) и `UserService` (получает map пользователей).
    *   *Склеивание* происходит в памяти на уровне API Gateway или контроллера.
    *   *Trade-off*: N+1 проблема, Latency.
2.  **Data Duplication (Denormalization)**:
    *   В таблице `orders` храним не только `user_id`, но и snapshot данных на момент заказа: `user_full_name`, `user_email`.
    *   *Trade-off*: Данные исторические (что часто и нужно для заказов), но не актуальные.
3.  **Local Read Model (CQRS Lite)**:
    *   Модуль `Orders` подписывается на событие `UserUpdated`.
    *   Модуль `Orders` обновляет свою локальную таблицу-реплику `ordering.users_cache`.
    *   *Trade-off*: Eventual Consistency, сложность синхронизации.

#### В. Запрет Foreign Keys
Вы **не можете** создать FK constraint между `ordering.orders.user_id` и `users.users.id`.
*   **Soft Constraints**: Целостность проверяется валидатором при создании заказа (синхронный вызов `UserService.exists(id)`).
*   **Reconciliation**: Фоновые джобы (Cron), которые раз в сутки ищут "битые" ссылки и алертуют.

---

### 2.2. Контракты взаимодействия (Explicit Public Contracts)

Модульность держится на дисциплине API. Если вы меняете внутренности модуля, ни один другой модуль не должен перекомпилироваться.

#### А. Паттерн "Published Interface"
У модуля есть **Public API Package**, который является единственной точкой контакта.

*   **DTO Only**: Входные и выходные параметры методов API — только DTO (Record/POJO).
    *   *Anti-pattern*: Возвращать Domain Entity (`Order`). Если вы добавите поле в Entity, вы сломаете клиента.
    *   *Anti-pattern*: Принимать `HttpServletRequest` или ORM-сущности.
*   **Immutability**: Все API DTO должны быть неизменяемыми.

#### Б. Версионирование внутри монолита?
Да. Даже в монолите изменение сигнатуры публичного метода — это Breaking Change.
*   **Deprecated first**: Помечаем старый метод `@Deprecated`, создаем новый, мигрируем вызовы, удаляем старый. Это защищает от "Big Bang" рефакторинга.

#### В. Internal Public API
Как технически скрыть внутренности?
*   **Java**: JPMS (Jigsaw) — сложно. Пакетная видимость + ArchUnit — прагматично.
*   **.NET**: `internal` видимость + `[InternalsVisibleTo("Tests")]`.
*   **Go**: `internal` пакеты (поддерживается языком).

---

### 2.3. Событийная архитектура (Internal Event Sourcing)

Для развязывания модулей используйте события. Но дьявол в деталях.

#### А. Domain Events vs Integration Events
На уровне Expert вы должны четко разделять два типа событий:

1.  **Domain Event (Внутреннее)**:
    *   *Имя*: `OrderCalculated`, `TaxApplied`.
    *   *Содержание*: Полный контекст изменения, сущности.
    *   *Область*: Живет **только внутри** модуля (внутри гексагона). Никогда не покидает его.
2.  **Integration Event (Публичное)**:
    *   *Имя*: `OrderCreated`, `PaymentFailed`.
    *   *Содержание*: Минимальный payload (ID, статус) или "Fat Event" (DTO состояния). Стабильная схема.
    *   *Область*: Публикуется в шину (Internal Event Bus) для **других модулей**.

#### Б. Транзакционность событий (At-Least-Once Delivery)
Даже в памяти (In-Memory) события могут теряться (например, если сервер упал сразу после коммита БД, но до отправки события).

**Expert Pattern: The Outbox**
1.  Транзакция БД начинается.
2.  Сохраняем `Order` в таблицу заказов.
3.  Сохраняем `IntegrationEvent` в таблицу `outbox` (в той же транзакции!).
4.  Транзакция коммитится.
5.  *Async Listener*: Читает `outbox` и публикует в `EventBus` (или брокер сообщений).

Это гарантирует, что событие уйдет тогда и только тогда, когда бизнес-операция прошла успешно.

---

### 2.4. Architecture as Code (Fitness Functions)

Документация устаревает в момент написания. Ограничения должны быть в коде. Мы используем **ArchUnit** (Java) или **NetArchTest** (.NET) в юнит-тестах.

**Примеры тестов уровня Staff Engineer:**

1.  **Cycle Detection (Запрет циклов)**:
    ```java
    slices().matching("com.myapp.modules.(*)..")
            .should().beFreeOfCycles();
    ```
    *Почему важно:* Циклические зависимости между модулями (A -> B -> A) делают невозможным их разделение в будущем.

2.  **Layer Violation (Соблюдение слоев)**:
    ```java
    noClasses().that().resideInAPackage("..domain..")
            .should().dependOnClassesThat()
            .resideInAPackage("..infrastructure..");
    ```
    *Почему важно:* Защищает принцип DIP (Гексагональная архитектура).

3.  **Module Privacy (Запрет "черных ходов")**:
    ```java
    classes().that().resideInAPackage("..modules.inventory..")
            .and().arePublic()
            .should().haveSimpleNameEndingWith("Facade")
            .orShould().haveSimpleNameEndingWith("Dto");
    ```
    *Почему важно:* Заставляет разработчиков открывать только Фасады и DTO, оставляя сервисы и репозитории скрытыми.

---

### 2.5. Обработка сбоев (Failure Isolation)

В монолите `OutOfMemoryError` в одном модуле убивает всех. Это главный минус по сравнению с микросервисами. Но логические сбои можно изолировать.

**Паттерны:**
*   **Defensive Programming в Адаптерах**: Если модуль `Shipping` кидает RuntimeException, адаптер в модуле `Orders` должен перехватить его и вернуть понятный бизнес-ответ (например, `ShippingUnavailableResult`), а не ронять весь HTTP-запрос пользователя.
*   **Timeouts**: Даже для вызовов внутри процесса (если они идут через сложные вычисления или блокировки) полезно иметь таймауты, чтобы зависший модуль не съел весь Thread Pool.

### Итоговый чек-лист эксперта для раздела 2:
1.  [ ] У каждого модуля своя схема БД?
2.  [ ] Между схемами нет FK и JOIN?
3.  [ ] Весь межмодульный обмен идет только через DTO?
4.  [ ] CI падает, если кто-то импортирует класс из чужого `internal` пакета?
5.  [ ] Используется Outbox для критически важных событий?

Если везде "Да" — вы построили **Modular Monolith**, готовый к масштабированию и эволюции.

## 3. Стратегический выбор: MonolithFirst vs Microservices

**Основной тезис эксперта**: Архитектура — это опцион. Ваша цель — отложить принятие необратимых решений (распил на микросервисы) до момента, когда у вас будет достаточно информации о границах домена, или когда "цена" монолита (время сборки, когнитивная нагрузка) превысит "цену" микросервисов (операционная сложность).

### 3.1. Стратегия MonolithFirst (Переосмысление 2025)

Мартин Фаулер сформулировал это еще в 2015-м, но смысл часто искажают.
**Суть стратегии**: Начинайте с Модульного Монолита, потому что в начале проекта вы **гарантированно ошибетесь с границами контекстов (Bounded Contexts)**.

*   **Refactoring Cost**:
    *   Переместить класс из одной папки в другую в IDE: **30 секунд** (Ctrl+Drag).
    *   Переместить функциональность из одного микросервиса в другой: **2 недели** (новые контракты, миграция БД, Dual Write, изменение CI/CD, тестирование обратной совместимости).
*   **Domain Discovery**: Монолит служит "песочницей" для кристаллизации домена. Только когда границы стабилизировались, их можно цементировать сетевым разрывом.

**Исключения (Когда Microservices First оправдан):**
1.  Вы точно знаете границы (стандартный домен, например, Email Sender).
2.  Технологическая гетерогенность (нужен Python для ML и Java для Core).
3.  Разные требования к масштабированию "железа" (CPU-bound vs Memory-bound).

---

### 3.2. Экономика выбора: The Microservices Premium

На уровне Staff Engineer вы должны объяснить бизнесу "цену" микросервисов. Это не бесплатно.

График эффективности выглядит как **J-кривая**:
1.  **Low Complexity (Start)**: Микросервисы замедляют разработку (инфраструктурный оверхед, распределенная трассировка, контракты). Монолит выигрывает.
2.  **Inflection Point (Точка перегиба)**: Момент, когда монолит становится слишком большим (CI идет час, IDE виснет, merge conflicts каждый день).
3.  **High Complexity (Scale)**: Здесь микросервисы дают ускорение, позволяя командам работать автономно.

**Базовый набор (Baseline Requirements) для микросервисов:**
Если у вас нет **Platform Engineering** команды, готовой поддерживать:
*   Service Mesh / Service Discovery;
*   Distributed Tracing (Jaeger/Tempo);
*   Centralized Logging (ELK/Loki);
*   Automated Canary Deployments;

...то переход на микросервисы приведет к созданию **"Распределенного кома грязи" (Distributed Big Ball of Mud)**, где отладка баги занимает недели.

---

### 3.3. Сравнительный анализ (Expert Matrix)

Мы сравниваем не просто "хорошо/плохо", а конкретные векторы сложности.

| Характеристика | Classical Monolith | Modular Monolith (Modulith) | Microservices |
| :--- | :--- | :--- | :--- |
| **Главный риск** | Спагетти-код, невозможность поддержки | Нарушение границ (leaky abstractions) | **Распределенные транзакции**, Latency, Network Partitions |
| **Cognitive Load** | Высокая (надо знать всё, чтобы не сломать) | Средняя (фокус на модуле, но виден весь код) | Низкая (фокус на сервисе) + Высокая (Platform complexity) |
| **Failure Modes** | "Всё или ничего" (OOM убивает всё) | Изолируемые (через try-catch), но процесс общий | **Cascading Failures** (один сервис кладет остальные) |
| **Transactionality** | ACID (легко) | ACID внутри модуля, Eventual снаружи | **Saga / Eventual Consistency** (сложно, hard requirement) |
| **Deploy Velocity** | Медленно (очередь на merge, долгий build) | Средне (кэширование сборки) | Высокая (независимый деплой) |
| **Scaling** | X-Axis (клонирование инстансов) | X-Axis + Y-Axis (разделение функций*) | X, Y, Z Axis (полная гибкость) |

*\*Примечание: Modulith можно скейлить по Y-Axis только если вынести модуль в отдельный сервис. Внутри процесса это невозможно.*

---

### 3.4. Драйверы декомпозиции (Decomposition Drivers)

Когда эксперт принимает решение "пилить" Модульный Монолит?
Не "когда много кода". А когда срабатывает один из триггеров:

1.  **Velocity Mismatch (Разная скорость изменений)**:
    *   Модуль `Promotions` меняется каждый день. Модуль `Accounting` — раз в полгода. Их совместный деплой тормозит маркетинг и рискует стабильностью бухгалтерии.
    *   *Решение*: Выносим `Promotions`.
2.  **Resource Constraints (Разные профили нагрузки)**:
    *   `VideoTranscoding` жрет CPU и требует GPU. `UserAuth` требует мало памяти и CPU.
    *   В монолите приходится скейлить дорогие GPU-ноды ради легкой авторизации.
    *   *Решение*: Выносим `VideoTranscoding`.
3.  **Fault Isolation (Изоляция сбоев)**:
    *   Ошибка в `ReportGeneration` вызывает утечку памяти и OOM Kill всего пода, убивая `Checkout`.
    *   *Решение*: Выносим `ReportGeneration`.
4.  **Organizational Scaling (Закон Конвея)**:
    *   Команда бэкенда выросла до 50 человек. Daily Standup невозможен. Merge conflicts блокируют работу.
    *   *Решение*: Делим на стримы (Stream-aligned teams) и даем им свои сервисы.

---

### 3.5. Архитектурный паттерн "The Citadel" (Цитадель)

Это современный гибридный подход, часто применяемый в FinTech и E-commerce.

*   **The Citadel (Цитадель)**: Ядро системы (Core Domain), например, "Леджер" или "Управление заказами", реализовано как **Modular Monolith**. Здесь нужна ACID-транзакционность, сложная логика и консистентность. Оно меняется консервативно.
*   **Outposts (Форпосты)**: Вспомогательные или экспериментальные функции (`Recommendations`, `DeliveryTracking`, `Notifications`) реализуются как **Microservices** вокруг Цитадели.

**Преимущества**:
*   Критические данные целостны (в монолите).
*   Инновации и рискованные фичи изолированы (в микросервисах).
*   Цитадель общается с форпостами асинхронно через Integration Events.

### 3.6. Стратегия миграции: Strangler Fig Application

Если вы уже имеете легаси-монолит ("Ком Грязи"), переписывать его с нуля (Big Bang Rewrite) — это самоубийство карьеры.

**Expert Approach:**
1.  Поставьте перед монолитом **API Gateway** (Proxy).
2.  Начните писать новый функционал (или переписывать модуль) как отдельный **Микросервис** или **Изолированный Модуль**.
3.  Настройте Gateway перенаправлять трафик для конкретных урлов (`/api/v2/cart`) на новый сервис.
4.  Постепенно "душите" (strangle) старый монолит, пока он не исчезнет или не станет микросервисом.

### Резюме раздела 3
Стратегическая формула эксперта:
`Modulith + Hexagonal Architecture` = **Default State**.
Переход к микросервисам — это **осознанная оптимизация** под конкретную боль (Scale, Team Topology, Fault Tolerance), за которую вы платите операционной сложностью.

*Ваша работа как архитектора — максимально продлить жизнь Модульному Монолиту, сохраняя возможность его распила за 1 спринт.*

## 4. Практические паттерны реализации (Implementation Patterns)

Здесь мы рассмотрим проверенные боем (battle-tested) способы организации кода, которые позволяют сохранять жесткость границ (Boundaries) без паралича разработки.

### 4.1. Паттерн "Модульный Фасад" (The Module Facade)

Это эволюция паттерна Facade. Вместо того чтобы позволять другим модулям копаться в ваших сервисах, вы предоставляете **единую точку входа**.

*   **Проблема**: Если модуль A использует 5 разных сервисов модуля B, изменение внутренней структуры B ломает A в 5 местах.
*   **Решение**: Каждый модуль экспортирует ровно один интерфейс (или малый набор интерфейсов), который инкапсулирует все сценарии использования.

**Структура реализации:**
1.  **Public Interface**: `IInventoryModuleApi` (лежит в пакете `api`).
2.  **DTOs**: `CheckStockResult`, `ReserveItemCommand` (лежат в пакете `api`).
3.  **Implementation**: `InventoryModuleFacade` (лежит в `internal`, реализует интерфейс).
    *   Этот класс сам **не содержит логики**. Он работает как диспетчер: принимает DTO, вызывает нужный `UseCase`/`DomainService`, маппит результат обратно в DTO.

**Code Example (Java):**

```java
// --- PACKAGE: com.app.inventory.api (PUBLIC) ---
public interface InventoryModuleApi {
    // Единственная точка входа. Никаких сервисов, репозиториев или сущностей.
    CompletableFuture<StockResultDto> checkStock(String sku);
    void reserveItems(ReservationCmd cmd);
}

// --- PACKAGE: com.app.inventory.internal (PACKAGE-PRIVATE) ---
@Service // Spring Bean
class InventoryFacadeImpl implements InventoryModuleApi {
    private final StockChecker stockChecker; // Internal Domain Service
    private final ReservationUseCase reservationUseCase; // Internal Use Case

    @Override
    public void reserveItems(ReservationCmd cmd) {
        // Трансформация Public DTO -> Internal Command
        var domainCmd = ReservationMapper.toDomain(cmd);
        // Делегирование UseCase
        reservationUseCase.execute(domainCmd);
    }
}
```

### 4.2. Управление Общим Ядром (Shared Kernel Management)

**Shared Kernel** — это модуль, от которого зависят **все**. Это самое опасное место в архитектуре.
*   **Риск**: Любое изменение в Shared Kernel вызывает перекомпиляцию всего монолита.
*   **Правило Эксперта**: Shared Kernel должен быть **стабильным** и **тонким**.

**Что МОЖНО класть в Shared Kernel:**
1.  **Базовые типы (Primitive Obsession mitigation)**: `UserId`, `Money`, `Currency`, `Email`.
2.  **Cross-Cutting Interfaces**: Интерфейс `DomainEvent`, маркерный интерфейс `AggregateRoot`.
3.  **Utils**: Функции для работы с датами, StringUtils.

**Что ЗАПРЕЩЕНО класть:**
1.  **Domain Entities**: Никогда не кладите `User` или `Product` в Shared. У каждого модуля должен быть *свой* класс `User`, содержащий только нужные ему поля.
2.  **DTO для API**: Если вы положите `OrderDto` в Shared, вы свяжете всех потребителей одной структурой.

### 4.3. Паттерны межмодульных запросов (Query Patterns)

Чтение данных из чужого модуля — главная точка боли.

#### Паттерн А: Синхронный запрос (Direct Inquiry)
Простой вызов Фасада.
*   *Когда*: Нужны актуальные данные (Strong Consistency), данные небольшие.
*   *Минус*: Latency складывается.

#### Паттерн Б: Event-Carried State Transfer (ECST)
Репликация данных для разрыва зависимости.
*   **Сценарий**: Модулю `Orders` нужно знать цену товара из `Catalog`.
*   **Реализация**:
    1.  `Catalog` публикует событие `ProductPriceUpdated`.
    2.  `Orders` слушает его и обновляет свою локальную таблицу `order_product_prices`.
    3.  При создании заказа `Orders` читает цену из **своей** таблицы.
*   **Выигрыш**: Zero Latency при создании заказа, полная автономность (Catalog может лежать).
*   **Цена**: Eventual Consistency, дублирование данных.

#### Паттерн В: Модуль-Агрегатор (View Module / BFF)
Если UI нужно собрать сложный дашборд из 10 модулей.
*   Создается отдельный модуль `Dashboard` или `Reports`.
*   Он не содержит бизнес-логики.
*   Он либо ходит синхронно по фасадам других модулей и клеит JSON, либо (лучше) слушает события и строит оптимизированную "плоскую" таблицу (Materialized View) для быстрого чтения.

### 4.4. Инъекция Зависимостей (DI Isolation Strategy)

Как собрать модули вместе, не превратив DI-контейнер в кашу?

**Spring/Dependency Injection Nuances:**
Если вы поставите `@ComponentScan("com.app")` в корне, вы убьете модульность. Spring создаст бины всех классов, даже внутренних.

**Expert Pattern: Explicit Configuration**
Каждый модуль должен иметь свой `@Configuration` класс, который является его манифестом.

```java
// В модуле Inventory
@Configuration
@ComponentScan("com.app.inventory.internal") // Сканируем только свои внутренности
public class InventoryModuleConfig {
    // Явно экспортируем только Фасад
    @Bean
    public InventoryModuleApi inventoryApi(InventoryFacadeImpl impl) {
        return impl;
    }
}

// В корне приложения (Application.java)
@Import({
    InventoryModuleConfig.class,
    BillingModuleConfig.class,
    ShippingModuleConfig.class
})
public class MonolithApp { ... }
```
Это гарантирует, что в глобальный контекст попадут только те бины, которые модуль разрешил "выпустить наружу".

### 4.5. Разрыв циклических зависимостей (Breaking Dependency Cycles)

Цикл `A -> B -> A` — это смерть модульности. Как его разорвать?

#### Техника 1: Dependency Inversion (Events)
*   *Было*: `Order` вызывает `Customer.validate()`. `Customer` вызывает `Order.getLastOrderDate()`. (Цикл!)
*   *Стало*: `Order` вызывает `Customer`. `Customer` слушает событие `OrderCreated` и сохраняет дату у себя. Теперь `Customer` не зависит от API `Order`, он зависит только от контракта события (который можно вынести в Shared или API пакет).

#### Техника 2: Интерфейс обратного вызова (Callback Interface)
Если событийность не подходит (нужен синхронный ответ).
1.  В модуле `A` (который зависит от B) определяем интерфейс `IDataProviderForA`.
2.  Модуль `B` реализует `IDataProviderForA` в своем инфраструктурном слое.
3.  На уровне конфигурации приложения (`Main`) мы инжектим реализацию из B в A.
*   *Результат*: На уровне компиляции B зависит от A (реализует его интерфейс), но A не зависит от B. Мы развернули стрелку зависимости.

### 4.6. Стратегия тестирования "Test Fixtures"

В модульном монолите сложно создавать тестовые данные.
*   *Проблема*: Чтобы протестировать `Shipping`, мне нужно создать `Order`, а для этого нужен `User` и `Product`.
*   *Решение*: Каждый модуль предоставляет **Test Fixture Artifact** (отдельную библиотеку `test-jar`).
    *   Модуль `Inventory` предоставляет `InventoryTestFactory.createItem()`.
    *   Это позволяет писать интеграционные тесты, не зная внутренней структуры таблиц чужих модулей.

### Итоговое резюме Expert-уровня
Реализация Modular Monolith — это постоянный баланс между **DRY** (Don't Repeat Yourself) и **Loose Coupling** (Слабая связность).
**Expert Rule**: В архитектуре **Loose Coupling всегда важнее DRY**. Лучше скопировать класс DTO или утилиту, чем создать неявную зависимость между двумя несвязанными доменами.

## 5. Главные риски Модульного Монолита и стратегии управления (Expert-level Risk Management)

Модульный монолит (Modulith) не является панацеей. Он представляет собой набор компромиссов, и на уровне Expert вы должны не просто знать о них, а активно управлять этими рисками.

### 5.1. Архитектурный дрейф и деградация модульности (Architectural Drift & Erosion)

**Риск**: "Модульный" монолит со временем превратится в "Большой Ком Грязи" (Big Ball of Mud), если команда не будет поддерживать жесткие границы. Код естественным образом стремится к связности (coupling), и без активного сопротивления модульность будет размываться.

**Последствия**:
*   Замедление разработки из-за роста сложности и неочевидных зависимостей.
*   Увеличение технического долга.
*   Невозможность или высокая стоимость рефакторинга и разделения модулей в будущем.
*   Снижение качества кода и увеличение количества дефектов.

**Экспертное управление (Mitigation Strategies):**

1.  **Автоматизированные архитектурные тесты (Fitness Functions)**:
    *   **Суть**: Внедрите в CI/CD пайплайн статический анализ, который проверяет соблюдение архитектурных правил.
    *   **Инструменты**: ArchUnit (Java), NetArchTest (.NET), Deptrac (PHP), Nx (JS/TS) для проверки границ пакетов/библиотек.
    *   **Примеры правил**:
        *   Запрет циклических зависимостей между модулями.
        *   Запрет на прямое обращение к `Internal` пакетам других модулей.
        *   Запрет на зависимость доменного слоя от инфраструктурного.
        *   Обязательное использование DTO для межмодульных вызовов.
    *   **Результат**: Компиляция или сборка проекта должна падать, если нарушено архитектурное правило.

2.  **Architecture Decision Records (ADR)**:
    *   **Суть**: Формализуйте ключевые архитектурные решения. ADRs объясняют *почему* было принято то или иное решение, его контекст, рассматриваемые альтернативы и последствия.
    *   **Результат**: ADRs служат живой документацией, которая помогает новым членам команды понять логику дизайна и предотвращает повторное принятие уже отклоненных решений.

3.  **Code Reviews и парное программирование**:
    *   **Суть**: Используйте эти практики для распространения знаний об архитектуре и обеспечения ее соблюдения на ранних этапах.
    *   **Роль архитектора**: Активное участие в ревью сложных PR, проведение сессий по архитектурным паттернам.

4.  **Владельцы модулей (Module Owners)**:
    *   **Суть**: Назначьте ответственных (Staff/Senior Engineers) за конкретные модули, которые будут следить за чистотой границ, качеством API и соблюдением архитектурных принципов внутри своего модуля.

### 5.2. Управление легаси и миграция (Brownfield Migration & Legacy Evolution)

**Риск**: Интеграция нового модульного кода с существующей, возможно, "спагетти-подобной" легаси-системой. Невозможность одномоментного переписывания (Big Rewrite).

**Последствия**:
*   Высокие риски поломки существенной функциональности.
*   Паралич разработки, если вся команда пытается рефакторить старый код.
*   Затягивание сроков, превышение бюджета.

**Экспертное управление (Mitigation Strategies):**

1.  **Паттерн Strangler Fig (Удушающая Фига)**:
    *   **Суть**: Постепенно "душите" старую функциональность, обертывая ее новым кодом.
    *   **Реализация**:
        *   **Перехват трафика**: Новые запросы (например, `/api/v2/orders`) направляются на новый, модульный код. Старые (`/api/v1/orders`) идут в легаси.
        *   **Фасады**: Создавайте новые "тонкие" фасады поверх легаси-кода, чтобы новые модули зависели от этого фасада, а не от всей "грязи".
        *   **Dual-Write / Dual-Read**: При миграции данных (например, пользователей) из старой БД в новую:
            *   **Dual-Write**: При любой записи в старую БД, дублируйте запись в новую.
            *   **Dual-Read**: При чтении сначала читайте из новой БД, если нет — из старой. После успешного чтения из старой, запишите данные в новую.
    *   **Ценность**: Позволяет плавно мигрировать, минимизируя риски и поддерживая работу системы.

2.  **Branch By Abstraction**:
    *   **Суть**: Для сложных переписываний критически важных компонентов. Создайте новую абстракцию (интерфейс), которую будет реализовывать как старый, так и новый код. Постепенно переключайте пользователей на новую реализацию.

3.  **Оценка ценности**: Не модулируйте все подряд. Если какой-то кусок легаси-кода стабилен, редко меняется и не является узким местом, оставьте его как есть. Сосредоточьтесь на областях с высокой частотой изменений и критическим бизнес-влиянием.

### 5.3. Производительность сборки и развертывания (Build & Deployment Performance)

**Риск**: По мере роста монолита время компиляции, сборки и запуска тестов увеличивается, замедляя цикл обратной связи для разработчиков.

**Последствия**:
*   Снижение продуктивности команды (ожидание сборок).
*   Уменьшение частоты развертываний (долго, рискованно).
*   Задержка обнаружения ошибок.

**Экспертное управление (Mitigation Strategies):**

1.  **Инкрементальные сборки (Incremental Builds)**:
    *   **Суть**: Используйте системы сборки, которые понимают граф зависимостей и пересобирают только изменившиеся модули и их потребителей.
    *   **Инструменты**: Bazel (Google), Gradle (с Gradle Enterprise Build Cache), Nx (для JavaScript/TypeScript монорепозиториев).
    *   **Пример**: При изменении только одного модуля, Bazel пересобирает только этот модуль и перепрогоняет его тесты, а не весь проект.

2.  **Параллелизация в CI/CD**:
    *   **Суть**: Распараллельте выполнение тестов и шагов сборки в вашем CI/CD пайплайне.
    *   **Пример**: Запуск юнит-тестов для каждого модуля на отдельном агенте параллельно.

3.  **Оптимизация образов контейнеров (Docker Image Optimization)**:
    *   **Суть**: Используйте многоступенчатые (multi-stage) Dockerfile для уменьшения размера и ускорения сборки образов.
    *   **Результат**: Меньшие образы быстрее собираются, загружаются и запускаются.

4.  **Стратегии тестирования**:
    *   **Приоритет Unit/Module Integration Tests**: Они быстрые и дают быструю обратную связь.
    *   **Сокращение E2E тестов**: До минимума, прогоняя их реже или на отдельном, более медленном пайплайне.

### 5.4. Масштабирование и узкие места (Scaling & Bottlenecks)

**Риск**: Если один модуль внутри монолита становится "горячей точкой" (bottleneck), потребляющей непропорционально много ресурсов (CPU, память, I/O), то приходится масштабировать весь монолит, что неэффективно.

**Последствия**:
*   Неэффективное использование ресурсов, переплата за инфраструктуру.
*   Ограничение общей производительности системы по самому слабому звену.
*   Сложность в изоляции проблем.

**Экспертное управление (Mitigation Strategies):**

1.  **Проактивное профилирование и нагрузочное тестирование**:
    *   **Суть**: Регулярно проводите нагрузочные тесты и профилирование кода, чтобы заранее выявлять потенциальные узкие места.
    *   **Инструменты**: JProfiler, VisualVM (Java), JMeter, Gatling, K6.
    *   **Цель**: Обнаружить "горячие" модули до того, как они станут проблемой в продакшене.

2.  **Вертикальное и горизонтальное масштабирование (Vertical & Horizontal Scaling)**:
    *   **Вертикальное**: Увеличивайте ресурсы (CPU, RAM) на одном инстансе монолита. Это просто, но имеет пределы.
    *   **Горизонтальное**: Запускайте несколько инстансов монолита за балансировщиком нагрузки. Это стандартный способ масштабирования, но он не решает проблему, если узкое место внутри одного инстанса (например, одна медленная база данных).

3.  **Асинхронная обработка (Asynchronous Processing)**:
    *   **Суть**: Переносите ресурсоемкие, некритичные к задержке операции в асинхронные очереди.
    *   **Пример**: Генерация отчетов, отправка уведомлений, обработка изображений. Модуль публикует событие в RabbitMQ/Kafka, а отдельный (возможно, внешний) worker-сервис его обрабатывает.
    *   **Результат**: Освобождение основного потока обработки, увеличение пропускной способности.

4.  **Кэширование на разных уровнях**:
    *   **In-Memory Cache**: Внутри монолита (Guava Cache, Caffeine).
    *   **Распределенный кэш**: Redis, Memcached (снижает нагрузку на БД).
    *   **CDN**: Для статического контента.

5.  **Экстракция модуля (Module Extraction)**:
    *   **Суть**: Если модуль становится критическим узким местом и его дальнейшая оптимизация в рамках монолита невозможна или нерентабельна, выделите его в отдельный микросервис.
    *   **Преимущество Modulith**: За счет четких границ и API, этот процесс значительно проще, чем вычленение функционала из "кома грязи". API модуля становится контрактом для нового микросервиса.

### 5.5. Когнитивная нагрузка и управление сложностью (Cognitive Load & Complexity Management)

**Риск**: По мере роста числа модулей и их взаимодействий, общая сложность системы может превысить способность отдельного инженера или небольшой команды полностью понимать ее.

**Последствия**:
*   Медленный онбординг новых сотрудников.
*   Ошибки в проектировании из-за неполного понимания системы.
*   Увеличение "Bus Factor" (зависимость от знаний одного человека).
*   Замедление инноваций.

**Экспертное управление (Mitigation Strategies):**

1.  **Team Topologies**:
    *   **Суть**: Организуйте команды таким образом, чтобы они были согласованы с архитектурой модулей. Stream-aligned teams владеют одним или несколькими связанными модулями.
    *   **Результат**: Каждая команда имеет глубокие знания о своей части системы, снижая когнитивную нагрузку на отдельных разработчиков.

2.  **Чистая, актуальная документация**:
    *   **Суть**: Поддерживайте ADRs, README-файлы для каждого модуля, обзорные архитектурные схемы.
    *   **Автоматизация**: Используйте инструменты для генерации документации из кода (Swagger/OpenAPI).

3.  **Инструменты визуализации**:
    *   **Суть**: Используйте генераторы графов зависимостей (например, из Bazel/Gradle), чтобы визуализировать связи между модулями.
    *   **Результат**: Помогает быстро понять структуру системы и выявить аномалии.

4.  **Последовательность и стандарты кода**:
    *   **Суть**: Единые стандарты кодирования, именования, использования фреймворков и библиотек по всей кодовой базе.
    *   **Результат**: Снижает ментальные издержки при переключении между модулями.

### 5.6. Управление распределенными операциями и транзакциями (Distributed Transaction Management)

**Риск**: Хотя Modulith — это один процесс, логически он состоит из независимых доменов. Выполнение бизнес-операции, затрагивающей несколько модулей, требует координации, схожей с распределенными транзакциями.

**Последствия**:
*   Несогласованные данные (нарушение инвариантов).
*   Сложность отката или компенсации ошибок.
*   "Призрачные" записи или неполные операции.

**Экспертное управление (Mitigation Strategies):**

1.  **Предпочитайте Eventual Consistency**:
    *   **Суть**: Для большинства межмодульных операций стремитесь к событийной согласованности вместо строгой ACID.
    *   **Пример**: Заказ создан (модуль `Ordering`) -> событие `OrderCreated` -> инвентарь уменьшен (модуль `Inventory`). Если инвентарь не уменьшился, это не отменяет создание заказа, а требует компенсирующих действий.

2.  **Паттерн Transactional Outbox**:
    *   **Суть**: Как уже упоминалось, используйте его для надежной публикации событий из одного модуля в другой.
    *   **Результат**: Гарантия доставки событий и атомарность изменений состояния модуля и публикации события.

3.  **Паттерн Saga (хореография или оркестровка)**:
    *   **Суть**: Для сложных, долгоживущих бизнес-процессов, охватывающих несколько модулей, используйте Саги.
        *   **Хореография**: Каждый модуль реагирует на события и публикует свои.
        *   **Оркестровка**: Центральный "оркестратор" координирует шаги.
    *   **Результат**: Управляемое управление потоком операций с возможностью компенсации при сбоях.

4.  **Распределенная трассировка (Distributed Tracing)**:
    *   **Суть**: Внедрите сквозную трассировку (например, OpenTelemetry, Zipkin), даже если это монолит.
    *   **Результат**: Позволяет отслеживать весь путь запроса через несколько модулей, идентифицировать задержки и места сбоев.

Понимание и активное управление этими рисками — это отличительная черта опытного архитектора. Modulith — это мощный инструмент, но, как и любой мощный инструмент, он требует умелого и дисциплинированного использования.

## 6. Self-Check (Проверка знаний)

Чтобы подтвердить уровень **Expert**, ответьте на вопросы:
1.  Как организовать транзакционность (Transaction Boundary), если бизнес-операция затрагивает два разных модуля в Modular Monolith? (Ответ: Идеально — через Eventual Consistency. Если нужен ACID — пересмотреть границы модулей, они, вероятно, неверны. В крайнем случае — общая транзакция БД, но это увеличивает coupling).
2.  В чем разница между Hexagonal Architecture и Onion Architecture? (Ответ: Концептуально идентичны в вопросе DIP. Onion явно выделяет слои Application Services и Domain Services, Hexagonal фокусируется на Портах и Адаптерах).
3.  Какие метрики кода укажут на деградацию модульности? (Ответ: Afferent/Efferent Coupling, Instability, Abstractness, LCOM4).

**Резюме**: Ваша задача как архитектора — построить монолит так, чтобы его *можно было* распилить, но *не обязательно было* это делать. Это называется **Design for Replaceability**.

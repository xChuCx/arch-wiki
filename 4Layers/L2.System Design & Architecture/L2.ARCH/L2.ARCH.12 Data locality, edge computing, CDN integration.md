**TL;DR**: В глобальных системах **Latency is the new Downtime**. Ваша задача — переместить вычисления и данные как можно ближе к пользователю, соблюдая при этом законы о хранении данных (Data Residency). CDN больше не "тупой кэш картинок", это программируемый слой (Edge), способный брать на себя роутинг, авторизацию и даже SSR (Server-Side Rendering).

## 1. Data Locality (Локальность данных) и Data Residency

### 1.1. Data Locality: Борьба со скоростью света

**Data Locality** — это архитектурная стратегия размещения данных в непосредственной близости от вычислительных мощностей (Compute) или конечного пользователя для минимизации задержек (Latency) и затрат на передачу данных (Egress cost).

*Термин для понимания:* **Data Gravity (Гравитация данных)**. Приложения и сервисы "притягиваются" к данным. Перенести 100 ТБ данных к приложению сложнее, чем запустить контейнер приложения рядом с данными.

#### Основные паттерны реализации (Topologies):

**А. Read-Local, Write-Global (Репликация чтения)**
Самый простой паттерн.
*   **Архитектура**: Один Master-узел (RW) в регионе (например, `us-east`). Read Replicas (RO) в регионах `eu-central` и `ap-southeast`.
*   **Поток**: Пользователь из Берлина читает из Франкфурта (20ms), но пишет в Вирджинию (100ms).
*   **Применимость**: Content-heavy системы (блогы, каталоги товаров), где `Read >> Write`.
*   **Проблема**: **Replication Lag**. Пользователь обновил профиль, перезагрузил страницу, а данные старые (реплика еще не доехала). Требует техники "Read your own writes" (например, после записи читать с мастера в течение 5 секунд).

**Б. Regional Silos (Региональные колодцы / Шардинг по региону)**
Полная изоляция.
*   **Архитектура**: Стек `EU` (App + DB) и стек `US` (App + DB) ничего не знают друг о друге.
*   **Home Region**: Каждому пользователю при регистрации назначается "Домашний регион".
*   **Роутинг**:
    *   *Geo-DNS (Route53 / NS1)*: Направляет запрос на ближайший IP.
    *   *Global Router (L7 Proxy)*: Если европеец прилетел в США, Geo-DNS отправит его на сервер США. Сервер США проверит JWT/Cookie, увидит `region: eu`, и спроксирует запрос через океан в европейский кластер (или вернет 302 Redirect).
*   **Применимость**: Соцсети, SaaS с жесткими требованиями к локальности.

**В. Active-Active Global Database (Multi-Master)**
Высший пилотаж (и максимальная цена).
*   **Технологии**: Google Spanner, DynamoDB Global Tables, CockroachDB.
*   **Архитектура**: Запись возможна в *любом* регионе. Данные реплицируются во все остальные.
*   **Конфликты**: Как быть, если в Токио и Лондоне одновременно изменили одно поле?
    *   *Last-Write-Wins (LWW)*: Кто последний (по timestamp), тот и прав. Опасно потерей данных.
    *   *CRDTs (Conflict-free Replicated Data Types)*: Математически гарантированное слияние (например, счетчики или множества, которые можно только добавлять).

### 1.2. Data Residency и Data Sovereignty: Юридические границы

**Data Residency** — требование физического хранения данных на территории определенной юрисдикции.
**Data Sovereignty** — подчинение данных законам страны, где они находятся (включая право спецслужб на доступ).

*Пример*: Данные граждан РФ должны храниться в РФ (152-ФЗ). Данные граждан ЕС не должны покидать ЕС без специальных условий (GDPR).

#### Стратегии реализации (Compliance Patterns):

**А. The "Tokenization Proxy" (Паттерн Сейфа)**
Используется, когда основная система глобальна, но нужно соблюсти закон.
1.  **Локальное хранилище (The Vault)**: Внутри защищенного периметра страны (например, Германия) стоит БД с таблицей `PII_Table`: `{UUID: "123-abc", RealName: "Hans Gruber", Passport: "DE..."}`.
2.  **Глобальная система**: Видит только UUID (`123-abc`). Вся бизнес-логика (аналитика, рекомендации) работает с обезличенными ID.
3.  **Tokenization Service**: При вводе данных они немедленно заменяются на токен перед отправкой в глобальное облако. При выводе (отображении в UI) токен "разменивается" обратно на реальные данные на лету, только для пользователя с правами доступа.

**Б. Row-Level Partitioning (Гео-партиционирование строк)**
Современные Distributed SQL базы (CockroachDB, YugabyteDB) позволяют привязывать конкретные строки к физическим узлам.
*   **SQL DDL Пример**:
    ```sql
    ALTER TABLE users PARTITION BY LIST (country_code) (
        PARTITION p_eu VALUES IN ('DE', 'FR', 'IT'),
        PARTITION p_us VALUES IN ('US', 'CA')
    );
    ALTER PARTITION p_eu CONFIGURE ZONE USING constraints = '[+region=eu-central]';
    ```
*   **Результат**: База данных *выглядит* как одна таблица. Вы делаете `SELECT * FROM users`. Но физически данные Ганса лежат на диске во Франкфурте, а данные Джона — в Нью-Йорке. СУБД сама маршрутизирует запрос.
*   **Плюс**: Прозрачность для разработчика.
*   **Минус**: `SELECT *` без фильтра по стране будет работать ужасно медленно (Scatter-Gather запрос по всему миру).

### 1.3. Edge Computing как инструмент локальности

Локальность — это не только база данных, но и вычисления.

**Паттерн "Edge-Side Personalization"**:
Вместо того чтобы гонять запрос в центральную БД за профилем пользователя:
1.  Зашифрованный профиль (lite-версия: имя, тариф, права) кладется в **JWT** или **Encrypted Cookie**.
2.  **Edge Worker** (Cloudflare/Fastly) расшифровывает куку на ближайшем к пользователю узле (CDN PoP).
3.  Edge рендерит HTML ("Привет, Иван! Твой тариф: Pro"), не обращаясь к Origin-серверу.
*   *Результат*: Мгновенная загрузка персонализированного контента при нулевой нагрузке на БД.

---

### Сводная таблица для принятия решений

| Сценарий | Стратегия Locality | Стратегия Residency | Сложность |
| :--- | :--- | :--- | :--- |
| **Интернет-магазин (глобальный)** | Read Replicas (CDN кэш) | Обычно не требуется (кроме оплаты) | Низкая |
| **Банковское приложение** | Regional Silos | Strict Isolation (Разные инстансы) | Высокая |
| **Социальная сеть / Мессенджер** | Geo-Sharding + Follow-me | Row-Level Partitioning (или игнорирование до штрафа) | Очень Высокая |
| **Глобальная аналитика (Logs/Metrics)** | Centralized Data Lake | Anonymization/Scrubbing на Edge перед отправкой | Средняя |

**Вывод Practitioner-уровня**:
Никогда не обещайте бизнесу "глобальную базу данных с задержкой как в локальной сети". Это невозможно физически. Ваша работа — явно выбрать компромисс:
1.  Либо пользователь привязан к региону (**Silos**).
2.  Либо запись медленная (**Global Active-Active**).
3.  Либо данные иногда устаревшие (**Read Replicas**).

## 2. CDN Integration Deep Dive

CDN — это распределенная сеть Reverse Proxy серверов. Главная задача архитектора при интеграции — максимизировать **Cache Hit Ratio** (процент запросов, обслуженных с Edge) и минимизировать **Origin Load** (нагрузку на ваш бэкенд), не нарушая консистентности данных.

### 2.1. Анатомия Cache Key (Ключ кэширования)

Кэш — это хеш-таблица. Чтобы понять, есть ли у нас контент, CDN вычисляет **Cache Key**.
По умолчанию: `Key = Scheme + Host + Path + Query String`.

**Проблема экспертного уровня: "Размытие кэша" (Cache Dilution)**
Маркетологи запускают кампанию с метками `?utm_source=google&utm_campaign=blackfriday`.
*   Пользователь 1: `GET /product?utm_id=123` -> MISS (Origin генерирует страницу)
*   Пользователь 2: `GET /product?utm_id=456` -> MISS (Origin снова генерирует ту же страницу!)
*   *Результат*: Кэш бесполезен, Origin падает под нагрузкой.

**Решение: Нормализация ключа (Key Normalization)**
Вы должны настроить CDN (через VCL в Fastly, Rules в Cloudflare или Policies в AWS CloudFront) так, чтобы игнорировать "мусорные" параметры при *сохранении* в кэш.
*   *Стратегия*: "Включить в ключ только `productId` и `lang`. Все остальные параметры (utm, fclid) передать на Origin (если нужно), но **не использовать** для генерации ключа кэша".

---

### 2.2. HTTP-Заголовки: Пульт управления

Заголовки ответа (Response Headers) диктуют поведение CDN.

#### 1. `Cache-Control`: Разделяй и властвуй
Базовый синтаксис: `Cache-Control: public, max-age=3600, s-maxage=86400`.

*   **`public`**: Разрешает кэширование в Shared Caches (CDN, корпоративные прокси).
*   **`private`**: Запрещает CDN кэшировать это. Только браузер пользователя. (Для страниц "Мой профиль").
*   **`max-age`**: Инструкция для **браузера**. "Держи в локальном кэше 1 час".
*   **`s-maxage` (Surrogate max-age)**: Инструкция для **CDN**. "Держи на Edge-сервере 24 часа".
    *   *Архитектурный трюк*: Ставьте `max-age=0` (или малый), а `s-maxage=High`.
    *   *Зачем*: Браузер всегда идет за свежей версией, но попадает в быстрый кэш CDN. Вы сохраняете контроль над инвалидацией (сбросить кэш CDN вы можете, сбросить кэш в браузере пользователя — нет).

#### 2. `Vary`: Убийца Hit Ratio
Заголовок `Vary` говорит CDN: "Контент зависит не только от URL, но и от этого заголовка запроса".
*   *Сценарий*: Сервер отдает JSON или XML в зависимости от `Accept`. Вы шлете `Vary: Accept`.
*   *Опасность*: Если сервер пошлет `Vary: User-Agent`, CDN сохранит отдельную копию страницы для *каждой* версии Chrome, Safari, Firefox и бота. Кэш станет фрагментированным и неэффективным.
*   *Best Practice*: Никогда не делайте Vary по сырому `User-Agent`. Нормализуйте его на Edge до `X-Device: Mobile/Desktop` и делайте Vary по этому кастомному заголовку.

#### 3. `Surrogate-Control`
Специфичный для CDN заголовок (Akamai, Fastly). Он имеет приоритет над `Cache-Control` и полностью вырезается из ответа перед отправкой клиенту. Используется, чтобы скрыть логику кэширования от внешнего мира.

---

### 2.3. Стратегии Инвалидации: Event-Driven Caching

TTL (Time To Live) — это подход "надейся и жди". В e-commerce и медиа нужен подход "здесь и сейчас".

#### Паттерн: Cache Tagging / Surrogate Keys
Это самый мощный инструмент в арсенале архитектора для работы с динамическим контентом.
Вместо удаления по URL (`PURGE /products/123`), мы удаляем по логическим тегам.

**Алгоритм реализации:**
1.  **Origin**: При генерации ответа добавляет заголовок с мета-тегами.
    *   GET `/products/iphone-15`:
    *   Header: `Surrogate-Key: product-555 brand-apple cat-phones promo-blackfriday`
2.  **CDN**: Индексирует ответ по этим ключам. Заголовок `Surrogate-Key` удаляется перед отдачей клиенту (security through obscurity).
3.  **Событие**: Менеджер меняет цену на все телефоны Apple.
4.  **Purge**: Бэкенд шлет в API CDN запрос: `PURGE tags=[brand-apple]`.
5.  **Результат**: Мгновенно удаляются из кэша:
    *   Страница продукта iPhone 15.
    *   Страница категории "Телефоны".
    *   Страница результатов поиска "Apple".
    *   Все, что было помечено этим тегом.

Это позволяет кэшировать HTML-страницы "навечно" (TTL=1 year) и сбрасывать их точечно при изменении данных.

### 2.4. Защита Источника: Request Collapsing & Shielding

Что происходит, когда контент протухает (Expired) на CDN, а на сайт заходит 10 000 пользователей одновременно?

#### Request Collapsing (Request Coalescing)
Без этой функции CDN пропустит все 10 000 запросов на Origin (эффект **Thundering Herd** — "Бегущее стадо").
*   **Механизм**: CDN видит, что 10 000 запросов идут за одним и тем же ресурсом (`/big-file.json`).
*   CDN пропускает *только первый* запрос на Origin.
*   Остальные 9 999 запросов ставятся в очередь (Wait) на Edge-сервере.
*   Как только первый запрос возвращает ответ, CDN отдает его всем ожидающим и кладет в кэш.
*   *Внимание*: Работает только если ресурс кэшируемый.

#### Origin Shield (Многоуровневое кэширование)
У глобального CDN могут быть сотни PoP (точек присутствия). Если кэш пуст везде, Origin получит по 1 запросу от каждого PoP (сотни запросов).
*   **Решение**: Включить "Shield Layer" (например, в Вирджинии).
*   Все PoP идут не на Origin, а на Shield.
*   Origin получает всегда только **один** запрос от Shield.

---

### 2.5. Stale-While-Revalidate (SWR): SRE Pattern

Этот паттерн превращает синхронную зависимость от Origin в асинхронную.

`Cache-Control: max-age=60, stale-while-revalidate=300, stale-if-error=86400`

1.  **0-60 сек**: Контент свежий. CDN отдает из кэша.
2.  **60-360 сек**: Контент протух.
    *   Пользователь делает запрос.
    *   CDN **сразу** отдает протухшую версию (Latency = min).
    *   CDN **в фоне** идет на Origin за обновлением. Следующий пользователь получит свежее.
3.  **Origin Down**: Если Origin лежит (5xx Error), директива `stale-if-error=86400` говорит CDN: "Отдавай протухшее еще сутки, но не показывай ошибку пользователю".
Это повышает доступность системы (Availability) за счет строгой консистентности.

### 2.6. Debugging & Observability

Как понять, почему `MISS`? Смотрите на отладочные заголовки (обычно включаются отдельно).

*   `X-Cache`: `HIT`, `MISS` или `REFRESH` (Hit, но протух).
*   `X-Cache-Hits`: `543` (сколько раз объект отдали из кэша).
*   `Age`: `120`. (Сколько секунд объект живет в кэше).
    *   *Диагностика*: Если `Age` всегда `0`, значит что-то мешает кэшированию (Set-Cookie, Vary, Cache-Control: no-cache).
*   `CF-Ray` / `X-Amz-Cf-Id`: Уникальный ID запроса для обращения в саппорт CDN.

**Пример для Practitioner**:
Если вы видите `Set-Cookie: session_id=...` в ответе на статический ассет (JS/CSS), CDN (по умолчанию) перестанет его кэшировать, считая приватным.
*Fix*: Настройте Web Server / Edge Worker на вырезание заголовка `Set-Cookie` для публичных расширений (`.js`, `.css`, `.png`).

## 3. Edge Computing (Вычисления на границе)

**Edge Computing** в контексте веба — это исполнение кода на тысячах узлов (PoP — Points of Presence) CDN, максимально близко к пользователю.

**Главное отличие от Cloud Functions (AWS Lambda/GCP Functions):**
1.  **Cloud Functions**: Живут в региональных ДЦ (us-east-1). Латенси до пользователя зависит от географии. Есть проблема "Cold Start" (запуск контейнера).
2.  **Edge Functions**: Живут везде. Латенси < 50ms. Используют технологии изоляции (V8 Isolates), что дает **почти нулевой Cold Start**.

### 3.1. Runtime Internals: Isolates vs Containers

Чтобы использовать Edge эффективно, нужно понимать, *как* он работает.

*   **Модель Контейнеров/MicroVM (AWS Lambda@Edge)**:
    *   Для каждого вызова (или группы) поднимается микро-виртуальная машина (Firecracker) или Node.js процесс.
    *   *Плюсы*: Полная совместимость с Node.js, доступ к файловой системе (/tmp).
    *   *Минусы*: Дороже, медленнее старт (сотни мс).
*   **Модель Изолятов (Cloudflare Workers, Deno Deploy)**:
    *   Используется движок V8 (как в Chrome). Один процесс на сервере крутит тысячи "Изолятов" (Isolates).
    *   Изолят — это не процесс и не контейнер. Это изолированная область памяти внутри V8.
    *   *Плюсы*: Cold Start ~0-5ms. Очень дешево.
    *   *Минусы*: **Нет Node.js API** (нет `fs`, нет `net` для сырых TCP сокетов в старых версиях, специфичные API). Ограничения по CPU time жестче (часто 10-50ms чистого времени процессора).

---

### 3.2. Паттерны применения (Use Cases & Patterns)

Мы не переносим *весь* бэкенд на Edge. Мы выносим туда **Request/Response Manipulation**.

#### Паттерн А: The Security Gatekeeper (Шлюз безопасности)
Самый эффективный способ использования Edge. Отсекайте невалидные запросы *до* того, как они нагрузят вашу инфраструктуру.
*   **JWT Validation**: Проверка подписи токена (CPU-bound операция) делается на Edge. Если подпись неверна — `401 Unauthorized` возвращается мгновенно. Origin даже не узнает о попытке взлома.
*   **WAF & Rate Limiting**: "Если IP из подсети X делает > 100 запросов в минуту к /login — банить на уровне CDN".

#### Паттерн Б: Edge-Side Personalization (Персонализация)
Замена устаревшему ESI (Edge Side Includes).
*   **Проблема**: Кэшировать страницу целиком нельзя, так как в шапке написано "Привет, User".
*   **Решение**:
    1.  Origin отдает HTML-шаблон, где вместо имени — плейсхолдер `<!-- USER_NAME -->`. Этот шаблон кэшируется на Edge **агрессивно** (public, max-age=year).
    2.  Edge Function перехватывает ответ.
    3.  Она расшифровывает Cookie пользователя (или делает быстрый запрос в Edge KV).
    4.  Делает Stream Replace: заменяет плейсхолдер на "Привет, Иван" *на лету*, пока байты летят к пользователю.
*   **Результат**: TTFB (Time To First Byte) как у статики, контент динамический.

#### Паттерн В: The Traffic Router (Умный маршрутизатор)
*   **A/B Testing**: Вместо того чтобы грузить тяжелый JS на клиенте для переключения версий, Edge решает: "User ID нечетный? Проксируем запрос на `backend-v2`. Четный? На `backend-v1`".
*   **Canary Release**: "Пустить 5% трафика из Бразилии на новую версию API".
*   **Waiting Room**: Если Origin перегружен, Edge ставит пользователей в очередь (отдает HTML с таймером), не убивая базу данных.

---

### 3.3. Проблема данных (The Data Bottleneck)

Это "Священный Грааль" Edge-вычислений. Код работает быстро, но данные далеко.

**Проблема 1: Connection Limits**
Если у вас 1000 Edge-узлов, и каждый попробует открыть TCP-соединение к вашей PostgreSQL базе (`max_connections=100`), база упадет мгновенно.
*   **Решение 1 (Connection Pooling)**: Использовать промежуточный пулер (PgBouncer, Supabase, Prisma Data Proxy), который работает по HTTP.
*   **Решение 2 (Database-over-HTTP)**: Использовать базы данных с родным HTTP API (DynamoDB, Neon, PlanetScale).

**Проблема 2: Latency to Origin**
Если Edge в Сиднее, а БД в Вирджинии, запрос из Edge Function будет идти те же 200ms. Выигрыша нет.
*   **Решение 1: Edge KV (Key-Value)**.
    *   Распределенные хранилища (Cloudflare KV, Redis Global).
    *   Данные реплицируются во все регионы. Чтение локальное (ms). Запись медленная (eventual consistency).
    *   *Use Case*: Конфиги, списки редиректов, переводы (i18n), черные списки IP.
*   **Решение 2: Distributed SQL (D1, CockroachDB)**.
    *   Попытка принести реляционные данные на Edge. Часто используют Read Replicas в каждом регионе.

---

### 3.4. Server-Side Rendering (SSR) на Edge

Популярный тренд (Next.js, Remix, Nuxt). Рендеринг React/Vue компонентов происходит не на сервере, а на Edge.

*   **Преимущество**: HTML генерируется близко к пользователю. Меньше сетевых хопов.
*   **Риск (Hydration Mismatch)**: Если Edge срендерил дату как "10:00" (по времени сервера в Лондоне), а клиент в браузере ожидает "12:00" (по Москве) — произойдет ошибка гидратации.
*   **Совет Архитектора**: На Edge рендерите только то, что не зависит от сложных данных из центральной БД. Если для рендера нужно сделать 5 запросов к медленному API в другом регионе — Edge SSR будет *медленнее*, чем обычный серверный рендеринг рядом с БД.

### 3.5. Ограничения (Limitations), о которых молчат в маркетинге

На уровне Practitioner вы должны знать границы применимости:

1.  **CPU Time Limits**: Обычно дается 10-50ms *процессорного* времени. Вы не можете майнить крипту или сжимать тяжелые изображения на Edge.
2.  **Memory Limits**: Обычно 128MB. Тяжелые ML-модели не загрузить.
3.  **Code Size**: Размер скрипта часто ограничен (например, 1MB сжатого кода). Нельзя засунуть туда огромное монолитное приложение.
4.  **Request Subrequests**: Обычно есть лимит на количество исходящих запросов (например, не более 50 fetch-запросов на один входящий).

**Пример для закрепления**:
*Задача*: Сделать ресайз аватарок пользователей.
*   *Плохое решение*: Грузить картинку в Edge память, ресайзить JS-библиотекой (Memory Limit OOM / CPU timeout).
*   *Хорошее решение*: Использовать специализированное API CDN (Cloudflare Image Resizing / AWS Lambda с нативными бинарниками ImageMagick), а Edge использовать только для *подписи* URL (валидации прав доступа к картинке).

## 4. Паттерны проектирования с учетом Edge (Edge-Native Patterns)

Использование Edge меняет топологию трафика. Если вы не спроектируете этот слой явно, вы рискуете получить "распределенную атаку" на собственный бэкенд в момент сброса кэша.

### 4.1. The Origin Shield & Tiered Caching (Многоуровневый щит)

**Проблема**: У глобального CDN тысячи Edge-серверов (PoPs). Если вы сбросите кэш для популярного ресурса (например, `homepage.json`), каждый из этих тысяч серверов одновременно пойдет на ваш Origin за обновлением.
*   *Термин*: **Cache Stampede** или **Thundering Herd** (Бегущее стадо). Ваш Origin упадет, даже если за ним стоит автоскейлинг, так как он не успеет раскрутиться за секунды.

**Решение**: Внедрение промежуточного слоя кэширования — **Regional Shield**.

*   **Топология**: `Client` → `Edge PoP (1000 nodes)` → `Regional Shield (10 nodes)` → `Origin (1 cluster)`.
*   **Механизм**:
    1.  Запрос приходит в Edge PoP (Лондон). Кэша нет (`MISS`).
    2.  Edge PoP идет не на Origin, а на ближайший Shield PoP (Франкфурт).
    3.  Shield PoP агрегирует запросы со всей Европы. Если у него нет кэша, он делает **один** запрос на Origin.
    4.  Shield кэширует ответ и раздает его всем Edge PoP.
*   **Результат**: Нагрузка на Origin снижается с `N * M` (где N — трафик, M — кол-во PoP) до `K` (кол-во Shield регионов).

### 4.2. Request Coalescing (Схлопывание запросов)

**Проблема**: Даже с Shield, если 1000 пользователей *одновременно* (в одну миллисекунду) запросят "холодный" ресурс, прокси может пропустить их всех на Origin, так как первый запрос еще не успел вернуть ответ и записать его в кэш.

**Решение**: Включение **Request Collapsing / Coalescing**.

*   **Алгоритм**:
    1.  Приходит Запрос А на ресурс `/big-data.json`.
    2.  CDN видит `MISS`. Отправляет запрос на Origin. Создает "блокировку" (Lock) на этот URL-ключ.
    3.  Приходят Запросы Б, В, Г... на тот же URL.
    4.  CDN видит Lock. Вместо отправки новых запросов на Origin, он ставит эти запросы в очередь ожидания (Pause) на Edge.
    5.  Запрос А возвращается с данными.
    6.  CDN записывает данные в кэш и **копирует** ответ для Запросов Б, В, Г.
*   **Важно для Practitioner**: Это работает *только* для идемпотентных запросов (GET). Никогда не включайте это для POST/PUT, иначе пользователи получат чужие ответы.

### 4.3. The Valet Key Pattern (Паттерн камердинера) / Direct-to-Object

**Проблема**: Загрузка и скачивание тяжелых файлов (видео, отчеты) через ваш бэкенд (Node.js/Python) блокирует потоки (Event Loop) и расходует память. Бэкенд становится "бутылочным горлышком".

**Решение**: Бэкенд делегирует доступ к хранилищу (S3/GCS), выдавая временный "ключ" (Pre-signed URL).

*   **Upload Flow**:
    1.  Клиент -> Edge/Backend: `POST /api/upload-intent {filename: "video.mp4"}`.
    2.  Backend (Auth Check): Генерирует **Signed URL** (например, S3 `PUT` URL, валидный 5 минут).
    3.  Backend -> Клиент: Возвращает этот URL.
    4.  Клиент -> **S3 (напрямую)**: Загружает гигабайты данных по Signed URL.
*   **Download Flow**:
    1.  Клиент -> Edge: `GET /secure-files/report.pdf`.
    2.  **Edge Worker** (вместо Origin): Проверяет JWT токен в заголовке.
    3.  Edge Worker: Подписывает запрос "на лету" (добавляет подпись ключом AWS/Cloudflare) и проксирует в приватный бакет S3.
*   **Результат**: Трафик данных идет мимо вашего вычислительного кластера. Вы платите только за генерацию подписи (CPU ~0ms).

### 4.4. The "Sorry Server" / Failover at Edge

**Проблема**: Ваш Origin (весь дата-центр) упал. Пользователи видят белый экран или стандартную заглушку 502 Bad Gateway от балансировщика. Это потеря репутации.

**Решение**: Интеллектуальный фоллбэк на Edge.

*   **Реализация**:
    *   Настраиваем в CDN (VCL/Worker) логику обработки ошибок `5xx`.
    *   `if (origin_response.status >= 500)`:
        *   **Вариант А (Stale)**: Отдать протухшую версию из кэша (даже если TTL истек неделю назад). `stale-if-error`.
        *   **Вариант Б (Static Site)**: Сделать редирект или (лучше) внутренний рерайт на статический бакет (S3), где лежит "Lite-версия" сайта или красивая страница "Мы проводим обслуживание".
*   **Пример**: Во время падения Twitter пользователи могли читать старые твиты (Stale Content), но не могли постить новые. Это лучше, чем белый экран.

### 4.5. Backend for Frontend (BFF) at the Edge

**Проблема**: Мобильному приложению нужно собрать данные из 3 микросервисов (Profile, Billing, Notifications). Делать 3 запроса с телефона с плохим 4G — долго (Latency x3).

**Решение**: Перенос агрегации на Edge.

*   **Архитектура**:
    *   Edge Worker выступает как API Gateway.
    *   Клиент делает один запрос: `GET /api/me-aggregate`.
    *   Edge Worker (находясь на быстрой магистрали интернета) делает 3 параллельных `fetch` запроса к вашим микросервисам.
    *   Edge склеивает JSON и отдает клиенту.
*   **Преимущество**: Запросы "Edge -> Origin" идут по оптимизированным бэкбонам (AWS Backbone / Google Network), которые гораздо стабильнее и быстрее публичного интернета.
*   **Ограничение**: Не делайте тяжелую трансформацию данных (фильтрацию массивов на 10к элементов) на Edge из-за лимитов CPU.

### Сводка паттернов (Cheat Sheet)

| Паттерн | Проблема, которую решает | Ключевая технология |
| :--- | :--- | :--- |
| **Origin Shield** | Thundering Herd (атака клонов при сбросе кэша) | Tiered Caching topology |
| **Request Coalescing** | Гонка запросов при `MISS` | Mutex/Lock на URL в CDN |
| **Valet Key** | Перегрузка бэкенда тяжелым I/O (файлы) | Signed URLs / Signed Cookies |
| **Failover at Edge** | Полный отказ дата-центра (Downtime) | `stale-if-error`, синтетический ответ |
| **Edge BFF** | Высокая задержка на мобильных клиентах | Fetch API, Promise.all() на Edge |

## 5. Self-Check (Практические сценарии)

1.  *Сценарий*: Вы задеплоили новый JS-бандл, но пользователи жалуются, что видят старую верстку с новым JS, и сайт падает.
    *   *Диагноз*: Рассинхрон кэша. HTML закэшировался с одной версией, JS с другой.
    *   *Решение*: Использовать **Immutable Deployments**. Файлы называются `app.v123.js`. HTML никогда не кэшируется (или кэшируется с SWR), а JS-файлы кэшируются навечно (`max-age=31536000`).
2.  *Сценарий*: Нужно заблокировать доступ к видео для пользователей из страны X, но разрешить поисковому боту Y.
    *   *Решение*: Реализовать логику на Edge Worker (WAF Rule), анализируя Geo-IP базу и User-Agent/IP бота. Делать это на бэкенде — слишком дорого и медленно.

**Резюме**: Интеграция CDN и Edge — это перенос сложности из кода приложения в инфраструктуру сети. Это снижает Latency, но повышает сложность отладки. Главный инструмент архитектора здесь — **Observability на уровне CDN** (логи Edge-воркеров, метрики Hit Ratio).

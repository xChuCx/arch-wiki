# L1.HW.06 Архитектура Современной Памяти (Deep Dive): От Физического Кремния до CXL Фабрик

> [!abstract] Опорный концепт для Staff Engineer
> Рядовой программист уверен, что оперативная память ($RAM$) обладает константным временем доступа $O(1)$. Это самая опасная и дорогая иллюзия в $Computer \ Science$.
> Настоящая оперативная память глубоко асимметрична. Она представляет собой трехмерный лабиринт из Каналов (Channels), Ранков (Ranks), Банков (Banks), Строк (Rows) и Столбцов (Columns). Понимание того, как контроллер памяти (IMC) физически открывает и закрывает страницы Транзисторов внутри этой иерархии — это грань, отделяющая медленный enterprise-софт от высокопроизводительных биржевых (HFT) или In-Memory баз данных ($ScyllaDB, \ Redis \ Enterprise$).
> В этой лекции мы погрузимся на уровень физики передачи сигналов, разберем причины возникновения Memory Wall, заглянем в пакеты протокола CXL и изучим методы ОС Linux по управлению гетерогенными слоями RAM.

## 1. Физическая Ложь Random Access: Анатомия DRAM

Термин **Random Access** (Случайный доступ) исторически означал отличие от магнитных лент (где для чтения байта нужно физически перемотать бобину). Но сегодня $DRAM$ абсолютно непредсказуема при случайном доступе из-за своей внутренней топологии.

### 1.1. Микротопология Памяти: Иерархия Банка

Взгляните на обычный модуль $DDR5$ сервера. Когда ваш $CPU$ запрашивает физический адрес, Контроллер Памяти дешифрует этот 64-битный адрес и разбивает его на кусочки маршрутизации: `[Канал | Ранк | Банк | Строка | Столбец]`.

Физической транзакционной единицей (сердцем) является **Банк Памяти (Bank)**.
Каждый Банк — это гигантская двумерная Электронная Таблица (Матрица конденсаторов). 
*   Размерность типичного Банка: **$65536 \ Строк \ (Rows)$** на **$1024 \ Столбца$**.
*   Размер одной Строки (DRAM Page/Row Buffer): Обычно **$8 \ Килобайт$**.

В самом низу этой Матрицы находится **Row Buffer (Усилитель считывания / Буфер Строки)**. Это крошечный кэш уровня SRAM размером ровно в $8 \ KB$. 
*Драматическое правило физики:* Центральный процессор **ФИЗИЧЕСКИ НЕ МОЖЕТ** прочитать данные прямо из Матрицы Конденсаторов. Он может читать данные ТОЛЬКО из Row Buffer!

### 1.2. Анатомия Запроса (RAS и CAS)

Рассмотрим, что физически происходит в кремнии, когда вы делаете `$return \ array[0];$` и ловите $L3 \ Cache \ Miss$. Идет поход в $DRAM$.

**Сценарий 1: Успех (Page Hit / Открытая Страница)**
Вам невероятно повезло. Строка $8 \ KB$, в которой лежит `array[0]`, УЖЕ была загружена в $Row \ Buffer$ предудыщим запросом (Например, вы итерируете массив).
*   Контроллер посылает только сигнал **CAS (Column Address Strobe)** — забрать нужный столбец из готового буфера.
*   *Задержка:* Менее **$15 \ Наносекунд$**. Идеальная скорость $DDR5$.

**Сценарий 2: Холодный Старт (Page Empty)**
Буфер строки пуст. 
*   Контроллер посылает сигнал **RAS (Row Address Strobe)**. 
*   *Физика:* Транзисторы во всей строке матрицы на $8 \ KB$ открываются. Миллионы крошечных зарядов (электронов) стекают по микропроводникам (Bitlines) вниз, в $Row \ Buffer$. Усилитель "узнает" нолики и единички.
*   Только после этого идет сигнал $CAS$, чтобы забрать ваши $64 \ Байта$ в CPU.
*   *Задержка:* **$RAS \ + \ CAS \ \approx \ 30 \ Наносекунд$**.

**Сценарий 3: Катастрофа (Bank Conflict / Страничный Конфликт)**
Вы пишете плохой код (Связный Список $Linked \ List$, случайные прыжки по всей куче $Heap$).
В $Row \ Buffer$ сейчас лежит Строка $\text{№1}$ (вы читали `Node_A`). Вы просите `Node_B`, которая лежит в Строке $\text{№9000}$ ТОГО ЖЕ САМОГО БАНКА.
*   *Физика:* В Банке всего ОДИН Буфер. В него нельзя положить 2 строки!
*   Контроллер памяти обязан послать сигнал **PRE (Precharge / Предзаряд)**. Это жестокая физическая операция: нужно взять $8 \ KB$ данных из Буфера и *насильно впихнуть заряды обратно вверх* в матрицу конденсаторов Строки $\text{№1}$ (Закрыть страницу).
*   Затем нужно выждать время `tRP` ($Row \ Precharge \ Time$).
*   Затем подать $RAS$ на Строку $\text{№9000}$. Выждать `tRCD` ($RAS \ to \ CAS \ Delay$).
*   Затем подать $CAS$, чтобы получить данные.
*   *Задержка (Проклятие Bank Conflict):* **$PRE \ + \ RAS \ + \ CAS \ \approx \ 70 - 100 \ Наносекунд!$**

> [!warning] Следствие для Staff Инженера
> Ваш код на C++/Rust может работать в **5 раз медленнее** только потому, что алгоритм неудачно "прыгает" по памяти, попадая в один и тот же Банк (с шагом, кратным степени двойки), вызывая $Bank \ Conflict \ Storm$. 
> Чтобы этого избежать, мощные СУБД делают Memory Padding или перемешивают адреса, чтобы запросы равномерно распределялись паралелльно по ВСЕМ 32 Банкам памяти $DDR$ модуля (Банки независимы). Это называется $Bank-Level \ Parallelism \ (BLP)$.

## 2. Налог Регенерации: Температура и Атака Rowhammer

Кроме задержек Маршрутизации ($RAS/CAS$), память скрывает еще один слой стагнации — Амнезию.

### 2.1. Тайминги tREFI и tRFC

Крошечный конденсатор ($Capacitor$) ячейки 1T1C идеален для плотности (Мы можем запихать миллиарды на микросхему), но катастрофичен с точки зрения физики удержания. Диэлектрик несовершенен. Электроны, накопленные при $V_{dd}$, утекают в кремниевую подложку.

Чтобы Сервер не забыл ваши данные СУБД, Контроллер Памяти жестко диктует два закона (Тайминга):
1.  **tREFI (Refresh Interval):** Пауза свободы. По стандарту $JEDEC$, это $7.8 \ \mu s$ (Микросекунд). Ровно столько времени ваш Процессор имеет право нормально работать с памятью. Через каждые $7.8 \mu s$ контроллер обязан послать аппаратную команду $REF$ (Refresh).
2.  **tRFC (Refresh Cycle Time):** Сервисное Обслуживание. Как только послан $REF$, Банк памяти полностью БЛОКИРУЕТСЯ. Системы подают питание и прочитывают/перезаряжают целые сектора строк с помощью $Sense \ Amplifiers$, прогоняя ток. Это занимает астрономические по меркам кремния $350 \ Наносекунд$. 

**Температурный Гнев:** Закон Аррениуса гласит, что утечки тока растут экспоненциально с нагревом.
*   До $85^\circ \text{C}$: Стандартный $tREFI \ = \ 7.8 \ \mu s$.
*   От $85^\circ \text{C}$ до $95^\circ \text{C}$: Вы обязаны удвоить агрессивность. $tREFI$ сжимается до **$3.9 \ \mu s$**. 
    *Что это значит для Архитектора Дата-центра?* Если в стойке жарко, ваш Модуль Памяти переходит в фазу жесткого Рефреша. Он будет недоступен (Locked) почти $20\%$ своего времени жизни, просто обновляя сам себя! Ваша пропускная способность ($Bandwidth$) просядет на пятую часть, а $P99 \ Latency$ базы данных покажет гигантские всплески, потому что запросы уперлись в $tRFC \ Lock$.

### 2.2. Rowhammer: Взлом Железа через Физику

Гонка за плотностью (переход на техпроцессы $14 \ nm$ $DRAM$) приблизила транзисторы и провода в матрице на фатально близкое атомное расстояние. 
Паразитная электро-магнитная емкость (Cross-talk) между соседними проводами достигла предела.

**Сценарий Атаки (Код без Привилегий):**
Вы - хакер, исполняющий код в $Docker$-контейнере с нулевыми правами:
1. Вы находите две Строки Памяти (Rows) в одном Банке: Строку $N-1$ и Строку $N+1$.
2. Вы в цикле `While(true)` делаете миллионы обращений $Чтение-Запись$ в эти две строки (Поднимая и закрывая напряжение по $Bitline$ проводам, используя $CLFLUSH$ чтобы обойти кэши CPU).
3. Строка $N$ (которая лежит между ними зажатая), у которой может лежать $Page \ Table$ ядра Линукса $Root-a$, начинает облучаться ЭМИ-полем от соседних проводов. 
4. Её конденсаторы начинают бешено терять заряды из-за $Electromagnetic \ Leakage$, и *ОНИ РАЗРЯЖАЮТСЯ БЫСТРЕЕ*, чем наступит штатный спасительный цикл контроллера $tREFI \ 7.8 \mu s$! 
5. Бит "1" превращается в "0". Вы аппаратно изменили чужие данные без доступа к ним!

**TRR (Target Row Refresh)**
Для компенсации этого бага аппаратуры, производители внедрили $Микро-Радары$ на чипы DDR4/DDR5: **TRR**.
Микросхема $DDR5$ теперь содержит крошечный кэш-трекер внутри себя. Он считает: "Ага, строку $N-1$ кто-то прочитал уже $200,000$ раз за последнюю миллисекунду. Это подозрительно (Агрессор)! Я СРОЧНО вызову асинхронный Рефреш для *строки N* (Жертвы), чтобы спасти ее от утечки!".
Это удорожает логику чипа, но спасает Облачные Виртуальные Машины (AWS/GCP) от пробития песочниц.

## 3. Вертикальный Побег: 3D Stacking (HBM) и Интерпозеры

Шина $DDR$ на материнской плате уперлась в потолок. Передача сигнала частотой $4 - 6 \ GHz$ по Медным дорожкам длиной в $15$ сантиметров (Trace routing) через Разъем $DIMM-слота$ превращает прямоугольный сигнал (1 и 0) в "Размазанную Кашу" (Signal Integrity degradation / Jitter). 
Разгонять частоту больше законы электродинамики текстолита не давали (пришлось выдумывать дикие кодировки $PAM4/NRZ$). На помощь пришла 3D-геометрия упаковки (Advanced Packaging).

### 3.1. TSV: Просверливая Кремний
Для создания **HBM (High Bandwidth Memory)** инженеры отказались от идеи "Класть чипы вокруг Процессора". Они стали класть чипы *Вверх*.
*   Но как соединить 12 этажей кремния проводами, если провод нельзя вытянуть сбоку (cлишком длинно и медленно)?
*   Технология **TSV (Through-Silicon Via)**: В слое $Silicon \ Wafer$ лазером сверлятся отверстия толщиной в несколько микронов, и заливаются металлом. 
*   Вавилонская башня собирается вместе: на макушку каждого TSV-канала капают шарик меди/олова (**Micro-bump**, размер около $25 \ \mu m$). Этажи прижимают и запекают в духовке ($Thermosonic \ Bonding$). 
*   *Результат:* Мы получили тысячи ультра-коротких "вертикальных лифтов", пронизывающих 12 чипов насквозь. Сопротивление (Resistor) такого провода около-нулевое, паразитная емкость (Capacitor) смешная. Сигнал летает с невероятной энергоэффективностью ($pJ / bit$).

### 3.2. Base Logic Die (Декомпозиция IMC)
Канонический Модуль Планки DDR имеет Контроллер (IMC) прямо в Голове Процессора $CPU$. В стопке $HBM$ подход другой.
Нижний этаж (Фундамент 3D-Сборки) — это **Logic Die**. Зачем он нужен?
Вместо того, чтобы тратить сверхценные нанометры дорогого техпроцесса GPU ($TSMC \ 4nm$) на обслуживание памяти $DRAM$, инженеры спаивают Контроллер Памяти, Блоки Регенерации, Системы Тестирования BIST, и Роутинг ECC *в отдельный дешевый Логический Чип* (например на $14nm$).
Все верхние слои памяти в Башне HBM абсолютно "Тупые". Они содержат только Транзисторы и Конденсаторы. Logic Die берет сигнал от процессора, и как диспетчер, раскидывает его по лифтам TSV в нужные банки нужного Этажа.

### 3.3. Широте плевать на Частоту
*   Почему GDDR6/GDDR6X (На Игровых Видеокартах, 2D упаковка) горячие? Там шина $384 \ Бита$. Чтобы достичь $1 \ TB/s$, нужно разгонять частоту чипов памяти до $\mathbf{21 \ GHz}$. Это кипяток и энергопотребление.
*   Конструкция $HBM3$ (На $A100 / H100$). За счет того, что TSV контактов на подложке (Interposer-е) можно просверлить безумное множество, Шина *одного* Stack-а HBM достигает **$1024 \ Бита$!** Установив 6 таких кубиков вокруг GPU-чипа на расстояние миллиметра, Вы получаете сверхширокую магистраль **$6144 \ Бита$**.
*   Вам больше не надо гнать частоту! Вы передаете "Океан" байт, работая на смешных и ледяных частотах в $2-3 \ GHz$. Вы получаете $\mathbf{3.3 \ Terabytes \ per \ Second}$ (H100) при невероятно низком напряжении. 
*   Единственный минус HBM: Это дорого ($>\$500$ за чип) и термически изолированно. Горячий Logic Die на дне этой башни накрыт крышей из 12 слоев кремния. Если охладить это плохо (Плохая водоблоковая система), $HBM$-модуль впадет в троттлинг ($Refresh \ Tax \ x2$).

## 4. Compute Express Link (CXL): Разрушение PCIe и Когерентность

Долгое время серверы строились как "Коробочные замки". Вся память, воткнутая в материнскую плату, являлась собственностью одного Процессора. Если Серверу А нужно расширить ОЗУ, мы вынимали старые Планки, и ставили новые ёмкие ($Scale-Up$).
Периферия (Видеокарты, NVMe Диски, Сетевые Адаптеры) общались с памятью Процессора через интерфейс **PCIe (Peripheral Component Interconnect Express)**.

Но PCIe — это $Block-Level$ шина, созданная для передачи Изолированных пакетов. Она **НЕ ЗНАЕТ** о существовании Протоколов Когерентности Кэшей (MESI, см. Лекцию HW.03).

### 4.1. Тупик PCIe: Snooping и DMA Боль
*Кейс:* Сетевая Карта ($SmartNIC$) использует DMA (Direct Memory Access) чтобы записать Сетевой Пакет прямо в оперативную $DRAM$ сервера.
*Проблема:* Центральный процессор Линукса в этот момент может держать этот же физический адрес в своем Горячем $L1$ Кеше!
*   PCIe карточки вынуждены посылать гигантские сигналы Прерываний ($Interrupts$), или процессор должен аппаратно сбрасывать (Flush) свои Кеши, чтобы "Свистнуть" в RAM и понять, изменил ли что-то Контроллер Сети.
*   Каждый $I/O$ чихание периферии убивает производительность ЦПУ (Остановка Конвейера, Stall).

### 4.2. Рождение CXL (FLITs и 3 Суб-Протокола)

Индустрия договорилась о стандарте **CXL**. Гениальность CXL в том, что он **ФИЗИЧЕСКИ** втыкается в ТЕ ЖЕ САМЫЕ разъемы материнской платы (Штатный Слот PCIe 5.0 x16). Мы не меняем железо коннекторов. Мы меняем $Wire \ Protocol$ (Смысл сигналов). Стандарт нарезает данные не в PCIe Payload блоки, а в **FLITs (Flow Control Units)** — микросекундные атомарные пакеты по $68 \ Байт$, что минимизирует Latency.

На шине CXL работают 3 одновременных логических линка:
1.  **CXL.io:** Это обычный старый PCIe интерфейс (Для Дискавери устройств, монтирования и конфигурации прерываний).
2.  **CXL.cache:** Это Революция $\text{№1}$. Периферия (GPU или SmartNIC) получает РАВНЫЕ права с Процессором Линукса. NPU $Accelerator$, на котором считается Машинное Зрение, может аппаратно, напрямую лазить в **$L3 \ Cache$ Центрального процессора Intel!** Протокол CXL транслирует Snooping (Snoops, Invalidates), и теперь NPU ведет себя так, будто бы он является "Еще Одним Сокетом x86", участвующим в MESI протоколе сервера. Никаких Flush или DMA Interrupts! Ускоритель видит измененные байты за $10 \ ns$.
3.  **CXL.mem:** Это Революция $\text{№2}$. Центральный процессор Intel/AMD использует периферийное устройство (Например CXL-плату воткнутую в порт расширения), и воспринимает ее как **Абсолютно штатную Планку Оперативной Памяти DDR5**, но подключенную через удлинитель). Linux Kernel при загрузке опрашивает ACPI (SRAT таблицы), и ему говорят: "У нас есть локальная NUMA node 0 (DDR5), и CPU-less NUMA node 1 на шине CXL". Линукс делает `malloc()` туда прозрачно!

*Задержка (Latency):* CXL.mem Добавляет поверх штатного контроллера памяти (IMC) задержку маршрутизатора (CXL Controller Flit conversion).
*   Локальная $DDR5$: $\approx 80-100 \ Наносекунд$.
*   Плата $CXL \ CMM$: $\approx 150-180 \ Наносекунд$.
Для огромных InMemory баз данных типа $Memcached$ или гигантских кэшей $JVM / Redis$, $150 \ ns$ - это абсолютно приемлемо, зато емкость Стойки можно увеличить в Терабайты, просто вставляя CXL-модули как флешки (E3.S / EDSFF).

## 5. Композитная Архитектура: CXL Fabric и Memory Pooling (CXL 2.0/3.0)

Технология CXL.mem позволяет подключить Плату ОЗУ к Одному Серверу. Но настоящая Дата-центровая (Datacenter-Scale) революция случается, когда мы добавляем понятие Сети (Switches).

### 5.1. Трагедия Stranded Memory (Застрявшая память)
В AWS/GCP миллионы серверов. По статистике облачных провайдеров, в любой момент времени **до $40\%$ всей Оперативной Памяти в датацентрах простаивает пустой**. Это колоссальные миллиарды долларов похороненного кремния.
*   **Изоляция:** Если Серверу А (Машинное обучение) срочно нужны лишние $512 \ GB \ RAM$, он падает с $Out-Of-Memory \ (OOM)$. А в это время соседний Сервер $B$ (Веб-Рендеринг) стоит пустым и у него свободно $700 \ GB \ RAM$. ОС Линукс Сервера $А$ не может просто "взять" планки Сервера $B$. Физическая архитектура $Von \ Neumann$ заперла ресурсы внутри материнских плат (Motherboard boundary).

### 5.2. CXL Switches и Бассейны Памяти (Memory Pooling)

Спецификация $CXL \ 2.0+$ вводит Композитную Архитектуру (Composable Disaggregated Infrastructure / CDI). Роль материнской платы забирает Коммутатор Стойки (CXL Switch, Top-of-Rack).
Мы собираем Стойку по-другому:
1.  **Корзины Памяти (Memory Appliances):** Вынимаем $DDR5$ из серверов. Ставим в стойку отдельный железный "Шкаф" формата $4U$ JBOF (Just a Bunch of Flash/RAM). Он набит терабайтами ОЗУ. Он называется **MLD (Multi-Logical Device)**.
2.  **Вычислительные Ноды (Compute Nodes):** Это простолезвия ($Blades$), на которых торчат только $Intel/AMD \ CPU$ и нет ничего кроме пары локальных модулей RAM для загрузки ОС. 
3.  **CXL Fabric (Фабрика):** Сервера подсоединены к MLD-шкафам через оптические кабели CXL-Коммутатора.

**Магия Динамического Аллоцирования (Dynamic Capacity Binding):**
Управляющий Софт Датацентра (Fabric Manager / Orchestrator) работает как Бог.
*   *12:00 Дня:* Запускается Кластер БД на Серверах $X$ и $Y$. Fabric Manager посылает сигнал в CXL-Свитч: "Отрежь $2 \ Terabytes$ из Корзины ОЗУ, и аппаратно пробрось ($Map$) их на Сервер $X$. И еще $1 \ TB$ на Сервер $Y$". 
    Операционные системы Серверов $X$ и $Y$ загружают драйверы CXL hot-plug, и ВНЕЗАПНО видят, что у них "появилась" новая $NUMA$ нода локальной памяти. Они делают в нее `malloc()`. 
*   *18:00 Вечера:* Нагрузка на БД падает. Сервера $X/Y$ ужимают свою кучу и отдают страницы. Fabric Manager шлет Де-аллокацию: "Отстегнуть $1.5 \ Terabytes$ от $X$ и отдать их запущенному кластеру Ночного Видео-Рендеринга на Сервере $Z$!".
*   *Latency Penalty:* Проход через $CXL Switch$ добавляет всего около $\approx 50 - 80 \ Наносекунд$ задержки (Flit routing). Итого Сервер общается с "Чужой" Корзиной ОЗУ по оптике с задержкой в $200 \ ns$ - это почти не отличимо от похода в чужой сокет (Remote NUMA) на старой классической материнской плате ($150 \ ns$).

### 5.3. Memory Sharing (Разделяемая Коммуналка - CXL 3.0) 
$CXL \ Pool$ разделяет физический Кремний, но логически каждый кусок отдан только *одному* Серверу (Exclusive).
Версия **CXL 3.0** разрешила **Memory Sharing**.
ОДИН физический байт (Address $0xAAAA$) внутри Корзины Памяти MLD может быть привязан к Серверу $X$ и к Серверу $Y$ ОДНОВРЕМЕННО.
*   Они могут читать и писать туда как в коммунальной квартире.
*   Аппаратный протокол $CXL.cache$ через коммутатор гарантирует (Snoop Filter Tracking), что если Сервер $X$ запишет единичку в общий байт, L3 Кеши Сервера $Y$ мгновенно инвалидируются. Мы получаем Shared-Memory Базу Данных, распределенную по независимым Физическим серверам БЕЗ ИСПОЛЬЗОВАНИЯ Сегментов $TCP/IP / Ethernet / Sockets$ в принципе! Это конец эпохи Microservices RPC-вызовов (gRPC/REST) для In-Memory агрегации.

## 6. Processing-in-Memory (PIM): Переворот Фон Неймана

В классической Вычислительной Системе (Архитектура Фон Неймана), Центральный Процессор (CPU/GPU) — это "Король", а Память (DRAM) — это "Пассивный Раб". 
Если Король хочет сложить массив из $1 \ Миллиарда \ Элементов$, Раб обязан упаковать каждый из миллиарда элементов в $64-байтные \ Cache \ Lines$, сжечь огромное количество Ватт электроэнергии ($pJ/byte$), перегоняя их по длинным медным мостам шины материнской платы в Кэши Процессора, чтобы Королевский транзистор $ALU$ сделал математическое сложение, и потом Раб принял результат обратно.

В BigData Эпохе (Рекоммендательные графы $Meta$, LLM Инференс) перекос стал чудовищным. Процессор $CPU$ 99% времени ПРОСТАИВАЕТ, ожидая пока Раб перетащит данные. $Bandwidth$ уперся в стену ($Memory \ Wall$). Мы вынуждены сжигать серверное электричество на транспортировку, а не на само вычисление. 

Развязка проблемы: **Раз Data-Gravity (Гравитация Данных) не дает нам тащить Данные к Коду, мы отправим Код к Данным!**

### 6.1. Архитектура UPMEM: DPU внутри Банки 

Концепция $Processing-In-Memory \ (PIM)$ или $Processing-Near-Memory \ (PNM)$ в индустрии реализуется компаниями $Upmem$, $Samsung$ (HBM-PIM, AXIOM), $SK \ Hynix$ (AiM). Разберем классический подход (UPMEM):

Мы не строим новую шину. Мы меняем саму планку $DDR4/DDR5$.
*   Мы заглядываем под микроскоп физического Кремния чипа Памяти. $DRAM$ нарезана на квадратики $Bank-ов \ (M-RAM \ \sim \ 64 \ MB)$. Рядом с матрицей Конденсаторов каждого такого Банка инженеры высвобождают жалкие $\sim 2 \ mm^2$ площади.
*   На эту микро-площадь они намертво спаивают **Компьютер в миниатюре (DPU - Data Processing Unit)**. Это 32-битный RISC $in-order$ калькулятор (Аналог старого $ARM \ Cortex-M$). У него есть своя "Оперативка" ($W-RAM \ \sim \ 64 \ KB$) и своя память Инструкций ($I-RAM \ \sim \ 24 \ KB$).
*   Таких микро-процессоров на *Одной планке DDR4 ОЗУ* распаяно до $\sim \ 128 \ Штук$. В сервере их **Тысячи!**.

### 6.2. Программная Парадигма PIM (Как переписать код C++)

Для $Staff-Engineer-а$ интеграция PIM требует фундаментального рефакторинга кода (Host-Accelerated модель в стиле CUDA `C++`).

**Сценарий:** У нас есть Гигантская база Данных ДНК. Нам нужно пропустить её через Regex Regex-Pattern (Поиск Глобальной Строки / Золотоискатели).
1.  **Загрузка данных:** $CPU сервера (Host)$ заливает терабайт ДНК строк в обычные адреса $DDR4$ (Которые физически ложатся в Банки). Каждая часть массива оказывается "рядом" со своим личным $DPU$.
2.  **Диспатчинг Кода (Broadcast Kernel):** Программа на $C++$ (Host) компилирует крошечную функцию Regex-парсера (Байткод занимающий $12 \ KB$). Процессор $CPU$ посылает команду Широковещания (Broadcast) на контроллер Памяти. "Эй, все $DPU$, вот вам бинарный код, проснитесь!".
3.  **Асинхронный Запуск:** Тысячи DPU микро-ядер просыпаются внутри плашек. Они не ходят на материнскую плату! Они начинают молотить байты, лежащие в ВЕРТИКАЛЬНЫХ нанометрах от их $ALU-блоков$, вытаскивая их со скоростью $\sim 1 \ GB/s$ (внутренняя шина каждого банка!). Совокупная Скрытая Пропускная способность (Aggregate Latent Bandwidth) PIM-планок в одном сервере обходит самый мощный $H100$ за $\$30,000$, достигая десятков Террабайт в секунду!
4.  **Смерть $MESI$:** $DPU$ не поддерживают когерентность (Cache Coherence) с $Host-CPU$. Пока DPU считает (PIM Mode Active), $CPU$ Линукса ФИЗИЧЕСКИ ЗАПРЕЩЕНО читать этот Банк памяти. $Memory \ Bank$ заблокирован на уровне транзисторов.
5.  **Сбор Ответов:** $DPU$ нашел кусочек ДНК, записал `ID=15` в свой выходной лог, и уснул. Контроллер Пим-планки делает Interupt в $CPU$, процессор Линукса снова получает владение Банком, и собирает "Ответы" (Результаты MapReduce). Электроэнергия спасена в десятки раз, Latency сжата.

*Ограничения:* Вы не можете запустить на $PIM$ Глобальную сортировку ($QuickSort$). $DPU \ \text{№1}$ не имеет понятия о существовании $DPU \ \text{№2}$ в соседнем банке. Они полностью Слепы Друг к Другу (Zero Cross-Communication). $PIM$ идеален для $Embarrassingly \ Parallel$ задач (Векторный поиск, сканирование Таблиц Баз данных).

## 7. Многоэтажка Linux: Tiered Memory и Авто-NUMA Балансировка

В Стойке 2030 года Сервер несет в себе полный франкенштейн-набор слоев:
1. $L3$ Процессорный Кеш. 
2. Напаянный $HBM$ Куб (Быстрый, $High \ Bandwidth \ Memory$, как $Tier \ 1$).
3. Локальные Слоты $DDR5$ (Обычный, $Tier \ 2$).
4. Огромная прицепная Корзина $CXL.mem \ MLD$ (Медленный, $Tier \ 3$, $Scale-out \ Box$).
5. $NVMe-over-Fabric \ SSD \ Drives$ (Archive, $Swap$, $Tier \ \infty$).

### 7.1. Cgroups и Архитектура Слоев
Как Программисту на $Python \ / \ Go$ управлять всем этим зоопарком без переписывания софта? Никак.
Все делает Операционная Система (Ядро Linux $Kernel \ 6.x+$). 
*Система инициализации ACPI/SRAT:* Linux Kernel при загрузке опрашивает ACPI (Firmware сервера). Ему выдается матрица **$SLIT (System \ Locality \ Information \ Table)$**. Это таблица "Штрафов" (Расстояний). Если $CPU_0$ читает свою $HBM \ \rightarrow \ Distance=10$. Если $DDR5 \ \rightarrow \ 20$. Если чужой $CXL \ \rightarrow \ 50$.
*Линукс создает Абстракцию НОД (Memory Nodes).*
Когда вы делаете `malloc()` или `List.add()`, Менеджер Памяти Линукса (Buddy Allocator) использует $Watermark \ Policy$: "Сначала набей до отказа самую быструю Локальную $NUMA \ Node \ (HBM)$, если кончилась — Лей страницы в Ноду Дальнюю $DDR5$, если кончилась — Лей в $CXL$".

### 7.2. Page Demotion (Понижение в должности)
Это работа **Kswapd (Kernel Swap Daemon)**. В классическом $Linux$, когда память кончалась, `kswapd` просыпался и судорожно выгружал страницы памяти $RAM$ прямо на медленный магнитный жесткий диск (Трагический $Swap \ Storm \ / \ OOM Killer$).
В $Tiered \ Memory$, $kswapd$ занимается **Demotion (Скидыванием)**. "Я вижу, что этот кусок массива $Java$ никто не читал 10 минут. Я не буду убивать сервер. Я деликатно перемещу (поменяю физический адрес) из $DDR5 \ Node$ в дальнюю дешевую $CXL \ Node$!". Для Java это незаметно (Виртуальный адрес не поменялся). Память в основном сервере высвободилась под полезную нагрузку биржевого $HFT$ робота.

### 7.3. AutoNUMA Promotion (Карьерный Лифт Данных)
Страница 4KB уехала в "грязный" CXL. Спустя час Приложение внезапно начинает крутить цикл обработки данных прямо по этим адресам. Латентность у приложения падает, процессор ловит $Stall$-ы.
*   *Детектив Ядра:* Ядро Линукса периодически (Раз в Секунду) хитро снимает (Unmap) флаг присутствия со случайных страниц. Когда ваше приложение по ним стукает, CPU ловит $Minor \ Page \ Fault$ прерывание. Линукс перехватывает его, записывает в Блокнот (Statistics Matrix): "Ага, страница $0xAAAA$ стала Горячей (Hot)!".
*   *Действие Архитектора:* Демон **AutoNUMA Balancing** просыпается. Значит, данные в CXL "ожили"! Демон тихонько в фоне запускает Аппаратный $DMA-Копир$, который перетаскивает эти $4KB$ физически обратно из $CXL$ прямо в самую быструю $HBM \ Memory \ Tier \ 1$.
*   *Итог:* Ваши структуры данных "Дышат" и путешествуют по материнским платам ЦОДа сами по себе, повинуясь градиентам теплоты использования (Heat Maps). $Staff-Engineer$ должен только правильно настроить лимиты в `/sys/kernel/mm/numa/` и радоваться эластичности железа.

## 8. Scale-out RDMA: Оптический DMA Замкнутого Цикла Датацентра

Мы разобрались, как память балансируется внутри стойки сервера ($Scale-Up \ / \ CXL$). Если вам нужно выйти за предел Стойки (Например Обучение Нейросети GPT4 на 20,000 Северов, расположенных в разных рядах ЦОДа), $CXL$ не дотянется (Длина сигнала CXL ограничена кабелем $\sim 20$ метров).
Тут в игру вступает **RDMA (Remote Direct Memory Access)** поверх Сети $Ethernet/Infiniband$ (Стандарт **RoCEv2**).

### 8.1. Секрет Скорости: Bypassing TCP/IP (Queue Pairs)
В обычных микросервисах (Spring Boot, Go HTTP) вы шлете JSON из Сервера А на Сервер В. Пакет проходит $User \ Space \ \rightarrow \ Kernel \ Space$ (Ядерный контекст Линукса) $\rightarrow \ TCP \ Stack$ (Сборка окна, проверка Контрольных сумм) $\rightarrow \ Driver \ \rightarrow \ NIC$.
Задержка такого маршрута - сотни Миллисекунд (из-за $Context \ Switch$ тактов $CPU$).
*   **Архитектура Queue Pairs (QP):** RDMA убивает $TCP/IP$. При инициализации Приложения $A$, оно регистрирует кусок своей Оперативной памяти (Memory Region регистрация `ibv_reg_mr()`) "жестко сцепив" его с Сетевой Картой NIC (SmartNIC). 
*   Операционная система Линукса ОТОДВИГАЕТСЯ.
*   Приложение создает две Очереди (Send Queue и Recv Queue — Queue Pair), которые лежат на памяти приложения, но в которые ИМЕЕТ АППАРАТНЫЙ ДОСТУП Сетевая Карта. Приложение просто кладет Рабочий Пакет (WQE) в очередь. Сетевая Карта забирает его, превращает в Оптический Свет и стреляет в Свитч. Задержка $\sim 0.5 \ \mu s$. ЦПУ освобожден! 

### 8.2. Односторонняя Магия: RDMA Read / RDMA Write
Классические RPC $Socket$ сети — это Двухсторонний Контракт. Сервер А шлет `Send`. Сервер В обязан запустить Процесс $CPU$, чтобы сделать `Recv()`.
RDMA ломает эту парадигму (Тот самый $Direct \ Memory \ Access$).
*   **RDMA One-Sided Operation:** Сервер А, обладая Правами и Токенами ($R_Key$), приказывает Сетевой карте Сервера $A$: "Пойди и Запиши Массив '1024 Байта' прямо в физический адрес `0xBADBEEF` на Сервере В!".
*   Сетевая карта Сервера В (ConnectX-7) Ловит Оптический пакет. Она сама, БЕЗ прерываний (No Interrupts), БЕЗ пробуждения $CPU$ Сервера В, через шину $PCIe$ материнской платы внаглую пролазит в Планки $DDR5$ сервера В, и записывает туда эти 1024 байта!
*   Программа на Сервере В даже не знала, что по Сети что-то пришло. Просто переменная в её массиве вдруг изменила значение за $\sim 1 \mu s$! 

### 8.3. Итог: Кластер как Единый Организм (PFC и Потеря Пакетов)
Без RDMA протокола не существовало бы Распределенного $PyTorch$-а ($DistributedDataParallel$). Градиенты обучения не смогли бы синхронизироваться на тысячах $H100$-нодах. Карточки Nvidia переговариваются друг с другом через Опто-Свитчи вообще минуя $x86$ процессоры Либеральных серверов (Технология $GPU-Direct \ RDMA$).
*   **Цена Технологии (Контроль Потока):** $TCP/IP$ умеет замедляться, если пакеты теряются. $RDMA$ не имеет права терять пакеты (Иначе Жесткий Сброс Коннекта Go-Back-N, убивающий всю скорость). Сетевые Коммутаторы (Arista/Mellanox Switches) в ЦОД для RDMA обязаны поддерживать **PFC (Priority Flow Control)** — если буфер свитча переполнен, он кричит аппаратно Серверам: "ПАУЗА!". Это "Святая Сеть" без потерь ($Lossless \ Ethernet$).

### Гранд-Финал Лекции Memory Architecture
Парадоксально, но чем быстрее становятся Вычислители ($CPU/GPU$), тем сильнее Инженерия превращается в "Логистику Перемещения Байт". Staff Инженер обязан смотреть сквозь абстракции кода Языков Программирования. 
Оператор присваивания $A = B$ маскирует под собой Драму $Bank \ Conflicts$ внутри $DDR5$, Температурные локи $Refresh \ Cycles$, Перемещение по Иерархии Линукса Вплоть до $CXL \ Фабрик$, и Односторонние Инъекции через $RDMA$. Ваша Зарплата зависит от того, насколько близко Вы сможете положить $A$ и $B$ друг к другу в физическом кремниевом пространстве.

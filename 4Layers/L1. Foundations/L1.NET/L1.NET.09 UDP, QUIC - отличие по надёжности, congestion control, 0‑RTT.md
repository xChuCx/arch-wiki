**TL;DR**:
*   **UDP** — это "сырая глина". В нем нет ничего, кроме портов и чексуммы. Используется, когда вам нужна полная свобода (свой протокол) или когда потеря пакетов допустима (VoIP, DNS).
*   **QUIC** — это "космический корабль", построенный из глины UDP. Это **надежный**, **защищенный**, **мультиплексированный** транспорт, который работает в Userspace, обходя ограничения ядер ОС ("оссификацию").
*   **0-RTT** — это возможность отправить запрос *вместе* с рукопожатием. Это невероятно быстро, но открывает дыру безопасности (Replay Attacks), если архитектор не понимает семантику идемпотентности.

## 1. UDP (User Datagram Protocol): Архитектурный анализ примитива [RFC 768]

Для Staff Engineer UDP — это не просто «ненадёжный протокол». Это **Message-Oriented** (ориентированный на сообщения) транспорт с минимальным оверхедом, который перекладывает ответственность за управление состоянием сети с ядра операционной системы (Kernel Space) на приложение (User Space).

### 1.1. Фундаментальные отличия: Stream vs Datagram
В отличие от TCP, который предоставляет абстракцию "бесконечного потока байт" (Byte Stream), UDP работает с **дейтаграммами**.
*   **Сохранение границ (Message Boundaries):** Если вы отправите через UDP 50 байт, а затем 100 байт, получатель гарантированно считает сначала 50, потом 100 (два вызова `recvmsg`). В TCP эти данные могут склеиться или разбиться (TCP Segmentation), и приложению нужно парсить поток.
*   **Отсутствие состояния (Stateless):** Ядро не хранит TCB (Transmission Control Block) для UDP "соединения".
    *   *Инсайт:* Вы можете вызвать `connect()` на UDP сокете. Это **не вызовет** сетевого трафика (рукопожатия), но зафиксирует фильтр в ядре: сокет будет принимать пакеты только с указанного IP/Port и позволит использовать `send()` вместо `sendto()`. Это оптимизация производительности (меньше проверок маршрутизации при каждой отправке).

### 1.2. Анатомия заголовка и Overhead
Заголовок UDP экстремально компактен — всего **8 байт** (против 20-60 байт у TCP).
1.  **Source Port (2 байта)** — опционально.
2.  **Destination Port (2 байта)**.
3.  **Length (2 байта)** — длина заголовка + данных.
4.  **Checksum (2 байта)** — проверка целостности (CRC-16 complement).

**Архитектурное следствие:**
Для коротких сообщений (например, метрики StatsD или DNS-запросы) оверхед TCP (Handshake + Teardown + Header) может превышать полезную нагрузку в разы. UDP здесь дает минимальную латентность и нагрузку на сеть.

### 1.3. Проблема MTU и IP Fragmentation
Это самая частая причина "мистических" потерь UDP пакетов в продакшене.
*   **MTU (Maximum Transmission Unit):** Обычно 1500 байт (Ethernet).
*   Если вы отправите UDP пакет размером 4000 байт, IP-уровень разобьет его на 3 фрагмента (IP Fragmentation).
*   **Катастрофа:** Если **хотя бы один** фрагмент потеряется, весь UDP пакет будет отброшен на уровне IP сборки получателя. UDP не умеет перепосылать отдельные фрагменты.
*   **Решение эксперта:** Никогда не полагайтесь на IP-фрагментацию.
    *   Используйте **Path MTU Discovery** (сложно с UDP, так как ICMP часто блокируют).
    *   Либо жестко ограничьте размер пейлоада безопасным значением (например, **512 байт** для старого DNS, **1200-1400 байт** для современных сетей с учетом инкапсуляции вроде VXLAN).

### 1.4. Отсутствие Congestion Control (CC) и Flow Control
*   **Flow Control (Управление потоком):** Защита *получателя* от переполнения. В TCP это Window Size. В UDP этого нет: если приложение не успевает читать из буфера сокета (`SO_RCVBUF`), ядро молча дропает новые пакеты.
    *   *Метрика:* `netstat -su` или `/proc/net/udp` (колонка `RcvbufErrors` / `drops`).
*   **Congestion Control (Управление перегрузкой):** Защита *сети* от переполнения. UDP не реагирует на потерю пакетов снижением скорости.
    *   *Риск:* Одно плохо написанное UDP-приложение может положить гигабитный канал ("UDP Flood"), вызвав packet loss для всех соседей, включая TCP (который "вежливо" снизит скорость).
    *   *Требование RFC:* Протоколы поверх UDP (как QUIC или WebRTC) **обязаны** реализовывать свой CC в userspace.

### 1.5. Почему UDP — король High-Performance (HFT, Gaming, DC)
1.  **Kernel Bypass & Zero Copy:**
    Обработка TCP стека в ядре Linux стоит дорого (контекстные переключения, локи). С UDP проще работать через технологии обхода ядра (DPDK, XDP, Solarflare OpenOnload). В High-Frequency Trading (HFT) это экономит микросекунды.
2.  **Multicast (Групповая рассылка):**
    Только UDP поддерживает мультикаст (IGMP). Если вам нужно отправить рыночные котировки 1000 подписчикам одновременно, TCP заставит вас отправить данные 1000 раз. UDP Multicast — один раз, а свитчи размножат пакеты.
3.  **Отсутствие Head-of-Line (HoL) Blocking:**
    *   *Сценарий:* Вы стримите видео (WebRTC/RTP). Пакет с кадром №50 потерялся.
    *   *В TCP:* Плеер замрет (буферизация), пока кадр №50 не будет перепослан, даже если кадры 51, 52, 53 уже пришли.
    *   *В UDP:* Плеер просто пропустит кадр 50 (артефакт на экране) и покажет 51, 52... **Latency важнее целостности.**

### 1.6. Use Case: Инкапсуляция в ЦОД (VXLAN, Geneve)
В современных облаках (AWS, Kubernetes) ваша сеть — виртуальная (Overlay).
Она строится поверх физической сети (Underlay) с помощью туннелирования.
Используется **UDP**, а не TCP.
*   **VXLAN (Virtual Extensible LAN):** Ethernet-кадр упаковывается в UDP-пакет.
*   *Почему UDP:* Физические свитчи используют хеш от заголовков (Source IP, Dest IP, **Source Port**, Dest Port) для балансировки нагрузки (ECMP - Equal-Cost Multi-Path).
*   VXLAN меняет Source Port для каждого потока, заставляя физическую сеть "размазывать" трафик по всем доступным кабелям. С TCP или GRE это было бы сложнее.

### Резюме раздела
UDP — это **транспорт без гарантий, но с максимальным контролем**.
*   Используйте его, когда **актуальность** данных важнее их **полноты** (VoIP, FPS игры).
*   Используйте его как "подложку" для создания собственных гарантий (QUIC, KCP, Reliable-UDP), если TCP вас не устраивает (например, в спутниковых сетях с огромным RTT).
*   Всегда помните про MTU и буферы сокетов.

## 2. QUIC (Quick UDP Internet Connections): Глубокий анализ

QUIC — это не просто "TCP поверх UDP". Это попытка переосмыслить 40 лет эволюции транспортных протоколов и решить фундаментальную проблему Интернета — **Оссификацию (Ossification)**.

### 2.1. Проблема Оссификации и "Middlebox Interference"
**Определение:** *Оссификация* — это потеря гибкости сетью.
Маршрутизаторы, NAT-шлюзы и корпоративные DPI (Deep Packet Inspection) "выучили", как выглядит TCP-пакет (заголовок, флаги SYN/ACK, Sequence Numbers). Если вы попытаетесь добавить в TCP новое расширение (например, TCP Fast Open), многие Middleboxes просто дропнут такой пакет, потому что он "выглядит подозрительно" или не соответствует их жестко зашитой логике 10-летней давности.

**Решение QUIC:**
*   QUIC инкапсулируется в **UDP**. Для сети это просто "шум" (payload) внутри UDP пакетов.
*   **Все заголовки, кроме минимальных флагов, зашифрованы.** Middlebox не видит Sequence Numbers, не видит ACK-ов, не видит данных. Он видит только непрозрачный поток байтов.
*   Это возвращает контроль над транспортным протоколом от производителей железа (Cisco, Juniper) к разработчикам приложений (End-to-End principle).

---
### 2.2. Архитектура пакета и Packet Numbers (Монотонность)

В TCP `Sequence Number` выполняет две функции:
1.  Порядок данных (reassembly).
2.  Идентификация пакета для логики перепосылки (retransmission).

В QUIC эти понятия **разделены**, что устраняет критическую уязвимость TCP.

#### Терминология:
*   **Packet Number (PN):** Уникальный номер физического пакета UDP.
*   **Stream Offset:** Смещение байта данных внутри логического потока.

#### Механизм Strictly Monotonic PN:
В QUIC номер пакета **всегда возрастает**.
*   **Сценарий:** Вы отправляете пакет с `PN=10`, содержащий данные "ABC".
*   Пакет потерян.
*   **TCP:** Вы перепосылаете пакет с тем же `Seq=10` и данными "ABC".
    *   *Проблема (Retransmission Ambiguity):* Если приходит ACK, отправитель не знает, подтверждает ли он первую попытку (RTT огромный) или вторую (RTT маленький). Это ломает Congestion Control.
*   **QUIC:** Вы перепосылаете данные "ABC", но в новом пакете с `PN=11`.
    *   Фрейм внутри пакета говорит: "Это данные со смещением 0".
    *   Если приходит ACK на `PN=11`, мы точно знаем RTT. Если на `PN=10` — тоже точно знаем.

**Зачем это нужно (Security):** Packet Number используется как **Nonce** (одноразовое число) для шифрования (AEAD). Повторное использование Nonce с одним ключом ломает криптографию. QUIC запрещает повторение PN.

---
### 2.3. Streams & Multiplexing (Убийство HoL Blocking)

Это главная фича для HTTP/3.

#### Head-of-Line (HoL) Blocking в HTTP/2 (TCP):
TCP представляет собой **один** линейный поток байтов.
*   Пример: Вы грузите `style.css` (маленький) и `video.mp4` (большой).
*   Если теряется **один** пакет от `video.mp4`, ядро ОС (TCP Stack) замораживает **весь** буфер приема.
*   Браузер не получит `style.css`, даже если он уже пришел полностью, пока не будет восстановлен потерянный пакет видео. Одна потеря тормозит всё.

#### Независимость в QUIC:
QUIC вводит понятие **Stream** как первоклассного гражданина транспортного уровня.
*   Один UDP-пакет может нести фреймы (frames) от разных потоков: `{Stream 1, Offset 500, Data...}, {Stream 5, Offset 0, Data...}`.
*   Если теряется пакет с куском `Stream 1`, доставка `Stream 5` **не блокируется**. Приложение получает данные `Stream 5` мгновенно.

**Типы потоков:**
1.  **Uni-directional:** Односторонний (например, сервер пушит данные).
2.  **Bi-directional:** Двусторонний (классический Request-Response).

---
### 2.4. Flow Control (Двойная плотина)

Не путать с *Congestion Control* (который защищает сеть от перегрузки). **Flow Control** защищает *получателя* от переполнения буфера памяти.
В QUIC он двухуровневый (похож на SSH):

1.  **Stream-level Flow Control:**
    *   "На потоке №5 я готов принять еще 10 КБ".
    *   Защищает от ситуации, когда один "тяжелый" запрос (скачивание ISO-образа) съедает всю память, не давая обработать легкие JSON-запросы.
2.  **Connection-level Flow Control:**
    *   "Суммарно по всем потокам я готов принять еще 1 МБ".
    *   Защищает глобальный буфер соединения.

**Пример:** Если приложение перестало вычитывать данные из сокета для `Stream 5`, отправитель остановит передачу только `Stream 5`, но продолжит слать данные для `Stream 7`, пока позволяет глобальное окно (Connection window).

---
### 2.5. Handshake: 1-RTT Setup и TLS 1.3

В стеке TCP+TLS рукопожатия идут последовательно: сначала TCP SYN/ACK (1 RTT), потом TLS ClientHello/ServerHello (еще 1-2 RTT).
QUIC объединяет транспортное и криптографическое рукопожатие.

1.  **Initial Packet:** Клиент отправляет пакет, содержащий и параметры транспорта (версия QUIC, Flow Control limits), и криптографию (`TLS ClientHello`).
2.  **Server Response:** Сервер отвечает сертификатом и транспортными параметрами.
3.  **Итог:** Соединение установлено и зашифровано за **1 RTT**.

**Anti-Amplification Limit (Защита от DDoS):**
Поскольку UDP не проверяет обратный адрес (нет SYN-ACK), злоумышленник мог бы отправить маленький пакет от имени жертвы (Source IP Spoofing), и сервер QUIC ответил бы жертве огромным сертификатом.
*   **Правило RFC 9000:** До тех пор, пока адрес клиента не подтвержден, сервер не имеет права отправить данных больше, чем в **3 раза** больше объема полученных данных.

---
### 2.6. Connection Migration (Миграция без разрывов)

Это фундаментальное отличие от TCP.

*   **TCP:** Идентификатор соединения — **4-tuple** `{SrcIP, SrcPort, DstIP, DstPort}`. Смена IP (Wi-Fi -> LTE) меняет 4-tuple $\to$ соединение мертво.
*   **QUIC:** Идентификатор — **Connection ID (CID)** (набор байтов в заголовке).

**Сценарий (Смартфон переходит с Wi-Fi на 4G):**
1.  Клиент меняет физический интерфейс. IP-адрес меняется.
2.  Клиент отправляет QUIC-пакет с нового IP, но с **тем же Destination CID**.
3.  Сервер видит новый Source IP, но узнает CID в своей таблице сессий.
4.  Сервер продолжает обрабатывать поток данных, просто обновляя маршрут ответа на новый IP.
5.  **Path Validation:** Чтобы предотвратить атаку (злоумышленник подставил IP жертвы и "украл" сессию), сервер запускает процедуру проверки пути: отправляет `PATH_CHALLENGE` (случайные байты) на новый IP и ждет `PATH_RESPONSE`.

---
### 2.7. Резюме: Сравнение "в лоб"

| Характеристика | TCP + TLS / HTTP/2 | QUIC / HTTP/3 |
| :--- | :--- | :--- |
| **Пространство** | Kernel Space (ядро ОС) | **User Space** (библиотека приложения) |
| **Handshake** | 2-3 RTT | **1 RTT** (или 0-RTT) |
| **Head-of-Line Blocking**| Да (на уровне соединения) | **Нет** (потоки независимы) |
| **Идентификация** | IP + Port (4-tuple) | **Connection ID** (устойчив к смене IP) |
| **Шифрование** | Только Payload (TLS) | **Payload + Headers** (даже Packet Numbers) |
| **Эволюция** | Годы (обновление ядер ОС) | **Дни** (апдейт приложения) |

Для архитектора переход на QUIC означает, что вы берете на себя ответственность за CPU (шифрование и обработка пакетов теперь в процессе приложения, а не в ядре), но получаете полный контроль над качеством доставки.

## 3. Deep Dive: Congestion Control в QUIC (RFC 9002)

В мире TCP алгоритм контроля перегрузки — это религия ядра Linux. Чтобы обновить алгоритм, вам нужно обновить ядро на миллионах серверов. В QUIC контроль перегрузки вынесен в **Userspace**. Это архитектурная революция, дающая полный контроль над тем, как байты заполняют канал (The Pipe).

### 3.1. Улучшенная телеметрия (Richer Signals)

Эффективность любого CC алгоритма зависит от качества входных данных (Input Signals). TCP страдает от шума. QUIC этот шум фильтрует.

1.  **Разделение Network RTT и Host Delay (`ack_delay`):**
    *   *Проблема TCP:* Если приемник занят (GC, CPU spike) и отправляет ACK с задержкой 50мс, отправитель TCP думает, что сеть тормозит (RTT вырос), и снижает скорость.
    *   *Решение QUIC:* Фрейм `ACK` в QUIC явно содержит поле `ACK Delay` — время, которое прошло между получением пакета и отправкой подтверждения.
    *   *Алгоритм:* $\text{NetworkRTT} = \text{SampleRTT} - \text{PeerACKDelay}$.
    *   *Результат:* CC не паникует из-за тормозов процессора на клиенте, реагируя только на реальные заторы в сети.

2.  **Монотонность номеров пакетов (No Retransmission Ambiguity):**
    *   Как упоминалось ранее, даже при ретрансмиссии QUIC использует новый Packet Number.
    *   *Инсайт:* Это позволяет строить **идеально чистую карту потерь**. Мы точно знаем, какой пакет потерян, а какой задержался. Это критично для алгоритмов, чувствительных к задержкам (delay-based CC, например, BBR).

3.  **ECN (Explicit Congestion Notification) "First-Class Citizen":**
    *   В TCP поддержка ECN часто ломается мидлбоксами. QUIC шифрует заголовки (кроме пары бит), но корректно пробрасывает ECN-метки из IP-заголовка в зашифрованные ACK-фреймы. Это позволяет маршрутизаторам сигнализировать о перегрузке *до* начала дропа пакетов.

### 3.2. Pluggable & Per-Stream Algorithms

Поскольку CC — это код в вашем бинарнике, вы можете выбирать стратегию поведения.

*   **CUBIC (RFC 8312):** Стандарт де-факто. Агрессивно растет до момента потери пакета, затем резко снижает окно (`cwnd`) и быстро восстанавливается по кубической функции. Хорош для Bulk Data Transfer, но заполняет буферы (Bufferbloat).
*   **BBR (Bottleneck Bandwidth and Round-trip propagation time):** Алгоритм от Google. Не реагирует на потери пакетов как на сигнал к торможению (потери могут быть фоновыми). Он строит модель канала: измеряет пропускную способность (BtlBw) и минимальную задержку (RTprop).
    *   *Сценарий эксперта:* Для соединения, передающего **Live Video**, вы включаете BBR (чтобы минимизировать задержку и буферизацию). Для соединения, качающего **обновление прошивки** в фоне, вы можете оставить CUBIC или LEDBAT. В QUIC это делается `connection.setCongestionControlAlgorithm(Alg.BBR)`.

### 3.3. Pacing (Пейсинг): Убийца микробёрстов

Это, пожалуй, самое важное отличие реализации QUIC от классического TCP.

**Проблема (Micro-bursts):**
В классическом TCP, когда приходит ACK, подтверждающий получение большого куска данных, окно перегрузки (`cwnd`) открывается, и сервер мгновенно выплевывает пачку пакетов (например, 64KB за 10 мкс).
*   Маршрутизаторы имеют маленькие буферы (shallow buffers). Такой "взрыв" пакетов переполняет буфер, вызывая дропы.
*   Получается "пилообразный" график скорости и потери на ровном месте.

**Решение QUIC (Pacing):**
RFC 9002 настоятельно рекомендует (SHOULD) использовать пейсинг.
*   Отправитель вычисляет текущую скорость доставки (например, 100 Мбит/с).
*   Вместо отправки 10 пакетов мгновенно, он ставит их в микро-таймеры: отправить пакет, подождать $\Delta t$, отправить следующий.
*   $\Delta t = \text{PacketSize} / \text{PacingRate}$.
*   **Результат:** Трафик течет как вода из шланга, а не вылетает кусками. Снижается Packet Loss, растет Throughput на "шумных" сетях.

### 3.4. Recovery: RACK-TLP вместо "3 Dup ACKs"

TCP исторически использует эвристику: "Если пришли 3 дубликата ACK, значит пакет потерян". Это плохо работает, если окно маленькое или потери массовые (Tail Drop).

QUIC нативно реализует логику **Time-based Loss Detection** (аналог RACK-TLP в Linux TCP, но "из коробки"):
*   Если пакет $X$ не подтвержден, а пакет $X+n$, отправленный позже, уже подтвержден, И прошло времени больше чем $\text{RTT} + \text{TimeThreshold}$ — пакет $X$ считается потерянным.
*   Это позволяет обнаруживать потери быстрее и восстанавливаться (Fast Retransmit) даже в конце передачи данных (Tail Loss), когда новых пакетов для провоцирования ACK уже нет.

### 3.5. Пример для наглядности

Представьте, что вы скачиваете файл через нестабильный Wi-Fi в кафе.

1.  **Сценарий TCP:**
    *   Wi-Fi лагает на 200мс.
    *   TCP на сервере видит задержку ACK, думает "Затор!", режет скорость в 2 раза (CUBIC).
    *   Wi-Fi "отлипает", прилетает пачка ACK.
    *   TCP выстреливает burst пакетов. Роутер кафе захлебывается и дропает их.
    *   Скорость падает до нуля, соединение "висит".

2.  **Сценарий QUIC (BBR + Pacing + ACK Delay):**
    *   Wi-Fi лагает. Клиент шлет ACK с полем `ACK Delay = 200ms`.
    *   Сервер видит: RTT сети не изменился, просто клиент тупил. Скорость **не снижается**.
    *   Сервер использует Pacing, отправляя пакеты равномерно, пролезая в узкий буфер роутера кафе.
    *   Даже если пакет потерялся, уникальный Packet Number позволяет перепослать только его, не тормозя остальные стримы (картинки грузятся, даже если текст подвис).

**Вывод:** Congestion Control в QUIC — это хирургический инструмент, а не кувалда.

## 4. 0-RTT (Zero Round Trip Time): Скорость vs Безопасность

Для Staff Architect 0-RTT — это не просто "быстрое подключение". Это архитектурный компромисс между латентностью, защитой от повторов (Anti-Replay) и совершенной прямой секретностью (Forward Secrecy).

### 4.1. Механика: Как это работает "под капотом"

В стандартном TLS 1.3 (и QUIC) для начала шифрованной передачи требуется обмен ключами (обычно Ephemeral Diffie-Hellman), что занимает 1 RTT (путь туда-обратно).

**0-RTT Resumption (Возобновление сессии):**
Чтобы отправить данные *вместе* с первым пакетом (`ClientHello`), клиент должен заранее знать ключ шифрования.
1.  **Session Ticket (Билет сессии):** При *предыдущем* соединении сервер отправляет клиенту сообщение `NewSessionTicket`. Это зашифрованный блоб, содержащий параметры для восстановления сессии (PSK — Pre-Shared Key).
2.  **Derivation (Вывод ключа):** Клиент использует этот PSK, чтобы вывести ключи шифрования для "ранних данных" (Early Data).
3.  **Attack Surface:** Сервер *еще не участвовал* в генерации ключей для этого конкретного нового соединения (он еще не прислал свой `ServerHello` со случайным числом `Random` или своей частью Diffie-Hellman). Он просто получает пакет, зашифрованный ключом, о котором договаривались "в прошлый раз".

**Сравнение потоков:**

*   **1-RTT (Standard):**
    1.  Client: `ClientHello` (хочу говорить)
    2.  Server: `ServerHello` + `Keys` (вот параметры) — **Прошел 1 RTT**
    3.  Client: `Finished` + `HTTP Request` (GET /index)
*   **0-RTT (QUIC):**
    1.  Client: `ClientHello` + `Early Data` (GET /index) — **0 RTT до отправки запроса**

### 4.2. Главная угроза: Replay Attacks (Атаки повторного воспроизведения)

В стандартном рукопожатии сервер отправляет клиенту уникальное случайное число (`Server Random` / `Nonce`) *до* того, как клиент отправит данные. Это гарантирует уникальность сессии. В 0-RTT клиент отправляет данные *до* получения чего-либо от сервера.

**Сценарий атаки:**
1.  **Алиса** отправляет запрос "Перевести $100 Бобу" в режиме 0-RTT через публичный Wi-Fi.
2.  **Ева** (злоумышленник) перехватывает этот зашифрованный UDP-пакет. Ева не может его расшифровать (ключа у нее нет), но пакет валиден.
3.  **Ева** отправляет копию этого пакета серверу банка еще 5 раз.
4.  **Сервер Банка:**
    *   Получает пакет Евы.
    *   Проверяет Session Ticket — он валиден и выпущен этим сервером.
    *   Расшифровывает данные корректным ключом.
    *   **Результат:** Сервер выполняет транзакцию 5 лишних раз.

**Почему это происходит:** У сервера на сетевом уровне нет контекста, чтобы отличить оригинал Алисы от копии Евы, так как в 0-RTT нет предварительного "рукопожатия уникальности".

### 4.3. Вторая угроза: Отсутствие Forward Secrecy (PFS)

Это нюанс для экспертов по безопасности (SecOps).
*   **1-RTT:** Использует (EC)DHE — эфемерный обмен ключами. Если завтра злоумышленник украдет приватный ключ сервера, он **не сможет** расшифровать перехваченный вчера трафик 1-RTT.
*   **0-RTT:** Шифруется ключом, привязанным к `Session Ticket`. Этот билет обычно шифруется статичным ключом шифрования тикетов (STEK) на сервере.
*   **Риск:** Если злоумышленник украдет STEK сервера, он сможет расшифровать **все перехваченные ранее 0-RTT пакеты**.
*   *Вывод:* Никогда не передавайте особо чувствительные данные (пароли, CVV) в 0-RTT payload.

### 4.4. Стратегии защиты (Architecture Patterns)

Как архитектор, вы должны реализовать защиту на нескольких уровнях.

#### А. Сетевой уровень (Single-use Tickets & Strike Registers)
Сервер должен гарантировать, что один Ticket используется только один раз.
1.  **Sliding Window / Bloom Filter:** Сервер хранит "окно" использованных `ClientHelloRandom` или идентификаторов тикетов.
2.  **Проблема распределенных систем:** Если у вас кластер из 100 бэкендов за L4 балансировщиком, синхронизировать этот стейт ("этот тикет уже был использован") мгновенно невозможно. Ева может отправить копии пакета на разные инстансы.

#### Б. Уровень протокола (RFC 8470) — "Too Early"
Если запрос не идемпотентен, сервер не должен его обрабатывать в 0-RTT.
1.  Сервер получает 0-RTT запрос `POST /pay`.
2.  Сервер видит, что это 0-RTT (по внутренним флагам TLS/QUIC стека).
3.  Сервер отвечает кодом **HTTP 425 Too Early**.
4.  Клиент (браузер/мобильное приложение) понимает этот код, ждет завершения рукопожатия (1-RTT) и автоматически перепосылает запрос уже по защищенному каналу.

#### В. Прикладной уровень (Idempotency)
Это самая надежная защита.
*   **Определение:** Операция $f(x)$ идемпотентна, если $f(f(x)) = f(x)$.
*   **Решение:** Разрешайте 0-RTT **только** для безопасных методов (`GET`, `HEAD`, `OPTIONS`) или методов с ключами идемпотентности.
*   **Header-based routing:** L7 Балансировщик (Nginx, Envoy) добавляет заголовок `Early-Data: 1` к запросам из 0-RTT. Бэкенд-приложение видит этот заголовок и само решает:
    *   Если это `GET /profile` — обработать.
    *   Если это `POST /buy` — реджектнуть (вернуть 425) или потребовать подтверждения.

### 4.5. Пример конфигурации (Mental Model)

Представьте конфигурацию вашего API Gateway:

```yaml
listener:
  protocol: QUIC
  0_rtt_enabled: true
  
routing_policy:
  - method: GET
    allow_early_data: true  # Безопасно, ускоряет загрузку ленты новостей
  
  - method: POST
    path: /api/v1/transfer
    allow_early_data: false # Запрещено! Балансировщик заставит клиента переповторить через 1-RTT
```

### Итоговое резюме по 0-RTT

1.  **Это опасно по умолчанию.** Включайте только с полным пониманием рисков.
2.  **Anti-Replay на сервере не идеален.** В кластерных системах он не дает 100% гарантии.
3.  **Idempotency is King.** Единственная надежная защита — проектирование API так, чтобы повтор запроса не ломал данные.
4.  **Forward Secrecy ограничен.** Не шлите секреты первым пакетом.

## 5. Connection Migration (Миграция соединений): Deep Dive

В классическом стеке TCP/IP соединение жестко привязано к сетевому адресу. QUIC разрывает эту связь, вводя понятие **логического идентификатора соединения**, который живет дольше, чем физический маршрут пакетов.

### 5.1. Проблема: Диктатура 5-tuple
В TCP (и в обычном UDP потоке) соединение уникально идентифицируется кортежем из 5 элементов (часто называют 4-tuple, опуская протокол):
`{SrcIP, SrcPort, DstIP, DstPort, Protocol}`.

*   **Сценарий сбоя:** Пользователь выходит из офиса, смартфон переключается с Wi-Fi (IP: `192.168.1.50`) на LTE (IP: `100.64.0.1`).
*   **Результат в TCP:** `SrcIP` изменился. Сервер получает пакет с нового IP, но со старыми SEQ/ACK номерами. С точки зрения ядра ОС сервера — это мусор или атака. Соединение сбрасывается (RST) или висит до таймаута. Приложение должно создать новый TCP сокет, заново сделать TLS Handshake (2-3 RTT) и восстановить контекст.

### 5.2. Решение QUIC: Connection ID (CID)
QUIC вводит уровень абстракции. Пакеты маршрутизируются сетью по IP, но **обрабатываются эндпоинтом по CID**.

CID — это произвольная последовательность байт (от 0 до 20), которая находится в **открытом** (незашифрованном) заголовке QUIC-пакета (Public Header).

*   **Принцип:** Клиент и сервер договариваются о наборе идентификаторов.
*   **Механизм:** Если IP-адрес клиента меняется, он продолжает отправлять пакеты с тем же (или согласованным новым) CID.
*   **Обработка:** Сервер видит: "Ага, IP новый, но CID `0x4A...` мне знаком, это контекст пользователя Bob". Пакет обрабатывается бесшовно, криптографический контекст (ключи шифрования) остается прежним.

### 5.3. Механика безопасности и Path Validation
Архитектор должен понимать: нельзя просто так разрешить присылать данные с нового IP. Это открывает вектор для **IP Spoofing** и атак усиления.

Злоумышленник может подделать свой IP под IP жертвы и отправить серверу пакет с валидным CID, заставив сервер слать гигабайты видеопотока на IP жертвы.

**Протокол миграции (Active Migration):**
1.  **Detection:** Клиент замечает смену интерфейса (Wi-Fi $\to$ 4G).
2.  **Probing (Path Challenge):** Прежде чем слать полновесные данные, клиент отправляет с нового адреса специальные фреймы `PATH_CHALLENGE` (содержат случайные данные).
3.  **Validation (Path Response):** Сервер должен ответить `PATH_RESPONSE` (с теми же данными) на новый адрес.
4.  **Amplification Limit:** Пока сервер не получил подтверждение владения новым IP, он ограничивает объем отправляемых данных (правило 3x: нельзя отправить больше 3 байт на 1 полученный).

**Инсайт для эксперта:** Это происходит прозрачно для прикладного уровня (HTTP/3). Стрим не прерывается, но пропускная способность (Congestion Window) на новом пути сбрасывается или уменьшается до валидации.

### 5.4. Privacy: Проблема Linkability
Если я буду использовать один и тот же CID `0x1234` и в Wi-Fi, и в 4G, пассивный наблюдатель (SORM, ISP, хакер в кафе) сможет коррелировать мои перемещения. "Человек с ID `0x1234` перешел из сети A в сеть B".

**Решение: Ротация CID**
*   В начале соединения сервер выдает клиенту **пачку** запасных CID через фрейм `NEW_CONNECTION_ID`.
*   При смене сети клиент **обязан** переключиться на новый CID из этого списка.
*   Для наблюдателя это выглядит как совершенно новое соединение с новым ID. Связать их может только сервер, у которого есть таблица маппинга `{CID_1, CID_2, CID_3} -> SessionPtr`.

### 5.5. NAT Rebinding (Скрытая миграция)
Это самый частый кейс, о котором забывают. Вы не меняете сеть, вы просто сидите в Facebook.
1.  NAT провайдера имеет таймаут трансляции (например, 60 секунд UDP idle timeout).
2.  Вы молчали 61 секунду, затем отправили пакет.
3.  NAT может открыть **новый внешний порт** для вашего внутреннего IP.
4.  Для сервера это выглядит как смена `SrcPort`.
5.  В TCP соединение бы умерло. В QUIC это "Unintentional Migration" — сервер видит тот же CID, обновляет путь и продолжает работу. Это критично для стабильности мобильных приложений.

### 5.6. Головная боль Архитектора: Load Balancers (L4 vs L7)

Это самый важный пункт для построения инфраструктуры.

**Проблема ECMP и L4 LB:**
Обычные балансировщики (IPVS, Maglev, аппаратные роутеры) распределяют пакеты на основе хеша 5-tuple.
*   Если клиент сменил IP, хеш изменился.
*   Балансировщик отправит пакет на **другой** бэкенд-сервер.
*   Новый сервер не знает контекста этого CID (ключей шифрования). Соединение разорвется.

**Решения:**
1.  **Connection ID Aware LB:** Балансировщик должен уметь парсить заголовок QUIC (он не зашифрован в этой части) и делать роутинг на основе CID, а не IP.
2.  **Encoded CID (Server-id insertion):** Сервера сами генерируют CID так, чтобы в нем был закодирован их ID (или ID шарда).
    *   *Пример:* Первые 4 байта CID — это ID сервера.
    *   Балансировщик смотрит на эти байты и всегда шлет пакет на нужный хост, независимо от IP клиента.
    *   Существует IETF черновик `QUIC-LB`, стандартизирующий этот подход.

### Пример для наглядности (The Elevator Case)

Вы совершаете видеозвонок через Zoom (использующий кастомный UDP/QUIC) и заходите в лифт.

1.  **00:00** — Вы в холле на Wi-Fi. CID соединения: `A1`.
2.  **00:05** — Двери закрываются, Wi-Fi пропадает. Радиомодуль переключается на LTE.
3.  **00:06** — Клиент Zoom обнаруживает смену интерфейса. Он выбирает из запаса новый CID `B2` (выданный ранее сервером).
4.  **00:07** — Клиент шлет пакет с видео (или `PATH_CHALLENGE`) через LTE с CID `B2`.
5.  **00:08** — Пакет приходит на Load Balancer. LB видит новый IP, но читает CID `B2`. В `B2` закодирован ID того же медиа-сервера, что обслуживал `A1`. LB пересылает пакет туда.
6.  **00:09** — Медиа-сервер видит `B2`, находит в памяти сессию, обновляет "текущий адрес клиента" на LTE-адрес. Видео продолжает идти без фризов.
7.  **00:10** — Сервер шлет ответ на LTE.

В TCP звонок бы прервался с сообщением "Reconnecting...".

## 6. Чек-лист уровня Expert

1.  **UDP Checksum:**
    Можно ли отключить чексумму в UDP?
    *   *Ответ:* В IPv4 да (поставить 0), в IPv6 — **нет** (обязательна). QUIC требует, чтобы UDP checksum работала, плюс добавляет свою мощную криптографическую защиту целостности (AEAD).
2.  **Middleboxes & UDP:**
    Многие корпоративные файрволы блокируют UDP (кроме DNS/NTP). Как QUIC работает там?
    *   *Ответ:* Fallback to TCP (HTTP/2). Клиент пытается установить QUIC, если таймаут — идет по TCP. Это называется "Happy Eyeballs" pattern.
3.  **Spin Bit:**
    Как операторам связи мониторить RTT в QUIC, если все заголовки зашифрованы?
    *   *Ответ:* В заголовке (RFC 9000) есть специальный бит — **Spin Bit**. Клиент и сервер меняют его значение раз в RTT. Пассивный наблюдатель может просто считать частоту переключения этого бита, чтобы оценить Latency, не взламывая шифрование.
4.  **Amplification Attack:**
    Поскольку UDP не требует рукопожатия, можно ли использовать сервер QUIC для DDoS (отправить маленький пакет, получить большой ответ)?
    *   *Ответ:* Нет. RFC 9000 требует, чтобы до валидации адреса сервер не мог отправить данных больше, чем в **3 раза** больше полученных. Это блокирует использование QUIC как усилителя (Amplifier).

### Заключение
*   **UDP** — для ситуаций, где важен каждый такт CPU и вы готовы писать свой контроль потерь.
*   **QUIC** — это современный TCP. Он устраняет фундаментальные архитектурные баги TCP (HoL blocking, Ambiguity, Ossification).
*   **0-RTT** — мощное оружие, которым легко выстрелить себе в ногу (Replay Attacks). Используйте только для `GET`-запросов.

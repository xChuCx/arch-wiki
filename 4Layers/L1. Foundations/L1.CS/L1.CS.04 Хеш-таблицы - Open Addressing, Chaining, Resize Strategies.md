## 1. Физика памяти: Почему Pointer Chasing — это "убийца" CPU

В классической теории алгоритмов (Big O) предполагается, что доступ к любой ячейке памяти стоит $Cost = 1$.
В реальности (современная x86_64/ARM64 архитектура) доступ к памяти — это спектр от **1 такта** (L1 Cache) до **300+ тактов** (RAM). Хеш-таблица — это структура, которая по своей природе (random access) тяготеет к худшему концу этого спектра.

### 1.1. Анатомия "Pointer Chasing" (Охота за указателями)

**Separate Chaining** (метод цепочек), используемый в `java.util.HashMap` или `std::unordered_map` (до C++20), хранит данные как массив указателей на узлы связного списка (`Node*`).

**Сценарий поиска ключа:**
Чтобы найти элемент, процессор должен выполнить цепочку *зависимых* чтений (Dependent Loads).

1.  **Вычисление хеша:** `idx = hash(key) % size`.
2.  **Load #1 (Bucket Head):** Читаем указатель из массива бакетов.
    *   *Адрес:* `BaseArray + idx * 8`.
    *   *Статус:* Скорее всего **Cache Miss** (промах кэша), так как доступ случайный.
    *   *Цена:* ~300 тактов простоя (CPU Stall).
3.  **Load #2 (Node Data):** Переходим по полученному указателю к первому узлу `Node`.
    *   **Критическая проблема (Serial Dependency):** Процессор **не знает** адреса узла, пока не завершится Load #1. Конвейер (Pipeline) процессора встает. Никакой спекулятивное выполнение (Speculative Execution) здесь не поможет.
    *   Узел лежит в куче (Heap) в случайном месте. Это снова **Cache Miss**.
    *   *Цена:* Еще ~300 тактов.
4.  **Load #3 (Next Pointer):** Если ключ не совпал, читаем поле `node->next`.
    *   Снова зависимость: адрес следующего узла лежит в памяти текущего. Мы не можем начать загрузку `NextNode`, пока не прочитали `CurrentNode`.

**Итог:** Поиск в цепочке из 3-х элементов — это не 3 инструкции, это 3 последовательных обращения в RAM.
$$Latency \approx 3 \times 100ns = 300ns$$
Для процессора с частотой 3GHz это простой в **900 тактов**. За это время можно было бы выполнить 3000 арифметических операций.

### 1.2. Скрытый враг: TLB Thrashing (Пробуксовка буфера трансляции)

Инженеры часто забывают про виртуальную память.
*   Указатели — это *виртуальные* адреса.
*   Чтобы процессор мог прочитать данные, он должен перевести Виртуальный Адрес $\to$ Физический Адрес.
*   Для этого используется кэш **TLB (Translation Lookaside Buffer)**.

**В чем проблема Chaining?**
В большой хеш-таблице (миллионы объектов) узлы `Node` разбросаны по всей оперативной памяти. Каждый переход по указателю `node->next` — это прыжок на новую страницу памяти (обычно 4KB).
1.  Вы прыгаете на случайную страницу.
2.  В TLB (который хранит всего 512-1500 записей) нет маппинга для этой страницы.
3.  Происходит **TLB Miss**.
4.  Аппаратный Page Walker идет в RAM, чтобы прочитать таблицу страниц (Page Table), чтобы узнать физический адрес.
5.  **Двойной штраф:** Вы платите за чтение данных + платите за чтение таблицы страниц.

### 1.3. Почему Open Addressing побеждает (Cache Locality & Prefetching)

В **Open Addressing** (Линейное пробирование) все данные лежат в одном плотном массиве структур `Entry`.

**Физика процесса:**
При коллизии (или просто поиске) мы проверяем ячейки: `idx`, `idx+1`, `idx+2`...

1.  **Cache Lines (Кэш-линии):**
    Память читается блоками по **64 байта** (стандарт x86).
    Если ваша структура `Entry` занимает 16 байт (8 байт ключ + 8 байт значение), то **одна** загрузка из RAM (Load #1) притаскивает в L1 кэш сразу **4 элемента** (текущий и 3 следующих).
    *   Проверка 2-го, 3-го и 4-го элемента происходит за **1-3 такта** (L1 hit), а не за 300 тактов.

2.  **Hardware Prefetching (Аппаратное предсказание):**
    Современные CPU видят паттерн доступа: "Ага, он читает `addr`, потом `addr + 16`, потом `addr + 32`".
    Блок **Prefetcher** начинает фоново подгружать данные из RAM в L1 кэш *до того*, как ваш код их запросит.
    В связных списках (Chaining) префетчер бесполезен, так как адреса хаотичны.

3.  **Отсутствие зависимостей по данным (Data Dependencies):**
    Адрес следующей ячейки вычисляется арифметически: `NextAddr = CurrentAddr + sizeof(Entry)`.
    Процессор может вычислить этот адрес и выставить запрос на чтение **параллельно** с обработкой текущего ключа (Instruction Level Parallelism).

### 1.4. Наглядный пример (Memory Layout)

Представьте таблицу: `Map<Int, Int>`.

**A. Separate Chaining (Java/Old C++):**
```cpp
// Структура в памяти размазана:
[Bucket Array] -> [Ptr1] -------------------------> [Node A] (на странице 0x1000)
                  [Ptr2] -> [Node B] (на 0x5000) -> [Node C] (на странице 0x9000)
                  [Ptr3] -> NULL
```
*   Поиск `Node C`: Jump to Bucket -> Jump to 0x5000 -> Jump to 0x9000.
*   3 прыжка, 3 потенциальных Cache Miss, 3 потенциальных TLB Miss.

**B. Open Addressing (Modern High-Perf):**
```cpp
// Структура монолитна:
[ Key1 | Val1 | Key2 | Val2 | Key3 | Val3 | Key4 | Val4 ] ...
^
|
Загрузка одной Cache Line (64 байта)
```
*   Если `Key1` — это коллизия, то `Key2`, `Key3` и `Key4` **уже лежат в регистрах CPU** или L1 кэше. Проверка стоит практически 0.

### Резюме для Эксперта

Переход от Chaining к Open Addressing — это переход от **Pointer Chasing** (последовательного блуждания по памяти с ожиданием ответа от RAM) к **Sequential Scan** (последовательному сканированию, которое дружелюбно к префетчеру и кэш-линиям). Именно поэтому `absl::flat_hash_map` или `Rust HashMap` быстрее `std::unordered_map` в 3-10 раз на задачах поиска (Lookup), несмотря на теоретически одинаковую асимптотику $O(1)$.

## 2. Анатомия Современных Таблиц (State of the Art)

Забудьте про `std::unordered_map` из C++11. Современный стандарт индустрии — это **Swiss Tables** (Google Abseil, Rust `std::HashMap` с версии 1.54+, Go `map` частично) и **Robin Hood Hashing**. Эти структуры спроектированы не для абстрактной машины Тьюринга, а для реальных CPU с конвейерами, кешами L1/L2 и векторными инструкциями (SIMD).

### 2.1. Swiss Tables (Google Abseil `flat_hash_map`)

Название происходит от "швейцарского армейского ножа", подразумевая универсальность, но внутри это **SIMD-accelerated Group Probing**.

#### А. Разделение памяти (Memory Layout)
Вместо одного массива структур `Node { key, value, hash, next }` (как в Chaining), мы расщепляем данные на два параллельных массива. Это критически важно для **Cache Density**.

1.  **Metadata Array (`ctrl`):** Массив байтов (1 байт на слот). Хранит *состояние* слота. Этот массив очень компактный и горячий (всегда в L1 кеше).
2.  **Slot Array (`slots`):** Массив, хранящий сами пары `Key` и `Value`.

#### Б. Структура Metadata Byte (Control Byte)
Один байт `ctrl[i]` кодирует состояние $i$-го слота. Мы используем хеш функцию $H(k)$, разбивая её результат (64 бита) на две части:
*   **H1 (57 бит):** Индекс бакета. $idx = H1 \mod Capacity$.
*   **H2 (7 бит):** "Отпечаток" (Signature). Используется для быстрой фильтрации.

Значения байта `ctrl`:
*   `0xFF` (-128): **EMPTY** (Слот пуст).
*   `0xFE` (-127): **DELETED** (Tombstone, удален).
*   `0x00...0x7F`: **FULL** (Занят). Хранит 7 бит $H2$.

#### В. Алгоритм поиска с SIMD (The Magic)
Вместо того чтобы проверять слоты по одному (Linear Probing), мы проверяем их **группами по 16 штук** за один такт процессора.

**Шаги `find(key)`:**
1.  Вычисляем $H1$ и $H2$.
2.  Идем в позицию $pos = H1$ в массиве `ctrl`.
3.  **Load:** Загружаем 16 байт метаданных начиная с $pos$ в 128-битный регистр (инструкция `_mm_loadu_si128` в SSE2 или NEON аналог).
4.  **Compare:** Одной инструкцией (`_mm_cmpeq_epi8`) сравниваем все 16 байт с нашим $H2$.
    *   Результат: вектор, где `0xFF` там, где совпало, и `0x00` где нет.
5.  **Mask:** Превращаем вектор сравнения в битовую маску (`_mm_movemask_epi8`).
    *   На выходе получаем `int mask` (16 бит). Если $i$-й бит равен 1, значит в слоте $i$ совпал хеш H2.
6.  **Iterate:** Если маска не ноль, мы итерируемся только по установленным битам (инструкция `TZCNT` - Count Trailing Zeros) и проверяем ключи в `slots` на *полное равенство*.
7.  Если маска ноль (или ключи не подошли) — прыгаем на следующую группу из 16 слотов.

**Пример (псевдокод на уровне железа):**
```cpp
// Ищем хеш с H2 = 0x5A (01011010)
__m128i target = _mm_set1_epi8(0x5A); // Вектор {5A, 5A, ... 5A}
__m128i group  = _mm_loadu_si128((__m128i*)&ctrl[pos]); // Загружаем 16 байт метаданных
__m128i match  = _mm_cmpeq_epi8(target, group); // Параллельное сравнение
int mask = _mm_movemask_epi8(match); // Получаем, например, 0000000000100000

while (mask != 0) {
    int bit_pos = __builtin_ctz(mask); // Нашли бит (индекс 5)
    if (slots[pos + bit_pos].key == key) return &slots[pos + bit_pos].val;
    mask &= ~(1 << bit_pos); // Сбросили бит, ищем дальше
}
// Если не нашли - переходим к следующей группе (Triangular probing или Linear)
```

**Почему это Game Changer:**
Мы отфильтровываем 99% ложных кандидатов, не прикасаясь к тяжелому массиву `slots`. Процессор не получает Cache Miss, читая ключи, которые заведомо не подходят.

### 2.2. Robin Hood Hashing (Минимизация дисперсии)

Если Swiss Tables фокусируются на скорости *чтения* (Lookup) через железо, то Robin Hood фокусируется на *алгоритмической стабильности* размещения.

Главная проблема Linear Probing — **кластеризация**. Некоторые элементы "воруют" удачные места, а другим приходится шагать очень далеко. Это создает длинные хвосты в Latency.

#### А. Терминология
*   **Ideal Bucket (Home):** Индекс, куда хеш-функция отобразила ключ изначально ($h \mod N$).
*   **PSL (Probe Sequence Length):** Расстояние от текущей позиции элемента до его Ideal Bucket. "Богатство" элемента.
    *   PSL = 0: Элемент дома (очень богат).
    *   PSL = 10: Элемент смещен на 10 позиций (очень беден).

#### Б. Инвариант Робин Гуда
При вставке, если мы встречаем коллизию, мы сравниваем PSL текущего элемента в слоте ($PSL_{curr}$) и PSL вставляемого ($PSL_{new}$).
**Правило:** "Если ты богаче меня — уступи место".
Если $PSL_{new} > PSL_{curr}$, мы:
1.  Вынимаем старый элемент (`curr`) из ячейки.
2.  Вставляем новый (`new`) на его место.
3.  Старый элемент становится "беженцем", и мы идем искать место для него дальше (увеличивая его PSL).

#### В. Пример (Trace)
Массив размера 5. Хеш-функция $h(k) = k \mod 5$.
Уже есть: `[A(0), B(0), _, _, _]`.
*   A на месте 0 (PSL=0).
*   B на месте 1 (хотел 0, сместился на 1, PSL=1).

Вставляем **C** с хешем 0.
1.  Индекс 0: Там A (PSL=0). Наш C тоже имеет PSL=0. Равны. Идем дальше.
2.  Индекс 1: Там B (PSL=1). Наш C имеет PSL=1 (так как мы уже сместились на 1 шаг от 0). Равны. Идем дальше.
3.  Индекс 2: Пусто. Вставляем C.
Итог: `[A, B, C, _, _]`. Все счастливы.

Теперь (альтернативная реальность) вставляем **D** с хешем 1.
Состояние: `[A(0), B(0), C(0), _, _]`.
1.  Индекс 1 (Home для D): Там B (PSL=1). У D PSL=0. $0 < 1$ (D богаче B). D не может выгнать B. Идем дальше. У D теперь PSL=1.
2.  Индекс 2: Там C (PSL=2). У D PSL=1. $1 < 2$. D не может выгнать C. Идем дальше. У D теперь PSL=2.
3.  Индекс 3: Пусто. Вставляем D.

**Инсайт:** Алгоритм автоматически "выравнивает" PSL. Не бывает такого, что один элемент имеет PSL=0, а соседний PSL=20. Все будут иметь PSL примерно 2-3.
Это делает `Lookup` крайне предсказуемым. Если мы прошли PSL больше определенного порога (например, 6) и не нашли элемент — можно делать **Early Exit** (гарантированно элемента нет), не проверяя всю таблицу.

### 2.3. F14 (Facebook 14-slot Hashing)

Это вариация Swiss Tables, оптимизированная Facebook для C++.
В `std::unordered_map` ключи и значения должны иметь стабильные адреса (Pointer Stability). Обычный Open Addressing этого не дает (ресайз перемещает данные).

**Решение F14:**
*   **Chunking:** Память разбита на чанки.
*   **Indirection:** В слоте хранится не значение, а указатель (если объект большой) или значение (если small object optimization).
*   Название F14 происходит от того, что они используют SIMD фильтрацию (как Swiss Table), но группируют по 14 слотов (плюс 2 байта метаданных на чанк) для идеального выравнивания.

### Сводная таблица для Архитектора

| Характеристика | Chaining (`std::unordered_map`) | Linear Probing | Swiss Tables (Abseil) | Robin Hood |
| :--- | :--- | :--- | :--- | :--- |
| **Cache Access** | Random (Poor) | Sequential (Good) | **SIMD Filtered (Excellent)** | Sequential (Good) |
| **Load Factor** | > 1.0 (ok) | < 0.5 (must) | **< 0.875 (stable)** | < 0.9 (stable) |
| **Metadata** | 8-16 bytes overhead | 0 overhead | 1 byte overhead | 1-2 byte (optional PSL) |
| **Worst Case Lookup** | $O(N)$ | $O(N)$ (clustering) | $O(N)$ (rare) | $O(\log N)$ (effectively) |
| **Best For** | Heavy writes, bad hash func | Simple integer keys | **General Purpose High Perf** | Latency Sensitive Read-Heavy |

## 3. Tombstones: Грязный секрет Open Addressing

В методе открытой адресации (Open Addressing) удаление элемента — это не просто "очистка памяти". Это архитектурная проблема, которая нарушает фундаментальную логику поиска. Если вы просто обнулите ячейку, вы "порвете" цепочку поиска для других элементов, вызвав потерю данных.

Для решения этой проблемы вводится специальное состояние ячейки — **Tombstone** (могильный камень, маркер удаления).

### 3.1. Фундаментальная проблема: Разрыв цепочки (Broken Probe Sequence)

Чтобы понять, зачем нужен Tombstone, рассмотрим механику **Linear Probing** (линейного пробирования).

**Сценарий без Tombstones (наивная реализация):**
1.  У нас есть пустая таблица, хеш-функция $h(k) = k \pmod{10}$.
2.  **Insert(15):** $15 \pmod{10} = 5$. Ячейка [5] свободна. Пишем 15.
3.  **Insert(25):** $25 \pmod{10} = 5$. Коллизия! Идем дальше. Ячейка [6] свободна. Пишем 25.
    *   *Probe Sequence для 25:* `[5] -> [6]`
4.  **Delete(15):** Удаляем 15 из ячейки [5]. Ставим статус `EMPTY` (пусто).
5.  **Search(25):**
    *   Идем в хеш: $25 \pmod{10} = 5$.
    *   Смотрим ячейку [5]. Там `EMPTY`.
    *   **Логика алгоритма:** "Если мы встретили пустоту, значит элемента в таблице нет".
    *   **Результат:** `NOT_FOUND`.
    *   **Ошибка:** Элемент 25 потерян, хотя он лежит в ячейке [6].

**Решение с Tombstones:**
В шаге 4 вместо `EMPTY` мы ставим специальный маркер `DELETED` (Tombstone).
При поиске `Search(25)`:
1.  Ячейка [5] — `DELETED`. Алгоритм понимает: "Здесь кто-то был, но умер. Возможно, то, что я ищу, проскочило дальше". **Идем дальше.**
2.  Ячейка [6] — 25. **Нашли!**

### 3.2. Contamination: Эффект "Города-призрака"

Tombstones решают проблему корректности, но создают проблему производительности. Это явление называется **Contamination** (загрязнение).

Представьте таблицу емкостью 1000 слотов.
1.  Мы вставили 800 элементов.
2.  Мы удалили 800 элементов.
3.  В таблице 0 живых элементов и 800 надгробий.

**Что происходит при `Search(Key)`?**
Если ключа нет в таблице, алгоритм хеширует его, попадает в "кладбище" и вынужден прыгать по надгробиям (`DELETED` -> `DELETED` -> ...), пока не найдет `EMPTY` слот.
*   **Сложность:** $O(N)$ вместо ожидаемого $O(1)$.
*   **Парадокс:** Таблица пустая (0 полезных данных), но работает медленно, как полностью забитая.

**Определения для метрик:**
*   **Load Factor ($\alpha$):** $\frac{\text{Alive Items}}{\text{Capacity}}$.
*   **Occupancy (Заполненность):** $\frac{\text{Alive Items} + \text{Tombstones}}{\text{Capacity}}$.

Алгоритм поиска замедляется пропорционально *Occupancy*, а не *Load Factor*.

### 3.3. Стратегии управления Tombstones (Lifecycle Management)

Как архитектор, вы должны выбрать стратегию очистки, чтобы избежать деградации сервиса.

#### А. Triggered Rehash (Ленивая очистка)
Самый простой метод. Мы следим за количеством "мертвых душ".
Стандартное условие ресайза (расширения) — `Load Factor > 0.75`.
Добавляем новое условие для пересборки (без расширения, просто чистка):
*   Если `Occupancy > 0.70` И `Load Factor < 0.30`.
Это означает: "Таблица забита мусором, но данных мало". Мы выделяем новый массив *того же размера* (или меньше) и переносим только живые данные. Надгробия исчезают.

#### Б. Tombstone Recycling (Повторное использование)
Можно ли писать новые данные поверх надгробия?
**Вставка `Insert(K)`:**
1.  Вычисляем хеш. Идем по цепочке.
2.  Запоминаем индекс *первого встреченного* Tombstone (`first_tomb`).
3.  Продолжаем идти, пока не найдем `K` (обновление) или `EMPTY`.
4.  Если нашли `EMPTY` (ключа нет), мы можем записать новый `K` в позицию `first_tomb`, а не в текущую пустую.
**Выгода:** Это замедляет рост Occupancy, переиспользуя слоты.
**Нюанс:** Мы все равно обязаны пройти цепочку до конца (`EMPTY`), чтобы убедиться, что дубликата ключа `K` нет дальше. Нельзя просто писать в первый Tombstone и выходить!

#### В. Backward Shift Deletion (Отказ от Tombstones)
Это "высший пилотаж" для **Linear Probing**, используемый в высоконагруженных системах (например, в некоторых реализациях Python dict или Zig `HashMap`).
Идея: При удалении элемента мы физически "залечиваем" разрыв.

**Алгоритм `Delete(i)`:**
1.  Очищаем слот `i`. Делаем его `EMPTY`.
2.  Смотрим на соседа `j = i + 1`.
3.  Если слот `j` `EMPTY` — стоп.
4.  Если слот `j` занят, проверяем его "желаемую" позицию (Ideal Hash Position).
    *   Если элемент в `j` "хочет" быть на позиции `i` или раньше (из-за коллизии его снесло вправо), мы **сдвигаем** его в `i`.
    *   Теперь дырка образовалась в `j`. Повторяем процесс для `j+1`.
5.  Продолжаем, пока не встретим `EMPTY`.

*   **Плюсы:** Нет Tombstones. Всегда идеальная производительность поиска ($O(1)$). Нет деградации со временем.
*   **Минусы:** Операция `Delete` становится дороже (потенциально $O(Cluster\_Length)$) и портит Cache Locality из-за записей. Сложно реализовать потокобезопасно.

### 3.4. Tombstones и Swiss Tables (Meta-data trick)

В современных **Swiss Tables** (Abseil/C++20) проблема Tombstones решается изящнее за счет метаданных.
В массиве `Control Bytes`:
*   `0xFF` = Empty
*   `0xFE` = Deleted (Tombstone)
*   `0x00..0x7F` = Hash prefix

Группы по 16 слотов читаются одной SIMD инструкцией.
Внутри группы (16 элементов) мы можем делать "локальный ребилд" или просто игнорировать Tombstones битовой маской. Поскольку мы не грузим данные (ключи) из памяти, проверка Tombstone стоит дешево (регистровая операция), пока вся группа не заполнится надгробиями.

---
### Резюме для Эксперта:
1.  **Tombstone** — это "костыль" для сохранения связности probe sequence.
2.  **Occupancy, а не Load Factor** определяет реальную Latency вашего `get()`.
3.  Если вы пишете систему с интенсивным удалением (например, кэш с TTL), обычный Open Addressing умрет. Вам нужна реализация с **Backward Shift Deletion** или агрессивным **Rehashing**.
4.  Никогда не используйте Open Addressing без стратегии очистки Tombstones в долгоживущих процессах.

## 4. Resize Strategies & Bit Magic: Битва за такты и байты

Расширение (Resizing) и вычисление индекса — это не просто алгоритмические шаги. Это операции, которые напрямую взаимодействуют с ALU (арифметико-логическим устройством) процессора и менеджером памяти ОС. Ошибки здесь приводят к Stall Cycles (простоям конвейера) и фрагментации кучи.

### 4.1. Modulo Arithmetic vs Bitwise Masking

Как превратить 64-битный хеш `H` в индекс массива `idx` размером `N`?

#### **Подход 1: Простые числа и деление (`%`)**
Традиционный подход (Cormen et al.): выбираем `N` как **простое число** (Prime number).
$$ idx = H \pmod N $$
*   **Зачем:** Это "страховка" от плохих хеш-функций. Если данные имеют паттерн (например, кратные 4: 4, 8, 12...), а размер таблицы — степень двойки (16), то мы будем попадать только в 4, 8, 12, 0... Простые числа ломают этот резонанс.
*   **Проблема (Latency):** Инструкция `DIV` (или `IDIV`) на x86/ARM — одна из самых медленных. Она не конвейеризуется.
    *   `ADD/SUB/XOR`: ~0.3 - 1 такт.
    *   `DIV`: **20 - 60 тактов**.
    *   В High-Load системе тратить 40 тактов только на вычисление адреса — непозволительная роскошь.

#### **Подход 2: Power of Two и Маскирование (`&`)**
Современный стандарт (Java HashMap, Go Map, Rust HashMap, Swiss Table). Размер таблицы `N` всегда равен $2^k$.
$$ idx = H \ \& \ (N - 1) $$
*   **Механика:** Если $N=16$ ($10000_2$), то $N-1 = 15$ ($01111_2$). Операция `AND` просто "отрезает" старшие биты, оставляя младшие $k$ бит.
*   **Скорость:** Операция занимает **< 1 такта**.
*   **Риск (The Trap):** Мы используем *только* младшие биты.
    *   *Пример катастрофы:* Вы хешируете указатели (Pointers). В 64-битных системах указатели часто выровнены по 8 байт (оканчиваются на `000` или `1000`).
    *   Если вы используете "сырой" хеш указателя и маску `111` (размер 8), вы всегда будете попадать только в 0-й бакет. Это 100% коллизий, превращающих хеш-мапу в связный список ($O(N)$).

### 4.2. Bit Mixing (Avalanche Effect)

Чтобы использовать быстрый подход Power of Two, мы **обязаны** исправить недостатки пользовательской хеш-функции. Нам нужно, чтобы изменение *любого* бита во входных данных (ключе) лавинообразно меняло биты в младшей части хеша.

Это делается с помощью **Bit Mixing** (или Finalizer) — набора быстрых операций (XOR, Shift, Multiply) перед наложением маски.

**Пример (Java HashMap implementation trick):**
```java
// "Размываем" старшие биты (которые обычно качественные) на младшие.
// >>> - беззнаковый сдвиг вправо.
static final int hash(Object key) {
    int h;
    return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
}
```
*   **Суть:** Мы берем старшие 16 бит и делаем XOR с младшими 16 битами. Теперь младшие биты (которые мы используем для индекса) содержат "энтропию" (информацию) всего числа.

**Пример (MurmurHash / WyHash mixer - C++ level):**
Более агрессивное перемешивание для системных языков:
```cpp
uint64_t mix(uint64_t h) {
    h ^= h >> 33;
    h *= 0xff51afd7ed558ccd; // Магическая константа (большое простое число)
    h ^= h >> 33;
    h *= 0xc4ceb9fe1a85ec53;
    h ^= h >> 33;
    return h;
}
```
Это гарантирует, что даже "плохие" ключи (1, 2, 3...) разлетятся по таблице равномерно.

### 4.3. Стратегии Аллокации (Memory Growth Strategies)

Когда `Load Factor` превышен, мы должны выделить новый буфер. Как выбрать новый размер?

#### **Коэффициент роста 2 (Doubling)**
`new_cap = old_cap * 2`. Самый простой подход.
*   **Проблема:** Фрагментация памяти (Bad fit for Allocators).
    *   Представим, мы аллоцируем: 16 байт, затем 32, затем 64, затем 128.
    *   Когда мы просим 128 байт, мы уже освободили $16+32+64 = 112$ байт.
    *   $112 < 128$. Аллокатор (jemalloc/tcmalloc) **не может** переиспользовать освобожденную память ("дырку" в куче). Ему приходится просить у ОС новые страницы в конце кучи. Старая память остается неиспользуемой "дырой" до тех пор, пока не придет запрос на маленький объект.

#### **Коэффициент роста 1.5 (Golden Ratio Approximation)**
`new_cap = old_cap * 1.5` (примерно). Используется в `folly::fbvector` и некоторых реализациях STL.
*   Последовательность: 16, 24, 36, 54, 81, 121...
*   Сумма $16+24+36+54 = 130$.
*   Следующий запрос 121. $130 > 121$.
*   **Победа:** Аллокатор может положить новый массив прямо поверх старых освобожденных блоков. Это значительно снижает потребление RAM в долгоживущих процессах.

### 4.4. Zero-Copy Resize (OS-Level Hacks)

Для экстремально больших таблиц (гигабайты, сотни миллионов записей) классический `malloc` + `memcpy` + `free` убивает производительность.
`memcpy` 10 ГБ данных забивает пропускную способность памяти (Memory Bandwidth) и вымывает полезные данные из CPU Cache.

**Продвинутая техника (Linux only): `mremap`**
Если данные хранятся в `std::vector`-подобном буфере (как в Open Addressing), мы можем попросить ядро ОС переназначить страницы виртуальной памяти.

1.  Мы аллоцируем память через `mmap` (анонимные страницы).
2.  При ресайзе вызываем `mremap`.
3.  **Магия:** ОС меняет записи в таблице страниц (Page Table Entries). Физические фреймы RAM **не копируются**. Меняются только виртуальные адреса (или просто расширяется диапазон).
4.  Операция занимает микросекунды независимо от объема данных.

*Примечание:* Это работает для самого буфера. Однако, если хеш-таблица требует *перехеширования* (изменения позиции элемента из-за смены маски), нам все равно придется читать и писать данные. Но `mremap` идеально подходит для структур типа `Append-Only Log` или при изменении capacity без изменения хеш-правил (редкие кейсы).

### 4.5. Trigger Policies: Когда начинать ресайз?

Наивный подход: `if (size > capacity * 0.75) resize()`.
Экспертный подход учитывает **Tombstones** (удаленные элементы).

В таблицах с открытой адресацией:
$$ \text{Effective Load} = \frac{\text{Alive Items} + \text{Tombstones}}{\text{Capacity}} $$

Поиск тормозит из-за занятых слотов (неважно, живой там элемент или "мертвый").
**Стратегия:**
1.  Если `Alive Items > Capacity * 0.75` $\rightarrow$ **Grow** (увеличиваем размер $\times 2$).
2.  Если `Alive + Tombstones > Capacity * 0.75`, НО `Alive < Capacity * 0.5` $\rightarrow$ **Rehash in place** (размер не меняем, но вычищаем "мертвецов").
    *   Это спасает память, не раздувая таблицу из-за частых вставок/удалений.

## 5. Concurrency: Архитектура потокобезопасной мапы

Обернуть обычную `HashMap` в `Global Lock` (например, `Collections.synchronizedMap` в Java или `std::mutex` поверх `std::map` в C++) — это "смерть" производительности.
*   **Проблема:** *Contention* (конкуренция). Все потоки выстраиваются в очередь к одному мьютексу. На 64-ядерном сервере 63 ядра будут спать, пока одно работает.
*   **Цель:** *Scalability* (масштабируемость). При добавлении потоков пропускная способность должна расти линейно.

Для этого мы используем гибридные подходы: **Lock-Free** (для чтения и простых записей) + **Fine-Grained Locking** (для сложных коллизий).

### 5.1. CAS (Compare-And-Swap) — Атом первоосновы

Прежде чем говорить о мапе, нужно понять инструкцию, на которой все держится.
`CAS(Address, ExpectedValue, NewValue)` — это **атомарная** инструкция процессора (x86: `CMPXCHG`).

*   **Логика:** "Посмотри в ячейку памяти `Address`. Если там лежит `ExpectedValue`, то запиши туда `NewValue` и верни `true`. Если там что-то другое (кто-то успел изменить), ничего не делай и верни `false`".
*   **Почему это круто:** Это происходит без переключения контекста ядра ОС (syscall). Это очень быстро (~10-20 тактов), если нет дикой конкуренции.

### 5.2. Эволюция блокировок: От сегментов к бакетам

#### Gen 1: Lock Striping (Сегментация)
*Использовалось в Java 7 `ConcurrentHashMap`.*
Вместо одного замка мы берем массив из 16 замков (Segments).
*   Хеш ключа определяет сегмент: `segmentIndex = (hash >>> shift) & mask`.
*   **Плюс:** 16 потоков могут писать одновременно.
*   **Минус:** Это жесткий лимит. На сервере со 128 ядрами мы все равно упремся в потолок. К тому же, сегменты "дорогие" по памяти.

#### Gen 2: Bucket-Level Locking (CAS + Synchronized)
*Стандарт современности (Java 8+, Go `sync.Map` variations, .NET `ConcurrentDictionary`).*
Мы отказываемся от понятия "Сегмент". Теперь **каждый бакет** (slot) может быть заблокирован независимо.

**Алгоритм `put(Key, Value)` — это State Machine:**

1.  **State: Slot is Empty (Слот пуст)**
    *   Мы не берем никаких блокировок.
    *   Мы создаем `Node(K, V)` и пытаемся положить его в слот через **CAS**.
    *   `CAS(table[i], null, newNode)`.
    *   Если успех — отлично, мы вставили элемент за наносекунды.
    *   Если провал (другой поток опередил) — повторяем цикл (spin loop).

2.  **State: Hash Collision (Слот занят обычным узлом)**
    *   В слоте уже есть данные (голова цепочки/дерева). CAS здесь применять сложно (сложно атомарно добавить в середину связного списка без сложных схем типа Harris Linked List).
    *   Мы захватываем **монитор (lock) только на этот первый узел** (`synchronized (headNode)`).
    *   Остальная таблица (миллионы других бакетов) остается доступной для записи!
    *   Проходим по цепочке, обновляем или добавляем значение.

3.  **State: Resizing (Идет ресайз)**
    *   Если поток видит в слоте специальный маркер **Forwarding Node** (обозначает "этот бакет уже переехал"), он не ждет. Он идет **помогать** переносить данные.

### 5.3. Collaborative Resizing (Кооперативный ресайз) — Высший пилотаж

Самая сложная часть lock-free структур. Как увеличить массив в 2 раза, не останавливая мир?

**Проблема:** Если один поток начнет переносить 10GB данных, он "зависнет". Остальные потоки упрутся в него и тоже зависнут.
**Решение:** Мультипоточный перенос.

1.  **Инициация:** Поток А понимает, что Load Factor превышен. Он создает новый массив `nextTable`.
2.  **Forwarding Node (MOVED):** Это специальный тип узла, который содержит хеш `-1` и ссылку на `nextTable`.
3.  **Процесс:**
    *   Массив бакетов разбивается на "страйды" (кусочки), например, по 16 бакетов.
    *   Поток А берет себе страйд (индексы 0-15) и начинает переносить узлы. На месте старых узлов он оставляет `ForwardingNode`.
    *   Поток Б приходит делать `put()` в индекс 20. Видит, что там пусто/обычный узел. Работает спокойно.
    *   Поток В приходит делать `put()` в индекс 5. Видит `ForwardingNode`. Он понимает: "Ага, идет ресайз". Вместо того чтобы ждать, он **запрашивает себе задачу**. Система выдает ему страйд (индексы 16-31).
4.  **Результат:** Чем больше нагрузка на систему, тем больше потоков участвуют в ресайзе. Ресайз проходит быстрее.

### 5.4. False Sharing (Ложное разделение) — Аппаратный нюанс

На уровне Expert вы обязаны это знать.
*   Процессор читает память строками по 64 байта (Cache Line).
*   Представьте массив счетчиков (например, для статистики мапы), лежащих рядом: `CounterA` и `CounterB`.
*   Поток 1 инкрементирует `CounterA`. Поток 2 инкрементирует `CounterB`.
*   Логически они независимы. Физически они лежат в одной Cache Line.
*   **MESI Protocol:** Когда Поток 1 пишет в `CounterA`, он помечает всю линию как "Dirty". Ядро Потока 2 обязано сбросить свой L1 кеш и перечитать линию из RAM (или L3).
*   **Эффект:** Производительность падает в 50-100 раз. Это называется "Ping-ponging".

**Решение:**
Использовать паддинг (padding), чтобы отодвинуть данные друг от друга.
В Java: аннотация `@Contended` (добавляет 128 байт пустоты вокруг поля).
В C++: `alignas(64)` или добавление фиктивных полей `char pad[64]`.

В `LongAdder` (высокопроизводительный счетчик) и внутри `ConcurrentHashMap` (для `CounterCells`) этот прием используется обязательно.

---
### Пример кода (Псевдокод логики ConcurrentHashMap)

```java
public V put(K key, V value) {
    int hash = spread(key.hashCode());
    
    // Бесконечный цикл (Spin Lock), пока не сделаем дело
    for (Node<K,V>[] tab = table;;) {
        Node<K,V> f; int n, i;
        
        // 1. Инициализация (Lazy allocation)
        if (tab == null)
            tab = initTable();
            
        // 2. Слот пустой? Пытаемся вставить через CAS
        else if ((f = tabAt(tab, i = (n - 1) & hash)) == null) {
            // casTabAt: атомарно "если null, то new Node"
            if (casTabAt(tab, i, null, new Node<K,V>(hash, key, value)))
                break; // Успех! Выходим.
        }
        
        // 3. Слот помечен как "MOVED"? Помогаем переносить данные!
        else if ((fh = f.hash) == MOVED)
            tab = helpTransfer(tab, f);
            
        // 4. Коллизия. Блокируем ТОЛЬКО этот узел
        else {
            V oldVal = null;
            synchronized (f) { // <-- Блокировка узкая, на 1 бакет
                if (tabAt(tab, i) == f) { // Double-check locking
                    // Обычная логика вставки в LinkedList или Tree
                    // ...
                }
            }
            if (binCount >= TREEIFY_THRESHOLD)
                treeifyBin(tab, i); // Превращаем список в дерево
            if (oldVal != null) return oldVal;
            break;
        }
    }
    addCount(1L, binCount); // Обновляем размер (тоже хитро, через LongAdder)
    return null;
}
```

**Резюме раздела:**
Современная конкурентная карта — это **Lock-Free Fast Path** (чтение и запись в пустые слоты) + **Fine-Grained Locking** (при коллизиях) + **Parallel Processing** (при ресайзе). Блокировка всего объекта — признак легаси-кода.

## 6. Чек-лист уровня Expert

1.  **Probe Sequence Degradation:** Почему *Quadratic Probing* имеет проблему "Secondary Clustering"? (Те, кто попал в один бакет, пойдут по одному и тому же квадратичному маршруту). Как *Double Hashing* решает это? (Шаг прыжка зависит от второго хеша ключа, маршруты уникальны).
2.  **DoS атаки (Hash Flooding):**
    *   Как атакующий может положить Rust/Python сервер, отправляя JSON? (Ключи `{"a": 1, "b": 2...}`).
    *   *Решение:* Использование **SipHash** с секретным ключом, который генерируется при старте процесса. Злоумышленник не может предсказать коллизии, не зная ключа. В C++ `std::unordered_map` по умолчанию НЕ защищен (использует быструю, но слабую функцию).
3.  **CPU Cache Lines & False Sharing:**
    *   В многопоточной Open Addressing карте мы пишем в `metadata[i]`. Соседний поток пишет в `metadata[i+1]`.
    *   Они сидят на одной Cache Line (64 байта).
    *   Ядра начинают играть в пинг-понг кеш-линией (Cache Coherency Protocol MESI), производительность падает в 100 раз.
    *   *Решение:* Выравнивание (Padding) или использование Thread-Local буферов.
4.  **Load Factor > 0.9:** Почему Swiss Tables работают эффективно даже при заполнении 90%, а Linear Probing умирает на 70%? (Благодаря SIMD-фильтрации мы проверяем 16 слотов за раз. Вероятность того, что *все* 16 слотов заняты "чужими" элементами, ниже, чем вероятность наткнуться на длинную цепочку при поштучной проверке).

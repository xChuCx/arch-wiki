Мы рассматриваем деревья как **паттерны доступа к памяти**.
Главный враг производительности — **Memory Wall**.
*   1 операция сравнения (ALU) = < 1 цикла CPU.
*   1 доступ к L3 Cache = ~40-50 циклов.
*   1 доступ к RAM (Cache Miss) = ~300 циклов.

## 1. Смерть Бинарных Деревьев в High-Perf системах: Memory Wall

В современной разработке (High Frequency Trading, GameDev, In-Memory Databases) действует правило: **«CPU — это зверь, которого нужно постоянно кормить данными»**.

Проблема бинарных деревьев (RB-Tree, AVL) не в количестве сравнений ($O(\log N)$), а в том, *как* они взаимодействуют с подсистемой памяти. Процессор тратит 99% времени не на сравнение ключей, а на ожидание данных из оперативной памяти. Это явление называется **Memory Wall**.

### 1.1. Проблема №1: Низкая плотность информации (Low Information Density)

Рассмотрим физическую структуру узла `std::map<int64_t, int64_t>` (обычно RB-Tree) на 64-битной архитектуре.

**Анатомия узла (Node Layout):**
```cpp
struct RBNode {
    RBNode* parent;  // 8 байт
    RBNode* left;    // 8 байт
    RBNode* right;   // 8 байт
    bool color;      // 1 байт (+7 байт padding для выравнивания)
    int64_t key;     // 8 байт (Payload)
    int64_t value;   // 8 байт (Payload)
};
```
*   **Размер узла:** ~48 байт.
*   **Полезная нагрузка (Payload):** 16 байт (Key + Value).
*   **Накладные расходы (Overhead):** 32 байта (66% памяти тратятся на указатели и метаданные!).

**Влияние на кэш:**
Процессор читает память **кэш-линиями** (обычно 64 байта). Загружая один узел RB-дерева, вы "загрязняете" кэш L1 мусором (указателями), который нужен только для навигации, а не для обработки данных. Вы используете пропускную способность шины памяти (Memory Bandwidth) вхолостую.

### 1.2. Проблема №2: Pointer Chasing и «Остановка мира»

Термин **Pointer Chasing** (погоня за указателями) описывает паттерн доступа, когда адрес следующего элемента можно узнать, только прочитав текущий.
`NextAddr = CurrentNode->left;`

Почему это катастрофа для суперскалярного процессора (современные Intel/AMD/Apple Silicon)?

1.  **Сбой Конвейера (Pipeline Stall):** Процессор может исполнять 4-6 инструкций за такт (ILP — Instruction Level Parallelism). Но когда он встречает инструкцию загрузки из памяти (`MOV`), которой нет в кэше (Cache Miss), он **останавливается**.
2.  **Задержки (Latency):**
    *   Доступ к регистрам/L1: ~4 такта.
    *   Доступ к RAM: ~300-400 тактов.
    *   Во время Pointer Chasing процессор 300 тактов просто "курит", ожидая данные.
3.  **Бессилие Префетчера (Hardware Prefetcher):** В процессоре есть модуль, который пытается угадать, какие данные понадобятся дальше.
    *   *Массив:* Адреса $A, A+1, A+2$. Префетчер легко это видит и загружает данные заранее.
    *   *Дерево:* Узлы разбросаны по куче (Heap) хаотично через `new`/`malloc`. Адреса $0x8000$, затем $0x2040$, затем $0xF000$. Префетчер не видит паттерна и отключается.

**Итог:** Поиск в дереве — это серия последовательных промахов кэша (Serial Cache Misses).

### 1.3. Решение: B-деревья в оперативной памяти (In-Memory B-Trees)

Мы заменяем "узкие" узлы бинарного дерева на "толстые" узлы B-дерева, размер которых выровнен по кэш-линии (cache-line aligned).

**Анатомия Cache-Conscious узла:**
Представьте узел размером 256 байт (4 кэш-линии).
В нем лежит **сортированный массив** из ~30 ключей.

**Почему это быстрее:**
1.  **Высота дерева:**
    *   RB-Tree ($N=10^6$): Высота ~20. Это 20 прыжков в память = **20 Cache Misses**.
    *   B-Tree ($M=32$, $N=10^6$): Высота ~4. Это **4 Cache Misses**.
    *   *Выигрыш:* Мы сократили время ожидания памяти в 5 раз.

2.  **Локальность данных (Spatial Locality):**
    Когда мы загрузили "толстый" узел в L1 кэш (потратив 1 промах), поиск внутри этого узла (среди 30 ключей) происходит **мгновенно** (на скорости регистров CPU).

3.  **SIMD Векторизация (Single Instruction, Multiple Data):**
    Внутри узла B-дерева мы можем использовать инструкции AVX2/AVX-512.
    *   Вместо цикла `for` или бинарного поиска, мы одной инструкцией `_mm256_cmpgt_epi32` сравниваем искомый ключ сразу с 8 ключами в узле.
    *   Это позволяет найти нужный выход из узла за пару наносекунд.

### 1.4. TLB Thrashing (Упускаемый из виду аспект)

Кроме кэша данных, есть кэш трансляции виртуальных адресов в физические (**TLB** — Translation Lookaside Buffer).
*   **Бинарное дерево:** Миллион узлов разбросаны по тысячам страниц памяти. Обход дерева требует постоянного переключения между страницами, вызывая **TLB Misses**. Обработка промаха TLB требует дорогого обхода Page Table операционной системой (Page Walk).
*   **B-Tree:** Данные упакованы плотнее. Один узел содержит много ключей. Мы обращаемся к меньшему количеству страниц памяти, снижая давление на TLB.

### Резюме для Архитектора

| Характеристика | Классическое Бинарное Дерево (Pointer Based) | Современное B-Tree / Flat Map (Contiguous Memory) |
| :--- | :--- | :--- |
| **Паттерн памяти** | Random Access (прыжки) | Sequential / Block Access |
| **Hardware Prefetcher** | Бесполезен | Работает эффективно |
| **Data Dependencies** | Высокие (ждем загрузку указателя) | Низкие (данные рядом) |
| **Instructions per Cycle** | Низкий (много Stalls) | Высокий (ALU работает) |
| **Пример реализации** | `std::map`, `java.util.TreeMap` | `absl::btree_map`, `boost::flat_map`, `Rust BTreeMap` |

**Вывод:** Если ваши данные помещаются в RAM и вам важна производительность — **избегайте структур, основанных на индивидуальных нодах (`Node*`)**. Используйте структуры, основанные на массивах и блоках. В 2025 году `std::vector` с бинарным поиском часто обгоняет `std::list` и `std::set` на данных до 100-1000 элементов именно по этой причине.

## 2. Дисковые B+ Trees: Микроскопическая анатомия

Когда мы говорим "узел дерева" в контексте алгоритмов, мы представляем `struct Node { Node* left; Node* right; T value; }`.
В мире баз данных (PostgreSQL, InnoDB, Oracle) **узлов не существует**. Существуют **Страницы (Pages)**.

**Страница** — это фундаментальная единица обмена данными между диском и памятью (Buffer Pool). Обычно это фиксированный блок размером **8KB** (Postgres) или **16KB** (MySQL/InnoDB).

### 2.1. Физика I/O: Почему именно страница?
Диск (SSD/HDD) не умеет читать 10 байт. Минимальная единица атомарного чтения/записи на SSD — это **LBA Block** (обычно 4KB).
*   Если вы хотите прочитать одну строку таблицы размером 100 байт, СУБД вынуждена прочитать с диска **всю страницу целиком** (например, 16KB).
*   Если вы меняете 1 бит, СУБД должна записать всю страницу (16KB) обратно.

**Инсайт эксперта:** Эффективность B-дерева определяется не "O-большим", а тем, сколько **полезных данных** вы запихнули в одну страницу. Чем плотнее упаковка, тем ниже дерево, тем меньше IOPS.

---
### 2.2. Внутренняя структура страницы (Slotted Page Structure)

Это стандарт де-факто для хранения данных переменной длины (VARCHAR, TEXT). Как упаковать сотни строк разной длины в один блок 16KB, обеспечив доступ за $O(1)$ внутри блока?

Используется структура **"Сэндвич" (Slotted Page)**:

1.  **Header (Заголовок):** Фиксированная структура в начале страницы. Содержит метаданные:
    *   `LSN` (Log Sequence Number) — версия страницы для восстановления после сбоя.
    *   `FreeSpacePointer` — где начинается свободное место.
    *   `Checksum` — защита от bit rot (битовой гнили диска).

2.  **Slot Array (Массив слотов / Indirection Vector):** Растет от начала страницы к концу.
    *   Это массив 2-байтовых указателей (оффсетов).
    *   `Slot[0]` указывает на начало записи №0.
    *   `Slot[1]` указывает на начало записи №1.

3.  **Free Space (Свободное место):** Дырка в середине.

4.  **Tuples / Records (Сами данные):** Растут **с конца страницы к началу**.

**Визуализация:**
```text
[ Header | Slot 0 | Slot 1 | Slot 2 | ...  ->       <- ... | Record 2 | Record 1 | Record 0 ]
0 байт                                                                                16 КБ
```

**Зачем такая сложность? (Почему не писать подряд?)**
Представьте, что вы удалили `Record 1` (которая была посередине).
*   Если бы мы хранили данные подряд, нам пришлось бы сдвигать все последующие записи (`memmove`), чтобы закрыть дырку. Это дорого.
*   В **Slotted Page** мы просто помечаем `Slot 1` как "dead". Сами байты данных `Record 1` остаются мусором, который будет вычищен при дефрагментации страницы (Vacuum или Page Compaction). Сдвигать гигабайты данных не нужно.

### 2.3. Внутренние узлы (Internal Nodes) vs Листья (Leaf Nodes)

В B+ дереве структура страницы различается в зависимости от уровня.

#### А. Внутренние страницы (Router Pages)
Их единственная цель — навигация. Они содержат массив пар: `(Key, PageID)`.
*   **Задача архитектора:** Максимизировать **Fan-out** (коэффициент ветвления).
*   *Пример:* Если размер ключа (PK) 8 байт + указатель 4 байта = 12 байт. В страницу 8KB влезает ~680 ключей.
*   Если вы используете **UUID** (16 байт) как PK, размер записи во внутреннем узле растет (16+4=20 байт). Fan-out падает до ~400.
*   **Результат:** Дерево становится выше. Вместо 3 чтений с диска вам нужно 4 или 5. Производительность падает экспоненциально.

#### Б. Листовые страницы (Leaf Pages)
Здесь лежат сами данные. И тут есть два глобальных подхода:

1.  **Clustered Index (InnoDB, SQL Server):**
    *   Лист B-дерева содержит **всю строку целиком** (все колонки таблицы).
    *   *Плюс:* Если вы нашли ключ, данные у вас уже в руках. `SELECT * WHERE id=5` — идеально быстро.
    *   *Минус:* Страницы быстро забиваются. Fan-out мал. При сплите страницы перемещается много данных.

2.  **Heap Organized / Non-Clustered (PostgreSQL):**
    *   B-дерево (индекс) содержит только `(Key, Pointer_to_Heap)`.
    *   Сами строки лежат в отдельной куче (Heap File) в произвольном порядке.
    *   *Плюс:* Индекс очень компактный, обновлять индекс дешево.
    *   *Минус:* Чтобы получить данные, нужно сделать **еще одно** случайное чтение в Heap (Double IO).

### 2.4. Сжатие и Локальность (Prefix Compression)

В реальных системах ключи часто имеют общую часть.
*   URLs: `https://google.com/images`, `https://google.com/maps`
*   Composite Keys: `(TenantID, UserID)` — TenantID одинаковый для миллионов записей.

**Prefix Compression (Suffix Truncation):**
В странице B-дерева мы храним:
1.  `Lowest Key` на странице: `https://google.com/`
2.  Остальные ключи хранятся как **дельта**:
    *   `images`
    *   `maps`

**Инсайт для эксперта:** Это не просто экономия места на диске. Это экономия места в **L1-кэше процессора**. При бинарном поиске внутри страницы процессору нужно сравнивать меньше байт, что ускоряет поиск в разы. Без префиксного сжатия B-деревья на строковых ключах работают отвратительно.

---
### 2.5. Жизненный цикл записи (Write Amplification)

Понимание этого процесса отличает Junior от Principal инженера.
Что происходит физически при `UPDATE users SET age=30 WHERE id=100`?

1.  **B-Tree Search:** СУБД находит листовую страницу, где живет `id=100`.
2.  **Buffer Pool Load:** Если страницы нет в памяти, она читается с диска (16KB Random Read).
3.  **Page Pinning & Latching:** Страница "пинится" (защищается от вытеснения) и лочится (Exclusive Latch).
4.  **Mutation:** В памяти внутри Slotted Page меняются байты (обновляется версия строки).
5.  **WAL (Write Ahead Log):** Генерируется маленькая запись лога ("Page 542, offset 20: set value 30"). Эта запись летит на диск **последовательно** (Append-only). Это быстро.
6.  **Dirty Page:** Сама страница в памяти теперь "грязная". На диске она все еще старая.
7.  **Checkpoint (Проблема!):** Раз в N минут процесс чекпоинта берет эту страницу (16KB) и пишет её на диск в произвольное место.

**Проблема Write Amplification:** Мы поменяли 4 байта (число `30`). В лог записали ~50 байт. Но в файл данных мы рано или поздно запишем **16384 байта**.
*   Коэффициент усиления: $16384 / 4 \approx 4000x$.
*   Именно поэтому на high-write нагрузках B-деревья убивают SSD. Для решения этой проблемы придумали **LSM-Trees (RocksDB)**, которые превращают random-write страниц в sequential-write логов.

### 2.6. Fill Factor (Фактор заполнения)

Почему мы не заполняем страницы на 100%?
Если страница полна, вставка новой записи вызывает **Page Split**:
1.  Выделяется новая пустая страница.
2.  Половина записей из старой переносится в новую (`memcpy`).
3.  В родительский узел добавляется разделитель.
4.  Родитель тоже может лопнуть -> каскадный сплит до корня.

Это блокирует дерево на запись (Write Lock).
**Best Practice:** БД обычно оставляют 10-30% места свободным (Fill Factor 70-90%), чтобы поглощать будущие вставки без сплитов. Для статичных данных (архив) можно делать Rebuild Index с Fill Factor 100% для максимального сжатия.

## 3. Concurrency Control: Жизнь без глобальных локов

### 3.0. Терминология: Lock vs Latch

Прежде чем углубляться, эксперт обязан различать эти понятия. В учебниках их смешивают, в ядрах СУБД — никогда.

*   **Lock (Логическая блокировка):** Защищает логические данные (строку таблицы, транзакцию) от других транзакций.
    *   *Scope:* Длится всю транзакцию (секунды).
    *   *Deadlocks:* Возможны, нужен детектор (Wait-for graph).
    *   *Пример:* `SELECT * FROM users FOR UPDATE`.
*   **Latch (Физическая защелка):** Защищает структуру данных (страницу памяти B-дерева) от повреждения другими потоками.
    *   *Scope:* Длится микросекунды (время чтения/записи одной страницы).
    *   *Deadlocks:* Не допускаются дизайном (Latch Ordering).
    *   *Пример:* `std::shared_mutex` или `pthread_rwlock_t` на узел дерева.

**Наша цель:** Реализовать эффективный Latching для индекса.

### 3.1. Проблема "Бутылочного горлышка" (Root Bottleneck)

Представьте, что у вас 100 потоков, делающих `SELECT` (чтение).
Если вы используете стандартный `Reader-Writer Lock` (`std::shared_mutex`) на корневом узле:
1.  Поток А хочет прочитать корень. Он делает `atomic_fetch_add` на счетчике читателей (внутри мьютекса).
2.  Это операция **записи** в кеш-линию, где лежит мьютекс.
3.  Протокол когерентности (MESI) инвалидирует эту кеш-линию на всех остальных 99 ядрах.
4.  **Результат:** Трафик шины процессора (Interconnect traffic) забит пересылкой этой кеш-линии. Производительность падает, несмотря на то, что логически никто данные не меняет.

**Вывод:** Даже Read-Lock — это Write с точки зрения железа. Нам нужно читать, *ничего не записывая*.

### 3.2. Latch Crabbing (Coupling) — Классический подход

Метод "спуска крабиком" (или "рука об руку"). Гарантирует, что мы всегда держим "якорь" выше, пока не захватим "якорь" ниже.

**Алгоритм (Поиск/Чтение):**
1.  `Lock(Parent, READ)`
2.  Находим, в какого ребенка идти.
3.  `Lock(Child, READ)`
4.  `Unlock(Parent)` — отпускаем верхнюю руку только тогда, когда схватились нижней.
5.  Повторять до листа.

**Алгоритм (Вставка/Запись):**
Здесь сложнее. Мы должны гарантировать, что Page Split (разделение страницы) не затронет разблокированных родителей.
*   *Safe Node:* Узел, в котором есть свободное место (не переполнится при вставке).
*   Мы спускаемся с `Write Lock`. Если встречаем *Safe Node*, мы можем разблокировать всех предков (так как сплит не пойдет выше этого узла).

**Недостаток:** Высокая нагрузка на блокировки (Lock Contention) на верхних уровнях дерева. Корень по-прежнему блокируется (пусть и ненадолго) каждым запросом.

### 3.3. Optimistic Lock Coupling (OLC) — Современный стандарт

Используется в **HyPer, Leis et al. (TUM)**, внедрено в DuckDB, LeanStore.
Это техника, позволяющая читать B-дерево, **вообще не создавая записей в память** (Zero writes for readers). Это дает линейную масштабируемость на любом количестве ядер.

**Суть (Versioned Latches):**
Вместо Мьютекса в каждом узле (странице) есть 64-битный атомарный счетчик `Version`.
*   Четное число: "Стабильно".
*   Нечетное число: "Идет модификация" (Locked).

**Алгоритм Читателя (Reader Protocol):**
Никаких блокировок. Только чтение и проверка версий.

1.  **Read Version (Start):**
    *   Читаем `v1 = node.version`.
    *   Если `v1` нечетное (узел залочен писателем) → Spin/Wait или Restart.
    *   *Memory Fence (Acquire):* Гарантируем, что мы не начнем читать данные *до* чтения версии.
2.  **Optimistic Read:**
    *   Читаем данные (ключи, указатели) в регистры или стек.
    *   *Важно:* Мы можем прочитать "мусор", если в этот момент писатель меняет страницу. Это нормально, главное не упасть (Segfault).
3.  **Validate Version (End):**
    *   *Memory Fence (Acquire):* Гарантируем, что чтение данных закончилось *до* проверки.
    *   Читаем `v2 = node.version`.
    *   **Check:** Если `v1 != v2`, значит, пока мы читали, пришел писатель и все испортил.
    *   **Action:** Отбрасываем прочитанное, прыгаем обратно к началу (Restart operation).

**Алгоритм Писателя (Writer Protocol):**
1.  Захватываем защелку: `CAS(version, v, v + 0b01)`. Версия становится нечетной.
2.  Меняем данные.
3.  Отпускаем защелку: `Store(version, v + 0b10)`. Версия становится четной (но больше на 2).

**Наглядный пример (C++ Pseudocode):**

```cpp
struct Node {
    std::atomic<uint64_t> version_lock;
    Key keys[M];
    Node* children[M];

    // Чтение без блокировок
    Node* find_child_optimistic(Key k) {
        while (true) {
            // 1. Читаем версию
            uint64_t v_start = version_lock.load(std::memory_order_acquire);
            
            // Если заблокировано (нечетное) - ждем (spin)
            if (v_start & 1) { _mm_pause(); continue; }

            // 2. Читаем данные (Спекулятивное выполнение)
            // Ищем нужного ребенка бинарным поиском
            Node* next = binary_search(keys, k); 

            // 3. Валидация
            std::atomic_thread_fence(std::memory_order_acquire); // Барьер
            uint64_t v_end = version_lock.load(std::memory_order_relaxed);

            // Если версии совпали - ура, мы прочитали консистентные данные
            if (v_start == v_end) {
                return next;
            }
            
            // Иначе: рестарт (данные были "грязными")
        }
    }
};
```

### 3.4. Почему OLC побеждает Latch Crabbing?

1.  **Cache Line State:** При OLC кеш-линия узла остается в состоянии **Shared (S)** протокола MESI. Ядра просто читают её. При Crabbing (Locking) линия переходит в **Modified (M)** при каждом захвате лока, заставляя другие ядра сбрасывать свои копии.
2.  **Scalability:** OLC позволяет 100 ядрам сканировать корень одновременно без деградации. Crabbing упирается в пропускную способность шины на корне.

### 3.5. B-Link Trees (Link Technique) — Для полноты картины

Это классика 80-х (Lehman & Yao), используемая в **PostgreSQL** и **WiredTiger (MongoDB)**.
*   **Идея:** Что, если мы пришли в узел, а он только что расщепился (Split)? Половина ключей уехала в новый узел-сосед справа.
*   **Решение:** Добавляем указатель `HighKey` и `RightSibling` (ссылку вправо).
*   Если мы ищем ключ `K`, и видим, что `K > HighKey` текущего узла, мы понимаем: "Ага, данные переехали". Мы просто идем по ссылке вправо (`RightSibling`), не поднимаясь к родителю.
*   Это позволяет **не блокировать родителя** при расщеплении ребенка.

### 3.6. Hardware Transactional Memory (HTM / Intel TSX)

Для архитектора уровня Principal стоит упомянуть, что была попытка решить это аппаратно (TSX instructions `xbegin`, `xend`).
*   Идея: Процессор сам следит за тем, читал ли кто-то нашу память, пока мы выполняли транзакцию.
*   **Реальность:** В большинстве баз данных (включая SAP HANA) от этого отказались или сделали опциональным из-за багов в процессорах и непредсказуемой производительности (частые `abort`). **OLC (программный подход) оказался надежнее.**

## 5. Чек-лист уровня Expert (Self-Check)

1.  **False Sharing:** Вы реализуете Lock-Free B-дерево. Как размещение `spinlock` прямо в заголовке узла (struct Node) может убить производительность на многопроцессорной системе?
    *   *Ответ:* Если два потока читают соседние узлы, которые случайно попали в одну Cache Line (64 байта), запись в спинлок одного узла инвалидирует кэш ядра, читающего другой узел. Решение: `alignas(64)` для критических структур.
2.  **Leaf Node Fragmentation:** Почему при удалении записи в B+ дереве БД (Postgres) не всегда происходит немедленное слияние (Merge) страниц, даже если они пустые наполовину?
    *   *Ответ:* "Lazy Merging". Слияние вызывает эксклюзивную блокировку на родителя и соседей. Чтобы избежать "thrashing" (вставили-разбили, удалили-слили), БД ждет, пока страница не опустеет до критического уровня (напр., 20%).
3.  **Adaptive Radix Tree (ART):** Слышали ли вы о ART (используется в HyPer)?
    *   Это гибрид trie и B-tree для RAM. Оно решает проблему длинных ключей (строк), имея высоту, зависящую от длины ключа, но с шириной узла 4, 16, 48, 256 детей (адаптивно). Это часто быстрее хеш-таблицы для упорядоченных данных.
4.  **Covering Index:** В чем физическая разница между `SELECT *` и `SELECT id` при наличии индекса по `id` в B+ дереве?
    *   *Ответ:* `Index Only Scan`. Если все запрашиваемые данные лежат в B-дереве индекса (в ключах или include-колонках), движок не ходит в основную кучу (Heap/Clustered Index). Это экономит 50% I/O.

*   **Пишете на C++ для HFT/GameDev?** Забудьте `std::map`. Возьмите `flat_map` (сортированный вектор) или B-tree библиотеку.

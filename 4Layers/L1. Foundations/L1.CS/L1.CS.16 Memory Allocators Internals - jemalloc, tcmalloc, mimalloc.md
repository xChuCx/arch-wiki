**TL;DR**: Стандартный системный аллокатор (glibc `malloc`) — это "универсал", который часто проигрывает в специализированных нагрузках. Для высоконагруженных серверов (High-Load C++/Rust/Java services) смена аллокатора на **jemalloc** или **mimalloc** может дать **-30% к RSS** и **+20% к Throughput** просто за счет `LD_PRELOAD`, без изменения единой строчки кода. Вы должны понимать *почему*, чтобы лечить "утечки памяти", которые на самом деле являются фрагментацией.

---

Как эксперт, вы должны понимать: `malloc` — это не просто "дай память". Это сложнейшая система управления ресурсами, решающая NP-трудную задачу упаковки (Bin Packing) в реальном времени, пытаясь угодить одновременно и по Latency, и по Throughput, и по RSS.

# 1. Архитектура: Где живут метаданные? (Memory Layout Internals)

Любой аллокатор обязан знать о выделенном блоке две вещи:
1.  **Размер блока** (чтобы `free(p)` знал, сколько байт вернуть).
2.  **Статус** (занят/свободен, чтобы избегать Double Free).

Существует два фундаментально разных архитектурных подхода к хранению этой информации. Выбор подхода определяет Cache Locality, накладные расходы на память (Memory Overhead) и устойчивость к эксплойтам.

## 1.1. In-band Metadata (Внутриполосное хранение)
*Классический подход: dlmalloc, ptmalloc (glibc default), ранние версии аллокаторов.*

Идея проста: хранить служебную информацию (Header) непосредственно **перед** указателем, который возвращается пользователю, и иногда **после** данных (Footer/Boundary Tag).

### Анатомия чанка в glibc (User View vs Allocator View)
Когда вы вызываете `ptr = malloc(32)`, аллокатор находит свободное место, но выделяет не 32 байта, а, например, 48.

```text
Память физически:
+-------------------+---------------------------+-------------------+
| Header (8-16 B)   | User Payload (32 Bytes)   | Padding (0-7 B)   |
+-------------------+---------------------------+-------------------+
^                   ^
|                   |
Адрес чанка         ptr (возвращается пользователю)
(p)                 (p + sizeof(Header))
```

**Header (Заголовок) обычно содержит:**
1.  **Size:** Размер текущего чанка.
2.  **Flags (в младших битах размера):**
    *   `P` (PREV_INUSE): Занят ли *предыдущий* физический сосед? (Критично для слияния).
    *   `M` (IS_MMAPPED): Выделен ли блок через `mmap`.
    *   `A` (NON_MAIN_ARENA): Принадлежит ли блок не главной арене.

**Механизм Boundary Tags (Граничные метки Кнута):**
Чтобы эффективно бороться с фрагментацией, аллокатор должен уметь **сливать** (coalesce) соседние свободные блоки.
*   Если я освобождаю блок `B`, и следующий за ним `C` свободен — я узнаю это из заголовка `C`.
*   А если свободен *предыдущий* блок `A`? Как мне найти его начало, чтобы объединиться?
    *   Для этого в конце каждого свободного блока пишется **Footer** (копия размера).
    *   Тогда `Address(A) = Address(B) - Size(Footer_of_A)`.

### Проблемы архитектуры In-band:
1.  **Уязвимость "Heap Overflow" (Off-by-one):**
    Злоумышленник пишет в свой массив `buf[i]` и выходит за границу всего на 1 байт. Он перезаписывает **Header следующего блока**.
    *   *Сценарий:* Меняем размер следующего блока. Когда следующий блок будет освобожден, аллокатор, доверяя (испорченному) заголовку, объединит его с куском памяти, который на самом деле занят другим объектом. Это ведет к **Overlapping Chunks** и удаленному исполнению кода (RCE).
2.  **Cache Pollution (Загрязнение кэша):**
    Аллокатор ищет свободный блок, пробегая по заголовкам. При этом в кэш процессора (L1) загружаются не только заголовки, но и (частично) пользовательские данные, лежащие рядом. Это вымывает полезные данные из кэша.
3.  **Alignment Padding:**
    Чтобы гарантировать выравнивание (например, 16 байт для SIMD инструкций), после заголовка часто приходится вставлять пустые байты (Padding), что увеличивает потребление памяти.

## 1.2. Out-of-band Metadata / BIBOP (Внеполосное хранение)
*Современный стандарт: jemalloc, tcmalloc, mimalloc, Go Runtime.*

**BIBOP** расшифровывается как **Big Bag Of Pages** (Большой мешок страниц).
Идея: Метаданные отделены от пользовательских данных. Мы группируем объекты одинакового размера в большие блоки (страницы/Slabs).

### Как это работает:
1.  Аллокатор берет страницу ОС (например, 4KB) или Huge Page (2MB).
2.  В **начале** страницы (или в отдельной структуре Descriptor) записывается Header Страницы.
3.  Всё остальное пространство страницы нарезается на объекты **фиксированного размера** (Size Class).

**Пример:** Страница для класса 32 байта.
```text
[ Page Header ] [ Obj 1 ] [ Obj 2 ] [ Obj 3 ] ... [ Obj N ]
    |               ^         ^
    |               |         |
    +-----> Знает: "Здесь лежат объекты по 32 байта"
            Bitmap занятости: 10110...
```

### Магия адресной арифметики (Address Masking)
Главный вопрос: Если у меня есть указатель `void* p`, как `free(p)` узнает размер объекта, если рядом с `p` нет заголовка?

Ответ: **Выравнивание (Alignment) и Маски.**
Страницы аллокатора всегда выровнены по своей границе (обычно 4KB, 64KB или 2MB).
Чтобы найти начало страницы (и её метаданные), достаточно обнулить младшие биты адреса.

**Пример для инженера:**
*   Размер страницы Slab: 4KB ($2^{12}$ байт = `0x1000`).
*   Указатель `p`: `0x7FFFAB041240`.
*   Маска: `~(4096 - 1)` = `0xFFFFFFFFFFFFF000`.
*   Адрес заголовка страницы: `p & Mask` = `0x7FFFAB041000`.

По этому адресу аллокатор читает структуру `SlabHeader`, в которой написано: `size_class = 32`.
Все вычисления занимают 2-3 такта CPU (bitwise AND).

### Преимущества BIBOP:
1.  **Zero Per-Object Overhead:**
    Для мелких объектов (например, 16 байт) в In-band подходе заголовок (8-16 байт) съедал бы 50-100% лишней памяти. В BIBOP заголовок один на сотню объектов. Экономия памяти колоссальная.
2.  **Безопасность (Hardening):**
    Переполнение буфера в `Obj 1` затрет `Obj 2`, но **не затрет метаданные** (размер класса, списки свободных блоков), так как они лежат в начале страницы или вообще в другом месте памяти (radix-tree в jemalloc). Структурная целостность кучи сохраняется.
3.  **Cache Locality при аллокации:**
    Чтобы найти свободный слот, аллокатор сканирует **Bitmap** в заголовке страницы (или Free List head). Это компактные данные, которые отлично ложатся в L1 кэш, не затрагивая сами объекты ("холодные" данные не трогаются).

### Недостаток (Gap Analysis):
Если на странице размером 16KB, нарезанной на блоки по 1KB, занят всего **один** блок, вся страница (16KB) обязана быть в памяти (RSS). В In-band подходе пустые места могли быть слиты с соседями и возвращены. Это решается механизмами *Slab Release* и *Purging*, но это сложнее в реализации.

---
### Резюме для Эксперта

| Характеристика | In-band (glibc/malloc) | Out-of-band / BIBOP (jemalloc/mimalloc) |
| :--- | :--- | :--- |
| **Определение размера** | Чтение `Header` по адресу `p - sizeof(Header)` | Битовая маска адреса `p & Mask` -> Page Header |
| **Overhead на объект** | Высокий (Header + Padding для каждого объекта) | Низкий (Амортизируется на всю страницу) |
| **Locality** | Spatial (Header рядом с данными), но Cache Pollution при поиске | Отличная (Meta отделена от Data) |
| **Уязвимость** | Heap Overflow ломает структуру кучи (Metadata Corruption) | Heap Overflow ломает данные соседей, но куча жива |
| **Сценарий использования** | General Purpose, десктоп, legacy | High-Load серверы, многопоточность, мелкие объекты |

## 2. Remote Free: Главная архитектурная боль (Cross-thread Deallocation)

**Определение:** *Remote Free* (или Cross-thread deallocation) — это сценарий, когда память выделяется (malloc) в потоке $T_A$, а освобождается (free) в потоке $T_B$.

**Типовой сценарий:** Паттерн "Producer-Consumer".
*   **IO Thread ($T_A$):** Читает байты из сокета, выделяет буфер, передает его в очередь задач.
*   **Worker Thread ($T_B$):** Забирает задачу, обрабатывает, отправляет ответ и вызывает `free()` для буфера.

### 2.1. Почему это сложно? (Физика кэшей и MESI)

Проблема не только в мьютексах (Locks). Проблема в **Cache Coherency** (когерентности кэшей).

Каждый аллокатор стремится вернуть освобожденный блок в *тот же* пул, откуда он был взят (чтобы избежать фрагментации и повторно использовать горячую память).
1.  Блок принадлежит "Арене" или "Кэшу" потока $T_A$.
2.  Метаданные этого списка свободных блоков находятся в L1/L2 кэше ядра, где работает $T_A$.
3.  Поток $T_B$ (на другом ядре) пытается записать в эти метаданные ("Я возвращаю тебе блок!").

**Эффект:**
*   **RFO (Request For Ownership):** Ядро $T_B$ посылает сигнал шине процессора, требуя эксклюзивного доступа к кэш-линии метаданных $T_A$.
*   **Cache Invalidation:** Ядро $T_A$ вынуждено сбросить свои горячие кэш-линии.
*   **Ping-Pong:** Если $T_B$ и $T_C$ постоянно освобождают память $T_A$, кэш-линия "скачет" между ядрами. Это убивает производительность в 10-100 раз эффективнее, чем простое ожидание лока.

---
### 2.2. Эволюция решений: От Блокировок к Атомикам

Как современные аллокаторы решают эту проблему? Рассмотрим три поколения архитектур.

#### Gen 1: Global/Arena Locking (Наивный подход)
*   **Механизм:** $T_B$ определяет, что блок принадлежит Арене $A$. $T_B$ берет `SpinLock` этой арены, кладет блок в список, отпускает лок.
*   **Проблема:** Lock Contention. Если у вас 1 Producer (IO) и 100 Consumers (Workers), все 100 воркеров будут драться за лок одной арены IO-потока.
*   **Где встречается:** Старые версии glibc `malloc`.

#### Gen 2: Batched Remote Lists (Подход Jemalloc)
*   **Идея:** "Не буди спящего". Не трогай структуры $T_A$ сразу.
*   **Механизм:**
    1.  В потоке $T_B$ есть специальный "Remote Free List" (почтовый ящик) для объектов, принадлежащих $T_A$.
    2.  $T_B$ кладет указатели в этот локальный список (быстро, без конкуренции).
    3.  Когда список накапливается (Batching), $T_B$ захватывает лок $T_A$ и переносит *сразу пачку* (например, 100 объектов).
*   **Баланс:** Снижает частоту локов в $N$ раз.
*   **Минус:** **Memory Drift**. Память уже освобождена логически, но поток $T_A$ еще не знает об этом и не может её переиспользовать, пока не заберет "почту". Это может временно раздувать RSS.

#### Gen 3: Wait-Free Atomic Lists (Подход Mimalloc / Snmalloc)
*   **Идея:** Использовать атомарные инструкции процессора вместо локов.
*   **Анатомия страницы (Mimalloc Page):**
    У каждой страницы памяти (Page), принадлежащей потоку $T_A$, есть два списка:
    1.  **Local Free List:** Приватный список $T_A$. Работает без синхронизации.
    2.  **Thread Free List (Shared):** Список для "чужаков".
*   **Механизм ($T_B$ делает free):**
    *   $T_B$ определяет страницу. Видит, что он не владелец.
    *   Выполняет **Atomic CAS (Compare-And-Swap)** или **Atomic Exchange**, добавляя блок в голову *Thread Free List*.
    *   Это **Wait-Free** операция (гарантированное завершение за конечное число шагов, никаких syscalls).
*   **Механизм ($T_A$ делает malloc):**
    *   Когда у $T_A$ заканчивается место в *Local Free List*, он проверяет *Thread Free List*.
    *   **Atomic Take-All:** $T_A$ одной инструкцией забирает *весь* цепочечный список от чужаков, перемещает его в свой локальный список и продолжает работу.
*   **Результат:** Нулевое ожидание для $T_B$. Минимальный оверхед для $T_A$.

### 2.3. Иллюстрация и Терминология

Для полного понимания рассмотрим пример на псевдокоде (логика Mimalloc).

**Термины:**
*   **Owning Thread:** Поток, который создал страницу памяти.
*   **Sharded Free List:** Разделение списка свободных слотов на "свой" и "чужой".

```cpp
// Структура страницы памяти (упрощенно)
struct HeapPage {
    Thread* owner;              // Кто создал
    FreeBlock* local_free;      // Приватный список (L1 cache friendly)
    std::atomic<FreeBlock*> thread_free; // Публичный список (Atomic access)
};

// Сценарий: Поток B освобождает память, созданную Потоком A
void free(void* ptr) {
    HeapPage* page = get_page_header(ptr); // Битовая маска адреса
    
    if (page->owner == current_thread()) {
        // Fast path: Вернули себе в кеш
        push_to_list(page->local_free, ptr); 
    } else {
        // Remote Free (Wait-Free Path)
        // Атомарно добавляем в начало чужого списка
        FreeBlock* expected = page->thread_free.load();
        do {
            ptr->next = expected;
        } while (!page->thread_free.compare_exchange_weak(expected, ptr));
    }
}

// Сценарий: Поток A выделяет память
void* malloc(size_t size) {
    // ... поиск страницы ...
    if (page->local_free == nullptr) {
        // Локальный кеш пуст. Проверим, вернули ли нам что-то соседи?
        
        // Атомарно забираем ВЕСЬ список (обнуляем thread_free)
        // Это стоит дорого (атомик), но делается редко (раз на пачку аллокаций)
        FreeBlock* returned_batch = page->thread_free.exchange(nullptr);
        
        if (returned_batch) {
            page->local_free = returned_batch; // Теперь это наши локальные данные
        } else {
            // Реально нет места, просим новую страницу у Арены
        }
    }
    return pop_from_list(page->local_free);
}
```

### 2.4. Инсайт для Архитектора

Почему это важно знать?

1.  **Паттерн архитектуры:** Если ваша система построена на принципе "Один поток выделяет, другой освобождает" (например, pipeline architecture), **не используйте стандартный `glibc malloc`**. Он оптимизирован под сценарий "кто выделил, тот и удалил". В сценарии перекрестного освобождения он деградирует из-за конкуренции за локи арен.
2.  **Выбор аллокатора:**
    *   **Jemalloc:** Хорош для смешанных нагрузок, но имеет небольшую задержку возврата памяти из-за батчинга.
    *   **Mimalloc:** Идеален для сценариев с массивным Remote Free (Actor systems, Game Servers), так как атомарный список обеспечивает предсказуемую латентность без спайков блокировок.
3.  **Локальность данных:** Даже с lock-free алгоритмами, Remote Free разрушает локальность. Данные, созданные на ядре 1 и освобожденные на ядре 2, приводят к миграции кэш-линий. В идеальной архитектуре (Share Nothing) поток должен сам освобождать то, что выделил, либо переиспользовать объекты (Object Pooling), чтобы не дергать аллокатор вовсе.

## 3. Deep Dive: jemalloc — Архитектура и Механизмы

Jemalloc — это аллокатор с **ориентацией на экстенты** (extent-based), который делает сильный акцент на локальность данных и минимизацию системных вызовов через умный механизм "распада" (decay).

### 3.1. Иерархия памяти: Arena, Bin, Extent, Slab

Забудьте упрощенную модель "кучи". В jemalloc память имеет строгую иерархию.

1.  **Arenas (Арены):**
    *   Это независимые зоны памяти. Чтобы избежать блокировок (Global Lock), потоки распределяются по аренам (обычно $4 \times N_{cpu}$).
    *   Поток привязывается к арене жестко (round-robin или хешированием), но может мигрировать.
    *   **Роль:** Управление метаданными и свободными списками для привязанных потоков.

2.  **Size Classes (Классы размеров):**
    *   Jemalloc не выдает произвольные куски. Все запросы округляются.
    *   **Small:** Объекты меньше размера страницы (обычно < 4KB). Хранятся в **Bins**.
    *   **Large:** Объекты больше страницы. Хранятся в собственных экстентах.
    *   *Пример:* Запрос 45 байт $\to$ класс 48 байт. Запрос 100 байт $\to$ класс 128 байт. Это минимизирует **внутреннюю фрагментацию**.

3.  **Bins (Корзины) и Slabs (Слябы):**
    *   Для каждого класса размеров (Small) внутри Арены есть свой **Bin**.
    *   Bin управляет набором **Slabs**.
    *   **Slab** — это непрерывный кусок памяти (обычно страница 4KB или несколько), нарезанный на объекты *одного* размера.
    *   *Визуализация:* Slab для класса 64 байта — это массив `[64][64]...[64]`.
    *   **Bitmap:** В начале сляба (или в метаданных) есть битовая карта занятости. Поиск свободного слота — это быстрые битовые операции (FFS - Find First Set bit).

4.  **Extents (Экстенты):**
    *   *Важное уточнение:* В старых версиях (до 5.0) это называлось **Chunks**. Теперь это **Extents**.
    *   Это базовые блоки виртуальной памяти, которые jemalloc запрашивает у ОС (через `mmap`).
    *   Экстенты могут быть разного размера (Dynamic sizing), но стремятся к выравниванию (обычно 2MB для поддержки Huge Pages).
    *   Extent может работать как Slab (быть нарезанным на мелкие объекты) или целиком хранить один Large объект.

### 3.2. Алгоритм Аллокации (Hot Path)

Что происходит, когда вы пишете `malloc(size)`?

1.  **Tcache Lookup (Fast Path, ~2-5ns):**
    *   Проверяем Thread Local Cache (Tcache) текущего потока для нужного size class.
    *   Если есть свободный слот — возвращаем указатель. **Никаких локов, никаких атомиков.** Это уровень L1/L2 кэша.

2.  **Tcache Refill (Slow Path):**
    *   Если Tcache пуст, мы идем в **Arena Bin**.
    *   Берем **Arena Lock** (блокировка на уровне бина, не глобальная!).
    *   Перемещаем пачку объектов из Slab в Tcache (batch fill). Мы берем не 1 объект, а сразу N, чтобы амортизировать стоимость взятия лока.

3.  **Arena Allocation (Hard Path):**
    *   Если в Bin нет свободных Slab'ов, берем **новый Extent** из списка свободных экстентов арены.
    *   Тут в игру вступают **Red-Black Trees** (или Pairing Heaps в новых версиях). Jemalloc ищет экстент по стратегии **Best Fit** (наилучшее совпадение по размеру) и **Lowest Address** (чтобы держать кучу компактной).

---
### 3.3. Dirty Page Decay: Умный возврат памяти

В отличие от `glibc`, который часто держит память "про запас" до перезапуска, или `tcmalloc`, который исторически был "жадным", jemalloc реализует **временнóй распад**.

**Терминология:**
*   **Active:** Память, в которой лежат живые объекты приложения.
*   **Dirty:** Страницы, которые приложение освободило (`free`), но jemalloc еще не вернул операционной системе. В них лежит "мусор".
*   **Muzzy (в новых версиях):** Промежуточное состояние (устаревает, но еще не сброшено).
*   **Retained:** Виртуальная память зарезервирована за процессом, но физические страницы (RSS) возвращены ядру.

**Механизм Decay (Smooth Sigmoid Curve):**
Jemalloc не возвращает память сразу (это вызовет шквал `mmap`/`munmap` syscalls). Он использует **Epochs** (эпохи времени).
Параметр `dirty_decay_ms` (по умолчанию 10 сек) определяет кривую.
*   Если вы освободили 1GB памяти, jemalloc начнет возвращать её ОС не мгновенно, а плавно в течение 10 секунд.
*   Это "сглаживает" нагрузку на CPU (меньше TLB shootdowns и page faults).

**Системный вызов:**
Когда страница "сгнила" (expired), jemalloc вызывает:
*   `madvise(..., MADV_DONTNEED)`: Ядро немедленно забирает физическую страницу. RSS падает. Следующий доступ — Page Fault (Zero page).
*   *Или* `madvise(..., MADV_FREE)` (если включено и ядро 4.5+): Ядро помечает страницу как "кандидат на удаление". RSS **не падает**! Память заберется только при нехватке RAM в системе.
    *   *Инсайт эксперта:* Это частая причина паники: "У нас утечка, RSS плато!". На самом деле это `MADV_FREE`. Проверяйте `/proc/PID/smaps_rollup` -> `LazyFree`.

### 3.4. Profiling (Heap Introspection)

Jemalloc имеет **встроенный семплирующий профайлер**. Это киллер-фича для продакшена.

Как это работает:
1.  Вы не платите оверхед за трекинг *каждого* байта.
2.  Jemalloc использует счетчик байт на аллокацию. Когда счетчик переполняется (порог `lg_prof_sample`, по умолчанию 512KB), текущая аллокация помечается.
3.  Сохраняется Stack Trace (backtrace) вызова.
4.  Статистика экстраполируется.

**Пример использования:**
Запуск приложения:
`MALLOC_CONF=prof:true,lg_prof_interval:30 ./my_app`
Это создаст дамп `jeprof.out.<pid>.<seq>` каждые 1GB ($2^{30}$ байт) выделенной памяти.

Анализ:
`jeprof --svg ./my_app jeprof.out.123 > graph.svg`
Вы получите граф вызовов, где видно не только кто *выделил* память, но и (что важнее) кто её *держит* прямо сейчас.

### 3.5. Сравнение с "Наивным" подходом

| Характеристика | Naive Allocator | Jemalloc | Почему важно для эксперта? |
| :--- | :--- | :--- | :--- |
| **Метаданные** | Заголовки перед объектом | Отдельно (в начале Slab/Extent) | Защита от heap overflow и Cache Locality. |
| **Поиск места** | First Fit (линейный скан) | Segregated Lists + Bitmaps | $O(1)$ для малых объектов, нет фрагментации. |

| **Многопоточность** | Global Lock (mutex) | Distributed Arenas + Lockless Tcache | Линейная масштабируемость на 100+ ядер. |

### Резюме для Архитектора

Переключение на **jemalloc** — это не просто оптимизация производительности. Это изменение **паттерна потребления ресурсов**:
1.  **Стабильный RSS:** Вместо пилообразного графика ("выделили-освободили") вы получаете плавный график благодаря Decay.
2.  **Предсказуемая латентность:** Tcache берет на себя 95% операций, делая их lock-free.
3.  **Наблюдаемость:** Возможность снять профиль памяти с живого продакшена без остановки сервиса.

### 4. Tcmalloc (Thread-Caching Malloc) 

**Tcmalloc** (разработка Google) — это аллокатор, созданный с одной целью: **максимальная скорость аллокации мелких объектов** в многопоточных C++ приложениях. Если jemalloc — это "умный" баланс, то tcmalloc — это "гоночный болид", который жертвует потреблением виртуальной памяти ради наносекунд.

#### 4.1. Архитектура: Три уровня кеширования (The 3-Tier Model)

Tcmalloc переносит сложность из "горячего пути" (Hot Path) в "холодный". Поток данных движется через три слоя:

1.  **Front-end (Thread Cache / Per-CPU Cache):**
    *   Самый быстрый слой. **Zero Locks**.
    *   Обслуживает 99% запросов `malloc`/`free` для мелких объектов.
    *   Если есть свободный слот нужного размера — возвращаем указатель. Время: ~5-10 нс (несколько инструкций CPU).
    
2.  **Middle-end (Transfer Cache & Central Free List):**
    *   Управляет **Spans** (Спенами) — наборами непрерывных страниц.
    *   Защищен спинлоками (Spinlocks), не мьютексами, так как операции очень быстрые.
    *   Разделен на **Size Classes**: для каждого размера (например, 32 байта, 48 байт) свой отдельный список и свой лок. Это называется **Fine-Grained Locking**.

3.  **Back-end (Page Heap):**
    *   Взаимодействует с ОС (`mmap`/`sbrk`).
    *   Хранит большие куски памяти (Spans) и занимается их нарезкой или объединением (Coalescing).
    *   Здесь живет глобальный лок (PageHeap Lock), но обращение к нему происходит редко.

#### 4.2. Ключевая концепция: The Span (Спен)

В отличие от `glibc`, который оперирует абстрактными "чанками", tcmalloc мыслит страницами (обычно 8KB).

*   **Определение:** **Span** — это непрерывный диапазон из $N$ страниц ($N \ge 1$).
*   **Состояния Спена:**
    1.  **Allocated:** Спен отдан приложению как один большой объект (Large Object allocation > 256KB).
    2.  **Split:** Спен нарезан на кучу мелких объектов одного Size Class (например, нарезали 8KB страницу на 128 блоков по 64 байта). Метаданные Спена хранят Bitmap или FreeList свободных объектов внутри него.
    3.  **Free:** Спен свободен и лежит в Page Heap, ожидая использования или возврата ОС.

**Инсайт для эксперта:** Метаданные Спенов хранятся не в самих страницах (Out-of-band), а в отдельном **Page Map** (Radix Tree). Это позволяет проверить свойства любого указателя за $O(1)$ без разыменования самого указателя (безопасность!).

#### 4.3. Инновация: Per-CPU Caches и `rseq` (Restartable Sequences)

Классический tcmalloc использовал **Thread-Local Storage (TLS)**.
*   *Проблема:* У вас микросервис на 2000 горутин или потоков (Java/Go/C++ fibers). Каждый поток хочет свой кеш. Даже если кеш пуст, метаданные занимают память.
*   *Результат:* Огромный Overhead по памяти (Metadata fragmentation).

**Современное решение (Google Temeraire):**
Вместо кеша на *поток*, tcmalloc использует кеш на **физическое ядро CPU**.
*   **Как это работает без локов?** Используется системный вызов Linux `rseq` (доступен с ядра 4.18).
*   **Механика:** Поток начинает операцию с кешем CPU #3. Если в середине операции ОС переключает контекст (Preemption) и переносит поток на CPU #4, транзакция `rseq` отменяется и перезапускается атомарно.
*   **Выигрыш:** Потребление памяти под кеши больше не зависит от числа потоков. Вы можете запустить 100,000 потоков, но если у вас 64 ядра, будет всего 64 кеша.

#### 4.4. Transfer Cache: Решение проблемы Producer-Consumer

Представьте паттерн:
*   **Thread A (Producer):** Генерирует задачи (Alloc).
*   **Thread B (Consumer):** Обрабатывает и удаляет (Free).

В наивной реализации Thread B быстро переполнит свой локальный кеш и пойдет возвращать объекты в Central List (Lock). Thread A исчерпает свой кеш и пойдет забирать из Central List (Lock).
**Результат:** Contention на Central List.

**Решение (Transfer Cache):**
Это промежуточный буфер.
*   Когда Thread B переполнен, он сбрасывает пачку указателей в Transfer Cache.
*   Когда Thread A голоден, он сначала проверяет Transfer Cache.
*   Это позволяет передавать память между потоками **минуя** тяжелые операции с Central Free List (разборка/сборка Spans, битовые маски). Это просто перекладывание указателей в массиве.

#### 4.5. Virtual Memory Bloat (Почему VIRT такой большой?)

Админы часто пугаются, видя VIRT usage под 10TB у процесса с tcmalloc.
*   **Причина:** Для быстрого маппинга `Pointer -> Page -> Span`, tcmalloc резервирует (но не коммитит!) адресное пространство под Page Map.
*   В 64-битных системах это бесплатно для физической памяти (RSS не растет), но VIRT огромен.
*   **Expert Check:** Если RSS нормальный, а VIRT огромный — это нормальное поведение tcmalloc. Не настраивайте алерты на VIRT.

#### 4.6. Пример: Аллокация 30 байт

1.  **Rounding:** 30 байт округляются до Size Class 32.
2.  **Front-end (Fast Path):**
    *   Проверяем Per-CPU cache текущего ядра для класса 32.
    *   Есть свободный блок? Декрементируем счетчик, возвращаем ptr. **Done.** (~5 ns).
3.  **Middle-end (Slow Path 1):**
    *   Кеш пуст. Берем лок Central Cache для класса 32.
    *   Ищем непустой Span. Берем оттуда `Batch Size` (например, 32 объекта) объектов.
    *   Переносим их в Front-end. Один возвращаем юзеру.
4.  **Back-end (Slow Path 2):**
    *   Central Cache пуст. Нужны новые страницы.
    *   Идем в Page Heap. Просим 1 страницу (Span length = 1).
    *   Page Heap ищет свободный Span в списке свободных. Если нет — делает `mmap`.
    *   Центральный кеш нарезает этот Span на объекты по 32 байта.

### Резюме для Архитектора

*   **Когда выбирать tcmalloc:**
    *   C++ сервисы с интенсивной многопоточностью.
    *   Высокая частота аллокаций мелких объектов (Protobuf, string processing).
    *   Вы можете использовать свежую версию с поддержкой `rseq` (иначе рискуете памятью на большом числе потоков).
*   **Когда избегать:**
    *   Системы с жестким лимитом по памяти (Embedded). tcmalloc склонен "кэшировать всё".
    *   Если вам нужен агрессивный возврат памяти ОС (jemalloc с этим справляется гибче).

## 5. Mimalloc: (Compact & Local)

Разработанный Daan Leijen (Microsoft Research), mimalloc (2019) переосмыслил подход к аллокации. Если jemalloc — это "комбайн" для серверов, то mimalloc — это "снайперская винтовка", ориентированная на **локальность данных** и **бесплатную безопасность**.

### 5.1. Архитектура: Heap $\to$ Segment $\to$ Page $\to$ Block
В отличие от классических аллокаторов, mimalloc делает ставку на малые, жестко типизированные по размеру страницы.

1.  **Thread Local Heap (TLH):** У каждого потока есть своя куча. Это структура данных, содержащая массив списков свободных страниц для каждого класса размеров (Size Class).
2.  **Segment (Сегмент):** Большой блок памяти (обычно 4MB или 64MB), выделяемый у ОС.
3.  **Page (Страница mimalloc):** Сегмент нарезается на страницы по **64 KB**.
    *   Это **не** страница ОС (4KB). Это логическая единица mimalloc.
    *   **Ключевой инсайт:** Одна страница (64KB) содержит блоки *только одного размера* (например, только 32-байтные).
    *   Страница "принадлежит" тому потоку, который её создал.

**Почему 64KB?** Это достаточно мало, чтобы страница быстро заполнялась и освобождалась (снижение фрагментации), но достаточно много, чтобы амортизировать накладные расходы на метаданные.

### 5.2. Free List Sharding: Механика "Без блокировок"
Это самая инновационная часть. Проблема любого аллокатора — **Producer-Consumer паттерн**: Поток A выделяет объект, передает его Потоку B, Поток B его освобождает.

В mimalloc у каждой Страницы есть **три** списка свободных блоков:

1.  **Local Free List:** Обычный односвязный список.
    *   Используется только **владельцем** страницы (Потоком A).
    *   Операции `malloc` и `free` (если поток тот же) — это просто чтение/запись регистра головы списка. **Никаких атомиков. Строгое $O(1)$.**
2.  **Thread Free List:** Атомарный список.
    *   Сюда пишут **другие** потоки (Поток B), когда освобождают объект, принадлежащий Потоку A.
    *   Используется инструкция `Atomic Push` (CAS или LL/SC). Это **Wait-Free** операция для Потока B.
3.  **Full List:** Список полностью свободных страниц (для возврата ОС).

#### Алгоритм "Heartbeat" (Отложенная сборка)
Поток A (владелец) **игнорирует** Thread Free List (тот, куда пишет Поток B), пока у него есть место в Local Free List.

*   **Сценарий:**
    1.  Поток A исчерпал свой локальный список свободных блоков.
    2.  Только тогда ("Heartbeat event") он **атомарно забирает** весь Thread Free List, который накопил Поток B.
    3.  Поток A превращает этот список в свой новый Local Free List.

**Результат:** Дорогостоящая атомарная синхронизация происходит не на каждый `remote free`, а *пачками*. Это радикально снижает нагрузку на шину процессора (Inter-Core Traffic) в высоконагруженных системах.

### 5.3. Security: Защита "из коробки"
В эпоху C++ уязвимостей, mimalloc — первый аллокатор общего назначения, который включает защиту по умолчанию без падения производительности.

**Free List Poisoning / Hardening:**
В классическом `dlmalloc`/`glibc` в освобожденном блоке лежит "голый" указатель на следующий свободный блок (`next_ptr`).
*   **Атака:** Хакер через переполнение буфера (Buffer Overflow) перезаписывает `next_ptr` на адрес своей функции. При следующей аллокации программа прыгнет по этому адресу.

**Решение Mimalloc (Encoded Pointers):**
Указатель `next` хранится в зашифрованном виде:
$$ \text{StoredValue} = \text{NextPtr} \oplus \text{SecretKey} \oplus \text{BlockAddress} $$

*   **SecretKey:** Генерируется случайно при старте процесса (ASLR-like).
*   **BlockAddress:** Адрес текущего блока.
*   **XOR ($\oplus$):** Быстрая операция.

Если злоумышленник перезапишет `StoredValue` (даже зная адрес), он не знает `SecretKey`. При декодировании (`Value ^ Key ^ Addr`) получится мусорный адрес. При попытке доступа к нему процесс упадет с `Segmentation Fault`.
**Это превращает RCE (Remote Code Execution) в DoS (Crash), что намного безопаснее.**

### 5.4. Пример для наглядности: HTTP-сервер

Представьте веб-сервер на C++ (или Rust/Node.js).

1.  **Request Thread (Поток A):** Принимает соединение, парсит JSON, выделяет объект `HttpRequest` (размер 128 байт).
    *   Mimalloc берет блок из *локальной* страницы Потока A. Это занимает ~4 наносекунды (как инкремент переменной).
    *   Все поля объекта лежат в одной кэш-линии (Spatial Locality).
2.  **Worker Thread (Поток B):** Обрабатывает запрос, отправляет ответ и делает `delete request`.
    *   Поток B видит, что страница принадлежит Потоку A.
    *   Делает *атомарный CAS*, добавляя блок в `Thread Free List` страницы Потока A.
    *   Поток B **не ждет** никаких локов арены (как в glibc). Он не мешает Потоку A работать.
3.  **Возврат:** Когда Поток A обработает еще 100 запросов и исчерпает свою страницу, он "одним махом" заберет объект, освобожденный Потоком B, и снова пустит его в дело.

### 5.5. Границы применимости (Когда НЕ использовать)
*   **Legacy Systems:** Mimalloc требует поддержки атомиков на уровне CPU (современные x64/ARM). На древних архитектурах (MIPS/SPARC) он может не собраться или работать медленно.
*   **Extreme Memory Constrains:** Из-за структуры "64KB Page на каждый Size Class на каждый поток", mimalloc может потреблять чуть больше памяти на старте (Startup RSS), чем минималистичный аллокатор, если у вас тысячи "спящих" потоков. Хотя `mimalloc` умеет возвращать страницы ОС (`mimalloc-page-reset`), на "холодном" старте потребление выше.

**Вердикт Эксперта:** Для новых проектов на C++, Rust или бэкендов на Node.js/Python (через подмену библиотек), mimalloc — это **дефолтный выбор** в 2024+ году. Он дает +10-15% перформанса "бесплатно" и защищает от класса уязвимостей.

## 6. OS Internals: Huge Pages, TLB и "Налог на память"

Чтобы понять, зачем нужны Huge Pages (и почему они опасны), нужно спуститься на уровень кремния — в **MMU (Memory Management Unit)**.

### 6.1. Физика процесса: Page Table Walk и TLB Reach

В архитектуре x86-64 доступ к памяти не прямой. Виртуальный адрес (который видит ваша программа) должен быть транслирован в физический.

1.  **Page Table Walk (PTW):** Это "налог", который платит процессор. Чтобы найти физический адрес для одной переменной, CPU должен прочитать **4 уровня таблиц страниц** в памяти (L4 $\to$ L3 $\to$ L2 $\to$ L1).
    *   *Худший сценарий:* Одно чтение переменной превращается в **5 чтений из RAM** (4 чтения структуры таблиц + 1 чтение данных). Это катастрофа для Latency.
2.  **TLB (Translation Lookaside Buffer):** Кэш внутри CPU, хранящий последние трансляции. Если адрес есть в TLB — доступ мгновенный ($O(1)$). Если нет (TLB Miss) — включается дорогой PTW.

**Проблема 4KB страниц (Small Pages):**
Стандартная страница — 4 КБ (4096 байт).
*   Типичный размер L1 TLB (Data) — 64 записи.
*   **TLB Reach (Охват):** $64 \times 4 \text{ KB} = 256 \text{ KB}$.
*   *Вывод:* Если ваше приложение активно работает с массивом данных больше 256 КБ (что смешно для современных серверов), вы постоянно получаете TLB Misses. Процессор тратит до 20-30% времени просто на то, чтобы понять, *где* лежат данные.

**Решение 2MB страниц (Huge Pages):**
*   Типичный размер L1 TLB для Huge Pages — 32 записи.
*   **TLB Reach:** $32 \times 2 \text{ MB} = 64 \text{ MB}$.
*   *Результат:* Охват увеличивается в 256 раз. Количество промахов падает, CPU занимается вычислениями, а не хождением по таблицам.

### 6.2. Transparent Huge Pages (THP): Скрытая угроза

Linux пытается помочь автоматически через механизм **THP**. Ядро запускает фоновый тред `khugepaged`, который ищет подряд идущие 512 страниц по 4KB и склеивает их в одну 2MB страницу.

**Термины и риски:**

1.  **System Stall / Latency Spikes:**
    *   Когда приложение запрашивает память (Page Fault), и THP включен в режим `always`, ядро может попытаться выделить сразу 2MB.
    *   Если свободной непрерывной памяти 2MB нет (память фрагментирована), ядро запускает **Direct Compaction** (дефрагментацию "на лету").
    *   **Эффект:** Ваш поток `malloc()` замораживается на десятки миллисекунд, пока ядро двигает страницы других процессов. Для Redis или HFT это неприемлемо.

2.  **Memory Bloat (Раздувание памяти):**
    *   THP работает грубо. Если вы выделили 100 КБ данных, но попали под THP, ядро выделит вам 2 МБ.
    *   *Хвост:* 1.9 МБ физической памяти (RSS) будут заняты нулями, просто потому что "минимальный квант" теперь огромный.

**Инсайт Эксперта:** Именно поэтому базы данных (Oracle, Postgres, Redis, MongoDB) в своих Best Practices **требуют** отключать системный THP (`/sys/kernel/mm/transparent_hugepage/enabled = madvise`). Они хотят контролировать использование Huge Pages сами (через `madvise` или Explicit Huge Pages).

### 6.3. Взаимодействие Аллокатора и Huge Pages (Huge Page Fragmentation)

Современные аллокаторы (jemalloc 5+, tcmalloc) умеют работать с Huge Pages, но сталкиваются с фундаментальной проблемой фрагментации внутри огромной страницы.

**Пример (Сценарий "Швейцарский сыр"):**
Представьте одну 2MB страницу (Huge Page), которой управляет аллокатор.
1.  Аллокатор нарезал её на 32,000 объектов по 64 байта.
2.  Приложение заполнило их данными. RSS = 2MB.
3.  Со временем приложение освободило 31,999 объектов. Остался жив **один** маленький объект (64 байта) в середине страницы.

**Проблема:**
ОС не умеет выгружать "часть" Huge Page.
*   Пока жив хоть 1 байт на странице, вся страница (2 MB) должна находиться в физической памяти (RAM).
*   **Fragmentation Ratio:** Полезная нагрузка 64 байта / Занято 2 МБ $\approx$ 99.999% потерь.

**Как с этим борются аллокаторы (HPA - Huge Page Allocator):**
Jemalloc и tcmalloc реализуют сложные эвристики:
1.  **Grouping:** Они стараются селить долгоживущие объекты отдельно от короткоживущих.
2.  **Breaking (Расщепление):** Если на 2MB странице слишком много пустот, аллокатор может попросить ядро (через `madvise`) разбить её обратно на 4KB страницы, чтобы вернуть системе пустые куски. Это дорогая операция.

### 6.4. Copy-on-Write (COW) Faults: Кошмар для Redis

Для процессов, использующих `fork()` (например, Redis для создания снапшотов RDB/AOF), Huge Pages — это зло.

**Механизм:**
1.  Redis делает `fork()`. Дочерний процесс получает копию таблицы страниц родителя (COW). Память общая (Read-only).
2.  Родитель меняет **1 байт** в данных.
3.  Процессор вызывает Page Fault (защита записи). Ядро должно скопировать страницу для дочернего процесса.

**Сценарий с 4KB:** Ядро копирует 4 КБ. Быстро (микросекунды).
**Сценарий с THP (2MB):** Ядро копирует 2 МБ. Медленно.
*   **Результат:** Write Latency родительского процесса подскакивает. Память удваивается гораздо быстрее.

---
### Практическое руководство (Что делать инженеру)

1.  **Для Java/Go/Node.js (General Purpose):**
    *   Обычно оставляют THP `madvise`. Аллокаторы (Go runtime, jemalloc) сами решат, когда просить Huge Pages для больших арен, не блокируя систему.

2.  **Для Баз Данных (Latency Sensitive):**
    *   **Disable THP:** `echo never > /sys/kernel/mm/transparent_hugepage/enabled`.
    *   Используйте **Explicit Huge Pages** (HugeTLBfs), если база это поддерживает (Postgres `huge_pages = on`), это резервирует память на старте и гарантирует отсутствие фрагментации и свапа.

3.  **Для C++ (High Performance):**
    *   Используйте `jemalloc` с опцией `metadata_thp:auto`. Это позволяет использовать Huge Pages только для *метаданных* аллокатора (снижая TLB miss на структурах управления), но использовать 4KB для данных пользователя, чтобы избежать раздувания памяти.

## 7. Практический Тюнинг (Expert Toolkit)

В продакшене дефолтные настройки аллокаторов ("one size fits all") — это компромисс, который редко подходит для Edge-кейсов. Мы разберем инструменты диагностики и конкретные конфигурации **jemalloc** (так как это наиболее гибкий industry standard).

### 7.1. Диагностика: Доказательство вины аллокатора

Прежде чем менять настройки, нужно доказать, что проблема не в утечке бизнес-логики (Java Heap / C++ raw pointers), а именно во фрагментации или метаданных.

**Симптомы:**
1.  **RSS Plateau:** Потребление памяти (RSS) растет и замирает на высокой планке, хотя нагрузка упала.
2.  **Heap vs RSS Gap:** Профайлер языка (например, `pprof` в Go или Native Memory Tracking в JVM) показывает, что занято 2GB, а `top` показывает 5GB RSS. Разница в 3GB — это "Dark Matter" (фрагментация + кэши аллокатора).

**Инструмент: Jemalloc Stats Dump**
Jemalloc позволяет получить детальный отчет без остановки процесса и без перекомпиляции (если он загружен через `LD_PRELOAD`).

*   **Настройка:** Запустите приложение с `MALLOC_CONF=stats_print:true`. Это выведет статистику при выходе (бесполезно для демонов).
*   **Expert Trick (Live Profiling):** Настройте вывод статистики по сигналу.
    *   В коде (C++/Rust): привязать `malloc_stats_print` к сигналу (например, `SIGUSR1`).
    *   Конфигом: `MALLOC_CONF=prof:true,prof_leak:true`.
*   **Чтение отчета (Key Metrics):**
    *   `allocated`: Сколько байт запросило приложение (Payload).
    *   `active`: Сколько страниц физически выделено под эти данные (Payload + Internal Fragmentation).
    *   `mapped`: Сколько виртуальной памяти запрошено у ОС (включая пустоты в чанках).
    *   **Fragmentation Index:** `active / allocated`. Если > 1.2-1.3 (20-30% оверхед), у вас проблемы с фрагментацией.

### 7.2. Jemalloc Knobs: Тонкая настройка

Jemalloc управляется через переменную окружения `MALLOC_CONF` (список `key:value,key:value`).

#### A. Управление возвратом памяти (`dirty_decay_ms`, `muzzy_decay_ms`)
Это главные настройки для баланса **CPU vs RAM**. Аллокатор хранит "грязные" страницы (освобожденные приложением, но не возвращенные ОС) в кеше.

*   **`dirty_decay_ms:0`** (Aggressive/Serverless):
    *   *Суть:* Вызывать `madvise(MADV_DONTNEED)` немедленно после освобождения.
    *   *Плюс:* Минимальный RSS. Идеально для Lambda/FaaS или плотных Kubernetes кластеров.
    *   *Минус:* Огромный Overhead на системные вызовы. Взрывной рост CPU при активной работе с памятью.
*   **`dirty_decay_ms:10000`** (Default): Плавный возврат за 10 секунд.
*   **`dirty_decay_ms:-1`** (High Performance / HFT):
    *   *Суть:* Никогда не возвращать память ОС.
    *   *Плюс:* Нулевой оверхед на `madvise`, нет Page Faults при повторном использовании.
    *   *Минус:* RSS будет равен пиковому потреблению за все время работы (`High Watermark`). Риск OOM, если пик был разовым.

**Нюанс Linux 4.5+ (`muzzy_decay_ms`):**
Jemalloc различает **Dirty** (не сброшенные страницы) и **Muzzy** (страницы, помеченные `MADV_FREE`).
*   `MADV_FREE` дешевле, чем `MADV_DONTNEED`, так как не требует немедленного сброса TLB. Память остается в RSS, но ОС может забрать её при нехватке.
*   *Совет:* Если мониторинг (Prometheus/Grafana) "кричит" на высокий RSS, но OOM не происходит — скорее всего, это Muzzy страницы. Установите `muzzy_decay_ms:0`, чтобы форсировать `DONTNEED` и успокоить мониторинг, ценой CPU.

#### B. Изоляция потоков (`background_thread`)
По умолчанию очистка (Purging) неиспользуемой памяти происходит синхронно: поток вызывает `free()`, и иногда этот `free()` "зависает", выполняя `madvise`.

*   **`background_thread:true`**
    *   *Суть:* Jemalloc создает служебные pthreads, которые просыпаются и чистят "грязные" страницы фоном.
    *   *Результат:* Резкое снижение **Tail Latency** (P99/P999) для рабочих воркеров. Критично для баз данных (Redis, Scylla) и Event-Loop серверов (Netty, Node.js).
    *   *Требование:* Нужно разрешить приложению создавать потоки (учитывать в квотах `pids.max` в cgroup).

#### C. Борьба с фрагментацией (`narenas`, `percpu_arena`)
Сколько "независимых куч" (арен) создавать?
*   Default: $4 \times \text{CPU Cores}$.
*   **Проблема:** Если у вас 96 ядер, будет ~384 арены. Метаданные для каждой занимают память. При малом объеме RAM это лишний оверхед (Arena Bleed).
*   **Тюнинг:** Для приложений с малым Heap (< 1GB), но на мощном сервере, ограничьте `narenas:4` или `narenas:8`.
*   **`percpu_arena`:** Привязывает арены жестко к CPU ID, а не хешу потока. Улучшает локальность на NUMA-системах, но требует, чтобы потоки не мигрировали между ядрами (CPU Pinning).

### 7.3. Сценарии применения (Recipes)

Вот готовые пресеты настроек для разных профилей нагрузки. Скопируйте в Env Vars вашего Deployment.

**Сценарий 1: Low Latency Database / HFT (Максимальная скорость)**
Память дешевая, задержки дороги. Не отдаем память ОС, чистим фоном.
```bash
export MALLOC_CONF="background_thread:true,dirty_decay_ms:-1,muzzy_decay_ms:-1,metadata_thp:always"
```
*   `metadata_thp:always`: Использовать Huge Pages для метаданных аллокатора (уменьшает TLB Misses при поиске свободных блоков).

**Сценарий 2: Плотный Kubernetes Microservice (Java/Go + Sidecars)**
Экономим RAM, чтобы впихнуть больше подов.
```bash
export MALLOC_CONF="background_thread:true,dirty_decay_ms:1000,muzzy_decay_ms:0,narenas:2"
```
*   `muzzy_decay_ms:0`: Заставляем Linux реально забирать страницы (уменьшаем RSS), чтобы не триггерить K8s OOM Killer.
*   `narenas:2`: Минимум арен для экономии памяти на метаданных (ценой небольшого lock contention).

**Сценарий 3: Решение проблемы фрагментации (Long-running process)**
Если `active/allocated` > 1.4.
```bash
export MALLOC_CONF="lg_extent_max_active_fit:2,narenas:16"
```
*   `lg_extent_max_active_fit`: Заставляет jemalloc агрессивнее искать "дырки" подходящего размера (Best Fit) вместо выделения новых чанков, жертвуя CPU ради плотности упаковки.

### 7.4. Процедура внедрения

Как правильно подключить `jemalloc` к уже скомпилированному бинарнику (Java, Python, Ruby, Node, или "чужой" C++ бинарник):

1.  **Установка:** `apt-get install libjemalloc2` (Debian/Ubuntu) или `yum install jemalloc` (RHEL).
2.  **Поиск библиотеки:** `find /usr -name libjemalloc.so.2`.
3.  **Инъекция:**
    ```bash
    export LD_PRELOAD=/usr/lib/libjemalloc.so.2
    # Проверка, что подцепилось (должен быть в списке):
    lsof -p <PID> | grep jemalloc
    ```
4.  **Java Special:** Для JVM (Hotspot) есть флаг `-XX:+UseNUMA`, который тоже влияет на аллокацию. Но `LD_PRELOAD` работает "ниже" JVM, заменяя системный `malloc`, который JVM использует для C-Heap (Direct Buffers, Metaspace, JIT code cache, Thread Stacks). Это **не** влияет на Java Heap (там свой GC), но лечит нативный OOM.

**Expert Warning:** `mimalloc` сложнее подключить через `LD_PRELOAD` из-за конфликтов с инициализацией TLS (Thread Local Storage) в некоторых версиях glibc. Его лучше линковать статически или использовать специальные preload скрипты из релиза. Jemalloc в этом плане (версии 5.3+) — как автомат Калашникова, работает везде.

## 8. Чек-лист уровня Expert

1.  **False Sharing in Allocators:**
    Почему аллокаторы выравнивают начало TCache структур по 64 байта?
    *   *Ответ:* Чтобы избегать False Sharing. Если переменная `free_list_head` потока A и потока B окажутся на одной кэш-линии L1, запись в одну будет инвалидировать кэш другого ядра, вызывая просадку производительности (Coherency traffic).
2.  **Arena Bleed:**
    Что произойдет в jemalloc, если число потоков сильно превысит число арен ($4 \times$ Cores), а потоки короткоживущие?
    *   *Ответ:* Метаданные арен займут много памяти. Для приложений с тысячами потоков (например, старый Java BIO) нужно ограничивать число арен (`narenas`).
3.  **VIRT Memory Panic:**
    Почему `tcmalloc` или `Go runtime` резервируют террабайты VIRT памяти, хотя RSS маленький?
    *   *Ответ:* Они создают огромную "карту" (Arena) в виртуальном адресном пространстве, чтобы упростить вычисление адресов метаданных (через смещение). Это бесплатно для ОС (пока страницы не потроганы), но пугает админов, настроивших алерты на VIRT.
4.  **Sbrk vs Mmap:**
    Использует ли современный `malloc` системный вызов `sbrk`?
    *   *Ответ:* Почти нет. `sbrk` не потокобезопасен и двигает только одну границу. `mmap` (особенно `MAP_ANONYMOUS`) позволяет создавать независимые регионы памяти, что критично для Multi-Arena архитектуры. `sbrk` остался только для совместимости и очень малых аллокаций в `glibc`.

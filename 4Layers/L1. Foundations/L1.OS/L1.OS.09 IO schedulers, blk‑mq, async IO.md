**TL;DR**: Если ваш сервер "тормозит диском", но `iostat` показывает утилизацию 50%, скорее всего, вы уперлись не в диск, а в **планировщик ядра** или архитектуру очередей.
Для современных NVMe SSD старые подходы (CFQ, Single Queue) — это бутылочное горлышко. Практик должен знать, как включить `blk-mq`, почему `io_uring` меняет правила игры для баз данных, и почему `O_DIRECT` — это необходимость, а не прихоть.

## 1. Революция Block Layer: От Single Queue к Multi-Queue (blk-mq)

Чтобы понять `blk-mq`, нужно понять физику проблемы, которую он решает. Проблема не в скорости диска, а в **пропускной способности шины памяти и когерентности кэшей процессорных ядер**.

### 1.1. Старый мир: The Single Queue Bottleneck (Узкое место)
В эпоху HDD (до ядра Linux 3.13) подсистема ввода-вывода была спроектирована вокруг допущения: «Диск медленный, CPU быстрый».

*   **Архитектура:** Существовала **одна** очередь запросов (`request_queue`) на одно блочное устройство.
*   **Механизм защиты:** Эта очередь защищалась **одним глобальным спинлоком** (`request_queue_lock`).
*   **Сценарий провала:** Представьте сервер с 64 ядрами и быстрым NVMe диском.
    1.  Ядро CPU #0 хочет отправить запрос на чтение. Оно захватывает спинлок.
    2.  Ядро CPU #1 тоже хочет читать. Оно встает в цикл ожидания (spin), пытаясь захватить лок.
    3.  **Cache Line Bouncing (Критическая проблема):** Когда CPU #0 отпускает лок, а CPU #1 его захватывает, линия кэша L1, содержащая этот лок, должна физически переместиться между ядрами. Это занимает сотни тактов.
*   **Итог:** На скоростях выше 300,000 IOPS процессор тратил 70-80% времени не на обработку данных, а на борьбу за лок (Lock Contention). Производительность упиралась в потолок ~1M IOPS на всю систему, даже если диски могли больше.

### 1.2. Новый мир: Multi-Queue Block Layer (blk-mq)

`blk-mq` (введен в 3.13, стал единственным путем для I/O в ядре 5.0+, полностью вытеснив legacy код) решает проблему масштабирования через двухуровневый дизайн.

#### Уровень 1: Software Queues (Программные очереди / Staging)
*   **Концепция:** `blk-mq` выделяет по одной очереди (`Software Staging Queue`) на каждое логическое ядро CPU (или на NUMA-ноду).
*   **Механизм:**
    *   Когда процесс на CPU #5 делает `read()`, запрос попадает в очередь CPU #5.
    *   **Lock-Free (почти):** Никаких глобальных локов. Локальность данных идеальна. Нет Cache Line Bouncing.
    *   Здесь происходит **Software Merge**: если приложение просит прочитать сектор 10, а в очереди уже лежит запрос на сектора 8-9, они объединяются в один запрос 8-10 *до* передачи оборудованию.

#### Уровень 2: Hardware Queues (Аппаратные очереди / Dispatch)
*   **Концепция:** Драйвер устройства (NVMe, VirtIO, SCSI) сообщает ядру, сколько реальных физических очередей (Submission Queues) поддерживает контроллер.
*   **NVMe Spec:** Стандарт NVMe поддерживает до **65,535** очередей, каждая глубиной до 64k команд.
*   **Mapping (Отображение):** Ядро маппит множество программных очередей (M) на множество аппаратных очередей (N).
    *   Если $M > N$ (много CPU, мало очередей диска): Несколько CPU делят одну аппаратную очередь (с локальным локом, но конкуренция низкая).
    *   Если $M \approx N$ (NVMe): Отношение 1:1. Полный паралеллизм.

### 1.3. Жизненный цикл запроса (Terminology Deep Dive)

Чтобы говорить на языке экспертов, нужно различать сущности:

1.  **Bio (Block I/O):** Это логический запрос от файловой системы ("Прочитай мне файл X"). Это сырые данные.
2.  **Request:** Это структура блочного уровня. `blk-mq` превращает `bio` в `request`. Именно здесь происходит слияние (merge) и планирование (scheduling).
3.  **Submission:** Перемещение `request` из программной очереди в аппаратную ("звонок в дверной звонок" контроллера — Doorbell register write).
4.  **Completion (Завершение):**
    *   В Single Queue прерывание (Interrupt) могло прийти на любое ядро, вызывая переключения контекста.
    *   В `blk-mq` работает **Interrupt Steering**: прерывание о завершении операции приходит **на тот же CPU**, который её инициировал. Это сохраняет горячий кэш процессора.

### 1.4. Наглядный пример: "Почта России" vs "Логистический Хаб"

*   **Single Queue (Legacy):**
    Огромный зал (Сервер), одно окошко приема писем (Очередь диска). 64 человека (Ядра CPU) толпятся у одного окошка. Даже если за стеной стоит 100 грузовиков (NVMe), приемщица (Спинлок) одна. Скорость ограничена скоростью тетеньки в окне.

*   **blk-mq (Modern):**
    У каждого из 64 сотрудников на столе стоит свой лоток для исходящих (Software Queue).
    Курьер (Kernel Dispatcher) периодически проходит и забирает письма, сразу раскладывая их по 64 разным контейнерам (Hardware Queues), которые напрямую грузятся в 64 грузовика.
    Никто не стоит в очереди.

### 1.5. Диагностика и Тюнинг (Для практика)

Как понять, работает ли это у вас?

1.  **Проверка топологии:**
    ```bash
    # Показать маппинг CPU на аппаратные очереди
    ls -l /sys/block/nvme0n1/mq/
    # Вы увидите папки типа 0, 1, ... N. Внутри файла cpu_list написано, какие ядра пишут в эту очередь.
    ```
2.  **Прерывания (MSI-X):**
    NVMe диск должен иметь множество векторов прерываний.
    ```bash
    cat /proc/interrupts | grep nvme
    # Если вы видите только одну строку — blk-mq не работает эффективно (или диск SATA/AHCI).
    # Вы должны видеть десятки очередей: nvme0q0, nvme0q1, ...
    ```
3.  **Влияние на планировщики:**
    Именно архитектура `blk-mq` сделала старый планировщик `CFQ` невозможным. Сортировать одну глобальную очередь нет смысла, когда у вас 64 независимых потока данных. Поэтому появились `kyber` (регулирует latency токенами) и `mq-deadline`.

**Вывод архитектора:** `blk-mq` — это механизм, который позволил Linux утилизировать миллионы IOPS современных SSD. Если ваше приложение упирается в I/O, но диск загружен не полностью, скорее всего, вы уперлись в **количество очередей** или неправильный **IRQ affinity**, а не в скорость флеш-памяти.

## 2. Планировщики ввода-вывода (I/O Schedulers): Анатомия и Выбор

Задача планировщика (I/O Scheduler) — это не просто передача запросов драйверу. Это **управление трафиком** между файловой системой (FS) и блочным устройством. Планировщик решает дилемму: «максимизировать пропускную способность» (Throughput) против «минимизировать задержку» (Latency).

### 2.1. Механика: Что делает планировщик?

Прежде чем запрос попадет на диск, планировщик выполняет две фундаментальные операции над структурами `bio` (Block I/O) и `request`:

1.  **Merging (Слияние):**
    *   *Суть:* Если приложение делает два последовательных запроса на чтение блоков 100 и 101 (по 4KB), планировщик объединяет их в один запрос на 8KB.
    *   *Зачем:* Это снижает накладные расходы на прерывания (IRQ) и служебные команды протокола (SCSI/NVMe overhead). Для HDD это критично, для SSD — полезно для повышения пропускной способности (Bandwidth).
    *   *Типы:* **Front merge** (редко) и **Back merge** (часто — когда файл читается последовательно).

2.  **Sorting (Сортировка / Elevator Algorithm):**
    *   *Суть:* Изменение порядка запросов в очереди так, чтобы они шли последовательно по адресам LBA (Logical Block Address).
    *   *Пример:* Очередь запросов: `[100, 5000, 101]`. Планировщик перестроит её в `[100, 101, 5000]`.
    *   *Зачем:*
        *   **HDD:** Минимизация движения считывающей головки (Seek Time). Это дает прирост производительности в разы.
        *   **SSD:** Увеличивает шанс на слияние (Merge) и помогает контроллеру SSD лучше утилизировать внутренний параллелизм чипов NAND.

### 2.2. Legacy (Single Queue) — История для контекста
В старых ядрах (до повсеместного `blk-mq`) использовалась одна очередь с глобальной блокировкой (`spin_lock_irq`).
*   **CFQ (Completely Fair Queuing):** Пытался выделить каждому процессу "квант времени" (time slice) доступа к диску.
    *   *Проблема:* Сложная логика на красно-черных деревьях. На быстрых SSD процессор тратил больше времени на расчет расписания CFQ, чем диск тратил на чтение данных.
*   **В современном Linux (RHEL 8/9, Ubuntu 20.04+):** Эти планировщики удалены или переписаны под мульти-очереди.

### 2.3. Modern (blk-mq Schedulers) — Арсенал Архитектора

В архитектуре **blk-mq** планировщик работает внутри программных очередей (software queues) перед отправкой в аппаратные.

#### A. [none] / noop (No Operation)
Самый частый выбор для High-Load на NVMe.
*   **Логика:** Практически отсутствует. Только простейший слияние (merging), если это возможно мгновенно. Сортировки нет. Запросы передаются драйверу в порядке FIFO.
*   **Почему это работает:** Современные NVMe устройства имеют настолько низкую латентность (десятки микросекунд), что любая сложная логика в CPU ядра (переупорядочивание списков) вносит задержку, превышающую время самого I/O.
*   **Use Case:**
    *   NVMe SSD (особенно Gen4/Gen5).
    *   Высоконагруженные базы данных (PostgreSQL, MySQL), которые сами внутри движка умно планируют I/O.
    *   Внутри виртуальных машин (Guest OS), так как планированием занимается гипервизор (Host OS).

#### B. mq-deadline
Адаптация старого алгоритма Deadline под мульти-очереди.
*   **Логика:** Использует две очереди — для чтения и для записи, сортированные по LBA. Плюс две очереди "по времени поступления" (FIFO).
*   **Механизм:** Устанавливает жесткий тайм-аут (Expiration time).
    *   Read: 500ms (по умолчанию).
    *   Write: 5s (по умолчанию).
    *   Приоритет отдается чтению, так как чтение обычно блокирует работу приложения (синхронное), а запись часто идет асинхронно в фоне.
*   **Use Case:**
    *   SATA SSD (где шина SATA медленнее Flash-памяти).
    *   Серверные HDD (Spinning Rust). Гарантирует, что запрос не "застрянет" навечно из-за сортировки.

#### C. Kyber (I/O Latency Controller)
Разработан Facebook специально для быстрых устройств.
*   **Логика (Token Bucket):** Не занимается сложной сортировкой. Вместо этого он регулирует поток.
    *   Очередь делится на два потока: Синхронный (Read) и Асинхронный (Write).
    *   Задается целевая латентность (target latency), например, "хочу чтение за 2 мс".
    *   Алгоритм выдает "токены" на операции. Если устройство тормозит, выдача токенов ограничивается (throttling), чтобы разгрузить очередь устройства.
*   **Use Case:** Смешанная нагрузка на быстрых SSD, когда "тяжелые" записи могут забить канал и замедлить "легкие" чтения.

#### D. BFQ (Budget Fair Queuing)
Самый сложный и "тяжелый" планировщик (наследник CFQ).
*   **Логика:** Каждому процессу/группе выдается "бюджет" (в секторах диска), который он может вычитать за определенное время.
*   **Цель:** Максимальная интерактивность (Desktop responsiveness) и честное распределение пропускной способности (Fairness).
*   **Минус:** Огромный оверхед CPU (может "съесть" ядро на 10-20% при активном I/O). Снижает пиковый Throughput на быстрых дисках.
*   **Use Case:**
    *   Медленные HDD, USB-флешки.
    *   Ситуации, где нужно, чтобы копирование файла в фоне не "фризило" SSH-консоль или веб-сервер.
    *   *Анти-паттерн:* Не ставьте BFQ на Enterprise NVMe сервер базы данных.

### 2.4. Практический пример: Merge Storm

Представьте, что вы пишете лог БД (WAL / Transaction Log). Это последовательная запись.
Приложение делает:
1. `write(4KB)`
2. `write(4KB)`
3. `write(4KB)`
4. `fsync()`

**Сценарий 1 (Планировщик `none`, устройство быстрое):**
Все три запроса улетают на диск по отдельности.
*   Overhead: 3 транзакции NVMe, 3 прерывания.
*   Latency: Минимальная для первого пакета.

**Сценарий 2 (Планировщик `mq-deadline`, устройство SATA SSD):**
Планировщик видит, что блоки идут подряд. Он держит их в "Plugged queue" (микро-пауза).
*   Результат: Он склеивает (Merge) три запроса в один запрос на 12KB.
*   Overhead: 1 транзакция SATA.
*   Throughput: Значительно выше.

### 2.5. Рекомендация Архитектора (Decision Matrix)

Как выставить правильный планировщик через `udev` правила, чтобы не делать это вручную на каждом сервере:

```bash
# /etc/udev/rules.d/60-ioschedulers.rules

# NVMe SSD: всегда none (или kyber)
ACTION=="add|change", KERNEL=="nvme[0-9]*n[0-9]*", ATTR{queue/scheduler}="none"

# SATA SSD: mq-deadline (баланс)
ACTION=="add|change", KERNEL=="sd[a-z]*", ATTR{queue/rotational}=="0", ATTR{queue/scheduler}="mq-deadline"

# HDD (rotational): bfq (для интерактивности) или mq-deadline (для серверов)
ACTION=="add|change", KERNEL=="sd[a-z]*", ATTR{queue/rotational}=="1", ATTR{queue/scheduler}="bfq"
```

**Главный вывод:** Если у вас NVMe и вы видите, что CPU тратится на `kernel spinlocks` внутри block layer — выключите планировщик (`echo none > ...`). Железо умнее софта.

## 3. Async I/O: Битва за отказ от блокировок и Syscalls

Стандартная модель UNIX `read()/write()` — это **синхронная блокировка**.
Когда поток вызывает `read()`, он переходит в состояние `TASK_INTERRUPTIBLE`. Операционная система убирает его из очереди планировщика (deschedule), сохраняет контекст регистров и ждет прерывания от диска.
**Цена вопроса:**
*   **Context Switch:** ~1-5 мкс. Это сброс конвейера CPU, загрязнение L1/L2 кэша и (в эпоху Meltdown/Spectre) сброс TLB.
*   **Memory Overhead:** Чтобы держать 100k соединений в блокирующей модели, нужно 100k потоков. При стеке 1MB (даже с ленивой аллокацией) — это гигабайты памяти впустую.

Архитектор должен выбрать модель, минимизирующую эти накладные расходы.

### 3.1. POSIX AIO (`aio_read`/`glibc`) — Симуляция
Часто путают с настоящим асинхронным I/O.
*   **Реализация:** Это user-space обертка в `glibc`. Библиотека просто создает пул обычных потоков (`pthread`), которые делают блокирующие вызовы.
*   **Почему это плохо:** Вы не выигрываете производительность, вы просто прячете сложность управления потоками внутрь библиотеки. Это не масштабируется.
*   **Вердикт:** Избегать в High-Load.

### 3.2. Linux Native AIO (`libaio`) — Старая гвардия (Proactor pattern)
Это *настоящий* интерфейс ядра для асинхронности, введенный в ядре 2.5. Использует системные вызовы `io_setup`, `io_submit`, `io_getevents`.

**Механика:**
1.  Приложение формирует структуру `iocb` (I/O Control Block) и вызывает `io_submit`.
2.  Вызов возвращает управление немедленно (Non-blocking).
3.  Когда диск закончил работу, ядро кладет уведомление в кольцевой буфер в пространстве пользователя.
4.  Приложение забирает результаты через `io_getevents`.

**Фундаментальные ограничения (почему его ненавидят):**
1.  **Только O_DIRECT:** AIO работает асинхронно *только* если файл открыт с флагом `O_DIRECT`.
    *   *Деталь:* Если вы используете буферизированный I/O (через Page Cache), вызов `io_submit` может **заблокироваться**, если метаданные файла недоступны или нужно выделить память под страницу кэша. Асинхронность ломается тихо и непредсказуемо.
2.  **Ограниченная поддержка:** Работает только с файлами. Не работает с сокетами, пайпами и т.д. (хотя были попытки).
3.  **Лишние копирования:** Требует копирования метаданных запроса при системном вызове.

**Use Case:** Базы данных (Oracle, MySQL/InnoDB, ScyllaDB), которые реализуют свой собственный кэш и работают с raw block devices или файлами в `O_DIRECT`.

### 3.3. io_uring (Linux 5.1+) — The Game Changer
Это не просто новый API, это новая парадигма взаимодействия с ядром, созданная Йенсом Эксбоу (Jens Axboe). Она решает проблему стоимости самих системных вызовов (syscall overhead).

**Архитектура: Ring Buffers в Shared Memory**
Вместо того чтобы каждый раз копировать данные через границу User/Kernel при вызове syscall, `io_uring` создает два кольцевых буфера, отображенных в память (mmap) и доступных обоим мирам:

1.  **SQ (Submission Queue):** Очередь отправки.
    *   Приложение кладет сюда SQE (Submission Queue Entries) — "опейшн-коды": *Read, Write, Accept, Send, Recv, Fsync*.
2.  **CQ (Completion Queue):** Очередь завершения.
    *   Ядро кладет сюда CQE (Completion Queue Entries) — результаты: "прочитано 4096 байт" или "ошибка -EAGAIN".

**Режимы работы (от быстрого к мгновенному):**

*   **Interrupt Driven (Default):**
    1.  App пишет в SQ.
    2.  App делает один syscall `io_uring_enter` (аналог "звонка в дверь", notifying the kernel).
    3.  Ядро обрабатывает батч запросов.
    *   *Выигрыш:* 1 syscall на 1000 операций I/O (Batching).

*   **Polled Mode (`IORING_SETUP_IOPOLL`):**
    *   Ядро не ждет прерываний от диска, а само активно поллит (опрашивает) железо. Снижает латентность (latency), но грузит CPU.

*   **Kernel Side Polling (`IORING_SETUP_SQPOLL`) — "Режим Бога":**
    *   Ядро запускает специальный kernel thread (`io_uring-sq`), который в цикле крутится и смотрит в SQ буфер.
    *   **App:** Просто пишет в память (SQ). Никаких syscalls. Вообще.
    *   **Kernel:** Видит запись в памяти, выполняет I/O, пишет результат в CQ.
    *   **Результат:** Zero-Syscall Overhead. Производительность ограничена только скоростью памяти и шины PCIe.

**Киллер-фичи для Staff Architect:**
1.  **Unified Async:** Работает и с диском (Buffered & Direct), и с сетью. Можно построить веб-сервер, который делает `accept` -> `read` -> `read file` -> `sendfile` полностью через `io_uring`.
2.  **Registered Buffers:** Можно заранее "запинить" (pin) страницы памяти приложения в RAM и зарегистрировать их в ядре. При I/O ядру не нужно делать `get_user_pages` (дорогая операция маппинга вирт. адресов) каждый раз.
3.  **Fixed Files:** Регистрация дескрипторов файлов, чтобы избежать атомарных операций со счетчиками ссылок (`fget`/`fput`) внутри ядра при каждом запросе.

### 3.4. Пример для наглядности (Mental Model)

Представьте задачу: "Прочитать 4KB данных с диска".

1.  **Blocking I/O (`read`):**
    *   Вы подходите к окошку бюрократа (Kernel).
    *   Заполняете бланк.
    *   Бюрократ говорит "Ждите". Вы стоите у окна (Thread Blocked).
    *   Бюрократ уходит в архив, пьет чай.
    *   Возвращается с бумажкой. Вы уходите.
    *   *Цена:* Вы не могли ничего делать, пока стояли.

2.  **Native AIO (`libaio` + `O_DIRECT`):**
    *   Вы заполняете бланк, кидаете его в ящик "Входящие" (`io_submit`) и уходите работать.
    *   Периодически возвращаетесь проверить ящик "Исходящие" (`io_getevents`).
    *   *Цена:* Тратите время на хождение к ящикам (syscalls). Если бланк заполнен неверно (не O_DIRECT), бюрократ заставит вас стоять у окна.

3.  **io_uring (SQPOLL mode):**
    *   У вас с бюрократом есть **общий стол** (Shared Memory).
    *   Бюрократ (Kernel Thread) сидит за столом и *неотрывно* смотрит на входящий лоток.
    *   Вы подходите, молча кладете листок на стол и тут же уходите.
    *   Бюрократ мгновенно берет его, делает работу и кладет результат в исходящий лоток.
    *   Вы (или ваш коллега) позже забираете результат.
    *   *Цена:* Никаких разговоров, никаких ожиданий, никаких переключений контекста. Максимальная пропускная способность.

### Резюме раздела
*   **glibc AIO** — игнорируйте.
*   **libaio** — знайте для отладки старых/текущих БД, помните про ловушку `O_DIRECT`.
*   **io_uring** — будущее. Если вы пишете high-load I/O backend (Rust/C++/Go/Modern Java), вы должны строить архитектуру вокруг него. Это переход от модели **Reactor** (`epoll` - готовность) к модели **Proactor** (`io_uring` - завершение).

## 4. Архитектурная дилемма: O_DIRECT против Page Cache

Этот выбор определяет, **кто** управляет памятью вашего приложения: ядро Linux (универсальный алгоритм) или вы сами (специализированная логика).

### 4.1. Page Cache (Buffered I/O): "Бесплатная" помощь ядра

Когда вы делаете стандартный `read()` или `write()`, данные не идут на диск немедленно. Они попадают в **Page Cache** — часть оперативной памяти, которой управляет ядро.

*   **Механика Write-Back:** Вызов `write()` возвращает управление почти мгновенно. Данные помечаются как **Dirty Pages** (грязные страницы) в RAM. Фоновый процесс ядра (`pdflush` / `kworker`) сбрасывает их на диск позже (обычно через 5-30 секунд или при нехватке памяти).
*   **Механика Read-Ahead:** Ядро пытается предсказать ваши действия. Если вы прочитали страницы 1 и 2, ядро превентивно загружает страницы 3 и 4.

**Почему это плохо для Баз Данных (Expert Analysis):**

1.  **Проблема Double Buffering (Двойная буферизация):**
    Представьте, что у вас MySQL с пулом буферов (InnoDB Buffer Pool) на 50 ГБ.
    *   MySQL читает страницу данных. Она попадает в **Page Cache** ядра.
    *   Затем MySQL копирует её в свой **Buffer Pool** (userspace memory).
    *   **Итог:** Одна и та же страница занимает память дважды. Вы тратите RAM впустую, увеличивая давление на систему и провоцируя OOM Killer.

2.  **Проблема "Вымывания" (Cache Pollution):**
    Ядро использует алгоритм LRU (Least Recently Used) для всех процессов.
    *   *Сценарий:* Вы запускаете `pg_dump` (бекап) или `grep` по логам на 100 ГБ.
    *   Ядро видит огромный поток свежих чтений и вымывает из Page Cache "старые" страницы.
    *   Но эти "старые" страницы были индексами вашей "горячей" БД!
    *   **Результат:** Производительность продакшена падает в ноль, пока бекап вытесняет полезные данные. БД не может сказать ядру: "Не кэшируй этот бекап, он мне не нужен".

3.  **Непредсказуемая латентность (Write Stalls):**
    Ядро сбрасывает грязные страницы пачками. Когда грязных страниц становится слишком много (sysctl `vm.dirty_ratio`), ядро **блокирует** все вызовы `write()` от приложений, пока не очистит память.
    *   Для приложения это выглядит как "фриз" на секунды или даже минуты.

### 4.2. O_DIRECT (Direct I/O): Полный контроль

Флаг `O_DIRECT` (или `FILE_FLAG_NO_BUFFERING` в Windows) при открытии файла говорит ядру: **"Не кэшируй это. Не используй read-ahead. Я знаю, что делаю"**.

*   **Zero-Copy (почти):** Данные передаются через DMA (Direct Memory Access) контроллером диска прямо в буфер вашего приложения в Userspace.
*   **Экономия CPU:** Исключается операция `memcpy` между пространством ядра и пространством пользователя.

**Цена использования (The Engineering Cost):**

1.  **Требование выравнивания (Memory Alignment):**
    Вы не можете просто прочитать 10 байт в произвольный буфер.
    *   Буфер в памяти должен быть выровнен по границе сектора (обычно 512 байт или 4KB). Используйте `posix_memalign()`.
    *   Размер чтения/записи должен быть кратен размеру сектора.
    *   *Пример:* Запись 100 байт с `O_DIRECT` невозможна напрямую. Вам нужно прочитать 4KB, изменить 100 байт, записать 4KB (Read-Modify-Write), если вы не управляете структурой файла целиком.

2.  **Вы обязаны реализовать свой кэш:**
    Без Page Cache каждое чтение — это поход на диск (latency 100 мкс для NVMe, 10 мс для HDD). Если у вас нет своего Buffer Pool, производительность упадет в тысячи раз.

### 4.3. Критический нюанс: O_DIRECT != O_SYNC

Это самая частая ошибка на собеседованиях Staff уровня.

*   **Миф:** "`O_DIRECT` пишет сразу на блины диска/ячейки SSD".
*   **Реальность:** `O_DIRECT` обходит кэш **ядра (Page Cache)**. Но он **НЕ** обходит встроенный кэш **самого диска** (Hardware Cache / Volatile Write Cache на контроллере SSD).

Если питание пропадет сразу после `write(O_DIRECT)`, данные могут быть потеряны, если они остались в DDR-кэше SSD-диска.

**Правильный паттерн надежности (Durability):**
1.  Открыть файл с `O_DIRECT`.
2.  Сделать `write()`. Данные ушли из RAM в SSD-контроллер.
3.  Сделать `fsync()` (или `fdatasync`), чтобы заставить SSD сбросить свой кэш в постоянную память (NAND Flash).
    *   *Альтернатива:* Использовать флаг `O_DSYNC` вместе с `O_DIRECT`, чтобы каждый `write` гарантированно ждал персистенции. Это медленнее, но надежнее (используется для WAL/Transaction Logs).

### 4.4. Пример из жизни: MySQL (InnoDB) vs PostgreSQL

Это классическая битва архитектур.

*   **MySQL (InnoDB):**
    *   Использует `O_DIRECT` для файлов данных (`innodb_flush_method=O_DIRECT`).
    *   Имеет свой мощный буфер (InnoDB Buffer Pool), который управляет LRU, знает про индексы и "грязные" страницы.
    *   *Итог:* Полный контроль, нет двойной буферизации.

*   **PostgreSQL (Классический):**
    *   Традиционно полагался на **Page Cache** (Buffered I/O).
    *   Имеет свой `shared_buffers`, но он обычно небольшой (рекомендуют 25% RAM), остальное оставляют ядру.
    *   *Проблема:* Postgres пишет в `shared_buffers`, потом сбрасывает в Page Cache, потом ядро пишет на диск. Двойная буферизация.
    *   *Эволюция:* В Postgres 14+ и особенно 16+ активно внедряется поддержка Direct I/O (через AIO), так как на современных NVMe старая архитектура становится узким местом.

### Резюме для Эксперта

| Характеристика | Page Cache (Buffered) | O_DIRECT |
| :--- | :--- | :--- |
| **Управление памятью** | Ядро (алгоритм LRU для всех) | Приложение (Domain-specific логика) |
| **Копирование памяти** | Kernel space $\leftrightarrow$ User space (CPU overhead) | DMA $\to$ User space (Zero-copy) |
| **Поведение при Read** | Read-Ahead (хорошо для файлов, плохо для Random DB) | Читаем ровно то, что просили |
| **Поведение при Write** | Write-Back (ленивая запись, риск потери при крэше ядра) | Запись в устройство (но нужен `fsync` для надежности) |
| **Alignment** | Не требуется | Строгое (обычно 4KB) |
| **Основной Use Case** | Веб-серверы, файлы логов, простые утилиты | **Базы данных**, High-Load Storage, Video Streaming |

**Совет Архитектора:** Если вы пишете свою базу данных или слой хранения (Storage Engine) — **начинайте с O_DIRECT**. Боль, которую вы испытаете при реализации выравнивания памяти, окупится полным контролем над I/O и отсутствием мистических лагов в продакшене.

## 5. Чек-лист уровня Practitioner

Для проверки навыков отладки дисковой подсистемы:

1.  **iostat -x 1:**
    *   Смотрите на `avgqu-sz` (Queue Size). Если для NVMe это число < 10, диск простаивает (недогружен). NVMe нужно "кормить" параллельностью (Queue depth 32-64+), чтобы получить заявленные IOPS.
    *   Смотрите на `await` (latency). Если `r_await` низкий, а `w_await` высокий — возможно, забит Write Cache диска.
2.  **fio (Flexible I/O Tester):**
    Умеете ли вы написать конфиг для эмуляции вашей БД?
    *   `iodepth=64`, `direct=1`, `ioengine=libaio` (или `io_uring`), `rw=randread`. Тестировать диск через `dd` — моветон.
3.  **Merge шторм:**
    Почему на последовательном чтении IOPS низкие, а пропускная способность (MB/s) высокая?
    *   *Ответ:* I/O Scheduler мерджит последовательные мелкие блоки в один большой запрос (напр., 4KB -> 1MB). Количество запросов к устройству падает, эффективность растет.

### Заключение
I/O — это не просто "чтение файлов".
1.  На современных ядрах убедитесь, что **blk-mq** активен.
2.  Для NVMe используйте планировщик **none/noop**.
3.  Если пишете High-Performance софт на Linux в 2025 году — изучайте **io_uring**.
4.  Понимайте разницу между `buffered` и `direct` I/O при настройке баз данных (`innodb_flush_method=O_DIRECT`).

**TL;DR**: Для уровня Staff/Expert eBPF — это не просто «инструмент трассировки» или «tcpdump на стероидах». Это **программируемое ядро** (kernel programmability interface). Это способ исполнять вашу логику в пространстве ядра (Ring 0) безопасно и эффективно, без написания модулей ядра (Kernel Modules), которые могут вызвать Kernel Panic. Вы должны понимать архитектуру eBPF, чтобы заменять Sidecar-контейнеры на уровне ноды (Cilium), профилировать продакшн без оверхеда (Pixie/Parca) и фильтровать DDoS на сетевой карте (XDP).

## 1. Архитектура eBPF VM (Virtual Machine)

eBPF — это не просто интерпретатор. Это **изолированная RISC-архитектура** с 64-битными регистрами, работающая внутри ядра. Она спроектирована так, чтобы взаимно-однозначно (1:1) мапиться на инструкции современных физических CPU (x86_64, arm64, ppc64), что делает JIT-компиляцию тривиальной и чрезвычайно эффективной.

## 1.1. Модель регистров (The ABI)

В eBPF доступно 11 регистров (`R0`–`R10`). Это рабочие лошадки. Понимание их назначения (Calling Convention) критично, так как компилятор Clang/LLVM будет пытаться уложить переменные именно сюда, избегая дорогого стека.

| Регистр | Роль (Calling Convention) | Тип | Описание для Эксперта |
| :--- | :--- | :--- | :--- |
| **R0** | Return / Exit Code | Scratch | **Возвращаемое значение.**<br>1. При выходе из программы: результат (Verdict, например `XDP_DROP`).<br>2. При вызове Helper-функции: сюда попадает результат её работы. |
| **R1** | Argument 1 / **Context** | Scratch | **Входной контекст.**<br>При старте программы `R1` всегда содержит указатель на контекст (например, `struct __sk_buff*` или `struct xdp_md*`). Это ваш `this`. |
| **R2 – R5** | Arguments 2 – 5 | Scratch | **Аргументы функций.**<br>Используются для передачи параметров в BPF Helpers (`bpf_map_lookup_elem(map, key)`).<br>*Важно:* Они "затираются" (Scratch) после вызова хелпера. Не храните здесь долгоживущие данные. |
| **R6 – R9** | **Callee-saved** | Preserved | **Сохраняемые регистры.**<br>Значения в них переживают вызовы Helper-функций. Компилятор старается хранить здесь локальные переменные функции, чтобы не делать Spilling (сброс) в стек. |
| **R10** | Frame Pointer (FP) | Read-only | **Указатель на стек.**<br>Всегда указывает на вершину стека eBPF (512 байт). Модифицировать нельзя. Доступ к локальным переменным идет как `R10 - offset`. |

**Архитектурный инсайт:** Ограничение в 5 аргументов (R1-R5) жестко зашито в архитектуру. Если вам нужно передать больше данных в функцию (BPF-to-BPF call), придется передавать указатель на структуру (`struct args_t`), лежащую на стеке.

## 1.2. Стек и память (The Stack Constraints)

*   **Лимит:** Жесткие **512 байт** на программу.
*   **Выравнивание:** Стек растет вниз. Доступ должен быть выровнен (aligned).
*   **Variable Stack Access:** Верификатор запрещает доступ к стеку по переменному смещению (например, `buf[i]`, где `i` — переменная), если он не может доказать границы `i` на этапе компиляции. Это делается для предотвращения атак типа Spectre/Meltdown и чтения произвольной памяти ядра.

**Как обойти лимит 512 байт?**
Если вам нужно собрать большой буфер (например, URL запроса):
1.  **Per-CPU Map:** Создайте карту `BPF_MAP_TYPE_PERCPU_ARRAY` с одним элементом нужного размера (напр., 16KB).
2.  В коде: получите указатель на этот элемент (`bpf_map_lookup_elem`).
3.  Используйте эту память как "кучу" (Heap). Это быстрее стека и не имеет лимита в 512 байт.

## 1.3. Система инструкций и JIT

Инструкции eBPF имеют фиксированный размер **64 бита**.
*   8 бит: код операции (opcode).
*   4+4 бита: регистры назначения (dst) и источника (src).
*   16 бит: смещение (offset) для ветвлений.
*   32 бита: непосредственное значение (immediate value).

**JIT Compilation (Just-In-Time):**
По умолчанию в современных дистрибутивах (`net.core.bpf_jit_enable = 1`) байт-код eBPF не интерпретируется.
При загрузке (`sys_bpf(BPF_PROG_LOAD)`) ядро транслирует eBPF инструкции 1-в-1 в машинный код:
*   `R0` $\to$ `rax`
*   `R1` $\to$ `rdi`
*   `R10` $\to$ `rbp`
*   eBPF `call` $\to$ x86 `call`

**Hardening (JIT Spray Protection):**
Для защиты от атак, когда злоумышленник загружает BPF-код, который в нативном виде содержит вредоносные инструкции (JIT Spraying), используется **Constant Blinding**. Все константы в коде XOR-ятся со случайным cookie, а перед выполнением "раз-XOR-иваются". Это меняет бинарный вид инструкций в памяти, делая атаку непредсказуемой.

## 1.4. The Verifier (Верификатор) — Абстрактная виртуальная машина

Это самая сложная часть eBPF. Верификатор запускает вашу программу в "симуляции" (Abstract Virtual Execution) **до** того, как она попадет в JIT.

**Что он делает (Step-by-Step):**

1.  **Построение CFG (Control Flow Graph):** Проверяет граф переходов. Убеждается, что нет недостижимого кода и бесконечных циклов (проверяет back-edges).
2.  **Tracking Register Types:** Верификатор знает, *что* лежит в каждом регистре в любой момент времени:
    *   `SCALAR_VALUE`: Просто число.
    *   `PTR_TO_CTX`: Указатель на пакет (R1).
    *   `PTR_TO_MAP_VALUE`: Указатель на значение в карте.
    *   `PTR_TO_STACK`: Указатель на стек.
3.  **Range Tracking (tnum):** Для скаляров верификатор отслеживает диапазон возможных значений (min/max).
    *   *Пример:* Если вы делаете `if (R2 > 100) return;`, то в ветке "else" верификатор "знает", что `R2 <= 100`. Если вы используете `R2` как индекс массива размером 101, верификатор разрешит доступ. Если массив размера 50 — запретит (`permission denied: R2 unbounded`).
4.  **Pointer Arithmetic Checks:** Нельзя просто так сложить два указателя. Можно вычитать (чтобы узнать длину), можно прибавлять скаляр к указателю (смещение), но нельзя превратить число в указатель (произвольный доступ к памяти запрещен).

**Пример логики верификатора:**
```c
// C code
void *data = (void *)(long)ctx->data;
void *data_end = (void *)(long)ctx->data_end;
struct ethhdr *eth = data;

if (eth + 1 > data_end) // Bounds check!
    return XDP_DROP;

// Verifier logic:
// До проверки: R1 (eth) is PTR_TO_PACKET. Length unknown.
// Если мы попытаемся прочитать eth->h_proto ДО проверки -> REJECT.
// После if (...): В ветке выполнения верификатор помечает R1 как "Safe to read 14 bytes".
```

## 1.5. Helper Functions (Интерфейс к ядру)

eBPF программа не может вызывать произвольные функции ядра (например, `printk` или `kmalloc`). Она может вызывать только разрешенный набор **BPF Helpers** (определенный в `uapi/linux/bpf.h`).

*   Синтаксис: `call <helper_id>`.
*   ABI: Аргументы в R1-R5, результат в R0.
*   **Стабильность:** Хелперы являются частью UAPI Linux. Их сигнатуры не меняются, в отличие от внутренних структур ядра (`struct sock`).

**Примеры критических хелперов:**
*   `bpf_map_lookup_elem`: Поиск в карте.
*   `bpf_ktime_get_ns`: Время (монотонное) для метрик.
*   `bpf_trace_printk`: Отладка (медленно, пишет в `/sys/kernel/debug/tracing/trace_pipe`).
*   `bpf_tail_call`: Передача управления другой BPF-программе (аналог `exec`, позволяет обходить лимит инструкций, разбивая логику на цепочки).

---

### Резюме для Эксперта

Понимая архитектуру VM, вы понимаете природу ошибок:
1.  **"R0 !read_ok"**: Вы забыли записать возвращаемое значение в R0 перед выходом.
2.  **"invalid access to packet"**: Вы забыли проверку `data_end` (Boundary Check).
3.  **"variable stack access"**: Вы используете неконстантный индекс при работе с буфером на стеке.
4.  **Производительность:** Вы понимаете, что использование регистров `R6-R9` эффективнее, чем постоянная работа со стеком, и что `Per-CPU Maps` быстрее обычных `Array Maps` за счет отсутствия блокировок шины памяти.

## 2. eBPF Maps: Управление состоянием

eBPF программы по своей природе — это чистые функции (stateless functions), запускаемые по событию. **Maps (Карты)** — это единственная возможность сохранить состояние между вызовами или передать данные между ядром и пользовательским пространством (Userspace).

С точки зрения архитектора ОС, eBPF Map — это **общий регион памяти (Shared Memory Region)**, управляемый ядром, доступ к которому осуществляется через:
1.  **Helper Functions** внутри BPF-программы (например, `bpf_map_lookup_elem`).
2.  **System Calls** (`bpf()`) со стороны Userspace (через файловый дескриптор).

### 2.1. Базовые структуры: Array vs Hash

Выбор типа карты определяет `O(n)` сложность и профиль использования памяти.

*   **`BPF_MAP_TYPE_ARRAY`**:
    *   **Структура:** Непрерывный блок памяти, аллоцированный при создании.
    *   **Ключ:** Строго `4 байта` (индекс массива).
    *   **Производительность:** Самый быстрый лукап (прямая арифметика указателей: `base_addr + index * elem_size`). Идеален для глобальных конфигов или счетчиков с известным диапазоном (например, порты 0-65535).
    *   **Особенность:** Не поддерживает удаление элементов (`delete` запрещен).

*   **`BPF_MAP_TYPE_HASH`**:
    *   **Структура:** Классическая хеш-таблица с преаллоцированными бакетами (buckets).
    *   **Ключ:** Произвольная структура данных.
    *   **Производительность:** Зависит от качества хеш-функции (JHash внутри ядра) и коллизий. Медленнее массива из-за вычисления хеша и прохода по цепочкам.
    *   **Caveat (Важно для эксперта):** По умолчанию память под все элементы *не выделяется* сразу (если не задан флаг `BPF_F_NO_PREALLOC`), но максимальный размер фиксирован. Если карта полна, вставка вернет ошибку. Динамического ресайза (как в Java HashMap) **нет**.

### 2.2. The Scalability King: Per-CPU Maps
Для систем с нагрузкой 10Gbps+ или миллионов RPS использование обычных `HASH` или `ARRAY` карт для метрик — **архитектурная ошибка**.

*   **Проблема (False Sharing & Cache Bouncing):**
    Представьте глобальный счетчик пакетов. Ядро 1 и Ядро 2 пытаются сделать `atomic_inc` одной и той же ячейки памяти.
    1.  Ядро 1 захватывает Cache Line в Exclusive state (MESI протокол).
    2.  Ядро 2 требует эту линию. Линия сбрасывается из L1/L2 Ядра 1 в L3/RAM и переезжает к Ядру 2.
    3.  **Итог:** Шинный трафик (Interconnect traffic) убивает производительность CPU, даже если логика проста.

*   **Решение: `BPF_MAP_TYPE_PERCPU_ARRAY` / `_HASH`**:
    *   Ядро аллоцирует массив размером `MAX_ENTRIES * NUM_CPUS`.
    *   При обращении eBPF-программа *автоматически* получает указатель на слот, соответствующий *текущему* CPU.
    *   **Zero Synchronization:** Никаких атомиков, никаких спинлоков. Каждое ядро работает со своей приватной памятью (L1 Cache hit).
    *   **Userspace Aggregation:** При чтении userspace-приложение получает массив значений (по одному от каждого CPU) и должно само их просуммировать.

### 2.3. IPC: RingBuffer vs PerfBuffer (Эволюция)
Как передать "событие" (например, лог HTTP-запроса) из ядра в userspace агент?

*   **Legacy: `BPF_MAP_TYPE_PERF_EVENT_ARRAY` (PerfBuffer)**
    *   Использует подсистему `perf` (как и `perf record`).
    *   Выделяется отдельный буфер на каждое CPU.
    *   **Недостатки:**
        1.  **Memory Overhead:** Нужно угадать размер буфера для каждого CPU. На одном ядре пусто, на другом переполнение и дропы.
        2.  **Double Copy:** Данные сначала копируются в стек BPF, потом в буфер perf.
        3.  **Ordering:** Нет гарантии глобального порядка событий (событие с CPU 2 может прийти раньше события с CPU 1, даже если случилось позже).

*   **Modern Standard: `BPF_MAP_TYPE_RINGBUF` (Kernel 5.8+)**
    *   **Структура:** Один общий кольцевой буфер (MPSC - Multi-Producer Single-Consumer) для всех CPU.
    *   **Reservation:** Поддерживает механизм `bpf_ringbuf_reserve`. Вы резервируете место в буфере и пишете данные *напрямую* туда, минуя копирование в стек BPF (Zero-copy write). Это критично для больших структур.
    *   **Wakeups:** Адаптивные уведомления (notification) userspace, чтобы не будить процесс слишком часто (Busy polling vs Interrupt-driven).

### 2.4. Специализированные карты (Advanced)

*   **`BPF_MAP_TYPE_LRU_HASH`**:
    *   Для кэширования сессий (Connection Tracking).
    *   Когда карта полна, ядро автоматически удаляет "старые" элементы.
    *   *Нюанс:* LRU в ядре не "честный" (не глобальный список), а пер-процессорный, чтобы избежать глобального лога. Это "Approximate LRU".

*   **`BPF_MAP_TYPE_PROG_ARRAY` (Tail Calls)**:
    *   Карта хранит файловые дескрипторы *других* eBPF программ.
    *   Позволяет обойти лимит инструкций (1M). Вы делаете `bpf_tail_call(ctx, &prog_array, index)`.
    *   Это работает как `GOTO` или `execve()`: контекст передается, стек очищается (старый фрейм переиспользуется), возврат в вызывающую программу невозможен.
    *   Основа модульной архитектуры Cilium.

*   **`BPF_MAP_TYPE_SOCKMAP` / `SOCKHASH`**:
    *   Позволяет перенаправлять трафик между сокетами *внутри* ядра (Socket Redirection), минуя TCP/IP стек. Основа ускорения Service Mesh (избавление от накладных расходов localhost коммуникации).

### 2.5. Пример определения карты (C code / `libbpf`)

Для наглядности, так выглядит определение карты в современном BPF коде (CO-RE стиль):

```c
struct {
    __uint(type, BPF_MAP_TYPE_LRU_HASH); // Тип: Хеш с вытеснением
    __uint(max_entries, 10240);          // Макс. кол-во элементов
    __type(key, struct ip_key);          // Структура ключа (IP src/dst)
    __type(value, struct traffic_stats); // Структура значения (bytes, packets)
} traffic_map SEC(".maps");              // Секция ELF файла
```

### 2.6. Чек-лист по проблемам (Pitfalls)

1.  **Atomicity:** `bpf_map_update_elem` атомарен для всей структуры. Но если вы получили указатель через `lookup` и меняете поля вручную:
    *   `val = bpf_map_lookup_elem(...)`
    *   `val->cnt += 1;` // **RACE CONDITION!** (Даже на одном CPU, если будет прерывание/preemption, хотя eBPF обычно non-preemptible, но на мульти-CPU это точно гонка).
    *   *Решение:* Использовать `__sync_fetch_and_add` или `bpf_spin_lock`.

2.  **Stack Limit:** Ключ и Значение при вызове `update` обычно копируются со стека. Если структура `value` занимает 600 байт (при лимите стека 512), программа не загрузится.
    *   *Решение:* Использовать Per-CPU карты как "scratch buffer" (временный буфер) или `bpf_ringbuf_reserve`.

3.  **Memory Locking:** Карты лочат RAM (`RLIMIT_MEMLOCK`). В контейнерах это часто вызывает ошибку "Permission denied" при загрузке карты, если лимиты не настроены.

## 3. Hooks (Точки прикрепления): Где живет код?

В мире eBPF программа не висит в памяти постоянно как демон. Она — обработчик события (Event Handler). **Hook** — это комбинация события в ядре и места, куда мы врезаем наш байт-код.

### 3.1. Static Instrumentation: Tracepoints и Raw Tracepoints
Это "официальный API" ядра для трассировки. Разработчики ядра (Linus Torvalds и мейнтейнеры подсистем) намеренно вставили макросы в исходный код (`include/trace/events`), чтобы мы могли на них подписаться.

*   **Tracepoints (`SEC("tracepoint/...")`):**
    *   **Определение:** Статическая метка в коде. Когда исполнение доходит до неё, ядро формирует структуру данных (контекст) с аргументами и вызывает BPF-программу.
    *   **Стабильность (Stable ABI):** Это контракт. Если в ядре есть трейс-поинт `sched:sched_switch`, его формат аргументов (prev_pid, next_pid) не менялся годами и не изменится без веской причины.
    *   **Производительность:** Средняя. Ядро тратит время на создание структуры контекста.
*   **Raw Tracepoints (`SEC("raw_tracepoint/...")`):**
    *   **Определение:** То же самое место в коде, но BPF-программа получает доступ к "сырым" аргументам функции трассировки (прямо из регистров), минуя стадию упаковки в структуру.
    *   **Expert Insight:** Используйте `raw_tracepoint` для High-Load систем. Это экономит такты CPU на упаковке данных.

**Пример:** Отслеживание переключения контекста (Context Switch).
```c
// Обычный tracepoint (удобный, есть готовая структура args)
SEC("tracepoint/sched/sched_switch")
int handle_sched_switch(struct trace_event_raw_sched_switch *ctx) {
    u32 prev_pid = ctx->prev_pid;
    u32 next_pid = ctx->next_pid;
    // ... logic
    return 0;
}
```

### 3.2. Dynamic Instrumentation: Kprobes, Kretprobes и Fentry
Когда нужного Tracepoint нет (а их нет для 90% кода ядра), мы используем динамическую инъекцию.

*   **Legacy Kprobe (`SEC("kprobe/...")`):**
    *   **Механизм:** Основан на прерываниях. Ядро заменяет первую инструкцию целевой функции на `INT3` (x86 breakpoint). При срабатывании процессора происходит Trap, управление передается обработчику, затем выполняется оригинальная инструкция.
    *   **Оверхед:** Высокий. Требует сохранения/восстановления регистров. Не рекомендуется для "горячих" функций (Packet processing, Memory alloc), вызываемых миллионы раз в секунду.
*   **Modern Fentry/Fexit (`SEC("fentry/...")`, Kernel 5.5+):**
    *   **Механизм (Trampoline):** Использует механизм `mcount` (изначально для ftrace). В начале почти каждой функции ядра есть `NOP`-инструкции. При загрузке BPF ядро заменяет `NOP` на прямой `CALL` вашей BPF-программы.
    *   **Оверхед:** Почти нулевой (стоимость прямого вызова функции).
    *   **Возможности:** `fexit` позволяет видеть возвращаемое значение функции (как `kretprobe`, но быстрее).
*   **Риск Staff-уровня (Instability):** Kprobes/Fentry привязываются к *именам функций* ядра (символам). В версии ядра 5.4 функция называлась `tcp_connect`, в 5.10 она может стать `tcp_v4_connect` или изменить аргументы. Ваши инструменты мониторинга **сломаются** при обновлении OS.

### 3.3. Networking: Data Plane Hooks (XDP vs TC)
Сетевая обработка — это главный драйвер развития eBPF (Facebook Katran, Cloudflare, Cilium). Здесь критично понимать путь пакета.

#### A. XDP (eXpress Data Path)
Срабатывает **сразу** после того, как сетевая карта (NIC) получила пакет через DMA, но **до** того, как ядро выделило память под тяжелую структуру `sk_buff` (Socket Buffer).
*   **Контекст:** `struct xdp_md` (сырой указатель на данные `data` и конец `data_end`).
*   **Modes:**
    1.  *Native/Driver:* Драйвер карты поддерживает XDP. Максимальная скорость.
    2.  *Generic:* Эмуляция в ядре (медленно, для тестов).
    3.  *Offload:* Исполнение прямо на SmartNIC (Netronome, BlueField).
*   **Действия (Return Codes):**
    *   `XDP_DROP`: Пакет исчезает. Идеально для DDoS защиты (сбрасываем 20 Mpps на одном ядре).
    *   `XDP_TX`: Отправить пакет обратно в ту же карту (Load Balancer "on a stick").
    *   `XDP_PASS`: Передать дальше в сетевой стек ядра (sk_buff).
*   **Ограничение:** XDP работает только на **Ingress** (входящий трафик). Нельзя использовать XDP для фильтрации исходящего трафика из контейнеров (для этого есть TC).

#### B. TC (Traffic Control)
Срабатывает на уровнях классификации трафика (Ingress и Egress). Работает уже с `sk_buff`.
*   **Плюсы:**
    *   Видит пакеты и на вход, и на выход.
    *   Может работать с Hardware Offload.
    *   Может изменять размер пакета (add headers), что сложно в XDP.
*   **Архитектурное применение:** Cilium использует TC для редиректа трафика между контейнерами, минуя полный сетевой стек (Netfilter/Iptables), что дает прирост производительности.

### 3.4. User Space: Uprobes и USDT
eBPF может следить не только за ядром, но и за вашим приложением (Nginx, Postgres, JVM).

*   **Uprobe/Uretprobe:**
    *   Работает как Kprobe, но для Userspace. Ядро подменяет инструкцию в виртуальной памяти процесса (или в shared library `.so`) на breakpoint.
    *   **Пример:** Перехват `SSL_read` в `libssl.so`, чтобы дампить расшифрованный трафик HTTP/2 (Observability без ключей шифрования).
    *   **Цена:** Огромная. Переключение контекста (Kernel <-> User) на каждое срабатывание. Не использовать для функций типа `malloc` или `getters`.
*   **USDT (User Statically Defined Tracing):**
    *   Аналог Tracepoints для юзерспейса. Разработчик вставляет макрос `DTRACE_PROBE` в код (C++, Rust, Go).
    *   В бинарнике это выглядит как `NOP`. При активации BPF ядро патчит `NOP` на вызов ловушки. Быстрее, чем слепой Uprobe, и стабильнее API.

### 3.5. Security: LSM Hooks (Linux Security Modules)
Это то, на чем построены современные средства защиты (Tetragon, Falco).
*   **Тип:** `BPF_PROG_TYPE_LSM` (Kernel 5.7+).
*   **Суть:** BPF-программы прикрепляются к хукам LSM (там же, где живут SELinux и AppArmor).
*   **Киллер-фича (Blocking):** В отличие от Tracepoints (которые только "наблюдают"), LSM-хук может вернуть ошибку (`-EPERM`).
*   **Пример:** Запретить процессу `curl` открывать соединения на определенные IP или запретить `rm -rf /` даже для root, если это не разрешено политикой.

### Сводная таблица для принятия решений

| Тип хука | Стабильность API | Производительность | Возможность блокировки | Use Case |
| :--- | :--- | :--- | :--- | :--- |
| **Tracepoint** | Высокая (Stable) | Средняя | Нет | Мониторинг ядра, скедулер |
| **Kprobe/Fentry** | Низкая (Unstable) | Высокая (Fentry) / Низкая (Legacy) | Нет (обычно) | Глубокий дебаг, профилирование |
| **XDP** | Высокая | **Экстремальная** | **Да (Drop)** | DDoS, L4 Load Balancing |
| **TC** | Высокая | Высокая | Да | Kubernetes Network Policies, Service Mesh |
| **LSM** | Средняя | Высокая | **Да (Prevent)** | Security Policies, Runtime Enforcement |
| **Uprobe** | Зависит от приложения | Низкая (Overhead) | Нет (обычно) | Трейсинг SSL, DB queries, malloc |

## 4. CO-RE (Compile Once – Run Everywhere): Глубокое погружение

До появления CO-RE экосистема eBPF страдала от проблемы, которую можно назвать "Kernel Header Hell". Чтобы ваша программа работала, вы должны были компилировать её на *целевой* машине (runtime compilation), используя Python-фреймворк BCC. Это требовало установки компилятора LLVM/Clang и пакетов `kernel-devel` (заголовков ядра) прямо на продакшн-серверах.
*   **Для безопасности:** Компилятор на проде — это расширение поверхности атаки.
*   **Для DevOps:** Это раздувание образа контейнера на сотни мегабайт.
*   **Для стабильности:** Если заголовки ядра отсутствовали, мониторинг падал.

CO-RE решает эту проблему, позволяя скомпилировать бинарный файл один раз (на CI/CD) и запускать его на любом совместимом ядре без перекомпиляции.

### 4.1. Три кита CO-RE

Технология держится на трех компонентах, работающих в синергии:

1.  **BTF (BPF Type Format):**
    Это стандарт метаданных (сжатый аналог DWARF). Он описывает структуру данных ядра: имена структур, смещения полей (offsets), типы.
    *   *В ядре:* Современные ядра (обычно 5.8+, но есть бэкпорты в RHEL 8) экспортируют свой BTF через файл `/sys/kernel/btf/vmlinux`. Это "карта местности" текущего ядра.
    *   *В бинарнике:* Ваша скомпилированная eBPF-программа тоже содержит BTF-секцию, описывающую структуры, с которыми она *ожидает* работать.

2.  **Компилятор (Clang/LLVM):**
    При компиляции с флагом `-g` Clang не просто генерирует инструкцию "прочитать память по смещению +16", он записывает в ELF-файл **Relocation Record** (запись о перемещении).
    *   *Смысл записи:* "В этой инструкции программист хотел прочитать поле `pid` структуры `task_struct`".

3.  **Загрузчик (Libbpf):**
    Это библиотека в Userspace, которая загружает байт-код в ядро.
    *   В момент загрузки (Load Time) `libbpf` берет BTF из вашей программы и BTF из `/sys/kernel/btf/vmlinux`.
    *   Он сравнивает их. Если в ядре поле `pid` сместилось (из-за CONFIG_PREEMPT или версии ядра), `libbpf` **патчит** байт-код вашей программы прямо в памяти перед отправкой в ядро, подставляя правильное смещение.

### 4.2. Механизм Field Relocation (Пример)

Разберем на конкретном примере, как работает "магия" перемещения полей.

**Сценарий:** Вы читаете `task->state`.
*   На машине разработчика (Kernel A): поле `state` находится по смещению **16** байт.
*   На проде (Kernel B): поле `state` находится по смещению **24** байта (потому что добавили новое поле перед ним).

**Процесс:**
1.  **Compilation:** Вы пишете `t->state`. Clang генерирует инструкцию `LDW R1, [R2 + 16]` (загрузить слово со смещением 16). Но он также добавляет метаданные: *"Инструкция по offset X ссылается на `task_struct->state`"*.
2.  **Startup:** Ваше приложение запускается на Kernel B.
3.  **Libbpf Patching:**
    *   `libbpf` видит намерение: нужен `task_struct->state`.
    *   Смотрит в `/sys/kernel/btf/vmlinux` текущего ядра.
    *   Находит `struct task_struct` и видит, что `state` теперь по смещению **24**.
    *   **Переписывает инструкцию:** `LDW R1, [R2 + 16]` превращается в `LDW R1, [R2 + 24]`.
4.  **Verification:** Патченный код загружается в ядро. Верификатор видит корректный доступ.

### 4.3. `vmlinux.h`: Конец `#include <linux/sched.h>`

Раньше вы подключали системные заголовки, которые конфликтовали с заголовками glibc и ломались от версии к версии.
В CO-RE вы генерируете **один** заголовочный файл `vmlinux.h`, содержащий **все** типы данных ядра.

```bash
# Генерация заголовка из текущего ядра
bpftool btf dump file /sys/kernel/btf/vmlinux format c > vmlinux.h
```

В коде вы просто пишете `#include "vmlinux.h"`. Поскольку `libbpf` все равно подстроит смещения, вам не важно, что `vmlinux.h` сгенерирован на ядре 5.15, а запускаетесь вы на 6.2. Главное — чтобы имена полей совпадали.

### 4.4. Обработка изменений API (Expert Patterns)

Что если поле не просто сдвинулось, а **исчезло** или переименовалось? Как Staff Architect, вы должны писать код, который адаптируется, а не падает.

CO-RE предоставляет макросы для проверки существования полей (Kconfig-aware code).

**Пример: Чтение `start_time` процесса**
В старых ядрах поле называлось `start_time`, в новых может быть переименовано или структура вложена.

```c
#include "vmlinux.h"
#include <bpf/bpf_core_read.h>

SEC("kprobe/dummy")
int handle_kprobe(struct pt_regs *ctx) {
    struct task_struct *task = (void *)bpf_get_current_task();
    u64 start_time;

    // Паттерн: "Попробуй прочитать A, если нет - читай B"
    if (bpf_core_field_exists(task->start_boottime)) {
        // Код для новых ядер (ветка вычисляется при загрузке!)
        start_time = BPF_CORE_READ(task, start_boottime);
    } else {
        // Код для старых ядер
        start_time = BPF_CORE_READ(task, start_time);
    }
    
    // Libbpf удалит "мертвый" код (dead code elimination) 
    // перед загрузкой, так что оверхеда на if не будет.
    return 0;
}
```

### 4.5. Итог по CO-RE
Для эксперта CO-RE означает:
1.  **Portable Binaries:** Один бинарник работает на Ubuntu 20.04, Fedora 35 и Arch Linux.
2.  **No Devel Packages:** Не нужно монтировать `/usr/src/kernels` в поды Kubernetes.
3.  **Adaptive Code:** Возможность поддерживать разные версии структур данных в одном исходнике через `bpf_core_field_exists`.

## 5. Кейсы для архитектора

eBPF позволяет перейти от модели "Black Box" (мы видим только входы и выходы ядра) к модели "White Box" (мы программируем поведение ядра). Рассмотрим три сценария, где это меняет правила игры.

### 5.1. Networking: Sidecar-less Service Mesh (Cilium / Istio Ambient)

**Проблема классической архитектуры (Envoy/Sidecar):**
В Kubernetes с классическим Istio каждый под содержит контейнер-приложение и контейнер-прокси (Envoy).
Путь пакета при общении двух сервисов на одной ноде выглядит чудовищно длинным:
1.  App A пишет в сокет.
2.  Ядро обрабатывает TCP стек.
3.  `iptables` перехватывает пакет и делает DNAT на localhost (Loopback).
4.  Контекст переключается (Context Switch) в Userspace контейнера Envoy.
5.  Envoy парсит пакет, применяет политики.
6.  Envoy пишет в сокет.
7.  Пакет снова проходит стек TCP/IP ядра...
8.  ...и повторяет этот путь на стороне получателя.

Это вносит огромный Latency penalty (иногда +2-5ms) и потребляет CPU на переключение контекстов и копирование памяти.

**Решение на eBPF (Socket-level Redirection):**
Используя хуки типа `sock_ops` и `sk_msg`, eBPF позволяет реализовать **eBPF-based Datapath**.
*   **Механизм:** eBPF программа прикрепляется к сокетам. Когда приложение А пишет данные (`sendmsg`), eBPF перехватывает их **до** попадания в стек TCP/IP.
*   **Short-circuiting:** Если получатель (App B) находится на той же ноде, eBPF просто копирует данные из TX-очереди сокета А напрямую в RX-очередь сокета Б.
*   **Результат:** Мы обходим стек TCP/IP, фильтры iptables и Ethernet-фрейминг. Это работает со скоростью копирования памяти (`memcpy`).
*   **Архитектурный выигрыш:**
    *   Снижение Latency на 40-50%.
    *   Удаление Sidecar-контейнеров освобождает ресурсы (RAM/CPU) на кластере (минус 1 прокси на каждый под).

### 5.2. Observability: Проблема "Off-CPU" и корреляция (Pixie / Parca)

**Проблема:**
Классические профайлеры (CPU Profilers) показывают, где процессор *тратит* время (On-CPU). Но они слепы, когда ваше приложение *ждет* (Off-CPU).
*   *Сценарий:* Ваш сервис отвечает 500ms, но CPU usage = 1%. Где 499ms?
*   *Варианты:* Ожидание мьютекса (Lock contention), ожидание диска (I/O wait), ожидание ответа сети, или троттлинг планировщиком (CPU Throttling).

**Решение на eBPF:**
Мы вешаем хуки на переключения контекста планировщика ОС (`sched:sched_switch`).
1.  **Захват:** Когда процесс уходит с CPU, eBPF запоминает timestamp и *причину* (state: TASK_INTERRUPTIBLE vs TASK_UNINTERRUPTIBLE).
2.  **Возврат:** Когда процесс возвращается на CPU, мы вычисляем дельту времени.
3.  **Корреляция:** Мы собираем Stack Trace (через Frame Pointers или LBR) в момент ухода.

**Термин для эксперта: Stack Unwinding (Размотка стека).**
Чтобы понять, *какая* функция ждала, eBPF должен прочитать стек вызовов. В ядре это просто. В Userspace (Java/Node/Go) это сложно, так как JIT-компиляторы не всегда сохраняют Frame Pointers. Современные eBPF-профайлеры (Parca) используют DWARF debug info или JITdump, чтобы сопоставить адреса памяти с именами функций без остановки приложения.

### 5.3. Security: Runtime Enforcement и защита от TOCTOU

**Проблема:**
Классические антивирусы и инструменты безопасности (Falco в старых режимах) работают на основе анализа системных вызовов через `ptrace` или чтение логов аудита.
Это подвержено уязвимости **TOCTOU (Time-Of-Check to Time-Of-Use)**.
*   *Пример атаки:* Злоумышленник вызывает `open("legit_file")`. Антивирус проверяет имя файла — всё ок. Но между проверкой и реальным открытием файла (в микросекундное окно) злоумышленник подменяет путь в памяти на `open("/etc/shadow")`. Ядро откроет секретный файл, так как проверка уже пройдена.

**Решение на eBPF (LSM BPF — Linux Security Modules):**
Начиная с ядра 5.7, eBPF может прикрепляться к хукам LSM (там же, где работают SELinux и AppArmor).
*   **Механизм:** Хук срабатывает глубоко внутри ядра, непосредственно перед выполнением операции, и получает доступ к **внутренним структурам ядра** (инодам, объектам файлов), а не к строковым путям из userspace.
*   **Enforcement:** eBPF программа может вернуть код ошибки (например, `-EPERM`), и ядро **заблокирует** операцию.
*   **Пример (Tetragon):** Вы можете написать политику: "Запретить процессу `nginx` запускать `bash` или открывать сокеты на порт 22". Если `nginx` (скомпрометированный) попытается сделать `execve("/bin/bash")`, eBPF убьет этот syscall внутри ядра (SIGKILL). Это невозможно обойти, подменяя аргументы, так как мы контролируем исполнение в Ring 0.

### Сводная таблица для принятия решений

| Сценарий | Традиционный подход | eBPF подход | Выигрыш архитектора |
| :--- | :--- | :--- | :--- |
| **Service Mesh** | Sidecar Proxy (Envoy) в каждом поде | eBPF Redirect (Kernel level) | Latency, -50% RAM overhead |
| **Profiling** | Instrumentation (код внутри app) | Kernel Tracing (`perf_event`) | Zero-code changes, видит ядро + app |
| **Firewall** | iptables / IPVS | XDP (eXpress Data Path) | Обработка миллионов пакетов/сек до sk_buff |
| **Security** | Log scanning / ptrace | LSM Hooks | Блокировка 0-day атак в реальном времени |

**Совет Staff-инженеру:** При внедрении eBPF инструментов (Cilium, Pixie, Tetragon) всегда проверяйте версию ядра ваших узлов. Для полного функционала (LSM, RingBuffer, CO-RE) нужно ядро **5.10+** (лучше 6.x). На старых ядрах (RHEL7/CentOS7) магия превратится в тыкву.

## 6. Чек-лист уровня Expert

1.  **Tail Calls:** Что делать, если логика не влезает в лимит инструкций (1М)?
    *   *Ответ:* Использовать `bpf_tail_call`. Это аналог `execve` или `GOTO`. Программа вызывает другую eBPF-программу, заменяя текущий контекст. Полезно для модульности (цепочка парсеров протоколов).
2.  **Map Element Atomicity:** Гарантирует ли BPF атомарность обновления всей структуры в карте?
    *   *Ответ:* Нет. `bpf_map_update_elem` атомарен для хеш-карт, но если вы обновляете поля *по месту* (in-place update) через указатель — нужны `__sync_fetch_and_add` или спинлоки (в новых ядрах `bpf_spin_lock`).
3.  **Kernel Version Dependency:**
    *   XDP требует свежих драйверов.
    *   CO-RE требует ядро 5.x+ (желательно 5.8+).
    *   На RHEL 7 (Kernel 3.10) eBPF практически бесполезен (только cBPF или очень ограниченный eBPF).
4.  **Verifier limitations:** Почему верификатор ругается на "variable offset access"?
    *   *Ответ:* Для безопасности. Если вы читаете массив по индексу, который неизвестен на этапе компиляции, верификатор не может гарантировать границы. Вы должны добавить проверку: `if (idx >= MAX_SIZE) return;` — тогда верификатор поймет range и пропустит код.

### Заключение
eBPF дает вам суперсилу видеть и менять всё, что происходит в ОС. Но как Solution Architect, вы должны помнить:
*   Код в ядре должен быть быстрым.
*   Память ограничена.
*   Hooks могут меняться (используйте Tracepoints или CO-RE).
*   Безопасность (Verifier) — это не баг, а фича, которая спасает вас от падения всего кластера.

**TL;DR**: ZFS — это не просто файловая система, это гибрид LVM (Logical Volume Manager) и FS.
*   **CoW** гарантирует, что вы никогда не увидите поврежденный файл после отключения питания (прощай, `fsck`).
*   **Checksums** спасают от тихой порчи данных (bit rot), чего не делает аппаратный RAID.
*   **ARC** — это самый умный алгоритм кэширования в индустрии, уделывающий LRU.
*   **Практику:** Никогда не включайте дедупликацию без 128GB+ RAM и всегда тюньте `recordsize` под вашу базу данных.

ZFS (Zettabyte File System) — это стандарт де-факто для надежного хранения данных (NAS, SAN, LXD контейнеры, PostgreSQL ноды).

## 1. Copy-on-Write (CoW): Транзакционная модель

В классических файловых системах (Ext4, XFS, NTFS) используется модель **Overwrite-in-place**. Если вы меняете данные, головка диска идет в сектор X и перезаписывает магнитный домен. В этот момент (Window of Vulnerability) отключение питания приводит к тому, что в секторе находится "мусор" (часть старых данных, часть новых). Журнал (Journaling) спасает только *структуру* ФС, но не *содержимое* файла.

ZFS работает иначе. Она представляет собой **Дерево Меркла (Merkle Tree)**, где блоки связаны не просто адресами, а криптографическими хешами. CoW в ZFS — это не просто "копирование при записи", это механизм **Redirect-on-Write** в контексте глобальных транзакций.

#### 1.1. Механизм "Bubble Up" (Всплытие изменений)
Представьте файловую систему как дерево, где листья — это блоки данных (Data Blocks), а ветви — это косвенные блоки (Indirect Blocks), указывающие на детей. Корень дерева — **Uberblock**.

1.  **Аллокация (Allocation):** Приложение отправляет запрос на изменение 4KB данных внутри файла размером 10GB. ZFS не трогает старый блок на диске. Она выделяет **новый** сектор из списка свободных (Space map) и пишет туда новые данные.
2.  **Распространение хеша (Checksum Propagation):**
    *   У каждого блока есть "родитель" (Indirect Block), который хранит **Block Pointer (BP)** на этот блок.
    *   BP содержит: физический адрес (DVA), размер, сжатие и **контрольную сумму (Checksum)** ребенка.
    *   Поскольку адрес ребенка и его содержимое изменились, его хеш тоже изменился.
    *   Следовательно, мы должны обновить родительский блок, чтобы записать туда новый BP.
3.  **Рекурсивный подъем:**
    *   Поскольку мы изменили родительский блок, его собственный хеш тоже изменился.
    *   Мы вынуждены перезаписать его родителя (дедушку) в новое место.
    *   Этот процесс ("пузырек" изменений) поднимается до самого верха иерархии объектов.

#### 1.2. Transaction Groups (TXG) — Группировка транзакций
ZFS не делает это для каждого `write()` вызова (это убило бы производительность). Она использует **Transaction Groups (TXG)**.
Это аналог "коммитов" в базе данных, но для всей ФС.

Жизненный цикл TXG (обычно 5 секунд):
1.  **Open:** Принимает новые записи в RAM.
2.  **Quiescing (Замирание):** Закрывается для новых записей, готовится к сбросу.
3.  **Syncing:** Сбрасывается на диск.

Все изменения за 5 секунд (тысячи файлов) агрегируются в **одно** гигантское дерево изменений. CoW происходит пакетно.

#### 1.3. Атомарный перевод стрелок (The Uberblock Update)
Это кульминация процесса.
*   Когда все новые блоки данных и все новые блоки метаданных записаны на диск, у нас есть "параллельная вселенная" — новое дерево, на которое пока никто не ссылается. Старое дерево все еще валидно и доступно.
*   В массиве дисков есть зарезервированная область (128 масивов по 256 байт) для **Uberblocks**.
*   ZFS записывает новый Uberblock, который указывает на *новый* корень дерева (root block pointer) с самым высоким номером транзакции (`txg`).
*   **Момент истины:** Это одна атомарная операция записи (обычно 1 сектор).
    *   До записи Uberblock: система при монтировании видит состояние на момент времени $T$.
    *   После записи: система видит состояние $T+1$.
    *   **Нет промежуточного состояния.** Понятие "битая файловая система" в ZFS отсутствует архитектурно (при исправном железе).

#### 1.4. Пример для наглядности
Представьте книгу (файл), у которой есть оглавление (Indirect blocks).
**Задача:** Изменить страницу 42.

*   **Классическая ФС:** Берет ластик, стирает страницу 42 и пишет новый текст. Если ударила молния — на странице грязное пятно.
*   **ZFS (CoW):**
    1.  Пишет новую версию страницы 42 на чистом листе бумаги. Старая страница 42 остается в книге.
    2.  Копирует оглавление, меняя в нем строчку "Страница 42" так, чтобы она указывала на новый лист.
    3.  Меняет обложку книги, чтобы она ссылалась на *новое* оглавление.
    4.  Старая обложка, старое оглавление и старая страница 42 теперь "мусор" (если на них нет снапшота) и позже будут переработаны.

#### 1.5. Архитектурные последствия (Trade-offs)
Как Staff Architect, вы платите за надежность следующую цену:

1.  **Фрагментация свободного пространства (Free Space Fragmentation):**
    Со временем диск превращается в "швейцарский сыр". Свободные блоки разбросаны хаотично. Найти непрерывный кусок для записи нового большого файла становится трудно. Это замедляет *запись* (аллокатор тратит CPU на поиск места).
2.  **Фрагментация файлов при чтении:**
    Даже если вы пишете файл последовательно, но "апдейтами" (как базу данных), блоки файла будут разбросаны по всему диску из-за CoW. Последовательное логическое чтение (`seq scan`) превращается в случайное физическое чтение (`random IO`).
    *   *Решение:* Использовать SSD (им все равно на random read) или агрессивно кэшировать в ARC/L2ARC.
3.  **Copy-on-Write Penalty:**
    На запись 4 КБ данных мы можем записать 16-32 КБ метаданных (родитель, дедушка, прадедушка...).
    *   *Смягчение:* TXG амортизирует это, объединяя обновления метаданных для множества файлов.

### Резюме раздела
CoW в ZFS — это механизм перевода состояния системы из одного консистентного состояния в другое через построение параллельного дерева Меркла и атомарное переключение корневого указателя (Uberblock). Это обеспечивает 100% гарантию целостности при сбоях питания, но создает нагрузку в виде фрагментации и оверхеда на метаданные.

## 2. Checksums и Merkle Tree: Архитектура целостности данных

В традиционных файловых системах (Ext4, XFS, NTFS) и аппаратных RAID-массивах целостность данных — это *допущение*. Вы верите диску на слово. ZFS исходит из парадигмы **Zero Trust** по отношению к физическому носителю.

### 2.1. Проблема: Тихая порча данных (Silent Data Corruption)
Чтобы понять решение, нужно определить врага. Аппаратные сбои бывают двух типов:
1.  **Reported Error:** Диск говорит «I/O Error», контроллер видит проблему. Это легко.
2.  **Silent Error (Bit Rot):**
    *   **Bit Flip:** Космический луч или деградация магнитного слоя меняет 0 на 1. Диск читает это как валидные данные, RAID контроллер не видит ошибки (четность сходится, если пересчитать её по факту чтения).
    *   **Phantom Write / Misdirected Write:** Контроллер послал команду «Запиши X в сектор 100». Диск подтвердил запись, но *не записал* ничего (firmware bug) или записал в сектор 101.
    *   **Результат:** Вы читаете файл, он открывается, но внутри мусор. Бэкапы тоже содержат мусор. Вы узнаете об этом через год.

### 2.2. Решение: Parent-Side Checksumming (Хеширование на стороне родителя)
Это фундаментальное отличие ZFS.

*   **Классический подход (Block Checksum):** Если файловая система (например, Btrfs или современные реализации Ext4) хранит чексумму *вместе* с данными (в том же блоке или рядом), это не спасает от *Phantom Write*. Если диск записал "не туда" валидный блок с валидной чексуммой, проверка пройдет успешно, но данные будут не теми, что вы ожидали.
*   **Подход ZFS (Parent Pointer):** Чексумма блока хранится не в нем самом, а в **указателе на этот блок** (Block Pointer), который находится в родительском узле.
    *   Когда ZFS хочет прочитать блок A, она сначала читает родителя, узнает ожидаемый хеш $H(A)$, затем читает блок A, вычисляет его хеш $H'(A)$ и сравнивает.
    *   Это делает невозможным подмену данных или запись "не туда".

### 2.3. Структура Merkle Tree (Дерево Меркла)
ZFS организует все данные в виде гигантского хеш-дерева.

1.  **Data Blocks (L0):** Листья дерева. Содержат ваши файлы.
2.  **Indirect Blocks (L1...Ln):** Узлы метаданных. Содержат массивы `Block Pointers` (BP), указывающих на детей. Каждый BP содержит:
    *   Адрес на диске.
    *   Физический размер (сжатый) и логический размер.
    *   **Checksum** (SHA-256, Fletcher4) содержимого дочернего блока.
3.  **Uberblock:** Корневой узел всей файловой системы.
    *   В Uberblock содержится хеш корневого узла дерева.
    *   **Свойство:** Изменение одного бита в любом файле на дне иерархии каскадно меняет хеши всех родителей вплоть до Uberblock.
    *   Это гарантирует, что состояние файловой системы криптографически верифицируемо и атомарно. Нельзя "подделать" часть дерева незаметно для корня.

### 2.4. Алгоритмы хеширования и производительность
ZFS позволяет выбирать алгоритм (`zfs set checksum=...`).

*   **Fletcher4 (Default):** Очень быстрый алгоритм, разработанный специально для ZFS. Устойчив к типичным паттернам ошибок дисков (обнуление секторов, перестановка байт). Оверхед CPU близок к нулю. Подходит для 99% задач.
*   **SHA-256:** Криптографический хеш. Исключает коллизии (случайное совпадение хешей разных данных). Требует инструкций CPU (SHA extensions). Используется, когда нужна абсолютная гарантия или включена дедупликация (где хеш используется как ключ поиска).
*   **Edon-R / Skein:** Высокопроизводительные современные хеши (доступны в новых версиях OpenZFS).

**Совет Практика:** Оставьте `on` (Fletcher4) для баз данных и файловых шар. Включайте `sha256` только если у вас параноидальные требования к безопасности или вы используете дедупликацию.

### 2.5. Self-Healing (Самолечение) в действии
Вот сценарий, демонстрирующий мощь ZFS. Допустим, у нас `Mirror` (зеркало) из двух дисков: Disk A и Disk B.

1.  Приложение запрашивает чтение блока `X`.
2.  ZFS читает указатель на `X`, видит ожидаемый хеш `1234`.
3.  ZFS читает блок `X` с **Disk A** (балансировщик нагрузки выбрал его).
4.  ZFS считает хеш прочитанных данных. Получает `5678`.
5.  **Checksum Mismatch!** ZFS понимает, что Disk A вернул мусор.
6.  **Вмешательство (Healing):** ZFS автоматически обращается к **Disk B** за тем же блоком.
7.  ZFS читает с Disk B, хеш равен `1234`. Данные корректны.
8.  **Repair:** ZFS отдает приложению верные данные (приложение даже не заметило задержки).
9.  **Writeback:** ZFS *тут же* перезаписывает битый сектор на **Disk A** правильными данными из памяти, исправляя ошибку на физическом уровне.

*В Hardware RAID контроллер просто отдал бы вам данные с Disk A, если он не сообщил об ошибке чтения.*

### 2.6. Scrubbing (Активная проверка)
Самолечение работает при чтении. Но что, если вы записали архив 5 лет назад и не читали его? Там мог случиться bit rot.
Для этого существует процедура **Scrub**.
*   `zpool scrub tank`
*   ZFS обходит все дерево Меркла, считывает *каждый* блок данных, сверяет контрольные суммы и автоматически чинит ошибки, используя избыточность.
*   **Рекомендация:** Настраивайте `systemd timer` или `cron` на выполнение scrub раз в 2-4 недели. Для NVMe массивов — чаще.

### 2.7. "IT Mode" и опасность Hardware RAID
Почему ZFS требует **HBA** (Host Bus Adapter) в режиме IT Mode (Initiator Target), а не RAID-контроллер?
*   RAID-контроллер скрывает физическую геометрию дисков и сам пытается управлять ошибками.
*   Если диск начинает сыпаться, контроллер может долго пытаться восстановить сектор (Time-limited error recovery), вызывая фризы системы, в то время как ZFS просто взяла бы данные с зеркала за миллисекунду.
*   ZFS нужна *прямая видимость* SMART-атрибутов и сырых секторов для корректной работы Self-Healing.
*   **Итог:** ZFS поверх Hardware RAID — это потеря функционала самолечения и риск потери всего пула при сбое контроллера.

## 3. Snapshots и Clones

В мире ZFS снапшот — это не копия данных. Это **фиксация состояния метаданных** (Block Pointers) на определенный момент времени (Transaction Group — TXG). Поскольку ZFS использует Copy-on-Write, старые данные никогда не перезаписываются. Создание снапшота — это просто инструкция файловой системе: «Не освобождай блоки, на которые ссылались в момент времени $T$, даже если мы их "удалим" в будущем».

#### 3.1. Механика: Deadlists и Birth Time
Чтобы понять эффективность снапшотов, нужно заглянуть под капот:
*   **Birth Time:** Каждый блок в ZFS хранит метку времени (TXG), когда он был создан.
*   **Snapshot Creation:** Это атомарная операция $O(1)$. Мы просто копируем указатель на текущий корневой узел (Uberblock) и сохраняем его под именем снапшота. Место на диске не тратится.
*   **Deadlist (Список мертвецов):** У каждого снапшота есть уникальная структура — *deadlist*.
    *   Когда вы удаляете файл в "живой" файловой системе, ZFS проверяет: "Нужен ли этот блок какому-либо снапшоту?".
    *   Если да -> Блок добавляется в *deadlist* "живой" системы (он мертв для нас, но жив для снапшота). Физическое место не освобождается.
    *   Если нет -> Блок помечается свободным.
*   **Space Usage:** Снапшот начинает занимать место (Referenced space) только тогда, когда данные в основной ФС изменяются или удаляются. Размер снапшота = объем данных, уникальных для него (diverged data).

#### 3.2. Snapshot vs Clone: Читаем или Пишем?
Многие путают эти понятия. Различие фундаментально:

1.  **Snapshot (Снимок):**
    *   **Read-Only:** Вы не можете изменить ни байта внутри снапшота.
    *   **Доступ:** Обычно доступен в скрытой директории `.zfs/snapshot/snap_name/` прямо в корне файловой системы (если свойство `snapdir=visible`).
    *   **User Self-Service:** Пользователи могут сами восстановить удаленный файл (`cp .zfs/snapshot/yesterday/file.txt .`), не дергая админа.

2.  **Clone (Клон):**
    *   **Read-Write:** Это полноценная файловая система, созданная на базе снапшота.
    *   **Zero-Copy:** При создании клон не занимает места. Он делит все блоки с родительским снапшотом.
    *   **Divergence:** Место тратится только на *новые* данные, которые вы запишете в клон.
    *   **Зависимость:** Клон жестко зависит от родительского снапшота. Вы не можете удалить снапшот, пока у него есть живой клон (сначала нужно сделать `zfs promote` или удалить клон).

#### 3.3. Репликация: `zfs send` / `zfs receive`
Это "киллер-фича" для Disaster Recovery (DR). В отличие от `rsync`, который сканирует миллионы файлов (`stat()`), ZFS работает с потоком метаданных.

*   **Full Stream:** `zfs send pool/fs@snap1`. Передает все блоки, существующие в `snap1`.
*   **Incremental Stream:** `zfs send -i snap1 pool/fs@snap2`.
    *   ZFS сравнивает *birth time* блоков.
    *   В поток попадают только блоки, рожденные *после* создания `snap1` и *до* `snap2`.
    *   Это позволяет передавать гигабайтные изменения за миллисекунды, игнорируя неизмененные терабайты данных.
*   **Replication Stream (`-R`):** Передает всю иерархию датасетов, их свойства, снапшоты и клоны.

#### 3.4. Продвинутые операции: Rollback, Promote, Bookmarks

*   **Rollback (Откат):**
    Мгновенный возврат файловой системы к состоянию снапшота.
    *   *Опасность:* Все изменения (и более новые снапшоты), сделанные *после* целевого снапшота, безвозвратно уничтожаются.
*   **Promote (Продвижение клона):**
    Превращает клон в независимую файловую систему, а "родительскую" ФС делает зависимой. Используется, когда клон становится "мастером" (например, при переключении на новую версию БД).
*   **Bookmarks (Закладки):**
    *   *Проблема:* Чтобы сделать инкрементальный `send`, вам нужно хранить снапшот-источник (`snap1`) на диске. Это занимает место.
    *   *Решение:* Создать закладку (`#bookmark1`) и удалить снапшот. Закладка не держит данные (место освобождается), но позволяет использовать её как точку отсчета для `zfs send -i #bookmark1 ...`.

#### 3.5. Практический пример: Мгновенный CI/CD для баз данных

Представьте, что у вас есть Production база данных PostgreSQL размером 5 ТБ. Разработчикам нужна копия для тестов миграции.

**Классический подход:**
1.  Dump & Restore: Занимает 10+ часов.
2.  Разработчики ждут. Место на диске удваивается (5 ТБ -> 10 ТБ).

**Подход ZFS (Thin Provisioning):**
1.  **Snapshot:** Делаем снапшот продакшена (`zfs snapshot tank/pg_prod@now`). Время: 0.1 сек.
2.  **Clone:** Создаем 10 клонов для 10 разработчиков (`zfs clone tank/pg_prod@now tank/pg_dev_1 ...`). Время: 0.5 сек.
3.  **Result:** У каждого разработчика своя *независимая* база на запись.
    *   Занятое место: 0 байт (изначально).
    *   Если разработчик испортил базу -> `zfs destroy` клона и создание нового за 1 секунду.
4.  **Promote:** Если миграция в клоне прошла успешно, мы можем "продвинуть" его, сделав новым продакшеном, а старый прод оставить как архив.

**Резюме для архитектора:** Используйте снапшоты для RPO (Recovery Point Objective) близкого к нулю и клоны для создания эфемерных сред. Это меняет парадигму работы с данными с "копирования" на "управление указателями".

## 4. Иерархия кэширования: ARC, L2ARC, ZIL

ZFS использует многоуровневую архитектуру памяти, которая принципиально отличается от страничного кэша Linux (Linux Page Cache). Понимание того, как данные перетекают между этими уровнями, критично для настройки производительности баз данных и виртуализации.

### 4.1. ARC (Adaptive Replacement Cache) — «Умнее, чем LRU»
В большинстве файловых систем используется алгоритм **LRU** (Least Recently Used): старые данные вытесняются новыми. Проблема LRU — **Scan Resistance**. Если вы запустите `backup` или `grep` по терабайтному файлу, LRU вымоет из кэша все "горячие" данные вашей базы данных, заменив их одноразовым мусором.

ARC (разработанный в IBM) решает эту проблему, разделяя кэш на 4 списка.

**Анатомия ARC:**
1.  **M(R)U List (Recent):** Данные, к которым обратились *недавно* (1 раз).
2.  **M(F)U List (Frequent):** Данные, к которым обратились *более 1 раза* (частые).
3.  **Ghost List Recent:** Метаданные (только заголовки) тех блоков, которые были недавно вытеснены из MRU.
4.  **Ghost List Frequent:** Метаданные тех блоков, которые были вытеснены из MFU.

**Алгоритм адаптации:**
*   Если происходит попадание в кэш (Hit) в **Ghost List Recent**, ZFS понимает: "Ага, если бы мой список MRU был чуть больше, я бы не промахнулся". Система увеличивает долю памяти для MRU.
*   Если попадание в **Ghost List Frequent**, система увеличивает долю MFU.
*   **Результат:** При последовательном сканировании (backup) новые блоки попадают в MRU, быстро вылетают в Ghost MRU, но *не* вытесняют ценные данные из MFU, так как сканирование редко обращается к одному блоку дважды.

**Критическая особенность для практика:**
ARC в ZFS хранит данные в **сжатом виде** (если включено `compression=lz4/zstd`).
*   *Пример:* У вас 64 GB RAM под ARC. Если коэффициент сжатия 2.0x, вы фактически кэшируете 128 GB данных. Linux Page Cache хранит только несжатые страницы.

### 4.2. L2ARC (Level 2 ARC) — Расширение, а не замена
L2ARC — это кэш на чтение (Read Cache), расположенный на быстрых SSD/NVMe. Он заполняется данными, которые вытесняются из ARC (Eviction policy).

**Главная архитектурная ловушка ("The L2ARC Header Penalty"):**
L2ARC — это не просто "черный ящик". Чтобы ZFS знала, какие данные лежат на SSD, она должна хранить **таблицу адресации (Headers)** в оперативной памяти (ARC).
*   **Математика:** Один заголовок занимает ~70 байт в RAM.
*   **Сценарий:** Вы выделили 1 TB SSD под L2ARC и используете дефолтный `recordsize=4K`.
    *   Количество записей: $1024 \text{ GB} / 4 \text{ KB} = 262,144,000$ записей.
    *   Потребление RAM: $262 \text{ M} \times 70 \text{ bytes} \approx 18.3 \text{ GB}$.
*   **Катастрофа:** Вы добавили SSD, чтобы ускорить систему, но потратили 18 GB драгоценной RAM на заголовки. В результате **размер полезного ARC уменьшился**, и производительность системы упала.
*   **Решение:**
    1.  Не использовать L2ARC, если RAM < 64 GB.
    2.  Использовать L2ARC только для данных с большим `recordsize` (напр., 64K+), чтобы уменьшить количество заголовков.
    3.  Включить **Compressed ARC**, чтобы заголовки занимали меньше места (доступно в OpenZFS 2.0+).

**Persistent L2ARC:** С версии OpenZFS 2.0 кэш L2ARC сохраняется после перезагрузки. Раньше "прогрев" кэша на 1 TB мог занимать часы, теперь он доступен сразу.

### 4.3. ZIL (ZFS Intent Log) и SLOG — Управление латентностью записи

Здесь часто возникает путаница между понятиями "Журнал" и "Устройство".

*   **TXG (Transaction Group):** ZFS — это *транзакционная* ФС. Все изменения (запись, удаление) сначала накапливаются в оперативной памяти в открытой транзакционной группе. Раз в 5 секунд (по умолчанию) группа закрывается и сбрасывается на диск. Это превращает случайную запись (Random Write) в последовательную (Sequential Write).
    *   *Риск:* Если питание пропадет, последние 5 секунд данных исчезнут.

*   **Sync Writes (`O_SYNC` / `fsync`):** Базы данных (PostgreSQL, MySQL) не могут позволить себе потерять 5 секунд. Они требуют гарантии записи (`fsync`).
    *   При `fsync` ZFS обязана записать данные на энергонезависимый носитель *немедленно*, не дожидаясь закрытия TXG.
    *   Эти данные пишутся в специальную структуру на диске — **ZIL**.

*   **Double Write Penalty:** При синхронной записи данные пишутся **дважды**:
    1.  В ZIL (чтобы быстро ответить приложению "Saved!").
    2.  Позже, в составе TXG, в основное место хранения (чтобы сохранить структуру пула).

*   **SLOG (Separate Intent Log):** По умолчанию ZIL находится на тех же медленных дисках, что и данные. Это убивает производительность БД (latency записи становится равным latency HDD).
    *   Мы выделяем отдельное устройство (SLOG) — обычно Intel Optane или Enterprise NVMe с конденсаторами (PLP).
    *   ZIL пишется на SLOG. Это происходит очень быстро.
    *   Приложение получает `ACK` мгновенно.
    *   **Важно:** SLOG — это устройство **только на запись** (Write-only). Данные из него читаются *только* в одном случае: если сервер упал по питанию. При загрузке ZFS читает ZIL и "проигрывает" потерянные транзакции. В штатном режиме SLOG не читается никогда.

**Пример архитектурного решения:**
*   **БД:** PostgreSQL OLTP.
*   **Диски данных:** 6x HDD RAID-10 (хорошо для объема, плохо для Random IO).
*   **Проблема:** `COMMIT` транзакции длится 10-20 мс (ждет вращения шпинделя HDD для записи в ZIL).
*   **Решение:** Добавляем зеркало (Mirror) из двух Intel Optane 16GB в качестве SLOG.
*   **Результат:** `COMMIT` падает до 0.1 мс. Общая пропускная способность HDD не меняется, но **Latency** транзакций улучшается в 100 раз.

### Резюме раздела
1.  **ARC:** Это не LRU. Он защищен от вымывания при бэкапах. Он сжатый.
2.  **L2ARC:** Ест RAM. Будьте осторожны с блоками 4K. Нужен только если ARC уже заполнен рабочим сетом (Working Set).
3.  **SLOG:** Нужен только для синхронной записи (БД, NFS, iSCSI). Не ускоряет асинхронную запись (копирование файлов). Читается только после аварии.

## 5. Тюнинг и "Подводные камни": От дефолта к High-Performance

ZFS изначально создавалась для медленных вращающихся дисков (HDD) и огромных массивов. В эру SSD/NVMe дефолтные настройки часто вредны.

### 5.1. `recordsize`: Главный рычаг производительности
Это не "размер блока" в привычном смысле (как 4KB в ext4). Это **максимальный логический размер блока** файла. ZFS использует *переменный* размер блока. Файл размером 1 КБ займет 1 блок по 512 байт (или 4KB, зависит от `ashift`). Но файл размером 10 ГБ будет нарезан на куски по `recordsize`.

*   **Дефолт:** `128K`.
*   **Проблема (Read-Modify-Write Penalty):**
    Представьте, что вы запускаете PostgreSQL. База пишет страницы по **8KB**.
    Если `recordsize=128K`, то для изменения одной страницы БД (8KB) ZFS должна:
    1.  Прочитать 128KB с диска (Read).
    2.  Изменить 8KB в памяти (Modify).
    3.  Посчитать новую чексумму для 128KB.
    4.  Записать новые 128KB на диск (Write).
    **Результат:** Write Amplification **x16**. Вы убиваете SSD ресурс и увеличиваете Latency в 16 раз.

*   **Решение для БД (Postgres/MySQL/Oracle):**
    Выставляйте `recordsize` равным размеру страницы БД.
    ```bash
    zfs set recordsize=8k tank/postgres  # Для PostgreSQL
    zfs set recordsize=16k tank/innodb   # Для MySQL/InnoDB
    ```
    *Нюанс:* Это также улучшает эффективность кэша (ARC). В кэше будут лежать только "горячие" 8KB, а не холодные хвосты по 120KB.

*   **Решение для BitTorrent / Backups / Media:**
    Увеличивайте до 1MB (максимум для старых ZFS) или 16MB (современный OpenZFS).
    ```bash
    zfs set recordsize=1M tank/media
    ```
    Это снижает фрагментацию, улучшает степень сжатия (алгоритм видит больше контекста) и снижает нагрузку на IOPS (меньше метаданных).

### 5.2. `ashift`: Проклятие выравнивания (Alignment)
Этот параметр задает физический размер сектора диска: $2^{\text{ashift}}$ байт.
*   **ashift=9** $\to$ 512 байт.
*   **ashift=12** $\to$ 4096 байт (4KB).
*   **ashift=13** $\to$ 8192 байт (8KB).

*   **Подводный камень:** Большинство современных SSD сообщают ОС, что у них сектор 512 байт (512e — emulation), чтобы поддерживать совместимость с Windows XP. Это **ложь**. Физически там 4KB или 8KB страницы (NAND Flash).
*   **Сценарий катастрофы:** Вы создали пул с дефолтным (автодетект) `ashift=9`. Вы пишете 4KB данных. ZFS посылает 8 команд по 512 байт. Контроллер SSD должен прочитать 4KB флеш-страницу, изменить кусочек, записать... (RMW внутри SSD).
    **Итог:** Write Amplification x2-x8, падение скорости записи в разы, мгновенный износ SSD.
*   **Imperative:** Всегда указывайте `ashift` вручную при создании пула. Изменить его на лету **нельзя** (только уничтожение пула).
    ```bash
    zpool create -o ashift=12 tank mirror /dev/nvme0n1 /dev/nvme0n2
    ```
    *Для некоторых Samsung SSD имеет смысл `ashift=13`.*

### 5.3. Дедупликация (Deduplication): Математика памяти
Включение `zfs set dedup=on` — самый быстрый способ убить производительность сервера.

*   **Механика:** ZFS хранит таблицу DDT (Deduplication Table): `SHA256 Hash` $\to$ `Physical Pointer`.
*   **Стоимость:** Каждая уникальная запись (record) требует примерно **320 байт** в RAM для DDT.
*   **Пример:** У вас файловое хранилище на 10 ТБ. `recordsize=4K` (худший случай).
    $$ \frac{10 \cdot 10^{12}}{4096} \approx 2.44 \cdot 10^9 \text{ блоков} $$
    $$ 2.44 \cdot 10^9 \times 320 \text{ bytes} \approx \textbf{781 GB RAM} $$
    Вам нужно 781 ГБ оперативной памяти *только* для таблицы дедупликации.
*   **Что будет, если RAM не хватит:** DDT вытесняется на диск. **Каждая** запись на диск требует случайного чтения DDT с диска, чтобы проверить хеш. Скорость записи падает с 500 МБ/с до 10-50 КБ/с. Пул становится неотзывчивым ("brick").

*   **Вердикт Практика:** Используйте **LZ4 Compression** (`zfs set compression=lz4`). Это бесплатно по CPU и дает выигрыш 1.5x-2x. Дедупликацию включайте только если у вас:
    1.  VDI (образы виртуалок), где 90% данных идентичны.
    2.  Есть Optane/NVMe для "Special VDEV" (Deduplication vdev), куда можно вынести DDT.

### 5.4. `xattr=sa`: Ускорение Linux
В ZFS на Linux (ZoL) атрибуты файлов (ACL, SELinux labels) по умолчанию хранятся в скрытых директориях (Directory-based xattrs).
*   **Проблема:** Любое обращение к файлу вызывает дополнительные чтения (seek) для поиска атрибутов. `ls -la` на директории с 1000 файлов тормозит.
*   **Решение:**
    ```bash
    zfs set xattr=sa tank
    ```
    Это заставляет ZFS хранить атрибуты прямо в inode (System Attributes), как это делают ext4/xfs. Ускорение операций с метаданными — колоссальное.

### 5.5. Топология: IOPS масштабируется по VDEV
Многие думают: "У меня 10 дисков в RAIDZ2, значит, скорость записи будет как у 10 дисков". **Нет.**

*   **Аксиома ZFS:** IOPS (операции ввода-вывода в секунду) пула равен сумме IOPS его **VDEV** (виртуальных устройств).
*   **RAIDZ (любой ширины):** Это **один** VDEV.
    *   Пул из 10 HDD в RAIDZ2 имеет IOPS на запись, равный IOPS **одного** HDD (~150 IOPS). Потому что блок данных нарезается и пишется на все диски синхронно.
*   **Mirrors (Striped Mirrors / RAID10):**
    *   Пул из 10 HDD, разбитых на 5 пар зеркал (5 VDEV).
    *   IOPS = $5 \times \text{IOPS одного диска}$.
*   **Resilvering (Ребилдинг):**
    *   Если умирает диск в RAIDZ (широком, напр. 10 дисков), перестроение нагружает **все** диски, читая метаданные. Это может длиться днями, и нагрузка может убить еще один диск.
    *   В Mirrors перестроение — это просто последовательное копирование с выжившего брата. Быстро и безопасно.
*   **Рекомендация:** Для баз данных и виртуализации — **только Mirrors**. Для бэкапов и "холодных" архивов — **RAIDZ2/Z3**.

### 5.6. `atime`: Лишние записи
Старая добрая классика Linux. Каждый раз, когда вы *читаете* файл, файловая система обновляет время доступа (`atime`), создавая *запись*.
*   **Решение:**
    ```bash
    zfs set atime=off tank
    ```
    (Или `relatime=on`, если вам нужно знать, читали ли файл после изменения, но для 99% серверов `off` безопасен).

### Итоговый пример создания пула для PostgreSQL
Вы инженер, вам дали сервер с 6 NVMe дисками по 2TB для базы данных.

**Плохо (Дефолт):**
`zpool create tank raidz2 nvme0 nvme1 ...` (Медленная запись, один VDEV, низкий IOPS).

**Экспертно (High-Performance):**
```bash
# 1. Создаем пул из 3 зеркал (Striped Mirrors) с правильным выравниванием
zpool create -o ashift=12 tank mirror nvme0n1 nvme1n1 mirror nvme2n1 nvme3n1 mirror nvme4n1 nvme5n1

# 2. Настраиваем корневой датасет
zfs set compression=lz4 tank
zfs set xattr=sa tank
zfs set atime=off tank

# 3. Создаем датасет под БД с правильным recordsize
zfs create -o recordsize=8k -o logbias=throughput tank/postgres
# logbias=throughput подсказывает ZFS не дублировать данные в ZIL, если они уже идут в основной пул, полагаясь на групповую запись. Но лучше иметь SLOG.
```

### Заключение
ZFS — это не про скорость "в попугаях" (хотя с ARC она быстра). Это про **Data Integrity** и удобство управления.
*   Для файловых помоек: RAIDZ2 + recordsize=1M + Compression=ZSTD.
*   Для баз данных: Mirrors + recordsize=DatabasePageSize + Compression=LZ4 + NVMe SLOG.
